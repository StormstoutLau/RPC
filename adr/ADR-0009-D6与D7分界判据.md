## 范围声明（先于一切）

**本决策仅约束"D6 / D7 之间的层级归属"，不改变 D6 或 D7 任何一侧的内部实现。**

它是一层**归属判据**：回答"某个能力/场景应落在哪一侧"。
显式排除：D7 内部的协议、权限模型、编排与多轮机制（归 `D7-P0-2` / `D7-P2` / `D7-P3` / `D7-P4`）；
以及"同一产物上由谁复核"这一正交问题（归 `D7-P0-3` 的两条判据）。

---

## 背景（Context）

### 触发实例（E3）

1. **边界只存在于"归属结果"里，不存在于"可求值的规则"里**：D6 与 D7 的职责划分在既有实现中
   以**事后归属**的方式界定 ⇒ **新增场景无法在派发环节自动落槽**，只能靠人工经验归档。
2. **事后复核一致 ≠ 有可复用的判定链**：既有 **14 项**"归给 D7"的条目虽经事后复核**结论全部一致**，
   但**没有一条能被复用的判定规则**——一致是"人看出来的"，不是"判据算出来的"。
3. **灰色地带两侧均可辩解**：判官抽检、跨站派发、受理阶段的协商回环等，在 D6 与 D7 两侧
   **都能讲出理由** ⇒ 缺乏唯一答案时会**被两边同时漏掉或重复建设**。

### 根因（E4）

不是"没人做归属"，而是**判据层缺失**：职责边界的判定链从未被显式化为"在受理完成、产出开始前
即可独立求值"的规则 ⇒ 判定与产出耦合成"看产物内容定归属"，而这一步**只能人来做、且不可复现**。

## 决策（Decision）

**在条件"判据可机械求值"下，采用三条判据 `B-1` / `B-2` / `B-3` 作为 D6/D7 的**唯一**分界依据，
而不是保留事后人工归属、也不是以"是否跨站"这类形态特征代替。**

### 1. 三条判据（原文照抄，不改写其含义）

- **B-1**：是否需要一个"**非产出方**"的主体来给结论？**是 ⇒ D7**
- **B-2**：是否在同一产物上需要**多轮往返**（改完再审）？**是 ⇒ D7**
- **B-3**：是否只是"**这一次派发内部**"的质量门（判官抽检、accept 判据）？**是 ⇒ D6**

### 2. 求值规则（互斥且穷尽）

任一派发场景对三条判据求值后：

- **`B-1=是` 或 `B-2=是` ⇒ 归 D7**；
- **`B-3=是` 且 `B-1=否` 且 `B-2=否` ⇒ 归 D6**。

### 3. 灰色地带归属表（8 项，逐项裁定）

| 灰色项 | 现状归属 | 裁定（留 D6 / 归 D7） | 依据（判据取值） |
|---|---|---|---|
| 判官抽检（证据链断言 + judge 校准） | D6 | 留 D6 | `B-1=否、B-2=否、B-3=是` |
| 受理阶段的协商回环（评审 ⇄ 修订） | D6（已实现） | 留 D6 | `B-1=否、B-2=否、B-3=否`（发生在受理阶段，属管理员↔需求方，非产出复核层） |
| 需求方验收签收 | D6（已实现） | 留 D6 | `B-1=否、B-2=否、B-3=否`（是 D7 接入点，复用同一状态语义，不新造） |
| 跨站派发 | D6 | 留 D6 | `B-1=否、B-2=否、B-3=否`（跨站只是派到哪个站，主体仍只有 1 个） |
| 站间互审（`--peer`） | D7 | 归 D7 | `B-1=是、B-2=是、B-3=否` |
| 异构复审编排 | D7 | 归 D7 | `B-1=是、B-2=是、B-3=否`（缺的正是编排层） |
| 多轮续聊（审→改→再审） | D7 | 归 D7 | `B-1=否、B-2=是、B-3=否` |
| agent 派生边表 / 多 agent 树 | D7 | 归 D7 | `B-1=是、B-2=是、B-3=否`（⚠ 九项目实测中**无一提出此需求**，无真实诉求支撑） |

**自洽检查**：上表所有行的裁定方向与判据取值一致 —— `B-1=是` 或 `B-2=是` 的行均裁定"归 D7"；
`B-3=是` 且 `B-1=否` 且 `B-2=否` 的行均裁定"留 D6"。**无冲突行**。

### 4. 复核既有归属（E3）

用这三条判据复核既有"归给 D7"的 **14 项**：**结论全部一致**，无一项应退回 D6 ——
它们要么命中 `B-1`（需要第二个主体给权限/结论/裁决），要么命中 `B-2`（需要多轮续聊/编排），
要么呈现跨站形态（架构/自环盲区）从而**隐含 `B-1`**。
⇒ D6 的剩余待办均为**事件驱动**（等限额 / 等升级窗口 / 等试点），**没有一项因"做不动"被推给 D7**。

### 机制原理（为何有效）

三条判据问的都是**流程形态**（要不要第二个主体 / 要不要多轮 / 是不是单次派发内部的质量门），
**不问产物主题** ⇒ 因此可在**受理完成、产出开始前**求值，得到确定的层级归属，
无需先看到产物内容。⇒ 这是"消除灰色地带两边都漏"的因果链。

**诚实标注论证强度**：本条属**机制设计常规论证 + 单实例（14 项复核）**，
且**尚未在派发引擎中实现** ⇒ 见 §"验证 · 待验证项"。

### 与既有 ADR/规则的关系

- **与 [ADR-0008](ADR-0008-跨项目受理区与目录治理.md) 正交**：ADR-0008 管"受理区的生命周期"
  （`open → triage → … → done`），本 ADR 管"进入执行后的**层级归属**"。两者串联而非替代。
- **与 `D7-P0-3` 的两条判据互补**：本 ADR 判"**归谁**"；`D7-P0-3` 判"**同一产物上由谁复核**"
  （`judge.family ≠ producer.family` · `judge.input ≠ producer.input`）。二者是"归属"与"复核资格"两层，不可互相代替。
- **不可替代性**：本 ADR 不引入任何新机制、不新增目录、不新增脚本；
  它把已有结论**固化为可在派发前求值的规则** —— 没有它，"归属一致"这件事**无法被复现或机判**。

## 考虑的替代方案（Alternatives Considered）

### 替代方案 A: 维持"事后人工归属"现状（否决）

- 优点: 零成本、零改动；且在实践中**确实得出了一致的结论**（14 项复核无争议）。
- 缺点: 判定与产出**耦合**（要看产物内容才能定）⇒ **不可复现、不可机判、不可在派发前完成**；
  灰色地带**没有唯一答案**，两侧都能讲理由。
- 否决理由: 触发本 ADR 的三条症状（新增场景无法落槽 / 无复用判定链 / 灰项两边漏）**全部来自这一形态**
  ⇒ 维持现状等于保留病灶。

### 替代方案 B: 用"是否跨站"作为分界判据（否决）

- 优点: 跨站与否是**派发前就已经确定**的事实，求值成本最低、机读性最好。
- 缺点: **跨站不自动带异构**，也不自动引入"非产出方结论主体"——
  "跨站"只说明**派到了哪个站**，主体仍只有 1 个。
- 否决理由: 8 项表里"**跨站派发**"的裁定正是"**留 D6**"（`B-1=否、B-2=否、B-3=否`）
  ⇒ 用跨站作判据会**当场误判这一项**。

### 替代方案 C: 只用单条判据（如只看 `B-1`）（否决）

- 优点: 判据集最小，只需要记一条规则，最容易宣讲与落地。
- 缺点: **漏判**——"多轮续聊（审→改→再审）"的取值是 `B-1=否、B-2=是、B-3=否`，
  它**不命中 `B-1`** 却必须是 D7。
- 否决理由: 单条判据会把这类项误归 D6（或判为"不适用"）⇒ 与既有 14 项复核结论冲突。

### 替代方案 D: 三条判据只登进路线文档、不落 ADR（否决）

- 优点: 不新增载体，路线文档已经是 D7 的权威源。
- 缺点: ADR 是"**非平凡改动必留决策**"的载体，而路线文档是**演进中的计划**——
  判据写在计划里，会随计划修订被静默改动。
- 否决理由: `D7-P0-1` 的退出判据明写"**ADR 落盘**"；
  且判据一旦被后续计划改写，就失去了"判据不能事后改"的意义。

## 后果（Consequences）

### 正面

- 派发引擎可在**受理完成、产出开始前**直接对三条判据求值 ⇒ 得到确定的层级归属。
- 8 项灰色地带**各有唯一答案**，消除"两边同时漏掉 / 重复建设"。
- 既有 14 项"归 D7"的结论**从'人的判断'升级为'判据的结论'** ⇒ 可复现、可机判。

### 负面

- 判据本身**尚未接入任何派发引擎**（本文是规则，不是实现）⇒ 现阶段仍是**纸面约束**。
- 三条判据的求值仍需**先有人把它写成机读形式**（`B-1` / `B-2` / `B-3` 各自的判定输入未定义）。
- 表中"agent 派生边表 / 多 agent 树"一项**无真实诉求支撑**（九项目实测中无一提出）⇒
  留下一条**有归属但无需求**的记录，日后需复核是否保留。

### 中性 / 需要后续行动

- `D7-P0-1` 的"**手动**归属表"与本文的判据**共存**：表是**判据的一次求值结果**，不是第二份真值。
  ⇒ 若日后改判据，表必须**整体重算**（不许局部改）。
- 本文档的 tier 已登记为 **`public`**（[sensitivity.yaml](../inventory/sensitivity.yaml)，2026-09-26）；
  依据 = 内容**全部来自已登记为 public 的出站版摘要** ⇒ 无超出该摘要的新披露。
  ⚠ 该行**带扩张条件**：内容一旦扩张到摘要之外（例：补入九项目逐项细节）⇒ **须重裁**。

### 待验证项

- **判据在派发引擎中的实际求值**：本文只给出规则，**没有任何一处代码在求值它**。
- **`B-1` / `B-2` / `B-3` 的判定输入未定义**：摘要未给出"谁提供这三个布尔值"、以什么字段承载。
- **`evidence_budget` / `constraints` / `decisions[]` 八字段 / `sensitivity` 取值域 / `redispatch?` 触发条件**
  —— 这些是**同批摘要未覆盖**的字段级定义，本文**不补齐**（见 `D7-P0-2` 的 `未实测登记`）。
- **14 项的具体清单**：摘要只给出"14 项"这个数与复核结论，**未逐项列出** ⇒ 本文无法逐项复核。

### 失效条件（何时重审本 ADR）

- 出现一项**既不改判据、又必须归 D7**（或反之）的场景 ⇒ 说明判据集不穷尽，须重审。
- 出现一项对三条判据求值后**同时命中 `B-1=是` 与 `B-3=是`** 的场景 ⇒ 说明求值规则不自洽，须重审。
- 8 项表中的任一项在后续复核中被改判 ⇒ 本 ADR 的"结论一致"前提失效。
- "agent 派生边表 / 多 agent 树"若因**长期无诉求**被移出 D7 ⇒ 表须重算。
