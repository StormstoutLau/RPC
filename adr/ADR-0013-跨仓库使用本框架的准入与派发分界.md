# ADR-0013: 跨仓库使用本框架的治理边界 —— 「受理（准入）」与「逐任务派发」分界

---------------------------------------------------------------------

id: ADR-0013
type: adr
version: 1.2
status: proposed
date: 2026-10-03
depends: [ADR-0004, ADR-0008, ADR-0009]
upstream: null
---------------------------------------------------------------------

> **Feature**: 为「**多个仓库（租户）长期共用本框架**（D6 `agent-cli` + 本机群）」划定一条**可操作的分界**：
> **受理（= 租户准入）** 归 inbox（`ADR-0008`；**低频、集中、跨信任域**）；
> **逐任务派发** 是**另一件事**（**其物理归属本 ADR 不裁** —— 见 §决策 **D4**）。
> 并**固化任务卡为跨此边界的稳定接口**：任何升级（含**图结构编排**）只能**附加式**扩展卡、**不得替换卡**。
> **创建日期**: 2026-10-03
> **状态**: proposed（提议）—— ★ **只记录边界，不裁治理形态**（用户 2026-10-03 明示"先只记录、暂不裁"）
> **适用**: 一切"某仓库/项目要长期使用本框架"的**准入与派发边界**判断；任务卡接口的**兼容性约束**
> ★ **2026-10-03 补充调研（v1.1）**：新增候选形态 **④「各仓库自编【图结构编排】+ `agent-cli` 仅作 worker」** 的可行性判据 ⇒ 见 §决策 **D6**。
> ★★ **2026-10-03 补充建议（v1.2）**：新增候选形态 **⑤「Auto_Prover 试点：受理面先接、编排面自研」** + **对 Auto_Prover 的接入建议（三种漂移 + 五条可机判护栏 + 顺序 + 两个前置）** ⇒ 见 §决策 **D7**。

## 背景（Context）

### 触发实例

1. ★ **用户指令（2026-10-03，E1）**：本框架是"学术推理 / 编程的**统一基座**"，此前已设计**任务受理机制**（= inbox，`ADR-0008`）。
   现提出**多仓库**使用下的两难：
   - **若本仓挨个监督执行、派发指令** ⇒ 可能**污染本框架的正常维护**，且**项目上下文不可避免膨胀**；
   - **若直接交给各仓库执行** ⇒ 各仓库可在本框架标准上**衍生特定分支**、任务各自独立，
     但**须保证每个仓库的 agent 使用本机群时遵守规范、避免漂移**。
2. **现有耦合点（E1 · 读码）** —— "监督"实际压在 RPC 单体上：
   - `$Script:PROJECTS`（proj→根）**硬编码**于 [agent-cli.ps1:44](../ops/station-bin/agent-cli.ps1)；
   - 而 `ADR-0008` **D5** 规定"受理通过才入台"、`inbox seal` 又把该 `$PROJECTS` 当作 **proj→根唯一真值**
     ⇒ **每准入一个仓库都要动 RPC 关键路径的单体**；
   - 台账 `agent-runs.log` 单文件在 `ops/station-bin/`；判据本体与 `local-only` 出口门都在 RPC。
3. **本仓已有可援引的先例（E1）**：[D7 协议契约 §1.4](../spec/d6-agent-standard/D7-PROTOCOL-CONTRACT.md) 已裁【甲】
   —— **「主控站 / 工作站」= 角色，不是机器**，角色绑定的是"驱动哪一段相" ⇒
   **"RPC 当主控"是当前选择，不是结构必然**。
4. **图结构编排调研已识别派发外壳的边界（E1/E3）**：`split`/`decompose` 已是"半张图"的**扇出**（真并行实测），
   缺**汇聚 / 片间依赖边 / 迭代**；且 `decompose` **仅对 readonly 合法**（`SPLIT_ABORT: writable merge not supported [exit 2]`）；
   派发外壳把上界**硬编码为站数**（`$stationPool = @('A','B','C')`）。

### 根因

**把「低频、高筹码、跨信任域的*准入*」与「高频、各仓库领域相关的*逐任务派发*」当成了同一件事，都压在 RPC 单体上。**
⇒ 每加一个仓库都要动**内核代码**，台账与决策上下文随租户数**线性累积** —— 这正是触发实例 1 里"污染 + 膨胀"两个症状的**同一根因**。

## 决策（Decision）

**在"多仓库共用"这一条件下，把 `受理（准入）` 与 `逐任务派发` 认定为【两件事】，并为它们之间的接口（= 任务卡）立稳定性约束；
治理形态本身不在本 ADR 内选择（D4）。**

### D1 ★ 「准入 ≠ 派发」是一条边界（**记录**，非裁定归属）

- **受理（inbox）承载 = 租户准入**：**低频**（一个仓库偶发一次）、**跨信任域**（需求方 → 机群管理员）、
  **高筹码**（决定该仓库能否入台、K 轨/P 轨、并发约束）⇒ 该**集中**（`ADR-0008` 已如此设计，本 ADR **不动其本体**）。
- **逐任务派发 = 另一件事**：**高频**（每次任务）、**领域相关**（卡/accept/golden 由仓库自定）⇒ **其物理归属待裁**（D4）。
- ★ **本 ADR 只钉"两者是两件事、不能混在一个面里压"** —— 不钉它们各自落在哪台机器、由谁驱动。

### D2 ★★ 任务卡是跨此边界的**稳定接口**（**工作约束**）

- 接口 = **任务卡 front-matter**（[CROSS-PROJECT-WORK-STANDARD §4](../spec/d6-agent-standard/CROSS-PROJECT-WORK-STANDARD.md)）
  + **三信封**（`TaskContract` / `RunReport` / `Verdict`）。
- **任何升级只能【附加式】扩展卡，不得【替换】卡**：新增字段必须**默认 fail-soft** ⇒ **存量卡行为不变**。
  先例 = **`backend:`** 字段（"不写 ⇒ 完全按 `sensitivity` 推导 ⇒ 存量卡行为不变"）。
- ⇒ **其他仓库存量卡在升级后仍然可派发**（这是"兼容"二字的**可机判含义**）。

### D3 ★★ 必须保持**单例**的集合（**约束**：守物理共享资源 + 安全边界的那部分）

**无论 D4 的形态如何裁定，以下各项都必须是单实例** —— 判据 = "它守的是**跨租户共享的硅片**还是**安全边界**"：

| 单例项 | 守什么 | 为什么多实例会坏（E1） |
|---|---|---|
| **判据本体**（`ops/rpc_check.py` 的 gate） | 「怎么知道」这一层 | fork 成 N 份 ⇒ **同一语义 N 个定义点**（本仓头号失败形态） |
| **台账 / 事件流单写者**（`I-1`） | 证据流单一真值 | 多写者 ⇒ 事件流分叉、计数不可复算 |
| **load-gate / 槽位仲裁**（`O-24` / `O-18`） | 共享硅片（内存带宽、单机容量 ≈119 GiB） | 各仓库各自一套锁 ⇒ **互相看不见** ⇒ 并发加载 ⇒ OOM |
| **egress / sensitivity 门**（`local-only → REJECT exit 4`，无覆盖通道） | 数据安全边界 | fork 一份旧 wrapper 即**丢门** ⇒ 未发表语料外发（`O-16` 血泪） |

★ 反之，**不守以上两者**的部分（任务卡 / accept / golden / 领域范式 / `.agentsync` / 产物 `agent-out/` / **该租户自己任务的"主控角色"**）
**可以各仓库自持** —— ★ 注意：**产物与 `.agentsync` 现状已经是每仓库一份**，即本仓**已半联邦**。

### D4 ★★ **未裁（明确记录，不在本 ADR 决定）**

- **治理形态（五个候选，均未裁）**：
  ① 单内核 + 联邦租户 · ② 维持单点受理（RPC 全监督）· ③ 全联邦（各仓库自跑整套）·
  ★★ **④ 各仓库自编【图结构编排】，`agent-cli` 仅作 worker**（2026-10-03 补充调研，可行性判据见 **D6**）·
  ★★ **⑤ Auto_Prover 试点：「受理面先接、编排面自研」**（2026-10-03 补充建议 —— 它是 ④ 的**首个申请方**，
  但建议**只先接受理面**；理由与前置见 **D7**）。
  **用户 2026-10-03 裁"先只记录、暂不裁"**。
- **`$PROJECTS` 是否从 `agent-cli.ps1` 代码挪到数据文件**（若挪，"加仓库"才可能不动内核）—— 属**具体改动**，须另案。
- **图编排框架是否引入**（图调研 P4）—— 须**另立 ADR**（`ADR-0004` D3①：新栈 = 新实体）。

### D5 ★ 图结构编排升级的**兼容性约束**（直接回答用户追加问题）

> 追问原文："如果升级图结构编排，对其他仓库使用有什么影响，是否还能兼容任务卡派发？"

- **兼容的前提 = D2**：图以**卡的附加字段**表达、**不替换卡**。
  ★ 事实上 `decompose:` **已经是卡的第一个"边"类型**（`split` 由主卡的 `decompose:` 生成 N 子卡）⇒
  图升级 = 顺势补 **`片间依赖边` / `汇聚(join)` / `有界迭代`** 三类**附加字段**，**不是换掉卡**。
- **三条现存的硬边界**（属 **D3 的仲裁面**，图升级**绕不过**；跨租户共享 ⇒ 不得各仓库自定）：
  ① `split`/`decompose` **仅 readonly 合法**（`SPLIT_ABORT: writable merge not supported`）⇒ **写任务的扇出+汇聚尚不支持**；
  ② 本地腿并行度受 `$stationPool`（= 站数）硬编码 + `O-18` 内存带宽约束；
  ③ 单写者台账 / `egress` 门。
- ★★ **领域语义归租户，内核不替租户决定**：**汇聚怎么归并 / 两片结论冲突听谁的 / 搜索策略** ——
  这些是**领域语义**（图调研 §1.2① 逐字："**任何图框架都不会替你决定'两个片结论冲突时听谁的'**"）
  ⇒ 必须在**卡里由租户声明**，**不得**硬编码进内核。★ 这**正是 D1（准入/派发分界）的直接后果**，二者自洽。
- ⚠ **若将来引入图框架（P4）**：其 checkpointer 崩溃重放（有独立论文实测 **at-least-once**）
  会**重复副作用 ⇒ 污染 run 产物与证据链**（`ADR-0007`），且会造**双真相源** —— **须另立 ADR，不在本 ADR 裁**。

### D6 ★★ 「各仓库自编图编排 + `agent-cli` 仅作 worker」的可行性（2026-10-03 补充调研）

> 追问原文："如果各个仓库单独写自己的图结构编排，工作站的 agent CLI 只作为 worker，是否可行？"

**结论：架构上成立（且是本仓角色模型的自然延伸），但【不可照现状直接落】—— 有一个硬前置：
「守不变量」的那几道门今天都在 **master 侧**，必须迁到 **worker 侧**（或共享 broker）；否则 N 个 master = N 个各自为政的门卫
⇒ 退化为 §替代方案 B（全联邦）的失败形态。**

**① 为什么"成立"（与既有裁定自洽）**

- D7 契约 §1.4 裁【甲】已把「主控站 / 工作站」定义为**角色**（`P0/P4a/P4b/P5` = 主控；`P1/P2/P3` = 工作站）
  ⇒ "`agent-cli` 仅作 worker" = **留 worker 角色的动作、交出去 master 角色的动作**，**契约层无需新增概念**。
- 图编排的【执行外壳】本就**可替换**（图调研 §4："外壳越晚绑越好"）⇒ 各仓库自写壳**不违背 D2** ——
  只要 **卡 = 固定接口**不变（**D2 是这条形态成立的前提，不是它的障碍**）。

**② 硬前置（E1 · 读码）—— 门要从 master 迁到 worker**

今天守不变量的门**全在 master 侧**：

| 门 | 今天的落点（master 侧） | 多 master 下的后果 |
|---|---|---|
| `local-only → REJECT` 出口门 | `Invoke-Router`（`agent-cli.ps1` L668–701） | N 个 master 各自判 ⇒ **门随 master 漂移** |
| 消毒（scrubber） | master（`ARCHITECTURE` 不变式 2："离开主控站前完成"） | 外仓 master 不跑 ⇒ **未消毒内容出站** |
| 槽位 / 加载门 | `Invoke-SlotGate`（L447，**纯探测 · 失败即 `na=allow`**）+ `Invoke-StationReady`（L403） | ★ **今天【没有】跨租户的站级互斥锁**（`flock` 是**每工作区**一把：不同 `proj` = 不同工作区） ⇒ 两个 master 同站派发 ⇒ **超 `O-18` / 撞 OOM** |

⇒ **可行性判据 = 这几道门能否在 worker 侧单例执行**。★ 而这**恰是 worker 的天然位置**：
worker **每站一份、且总在执行路径上** ⇒ 无论哪个 master 派来，都过它这一关。

**③ 因此必须抽取的两件东西（缺一即不可行）**

- **(a) 稳定 worker 契约** —— 今天 worker **不是接口**：`Invoke-RemoteScript`（L337）把 worker body 当
  **临时生成的 bash 脚本**（`/tmp/agent-cli-run-<ts>.sh` → scp → `ssh bash`）⇒ 外仓编排器**无法只调 worker**，
  只能调**整个 master + worker 单体**（`agent-cli task`）。⇒ 须把 worker 抽成**可发布 / 可版本钉 / 可机判**的入口（P1/P2/P3 面）。
- **(b) 站级跨租户准入**（今天不存在）—— worker 须持有**站级**（非工作区级）在跑锁 / 槽位，守 `O-18` / `O-24` / 单实例。

**④ 三条不变**：**D3 的单例集合照旧**（判据本体 · `I-1` 台账 · load/槽位 · `egress` 门）；
★ 且 **`I-1` 在多 master 下需要形态裁定** —— N 个 master ⇒ 台账**分租户** or 由内核**聚合**，但**每条事件流仍须单写者**。

**⑤ 唯一真实弱点 = 验收独立性**：若仓库**自产出自裁**（自己当 master 又自己跑 `P4b`/`P5`）⇒
撞验收铁律"**模型不自评、主控独立断言**"（= **自证**）⇒ 该形态**必须**配一个**非产出方的裁决角色**
（内核提供，或跨方复核 —— 即 `ADR-0009` 的 `B-1` 精神）。**这是它比"单内核"多出来的成本。**

**⑥ 前置清单（若裁采 ④）**：① 抽 worker 契约（**动 `agent-cli.ps1` 关键路径** ⇒ 须过 `_fm_golden_test` + `rpc check`）；
② 站级跨租户准入；③ `egress` / `sensitivity` / `scrubber` 迁到 worker（**fail-closed**）；④ 台账分租户（保 `I-1`）；⑤ 非产出方裁决者。
⇒ ⚠ **未测**：worker 契约 / 站级锁 / 门迁移 **均未实现、零实测**（见 §验证 · 待验证项）。

### D7 ★★ 对 **Auto_Prover** 的接入建议（2026-10-03 补充）

> 追问原文："Auto_Prover 正在考虑升级图编排结构，如果当前接入，用户有些担心在开发过程中出现漂移。"

**结论：「接入」要拆成两件事 —— 受理/派发面（D6 面）可以**现在**接；让本框架**托管它的【图编排执行外壳】**现在**不要**做。**
理由 = 现在做会**同时**触发三种漂移，其中两种本仓**已有取证**（不是推测）。

| 漂移类型 | 机制（本仓取证） | 接入后的形态 |
|---|---|---|
| **① 真值漂移** | 本仓头号形态：**同一事实两处定义** | 图拓扑/完成条件在它侧写一份、卡里再写一份 ⇒ 分叉。★ 先例：`decompose` 是**有序列表**但**实际并行派发** ⇒ 两边各自理解"依赖"即分叉 |
| **② 判据漂移** | 守不变量的门**全在 master 侧**；且站上**无跨租户站级锁**（`flock` = **每工作区**一把） | 外仓自编编排 ⇒ **门随它的实现漂移**，本框架不再是唯一判据（= **D6 的硬前置**） |
| **③ 行为漂移** | 图调研 §2.2：**图的"条件边"依赖本地模型的工具调用质量** —— `llama-server` 不加 `--jinja` 会**静默忽略 tools**；小模型 5+ 工具误报率 **>35%** | 条件判错 = **静默走错分支**（本仓最防形态） |

★ **另有第四层（同 D5 尾注）**：图框架 checkpointer 的**崩溃重放**（独立论文实测 **at-least-once**、会**重跑已记录工作**）——
Auto_Prover 是**长搜索**（最痛的一类负载）⇒ 重放会**重写已入链产物** ⇒ `digest 不符`（**本仓已有实测先例**：`O-140`）⇒ **须另立 ADR**。

**五条**可机判**护栏**（不是纪律口号）**：

1. **卡 = 唯一接口**（= **D2**）：图拓扑只能**附加式**写进卡，内核**不解析其内部语义** ⇒ 从根上不产生第二定义点。
2. **门留在 worker 侧**（= **D6 的硬前置**）：worker **每站一份、且总在执行路径上** ⇒ 判据**不随租户漂移**。★ **这是接入的入场券，不是可选项。**
3. **合规判据只在本框架一处定义**（= `O-143` 刚落的那条纪律"判据的两半必须同一处定义"）：租户侧**不得自带**"完成/合规"判据，只**消费**。
4. **入链时序写进它的编排**（= `O-140`）：复核必须**早于**该 run 入链；**checkpointer 不得接管产物写出**。
5. ★ **把漂移变成可机判（复用既有门，不新造）**：**`dialect`**（U-2 方言字典/映射表 —— 跨仓**术语**对账；现映射 26 行 / 5 族 / **冲突 4** / 不可判 11）+ **`id-census`**（**10 个项目根已含 `Auto_Prover@F:\Auto_Prover`**，口径可复算）⇒ 不必为"跨仓不漂移"发明新机制。

**顺序（复用图调研的收口，不另起）**：
- **现在可做** = **受理面**（低频 / 集中 / 合约化；**不碰它的编排内核**）—— 即转运包 → 裁决 → `20_plan` → 派发。
- **编排面**按 `P1`（补 `split` 的**汇聚语义**）→ `P2`（条件分支从"文档表"变**可机判判据**）→ `P3`（★ **它自研侧**把 **AND-OR 超图 + verifier 闭环**跑通，**不引框架**）→ **才谈** `P4`（外移执行外壳）。
- ★ `P4` 判据**须同时满足三条**（且**不接受**"项目变复杂了"这类不可机判的理由）：① `P3` 已跑通 ② 能给出**具体的**"现有表达不出来"实例 ③ 有 `P3` 的**实测成本数据**。

**两个"现在做会立刻制造漂移"的前置（须先解）**：
- **① `$PROJECTS` 硬编码**（`agent-cli.ps1`）⇒ **加一个仓库 = 改内核关键路径** ⇒ 每次接入都往内核塞一个租户特例 = **D4 第二条**（**先把 `$PROJECTS` 数据化**）。
- **② ★ 它当前的前置未满足** —— `inventory/untested-index.yaml` 记 Auto_Prover「**从未与真实形式化证明输入对接**」（`U5#1`）
  ⇒ **在没有真实负载时固化图拓扑 = 对着空气设计外壳**（正是"**外壳越晚绑越好**"的反面）。
  ⚠ **该登记项是否过时：已核（2026-10-10 · 双向实测）** —— 「从未对接」**口径收窄**为「**对接面 = 仅引擎调用 · 未走 D6 链**」
  （对方一手实测 `F:\Auto_Prover` D060/提交 `f5b21ab` ＋ 本仓复算三读数，见 §验证 · 待验证项 ②）
  ⇒ ★ **前置仍不满足**（「没有真实负载时固化图拓扑」的告诫**不变**）· ⚠ **不得读成「它侧无真实负载」**（其 D060 自证有大量真机实测）。

### 机制原理（为何有效）

分界的依据不是"摊子太大"，而是**两个轴的频率与信任域不同**：
**准入**低频且跨信任域（该集中）；**派发**高频且领域相关（该分散）。
把二者混在一个面里，就会让"**仓库数**"这个与内核无关的变量**驱动内核代码的改动**（触发实例 2）。
D2/D3 则给出"分散"的安全前提：**接口冻结** ⇒ 分散不产生兼容负债；**单例集合冻结** ⇒ 分散不碰物理不变量。

**诚实标注论证强度**：**机制设计常规论证 + 本仓单实例读码**；★ **尚未实测** —— 形态未裁（D4），
`$PROJECTS` 数据化未做，D5 的附加字段未落 ⇒ 见 §验证 · 待验证项。

### 与既有 ADR/规则的关系

- **`ADR-0008`（受理区）**：本 ADR **不替代、不修改**它；只**补一条其 D5 的延伸** ——
  "入台"之后**逐任务派发**是**另一个面**（D5 原文只说"受理通过才入台"，未说入台后谁派发）。
- **`ADR-0009`（D6/D7 归属）**：**正交**。ADR-0009 判"某能力归 D6 还是 D7"；本 ADR 判"准入与派发的**面**在哪"。
- **`ADR-0004`（统一管理面）**：**一致**。D3 的"单例集合"就是"统一管理面"在**多租户**下的**必然形态**（管理动作只一处）。
- ★ **D1 的依据直接援引 D7 契约裁【甲】**（"主控站/工作站 = 角色，不是机器"）—— 本 ADR **不新造先例**。

## 考虑的替代方案（Alternatives Considered）

### 替代方案 A: 维持单点受理（RPC 全监督每个仓库的每个任务）（否决/推迟）

- 优点: **零改动** —— 现状已跑通（受理→派发→证据回收全链在 RPC 侧）；语义最简单，只有一个主控。
- 缺点: **每加一个仓库都要动 `agent-cli.ps1` 关键路径**（`$PROJECTS` 硬编码）；台账与决策上下文随租户数**线性累积**；
  RPC 成为**吞吐瓶颈**（所有租户的任务共用一套派发面）。
- 否决/推迟理由: 它**正是**触发实例 1 两个症状（污染 + 膨胀）的来源 ⇒ 维持它等于保留病灶。
  ⚠ **但本 ADR 不据此把形态判为"另一侧"** —— 依用户裁定，形态**待裁**（D4）。

### 替代方案 B: 全联邦（各仓库自持 wrapper + ledger，自跑）

- 优点: RPC 最轻（不承担逐任务监督）；任务各自独立、可并行；各仓库可按领域范式自定分支。
- 缺点: 破 **D3 的物理/安全不变量** —— 并发/加载各持一套锁 ⇒ **互相看不见 ⇒ OOM**；
  `egress`/`sensitivity` 门 fork 后**漂移** ⇒ `local-only` 外发；**验收独立性消失**（仓库自产出自裁决 = 自证）；
  判据本体 fork 成 N 份 ⇒ **同一语义 N 个定义点**。
- 否决理由: 缺点**命中本仓头号失败形态（同一事实两处表达）**且破物理不变量 ⇒ **不可取**。
  ★ 依 D3，**可联邦的只是"不守物理/安全边界"的那部分**（卡/范式/产物），不是全部。

### 替代方案 C: 用图编排框架直接取代任务卡派发

- 优点: 一步到位拿到 DAG / 扇出-汇聚 / 持久化续跑；正对图调研 §4 的四痛点。
- 缺点: **替换冻结接口** ⇒ **所有租户的存量卡当场失效**（破 D2）；
  框架**不提供领域语义与搜索策略**（归并/冲突/搜索仍须自研）；其崩溃重放（at-least-once）**污染证据链**（`ADR-0007`）；
  引入新栈还须过 `ADR-0004` D3①。
- 否决理由: 与"接口稳定、存量卡不变"（D2）**正面冲突**；框架只该做**可替换的执行外壳**，且须**晚绑**（图调研 P4：先 P1/P2/P3，再谈 P4）。

## 后果（Consequences）

### 正面

- 给出"**加一个仓库**"的判定依据：**准入**走 inbox（不动内核），**派发**按 D2 只吃**附加式**卡字段。
- 把"**必须单例**"（D3）与"**可以联邦**"（卡/范式/产物/租户主控角色）**分开** ⇒ 为将来减负提供**已划好的接缝**。
- 图结构升级有了**明确兼容条件**（D5）：附加字段 + 三条硬边界 + 领域语义归租户。

### 负面

- **D4 未裁 ⇒ 现状行为不变**（仍是单点受理），本 ADR **只固化边界、不立即减负**。
- D3 的单例集合是**人为判据**（"是否守物理/安全边界"）⇒ 边界个案（如某租户的判据只服务它自己）仍需**逐案裁定**。

### 中性 / 需要后续行动

- **`$PROJECTS` 数据化**（若做，须另案）—— 它是"加仓库不动内核"的**前置**。
- **图升级 P0–P4**（图调研）各自独立推进；**P4 须另立 ADR**。
- **台账是否按租户隔离**（保 `I-1` 单写者前提）—— 未做，属 D4 形态裁定后的连带动作。

- 出现一个"**不替换卡（破 D2）就无法满足**"的租户需求 ⇒ 接口稳定性前提失效，须重审。
