# ADR-0006: 控制面传输绑定 LAN IPv4 —— 消除 `*.local` 解析的 16s 与"控制面走公网 IPv6"

---------------------------------------------------------------------

id: ADR-0006
type: adr
version: 1.3
status: accepted
date: 2026-09-16
depends: \[ADR-0003, ADR-0004, ADR-0005]
upstream: \[ADR-0004]
---------------------------------------------------------------------

> **Feature**: 把主控站到三站的 ssh/scp 控制面**显式绑定到 LAN IPv4**，使每次连接从 **~16.2s → ~0.18s（≈90×）**，
> 并把"LAN 管理面真值"登记进 `inventory/net.yaml` + 加一条防漂移门禁断言。
> **创建日期**: 2026-09-16
> **状态**: accepted
> **★ v1.1 升级（2026-09-29）**: 本 ADR 的 **D4（防漂移判据）实测存在射程漏洞** —— C 站登记为
> `host: null`（无名别名）⇒ 判据**整站跳过**；而它的"双覆盖"假设（D4 原文 L80）经 2026-09-29 实测
> **不成立**：可达性判定确实 FAIL，但只报"可达 2/3 站"、**不给根因**，且**掩盖了第一覆盖对 C 失效**这一事实。
> ⇒ 新增 **D5（C 站 LAN 静态化）** 与 **D6（判据改为「站上实况 + USB4 降级通道」）**，见 §决策补充。
> 完整归因见 [控制面 LAN 地址漂移 · 失效归因与判据升级](../docs/research/2026-09-29_控制面LAN地址漂移_失效归因与判据升级.md)。
> **★ v1.3 落体（2026-09-29）**: **D5 由「阻塞」翻「已落体」** —— 同日路由器「**桥 → 路由**」模式切换 ⇒
> 整段 LAN 重建，**DHCP 池边界首次可知**（`.100–.199`）⇒ D5 的两条前置条件（目标地址**可证在池外**、
> **USB4 退路**可用）同时成立。范围由「只做 C 站」**扩到三站 + 主控**（四机同刻全在池内、租期仅 120 分钟
> ⇒ 只钉 C **止不住漂**，主控自己就先漂了）。另补记一处**迁移清单漏项**：`known_hosts`（其缺失曾表现为
> `Host key verification failed`，见 §实施记录 v1.3）。验收 = 四机 `PrefixOrigin=Manual` / `Dhcp=Disabled` + **D6 判据四绿**（V14–V17）。
> 方案与脱敏口径见 [路由器模式切换 · LAN 寻址重建与静态化方案](../docs/research/2026-09-29_路由器模式切换_LAN寻址重建与静态化方案.md)。
> **适用**: 主控站 `~/.ssh/config`、[cluster.py](../ops/cluster.py) 的 `STATIONS`、[net.yaml](../inventory/net.yaml)、[rpc_check.py](../ops/rpc_check.py) 的 `stations` 断言

## 背景（Context）

**触发**：[OPEN-ISSUES](../spec/d6-agent-standard/OPEN-ISSUES.md) 登记的"框架级：每次 ssh/scp 建连 14-17s"（ADR-0005 实施期间实测发现；当时通过"合批回收"把 collect 的连接数 8→4 规避了一部分）。

**测量（2026-09-16 实测，非推断）**：

| # | 测量 | 结果 |
|---|---|---|
| 1 | `ssh scott-lau-GTR-Pro.local true`（按名） | **16,200 ms** |
| 2 | `ssh -o User=scott-lau -o IdentityFile=… 192.168.1.32 true`（按 LAN IPv4 + 显式身份） | **184 ms** |
| 3 | `ssh 192.168.1.37 true`（C 站，config 里本就是 IP） | **198 ms** |
| 4 | `[System.Net.Dns]::GetHostAddresses('scott-lau-GTR-Pro.local')` | **17,016 ms**，且**只返回 IPv6**（`2409:8a20:…`，无 A 记录） |
| 5 | `Resolve-DnsName <名>` / `-LlmnrNetbiosOnly` | 337ms / 0ms，**均无结果**（DNS 客户端 API 解析不出 `.local`） |
| 6 | 站上 `echo $SSH_CONNECTION`（按名连进去） | `2409:8a20:…:c428 12342 → 2409:8a20:…:bd20 22` ⇒ **控制面实际走公网 IPv6** |
| 7 | 站上 `echo $SSH_CONNECTION`（按 IPv4 连进去） | `192.168.1.36 12343 → 192.168.1.32 22` ⇒ **走 LAN** |
| 8 | `ip -4 -o addr`（A / B / 主控） | A=192.168.1.33、B=192.168.1.32、主控=192.168.1.36；**A/B 均为 DHCP 租约**（`scope global dynamic`, `valid_lft` ~14.5h） |
| 9 | `ssh -G <名>`（Win32-OpenSSH 9.5p1） | 可用，能读出 `hostname` = 名字（⇒ 可作为门禁判据来源，**不需网络**） |

**根因**：Windows 解析 `*.local` 走 mDNS 兜底路径，耗时 ~16-17s 且**只给出公网 IPv6 地址** ⇒ ① 每次 ssh/scp 白付 16s；② 控制面**没走局域网**，而是经 ISP IPv6 绕行（依赖运营商 IPv6 与临时隐私地址）。

**这不是新问题，本仓已有两处同源证据**：
- [cluster.py:160-175](../ops/cluster.py#L160-L175) 的注释：*"原先每次 ssh_run 都用主机名重连 ⇒ 每次连接白付 ~14s。9 次串行即 130s（这正是 `/api/status` 129.6s 的根因，见 CHECKLIST F19）。**C 站一直用 IP 故从未受影响**。此处缓存解析结果…"* —— 即：**问题早已诊断出，但缓解只覆盖了长驻 web 进程的进程内缓存**；`agent-cli.ps1` 的 CLI ssh/scp 路径与 `cluster.py` 的每次 CLI 调用仍在白付。
- [cluster.py:89](../ops/cluster.py#L89) 的 C 站条目：*"seaviv.local 可解析但**保持 IPv4 规避 paramiko/IPv6**"* —— **C 站当年就是按本文的结论办的**。

⇒ 本 ADR 不是引入新理念，而是把 C 站的做法**推广到 A/B**，并把"绑定"这件事**登记成可断言的真值**。

## 决策（Decision）

### D1. `~/.ssh/config`：名字保留为别名，`HostName` 绑定到 LAN IPv4

```
Host scott-lau-NEX.local
    HostName 192.168.1.33
Host scott-lau-GTR-Pro.local
    HostName 192.168.1.32
Host 192.168.1.33 192.168.1.32 192.168.1.37
    User scott-lau / IdentityFile ~/.ssh/id_ed25519 / IdentitiesOnly yes
+ AddressFamily inet   # 不再尝试 IPv6
```

- **名字继续可用**（所有调用点、文档、人的习惯都不用改）⇒ 改动面最小。
- **`AddressFamily inet`**：不再尝试 IPv6（实测 `inet` 单项省 ~3s，且确保不回落公网 IPv6）。
- 三个 IP 也加身份块：按 IP 连接时**默认用户名会退化为本机用户 `peng`**，实测会**卡在 stdin 等口令（>90s 挂起）** —— 这是本次调查中真实踩到的坑。

### D2. `cluster.py` 的 `STATIONS`：A/B 改用 LAN IPv4

与 C 站既有做法一致（D1 的注释即其理由）。`resolve_host()` 对 IP 直接返回，省掉解析与缓存；`_HOST_CACHE` 对仍以主机名登记的站保留。

### D3. LAN 管理面真值登记进 `inventory/net.yaml`

新增 `lan:` 段（三站 LAN IPv4 / 主控 IP / 接口 / DHCP 现状 / 测量方式），与既有的 USB4 `segments` 并列。**"改了网络就改本表"** 的维护约定沿用 net.yaml 既有措辞。

### D4. 门禁加"防漂移"断言（并入既有 `stations` 检查，非新脚本）

判据：**`ssh -G <名>` 的 `hostname` 必须等于 `net.yaml` 登记的 LAN IP**（纯本地计算，无网络开销）。
- 不符 ⇒ FAIL 并提示"DHCP 可能已漂移，请更新 net.yaml 与 `~/.ssh/config`"。
- 这一条把 D1/D2 的**唯一代价（IP 绑定对 DHCP 的脆弱性）转成可检出的红灯**，而不是"ssh 连不上"的谜题。若站真的漂移，既有的可达性判定也会同时 FAIL（双覆盖）。

> **★★ v1.1 更正（2026-09-29 实测）**：上面这段的最后一句 ——「若站真的漂移，既有的可达性判定也会同时 FAIL（**双覆盖**）」—— **不成立**，但它**不是**本次缺陷的根因，**本条判据的射程漏洞**才是：
> 1. **射程漏洞（根因）**：判据读的是 `net.yaml` 里的 `host`（别名）字段，而 [rpc_check.py L3990-3995](../ops/rpc_check.py#L3990-L3995)
>    对 `host: null` 的站**显式 `continue` 跳过**（注释原文即点名 C 站）⇒ **C 站从来不在本判据的射程内**。
>    ⇒ 一条判据的**射程**必须与它要防的**风险的分布**正交对齐；"有没有别名"与"会不会漂移"**无关**。
> 2. **「双覆盖」不成立**：可达性判定确实 FAIL 了，但它① **不提供根因**（只报 `可达 2/3 站`）；
>    ② 更糟：它让"第一覆盖对 C 完全失效"看起来像"已经被覆盖了"⇒ **一条不诊断的兜底会掩盖另一条兜底的缺失**。
> 3. **实测代价**：2026-09-29 C 站由 `.37` 漂到 `.8`，**6 项门禁红灯**（`usb4`/`gates`/`engine`/`backend`/`models`/`stations`）
>    明细**一律只有 `可达 2/3 站`**；`stations` 断言的处理是「站点不可达 (**未计入判定**): C」——
>    **正是本 D4 承诺要消灭的那个"ssh 连不上的谜题"**（见 §背景 net.yaml 引文口径）。
> ⇒ 处置见 **D6**（改为「站上实况」判据 + USB4 降级通道，覆盖全部三站）。

## 决策补充（v1.1 · 2026-09-29）

> **为什么是"补充"而不是"重写 D1–D4"**：D1–D4 的**收益成立且仍在生效**（16.2s → 0.18s 实测 90×）。
> 本文只补两个洞：**根治**（D5）与**判据射程**（D6）。原文一字未删 —— 与本文既有的
> 「2026-09-25 节名统一……**内容未改**」同一条留痕纪律。

### D5. C 站 LAN 改**静态**地址（复议原「替代方案」中被否决的一项）

**范围**：**只做 C 站**。A/B **维持 DHCP 不动** —— 它们地址稳定，且**本来就在 D4 判据射程内**
（有别名）；C 是唯一 `host: null`、且已漂两次的站，是**唯一同时缺"根治"与"兜底"**的站。

> **★ v1.3 范围变更（2026-09-29）**：上述"只做 C 站"的取舍**当日即被事件推翻** —— 路由器「桥 → 路由」
> 模式切换**重建整段 LAN**（`192.168.1.0/24` → `192.168.10.0/24`），且四机**同刻全在 DHCP 池内**（租期 120 分钟）
> ⇒ 只钉 C 站**止不住漂**。**处置扩到三站 + 主控**（末位八位组不变，只换网段段 ⇒ 落 `.2–.99`）。
> 原文一字未删 —— 与本文既有留痕纪律一致；落体验收见 §实施记录 v1.3。

**为什么现在可以做（原否决理由逐条复核 —— 这是新证据，不是重新讨论）**：

| 原否决理由（本 ADR 原文 L90） | v1.1 复核 |
|---|---|
| **远程改网络有失联风险** | ★ **已被消解**：USB4 段（`10.10.11.3`）提供了**不依赖 LAN** 的操作与恢复通道 —— 2026-09-29 的真实故障中已用它完成诊断、部署站上件、核实 worker 引擎（[归因文档 §1-#7](../docs/research/2026-09-29_控制面LAN地址漂移_失效归因与判据升级.md)）。**做法纪律**：先建立 USB4 会话再改 `eno1`，全程有退路 |
| **需与路由器 DHCP 池避让，易出地址冲突** | **理由成立 ⇒ 降级为「前置条件」而非否决**：改静态前必须确认目标地址**不在路由器 DHCP 动态池内**（当前 `.37` 无人应答、ARP 为空 ⇒ 空闲，但"现在空闲"≠"不在池里"） |

**验收判据**：C 站 `ip -4 -o addr` 的 LAN 地址 `scope` **不再是 `dynamic`**，且 `~/.ssh/config` 别名块与
`net.yaml §lan` 三者一致（沿用 D4 的维护约定）；改后 `usb4` / `gates` / `stations` 恢复 3/3。

**状态**：**★ 已落体（2026-09-29，范围扩到三站 + 主控）** —— 验收 V14–V17 全过（见 §实施记录 v1.3、§未实测登记 #1）。

### D6. 防漂移判据：从「别名」改为「站上实况 + USB4 降级通道」

**修 D4 的射程漏洞**，判据改为：

1. **来源改为站上实况** —— 读目标站 `ip -4 -o addr` 的 LAN 地址，与 `net.yaml §lan` 真值比对。
   **不依赖 `~/.ssh/config` 别名** ⇒ **三站全覆盖**，`host: null` 不再是跳过理由。
2. **解析路径带降级** —— 直连 LAN 优先；**LAN 不可达时经"与该站有 USB4 直连的站"中转**
   （`主控 → B → C via 10.10.11.3`）。★ 这条同时解决"查不出根因"：**LAN 已断时仍能问出它现在的地址**。
3. **输出形态必须是"红灯 + 根因"**，而不是"可达 2/3 站" —— 例：
   `C 站 LAN 已漂移 192.168.1.37 → 192.168.1.8（scope=dynamic/DHCP），请更新 net.yaml §lan / cluster.STATIONS / ~/.ssh/config`。
4. **记住 D4 的教训**：判据的**射程**必须显式声明（覆盖哪些站、凭什么），且**不得因"某一档数据缺失"整档跳过** ——
   缺数据时应**响亮报错**（同本仓「解析失败不能表现成业务全错」纪律），不得静默降级
   （ADR-0007 转引本 ADR 的「**判据必须自证不静默降级**」）。

**状态**：**★ 已落体（2026-09-29，v1.2）**，见 §实施记录 v1.2 与 §未实测登记 #2。
（★ v1.3 更正：本行原仍写"**已决 · 未落体**"，与 §实施记录 v1.2 自相矛盾 —— 属**自我陈述错误**，非未落体。）

## 考虑的替代方案（Alternatives Considered）

> 2026-09-25 节名统一（原名「否决/比较对象」），**内容未改**。

| 方案 | 否决理由 |
|---|---|
| **在 station 侧把 LAN 改静态**（netplan/NM `manual`） | 远程改网络有**失联风险**（net.yaml 已记录同类事故："A 站接口错位 → 重启后两段全断"）；且需与路由器 DHCP 池避让，易出地址冲突 |
| **在路由器做 DHCP 保留**（按 MAC 固定 .32/.33/.37） | 这是**最干净**的稳定化手段，但需操作者/路由器权限（本轮无法执行）⇒ 列为**建议**，落地后 D4 的红灯概率进一步降低 |
| **主控 hosts 文件写死名字→IP** | 与 D1 等效，但需管理员权限、影响面更大（所有程序而非仅 ssh/scp），且同样依赖 IP 稳定 |
| **扩大 `_HOST_CACHE` 缓存**（把解析结果落到文件/跨进程复用） | 治标：每次仍可能冷启动付一次 16s；且新增一个缓存机制（D3 新增能力）与失效策略；关键——**缓存解决不了"只解析出公网 IPv6"这个更严重的问题** |
| **关闭主控的 IPv6** | 影响面大（其它用途）、且不解决 16s 解析耗时本身 |
| **什么都不做，只用 ADR-0005 的"合批"绕** | 只减少连接数，不减少单次成本；agent-cli 每个 task run 仍有 10-20 次连接（实测 run 墙钟 ≈420s，模型仅占 21-53s） |

> **v1.1 复议（2026-09-29）**：第一行「**在 station 侧把 LAN 改静态**」**部分改判**
> —— ① 否决理由「失联风险」已被 **USB4 降级通道**消解（§决策补充 D5 的两条复核）；
> ② 否决理由「地址冲突」**成立，保留为前置条件**（目标地址须在 DHCP 池外）。
> ⇒ 由「否决」改为「**限 C 站执行**」（D5）。
> 第二行「**路由器 DHCP 保留**」的评估**不变**（仍是最干净的稳定化手段、仍需路由器权限），
> 但 ★ 它**不能替代 D6**：保留做对了也只是把漂移**概率**降低，**判据的射程漏洞依然存在**
> —— "概率变小"与"判据看得见"是两件事。

## 后果与待办

**收益**
1. **每次 ssh/scp：~16.2s → ~0.18s（≈90×）**；CLI 路径（`agent-cli.ps1` 的 station-ready / slot-gate / profile / sync / lock / collect）与 `cluster.py` 每次调用**同时**受益。
2. **控制面回到 LAN**（不再经 ISP IPv6 绕行）—— 安全性、可预期性、以及不依赖运营商 IPv6 与临时隐私地址。
3. 消除"按 IP 连接默认用户名退化 ⇒ 卡 stdin"的隐患（`~/.ssh/config` 的三个 IP 身份块）。
4. **机器级配置与 repo 真值之间有了一条可断言的绑定**（D4），使该改动可被门禁复核、可被后人复现。

**代价与风险**
- **DHCP 漂移**（A/B 是动态租约）⇒ 由 D4 断言 + 既有可达性判定**双重检出**；建议在路由器做 DHCP 保留以进一步稳定。
- `~/.ssh/config` 属**机器级资产、不在 repo 版本控制内** ⇒ 其内容以 ADR 文本 + `net.yaml` 的 lan 段 + D4 断言三重固化；备份见 `~/.ssh/config.bak-20260916`。
- 未在本轮处理（保持范围）：`agent-cli.ps1` / `cluster.py` 的 ssh/scp **未统一加 `-o BatchMode=yes`**（防"认证失败时静默等 stdin"，本轮实测踩到 >90s 挂起）—— 已登记为独立项。

> **v1.1 追加（2026-09-29）**
> - **口径更正**：上面「代价与风险」第一行的"**双重检出**"应读作 —— **A/B 双重、C 零重**。
>   D6 落地后才是三站双重。
> - **新增代价（诚实登记）**：D4 的**射程漏洞存在了 13 天**（2026-09-16 → 2026-09-29），
>   期间 C 站**实际漂移一次**（`.37 → .8`）而**判据无感**（见 §D4 的 v1.1 更正）。
>   ⇒ 教训不是"D4 写错了"，而是两条：
>   ① **判据的射程必须与风险的分布对齐**（"有没有别名"与"会不会漂移"无关）；
>   ② **判据必须自证"不只是没判"**（本 ADR 正是 ADR-0007 转引的那条纪律的出处）。
> - **新增待办**：① **D5** C 站 LAN 静态化（前置：确认目标地址在路由器 DHCP 池外；须经 USB4 会话操作）；
>   ② **D6** 判据改造（含 `net.yaml` 的 C 站 `iface: eno1` 回填）；
>   ③ 把 `net.yaml` `dhcp:` 段的"路由器 MAC 保留建议"从散句升格为**有 owner 的登记项**
>   —— 否则它会继续"写了没人做"（D4 的射程漏洞就是这条纪律缺位的产物）。

> **v1.3 追加（2026-09-29）**
> - **代价的前提消失**：上面「代价与风险」第一行假设的"**DHCP 漂移**"，在四机钉静态后**不再成立**
>   （`ipv4.method manual` / `Dhcp=Disabled`）⇒ D6 判据与 `ssh -G` 绑定**降为回归护栏**，
>   而不再是"日常漂移的探针"。
> - **残余耦合（诚实登记，消除不掉）**：静态地址仍落在 `192.168.10.0/24` 内 ⇒ 若**路由器再换 LAN 网段**
>   （如 `192.168.20.x`），控制面照样断 —— 主控在 WLAN 上、够不到站间 USB4 点对点段（`10.10.x`）。
>   这条现在**有判据**（D6 报根因），但**消除不掉**；已写进方案文档 §5 的**不变式 1/2**。
> - **闭环**：v1.1 追加的两项待办（① D5、② D6）**均已落体**；③ 则**随"不再依赖 DHCP + MAC 保留"失去对象**
>   —— 但**不变式 1/2 仍无机器判据**（池是否被改宽读不到，需路由器凭据；见方案文档 §8-5）。
