## 范围声明（先于一切）

**本决策仅约束运维层的四个改进方向（防挂死容错、集群操作聚合、仓库目录规范、升级前收尾），不改变推理架构本身（双端点拓扑、GTT 互斥、内存门控逻辑均维持现状）。** 模型选型、评测方法论、Agent 生态升级（P0/P1/P2）不在本 ADR 范围内。

## 背景（Context）

### 触发实例

用户四问（2026-09-01）：① 防过载/容错/参数优化是否齐备；② 能否傻瓜化一键管理+UI；③ D:\RPC 目录散乱如何规范；④ Agent 生态升级前还有什么未收尾。对两站做了实测取证（E1，命令见"审计记录"节），结论：**内存门控与进程级容错已实锤，但 hang 模态检测、网关级容灾、参数台账、集群聚合操作四项存在真实缺口**。

### 根因

四缺口不是"没人做"，而是机制层的结构性空档：

1. **systemd Restart 只覆盖"进程死亡"模态**。A 站两次挂死（E2，根因报告 §1）均为"进程存活、系统冻结"——GFXOFF worker 卡死 + bjork\_deepfix cron 每分钟扰动复合触发（置信度 \~70%，E1 判别实验 3/3 关案）。`Restart=on-failure` 对该模态零覆盖；现有看门狗是 ping 型**止损**（第二次挂死时触发过，E2），非 health 型**自愈**。
2. **LiteLLM 容灾止步于单路由内**：`num_retries=1 / cooldown_time=30 / background_health_checks=true / health_check_interval=300 / timeout=600`（E1，config.yaml 全文核对）——有重试与熔断，但**无跨模型 fallbacks、无 rpm/rps 限流**；模型未加载时错误直抛调用方。
3. **参数是模板复用而非逐模型调优**：6 个实例 conf 中 `THREADS=16` 全统一、`EXTRA_FLAGS="-fa on"` 全统一；CTX 已按模型分档（32k×4 / 128k nemotron / 262k qwen3.8，E1），`N_CPU_MOE` 取 0（gpt-oss）或 8（其余）**但选择依据无台账**，batch/ubatch 未显式配置（走默认值）。调优结论散落在聊天史与 results-ledger，不可复用。
4. **仓库无目录规范**：根目录 140 文件（115 个脚本 + 19 份 md + 杂项，E1 计数），`scripts/` 另有 149 个，一次性部署/诊断脚本（a1\_\~a4\_、b5\*、b6\*、hang\_forensic\_×4 等阶段编号命名）与活资产混放，复用成本高。
5. 附带发现：**LiteLLM 网关是** **`enabled`** **开机自启**（E1）——手册"零自加载"指推理服务（llama-server 两站均 disabled、A 站 rpc-server disabled，E1），网关自启是合理设计但手册语义需澄清，非缺陷。

## 决策（Decision）

在"运维层四缺口已实证"的条件下，**按收尾→重构→聚合→加固的顺序补全，而非重写推理层**。

### 1. 收尾先行（D4，\~30min）

1.1 提交 3 个未提交修改（调研.md/手册.md 表格重排 + gptoss\_spec\_test2.sh 核对后提交）。
1.2 清理三处 key 残留：A 站 `/tmp/aoc.jsonc`、B 站 `/tmp/cca.sh`、`/tmp/e2e.sh`（E1 grep 命中 `sk-RPC-`）。
1.3 `新建文本文档.txt`（端点速记）合并进手册 §1.2 后删除。
1.4 B 站 opencode 1.18.9→1.18.25 升级并入 Agent 生态升级 P0 批次。

### 2. 目录重构（D3，\~1h，git mv 保历史）

```
d:\RPC/
├── docs/      根目录全部 19 份 md（手册/调研/DEV-LOG×3/根因报告/SSH 排查记录）
├── spec/      维持现状（27 文件，已规范）
├── ops/       两站在跑框架的仓库副本（llama-serve-instance/rpc-nodes/nodes.env/netplan/systemd unit 等）
├── archive/   按阶段归档 a1-a4/ b5*/ b6*/ hang-forensic/ 一次性脚本
└── tests/
```

2.1 重构后根目录仅留：README（可选）、LICENSE、.gitignore、docs/spec/ops/archive/tests/ 五目录。
2.2 手册与调研文档中的相对链接同步更新。

### 3. 集群聚合操作（D2，\~半天）

3.1 主控站 `cluster.ps1`：`status/load/unload/e2e` 四子命令，内部自动路由正确站（load gpt-oss→A 站，load nemotron→B 站），免记 ssh 目标。
3.2 单页 HTML 总览（主控站静态页）：聚合两端 `/health` + `infer-list` + Beszel/Cockpit 链接。
3.3 **不做**第四个面板——Cockpit API + 静态页够用；不上报盘式方案。

### 4. 防挂死与容错补全（D1，与生态升级 P0 同批）

4.1 **health 型看门狗**：systemd timer（每 60s）探测两端 `/health` 端点 + GTT 水位；连续 N 次失败执行分级处置（warn→infer-unload→通知）。与既有 ping 型止损互补：ping 管"主机死"，health 管"服务冻结"。
4.2 **LiteLLM 跨模型 fallbacks**：`nemotron ↔ gpt-oss` 互为备份路由（同异构双端点天然支持），叠加 rpm 限流。
4.3 **参数台账**：`spec/infer-load/params-ledger.md`，逐模型记录 CTX/THREADS/N\_CPU\_MOE/batch 的取值、实测依据（引用 results-ledger）、试过的反例。
4.4 既有观测网（netconsole + softlockup 常驻，E2）维持不动。

## 机制原理（为何有效）

- D4→D3→D2→D1 的顺序遵循依赖：先清残留（避免归档进 key），再立目录（后续产物有落点），再聚合操作（D1 的看门狗挂在 cluster.ps1 体系上做部署/验证）。

- D1 的 health 看门狗针对已实锤的挂死模态（进程活、系统冻，E2 根因报告 F6/F7）——这是 systemd Restart 的机制盲区，只能靠端点探测补。

- D2/D3 是纯运维人体工学改进，论证强度：机制设计常规论证（无统计验证，预期收益是操作步数下降，可实测验证）。

- D1.2 fallbacks 的有效性依赖两模型可互替（均为通用 chat 模型，E2 双端点 E2E 已验证各自可用）；但语义互替是近似（nemotron 1M ctx vs gpt-oss 32k conf），fallback 触发时长上下文任务会截断——**已知局限，接受**。

### 与既有 ADR/规则的关系

- 与 \[spec/infer-load/DESIGN.md]（B5 交付层）互补：该 spec 定义加载机制，本 ADR 定义其上的运维护栏。

- 与 Agent 生态升级调研（P0/P1/P2）正交但同批执行：opencode 升级并入其 P0。

- 不与"零自加载"原则冲突：看门狗是 timer 探测不是推理服务自启。

## 考虑的替代方案（Alternatives Considered)

### 替代方案 A: 上报盘式集群管理平台（否决）

- 优点: 功能全（Open WebUI/OneAPI/New API 生态成熟，E3）

- 缺点: 引入新常驻服务与新依赖链，违背"三机预算上限+最小运维面"既定约束；与既有 LiteLLM+Cockpit+Beszel 三件套职责重叠

- 否决理由: 问题是"操作入口分散"而非"功能缺失"，cluster.ps1 30 行 PowerShell 即可解决主诉

### 替代方案 B: systemd WatchdogSec 进程内看门狗（否决）

- 优点: 内核级 sd\_notify 集成，零额外进程

- 缺点: llama-server 不支持 sd\_notify（未集成 NOTIFY\_SOCKET 协议）；且挂死模态是**系统级冻结**（journal 静默、USB4 链路死亡，E2），进程自身看门狗在 CPU 冻结时同样失效

- 否决理由: 看门狗必须部署在冻结域之外（另一站或 timer+外部探测），方案 B 在目标故障模态下与被监控者同死

### 替代方案 C: 现状不动，仅补文档（推迟）

- 优点: 零成本

- 缺点: hang 模态无自愈（每次挂死损失 15-90min + 人工断电风险）；LiteLLM 单路由故障直抛

- 否决理由: 挂死已发生两次（E2），复发概率非小；D1 投入约半天，与单次挂死损失相当

## 后果（Consequences）

### 正面

- 挂死从"人工断电止损"升级为"分级自愈"（预期恢复时间 15-90min → <5min，待验证）

- 换模型操作从"记站名+ssh+infer-load"三步变一步 `cluster.ps1 load <model>`

- 目录可导航，一次性脚本归档后 git 历史可追溯（git mv 保 blame）

- 参数决策有台账，调优不再依赖记忆/聊天史

### 负面

- 目录重构一次性成本 \~1h + 全库相对链接修复风险（手册/调研 md 内链）

- 看门狗误报会触发不必要的 unload（可通过 N 次确认+通知缓冲）

- LiteLLM fallbacks 会掩盖一端故障（降级服务不易察觉，需配合告警）

### 中性 / 需要后续行动

- Beszel 告警现状未核实（`~/.config/beszel/` 在 B 站无配置目录，hub 疑为 Docker 部署，E1 未见配置文件）——D1.1 通知通道选型前需补查

- 手册"零自加载"表述需加注"（网关 litellm 除外）"

- D1.4 观测网与看门狗职责边界（观测网取证用、看门狗处置用）在实施时明确
