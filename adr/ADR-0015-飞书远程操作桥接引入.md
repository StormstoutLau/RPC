> **Feature**: 引入**一个**受控的常驻进程（`cc-connect`），把飞书消息桥接到 **B 站本机 Claude Code**
> （后端 = 本机 halogen `127.0.0.1:8731`），实现「手机发消息 → 站上代理执行 → 结果回飞书」。
> **背景**：调研与实测见 [2026-10-30_claude-code三站halogen接入与飞书远程操作调研](../docs/research/2026-10-30_claude-code三站halogen接入与飞书远程操作调研.md)。

> **与 ADR-0004 的关系**: **修订**——为「零自加载 / 无 daemon」开一个**唯一、可枚举**的例外，不推翻该纪律。

## 1. 背景与问题

用户在**手机**上想指挥站上的 Claude Code 干活（查状态、跑小任务、看结果），
而 Claude Code 是 **CLI 前台交互**，没有天然的移动端入口。

2026-10-30 实测（E1，见 [调研 §1](../docs/research/2026-10-30_claude-code三站halogen接入与飞书远程操作调研.md)）：

- 三站 claude 2.1.258，A/B 已接本机 halogen `127.0.0.1:8731`（`claude -p` rc=0）；
- 站上可达飞书开放平台域名（`open.larksuite.com` 200）；
- 外部已有成熟桥接（cc-connect / remote_claude / 官方 CLI），其中 **cc-connect 支持飞书长连接、无需公网 IP**。

**冲突点**：桥接是**常驻进程**，而 `ADR-0004` 第 2 条逐字写明
「零自加载纪律：venv/renv 激活即用、**无 daemon**；容器（尤其 docker/podman 需常驻 daemon）与之冲突」。
⇒ 不立 ADR 就上桥接 = 绕过纪律；立 ADR 才能把「例外」写成可审计的边界。

---

## 2. 决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | 引入 **cc-connect**（`chenhg5/cc-connect`）作为桥接实现 | 飞书**长连接**（出站 WebSocket，**无需公网 IP / 无入站端口**）；`config.toml` 直接支持 `agent=claudecode` + `platform=feishu`；带 Web 管理界面便于改配置；同时支持多平台，未来可扩 |
| **D2** | 部署在 **B 站**（master） | `nodes.env` 在此、出网实测正常、claude 已接本机 halogen；装主控会多一条隧道依赖 |
| **D3** | **对 ADR-0004 的唯一例外**：允许**一个**常驻进程 `rpc-bridge.service` | 例外必须**可枚举**（就这一个名字）；其余 daemon 仍禁止 |
| **D4** | 该 unit **`Restart=no` + `systemctl disable`**，只在人工 `start` 时运行 | 与 `llama-server@` 同风格：**不自加载、不自动重启**。崩了不拉活，人要它跑才跑 |
| **D5** | 模型侧**不引入新依赖**：桥接只调本机 `claude`，其后端仍是 halogen `127.0.0.1:8731` | 桥接不碰推理栈；halogen 停机时桥接只会报错，不会另起模型 |
| **D6** | 安全边界写死在配置里（见 §3），**禁止** `--dangerously-skip-permissions` | 手机消息 = 任意指令入口，必须锁范围 |
| **D7** | 桥接**不背书**：不纳入生产 SLA；故障不影响本地 Claude Code 与集群服务 | 避免把「便利通道」变成「必须常驻的关键路径」 |

## 考虑的替代方案（Alternatives Considered）

| 方案 | 未选的理由 | 何时会改选 |
|---|---|---|
| **remote_claude**（`yyzybb537/remote_claude`，E3） | 只做飞书、单用途；无多平台与管理面，维护面更窄 | 若只要「飞书 + 单一工作目录」且不想引入 Node 依赖 |
| **飞书官方 CLI**（`npx @larksuite/cli`，E3） | 方向相反：它让 Claude **操作飞书**，不能让手机**驱动 Claude** | 若后续要给 Claude 增加「读写飞书文档」能力 —— 作为**补充**而非替代 |
| **自建 webhook 回调** | 需公网 IP 或内网穿透，暴露面与 `ADR-0006`（控制面绑 LAN IPv4）冲突 | 若已有受控公网入口与反向代理，且愿意承担暴露面 |
| **tunnelbox / claude-mobile-bridge**（E3） | 走第三方 relay 云，代码与数据面外置，不符合「本仓自有通道」 | 若接受第三方 relay，且不需要飞书原生体验 |
| **不做桥接**（保持纯本地 CLI） | 手机无法驱动，但**零**新增常驻面 | **当前默认** —— 本 ADR 正是为明确解除该默认而立的 |

## 3. 边界（必须与配置逐条对齐）

| 边界 | 取值 | 判据 |
|---|---|---|
| 工作目录 | 单一 `work_dir`（建议 `/home/scott-lau/work`），**不含**仓库生产目录 | `config.toml` 的 `projects.agent.options.work_dir` |
| 飞书身份 | 仅响应**指定 user / 群**（白名单），忽略其他会话 | 桥接日志打出 `open_id`，非白名单直接丢弃 |
| 应用权限 | 最小集：`im:message`（收）+ `im:message:send_as_bot`（回）；**不申请**通讯录/文档写权限 | 飞书开发者后台 |
| 工具权限 | Claude Code 侧用 `--allowedTools` 白名单；默认需审批的等高危动作不放开 | unit 的 `ExecStart` |
| 进程身份 | 以**服务用户**（`RPC_USER`，见 `O-181`）运行，不 root | `systemctl show rpc-bridge -p User` |
| 网络面 | **仅出站**长连接；不新增监听端口 | `ss -ltnp` 无新增 |
| 审计 | 每条指令落 `journald`：时间 / `open_id` / 文本摘要 / 结果码 | `journalctl -u rpc-bridge` |

**非目标**：不做多用户；不做文件上传/图片；不做飞书文档写入；不做「让手机直接操纵生产集群」。

## 4. 后果

**正面**：手机上可用；与宿主机/集群服务**解耦**（停桥接不影响任何生产面）；例外只有一个名字，可被门禁点名。

**负面 / 代价**：
- 新增一个**需要人维护**的配置面（飞书 app_secret、`config.toml`）；
- 新增一条**出网**通道（虽然是出站）；
- 若 `work_dir` 选错，手机端可能改到不该改的目录 ⇒ §3 第一条是**硬边界**。

**对纪律的影响**：`ADR-0004` 的「无 daemon」从「绝对」变成「**默认禁止 + 一个显式例外**」——
这本身是退让，必须在台账里可查（见 §6 与 `OPEN-ISSUES` 的 cross-ref）。

## 5. 验证与回滚

**上线前（缺一不可）**
1. `systemd-analyze verify` 通过；unit 里 `Restart=no`、`User=<服务用户>`、`WantedBy` 不启用；
2. 桥接只在白名单会话响应（用非白名单账号发一条，日志应丢弃）；
3. `ss -ltnp` 无新增监听；
4. `journalctl` 能看到审计三要素（时间 / open_id / 结果码）。

**回滚（一条命令）**
```bash
sudo systemctl stop rpc-bridge && sudo systemctl disable rpc-bridge
# 彻底移除：删 unit + config.toml + 飞书应用停用
```
**不影响面**：Claude Code 本地使用、halogen、deepseek、门禁 —— 均不依赖桥接。
