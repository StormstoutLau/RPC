## 背景（Context）

1. **存量已经失控（E1）**：`ops/` 下 git 跟踪的**脚本共 256 个**，其中 **230 个属历史一次性脚本** ——
   `ops/station-bin/_*.sh` 一片（`_aportchk.sh` / `_bportchk.sh` / `_astate.sh` / `_bocdbg.sh` /
   `_qwen27_*.sh` …），另有 `repro-*.sh` ×6、`check_llama_version.{sh,py,ps1}`、`make-dashboard.ps1` 等。
   命名本身就承认了性质：`_` 前缀 = "临时的"。
2. **它们与统一入口能力重复（E1）**：端口/状态/加载/卸载/凭据/出站/版本/观测这几类动作，
   `cluster.py` 与 `cluster_web.py` 都已有对应子命令或卡片，而且是**三站一次做完 + 有判据 + 有台账**；
   而 `_xxx.sh` 是**单站、无判据、无留痕**的一次性动作，做完没人再读。
3. **它带来的不是便利而是复利式债务**：每次新需求 → 再写一个脚本 → 下次要改同一件事时，
   得先判断"该改哪一个"；改错了没人知道（没有门禁看它们）。这正是 ADR-0001 记录的
   "40+ 手工校验脚本却没有总入口"的同类问题，只是发生在管理面上。
4. **既有纪律已作方向性表态、但缺执行**：手册早已写"多个 Python 工具应并入 cluster.py 子命令"、
   方案 v2 把观测类能力逐项收进入口（`reqlog` / `ttl` / `agent` / 各 flow）。缺的是**拦住新增**的机制 ——
   只靠自觉的规则在本仓库被证明会失效（同 2026-09-14 调研的方法论教训）。
5. **`tmp/` 通道已存在且被 `.gitignore` 覆盖（E1）**：一次性验证脚本有正确去处，
   不需要占用 `ops/` —— 本会话的验证脚本（`_verify_agent_p0.py` 等）全部落在 `tmp/`，不入库。

---

## 决策（Decision）

### D1. 唯一管理面 = `ops/cluster.py`（+ 同一入口的 web 形态 `ops/cluster_web.py`）
所有**管理操作**（集群/模型/凭据/出站/观测/门禁/流程）一律从统一入口执行：
CLI 子命令，或 web 卡片（同一份取数实现）。**不再新增并列入口**。

### D2. 存量冻结：`inventory/ops.yaml` 登记 + 门禁断言（只减不增）
- 登记表三张清单：`entry`（入口本体）· `station_runtime`（被调方）· `frozen_ops_scripts`（历史存量）。
- 新增断言 `scripts`（`ops/rpc_check.py`，quick 项，进 pre-commit/pre-push）：
  `ops/` 下任何脚本必须 ∈ 三张清单之一，否则 **FAIL**；入口件缺失亦 FAIL。
- 依据与 `plugins.yaml` 的 `known_drift`、`models.yaml` 的 `non_model_conf` **同一套纪律**：
  真实差异可登记，但登记这个动作本身要在 review 里可见。
- **断言范围 = git 跟踪文件**（与门禁其余各项一致）：新脚本在 `git add` 后即进入范围，
  故 **pre-commit 就能拦住**（实测：新增未登记脚本 → `未登记 1` → FAIL 并点名）。
  反向推论：把一次性脚本放在 `tmp/`（已 gitignore）永远不会被本断言看到 —— 这正是想要的边界。

### D3. 新增脚本只有三条合法路径（按优先级）
| 序 | 情形 | 做法 |
|---|---|---|
| ① | **默认**：这是一项管理能力 | 给 `cluster.py` 加子命令（+ 需要时在 web 加卡片）；一次覆盖三站、带判据 |
| ② | 它是**被入口/systemd 调起的站上运行时件** | 加进 `station_runtime`（如 `infer-load`、`cluster-ttl`） |
| ③ | 确需独立一次性脚本 | 加进 `frozen_ops_scripts` + **在提交信息里说明为何不能并入入口** |
| — | 临时验证/探针脚本 | **放 `tmp/`**（gitignore 覆盖；本断言看不到它，也不该看到） |

### D4. 例外边界：什么算"站上运行时件"而不是"并列入口"
判据 = **它是否自带管理语义**：
- 有子命令/参数解析/状态输出，能被人直接当命令用 → 属**入口**，必须并入 D1（否则就是并列入口）。
- 只是被调起的实现细节（读 conf 起进程、探端口、采一次指标）→ 属 `station_runtime`。

### D5. 清减顺序：**先补入口能力，再删脚本**（顺序不能反）
冻结清单里的脚本逐条判：能力已被入口覆盖 ⇒ 删；能力仍需要 ⇒ **先**给入口加子命令/卡片，
验证通过 **再**删脚本，并在同一次提交里把它从 `inventory/ops.yaml` 移除。

**已核实的清减候选（E1，可作为第一批）**

| 存量脚本 | 入口已有 | 证据 |
|---|---|---|
| `ops/station-bin/_aportchk.sh` / `_bportchk.sh` | `rpc_check.py --only ports,stations`（端口真值表自洽 + 三站占用对账） | P1-4 落地：表内自洽 + 站上占用对账，且注入故障 16/16 抓到 |
| `ops/check_llama_version.{sh,py,ps1}` | `cluster.py versions`（三站引擎版本矩阵）+ web「引擎版本矩阵」卡片 | `cmd_versions` 存在且手册已收录 |
| `ops/station-bin/make-dashboard.ps1` + `dashboard.html` | web「Agent 任务」卡片 + `cluster.py agent` | 本会话 P1 落地；快照不标新鲜度，已被取代 |

> 其余 200+ 条需逐条判（不做"看不出来就批量删"这种危险动作）。

## 否决/比较对象

| 方案 | 结论 | 理由 |
|------|------|------|
| 只写"以后别新增脚本"的文档、不设门禁 | ❌ 否决 | 本仓库已多次证明只靠自觉会失效（空头承诺）；规则必须绑定执行 |
| 一次性删除全部 `_*.sh` | ❌ 否决 | 其中确实有**唯一实现**（golden 测试、评测冒烟、一次性迁移），盲删会丢能力 |
| 用目录约定（把一次性脚本移进 `archive/`） | ❌ 否决 | 仍是"攒着"，且新脚本照样会长；问题不是位置而是**没有断言** |
| 把 `tmp/` 也纳入门禁 | ❌ 否决 | `tmp/` 是**刻意的**临时区（已 gitignore）；门禁看 git 跟踪文件即可 |
| 允许"随手写、事后登记" | ⚠ 保留但收紧 | 登记仍在同一提交内完成 → review 可见；不登记即 FAIL |

## 后果与待办

**已完成（2026-09-15）**
- `inventory/ops.yaml`（entry 4 / station_runtime 22 / frozen 230，共 256 个脚本全登记）
- `ops/rpc_check.py` 新增断言 `scripts`（quick 项）→ 门禁现在会拦住新增脚本
- 本 ADR + 手册纪律 + 项目记忆（跨会话遵守）

**待办（按 D5 顺序，逐条做）**
1. 第一批清减候选 3 组（上表），每组：确认入口覆盖 → 删脚本 → 从 `inventory/ops.yaml` 移除
2. 其余冻结项分类（"仅存一次性调查"可直接删 / "能力仍需要"须先补入口）
3. 长期：`frozen_ops_scripts` 单调递减；`ops/` 目录逐步收敛到"入口 + 运行时件 + 真值表 + 文档"

**风险**
- 冻结清单可能掩盖"某脚本其实仍被引用"——缓解：删除前用 `grep` 反查引用（站上/systemd/其他脚本）
- 例外路径 ③ 可能被滥用成"照着登记就过"——缓解：`fix` 文案明确要求**在提交信息里说明理由**，且登记条目数可见
