## 背景（Context）

1. **存量已经失控（E1）**：`ops/` 下 git 跟踪的**脚本共 256 个**，其中 **230 个属历史一次性脚本** ——
   `ops/station-bin/_*.sh` 一片（`_aportchk.sh` / `_bportchk.sh` / `_astate.sh` / `_bocdbg.sh` /
   `_qwen27_*.sh` …），另有 `repro-*.sh` ×6、`check_llama_version.{sh,py,ps1}`、`make-dashboard.ps1` 等。
   命名本身就承认了性质：`_` 前缀 = "临时的"。
2. **它们与统一入口能力重复（E1）**：端口/状态/加载/卸载/凭据/出站/版本/观测这几类动作，
   `cluster.py` 与 `cluster_web.py` 都已有对应子命令或卡片，而且是**三站一次做完 + 有判据 + 有台账**；
   而 `_xxx.sh` 是**单站、无判据、无留痕**的一次性动作，做完没人再读。
3. **它带来的不是便利而是复利式债务**：每次新需求 → 再写一个脚本 → 下次要改同一件事时，
   得先判断"该改哪一个"；改错了没人知道（没有门禁看它们）。这正是 ADR-0001 记录的
   "40+ 手工校验脚本却没有总入口"的同类问题，只是发生在管理面上。
4. **既有纪律已作方向性表态、但缺执行**：手册早已写"多个 Python 工具应并入 cluster.py 子命令"、
   方案 v2 把观测类能力逐项收进入口（`reqlog` / `ttl` / `agent` / 各 flow）。缺的是**拦住新增**的机制 ——
   只靠自觉的规则在本仓库被证明会失效（同 2026-09-14 调研的方法论教训）。
5. **`tmp/` 通道已存在且被 `.gitignore` 覆盖（E1）**：一次性验证脚本有正确去处，
   不需要占用 `ops/` —— 本会话的验证脚本（`_verify_agent_p0.py` 等）全部落在 `tmp/`，不入库。

## 决策（Decision）

### D1. 唯一管理面 = `ops/cluster.py`（+ 同一入口的 web 形态 `ops/cluster_web.py`）
所有**管理操作**（集群/模型/凭据/出站/观测/门禁/流程）一律从统一入口执行：
CLI 子命令，或 web 卡片（同一份取数实现）。**不再新增并列入口**。

### D2. 存量冻结：`inventory/ops.yaml` 登记 + 门禁断言（只减不增）
- 登记表三张清单：`entry`（入口本体）· `station_runtime`（被调方）· `frozen_ops_scripts`（历史存量）。
- 新增断言 `scripts`（`ops/rpc_check.py`，quick 项，进 pre-commit/pre-push）：
  `ops/` 下任何脚本必须 ∈ 三张清单之一，否则 **FAIL**；入口件缺失亦 FAIL。
- 依据与 `plugins.yaml` 的 `known_drift`、`models.yaml` 的 `non_model_conf` **同一套纪律**：
  真实差异可登记，但登记这个动作本身要在 review 里可见。
- **断言范围 = git 跟踪文件**（与门禁其余各项一致）：新脚本在 `git add` 后即进入范围，
  故 **pre-commit 就能拦住**（实测：新增未登记脚本 → `未登记 1` → FAIL 并点名）。
  反向推论：把一次性脚本放在 `tmp/`（已 gitignore）永远不会被本断言看到 —— 这正是想要的边界。

### D3. 新增脚本只有三条合法路径（按优先级）
| 序 | 情形 | 做法 |
|---|---|---|
| ① | **默认**：这是一项管理能力 | 给 `cluster.py` 加子命令（+ 需要时在 web 加卡片）；一次覆盖三站、带判据 |
| ② | 它是**被入口/systemd 调起的站上运行时件** | 加进 `station_runtime`（如 `infer-load`、`cluster-ttl`） |
| ③ | 确需独立一次性脚本 | 加进 `frozen_ops_scripts` + **在提交信息里说明为何不能并入入口** |
| — | 临时验证/探针脚本 | **放 `tmp/`**（gitignore 覆盖；本断言看不到它，也不该看到） |

### D4. 例外边界：什么算"站上运行时件"而不是"并列入口"
判据 = **它是否自带管理语义**：
- 有子命令/参数解析/状态输出，能被人直接当命令用 → 属**入口**，必须并入 D1（否则就是并列入口）。
- 只是被调起的实现细节（读 conf 起进程、探端口、采一次指标）→ 属 `station_runtime`。

### D5. 清减顺序：**先补入口能力，再删脚本**（顺序不能反）
冻结清单里的脚本逐条判：能力已被入口覆盖 ⇒ 删；能力仍需要 ⇒ **先**给入口加子命令/卡片，
验证通过 **再**删脚本，并在同一次提交里把它从 `inventory/ops.yaml` 移除。

**已核实的清减候选（E1，可作为第一批）**

| 存量脚本 | 入口已有 | 证据 |
|---|---|---|
| `ops/station-bin/_aportchk.sh` / `_bportchk.sh` | `rpc_check.py --only ports,stations`（端口真值表自洽 + 三站占用对账） | P1-4 落地：表内自洽 + 站上占用对账，且注入故障 16/16 抓到 |
| `ops/check_llama_version.{sh,py,ps1}` | `cluster.py versions`（三站引擎版本矩阵）+ web「引擎版本矩阵」卡片 | `cmd_versions` 存在且手册已收录 |
| `ops/station-bin/make-dashboard.ps1` + `dashboard.html` | web「Agent 任务」卡片 + `cluster.py agent` | 本会话 P1 落地；快照不标新鲜度，已被取代 |

> 其余 200+ 条需逐条判（不做"看不出来就批量删"这种危险动作）。

## 实施记录：第一批清减（2026-09-15）

**D5 当场拦下了我自己的一处误判 —— 这正是这条顺序存在的意义**

上表把 `check_llama_version.*` 标为"可删"，理由是"`cluster.py versions` 已覆盖三站版本矩阵"。
真按 D5 逐条核对时发现**覆盖不完整**：

| 事实（E1） | 结论 |
|---|---|
| 旧脚本做 **MANIFEST 全量 `md5sum -c`** + 读 `rpc_protocol` | 入口的 `versions` 两样都没有 |
| 入口的"完整性"列三站全显示 **缺失** | 它只找 `MANIFEST.md5`，而站上文件叫 **`MANIFEST`**（md5 段在第 10 行起）⇒ **长期假阴性**：能力看着坏了，其实数据一直在 |
| 旧脚本里 C 站 IP 仍是 `192.168.1.24`（现为 `192.168.1.37`） | 旧脚本对 C 站**本就跑不通**（exit 2） |

**动作（顺序不可反）**：先把能力并入入口 → 验证 → 再删脚本。

1. `_VER_SCAN` 的完整性段改为：有 `MANIFEST.md5` 用它，否则用 `MANIFEST` 的 `[md5]` 段（`tail -n +10`）；
   并把 `rpc_protocol` 纳入采集与三站一致性比对。
2. **顺带修掉第二个真缺陷 —— locale 陷阱**：站上 `LANG=zh_CN.UTF-8`，`md5sum -c` 打印"**成功**"
   而不是 `OK` ⇒ 按英文文本解析会把**全部通过**读成"**全 FAILED**"（实测首跑就是这样）。
   修法：`LC_ALL=C md5sum -c`。**凡是解析命令输出的地方都必须锁 locale** —— 与 memory 里
   "`free` 输出随 locale 变化 ⇒ 改读 `/proc/meminfo`" 是同一条教训的复发。
3. 验证：`cluster.py versions` → 三站 `完整性 79 OK`、`rpc_protocol v6.0.0` 三站一致。
4. 删除 7 个文件：`_aportchk.sh` `_bportchk.sh` `check_llama_version.{sh,py,ps1}` `make-dashboard.ps1`
   `dashboard.html`（后两个中 `dashboard.html` 非脚本，不入登记表）；`inventory/ops.yaml` 重新生成
   （脚本 256 → 250，冻结存量 230 → 224）；**站上无残留副本**（三站 `NONE`）。
5. 引用修正：手册（`dashboard.html` → 已删）、`spec/vulkan-version-control/UPGRADE_SOP.md`
   （`check_llama_version.sh --deep` → `cluster.py versions`，并注明旧脚本 C 站 IP 过时）。
   历史记档（`docs/DEV-LOG-008`、`.trae/documents/*`、`docs/security/2026-09-13_*` 事故清单、
   `archive/*`）**有意不动** —— 它们记录的是当时的事实，不属于"指向未来的指令"。

> 第一批的经验：**"能力看起来重复" 不等于 "能力已被覆盖"**。判断必须落到"逐项功能对得上"，
> 而不是"入口有个名字差不多的子命令"。这也是本 ADR 把清减顺序写成硬步骤的原因。

## 实施记录：第二批清减（2026-09-15）

**判据换成更强的两条（可机械判定）**：第一批用的是"能力是否已被入口覆盖"（需逐条判断，且我判断错过一次）。
第二批改用两条**不需要判断能力**的判据 —— 满足任一条即可删，因为**脚本本来就跑不通或跑起来有害**：

| 判据 | 数量 | 说明 |
|---|---|---|
| ① 脚本自标 `DEPRECATED` / `勿执行` | 8 | 密钥脱敏后逻辑失效，且**重跑会把 `***REMOVED***` 占位符写进生产配置**（opencode/claude settings） |
| ② 含 `***REMOVED***` 占位密钥 + 认证必需 | 19 | 密钥已被脱敏成占位符 ⇒ **认证请求必然 401**，脚本已是空壳（含 4 个 `_bench*.py` unsloth 基准，能力已由 `flow bench` 承接） |
| ③ 目标子系统已退役 | 4 | `_bs2_*` 是 LiteLLM 网关（`:4000`，2026-09-13 退役）的探针 ⇒ 靶子不存在 |

**结果**：脚本 250 → **219**（冻结存量 224 → **193**）；git 跟踪文件里含占位密钥的从 36 个降到 **5 个**
（其余 5 个是：两份 security 事故记档、`spec/d2-cluster-cli/IMPLEMENTATION.md`、本 ADR 引用的 runbook、
以及 `ops/cluster.py` 里那条"占位符不命中"的检测器注释）。

**引用反查（删前必做）抓出一处真正的操作风险**：
`ops/station-bin/REPRO-RUNBOOK.md`（**活跃操作手册**）在 §1.3 与 §3 仍写着
"unsloth 重铸 key 后**必须重跑 `_bkeyupdate.sh`**" —— 而该脚本 2026-09-13 已标"勿执行"。
**照着手册操作会把占位符写进生产配置**。已改为走入口：

```powershell
python ops/cluster.py secrets status   # 看落点/引用/权限
python ops/cluster.py secrets push     # 从主控正本 secrets/stations/<站>/ 下发
python ops/cluster.py providers        # 复验 provider/默认模型无漂移
```

> 即"删脚本"顺带修掉了一处**会按旧手册踩坑**的隐患 —— 这正是 ADR-0004 想要的副作用。

**反查结论**：三站 `/usr/local/bin` 与 `/tmp` **均无副本**、systemd 单元不引用；仓库内 12 处引用
**全部属历史记档**（`DEV-LOG-011`、`docs/security/2026-09-13_*` 事故/轮换清单、`ADR-0002`、
`spec/model-eval/results-ledger.md`、`archive/*`）—— **有意保留**（记录当时事实）。
唯一"指向未来"的一处是 `docs/双端点部署与opencode混合框架调研.md` 把 `_bs2_*` 当"可复用先例"，
已改为指向 **git 历史**。

## 实施记录：第三批清减（2026-09-15）

**判据（比第二批更机械）：脚本显式引用已不存在的靶子** —— 由 `grep` 判定，不需要任何主观判断：

| 簇 | 数量 | 靶子状态（实测） |
|---|---|---|
| LiteLLM 网关簇 `_bs2*` ×8 + `_bcur.sh` | 9 | `:4000` 在**主控与三站均无监听**；三站 `ps -eo args` **无 litellm 进程**（网关 2026-09-13 退役） |
| claude 死端口写配置 `_acldset.sh` `_acldoverride.sh` `_acldofficial.sh` | 3 | 硬编码 `ANTHROPIC_BASE_URL=http://127.0.0.1:8087` —— 该端口**未登记且全集群无监听**；而现行生产配置是 `:8080` + 真实 token（B 站 `~/.claude/settings.json` 实测） |

**`_acldset.sh` / `_acldoverride.sh` 还带额外风险**：它们会**整体覆盖**生产 `settings.json`，写成
死端口 + `ANTHROPIC_AUTH_TOKEN='dummy'` ⇒ 今天跑一次就把 claude 打断。其作用（同步 claude/opencode
配置到后端）已由 `cluster.py secrets push`（正本在主控 `secrets/stations/<站>/`）承接。

**⚠ 本次核查中我自己踩了一次 `pgrep -f` 自匹配（值得记下）**：
第一版核实写的是 `ssh host 'pgrep -f litellm'` —— 三站**全部**报 `RUNNING`。
真因：`ssh` 那侧的包装 shell **命令行里就含 "litellm" 这个模式**，`pgrep -f` 匹配到了它自己。
**改用 `ps -eo args | awk` 实查才得到真相（三站都没有 litellm 进程）。**
教训：**跨 ssh 的 `pgrep -f` 必然自匹配**（包装层自带模式）；这与 RPC 排查时那条 `pgrep -f` 陷阱同源，
只是这次犯在我自己的核查脚本里。凡"进程是否存在"的判据，一律走 `ps args` / `pgrep -x` 并核对全文。

**结果**：脚本 219 → **207**（冻结存量 193 → **181**）。
**引用反查**：仓库内除登记表**零引用**；三站 `/usr/local/bin`、`/tmp`、`$HOME` **无副本**；systemd 不引用
⇒ 本批**无需改动任何文档**。

## 否决/比较对象

| 方案 | 结论 | 理由 |
|------|------|------|
| 只写"以后别新增脚本"的文档、不设门禁 | ❌ 否决 | 本仓库已多次证明只靠自觉会失效（空头承诺）；规则必须绑定执行 |
| 一次性删除全部 `_*.sh` | ❌ 否决 | 其中确实有**唯一实现**（golden 测试、评测冒烟、一次性迁移），盲删会丢能力 |
| 用目录约定（把一次性脚本移进 `archive/`） | ❌ 否决 | 仍是"攒着"，且新脚本照样会长；问题不是位置而是**没有断言** |
| 把 `tmp/` 也纳入门禁 | ❌ 否决 | `tmp/` 是**刻意的**临时区（已 gitignore）；门禁看 git 跟踪文件即可 |
| 允许"随手写、事后登记" | ⚠ 保留但收紧 | 登记仍在同一提交内完成 → review 可见；不登记即 FAIL |

## 后果与待办

**已完成（2026-09-15）**
- `inventory/ops.yaml`（entry 4 / station_runtime 22 / frozen 230，共 256 个脚本全登记）
- `ops/rpc_check.py` 新增断言 `scripts`（quick 项）→ 门禁现在会拦住新增脚本
- 本 ADR + 手册纪律 + 项目记忆（跨会话遵守）

**待办（按 D5 顺序，逐条做）**
1. 第一批清减候选 3 组（上表），每组：确认入口覆盖 → 删脚本 → 从 `inventory/ops.yaml` 移除
2. 其余冻结项分类（"仅存一次性调查"可直接删 / "能力仍需要"须先补入口）
3. 长期：`frozen_ops_scripts` 单调递减；`ops/` 目录逐步收敛到"入口 + 运行时件 + 真值表 + 文档"

**风险**
- 冻结清单可能掩盖"某脚本其实仍被引用"——缓解：删除前用 `grep` 反查引用（站上/systemd/其他脚本）
- 例外路径 ③ 可能被滥用成"照着登记就过"——缓解：`fix` 文案明确要求**在提交信息里说明理由**，且登记条目数可见
