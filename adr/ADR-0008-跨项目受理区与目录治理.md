## 背景（Context）

1. **现状：转运包角色混叠（E1）**。`D:\Paper\handoff_to_rpc_admin` 放在**项目根**（`D:\Paper\`）
   之下，但它的角色是"需求方 → 机群管理员"的**跨信任域交接**。这个放置方式有以下问题：
   - **归属错位**：机群侧（`d:\RPC`）无法一眼看到"有哪些待受理请求"——要逐个项目根去翻。
   - **无生命周期**：`01_DR/02_CR/03_接口` 提交后，没有 `已裁决/已受理/已执行/已关闭` 的状态迁移，
     全靠人工记忆。
   - **无管理员视角**：管理员需要的是一份"待我裁决的队列"，而非散落各处的文档集。
   - **防上站靠项目 `.agentsync` 排除**（`handoff_to_rpc_admin/` 在 D:\Paper\.agentsync 中），
     而非受理区自身的主权。

2. **框架已有项目登记，但缺"受理"维度（E1）**。`agent-cli.ps1` `$Script:PROJECTS` 已注册
   `paper / Cpp_Hub / Auto_Prover`；`inventory/impact.yaml` 只登记模型/端口/配置/凭据四维，
   **没有"项目"维度的受理状态**。即：一个项目"是否已被机群受理、当前处于什么阶段"没有权威真值点。

3. **未来是"频繁受理"而非"偶尔一次"（E1，用户明示）**。因此需要一套**可复用、可排序、可审计**的
   目录范式，而不是为 `handoff_to_rpc_admin` 单独打一个补丁。

---

## 决策（Decision）

**在机群侧建立统一受理区 `d:\RPC\inbox\`**，每个跨项目请求 = 一个带日期的标准目录；需求方
原始包冻结、管理员裁决另存、生命周期用状态目录标记。并列：`$PROJECTS` 只登记**已受理/运行中**的项目，
inbox 待受理项目**不入台**，裁决通过后才进 `$PROJECTS`。

### 目录结构（拟采纳）

```
d:\RPC\inbox\                      # 机群侧统一受理区（新增，git 管理，门禁覆盖）
   README.md                       # 受理流程 + 状态机 + 验收标准（指向手册 §1.3）
   <project>-<yyyy-mm-dd>\        # 每笔受理（如 paper-2026-08-23）
      00_handoff\                 # 需求方提交的原始转运包（只读冻结，不被项目改动）
         01_DR-缺陷报告.md
         02_CR-变更需求.md
         03_编排与接口约定.md
         04_证据附录.md
         05_项目级配置\
      10_admin\                   # 管理员的裁决与回复（新增，非覆写需求方原件）
         裁决报告.md              # 逐条 DR/CR/接口确认打分与裁定
         受理决定.md              # 采纳/拒绝/替代，及最终受理边界
      20_plan\                    # 派发计划 / 任务卡模板
      30_evidence\                # 执行台账 / 回收产物指针（产物本身仍在 D:\<proj>\agent-out）
      40_state\                   # 生命周期标记：open → triage → accepted → running → done | rejected
```

### 关键设计决策（D1–D6）

- **D1 受理区在机群侧 `d:\RPC\inbox\`，不放各项目根**：管理面（跨项目、跨信任域）与
  `$PROJECTS` 注册、`impact.yaml`、门禁同属机群治理。项目根只留单项目专属内容。
- **D2 每笔 = `<project>-<date>` 目录**：天然唯一 + 可按日期排序，避免 "handoff" 这个词太泛、
  也避免后续 "handoff2/3"。
- **D3 `00_handoff/` 冻结 + `10_admin/` 新增**：职责分离，需求方原件只读不覆写（审计），
  管理员回复是新增文件（非改需求方原件）——守住"单源"纪律 + 可追溯。
- **D4 标注 `sensitivity` / 数据轨**：每笔受理标注轨 L（local-only）/ 轨 P（public），
  延续转运包 §3 的分轨合规。受理区本身**默认不进站**（门禁排除），杜绝未发表语料随 sync 上站。
- **D5 与框架咬合**：`$PROJECTS` 只登记已受理/运行中项目；inbox 待受理项目**先不入台**，
  裁决通过后才进。语料预处理（如 phase2）仍属项目侧，机群只认"卡 + 队列"。
- **D6 门禁集成（可选增强）**：`scripts` 断言或新增 `inbox` 断言，校验每个 inbox 目录有
  `00_handoff/` 且（若有 `10_admin/` 则状态非 triage）——避免受理区自身腐化。

---

## 选的理由（Why）

1. **符合 ADR-0004"统一管理面"纪律**：受理是管理动作，应集中在机群一个入口，而非散落项目根。
2. **生命周期可查**：`40_state` 状态机让"哪些待裁、哪些运行中、哪些已关闭"一眼可见。
3. **可追溯 / 可审计**：`00_handoff` 冻结 + `10_admin` 新增，完整保留"需求方提交了什么 → 管理员怎么裁"。
4. **对未来项目可复用**：标准目录模板 + 状态机，新增一个项目请求 = 复制模板 + 填内容。
5. **与现有框架天然咬合**：用 git 管理 + 门禁覆盖，受理本身可分支、可回滚；`$PROJECTS` 回归
   "只登已受理项目"的清晰语义。

---

## 被否的方案（Alternatives Considered）

1. **维持现状（转运包放项目根）**：不新增结构，最小改动。**否**：无法支撑"频繁受理"，无统一入口、
   无生命周期、跨项目散落。只适合"偶尔一次"。
2. **给每个项目根固定一个 `handoff/` 子目录**：统一了"项目内的受理目录名"，但**仍是项目侧**，
   管理员仍要翻各项目根找待办；且项目侧目录与站上 `.agentsync` 存在天然纠缠。**否**。
3. **用标签/看板（如 ledger 行）代替目录**：轻量，但**缺载体**——DR/CR/证据附录需要文件落盘，
   无目录则这些无家可归。**否**（可作为状态的可选可视化，不替代目录）。
4. **直接进 `$PROJECTS` + 台账**：跳过了"受理前"阶段。**否**：待受理项目还没有执行形态，不宜
   与已受理项目同列；且跳过裁决会让 `$PROJECTS` 语义从"已受理"污染为"被请求过"。

## 影响（Impact）

- **新增**：`d:\RPC\inbox\` 目录树 + README + 模板。
- **迁移**：`D:\Paper\handoff_to_rpc_admin` 作为第一笔受理，**复制**到
  `d:\RPC\inbox\paper-2026-08-23\00_handoff\`（复核用）；项目侧原目录标记
  `(archived see d:\RPC\inbox)` 并继续被 `.agentsync` 排除。
- **门禁**：可选新增 `inbox` 断言（或并入 `scripts`），校验目录结构完整性，防受理区腐化。
- **手册**：§1.3 增加"受理区位置与流程"指针。

## 实施记录：第二批治理（2026-09-23，两份调研合并落地）

> 合并来源：[inbox 社区 review](../docs/2026-09-23_inbox受理区_社区review与改进建议.md) +
> [受理协商协议与交付证据束 标准调研](../docs/2026-09-23_受理协商协议与交付证据束_标准调研.md) +
> [合并实施计划](../docs/2026-09-23_inbox治理_合并实施计划.md)。

**本次把 inbox 从"单向受理容器"升级为"双向协商 + 交付证据束"治理面**：

1. **状态机扩展**（协商回环 + 验收签收）：
   `open → triage ⇄ waiting → accepted → plan-review ⇄ plan-revise → running → release → done
   → accepted-by-requester | rejected-by-requester`（`rejected` 可从中间任一进入）。
   新增 `waiting`（等需求方/外部条件，区别于 triage 主动处理）、`plan-review/plan-revise`（方案复核回环）、
   `release`（交付证据束等验收）、`accepted-by-requester/rejected-by-requester`（验收签收终态）。
   `done` 语义收敛为**运维结案**，与需求方**验收签收**解耦；新需求开新 `open`，不重写旧状态。
2. **STATE 结构化 + LOG**：`40_state/STATE` 文本 → `STATE.json`（`state`/`updated_at`/`by`）+
   `LOG.md` 追加式变更记录；复核意见落 `10_admin/复核意见-N.md`，`20_plan` 修订留版本 vN。
3. **`inbox` 门禁断言（quick 已启用）**：校验每个 `<proj>-<date>/` 有 `00_handoff/`、
   `STATE.json` 合法且 state ∈ 白名单、状态内容自洽（`accepted+` 须有受理决定 / `plan-review+` 须有
   `20_plan` / `release+` 须有 `30_evidence`）。**先验红**：注入 `release`（30_evidence 仅占位）⇒ FAIL 点名，
   还原 ⇒ PASS。
4. **聚合入口**：`cluster.py inbox` 列出所有受理目录 + state + updated_at（一行一条）。
5. **web 跨项目进度看板 + 待办聚合**（`cluster_web.py` 受理区卡片，随 ADR-0004 管理面）：
   15s 自动刷新、按"需要动作"分组（`waiting`/`plan-review`/`release` 高亮 · 进行中 · 已关闭折叠）、
   健康快照（共 N 笔 · 需动作 M · 进行中 K），并从状态机**派生每笔"下一动作"**（待办聚合，零人工维护）。
   数据源 = 各笔 `40_state/STATE.json`（派生视图）。自证：HTTP 端到端（带 token 200 / 无 token 401）+
   多项目分组分离 + **门禁交叉验证**（看板分组与 `inbox` 门禁同判状态语义）。
6. **交付证据束标准**：`30_evidence/` 结案时以 `MANIFEST.sha256` 钉死 `agent-out/<ts>/` 的
   run.json + 单 run 证据束；未附证据束不 `done`；`done` 后 artifact freeze；验收判据 =
   "重放验证、非重放生成"（沿 ADR-0007）；交付物标注 `Reproduced`/`Replicated` 分级；环境快照
   （`cluster.py versions`）随证据束落档。
7. **容量预估**：`20_plan/` 模板加墙钟/站占用窗口预估段（业务判断，不强制）。
8. **交付证据束：判据收紧 + 生成工具**（2026-09-23 追加）：
   - **收紧**：`release`/`done`/`accepted-by-requester` 三态**必须存在 `30_evidence/MANIFEST.sha256`**
     （原判据只要求"目录非空"⇒ 放个无关文件即可过，「未附证据束不 `done`」形同虚设）。
     `rejected-by-requester`（可能交付前就终止）只保留"非空"。
     先验红：置 paper 为 `release` ⇒ FAIL 并点名生成命令；还原 ⇒ PASS。
   - **工具**：`cluster.py inbox seal <proj-dir> [--run <ts>|--all-runs] [--grade …] [--go]`
     —— 把项目根 `agent-out/<ts>/` **实际存在的全部证据件**逐个 sha256 写入
     `30_evidence/MANIFEST.sha256`（与 `00_handoff` 同格式，`sha256sum -c` 可校验）。
     proj→项目根真值取自 `agent-cli.ps1` 的 `$Script:PROJECTS`（不另抄一份）；默认只出计划。
   - **为什么钉"实际存在的文件"而非 `AGENT_EVIDENCE_FILES` 那 6 件**（实测）：真实 run 目录**不齐**
     那 6 件（`judgment-record.txt`/`accept-*` 仅在配 accept/golden 的任务里存在）——
     那 6 件是**链校验的"声明件"**，不等于"本次交付束"，硬套会导致常态失败。
   - **闭环自证**：`--go` 生成后独立复验 5/5 匹配；改坏 1 行 ⇒ 恰好报 1 条不匹配（判据非恒真）；
     清单在 + 交付态 ⇒ 门禁由 FAIL 转 PASS。

**回滚**：各件均独立可回滚（删模板/README 条目/断言条目/`cluster.py inbox` 分发即可）；
纸面为纯新增，不废除既有路径。
