### 本轮取证：三处"状态已过时"（写在计划之前，避免建在错前提上）

| 原表述 | 实测（2026-09-17） | 处置 |
|---|---|---|
| 「门禁对 agent 证据**零覆盖**」（缺口 7） | ❌ **已闭环** —— `rpc_check.py` 第 15 项断言 `evidence`（`quick=True`，进 pre-commit/pre-push） | 从待办移除；见 §阶段路线 |

| 「台账 `queue_s/run_s` **恒 0**」（缺口 6） | ◐ **形态被改写** —— `.agent-run.json` 的 queue/run **有值**（65 run 中 **61 / 57 非零**）；真正恒 0 的是**台账 `agent-runs.log` 的两列**：[:1207](../ops/station-bin/agent-cli.ps1#L1207) 硬编码 `"$ts,$proj,$id,$sens,$code,0,0"`，而 `$queue_s/$run_s` 在 [:1165-1183](../ops/station-bin/agent-cli.ps1#L1165-L1183) **就已解析好**（写台账在其后） | 缺口 6 从"补计量"降级为**一行接线**；归入批 B |

> **方法论**：这三处都是"**文档写的状态 ≠ 代码当前状态**"。故本 ADR 第 1 件事不是排计划，而是**用实测把前提钉住** —— 与 ADR-0006「判据必须自证不静默降级」同一纪律。

### 真正的卡点：不是工作量，是**改动窗口**

阶段 1 与阶段 2 的剩余项、以及缺口 4/5/6/8/10，**全部需要修改 `agent-cli.ps1`（派发关键路径）**。而该路径的改动在本框架里存在一个硬约束：

- **无活模型 + 无活站 ⇒ 无法端到端验证**（本 ADR 之前，两次改动均因此停在"代码走查级"）；
- "代码走查级"证据**不足以支撑判据**（本框架已有多次因"判据未自证"造成实际损失的记录）。

⇒ 于是形成死锁：**要改证据面 ⇒ 要改 .ps1 ⇒ 要能验证 ⇒ 要有派生夹具 ⇒ 夹具本身又不需要改 .ps1**。
**打破死锁的钥匙是"先建夹具、再动代码"** —— 这就是本 ADR 新增**阶段 0.5** 的由来。

## 决策（Decision）

### D1. 阶段顺序**修正**为 `0 → 0.5 → 2(内容补齐) → 1 → 3`（原「1→2→3 不可反」作废）

**原判断**（调研 §7.1）：顺序不可反，理由隐含"**复验器必须先有 manifest 才知道验什么**"。
**实测推翻**：复验器**不依赖 manifest** —— 需验的**件集已由 ADR-0005 固定**为 6 件（见 [AGENT_EVIDENCE_FILES](../ops/cluster.py#L3095)），复验器直接按该件集重算 digest 即可，且已端到端自证（§实施记录）。

**故 manifest（阶段 1）的边际价值重新定位**：

| 原定位 | 修正后定位 |
|---|---|
| 复验器的**前置条件** | **扩展性**（新证据类型如 `workspace-diff` 的声明载体）+ SLSA「**未识别 externalParameters ⇒ 校验失败**」语义 |

**代价（诚实记账）**：复验器的件集**硬编码在代码常量**里 ⇒ 新增证据类型**必须改代码 + bump recipe**。由 **D2** 处置。

### D2. 件集**单一真值**在代码常量；加件必须 bump recipe（不引入第二定义点）

`AGENT_EVIDENCE_FILES`（[cluster.py:3095](../ops/cluster.py#L3095)）是件集唯一真值；`AGENT_DIGEST_RECIPE` 是配方版本。
**加件/改序/改分隔符必须同时 bump recipe**，否则历史条目全部误判为"断链"。

> 判据已内置：复验器对每条记录比对 `recipe` 字段，不符报 `recipe_mismatch`（[`agent_chain_verify`](../ops/cluster.py#L3354) 内）。
> **为什么不做成"自动兼容旧 recipe"**：那会产生"同一链里两种配方"的模糊态，使"断链"不可判定 —— 与本框架"判据必须可判定"冲突。

### D3. **新增阶段 0.5：改动验证闭环**（前置条件，**不产出功能**）

**内容**：以「**轻卡 + 小模型**」建立 `agent-cli.ps1` 改动的**端到端夹具**。
**已有素材**（无需新建能力）：`spec/d6-agent-standard/test-cards/echo.md`（轻卡）+ B 站 `gpt-oss-20b`（`infer-load` 可载，load-gate 允许）+ ADR-0005 的 `tmp/e2e-evidence-card.md` 夹具先例。
**验收判据**：夹具能重复执行并给出**正负双向**结果 —— 正：正常卡派发 ⇒ runDir 生成且复验 PASS；负：人为破坏一处 ⇒ 门禁/复验器 FAIL 且定位到件。

**为什么要单列成一个"阶段"**：它不是功能，而是**后续所有 `.ps1` 改动的证据基础设施**。不建它，阶段 1/2-内容 与缺口 4/5/6/8/10 都只能停在走查级 —— 等于**把整条路线卡在"不敢改"上**。

### D4. 复验器判据的**严重度分层**（三类，不许混）

| 类别 | 例 | 处置 | 理由 |
|---|---|---|---|
| **篡改/损坏证据** | `digest_mismatch` / `chain_break` / `cold_mismatch` / `anchor_mismatch` / `run_dir_missing` | **FAIL** | 有明确对立面（改 vs 未改），可判定 |
| **覆盖缺口** | 有 run 未入链 / 缺锚 / 缺 `.meta`（老 run） | **WARN** | 属"没验到"，**不是"验出问题"**；报 FAIL 会让判据因噪声被整体忽略 |
| **合法演进** | golden 源哈希与当次不同 | **info/gap** | golden 会**合法变更**，与篡改**在此不可区分** ⇒ 只能报"已漂移，需人判" |

> 这条与门禁 `evidence` 断言的既有分层一致（[`check_evidence`](../ops/rpc_check.py#L1639)）；后续新增判据（`verdict-chain` / `golden-identity`）**必须**先归入某一类再落地。

### D5. 批次排序（批 A / B / C），其中 **阶段 3 明确挂起**

| 批 | 项 | 前置 | 理由 |
|---|---|---|---|
| **A** | `verdict-chain` 复验 / `golden-identity` 复验 / 缺口 9 文档漂移 / 缺口 6 **诊断落档** | 无（纯主控侧、可离线自证） | 零风险且**直击本议题原始命题**；同时**证明"复验器可扩展"**，为批 B 铺路 |
| **B** | 阶段 0.5 → 缺口 6 修复 / 缺口 4 diff + 阶段 1 manifest + 缺口 10 围栏 / 缺口 5 attach 哈希 / 缺口 8 遥测 | **阶段 0.5 必须先建** | 全部要动 `.ps1`；无夹具则不可自证 |
| **C** | 阶段 3 异基座管线审计 | 批 B 完成 | **挂起**：当前证据面仅 6+1 件，审计员**可判的东西很少**，成本高 ⇒ 会造出"因无人能应对而失败"的判据（正是调研 §5.6 的反面教训）。应等批 B 把证据面扩到能支撑"可重放性"判定后再上 |

## 否决/比较对象

| 方案 | 否决理由 |
|---|---|
| **坚持原顺序**（先 manifest 后复验器） | 实测复验器不依赖 manifest（D1）；且 manifest 要动 `.ps1`（含围栏加固），会把"能立刻拿到的自证能力"推迟到夹具建成之后 —— **用最贵的步骤挡住最便宜的收益** |
| **不建阶段 0.5 直接改 `.ps1`** | 等于接受"走查级证据"。本框架已多次因未自证的判据造成实际损失（含一次不可逆文件丢失），**不接受**把关键路径的改动降级为信念 |
| **让复验器自动"修复"不一致**（自动重锚 / 自动补链） | **会把篡改信号抹平** —— 攻击者重写链后跑一次 `chain` 即无痕。已实测该防护有效（`chain` 在锚≠链时**刻意不动锚**，须显式 `--reanchor`） |
| **把 gap 表升级为评分** | 评分已由评审环承担；管线审计应承担**可重放性**。职责混同会同时污染两者（调研 §7.2 要点 5） |
| **为兼容旧配方而双轨 digest** | 见 D2：会产生"同链两配方"的模糊态，"断链"不可判定 |
| **跨实例而非跨家族做异基座审计** | 自偏好是**家族级 + 风格级**（position bias 63%）⇒ 跨实例近乎无信息量（调研 §5.5） |

## 后果与待办

**收益**
1. 阶段推进不再依赖口头共识：**每阶段的"做什么 / 凭什么判做完 / 现在什么状态"**都可在本 ADR 一处查到（见下节路线表）。
2. 复验器能力已从"**验自建链的完整性**"起步（防篡改），并向"**验语义一致性**"扩展（防**转述失真**）—— 这是两类**不同**的失效，本 ADR 明确了它们的归属阶段。
3. 阶段 0.5 一旦建成，**所有**后续 `.ps1` 改动从"走查级"升到"实测级"。
4. 三处过时状态被钉正，后续排期不再基于错前提。

**代价与风险**
- 复验器件集硬编码（D2）；新增证据类型需改代码 + bump recipe。
- 阶段 0.5 的夹具**本身也要维护**（轻卡 + 小模型可用性变化会使其失效）—— 属**必要的**基础设施成本。
- 阶段顺序修正**偏离**了原调研的判断；若将来发现 manifest 确实被某条判据强依赖，需回退 D1（本 ADR 记明该风险）。

**验证边界（诚实声明）**
- 阶段 0 / 阶段 2-形态 / 关联工作：**已实测**（见 §实施记录，含负向自证）。
- 阶段 0.5 / 1 / 3 与批 A/B：**本 ADR 只定路线，未执行**；执行时逐批按 D3/D4 的判据收杆。
- 本 ADR **不声称**：证据链能防 T3、能证 judgement 级真伪、能防"提前不记录"（详见 [evidence-chain/DESIGN.md](../spec/d6-agent-standard/evidence-chain/DESIGN.md) §3/§6）。
- 外部锚的强度是"**多副本见证**"（需 push 到 origin 且被他方见证），**非密码学不可否认**。

### 批 B 次项（缺口 10）落地与实测（2026-09-18）—— 含两次"判断被实测推翻"

**① 我的原判被证伪（记账）**：我据 L621 的 `$l.Trim() -eq '---'` 即翻转 `$inFreq`，推断"正文里的 markdown 分隔线 ⇒ 其后正文被**静默丢弃**"（并类比 D-13/P1b）。**写用例实测后 12/12 全过 ⇒ 推断错了**：`$bodyRead` 一旦置真**不重置**，普通正文行仍走 body 分支，正文不会整体丢失。

**真陷阱（实测得出）**：分隔线后的正文行**若形如 `key: value` 且命中已知键**，会被 front-matter 分支吸收，经 `$h[$k] = $v` **静默覆盖**。用例（正文里引用另一张卡的 front-matter 示例）实测：

```
FAIL  fence: header task     NOT overwritten by body line   （'fence trap test' → 'EVIL-OVERWRITE'）
FAIL  fence: header readonly NOT overwritten by body line   （$true → $false  ← 安全相关！）
FAIL  fence: header model    NOT overwritten by body line   （'gpt-oss' → 'EVIL-MODEL'）
FAIL  fence: body keeps the quoted lines verbatim
```

⇒ **卡正文可静默改写卡契约**（含 `readonly`）。

**② 修法（一行）**：围栏判据加 `-not $bodyRead` 守卫 —— `$bodyRead` 置真即表示 front-matter 已闭合，此后任何 `---` 都只是正文。**修后 13/13 PASS**。

**③ 顺带发现：守门夹具本身早已静默失效（更值得记）**：`_fm_golden_test.ps1` **缺 UTF-8 BOM**（首字节 `23 20 3D`），PS5.1 按 ANSI 解码含中文的脚本时，**3 字节 UTF-8 序列被当 2 字节 GBK 解码会吞掉相邻换行** ⇒ 语句被并进注释 ⇒ `$fns` 从未赋值，输出 `DEBUG fns count=0` + `Get-FrontMatter not found`。**即"卡解析器的回归守门人"一直是死的**；补 BOM 后立刻恢复 `fns=32`。这与项目铁律"含非 ASCII 的脚本必须 UTF-8 BOM"**完全同源**，是该铁律的又一次实证。

**④ 由此暴露一个门禁盲区（已登记 OPEN-ISSUES）**：`syntax` 断言**抓不到这一类** —— PS5.1 对无 BOM 文件按 ANSI 解码**不报错**（只是内容变乱码），故"`.ps1:12文件/0失败`"通过 ≠ 脚本行为正确。**"语法通过"≠"语义正确"**，与 G8「'包在' ≠ '功能在'」同族。
