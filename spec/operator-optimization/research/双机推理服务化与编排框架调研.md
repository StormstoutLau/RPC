## 一、执行摘要

核心判断: **本集群需要的是"网关 + 监控"两层, 而不是"集群编排器"一层**。

1. **双路径并存设计 (8080/8081 同时在线) 决定了核心件是请求路由网关** — [LiteLLM Proxy](https://docs.litellm.ai/docs/proxy/load_balancing) 按 model 名路由 + fallback + 健康检查, 是社区标准答案, 与双后端同机零改动接入。
2. **llama-swap** (452+ commits, 2026-05 仍活跃) 是模型生命周期管理的最强单机方案 (热切换/TTL/自动重启/Web UI/Prometheus metrics), 但其"一次一模型省显存"的设计前提与本集群"双路径并存"冲突 — **定位为 C 站容量档模型增多后的可选项, 不是当前刚需**。
3. **exo 维持排除** (Linux 端 CPU-only, GPU 支持未落地) — 与前期互连调研结论一致。
4. **监控栈选 Prometheus + Grafana + node\_exporter(textfile)**: vLLM 原生 `/metrics` 直接可用; llama.cpp 无原生 metrics, 用 llama-swap `/metrics` 或自采 textfile 补; AMD 无 DCGM 等价物, GTT/显存走 sysfs textfile (a4\_diag 系列脚本已有现成读法)。
5. **扩展性**: LiteLLM `model_list` 加一行 = 加一个 deployment; C 站入网 = systemd unit 模板 + node\_exporter + 网关路由条目, 无框架级锁死。

**v1.1 增补结论 (主控站可视化控制)**: "从主控站直接控制"的正确解法是**主控站浏览器作统一入口 + 控制面服务分层部署**, 而非在 Win10 上自研控制程序 —

1. **控制层 = Cockpit** (v366, 2026-08-13 发布): 跑在 A/B 两站 (socket 激活, 零空转开销), 主控站浏览器访问 9090 端口, 直接点按钮管理 systemd 服务 (rpc-server / llama-server / pm-qos), 内嵌 journal 日志、实时指标、Web 终端 — 现有 SSH 工作流的图形化镜像, 与 CLI 完全同源 (底层就是 systemctl)。
2. **监控层 = Beszel** (23k stars, MIT): hub (PocketBase, :8090) + agent (A/B/C 站), 自带历史图表、告警 (温度/CPU/磁盘/网络/状态)、**AMD GPU 使用率与功耗**; hub 跑主控站 Win10 (Docker Desktop) 或 B 站二进制 — 替代 v1.0 的 Prometheus+Grafana 作为节点监控首选 (轻量一个量级)。
3. **交互层 = Open WebUI (可选)**: 指向 LiteLLM :4000, 模型下拉框即双路径切换 (minimax-m2 / minimax-m2-long), 附带对话历史/RAG/多用户。

## 二、需求映射 (本集群现状 → 服务化缺口)

| 需求     | 现状                                                                         | 缺口                                                        |
| ------ | -------------------------------------------------------------------------- | --------------------------------------------------------- |
| 启动编排   | systemd 三服务 + a4\_vllm\_launch.sh / a4\_restore.sh / a4\_cleanup.sh 手工互斥切换 | 启动顺序/依赖 (vLLM 需等 llama.cpp 停 + GTT 释放) 已在脚本内解决; 缺**统一入口** |
| 后端框架选择 | 客户端手工选 8080 (短输入) / 8081 (长上下文)                                            | 缺按 model 名/请求特征自动路由                                       |
| 模型切换   | 单模型 M2.7; C 站规划 Kimi/Q8 容量档                                                | 目前无需求; 未来需进程级切换 (显存互斥)                                    |
| 服务监控   | a4\_smoke.sh 冒烟 + crash\_drill.sh 演练                                       | 缺持续指标采集 (TTFT/吞吐/KV cache/错误率) 与告警                        |
| 节点负载监控 | a4\_diag\_mem.sh / a4\_diag\_amdsmi.sh 手工执行                                | 缺时序化 (GTT 曲线、RPC 链路 RTT、CPU/EPP)                          |
| 节点扩展   | C 站已购未装, 部署 runbook 待写                                                     | 缺"加节点 = 加配置"的架构约束                                         |

**关键架构事实**: 双机推理的"模型"对网关而言是 B 站两个端口上的服务, 节点内部拓扑 (RPC/Ray/TP) 对网关透明 — 服务化层不需要理解分布式细节, 只需路由与健康检查。这大幅缩小了选型范围: **不需要 k8s 级编排器, 不需要 exo 类拓扑感知框架**。

## 三、社区候选全景

### 3.1 LiteLLM Proxy (BerriAI) — 网关路由层 ★推荐

[GitHub](https://github.com/BerriAI/litellm) · [Router 文档](https://docs.litellm.ai/docs/routing) · [Proxy 负载均衡文档](https://docs.litellm.ai/docs/proxy/load_balancing)

- **机制**: `model_list` 中同名 `model_name` 的多个 deployment 之间负载均衡; 不同名则按请求的 model 字段精确路由 — 后者正是"后端框架选择"要的语义 (`minimax-m2` → 8080, `minimax-m2-long` → 8081)。
- **可靠性内建**: cooldown (失败 deployment 冷却移出)、fallbacks (8081 挂 → 自动切 8080)、timeout/重试(指数退避)、后台健康检查 (`background_health_checks`)。
- **路由策略**: simple-shuffle (默认, 生产推荐) / latency-based / least-busy / rate-limit-aware。
- **社区规模与活跃度**: 1.6k+ open issues, 3.2k+ PR, 月度级发版; 2026-03 有 [PyPI 供应链事件](https://futureagi.com/blog/best-ai-gateways-aider-local-models-2026/) (<1.82.7 版本), **需锁版本 ≥ 该修复版**。
- **已知缺陷**: [#27362](https://github.com/BerriAI/litellm/issues/27362) (2026-05) — `APIConnectionError` 被 `cooldown_handlers.py` 硬编码排除, 死节点不进 cooldown, 重试反复打同一死节点。对本集群影响: 后端整体宕机 (非多副本同模型) 时 fallback 仍有效 (fallback 是另一条路径), 但需开 `background_health_checks` 且验证所用版本行为。
- **先例**: [inferhost](https://pypi.org/project/inferhost/0.5.19/) 就是 "llama.cpp + llama-swap + LiteLLM 网关" 的组合打包 — 验证了该分层模式在单机场景的可行性。

### 3.2 llama-swap (mostlygeek) — 模型生命周期层 ○条件推荐

[GitHub](https://github.com/mostlygeek/llama-swap) (452+ commits, 2026-04/05 仍有 Prometheus metrics、UI histogram 等 PR 合入)

- **机制**: Go 单二进制零依赖, 按 OpenAI 请求的 model 字段**自动热切换**上游 server (错模型在跑 → 杀掉换对的); TTL 空闲卸载; `groups`/`matrix` DSL 控制并发常驻; Web UI (playground/token 指标/日志流); `/metrics` Prometheus 端点; 死后端下次请求自动重启 (对比 llama.cpp 自家 router 模式的不成熟, [有详细对比文档](https://github.com/Hrt-Htk/llama-cpp-proxy/blob/main/LLAMA_SWAP_VS_ROUTER.md))。
- **多后端**: 官方支持 llama.cpp/vllm/stable-diffusion.cpp 等, 通过 `cmd`/`cmdStop` 包装任意启动命令 — 可直接包 `a4_vllm_launch.sh` / `a4_cleanup.sh`。
- **与本集群的冲突点**:
  1. 默认语义是**互斥 swap** (省显存), 而本集群双路径是**并存** (两后端各占 GTT, 同时服务) — 需用 `groups` 把 8080/8081 放不同组绕过, 配置复杂度上升。
  2. vLLM TP=2 后端冷启动 3-5 分钟 (Ray 双机 + 模型加载 + GTT 等待), swap 停机窗口长 — TTL 自动卸载绝不能配在 vLLM 后端上。
  3. 它管的是**进程**, 与现有 systemd 兜底职责重叠 (llama-swap 自身也需 systemd 化, 形成双层 supervisor)。
- **结论**: 当前单模型双后端下净收益为负; **当 C 站上线、模型数 ≥3、显存互斥成为常态时再引入**, 届时它是该场景的社区标准答案。

### 3.3 llamactl (lordmathis) — 备选生命周期层

[GitHub](https://github.com/lordmathis/llamactl) (871+ commits, 2026-06 活跃)

- 特性: instance groups + 每组上限、LRU 驱逐、idle timeout、React 仪表盘、原生 llama.cpp/MLX/vLLM 多后端。
- 与 llama-swap 同生态位, 但更"instance 常驻池"取向 (MLX 生态背景); 对本集群无相对优势, 列为 llama-swap 的平行备选。

### 3.4 exo (exo-explore) — 维持排除

[GitHub](https://github.com/exo-explore/exo) (2,353 commits, 2026-06 活跃, zenoh 迁移中)

- 拓扑感知分片 + 自动发现 + RDMA over TB5, 但 **Linux 端 CPU-only, GPU 支持仍在开发** ([实测文章](https://corti.com/borrowing-memory-not-speed-clustering-a-mac-studio-and-a-dgx-spark-with-exo/) 明示 DGX Spark 的 GPU 在 exo 下完全不用)。本集群两站皆 Linux, 排除结论与前期互连调研一致。

### 3.5 监控栈 — Prometheus + Grafana 体系

社区 2026 标准模式 (多篇生产指南一致, 如 [iancloud 自托管推理可观测性](https://iancloud.ai/blog/llm-observability-self-hosted-inference-2026)、[Ollama 监控指南](https://localaimaster.com/blog/ollama-prometheus-grafana)):

- **面 1 — 推理运行时**: vLLM 原生 `/metrics` (TTFT、TPOT、KV cache、queue depth、batch size) 零成本; llama.cpp **无原生 metrics 端点** — 由 llama-swap `/metrics` (若引入) 或网关侧 token/延迟指标补。
- **面 2 — 节点主机**: node\_exporter 两站部署; AMD 平台无 DCGM 等价物 (NVIDIA 专属), **GTT/显存/CPU-EPP 走 sysfs textfile collector** — 读法与 a4\_diag\_mem.sh 完全相同 (`mem_info_gtt_used` 等), 移植即用。
- **面 3 — 链路**: 本集群特有需求 (USB4 RTT / rpc-server 存活), a3a\_rtt.py 已有 probe 逻辑, textfile 输出即可。
- **参考模板**: [PaulKnag/Observability-stack](https://github.com/PaulKnag/Observability-stack) — docker-compose 全套 (Prometheus/Alertmanager/Grafana provisioning/一键 exporter 安装脚本/告警规则), 3-GPU homelab 场景与本项目规模同量级, 直接改造。

## 五、推荐架构 (B5 服务化层)

```
客户端 (主控站/局域网)
   │  http://B:4000/v1/chat/completions  (model: minimax-m2 | minimax-m2-long)
   ▼
┌─ LiteLLM Proxy :4000 (B 站, 独立 venv) ──────────────────┐
│  model_list:                                             │
│    minimax-m2       → http://127.0.0.1:8080 (llama.cpp)  │
│    minimax-m2-long  → http://127.0.0.1:8081 (vLLM TP=2)  │
│  router_settings: fallbacks (long→8080), cooldown,       │
│                   background_health_checks               │
└──────────────┬───────────────────────┬───────────────────┘
               ▼                       ▼
   llama-server :8080        vLLM :8081 (Ray 双机)
   (systemd, 现状不动)        (a4_vllm_launch.sh, 现状不动)
               ▲                       ▲
   ┌───────────┴───────────────────────┴──────────────────┐
   │ 监控面: node_exporter(两站) + textfile(GTT/EPP/RTT/   │
   │ rpc存活) + vLLM /metrics → Prometheus → Grafana       │
   │ (跑在 B 站 docker-compose 或主控站 Win10)              │
   └───────────────────────────────────────────────────────┘
```

设计原则:

1. **网关与后端同机 (B 站)**: 后端流量零额外网络跳; 主控站保持纯管理/可视化角色。
2. **不接管进程**: LiteLLM 不 spawn 进程, 现有 systemd + a4 脚本职责不变 (已含启动顺序、GTT 等待、括号 pkill 等全部踩坑成果) — 服务化层零侵入。
3. **双路径语义进 model 名**: 客户端显式选 `minimax-m2-long` 走 vLLM; 不做按 prompt 长度自动分流 (LiteLLM 原生不支持; [社区做法](https://markaicode.com/integrate/multi-model-routing-llm-backend/)是网关前再垫一层 FastAPI token 计数器 — 可选件, 收益不值复杂度, 客户端自己知道上下文多长)。

### 分阶段行动项

| 阶段                             | 内容                                                                                                                                                                                             | 风险                  | 前置    |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | ----- |
| **B5a 网关上线**                   | B 站部署 LiteLLM (:4000, 锁版本 ≥1.82.8 避供应链事件), 双 model 路由 + fallback 配置, 冒烟 (a4\_smoke.sh 改端口)                                                                                                     | 低 (纯代理, 后端不动)       | 无     |
| **B5b 网关验证**                   | 崩溃传导演练: 停 8081 验证 fallback 到 8080; 复验 #27362 行为 (本集群单副本非多副本, 预期 fallback 路径不受该 bug 影响)                                                                                                         | 零                   | B5a   |
| **B5c 监控上线**                   | 两站 node\_exporter + textfile (GTT/amdgpu/EPP/a3a RTT probe/rpc-server 存活); B 站或主控 docker-compose 起 Prometheus+Grafana (改造 PaulKnag 模板); 告警规则: GTT >100GiB、RPC 链路 down、8080/8081 health 失败、两站温度 | 低                   | B5a   |
| **B5d C 站扩展 runbook** (C 站实装时) | systemd unit 模板复刻 + node\_exporter + LiteLLM 加容量档路由条目; 若模型 ≥3 且显存互斥, 评估 llama-swap 接管容量档后端                                                                                                     | 中 (vLLM 冷启动 3-5min) | C 站硬件 |

### 风险与盲区

1. **LiteLLM #27362**: 单模型多副本场景 failover 失效; 本集群 8080/8081 是不同 deployment 名, 走 fallbacks 机制而非 cooldown 选择 — 理论不受影响, B5b 实测为准。
2. **LiteLLM 供应链**: 2026-03 PyPI 事件 (<1.82.7); 锁版本 + pip 校验 hash。
3. **流式 SSE 转发**: 网关转发流式响应增加一跳缓冲 — B 站本地转发, 延迟增量预期 <10ms 量级, B5a 冒烟实测 TTFT 对比。
4. **llama.cpp 指标空缺**: LiteLLM 侧只有请求级指标 (延迟/tokens); 想要 llama-server 内部指标 (KV 使用率等) 需等上游或引入 llama-swap 陪跑 — 非刚需。
5. **vLLM 路径 TTL 禁配**: 任何自动卸载机制 (若未来引 llama-swap) 对 8081 后端必须显式禁用 (冷启动 3-5 分钟 + GTT 释放等待, 自动换血停机窗口不可接受)。

## 六、v1.1 增补 — 主控站可视化控制台 (2026-08-29)

### 6.1 需求重定义

用户补充需求: **主控站 (Win10, 192.168.1.10) 需要一个可视化程序, 从主控站直接控制整个推理集群**。

拆解后的真实需求:

| 子需求  | 含义                                        |
| ---- | ----------------------------------------- |
| 可视化  | 节点负载/GTT/链路/服务状态的仪表盘, 常驻主控站浏览器            |
| 直接控制 | 不登 SSH, 点按钮完成: 服务启停、路径切换 (8080↔8081)、故障恢复 |
| 模型切换 | C 站上线后多模型间切换                              |
| 后端选择 | 客户端/用户视角选 llama.cpp 或 vLLM 路径             |
| 扩展   | C 站加入后控制面自动覆盖                             |

**关键设计判断**: "主控站控制程序" ≠ "主控站上运行的程序"。主控站已有到 A/B 的管理网 (192.168.1.11/.15) 和浏览器 — 正确架构是**控制面服务部署在 Linux 站点上, 主控站浏览器作为唯一入口**。在 Win10 上自研 FastAPI+paramiko 控制程序技术上可行 (用户 Python 熟练), 但等于把 SSH 脚本层再包一层自己维护的代码, 无社区先例支撑, 排除。

### 6.2 新增候选

#### A. Cockpit — 控制层 ★推荐 (v1.1 最大增量发现)

[cockpit-project.org](https://cockpit-project.org/) · Red Hat 出品, RHEL 默认预装, **v366 发布于 2026-08-13** (活跃维护)

- **机制**: 每站 `apt install cockpit` + `systemctl enable --now cockpit.socket`, 浏览器访问 `https://<station>:9090`。**socket 激活 — 不用时零资源占用** (不碰推理负载)。
- **与本集群控制面精确对齐**:
  - systemd 服务管理 (start/stop/restart rpc-server / llama-server / pm-qos-usb4) — **底层就是 systemctl, 无并行配置数据库, UI 与 CLI 状态永远一致**;
  - journal 图形化浏览 (按服务/时间过滤) — 替代 `journalctl -u llama-server` 手工翻;
  - 实时指标页 (CPU/内存/网络/磁盘) + PCP 历史数据 (cockpit-pcp 可选);
  - **内置 Web 终端** — a4 系列脚本 (launch/cleanup/restore/bench) 直接在浏览器里跑, 排障不降级;
  - 多机切换 (cockpit-dashboard): 从 B 站单入口 SSH 扇出到 A 站, 一个标签页管两台。
- **安全模型**: PAM 认证 (系统账号密码), 自签 TLS, 可 polkit 精确授权非 root 用户仅管理指定 unit — LAN 内暴露面可控。
- **边界**: 单机视角工具, 非集群聚合视图 (dashboard 只是切换器); vLLM 路径当前非 systemd 服务 — 见 6.4 工程注记。

#### B. Beszel — 监控层 ★推荐 (替代 v1.0 Prometheus 首选位)

[beszel.dev](https://beszel.dev/) · [GitHub](https://github.com/henrygd/beszel) · \~23k stars, MIT, 2026 活跃

- **架构**: hub (PocketBase 单二进制, :8090, Web 仪表盘/告警/多用户/REST API) + agent (每站, :45876, **主动外连 hub** — 无需暴露端口, NAT 友好)。
- **指标覆盖**: CPU/内存(含 swap)/磁盘用量+IO/网络吞吐/load/**温度+风扇 (hwmon)**/**GPU 使用率+功耗 (Nvidia/AMD/Intel)**/SMART/电池 — **AMD GPU 原生支持**直击本集群痛点 (amdgpu 功耗温度此前只能 amdsmi 手工读)。
- **告警内建**: 阈值告警 → Slack/Discord/邮件 — 替代 Alertmanager 的配置工作。
- **部署形态**: hub 单二进制或 Docker (可跑主控站 Win10 Docker Desktop 或 B 站); agent 二进制安装脚本/Linux Docker/WinGet/Scoop — 两站 apt 无依赖负担。
- **诚实边界**: **无自定义指标插件** (无 textfile collector) — GTT 细粒度、USB4 RTT、rpc-server 进程状态不在其指标集内; 应用级推理指标 (TTFT/TPOT) 也没有。这些缺口 → 保留 Prometheus textfile 作为条件项 (B5c 降级, 非取消)。
- **对比修正**: v1.0 推荐 Prometheus+Grafana 是"能力上限"选型; Beszel 是"需求匹配"选型 — 节点层监控+告警一步到位, 维护量低一个量级; 若后续需要 vLLM `/metrics` 应用级面板, 再叠加 Grafana 不冲突 (两者可共存, Beszel 管节点, Grafana 管推理)。

#### C. Open WebUI — 交互层 (可选)

[Open WebUI](https://docs.openwebui.com/) · 社区标准自托管 ChatGPT 替代

- 连 LiteLLM :4000 (OpenAI 兼容), **模型下拉框 = minimax-m2 / minimax-m2-long 双路径切换**, 用户视角"后端选择"零学习成本;
- 附带: 对话历史/RAG/多用户/管理面板 — 主控站日常使用与演示入口;
- 部署: Docker (主控站 Docker Desktop 或 B 站) 或 pip; 纯前端性质, 不碰控制面。

#### D. harbor (av/harbor) — 检视后排除

### 6.4 工程注记与风险

1. **vLLM 路径进 Cockpit 的前置**: 把 `a4_vllm_launch.sh` 包成 `a4-vllm.service` (Type=simple, ExecStart 直接跑脚本, KillMode=control-group; 脚本内已含停 llama.cpp + GTT 等待逻辑)。收益: 8081 路径获得与 8080 同级的 UI 启停 + Restart 兜底。风险: Ray 跨站子进程在 systemd cgroup 清理下的行为需一次验证 (a4\_cleanup.sh 括号 pkill 全家作为兜底已存在); **先手工验证 unit, 再谈 UI**。

3. **Cockpit 暴露面**: 9090 仅管理网可达 (两站未装 ufw, 绑定默认全接口 — 主控网段 192.168.1.x 与 USB4 10.10.10.x 都可达; PAM 认证 + 自签 TLS 已够 LAN 场景, 公网零暴露)。
4. **Beszel GTT 盲区**: agent 不读 `mem_info_gtt_used` — 短期用 "内存用量+GPU 功耗+温度" 近似替代巡检; 若需要 GTT 精确曲线 (a4 期间 OOM 排障依赖它), 保留 B5c Prometheus textfile 路径 (probe 脚本已有, 只差采集端)。
5. **主控站 Docker Desktop 依赖**: Open WebUI / Beszel hub 若跑主控站需装 Docker Desktop (Win10, 当前未装); 替代 = 都跑 B 站 (二进制/容器), 主控站纯浏览器 — **推荐后者**, 保持主控站零服务原则。
6. **WinGet/Scoop agent**: C 站为 Ubuntu, 不涉及; 主控站自身监控可选装 Windows agent (Beszel 原生支持)。

### 6.13 架构机理归档 — 为何 A 站 rpc-server 不读 GGUF, 而启动脚本必须先合并分片 (2026-08-30)

对 6.12 "范围决策" (A 站分片不合并) 的机理解释, 用户问询后归档。

**核心: RPC 协议层没有"模型"概念**。整套协议只有 4 类动词:

| 协议动词            | 作用                   |
| --------------- | -------------------- |
| `buffer_alloc`  | 在远端 backend 申请显存/内存块 |
| `set_tensor`    | 把张量字节写进远端 buffer     |
| `get_tensor`    | 取回计算结果张量             |
| `graph_compute` | 把计算图发到远端执行           |

**职责分工**:

- **B 站 llama-server (client) = 模型的唯一入口**: GGUF header 解析、tensor 布局、量化格式解释全部发生在 B 站进程内。加载完成后, 按层切分把 A 侧计算份额的权重**逐张量解剖成原始字节** (`set_tensor`) 推给 A。A 收到的不是"模型文件", 是被解剖后的张量 blob。
- **A 站 rpc-server = 纯算力后端**: 全部"知识" = 收字节 → 存 GTT buffer → 算图 → 返结果。从头到尾不打开模型文件, 不需要 GGUF 解析器。

**该机理直接解释两个已观察事实**:

1. A 站 \~82G GTT 占用 (开机内存问题分析): 是 B 推送来的 A 侧计算份额权重, 以 raw buffer 驻留, `free` 显示 used 但不属任何进程 RSS — 与文件无关。
2. `-c` 缓存 (`/data/rpccache/<alias>`) 不是 GGUF: 是 rpc-server 把收到的张量字节落盘的 blob 缓存, 唯一作用是跳过下次网络重传, 与容器格式无关。

**为何最早启动脚本必须先合并分片** — 约束链全在 B 站 (client) 侧:

1. llama.cpp 主线加载器 (`llama_model_load_from_file_impl`) 接受**恰好一个文件路径**, 无多分片自动装配; mmap 也只能映射单个文件。
2. GGUF 格式本身无跨文件 manifest — 分片纯是 HF 平台 50G 单文件上限的产物, LM Studio 下载大模型默认分片态。
3. RPC 的层切分 (`-sm layer`) 与 `-ot` 放置都是**模型加载完成之后**的逻辑, 前提是模型先能被单个路径加载。
4. LM Studio GUI 能直接跑分片, 因其自带多 part 装配加载路径 — GUI 与集群走两条加载链, 这正是"GUI 能跑、集群不能"的原因。

**推论**: A 站的 GGUF 唯一消费者是 LM Studio GUI (自带分片加载), rpc-server 不读文件, 合并纯属浪费 145G 级磁盘读写 — 故 B5j 只合并 B 站三个模型, A 站分片原样保留。**B 站合并单文件 = 整个 RPC 集群的唯一模型入口**。与 vLLM 对比: vLLM TP=2 为对称对等, 两站各读本地权重分片; llama.cpp RPC 为主从执行, 权重分发是单点 (B) → 单点 (A) 的推送制。

### 6.16 DSpark 澄清 + DeepSeek 推理速度基线与优化空间 (2026-08-30 晚)

#### 6.16.1 DSpark 与当前路径的关系 — 未采用, 且实测无收益

**当前 DeepSeek 路径 = llama.cpp v0.2.0 双机 RPC + Vulkan + 默认层切分, 与 DSpark 零关系。**

DSpark 是 DeepSeek 专用 **draft 模型投机解码** 方案 (\~10.1GiB 草稿 + `--spec-type draft-dspark`), 早前调研 (DSpark与Flash模型加速框架调研.md v1.1) 已排除, 依据:

- **同硬件实证无加速**: sypherin (Strix Halo + Vulkan, 同芯片) 实测接受率 61.8% 但 **tg 持平** — 草稿推理开销吃掉全部收益; 1.5\~1.9x 加速数据全部来自 CUDA 后端, 不迁移
- **DSpark over RPC 有已知 hang 阻点** (#26610 评论区 ryan5rdx 报告, 未复验)
- Lucebox (ROCm 定制 fork, DSV4 专用 HIP kernel + DSpark) 同硬件 32 t/s 上限证明存在, 但为自研量化格式的定制 fork, 偏离两站版本化 SOP, 仅作上限基准

#### 6.16.2 实测基线 (server 路径, 热缓存加载 274s)

| 指标                        | 我方实测 (2x Strix Halo, USB4 RPC, v0.2.0, MXFP4) | 参照系                                                                                                                       |
| ------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| tg decode (batch 1)       | **6.6 tok/s**                                 | 同模型 2x Spark + RDMA + 新栈 `-sm tensor`: **19.75** (PR #26610 官方, 3.0x) / sypherin **单机** IQ3\_XXS: 12.24 (1.9x, 单机都快于我方双机) |
| pp prefill (唯一 prompt ×3) | **\~79 tok/s**                                | 同模型 2x Spark RDMA: **619** (7.8x) / M2.7 我方 pp512: 139                                                                    |

**判定: RPC 层切分对 DeepSeek V4 是净负收益路径** — 单机 (12.24) 快于我方双机 (6.6), 与 M2.7 结论 (双机优) 相反。机理: journal 警告 `fused DeepSeek V4 HC pre/comb/post is assigned to device RPC0 (missing support)` — **DSV4 专用融合算子在 RPC 后端不支持**, 边界层回退非融合路径 + 每token串行命令跨 TCP, 该架构对 RPC 惩罚远大于 M2.7。

#### 6.16.3 优化空间评估 (按证据强度排序)

1. **#26610 升级窗口 = 唯一大杠杆** (3x tg / 7.8x pp 同模型证据): async graph\_compute 消串行命令 + 新版 DSV4 kernel 成熟度 + 可能的 `-sm tensor`; 但 tensor 收益硬件依赖 (6.14.1), USB4 下需 before/after 实测。GLM (glm5next) 独立跟踪 (6.21: 滚升 master 不解锁 GLM, 须等 #27752/#27754) — 升级动机从"可选"升级为"应做" (当前 DS4 性能为升级前最差状态)。
2. **DSpark/投机解码**: Vulkan 无加速已证, 搁置; async graph 合入后投机解码经济学改变, 届时重评。
3. **参数层无空间**: A1/A2 已证 -ot 全负, -sm layer 默认最优; conf 当前 -fa on / CTX 32768 / THREADS 16 无可疑项。
4. **不追加单机路径**: MXFP4 145G > 单机 GTT 108G, 单机需换 IQ3\_XXS 量化 (另 103G 下载, sypherin 路线), 与"分布式跑大模型"需求定位冲突。

**净结论: 短期 (升级前) DeepSeek V4 Flash 维持 6.6 t/s 现状即合理, 不值得参数层折腾; 全部筹码押 #26610 升级窗口, 升级动机已从"跟踪项"升级为"应做项"。**

### 6.18 B5p 40G 线缆验证 + 端口误插事故 + IP 漂移修复 (2026-08-31 凌晨)

用户更换新线 (开博尔 "雷电4" 0.5m 对绞镀银, 无 Intel 认证标识) 后排查。事件经历了两次误判才收敛, 全程教训入档。

#### 6.18.1 事故时间线与误判链

1. **表象**: 换线后两站管理网不可达 → 实为 DHCP IP 漂移 (A .11→.33, B .15→.32)
2. **误判 1 "新线故障"**: TB 零枚举 + B 站 usb2-port1 `config error` 刷屏 → 判新线物理层故障 → 用户换回旧线
3. **误判 2 维持**: 旧线同样零枚举 + 同样 config error → 推翻"新线故障"单一解释
4. **根因 (PCI 拓扑归属法)**: B 站 config error 的 root hub 归属 **c6:00.4 (外设块 00:08.1 的普通 USB 3.2 xHCI 1587)**, 而 USB4 全家 (3 xHCI 1588/1589/158b + 2 NHI 158d/158e) 在 **c8 块 (00:08.3)** → **线一直插在 B 站唯一的 USB 3.2 Type-C 口上**, 与线缆新旧无关
5. **修复**: 用户把新线插到 B 站 USB4 口 → 链路立即建立, **协商 40Gbps** (旧线 20G)

**端口地图 (入档防复发)**: B 站 GTR-Pro 3 个 Type-C = **2×USB4 + 1×USB 3.2** (误插的即普通口); A 站 NEX 2 个 Type-C **均为 USB4**。

**诊断签名 (可复用)**: TB 链路零枚举 + 双端 xHCI `config error` 刷屏 = 线插在非 USB4 口 (或坏线); 判别法 = 读 config error root hub 的 PCI 归属, 与 USB4 Host Router 块比对。插对口后 config error 立即停止 (本次开机 2643 条全是误插期存量)。

#### 6.18.2 新线验证结果 (40G vs 基线 20G)

> **⚠ 口径修正 (2026-08-31 01:20, 见 6.19.3)**: 本节初版报的 pp512 "181.5 (+31%)" 系 **server API timings 口径与 llama-bench 基线口径混淆** 的假象, 不成立。下表已替换为 llama-bench 同参数复测的权威数字 — **40G 对推理仅 +1.5\~1.6% (噪声级), 真实收益是可靠性**。

| 指标                      | 基线 (20G 旧线, llama-bench) | 新线 (40G, llama-bench 同参数)  | 变化                                                                                      |
| ----------------------- | ------------------------ | -------------------------- | --------------------------------------------------------------------------------------- |
| 链路协商                    | 20Gbps                   | **40Gbps**                 | ✓ 2x                                                                                    |
| RTT min/avg             | \~0.100ms                | **0.087/0.137ms**          | min -13%                                                                                |
| iperf3 有效带宽 (单流/4并行/双向) | \~9.4Gbps                | **\~9.0Gbps**              | 持平 — **\~9G 是平台 TCP/GRO 天花板, 与链路速率无关** (dmesg: "Driver has suspect GRO implementation") |
| idle retimer 振荡         | 隐患 (found/disconnected)  | **90s 零事件**                | ✓ 消失 (**本升级的核心收益**)                                                                     |
| **pp512 (M2.7 双机 RPC)** | 139.19 ± 1.67            | **141.39 ± 0.64**          | **+1.6% (噪声级)**                                                                         |
| **tg128 (M2.7 双机 RPC)** | 20.6                     | **20.90 ± 0.16**           | **+1.5% (噪声级)**                                                                         |
| vLLM pp512 / tg (TP=2)  | 298 / 17.6               | **300.6 / 18.0** (6.19.1)  | +0.9% / +2.3% (持平)                                                                      |
| vLLM 16k PP / TTFT      | 193 / 84.9s              | **193.1 / 84.8s** (6.19.1) | 持平                                                                                      |

**机理结论 (修正后自洽)**: 与 A2 采证完全一致 — RPC 推理流量仅 17.6MB/s (链路占用 0.02%), decode 由串行命令数主导、prefill 由计算+命令数主导, **链路速率从来不是推理瓶颈**; 20G→40G 的收益只剩延迟微改善 (\~1.5%)。**换线的真实价值 = 消除 idle retimer 振荡隐患 (可靠性), 非性能** — 与《双机剩余优化空间评估.md》预判"换 40G 线归可靠性非性能"吻合。

### 6.26 Qwen3.8-Flash-Next 长上下文 (YaRN → 1M) 调研 (2026-08-31)

**触发**: 新入库 `qwen3.8-flash-next` 后问可达 1M token。操作方案落档于 [双机推理集群使用手册 §3.4](双机推理集群使用手册.md)。

**硬事实 (本地 GGUF 实测 + 官方/official recipe 交叉确认; 先信本地实测)**:

| 项 | 值 | 取证 |
|---|---|---|
| 架构 | `qwen4exp` = Qwen4 预览 (125B MoE + 51B N-gram, 6B active) | 本地 `gguf-dump`: `qwen4exp.context_length=262144`, `full_attention_interval=4` |
| 原生 ctx | **262,144 (256K)** | 本地 GGUF |
| 官方扩展 | YaRN → **1M**; `factor=4.0, original_max_position_embeddings=262144` 出自 **Community/Flash-Next vLLM recipe** (Qwen3.8-Flash-Next-FP8 全攻略; QwenDev 官方仅标"可 YaRN 到 1M", 未直接给 qwen4exp 的 llama.cpp config) | 社区全攻略 vLLM recipe |
| 注意力 | 36 GDN (固定状态) + 12 QSA (`full_attention_interval=4`) | GGUF + ll.cpp #27742 |
| llama.cpp 支持 | 架构可加载推理 ✓ (#27742 merged 2026-08-27); `--yarn-*`/`-ctk/-ctv` 参数在 | 本地冒烟 + `--help` |

**两条实现路径**:
1. **llama.cpp (优先, 本地引擎已装)**: `EXTRA_FLAGS="... --ctx-size 1048576 --rope-scaling yarn --yarn-orig-ctx 262144 --rope-scale 4.0 -ctk q8_0 -ctv q8_0"`
2. **vLLM (官方质量更贴近, 需 day-0 镜像)**: `--hf-overrides '{rope_parameters:{rope_type:yarn,factor:4.0,...}}' --max-model-len 1000000`; 我方 vllm-rocm 0.25.2 是否支持 qwen4exp QSA 存疑, 成本高

**关键裂缝 (执行前必须验证)**:
- **IMRoPE 专用路径 (2026-08-31 实测裁决: YaRN 不生效)**: qwen4exp 走 `ggml_rope_multi` (partial rotary 64/256), `--yarn-*` 未被 qwen4exp.cpp 消费 → 实测 `-c 524288 + --rope-scaling yarn --yarn-orig-ctx 262144 --rope-scale 2.0` 被 llama.cpp 强制 cap 回 `n_ctx_train=262144` (`slot context exceeds training context - capping`). **当前 master 构建无法对 qwen4exp 用 YaRN 超 256K**
- **decode 线性退化 (ll.cpp #28012, 2026-08-30)**: QSA top-k 当 dense mask + indexer 每步全量 re-pool → 报告 176K 已 ~122ms/token; 1M 交互吞吐会差
- **KV 内存 (排幻觉修正)**: 初判"12 层 QSA 全量 KV ≈24G/1M"**不成立** — ll.cpp#27742 证实 QSA 是稀疏有界缓存 (`indexer_top_k=2048`+compress ratio, `llama_memory_hybrid` third cache, dense-by-construction under budget), **KV 不随 ctx 全量线性增长**; 12 层全量 ~24G 仅最坏上界. 实际看 memory_hybrid 实现, 须 `-c 1M` 启动日志实测 → 双机 128G 可行性高于初判. N-gram 表 ~97.7G 走 host mmap (不占 GTT); 权重 103G RPC 分载
- **静态 YaRN 损害短文本**: 只真需要 >256K 才开; 日常 32K 用默认 conf

**来源**: [ll.cpp #27742](https://github.com/ggml-org/llama.cpp/pull/27742) / [ll.cpp #28012](https://github.com/ggml-org/llama.cpp/issues/28012) / QwenDev 官方 YaRN 参数 / NVIDIA GB300 blog / Ollama library / SGLang & vLLM recipe。

## 七、v1.2 增补 — LM Studio 资产整合 (2026-08-29)

### 7.1 新增条件与"合并转换"需求澄清

新事实: **A/B 两站均已安装 LM Studio, 各自有已下载的模型**。需要把这些模型资产纳入服务化框架, 用户表述为"模型需要合并转换"。

技术澄清 — "合并转换"实为两个不同的问题, 解法完全不同:

| 问题                  | 实质                                                                 | 解法                       |
| ------------------- | ------------------------------------------------------------------ | ------------------------ |
| **合并** = 两站模型目录统一   | LM Studio 默认目录在两站各自家目录, 独立下载必然产生重复文件; 集群 GGUF (M2.7, 121G) 又在第三个位置 | 目录统一 + 去重 (软链), 不动文件本体   |
| **转换** = 跨格式喂给 vLLM | LM Studio 模型全是 GGUF; vLLM 只吃 safetensors (AWQ/GPTQ)                | **不可行也不必要** — 见 7.3 兼容矩阵 |

### 7.2 关键事实: LM Studio 模型 = GGUF, 与 llama.cpp 完全同格式

- LM Studio 本质是 llama.cpp 的 GUI 封装 ([格式说明](https://inventivehq.com/blog/what-is-gguf-model-formats-explained): "If you run models through Ollama or LM Studio, you are already running GGUF"; "LM Studio, llama.cpp, Jan, KoboldCpp all store plain GGUF files in a `publisher/repo/model.gguf` tree — these can genuinely share one physical GGUF file")。
- 默认目录 `~/.lmstudio/models/publisher/model/model-file.gguf` ([官方 Import Models 文档](https://lmstudio.ai/docs/app/advanced/import-model)); 老版本在 `~/.cache/lm-studio/models/`。
- **因此两站 LM Studio 下载的模型对 llama.cpp 路径 (8080) 是零成本直接可用** — llama-server 的 `-m` 指到 GGUF 文件即可, 不存在任何转换。这正是社区"共享模型文件夹"模式的基础 ([InventiveHQ 实践](https://inventivehq.com/blog/share-models-folder-across-local-ai-tools): 单一 GGUF 目录被 LM Studio/llama.cpp/Jan/KoboldCpp 共用一份物理文件)。

### 7.3 格式兼容矩阵 (谁读什么)

| 资产                             | llama.cpp :8080 (GGUF 路径) | vLLM :8081 (AWQ 路径) | LM Studio GUI         |
| ------------------------------ | ------------------------- | ------------------- | --------------------- |
| 两站 LM Studio 下载的 GGUF          | ✅ 直接可用                    | ❌ **不可用**           | ✅ 原生                  |
| B 站 M2.7 Q4\_K\_S GGUF (121G)  | ✅ 现役                      | ❌                   | ✅ (可软链入 LM Studio 目录) |
| 两站 M2.7 AWQ G32 (155G, vLLM 用) | ❌                         | ✅ 现役                | ❌                     |

**vLLM 侧"转换"不可行的机理** ([CSDN 技术问答机制分析](https://ask.csdn.net/questions/9627179), [2026 量化格式对比](https://dreaming.press/posts/gguf-vs-gptq-vs-awq.html)): vLLM 加载器只注册 safetensors + AWQ/GPTQ 适配, 无 GGUF 解析入口; GGUF 的 K-quant 分组量化元数据与 AWQ 的 `qweight/scales` 布局结构性不兼容, 逆向转换 (社区工具 [ungguf](https://github.com/dreamfast/ungguf)) **必须以原版 safetensors 为参照**, 且量化是有损压缩 — GGUF Q4 已丢的精度不可能"转换回"高质量 AWQ。**正确路径 = vLLM 侧模型直接从 HF 获取 AWQ 版** (本集群 M2.7 AWQ 即如此获得), 与 GGUF 是平行资产非转换关系。

> 结论: **"合并"全做 (目录统一去重), "转换"零做 (格式各自平行获取)**。GGUF 资产池扩到两站 LM Studio 下载, vLLM 资产池维持 HF 直取不变。

### 7.4 LM Studio headless 服务化 (llmster) — 检视但不采纳为集群后端

LM Studio 0.4.0 (2026-01) 起提供 **llmster** 独立守护进程 ([官方 headless 文档](https://lmstudio.ai/docs/developer/core/headless)): `lms daemon up` / `lms server start` (:1234, OpenAI 兼容) / **JIT 加载 + TTL 自动卸载** ([ttl-and-auto-evict](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict)) / 官方 systemd unit 模板 ([Linux Startup Task](https://lmstudio.ai/docs/developer/core/headless_llmster))。0.4.x 还加了并行请求连续批处理、MTP 投机解码 (0.4.14 stable)、MCP host。

**定位判读**:

- llmster = llama.cpp 系的又一个 server 封装 — 与现有 llama-server :8080 功能重叠, 且**无 RPC 分布式能力** (单机引擎, 集群双机必须 llama-server+rpc-server 自建)。采纳它 = 用功能子集换一套新栈, 排除。
- 但 **LM Studio GUI 的模型管理/下载能力对集群有正价值**: 两站 LM Studio 可当"模型获取前端"用 (GUI 下载 GGUF → 落统一目录 → llama-server 直接喂), 比命令行 huggingface-cli 下载体验好, 且 llmster 的 JIT/TTL 语义与本集群前述 llama-swap 评估同构 — 单机多模型小场景工具, 不是双机大模型场景工具。

### 7.5 统一模型目录设计 (B5m 行动项)

```
每站 /data/models/                     (统一根, 独立于各家目录)
├── gguf/                              ← GGUF 资产池 (单一物理副本)
│   ├── MiniMax-M2.7/...Q4_K_S.gguf     (B 站现役, 迁入或软链)
│   └── <publisher>/<model>/x.gguf      (两站 LM Studio 下载去重后)
└── awq/
    └── MiniMax-M2.7-AWQ-G32/          (两站 vLLM 现役, 已各一份)

两站 ~/.lmstudio/models  → 软链到 /data/models/gguf  (LM Studio 继续可 GUI 管理)
llama-server -m          → 直接指 /data/models/gguf/...  (现状已独立路径, 收编)
```

- **去重原则**: 两站各自下载的同名 GGUF (MD5/sha256 相同) 保留一份, 其余删除; 跨站不复制 (llama.cpp 路径 GGUF 只需 B 站一份, A 站份额走 RPC 缓存 — 见 metrics-log Q2 归档)。
- **LM Studio 目录软链**是官方支持模式 ([模型共享指南](https://github.com/jameshroop-art/Overdue-Driver-Fixes/blob/main/LMSTUDIO_OLLAMA_MODEL_SHARING.md): Settings → Storage → Model Directories 添加目录, 或 `lms import`)。
- **vLLM 侧不整合**: AWQ 分片两站必须各一份 (TP 硬约束), 无去重空间; 未来新模型走 HF 直取 AWQ。
- **磁盘收益**: 取决于两站重复下载程度 (待盘点); 系统性收益 = 新模型只下一份 GGUF + LM Studio/llama.cpp 共读。

2. **GGUF 分片格式的既定事实: 00001 常为 header-only 小分片** (分片工具把 metadata header 单独切一片), "同模型分片应均分" 假设不成立

**方法论教训 (入操作安全规则)**: **判断文件完整性必须对照远端权威元数据 (size+sha256), 禁止用 "同模型其他分片大小均分" 外推** — 本次若直接启动 B5m1a, 将重下 46.6G 已有文件并覆盖一个完整分片, 且 LM Studio json 无 00001 任务条目 (它是 FINAL 文件, 从未进续传清单) 的旁证被误读为 "残片被遗漏"。假设需要验证, 验证要用权威源。
