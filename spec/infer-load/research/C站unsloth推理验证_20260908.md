## 4. 根因结论

> **C 站 BIOS 的 UMA Frame Buffer（dedicated VRAM）设为 1GB，而 AMD 官方对 Ryzen AI（gfx1151）的要求是 minimum 0.5GB；A/B 均为 0.5GB 成功，C 站 1GB 失败。**

- AMD 官方安装指南明确：*"AMD recommends setting the minimum dedicated VRAM in the BIOS (0.5GB)"*
- 社区同病案：ROCm issue #6139（gfx1151 + llama.cpp + `GCVM_L2_PROTECTION_FAULT_STATUS:0x00800932` + CPF 完全同签名，按官方指南修复）；vLLM gfx1151 两个变体（7.2.0 page fault / 7.1.1 segfault）同根因
- 非软件可修：已排除引擎、参数、库加载、并发、用户态 ROCm；剩余唯一平台差异即为 VRAM carveout + ODM BIOS

## 8. 最终突破 — UMA=4G 档 HIP 全链路打通（核心结论）

> 用户质疑"统一内存为何判断无法运行 gpt-oss" → 纠错排查发现真正变量是 **UMA Frame Buffer carveout 档位**。设 4G 后一次成功。

### 8.1 档位试验矩阵（同一 gpt-oss-120b / 同引擎 / 同参数）

| UMA carveout | 系统内存 | HIP 设备可用池 | 结果 |
|---|---|---|---|
| 1G（出厂最小档） | ~124G | ~117G（池够） | ❌ `[gfxhub] page fault` 死循环 |
| Auto（=64G） | 62G | **仅 61G** | ❌ `cudaMalloc out of memory`（池不足装 60G+overhead） |
| **4G（最终档）** | **121G** | **~120G free** | ✅ **加载 23s 成功，零 fault** |

### 8.2 成功实测数据

- 加载：`model loaded` ≈23s，`/health` ok
- prefill：**152 t/s**（74 tok / 486ms）
- decode：**48.8 t/s**（24 tok / 20.5ms·tok）
- 权重归属：**GTT 63.3G**（carveout 4G 仅显示用，权重经 GTT 借系统内存）→ 印证"显存/内存同池，carveout 越小 GTT 可借越多"

### 8.3 内存架构认知（统一内存本质）

- **carveout**：BIOS 启动固定划走，CPU 不可见。设大 → 浪费 + 压缩 GTT 可借上限（Auto 档 64G 即最劣形态）
- **GTT**：GPU 动态借系统内存（真正的统一内存价值），上限 min(gttsize, 系统剩余)
- AMD 官方建议 carveout `512M-4G`；C 站 ODM BIOS 最小 1G（触发 SVM fault）→ **4G 为最优可用档**

### 8.4 遗留看门狗/自启收口

- `llama-server@.service` 模板 `Restart=on-failure`→`Restart=no`（备份 `.bak-watchdog-20260908`）
- qwen 实例 `systemctl disable`（移除 multi-user.target.wants symlink）— **不再开机自启/失败复活**
- 显存占用溯源：qwen `-ngl 999` 全 offload → 权重进 GPU（carveout+GTT）；服务停后 vram 0.47G / gtt 0.05G 回归基线
- 当前 C 站无 llama 进程、18080/81 释放；如需手动起 qwen：`systemctl start llama-server@qwen3.8-27b-mtp`

### 8.5 HIP vs Vulkan 后端对照（同模型 gpt-oss-120b / 同参数 / UMA=4G，2026-09-08 晚）

| 指标 | **HIP**（`~/.unsloth` b10715, ROCm0） | **Vulkan**（`/opt` v0.3.0, Vulkan0） |
|---|---|---|
| 加载 | 23s | 23s |
| prefill | **152 t/s**（74 tok） | **88.6 t/s**（76 tok；18 tok 时 67.3） |
| decode | **48.8 t/s** | **53.3-53.7 t/s**（47 tok 稳定态） |
| page fault | 0 | 0 |
| 参数 | `--device ROCm0 -ngl -1 --fit off --load-mode none` | `-ngl 999 --fit off`（旧引擎无 --load-mode，须用 `/opt`） |

**结论**：与 A/B 站 nemotron 对照规律一致 — **Vulkan decode 略优（+9%）、HIP prefill 明显更快（+72%）**。C 站三后端（HIP/Vulkan/CPU）全部零 fault 可用；HIP 定为主引擎（与 A/B 同构），Vulkan 互补。
