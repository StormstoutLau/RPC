### 1.2 关键发现（studio 引擎解析逻辑）

studio 的 `_find_llama_server_binary()` 候选顺序（llama_cpp.py L7559-7570）：
1. `LLAMA_SERVER_PATH` env（direct）
2. `UNSLOTH_LLAMA_CPP_PATH` env
3. **`~/.unsloth/llama.cpp/llama-server`**（make build）← A/B 现存于此
4. `~/.unsloth/llama.cpp/build/bin/llama-server`（cmake build）← 实际生效项
5. Windows/legacy/PATH fallback

- **STORED_CUSTOM_LLAMA_CPP_PATH = None**（A/B 未 pin 自定义路径）
- 历史 run-gpt-oss-120b.log L37 直接证据：`Starting llama-server: /home/scott-lau/llama.cpp-vulkan-b10715/llama-server ... --device Vulkan0 ... -ngl -1 --fit off --load-mode none`（9/5 A 站；B 站同 9/6）

### 1.3 ⚠️ 主要风险（清理动作波及运行链）

**A/B 站 unsloth studio 的 gpt-oss-120b（MXFP4 120G）现役引擎 = 已清除的 vulkan-b10715**：
- 它被盘点误判为"与 .unsloth 同 commit 的 Vulkan 散置重复版"而清除；
- 但实测它是 studio 唯一带 **Vulkan 后端**的 b10715 引擎（studio 命令行固定 `--device Vulkan0`）；
- 现存 `~/.unsloth/llama.cpp` 是 **HIP/ROCm 构建（无 libggml-vulkan.so）** → 若由其接手 `--device Vulkan0` 必然失败；
- C 站完全无 unsloth 引擎，其 Qwen3.8 走独立路径，不受影响。

**结论**：vulkan-b10715 清除 = 破坏 gpt-oss-120b 现役运行链。备份在 `/data/backup/llama-cleanup-20260908/llama.cpp-vulkan-b10715`（md5 已验证一致），可秒级还原。

## 2. 引擎精简对比测试计划（现存后端实测）

### 2.1 目标
用**现存引擎**跑 unsloth 单站推理，对比「稳定性 + 吞吐」，确定：
- 是否可以**不还原 vulkan-b10715**，直接用现存后端承接（最小化版本数量）；
- 若 HIP 后端跑不动 gpt-oss-120b → 必须还原 vulkan-b10715（gpt-oss 现役引擎）。

### 2.2 候选引擎（A 站，内存 124G，模型 gpt-oss-120b MXFP4 ≈120G）

| 候选 | 路径 | 后端 | 预期可行性 |
|---|---|---|---|
| C1 | `~/.unsloth/llama.cpp/build/bin/llama-server`（b10715, HIP） | HIP/ROCm | ⚠️ LE：无 Vulkan；需确认 ROCm KFD 可用性（DEPLOYMENT O4 曾判 HIP 后端不可用） |
| C2 | `/opt/llama.cpp/llama-server`（master-d2e206c4, v0.3.0） | Vulkan | 中：Vulkan 就绪、lightning indexer ✅；但 studio 候选顺序不认 /opt（需 LLAMA_SERVER_PATH env 注入） |
| C3 | **还原** vulkan-b10715（备份在案） | Vulkan | 高：回到 9/5-9/6 现役形态（对照基准） |

### 2.3 测试方法（单机、同模型、同参数）

- 模型：`/data/models/gguf/lmstudio-community/gpt-oss-120b-GGUF/gpt-oss-120b-MXFP4.gguf`
- 启动：`llama-server -m <model> --port <p> --device <backend> -ngl -1 --fit off --load-mode none -c 4096 -t 16 --flash-attn on`
- 判定：/health 状态 → 生成冒烟 → `llama-bench` 或 server timings 记 pp/tg 吞吐 → 稳定性（运行 2-3 分钟无崩溃）
- 内存守护：启动前 `free -g` 快照；失败立刻 kill（遵守 OOM 防护与 110G 阈值经验）

### 2.4 预期结论分支

- **若 C1 (HIP) 可行**：优先用现存 HIP 引擎 + studio 默认路径 → 版本最精简（无需还原）；
- **若 C1 不可行、C2 (master) 可行**：用 `LLAMA_SERVER_PATH=/opt/llama.cpp/llama-server` 承接 → 单引擎复用现役 /opt（最精简且受 MANIFEST 管控）；
- **若 C2 也不稳**：还原 vulkan-b10715 → 回到现役对照，同时把"还原路径/依赖"固化为 SOP。

## 3. 实测结果（2026-09-08，A/B/C 三站）

> ⚠️ **事故与整改**：测试 A 站时曾因 C1(62G 常驻) 继续叠加启动 C2 致 A 站 kernel panic（125G>124G）。事故后固化**加载前硬规则 `load-gate`**（检查 used+need+12G、avail 缓冲、已有 llama RSS 防叠加、loadavg），后续 B/C 测试全部串行执行且通过 gate，无再发。

### 3.1 吞吐对比矩阵（同参数：-ngl -1 / --fit off / mmap / c4096 / t8）

| 站 | 引擎 | 后端 | 模型 | 加载耗时 | prefill t/s | decode t/s | 稳定性 |
|---|---|---|---|---|---|---|---|
| A | `.unsloth` b10715 | **HIP (ROCm0)** | gpt-oss-120b MXFP4 (60G) | 45s | 112-138 | **49.75-52.66** | ✅ 稳定 |
| B | `.unsloth` b10715 | **HIP (ROCm0)** | gpt-oss-120b MXFP4 (60G) | 80s | 135.6 | **50.26** | ✅ 稳定（与 A 复现一致） |
| B | `.unsloth` b10715 | **HIP (ROCm0)** | nemotron-120B-A12B Q4_K_M (81G) | 110s | 49.24 | **20.49** | ✅ 稳定 |
| B | `/opt` master v0.3.0 | **Vulkan** | nemotron-120B-A12B Q4_K_M (81G) | 110s | 41.56 | **23.21** | ✅ 稳定 |
| C | `/opt` master v0.3.0 | **Vulkan** | qwen3.8-27B MTP (常驻服务) | — | 36.5 | **12.41** | ✅ 稳定（未动） |

### 3.2 结论（定案）

1. **C1 (HIP/b10715) 完全可行**，且为现存引擎可承接 gpt-oss-120b（A/B 两站复现，decode ~50 t/s）→ **无需还原 vulkan-b10715**；版本精简路径成立。
2. **HIP vs Vulkan（同模型 nemotron-120B、单站、同参数）才是后端同级对比**：decode 20.49 vs 23.21 → **Vulkan 略优（+13%）**；prefill HIP 优（49 vs 42）。两后端均可用，差距小。
3. **⚠️ 归因修正：gpt-oss 的 50 t/s 不能与 V4-Flash 的 7.9 t/s 直接相除**——两者同时差了「模型大小（60G vs 146G）」「部署形态（单站 vs 三站 RPC 分布式）」「后端（HIP vs Vulkan）」三个变量，据此得出"HIP=Vulkan 6 倍"是错误的。gpt-oss-120b 无 Vulkan 单站对照数据，故 HIP 对 gpt-oss 的相对优势**未证实**；已证实的后端差异仅限 nemotron 同条件条目（Vulkan 略优）。
4. **C 站特殊性**：无 unsloth 引擎目录、无 120B 模型 → studio 单站推理在 C 站需 `/opt` Vulkan 承接（或补装 unsloth）。其活跃 qwen3.8 服务独立，未受影响。
5. **hardening 成果**：`load-gate`（ops/station-bin/load-gate）全程护航，B/C 全部串行卸载+gate 通过。

### 3.3 遗留

- [x] C2 master Vulkan 形态在 nemotron 上已验证（非全 offload 事故形态——本测试用 `-ngl -1` 级联但经 load-gate 单实例验收）
- [x] A/B 跨站 gpt-oss HIP 一致性确认
- [ ] C 站若需跑 120B 级模型：需补装 unsloth HIP 引擎或论 `/opt` Vulkan（depends 场景）

## 5. 术语附注：什么是"HIP 引擎"（2026-09-08）

> 澄清测试中反复出现的「HIP 引擎」一词，避免混淆。

- **HIP 不是独立框架**：它是 **AMD/ROCm 的 GPU 编程接口**（Heterogeneous-computing Interface for Portability），语法与 NVIDIA CUDA 高度兼容（一套代码可同时编译到 ROCm 与 CUDA）。
- **「HIP 引擎」= llama.cpp 以 HIP 为后端编译出的构建物**（`-DGGML_HIP=ON` → `libggml-hip.so` + `libamdhip64` + KFD）。与 Vulkan 构建（`-DGGML_VULKAN=ON` → `libggml-vulkan.so` + Mesa RADV + DRM）是**同一引擎的两种后端**，运行在同一块 Radeon 8060S 上。
- 设备命名：HIP 版 `--list-devices` 显示 **`ROCm0`**，Vulkan 版显示 **`Vulkan0`**——同一 GPU 的两条访问路径。
- 性能差异（nemotron: HIP 20.5 vs Vulkan 23.2 t/s）来自**驱动栈调度差异**，两者共享 UMA 128G 统一内存。
