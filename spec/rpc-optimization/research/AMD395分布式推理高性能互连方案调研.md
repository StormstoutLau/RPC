# AMD395 平台分布式推理高性能互连方案调研
# （USB4 直连之外的社区方案全景）

> **日期**: 2026-08-28
> **问题**: AMD Ryzen AI Max+ 395 (Strix Halo) 三节点集群（A/B 已运行，C 已购未装），当前 A↔B USB4 直连 + llama.cpp v0.2.0 RPC，MiniMax-M2.7 Q4_K_S 双机 tg128 ≈ 20 t/s。社区还有哪些高性能互连/分布式方案？
> **前提实证**: A2 采证（[metrics-log](../spec/rpc-optimization/metrics-log.md)）已确认 tg 瓶颈是**串行跨链的延迟与命令数**（每 token ≈ 38.7 次 RPC 命令，带宽占用仅 17.6 MB/s = 链路的 0.02%），**不是带宽**。任何"换更粗的管子"方案对该瓶颈基本无效——这是本报告筛选方案的第一判据。

---

## 0. 结论摘要

1. **互连介质层面：USB4 直连已是本硬件形态（迷你主机、无 PCIe 槽）的最优解**。以太网家族（2.5G/5G/10G）与 USB4 实测性能持平（9.4 Gbps 有效带宽同量级），且延迟不占优；其价值在**稳定性兜底**（免疫 TB retimer 振荡）而非提速。硬件 RDMA（E810 RoCE，~5µs）性能显著更优但**需要 PCIe 槽，只有 Framework Desktop / HP Z2 Mini G1a 等机箱可行**，GTR-Pro/NEX 迷你主机无解。
2. **软件栈层面存在一条已被社区验证的真升级路径**：`vLLM TP=2 (张量并行) + Ray + 自定义 MoE Triton kernel` over **现有 USB4 链路**（ayysasha/Strix-halo-dual-optimized，同款模型 MiniMax-M2 AWQ INT4，单流 18.5–24.8 t/s）。它不换线、不换机器，换的是并行策略（层切分→张量并行）+ 通信库（RPC→RCCL/Gloo 集合通信）。
3. **AMD 官方路线**就是 llama.cpp RPC（双节点 GLM-4.7 358B playbook + 四节点 Kimi K2.5 1T 5Gbps 以太网指南），互连用普通以太网即可——官方同样把分布式定位为**容量扩展**而非速度提升。四节点配方 = TTM 120GB/节点 + ROCm 7 (Lemonade SDK) + `--rpc` 多端点。
4. **三节点警示**：strix-halo-guide 社区 USB4 mesh 实测明确 "3-node RPC costs more than 2-node RPC in the measured rows"——节点数超过模型容量所需后，tg 持续劣化。C 节点的正确定位是**容量档**（Q8/Kimi 级模型），不要把 MiniMax-M2.7 从双机搬到三机。
5. **后端变量独立于互连**：AMD 官方与社区大型 MoE 配方全部用 **ROCm**（TTM 120GB 突破 Vulkan/GTT 108GiB 墙 + 绕开 RADV 792MB 分配墙），Vulkan 仅在单机可容纳的中小模型上更快。三节点部署时后端切换（Vulkan→ROCm）是必须评估项。
6. 排除项：exo（MLX/Apple 生态，AMD 不可用）、distributed-llama（CPU 优先，Vulkan 不成熟且慢于 CPU）、prima.cpp（弱设备研究原型，此前已判定不采用）、SGLang（消费级 APU 上部署困难，社区报告失败）、InfiniBand（需 PCIe 槽，同 E810 障碍且更贵）。

## 1. 筛选框架：两条正交轴

社区方案必须拆开看，混在一起谈会导致错误决策：

| 轴 | 选项 | 与本集群的关系 |
|----|------|----------------|
| **互连介质**（线/网卡） | USB4/TB4 直连、以太网 (1G/2.5G/5G/10G/25G)、硬件 RDMA (RoCE v2/IB)、软 RDMA (rxe) | A2 采证证明带宽不是瓶颈 → 介质升级收益有限，延迟才是变量 |
| **并行策略/软件栈** | llama.cpp RPC 层切分、vLLM TP 张量并行 + RCCL、exo/dllama 自研协议 | 命令数/同步模式才是吞吐杀手 → 软件栈升级可能绕开 RPC 串行税 |

关键事实：**Jeff Geerling 四台 M3 Ultra 实测**（Qwen3 235B）——llama.cpp RPC 单机 20.4 → 四机 15.2 t/s（负加速）；exo TP+RDMA 单机 19.5 → 四机 31.9 t/s（正加速）。同一条线、同样四台机器，**软件栈决定分布式是加速还是减速**。这是"互连 vs 软件"两条轴各自重要的最硬证据。

## 2. 方案详评

### 2.1 以太网家族（内置 2.5G/5G、USB 10GbE 适配器、25G SFP+）

**社区证据**：
- AMD 官方四节点 Kimi K2.5（UD_Q2_K_XL, 375GB）指南：**5Gbps 以太网**互连，Ubuntu 24.04 + ROCm 7 + llama.cpp RPC，每节点 TTM 扩到 120GB（`ttm.pages_limit=30720000 amdgpu.gttsize=120000`，四节点合计 480GB），成功跑 1T 参数模型。AMD 双节点 GLM-4.7 358B playbook 同架构（Windows 96GB VGM / Linux amd-ttm --set 120）。
- DGX Spark 双节点（ConnectX-7 200Gb/s QSFP 直连）：llama.cpp v8012 RPC 下 Qwen3-235B 单机 tg 15.51 → 双机 layer-split 8.72（-44%）、row-split 6.07 t/s。**链路带宽是 USB4 的 20 倍，仍救不了 RPC 层切分的 decode**——再次确认介质不是关键变量。
- visorcraft/strix-halo-llm-perf（双 Strix Halo，ROCm）：USB4 直连**有效带宽 ~9.4 Gbps**——与 AMD 4 节点用的 5GbE 以太网同量级，也解释了为什么 AMD 官方指南对互连只要求 5Gbps。
- USB 10GbE 适配器（RTL8156/WisdPi、RTL8157 5GbE）：Jeff Geerling 实测需 USB 3.2 Gen2x2 口才能跑满；ServeTheHome 论坛多篇报告 RTL8157 在 Linux 上**驱动不稳定**（ping 即崩、吞吐崩溃），且 USB 网卡全部**不支持 RDMA**。

**判定**：
- 性能：与 USB4 持平或更差（多一层 USB-以太网转换 + 可能的交换机跳数）。AMD 用 5GbE 只是"够用"，不是"更快"。
- 稳定性：以太网是**唯一免疫 TB retimer found/disconnected 振荡**的方案（本集群 [USB4-40G评估](../spec/rpc-optimization/USB4-40G链路能力评估.md) §4.2 发现的隐患）。作为管理网/心跳网/降级通道有真实价值。
- 结论：**非性能升级项**；建议作为三节点部署时的带外管理网（IPMI 式定位），成本≈0（三台机器都有 2.5GbE 板载口 + 一个 2.5G 交换机）。

### 2.2 vLLM 张量并行 TP=2 over USB4（ayysasha 配方）★ 现有硬件上的真升级

**来源**: [ayysasha/Strix-halo-dual-optimized](https://github.com/ayysasha/Strix-halo-dual-optimized)（MIT，完整可复现配方）。

**架构**：
- 双 Strix Halo，vLLM `--tensor-parallel-size 2 --distributed-executor-backend ray`（Ray 跨物理机编排，multiprocessing 不行）
- **通信**: `GLOO_SOCKET_IFNAME`/`NCCL_SOCKET_IFNAME` 强制集合通信走 USB4net 接口（不走 LAN）
- **内核**: 自调优 fused-MoE Triton kernel 配置（E=256, N=768, `int4_w4a16`）+ **device-name shim**（`moe/sitecustomize.py`，让调优配置在 Radeon 8060S 上真正加载——ROCm 上报的设备名与调优配置键不匹配，无 shim 时调优不生效）
- **模型**: 作者自制 [MiniMax-M2.7-AWQ-G32-STRIX-2H](https://huggingface.co/ayysasha/MiniMax-M2.7-AWQ-G32-STRIX-2H)（AWQ 4bit, group 32，Strix Halo 打包）
- **链路调优**: `99-usb4net-lowlatency.sysctl` + `usb4net-lowlatency.service`（保持 Thunderbolt 唤醒 + CPU EPP=performance），宣称互连延迟降 ~8×
- **服务策略**: 串行化单请求（latency-sensitive 单用户场景），配 llama-swap 前置

**实测**: 单流 18.5–24.8 t/s（同款模型家族 MiniMax-M2/M2.7）。对比本集群 llama.cpp RPC Q4_K_S tg128 ≈ 20 t/s：**上限同量级，上界略高，且 pp 端预期显著更优**（TP 并行 prefill）。另 MiMo-2.5 双 Halo llama.cpp ROCm + USB4net 案例：pp 356 t/s、tg 15 t/s @10k ctx，作为参照系。

**代价与风险**：
- 需要从 GGUF 生态切到 HF 格式 + AWQ 专用量化（作者量化可直接复用）
- 需 ROCm 7 环境（Lemonade SDK/容器），放弃 Vulkan 栈（RADV 优势只存在于单机场景）
- vLLM 在消费级 APU 上并非开箱即用：MiMo-2.5 案例作者明确报告 vLLM 执行错误、SGLang 部署失败——ayysasha 的成功依赖 shim + 调优 kernel + 特定量化三件套，缺一可能翻车
- KV cache/长上下文行为需自测（vLLM 默认行为与 llama.cpp 不同）

**判定**: 唯一**不花钱、不动硬件**、有同款模型实测背书的吞吐升级路径。定位为"第二推理引擎"平行部署（llama.cpp 服务保留），适合作为 Phase A 之后的试验项。

### 2.3 硬件 RDMA：Intel E810 (RoCE v2) + RCCL —— 性能天花板，但需换机箱

**来源**: Framework 社区《AMD Strix Halo RDMA Cluster Setup Guide》（2× Framework Desktop + Intel E810 双口 25G + QSFP28 DAC，Fedora 43）。

**架构与数据**：
- vLLM TP=2 + Ray + **RCCL**（AMD 版 NCCL），RoCE v2 内核旁路
- 延迟：TCP ~70–100µs → **RDMA ~5µs**；带宽 ~50 Gbps
- TP=2 时每层都要 all-reduce，RCCL+RDMA 让双机"像一台机器"——这是把分布式的每层通信税压到最低的物理手段
- 工程细节：E810 固件校验（`ethtool -i`）、内核参数（`iommu=pt pci=realloc`）、MTU 9000、防火墙接口信任、`refresh_toolbox.sh` 自动检测 IB 设备并配容器、**定制 librccl.so 补丁**（RCCL 对 gfx1151 的适配仍有补丁需求）

**硬约束**: **需要 PCIe 槽插 E810**。Framework Desktop 主板有 PCIe x16（半高），HP Z2 Mini G1a 亦可行；**本集群 GTR-Pro / NEX 迷你主机均无可用 PCIe 槽**——此路对现有三节点封闭。仅在未来新增节点选型时作为变量（Framework Desktop 二手价 ≈ 同配迷你主机）。

**判定**: 记录为"若重建集群"的参考架构；对现有硬件标记为**不可行（无槽）**。InfiniBand（ConnectX 系列）同理排除，且更贵、生态更繁琐。

### 2.4 软 RDMA（soft-RoCE / rxe）over thunderbolt-net —— 零成本试验项

- llama.cpp master 已合 RDMA transport（本集群 v0.2.0 未含，协议 v5.1.0 TCP），需 libibverbs；rxe 可跑在任何网卡上包括 thunderbolt_net
- 此前 [RPC串行跨链调研](RPC串行跨链社区优化调研.md) 已列行动项：rxe 试点。**注意外推边界**：M3 Ultra 双节点 DS4-Flash 的 RDMA +52% 恢复收益来自 Apple 硬件 RDMA（TB5 直连 RDMA 引擎），软 rxe 在 CPU 上做 verbs 处理，延迟远达不到 5µs 级，收益不可外推，预期个位数
- 与 #26610（async graph_compute）相比，#26610 直接消灭串行等待，优先级更高；rxe 排在其后
- **判定**: 保留为低成本试验项（`rdma link add rxe0 type rxe netdev thunderbolt0` 即可验证），不作为主路径。

### 2.5 其他分布式框架：全部排除

| 框架 | 机制 | 排除理由 |
|------|------|----------|
| **exo** (exo-explore, 43k★) | PP + TP，MLX 底座 | **MLX 是 Apple 生态**，Strix Halo 无后端；异构支持是宣传重灾区（2026-02 实测：NVIDIA 节点 NVRTC 编译崩、DGX+Mac 混合集群失败报告）。其价值是提供了"TP+RDMA 正加速 vs llama.cpp RPC 负加速"的对照证据 |
| **distributed-llama** (b4rtaz) | TCP 自研协议，2^n 节点，ring | CPU 优先设计（AVX Q40×Q80）；Vulkan 支持新增但**在 Pi5 上慢于纯 CPU**；无 ROCm/HIP 后端——对 40CU iGPU 的 395 是倒退。4×Pi5 Qwen3-30B-A3B 15.1 t/s 属于"弱设备奇迹"，不适用强节点 |
| **prima.cpp** (ICLR) | Halda 层分配 + 分片 | 弱设备（手机/平板/老笔记本）研究原型，此前调研已判定不采用 |
| **SGLang** | 数据中心导向 | 社区在 Strix Halo 部署报告困难（MiMo-2.5 案例作者明确失败），优化目标为数据中心 GPU |
| **Petals** | 公网分布式 | 延迟量级不匹配，仅列作知识背景 |

## 3. 三节点扩展的社区实证与拓扑

1. **节点数原则**（strix-halo-guide COMMUNITY_RESULTS + issue #12，USB4 3-node mesh 实测）："**3-node RPC costs more than 2-node RPC in the measured rows**"；"For ~140GB models that means 2-node, not 3-node. Adding nodes past necessity keeps costing tg performance"——节点数 = 容量所需的最小值，多加必亏。
2. **拓扑**: 本集群 MiniMax-M2.7 Q4_K_S (121GB) 双机已是正确配置；C 节点上线后的角色应是**容量档引擎**（Kimi K2.5 UD_Q2_K_XL 375GB 需四节点 5GbE/USB4 三节点 Q3 档），与 A/B 的速度档（双机 M2.7）并存，由 llama-swap/路由层按模型切换——与 [算子层 DESIGN](../spec/operator-optimization/DESIGN.md) 双路径策略一致。
3. **互连拓扑**: 双机点对点直连最优；三机要么环形（每机两个 USB4 口，strix-halo-guide 提出的 USB4 Ethernet ring）要么经 2.5G/5G 交换机。环形每跳 9.4Gbps，交换机型受限于端口速率但无 mesh 路由复杂度。AMD 官方四节点用交换机 + 5GbE，证明容量档对互连要求很低。
4. **后端**: AMD 官方双节点/四节点配方均 ROCm + TTM 120GB（绕开 Vulkan GTT 108GiB 上限与 RADV 792MB 分配墙——[RPC瓶颈调研](RPC协议瓶颈调研.md) 已识别的潜伏风险）。三节点容量档（超大 MoE）**必须**走 ROCm；速度档（M2.7 Q4_K_S 双机塞得下）维持 Vulkan。Lemonade SDK 提供 gfx1151 ROCm 每日构建（`llama-bxxxx-ubuntu-rocm-gfx1151-x64.zip`），免手动编译。

## 4. 行动建议（按成本分层）

### 零成本（本周可做）
- **A3a** 借用 ayysasha 的 `99-usb4net-lowlatency.sysctl`（TCP 低延迟参数 + 保持 TB 唤醒 + EPP=performance）逐项对照本集群现有 sysctl，增量应用到 llama.cpp RPC 路径——他宣称 8× 延迟削减中的可迁移部分
- **A3b** 确认 A/B 板载 2.5GbE 口 + 交换机组成管理网/心跳网（服务发现、/health、ssh），RPC 流量仍走 USB4——免疫 retimer 振荡的运营韧性

### 低成本试验（Phase A 后）
- **A4 vLLM TP=2 试验**：克隆 ayysasha 配方，拉 MiniMax-M2.7-AWQ-G32-STRIX-2H，在 B 站平行部署 vLLM+Ray（不动 llama.cpp 服务），跑同题对照（tg 单流 / pp / TTFT）。决策门：若单流 tg ≥ 24 t/s 且长上下文 (≥16k) 无崩溃，则 vLLM 路径升级为主力速度档之一
- **A5 软 rxe 验证**：`rdma link add` 一条命令试点，测 rxe over thunderbolt 的 RTT，若 <50µs 且 llama.cpp master RDMA transport 可用，再评估升级 master；否则关闭该项

### 事件驱动（跟踪）
- **A6** llama.cpp #26610 合并 → 走升级 SOP（before/after 锚点已建），预期收益 > 本报告所有互连类方案
- **A7** 未来新增节点若换机箱：选 Framework Desktop（有 PCIe 槽），届时 E810 + RoCE v2 + RCCL 的 ~5µs 路径解锁，vLLM TP 才能逼近单机体验

### 明确不做
- USB 10GbE 适配器（RTL8156/8157）：Linux 驱动不稳定报告多、无 RDMA、不优于 USB4
- exo / distributed-llama / prima.cpp / SGLang：见 §2.5
- 三节点跑 MiniMax-M2.7：负收益（§3.1）
