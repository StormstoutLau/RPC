## 1. 四项决定

### 1.1 算法：`sha256`

**取值**：`sha256`（SHA-256，FIPS 180-4）。

**为什么是它**：7 个出处里已有 5 个用 SHA-256（Open_Data · Macro_Data · factor_pipeline ·
Textbook · 本仓 inbox），是绝对多数；MD5 已知碰撞脆弱，只有 Auto_Prover 与 Fin_Agent 在用，
且前者还额外加 `u_` 前缀试图区分语义（**那正是"同长度不同语义"的补丁**）。

**否掉了什么**：MD5（含 `u_` 前缀变体）；**双算法并存**（那正是当前病）。

### 1.2 截断长度：`[:32]`（32 个十六进制字符 = 128 bit）

**取值**：`[:32]`。★ **2026-09-26 裁定：由 `[:16]` 改为 `[:32]`（对齐蓝本）** —— 本小节的两次变动都留在下面。

**为什么是它**（现在的依据 = 蓝本一致 + 余量）：
- ★ **与权威蓝本一致**：D-23 明裁"**蓝本取 `Open_Data`**"，而蓝本的产物 ID 就是 `sha256("ns|d1|d2")[:32]`
  （`blackmarble/collector.py:204` · `portwatch/collector.py:40` · `eia/collector.py:59` —— 3 处逐行核过）
  ⇒ 统一基座是"向**蓝本**收敛"，不是"向**待迁移的下游**收敛"。
- **余量**：128 bit 下生日碰撞阈值 ≈ `2^64`，比 16（`2^32`）强得多，对任何现实量级都可忽略。
- 代价仅是 ID 长一倍（对日志检索 / URL 嵌入的影响可忽略；到 **64 字符**那种长度才是有问题的）。
⚠⚠ **原依据（`16`）已被两轮实测推翻 —— 如实留档，别重犯**。原文的措辞是"**有在用先例（非纸面）**：
factor_pipeline 与 **Auto_Prover 的 `verdict_id`** 已在用 16 字符"⇒ **这句话说错了两处**：
  - **Auto_Prover 的 `verdict_id` 是 `v_` + **md5 + **12** 字符**（`proof_pipeline/kg/verdict_writer.py:65` ·
    `kg/verdict_store.py:111` · `pipeline.py:203` —— **三处已逐行核过，取值一致**）—— **既不是 sha256、也不是 16**；
  - 真正"16 字符"的是它的 **`case_id`** = `u_` + **md5** + **16**（实现 `proof_pipeline/kg/unified_cases.py:68`；
    `tests/test_s2_unified_cases.py:79` 有 `len == 2 + 16` 的断言 ⇒ 是**被测试钉住的**，不是口头约定）
    ⇒ 原文把 **两个字段混成了一件事**（本仓头号形态，而这次发生在**规范**里）。
  - `factor_pipeline` 侧仍有 `[:16]` 用例（`cache.py:148` · `cache_manager.py:83/156/157/174/175`）✓ ——
    ⚠ 但那是**缓存键 / 头尾哈希**，**未核实**其是否为"产物 ID"。
  - ⚠ **复核时又发现同项目内还有两个更短的 ID 方案**（原文与首稿**均未提**）：`case_` + md5 + **8**
    （`atlas_bridge/agent_runner.py:189`）· `thm_` + md5 + **8**（`stages/stage1_5_sketching.py:142`）
    ⇒ Auto_Prover 的 ID 长度**项目内至少 4 种**（`u_`16 · `v_`12 · `case_`8 · `thm_`8）⇒ 进一步支持 §2 的"不兼容"。
⇒ **"有在用先例"这条依据整体不成立** —— 它同时犯了两个错：**读错了字段**（把 `case_id` 与 `verdict_id`
当成一个）· **把单值当成了全域**（只看到 `factor_pipeline` 一处 `[:16]` 就断言"截断同为 16"）：
  - ★ **补测 `F:\Coding\factor_pipeline`**（原文**漏了**本项目）⇒ 口径化后 **21 行**
    （口径 = `ops/id_site_census.py`；**别再手数** —— 这个数手数过两回，得到过 18 和 16），截断**项目内并存 5 种**
    （`[:8]` / `[:12]` / `[:16]` / `[:32]` / md5 全 64）⇒ **并非"同为 16"**。

★ **本次改动的代价（已履行，如实记）**：本仓 2 个 `u1:` 声明**一并重算** ——
`inventory/dialect.yaml` · `inventory/edges.yaml`（含 `edges.yaml` 那条真实边的 `src` / `dst`）。
D-23 的"不追溯重算**历史产物**"**不适用**于它们 —— 那 2 个是**规范自身的元数据**、且**从未被外部消费**。
⚠⚠ **若将来某个身份已经"外发"过再要改长度，必须另立映射路径（`16` ⇄ `32` 的兼容解析），不能直接改** ——
那正是 D-23 要防的"追溯改历史"。
📌 裁定记录：**O-84（已闭环，裁"改 32"）** · `ops/rpc_check.py` 的 `U1_TRUNC` 注释 · DEV-LOG-014 §44。

**否掉了什么**：~~32 字符（对 ID 用途冗余）~~ ⇒ ⚠ **2026-09-26 改选它**（"冗余"这个判读被推翻：
蓝本**本人**用 32，且"与蓝本不一致"**本身就是一种歧义**）· **16 字符**（原取值，依据已被推翻，见上）·
12 / 8 字符（余量不足，且已被证是 `Auto_Prover` 的**局部**用法、不是可对齐的规范）· 全 64 字符（过长）·
**按用途分流的多长度**（会把"长度"变成需要解释的维度 ⇒ 正是 `Open_Data` 教训要消灭的歧义）。

### 1.3 取值维度：**规范化 JSON 数组**的 UTF-8 字节序列

**取值**：对待哈希对象 `["<namespace>", "<identifier>", "<version>"]` 做
**RFC 8785 规范化 JSON**（无多余空白 · 固定编码 · UTF-8）⇒ 对得到的**字节序列**取 SHA-256。

**字段定义**：

- **`namespace`**：产物所属命名空间。★ **取值域不在此另列一份** ——
  ~~真值 = [`inventory/dialect.yaml`](../../inventory/dialect.yaml) 的 `namespaces[].id`~~
  ⇒ ★★ **2026-10-01 已改（`U1#5` 裁，见末节第 5 条）**：
  真值 = [`inventory/namespaces.yaml`](../../inventory/namespaces.yaml)（**命名空间注册表**，单一真值来源）。
  **为什么换**（**实测**）：`dialect.yaml` 自称**生成物**（"禁止手工编辑语义"）⇒ 取值域挂在它上面时，
  **想新增一个 namespace 没有合法路径**（改它 = 违反生成物纪律；走重抽 = 源里没有这一节）。
  ★ **判据形态（三条治理规则）**：① 新增 = 向注册表追加一条 `status: active`（**门禁不看人，只看登记**）；
  ② 冲突 = **同一个字符串不许属于两条**（id 或 alias）；③ 退役改 `status: retired` 而**不删**。
  ★ **身份里只许写 canonical `id`** —— 写 alias **拒**（哈希吃原字符串 ⇒ 别名放行会让同一产物**有两个身份**）。
- **`identifier`**：业务主键，**原样保留、不做二次哈希**。
  既有各处可无损映射：Open_Data 的「源 + 维度 + 日期」· Macro_Data 的 `full_url` ·
  factor_pipeline 的 `id` · Auto_Prover 的 `normalized` · Fin_Agent 的 `text` ·
  Textbook 的「code + statement + mathlib_ver + lean_ver」· inbox 的文件路径。
- **`version`**：语义化版本（`major.minor.patch`）；**无版本者写 `0.0.0`**（⚠ 见末节第 6 条）。

**连接方式（本项的关键）**：**不做字符串拼接**。用 JSON 数组承载字段 ⇒
由 **RFC 8785 的转义规则**处理"字段里本身就含分隔符 / 引号 / 控制字符"的情形
（既有各处的竖线、双下划线都是特例）⇒ **解码端唯一还原，无歧义**。

**为什么是它**：结构化、自描述、字段顺序固定（消除拼接顺序歧义）；
把"分隔符注入"从"需要维护转义表"降为**规范已定义的行为**。

**否掉了什么**：管道/下划线/竖线等**自定义分隔符拼接**（需自维护转义表、易错）·
**对内容整体哈希**（语义不稳定、无法增量校验）· **只哈希标识符字符串**（丢掉 namespace / version 维度）。

### 1.4 算法标识前缀：`# u1:sha256:32`（**进头部注释**）

**取值**：`# u1:sha256:32` —— 三段式自描述（`u1` = 规范版本 · `sha256` = 算法 · `32` = 截断长度）。

**放置位置**：**独立的头部注释行**（每文件首行；或清单文件里每条之前一行）。

**为什么必须放注释行 —— 一手实测（2026-09-26，本机 Git Bash / coreutils）**：

| 写法 | `sha256sum -c` 结果 | 退出码 |
|---|---|---|
| **A** 前缀独占 `#` 注释行（**本规范主张**） | `_ss_f.txt: OK` | **0** |
| **B** 前缀写进哈希行（`u1:sha256:32:<hash>  file`） | `no properly formatted SHA256 checksum lines found` | **1** |

⇒ 写法 B **不是"格式不好看"，是整份清单校验直接失败**（连一行都没被验）。
而写法 A 被 `sha256sum -c` **静默忽略**（无警告、无输出噪音）。
⇒ 这就是 D-25「前缀进头部注释、不进哈希行」的**实测依据**（此前只是纸上假设）。

**否掉了什么**：写入哈希行（见上表 B）· 前缀只含算法名（无版本、无长度 ⇒ 无法自描述）·
二进制魔数（不便阅读与 grep）。

   "同一 identifier、不同版本"产生**相同哈希**（= 该维度实际失效）⇒ 真实冲突场景未验证。
