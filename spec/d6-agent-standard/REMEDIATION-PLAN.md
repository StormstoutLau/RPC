# D6 开放项：优先级分析与修复计划（2026-09-21）

> **本文什么不做**：不重复 OPEN-ISSUES 的证据与结论（那是登记表），**只做**跨条目的定级、合并与执行顺序。
> 每条都指回 [OPEN-ISSUES.md](OPEN-ISSUES.md) 的对应行。
> **本文会不会过期**：会 —— 定级依赖"触发面是否活跃"，而那会变。**每完成一个工作项就回来改一次**。

## 0. 定级判据（先写判据，否则排序无从复核）

四个因子，**按权重排序**：

1. **是否破坏"判据可信性"**（假绿灯 / rc 失真 / 证据空洞）—— 权重最高。**理由**：本项目的全部价值建立在"判据可信"上，而这类缺陷会让**其余判据同时失效**（一个报 rc=0 的失败路径，能让所有依赖 rc 的自动化误判）。
2. **是否有活跃触发路径**（已被踩到 / 与常态用法重合 / 有真实消费者）—— 区分"理论上会漏"与"现在就在漏"。
3. **失败是否可见**（**静默** 优先于 报错）—— 要报错的东西不会骗人，静默的会。
4. **修复成本 & 是否与其他项共享改动面** —— 同一处改动能一次付清多项时，**提前**。

⇒ **P0**：破坏判据可信性 **且** 有活跃路径。
⇒ **P1**：静默失败 **或** 有真实触发面，且成本低。
⇒ **P2**：结构性根因（会反复产生同类缺陷）**或** 需决策但可延后。
⇒ **P3**：性能 / 体验 / 低概率。

## 2. 四个工作项（**按共享改动面合并** —— 这是计划骨架）

> 原则：**同一处代码 + 同一次验证，能付清多项时就合并**。四项都动 `agent-cli.ps1` ⇒ **串行做**，每步过全套夹具（`_fm_golden_test` 101/101 + `_scrubber_coverage_test` 43/43 + `rpc check`）。

### W1｜judge 面收口（一次改动付清 **4 项**：P1×2 + P0×1 + P0 的一半）

**为什么合并**：这四项全在**同一段代码**（judge 选型 + 敏感度闸 + 判据提示词组装）。

| 步 | 内容 | 完成判据 |
|---|---|---|
| 1 | **换掉不可用的默认 judge**：`ultra`（zen）→ 可用的 egress 或本地 judge；或在 `ROUTE_TABLE`/`JUDGE_TABLE` 加站上 `openrouter/<id>` 条目（已实测 16s 可用、凭据在位、四开关已核） | `test-cards/sanitized.md` **能跑通**（久违的验收路径恢复） |
| 2 | **`compliance` 接线**：把 `Invoke-Review` 里只挡 `local-only` 的窄判据换成**表驱动**（按 `$sens` 卡 judge 选型） | 夹具：`local-only × egress ⇒ 拒`、`sanitized × egress ⇒ 放行`、`sanitized × 本地 ⇒ 放行` 三态 |
| 3 | **同源结构根因**：把 `Resolve-Model` / `Invoke-Task` / `Invoke-Task-Claude` 三处"按型号前缀 `^opencode/` 判"也改为**表驱动的后端属性**（`$backendEgress` 不再硬编码） | 夹具：新增"假想云端后端"负例 —— 加一个带 `egress=$true` 的表项 ⇒ 三处闸**都**能拦住（证明"再加一个后端不漏"） |
| 4 | **`review` 出网加同一套 scrub + `Get-ScrubBlockReason`**（位置：`Build-JudgePrompt` 之后 / `Invoke-Judge` 之前） | 实弹：`sanitized` 卡的 review ⇒ 控制台出现 `SCRUB[…] hit`；夹具：私钥块卡 ⇒ review **拒发** |

⚠ **步 4 与 W4 的①共享同一决策**（"消毒面收到哪为止"）⇒ 若你选"附件不纳入"，步 4 只覆盖提示词（卡正文 + 产出）；若选"全部纳入"，步 4 顺带覆盖附件清单。
⚠ **反对意见（须写进裁定）**：步 4 会让 judge 看到**被抹过的卡正文** ⇒ 评审质量可能下降（判据看到的不是原文）。缓解：只在 `sensitivity: sanitized` 时 scrub，`public` 原样。

### W2｜rc 可信性（P0）

| 步 | 内容 | 完成判据 |
|---|---|---|
| 1 | **复现**：`AGENT_AUTO_FALLBACK=1` + `fallback-deadlock`（`local-only`），打印 `$LASTEXITCODE` | 复现 ⇒ 进 2；**不复现 ⇒ 当场降级为 P2 并改登记**（别为一个看不见的缺陷动关键路径） |
| 2 | 按 09-18 的"归零纪律"修 `AUTO_FALLBACK` 返回点（标量化 / 吸收体内残留输出） | 同一命令 ⇒ 进程 rc **= 4**，与日志一致 |
| 3 | **补夹具断言**"进程级 rc 与日志 rc 一致"（这是缺的那条判据） | 夹具红/绿双向：正常路径绿、注入污染 ⇒ 红 |

### W3｜claude 路静默失败收口（P1）

| 步 | 内容 | 完成判据 |
|---|---|---|
| 1 | **站上变体 + 有附件 ⇒ fail-closed 拒**（`REJECT claude-station-attach-unsupported`，exit 4）—— **优先于"实现附件同步"**：理由 = "缺附件静默跑完"是假绿灯，而"明确拒绝"是可修的错误 | 实弹：`local-only` + `-Cli claude` + `-Attach` ⇒ rc=4 且 **claude run 计数不增** |
| 2 | （可选，后置）真正实现站上变体的附件同步 + `cd` 到站上工作区 | 实弹：附件在站上可读（同 P3 探针卡方法） |
| 3 | **headless 工具单测**：去掉卡里的工具禁令（"不要调用任何工具"），看 claude 路是否真能读文件 | 转录里 `tool_use ≥ 1` ⇒ 可用；`=0` ⇒ 登记"claude 路只能用上下文"这一**能力边界** |

### W4｜消毒面收口（P2，待决策）

| 步 | 内容 | 完成判据 |
|---|---|---|
| 1 | **裁决附件**：(a) 纳入 scrubber / (b) 纪律（含敏感附件的卡强制 `local-only`） | 我建议 **(b)**：附件被抹会破坏任务（agent 读不到原文），而"抹一半"比"明确不抹"更危险 |
| 2 | 落成 DESIGN 的**卡作者纪律**（若选 b）+ 在探针卡里加一条**反向守卫**（断言"附件确实未被抹"） | 夹具/探针：谁将来偷偷加上附件消毒 ⇒ 守卫变红（**决定也可判**） |
| 3 | 重审"被撤回的 `sanitized × 可能训练` 闸" | 该闸与"抹完 = public"**共享同一前提** ⇒ 前提未变则维持撤回（写一句结论即可） |

## 6. 执行顺序（含为什么是这个顺序）

```
W2 (rc 可信性)  →  W1 (judge 面)  →  W3 (claude 路静默失败)  →  W4 (消毒面收口)
   ↑ 先修"读数"        ↑ 再修"承诺"        ↑ 再修"静默"              ↑ 最后"待裁"
```

- **W2 第一**：它修的是**读数本身**。在读数是坏的时候去做别的验证，验证结论都不可信。
- **W1 第二**：它恢复**验收路径**（sanitized 卡能跑）+ 消灭"每加一个后端漏一次"的结构根因 ⇒ 后面 W3/W4 才**有验证手段**。
- **W3 第三**：静默失败，成本低，与 W1 无耦合。
- **W4 最后**：它需要决策，而决策在有验收路径（W1）之后**更容易验证**。
- **P3 批次**穿插在任一步之后（低风险、独立）。
