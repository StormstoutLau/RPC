## 0. 定级判据（先写判据，否则排序无从复核）

四个因子，**按权重排序**：

1. **是否破坏"判据可信性"**（假绿灯 / rc 失真 / 证据空洞）—— 权重最高。**理由**：本项目的全部价值建立在"判据可信"上，而这类缺陷会让**其余判据同时失效**（一个报 rc=0 的失败路径，能让所有依赖 rc 的自动化误判）。
2. **是否有活跃触发路径**（已被踩到 / 与常态用法重合 / 有真实消费者）—— 区分"理论上会漏"与"现在就在漏"。
3. **失败是否可见**（**静默** 优先于 报错）—— 要报错的东西不会骗人，静默的会。
4. **修复成本 & 是否与其他项共享改动面** —— 同一处改动能一次付清多项时，**提前**。

⇒ **P0**：破坏判据可信性 **且** 有活跃路径。
⇒ **P1**：静默失败 **或** 有真实触发面，且成本低。
⇒ **P2**：结构性根因（会反复产生同类缺陷）**或** 需决策但可延后。
⇒ **P3**：性能 / 体验 / 低概率。

## 5. 待裁决事项：细化分析（成本 / 收益 / 短期 / 长期）

### 5.0 先做一次**定级修正**（细化时查出的两个事实，推翻了 §1 的一处定级）

细化前先查了两件事，结果**改变了排序**：

1. **存量出网面**：24 张卡里 `local-only` **21 张**；`public` 3 张（`attach-*`）但**模型都是 `nemotron`（站上本地引擎）⇒ 不出网**。⇒ **真正会出网的卡只有 2 张**：`sanitized.md`（用 `lightning`）与本轮新加的 `scrub-attach-probe.md`（用 `claude`）。
2. **`review` 没有常态调用**：**没有任何卡声明 `review-model`**，且 `ops/` 下**没有任何脚本/自动化调用 `agent-cli review`**（仓里只有它自己的 usage 文本）⇒ 它是 O-16 的"**已实现但未常规化**"能力。

⇒ **修正**：`review` 不消毒**不是"现在就漏"**，而是"**引信已装、尚未点着**"。故：

| 项 | 原定级（§1） | **修正后** |
|---|---|---|
| `review` 出网不消毒 | P0（"活跃"） | **结构性 P0 / 暴露面 P1** —— 缺口是真的（承诺在 review 上是假的），但**当前无常态触发**；一旦 review 纳入常规流程就立刻变活，**且那时卡已在跑、改起来更贵** |
| `task` fallback-reject rc=0 | P0 | **维持 P0**（它不依赖 review 常规化，且 rc 是所有自动化的唯一判读面） |

### 5.1 决策 A：W1 该做到哪一步

**细化新得出的拆分**：W1 的步 1–3 与步 4 **性质不同** ——

- 步 1–3 = **让判据接在真值源上**（结构正确性，**无行为代价**：既不放宽也不收紧现有行为）；
- 步 4 = **把消毒面扩到 review**（策略收紧，**有行为代价**）。

⇒ **拆开**：**W1a（步 1+2+3）= 纯执行项，不必你点头**；**W1b（步 4）单列裁决**。

**W1b 的三个选项**：

| | (a) review 也过 scrub + block | (b) `sanitized` 卡的 review 强制**本地 judge**（**推荐**） | (c) 不动 |
|---|---|---|---|
| 成本 | 小（复用现成函数与规则表） | 小（judge 选型判据 + 夹具） | 0 |
| 收益 | 堵住旁路 | 堵住旁路 **且保住评审保真度** | — |
| 短期影响 | **judge 看到被抹的卡正文** ⇒ 评审质量下降；且"抹完"会把本该被拒的卡伪装成正常（须 `Get-ScrubBlockReason` 配合才安全） | 失去**异源判据**（本地模型审自己人） | 消毒承诺在 review 上继续是假的 |
| 长期影响 | 消毒面 = 出网面，**但保证依赖 scrubber 覆盖率** —— 而那 8 项 PII/拓扑**刻意不覆盖** ⇒ "抹完"仍只是"有条件 public" | 保证变成**结构性**的（不出网 ⇒ 不需要抹、不依赖覆盖率） | 每加一条出网路径就漏一次（**已漏两次**：claude 备路、review） |
| 可逆性 | 可（回滚） | 可（改回 egress judge） | — |

**为什么推荐 (b)**：消毒的**唯一可靠形态是"不出网"**（P3 实测：`local-only` 严于 ZDR）。让 `sanitized` 的 review 走 `main`/`m27`/`rpc-v4flash` ⇒ **零出网** ⇒ ① 不需要抹 ⇒ **无保真度损失**；② **不依赖覆盖率** ⇒ 无"抹过了"的假安全感。(a) 的本质是"把正则当防线"，而正则覆盖率**已被实测证明残缺**（14 项探测形态里 8 项刻意不覆盖）。

**⚠ (b) 的诚实代价**：若某类 review **确实需要异源模型**，则那张卡应**显式**写 `review-model: <egress judge>` 并同时接受出网 —— 即与下面 B(c) **同一个形状**（默认不出网 + 显式放行）。

### 5.2 决策 B：附件怎么收口

| | (a) 附件也过 scrubber | (b) 卡作者纪律（含敏感附件 ⇒ `local-only`） | (c) **附件默认不出网 + 显式放行**（**推荐**） |
|---|---|---|---|
| 成本 | 小（复用规则表）**但天然残缺** | ≈0 | 小（1 条判据 + 1 个豁免字段）+ 夹具 |
| 技术可行性 | ⚠ **只对纯文本附件有效**；二进制 / 压缩包 / 编码（base64、UTF-16）**抹不到** | 不涉及内容 | 不涉及内容（**不看内容 ⇒ 不依赖可判性**） |
| 收益 | 覆盖"纯文本 + 凭据类"附件 | 结构性（不出网） | **结构性 + 不依赖卡作者的意识** |
| 短期影响 | **破坏依赖附件内容的任务**（配置/数据文件里必然出现路径、主机名） | 依赖卡作者守规矩 | 含附件的**出网**任务需加一行显式放行。**存量影响 ≈ 0**（实测：3 张附件卡全是 `public` + 本地模型 ⇒ 本就不出网） |
| 长期影响 | **制造"抹过了"的错觉**（覆盖率天生残缺）⇒ 与"看起来处理过了"同族，**比不抹更危险** | 规则靠人记住 | 与 PII/拓扑的处置**统一**（都交给档位）⇒ **一个概念而非两个** |
| 可逆性 | 可 | 可 | 可（但会改变卡的语义：出网需声明） |

**为什么 (c) 优于 (b)**：(b) 的洞是**判定权在卡作者**（他可能没意识到附件里有机密路径）；(c) 把它变成 **fail-closed 默认拒绝 + 显式放行**，与本项目"默认不出网"的一贯取向一致（`local-only` 的实现也是这个形状）。
**为什么 (a) 排最后**：它把保证建立在**正则覆盖率**上，而附件形态（二进制/压缩/编码）让覆盖率**天生残缺**；且"抹了一半"比"明确不抹"**更难发现** ⇒ 是**假防线**。

### 5.3 决策 C：加"站上 `openrouter/<id>`"路由条目

| 维度 | 分析 |
|---|---|
| 成本 | **小**：1 条表项 + 夹具断言（表项 ↔ 站上 provider 名一致）。站上 provider **已有 key**、**已实测 16s 可用** ⇒ **无新凭据、无新账号、无新政策未知项** |
| 收益（短期） | ① 恢复 `sanitized` 验收卡（唯一那张 `sanitized` 验收卡现在跑不通）；② 修"表里那个消费者其实够不到"的不一致；③ 给"主路打真云"提供通道（P3 复验当时因此没做成） |
| 收益（长期） | 把 zen 从"**必需**"降为"**可选**" ⇒ 减少一个**未核过政策**的第三方依赖（OpenRouter 的四开关我们已逐条核过，zen **完全未核**） |
| 风险 | 多一条出网通道 ⇒ 须纳入敏感度闸。**但若 W1a 已做（判据表驱动），新通道自动纳管** ⇒ **顺序上必须先做 W1a 再加通道**，否则又走"每加一个后端就手改判据"的老路 |
| 不做 | 短期：`sanitized` 验收路径继续断（验收卡跑不通）；长期：zen 的"未核政策"依赖留在链路上 |
| 可逆性 | **完全可逆**（删表项） |

### 5.4 三者的耦合 + 建议的裁决组合

```
决策 C（加站上 openrouter 通道）── 是 决策 A(b) 的实现手段之一 ─┐
                                                              ├─→ 都应在 W1a（判据表驱动）之后落
决策 B（附件默认不出网）── 与 决策 A(b) 同源：                 ┘
        两者回答同一个问题 ——「消毒面收到哪为止」
```

**建议一次裁决的组合**：
1. **W1a（步 1–3）直接做**（无行为代价，且是 C 与 A/B 的**共同前置**：判据接真值源后，新通道/新规则**自动纳管**）。
2. **A 选 (b) + B 选 (c)** —— 两者**同一取向**：**把"出网"变成需要显式放行的例外**，而不是"抹过就算安全"。这两条一起定，才不会出现"附件默认不出网、review 却默认出网"的**不一致**。
3. **C 并入 W1a 一起做**（顺带恢复验收路径 + 修不一致，成本最小）。

⇒ **真正需要你点头的其实是一句话**：**是否接受"`sanitized` 档的 review 与附件默认不出网、出网需显式放行"这个取向**（= A(b) + B(c)）。
C 与 W1a 是纯执行项 —— 你同意取向，我按上面顺序做；你不同意，我们就退回 (a) 方案（抹）并接受评审保真度与覆盖率两处损失。

## 6. 执行顺序（含为什么是这个顺序）

```
W2 (rc 可信性)  →  W1a ✅(已完成)  →  W3 (claude 路静默失败)  →  W1b + W4 (两项待裁)
   ↑ 先修"读数"        ↑ 再修"承诺"        ↑ 再修"静默"                  ↑ 最后"待裁"
```

- **W1a ✅ 已完成（2026-09-21）**：判据已接到真值源、验收路径已恢复 ⇒ 后续 W3/W4 **有了验证手段**。
- **W1b 与 W4 现在可以一起裁**（两者都在回答"消毒面收到哪为止"，见 §5.4）—— 裁完再做，顺序不变。

- **W2 第一**：它修的是**读数本身**。在读数是坏的时候去做别的验证，验证结论都不可信。
- **W1 第二**：它恢复**验收路径**（sanitized 卡能跑）+ 消灭"每加一个后端漏一次"的结构根因 ⇒ 后面 W3/W4 才**有验证手段**。
- **W3 第三**：静默失败，成本低，与 W1 无耦合。
- **W4 最后**：它需要决策，而决策在有验收路径（W1）之后**更容易验证**。
- **P3 批次**穿插在任一步之后（低风险、独立）。
