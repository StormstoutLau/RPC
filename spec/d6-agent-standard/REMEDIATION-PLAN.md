## 0. 定级判据（先写判据，否则排序无从复核）

四个因子，**按权重排序**：

1. **是否破坏"判据可信性"**（假绿灯 / rc 失真 / 证据空洞）—— 权重最高。**理由**：本项目的全部价值建立在"判据可信"上，而这类缺陷会让**其余判据同时失效**（一个报 rc=0 的失败路径，能让所有依赖 rc 的自动化误判）。
2. **是否有活跃触发路径**（已被踩到 / 与常态用法重合 / 有真实消费者）—— 区分"理论上会漏"与"现在就在漏"。
3. **失败是否可见**（**静默** 优先于 报错）—— 要报错的东西不会骗人，静默的会。
4. **修复成本 & 是否与其他项共享改动面** —— 同一处改动能一次付清多项时，**提前**。

⇒ **P0**：破坏判据可信性 **且** 有活跃路径。
⇒ **P1**：静默失败 **或** 有真实触发面，且成本低。
⇒ **P2**：结构性根因（会反复产生同类缺陷）**或** 需决策但可延后。
⇒ **P3**：性能 / 体验 / 低概率。

> **W2 完成记录（2026-09-22）—— 复现成立，而且**影响面比登记的大**：**
> - **复现（实测，非推测）**：`AGENT_AUTO_FALLBACK=1` + `fallback-deadlock` ⇒ 日志逐字 `REJECT local-only+egress (fallback, claude) exit 4`，而**进程 `PROC_RC=0`**。
> - **⚠ 定级修正**：登记写的是"**特定于 AUTO_FALLBACK 那条返回路径**"（理由是 `route` 返回 2、`task -Cli claude` 返回 4 都对）——**错了**。实测**不带** `AGENT_AUTO_FALLBACK` 的普通超时 run 同样 `TASK_DONE … exit=6` + `ledger+=…,6,…` 而**进程 rc=0** ⇒ 真实范围 = "**任何走过 `.attach/` reset 之后的派发**" = **每一次真派发**；成功时看不出（本来就该 0），**失败时被静默读成成功**。那两条"排除普遍性"的反例都恰好在污染点**之前** early-return。
> - **根因（测出来的，不是猜的）**：入口加临时诊断 ⇒ `$code` 是**数组** `@(0, 4)`（`codeIsArray=True count=2 / [0]=Int32 0 / [1]=Int32 4`）。再用 **AST 扫 `Invoke-Task` 体内的"裸语句"**（未赋值、未 `| Out-Null`、未 return）⇒ 定位到 attach-reset 那行**裸调用** `Invoke-RemoteScript`（返回 int rc、成功后=0；09-18 缺口 5 把 `.attach/` 清理改成**无条件** ⇒ **每次派发都跑**）。机制另经**独立钉死**（临时脚本直测进程 rc）：`exit 4`⇒4 / `exit @($null,4)`⇒**0** / `exit @(0,4)`⇒**0**。
>   - **同族根因**：09-18"归零纪律"清点时只覆盖 **cmdlet**（`Copy-Item`/`Move-Item`/`Remove-Item`/`Add-Content`），**漏了自定义函数的返回值**。
> - **修法（两层，都要）**：① **根因** = 全仓 **6 处**裸 `Invoke-RemoteScript` 一律 `| Out-Null`；② **出口守卫** = 新增纯函数 `Resolve-ExitCode`（取**末元素**）并让**全部 5 个** `exit $code` 走它（防"新增子命令又漏"）。⚠ 守卫规则与 `_probe_fallback.ps1` 早已存在的 `Scalar` **完全相同** —— 这正是"**探针一直没被骗到、只有 CLI 的调用方被骗**"的原因。
> - **实测闭环**：同一命令 ⇒ `REJECT … exit 4` + **`PROC_RC=4`**，与日志一致。
> - **自证**：夹具 **137→147**（+10）+ **变异自证 3 次**（删回 `| Out-Null` ⇒ 裸调用断言红；守卫改取**首**元素 ⇒ 2 条标量化断言红；撤一处出口守卫 ⇒ 2 条计数断言红）。
> - ⚠⚠ **自证当场抓出我自己的一条假判据（本轮第二值钱的发现）**：裸调用的 **AST 判据第一版只判 `StatementBlockAst`**，而**函数体是 `NamedBlockAst`（与它是兄弟类，不是子类）** ⇒ "写在函数体顶层"的语句**全被漏掉** —— 而那处 bug 恰在顶层 ⇒ **删回 `| Out-Null` 也照样 PASS（假安全）**。收了两个容器类型后才红。**教训（与"位置断言被注释骗"同族）**：**结构判据必须先在"已知该红"的变异上验红，否则它只是"在跑"，不是在判。**

### 5.1 决策 A：W1 该做到哪一步

> ⚠ **结论已由 §5.5.1 裁定为 (a)（与 §5.1 原推荐 (b) 相反）** —— 下面的选项表是决策依据，保留；**别只看本节的"推荐"两字**。

**细化新得出的拆分**：W1 的步 1–3 与步 4 **性质不同** ——

- 步 1–3 = **让判据接在真值源上**（结构正确性，**无行为代价**：既不放宽也不收紧现有行为）；
- 步 4 = **把消毒面扩到 review**（策略收紧，**有行为代价**）。

⇒ **拆开**：**W1a（步 1+2+3）= 纯执行项，不必你点头**；**W1b（步 4）单列裁决**。

**W1b 的三个选项**：

| | (a) review 也过 scrub + block | (b) `sanitized` 卡的 review 强制**本地 judge**（**推荐**） | (c) 不动 |

| 成本 | 小（复用现成函数与规则表） | 小（judge 选型判据 + 夹具） | 0 |

### 5.2 决策 B：附件怎么收口

> ⚠ **结论已由 §5.5.2 裁定为 (c)**（与本节的推荐一致，但**理由更硬**：不是"作者可能不小心"，而是"**附件形态不可判 ⇒ 不能靠抹**"）。

| | (a) 附件也过 scrubber | (b) 卡作者纪律（含敏感附件 ⇒ `local-only`） | (c) **附件默认不出网 + 显式放行**（**推荐**） |
|---|---|---|---|
| 成本 | 小（复用规则表）**但天然残缺** | ≈0 | 小（1 条判据 + 1 个豁免字段）+ 夹具 |
| 技术可行性 | ⚠ **只对纯文本附件有效**；二进制 / 压缩包 / 编码（base64、UTF-16）**抹不到** | 不涉及内容 | 不涉及内容（**不看内容 ⇒ 不依赖可判性**） |
| 收益 | 覆盖"纯文本 + 凭据类"附件 | 结构性（不出网） | **结构性 + 不依赖卡作者的意识** |
| 短期影响 | **破坏依赖附件内容的任务**（配置/数据文件里必然出现路径、主机名） | 依赖卡作者守规矩 | 含附件的**出网**任务需加一行显式放行。**存量影响 ≈ 0**（实测：3 张附件卡全是 `public` + 本地模型 ⇒ 本就不出网） |
| 长期影响 | **制造"抹过了"的错觉**（覆盖率天生残缺）⇒ 与"看起来处理过了"同族，**比不抹更危险** | 规则靠人记住 | 与 PII/拓扑的处置**统一**（都交给档位）⇒ **一个概念而非两个** |
| 可逆性 | 可 | 可 | 可（但会改变卡的语义：出网需声明） |

**为什么 (c) 优于 (b)**：(b) 的洞是**判定权在卡作者**（他可能没意识到附件里有机密路径）；(c) 把它变成 **fail-closed 默认拒绝 + 显式放行**，与本项目"默认不出网"的一贯取向一致（`local-only` 的实现也是这个形状）。
**为什么 (a) 排最后**：它把保证建立在**正则覆盖率**上，而附件形态（二进制/压缩/编码）让覆盖率**天生残缺**；且"抹了一半"比"明确不抹"**更难发现** ⇒ 是**假防线**。

| 收益（短期） | ① 恢复 `sanitized` 验收卡（唯一那张 `sanitized` 验收卡现在跑不通）；② 修"表里那个消费者其实够不到"的不一致；③ 给"主路打真云"提供通道（P3 复验当时因此没做成） |

| 风险 | 多一条出网通道 ⇒ 须纳入敏感度闸。**但若 W1a 已做（判据表驱动），新通道自动纳管** ⇒ **顺序上必须先做 W1a 再加通道**，否则又走"每加一个后端就手改判据"的老路 |
| 不做 | 短期：`sanitized` 验收路径继续断（验收卡跑不通）；长期：zen 的"未核政策"依赖留在链路上 |
| 可逆性 | **完全可逆**（删表项） |

### 5.4 三者的耦合 + 建议的裁决组合

```
决策 C（加站上 openrouter 通道）── 是 决策 A(b) 的实现手段之一 ─┐
                                                              ├─→ 都应在 W1a（判据表驱动）之后落
决策 B（附件默认不出网）── 与 决策 A(b) 同源：                 ┘
        两者回答同一个问题 ——「消毒面收到哪为止」
```

**建议一次裁决的组合**：
1. **W1a（步 1–3）直接做**（无行为代价，且是 C 与 A/B 的**共同前置**：判据接真值源后，新通道/新规则**自动纳管**）。
2. **A 选 (b) + B 选 (c)** —— 两者**同一取向**：**把"出网"变成需要显式放行的例外**，而不是"抹过就算安全"。这两条一起定，才不会出现"附件默认不出网、review 却默认出网"的**不一致**。
3. **C 并入 W1a 一起做**（顺带恢复验收路径 + 修不一致，成本最小）。

⇒ **本节的"一句话"已于 2026-09-22 裁定（见 §5.5）**：**A = (a)（review 复用同一套 scrub + block，保持 `sanitized` 档的"抹后可出网"语义）/ B = (c)（附件默认不出网 + 显式放行）**。
⚠ 注意 A 与 §5.4 原先的推测方向相反 —— 我原以为取向应是"默认不出网"，写裁定时发现**对"可判"的载体（正文/judge 提示词）应沿用档位定义抹后可出网**，只有**不可判**的载体（附件）才默认不出网。**统一判据是"可判性"，不是"保守程度"**。
C 与 W1a 是纯执行项（W1a 已完成）；**A/B 的实施项见 §5.5.3，待批后执行**。

### 5.5 裁定结论（2026-09-22｜W1b 与 W4 各一条）

> ⚠ **本裁定修正了 §5.1 的推荐**（原推荐 (b) 本地 judge）—— 不是选项分析变了，而是写裁定时发现
> 原推荐**与 `sanitized` 档自身的定义冲突**。修正理由见 5.5.1 的"决定性判据"。§5.1/§5.2 的选项表保留（决策依据），
> 但**结论以本节为准**。

#### 5.5.1 裁定 A（W1b）：`review` 出网 → **选 (a)：与派发同一套 scrub + block**

**决定性判据 = 档位语义一致性。** `sanitized` 这一档的**定义**就是"**含可机判敏感项 ⇒ 机械 scrub 后进远端**"（DESIGN §2.1）。
⇒ 对**同一张卡**，"派发可出网、review 不可"会**让档位的含义取决于你跑哪个子命令** —— 这正是本项目一直在消灭的"同一概念两个定义点"。

原推荐 (b)（强制本地 judge）把保证从"覆盖率"移到"物理不出网"，方向是对的，但代价有两处**当时没算足**：
① 它把 `sanitized` 在 review 上**降级成 `local-only` 的语义**（同一张卡两个含义）；
② 它引入一个**新的可用性依赖** —— 三个本地 judge 都要**引擎在位**（`main` = 控制台 opencode + `local/nemotron`；`m27`/`rpc-v4flash` = 站上 `/v1`）⇒ 引擎不在位时，`sanitized` 卡的 review 会 **fail-closed 直接不可用**。

⇒ **(a) 胜在"一致 + 可用"，且不新增依赖类别**：派发路径**已经**依赖同一套 scrubber 覆盖率，review 只是**复用**，不是新增敞口。

**必须同时做三件事（否则 (a) 不完整）**：
1. 复用 `Get-ScrubRules` / `Invoke-Scrubber`（**单一真值源**，绝不写第二套规则）；
2. **同时**接 `Get-ScrubBlockReason` —— 否则"抹完"会把本该被拒的卡（私钥块）**伪装成正常**（沿用 DESIGN §193 的二分依据：**能不能安全抹除**）；
3. **只对 `sanitized` 抹**：`public` 原样（它没有承诺）、`local-only` 本就只能走本地 judge（已有闸）。

**保留 (b) 作为显式可选（不需要新机制）**：卡可写 `review-model: main`（或 `m27`/`rpc-v4flash`）把该卡的 review 钉在本地 —— `Invoke-Review` 的选型链（`--model` > `review-model` > 默认）与已接线的 `compliance` 闸**都已支持**。

**反对意见 3 条（已列）**：① (a) 让 judge 看到被抹的卡正文 —— 对"四档评分"通常无影响（被抹的正是**不该影响判断**的秘密）；② (a) 仍依赖 scrubber 覆盖率，而它**已知残缺**（14 项探测形态里 8 项刻意不覆盖 + 2 项残留缺口）—— 但**该敞口在派发路径上已存在且已登记**，review 复用它**不增大**敞口；③ **重审条件**：若将来 review 要承担"合规审计"用途（**需要原文**），则应改回 (b)。

#### 5.5.2 裁定 B（W4）：附件收口 → **选 (c)：附件默认不出网 + 显式放行**

**决定性判据 = 可判性。** 附件的**形态不可判**（二进制 / 压缩包 / base64 / UTF-16 / 未知编码）⇒ **无法**像卡正文那样把"抹干净"做成**可测的覆盖率**。而本项目确立的**第一条判据就是"可判性"**（[scrubber 规则扩充裁定 §6](../../docs/security/2026-09-21_scrubber规则扩充裁定与影响面.md)：①可判性 × ②真敏感 × ③误伤≈0 × ④有出现路径）⇒ 对**不可判**的载体，"抹"只产出**假防线**（"抹了一半"比"明确不抹"**更难发现**）。

⇒ 与 5.5.1 合起来，是**同一条原则在三个地方一致**：

| 载体 | 可判性 | 裁定 |
|---|---|---|
| 卡正文（`task` + `body`） | **可判**（正则 + 已建 14 项覆盖率判据） | **抹后可出网**（= `sanitized` 档的定义，见 5.5.1） |
| judge 提示词（卡正文 + agent 产出） | **可判**（同一套规则） | **抹后可出网**（5.5.1） |
| **附件** | **不可判**（形态未知） | **默认不出网 + 显式放行**（本裁定） |

**为什么不是 (b)（卡作者纪律）**：两者都靠"不出网"兜底，但 (b) 的**判定权在卡作者**（他未必知道附件里有机密路径）；(c) 是 **fail-closed 默认拒绝**，与 `local-only` 的实现**同一形状**。
**为什么 (a)（附件也抹）排最后**：见上 —— 形态不可判 ⇒ 覆盖率天生残缺 ⇒ **假防线**。
**存量影响 ≈ 0**（实测：3 张附件卡全是 `public` + **本地模型** ⇒ 本就不出网）。

**实施形态（待批）**：`-Attach` 非空 **且** 目标后端出网 **且** 卡未显式声明放行 ⇒ `REJECT attach-egress-unconfirmed (…, exit 4)`；放行字段建议 `attach-egress: ok`（与 `review-model` 同属"**显式接受出网**"家族）。⚠ 该字段是**卡 schema 变更** ⇒ 需同步 `Get-FrontMatter` 预置键 / 文档 / 夹具。

#### 5.5.4 收尾（追补，2026-09-22）：`review.json` 进产出方基线

**由来**：§5.5.3 实施并提交后跑门禁，报出 **WARN「可重放性审计：新增 1 条」**，明细逐字为
`paper/202609221131192690: 已归档但未被任何 subject 覆盖: review.json`。门禁的处置建议**逐字**给出了修法：
> 若明细里是「已归档但未被任何 subject 覆盖」= 新证据件没进产出方基线 ⇒ **应改 `ops/station-bin/agent-cli.ps1` 的 `Get-FrameworkSubjects`（清单唯一真值在那里），而不是接受它**

**根因**：`review` 子命令**事后**往 runDir 写 `review.json`（O-16 的"并行键"，`NEVER alters run.json/task accept semantics`），
而 `agent_audit` 的 undeclared 判据**动态枚举 runDir** ⇒ 只要某个 run 被 review 过一次，该件就成了"已归档但未被任何 subject 覆盖"。

**修法**：把 `review` 作为基线件加进 **两个**按路基线（`Get-FrameworkSubjects` / `Get-ClaudeFrameworkSubjects`），并**必须带 `ephemeral = $true`**。
- **为什么两个都要**：`Get-ReviewRunDir` 按 `.agent-run.json` **动态选目录、不分路** ⇒ claude 路的 run 一样能被 review、一样会落 `review.json`，不补则必然重演同一条缺口。
- **为什么必须带 `ephemeral`**：`review.json` 是**事后写入、非派发必有** ⇒ 裸列会让**每个没 review 过的 run** 都假报 `missing-artifact`（与既有那条"`accept-output` 不能无条件列入"是同族错误）。`ephemeral` 在此承担**第三态**的语义：不是"必有"，而是"**可合法缺席**" —— 缺席 ⇒ `artifact-ephemeral-by-design`（**不是缺口**），存在 ⇒ `offline-ok`（branch 3 已穷尽，两支都非缺口）。

**⚠ 关键发现（差点误判为"改完门禁就变绿"）**：**manifest 是派发时快照 ⇒ 改基线不回溯**（ADR-0007 已记过同一条"改卡不回溯"）。
⇒ 本条 WARN **不会被本次修复消掉** —— 存量那条 run 的 manifest 是**修复前**写的。本次修法只保证**将来**的 run 不再产生该缺口；
存量那条属**历史欠账**（同 v1 run 的先例），要消掉只能推进水印（`agent audit --accept`），而**推进水印按设计是人的显式动作**
（门禁全程只读、水印 `inventory/audit-baseline.json`（**2026-09-23 起已入仓**；原 `ops/.audit-baseline.json` 被 gitignore，见台账 O-33））—— 故本项**停在"修根因 + 报"**，不代跑 `--accept`。
