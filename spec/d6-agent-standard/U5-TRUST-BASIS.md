### 1.1 ★ V-1 的判据边界（不许把"有对照表"说成"定义正确"）

`v1_definition_correspondence` **只能**判"**对应关系被逐条写明且可追溯**"；
**"对应得对不对"仍需人**。⇒ 结论里必须带这句边界，否则就是一次典型的
"**判据判了别的东西**"（本仓头号形态）。

### 1.2 ★ V-3 是唯一"从关键词级升为白名单级"的一条

原文明确要求升级（§11.2：「需从**关键词级**升为**白名单级**」）。
本判据就是白名单比对；且**白名单为空 ⇒ fail**（否则"空白名单"会让判据恒真）。

### 1.3 ★ V-2 与其他三条**不同源**

V-1 / V-3 / V-4 都是把**已有实现**的做法升为机判；
**V-2 是真空**（九项目**没有一个**做过）⇒ `v2_bridge_completeness` 是**新造的形式**，
**不是**对既有实现的机判化。这一条必须区别对待，**不许混进"三处复用"的说法里**。

## 2. 晋升门 schema（D-38 的落地）

**已裁**：三处独立发明的晋升门 ⇒ **统一为一个 schema**，判据 = **成功率 / 复发次数 / 验证状态**，
**并存于同一 schema 的不同字段**；schema 须能被三处**各自映射**。

### 2.1 三处实现 → 同一 schema

| 实现（原文实测） | 它的判据 | 映射到 schema 的 |
|---|---|---|
| `Textbook` `FixMemory` | `success_count >= min_success_for_inject`（**唯一有完整三件套**：准入 + 容量 + 注入门槛） | 判据 `success_rate` · 字段 `success_count` / `min_success_for_inject` / `entries`（容量） |
| `Spec_Workflow` `discoveries/` | **"跨项目 / 跨 feature 复发"**；明文 **"缺锚点不得登记"** | 判据 `recurrence` · 字段 `recurrence` / `min_recurrence` · 必填 `anchor` |
| `Fin_Agent` `run_p0a_v2_batch` | **仅 `verified=True` 才写共享层** | 判据 `verified` · 字段 `verified` |

### 2.2 schema 的四件套

| 件 | 内容 | 依据 |
|---|---|---|
| **必填** | `anchor`（**缺锚点不得登记**） | `Spec_Workflow` 原文 **+** 本仓 [ADR-0007](../../adr/ADR-0007-证据流阶段推进路线与改动验证闭环.md)「an anchor is REQUIRED」⇒ **两处独立同源** |
| **容量** | `entries` ≤ 50 · `lru` | `Textbook` `FixMemory` 的容量件套 |
| **判据** | `success_rate` / `recurrence` / `verified` 三条，**任一满足即可晋升** | D-38（三处并存） |
| **结构** | 生成端/审计端**不对称配置** · **双盲**（审计者不得接触原推理文本） | §11.7（**单人开发者是常态假设** ⇒ 不得自审只能靠结构，不能靠人） |

### 2.3 ★ 门禁 `promotion` 的核心规则 = **映射闭包**

> **schema 里不许有孤儿字段 / 孤儿判据。**

一个**没有任何一处实现用到**的字段，就是**变相发明的第四种** —— 这正是 D-38 要禁的。
⇒ 门禁逐条判：`mapping_closure` 的 `uses` ∪ 必须覆盖 `fields` 全集、
`criteria_used` ∪ 必须覆盖 `criteria` 全集，且 `uses`/`criteria_used` 必须是 `fields`/`criteria` 的**子集**。
