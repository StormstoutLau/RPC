## 任务描述

**背景（抽象）**：有一个研究方法仓库，它的核心教训是 —— **"判据通过了，是因为它什么都没判"**：
一条检查显示"合格"，既可能因为它真检了，也可能因为它**恒为真 / 范围为空 / 异常被吞 / 只测了自己**。
仓库正在为若干"能力缺口"写**设计底稿**（形态 + 判据 + 假绿清单 + 缺料）。

**你的任务 = 对下面两份设计底稿做**独立缺陷复核**（**不采信底稿的自述**）。要找的是：

1. **内部矛盾** —— 底稿里两处说法互相冲突。⚠ 本类**最典型**的一种：一处把**非确定**的东西（时间戳 / 运行 ID / 绝对路径）
   列进"产物应包含的字段"，另一处又要求"两次运行**逐字节一致**" ⇒ **两条不可能同时成立**。
2. **机械缺陷 / 可漏报点** —— 设计里某个环节**报"成功/一致"但其实没覆盖**。
3. **假绿清单不实 / 不全** —— 清单里某条**与设计矛盾**（其实根本不会发生），或**漏掉了**最明显的一类。
4. **未加论证的断言** —— 声称"必然 / 一定 / 零遗漏 / 不可绕过"，却没有支撑。

### 唯一产物：`out/xrev2.md`

格式固定：

- 先写一行 `## 底稿一`，再逐条写缺陷，**每条一行、以 `- ` 开头**：
  `- [等级: 高/中/低] <缺陷一句话> ｜ 依据: <引底稿原文片段，≤30 字> ｜ 修法: <一句话>`
- 再写一行 `## 底稿二`，同样逐条。
- **每一份至少 4 条**。
- 拿不准的写等级 `低`，修法处写 `不确定：<缺什么>`。
- 末尾加一节 `## 无法判断项`：你没有足够信息判定的部分，逐条说明缺什么。

### 硬性要求

1. **只读复核**：**不要修改**内嵌底稿的任何内容；**不要**把底稿大段抄进产物。
2. **不许编造**：底稿里读不出来的 ⇒ 标 `不确定`，**不要猜**。
3. **不要引用、不要推测**任何具体项目 / 组织 / 主机 / 路径 / 人名。
4. `out/xrev2.md` 里 `^- ` 的行数 **≥ 8**。
5. **stdout 只输出一行**：`DOGFOOD_XREV2_OK`
6. 除 `out/xrev2.md` 外**不产生任何文件**。

## 视图形态

- 格式：纯文本 Markdown（`.md`），UTF-8，LF 换行
- 含确定性字段：`source-hash: <sha256-of-truth-files>`、`generator: <tool-version>`、`generated-at: <RFC3339-UTC>`（UTC 时间戳，非本地时区）
- 头部必须包含注释行：`<!-- DERIVED VIEW — DO NOT EDIT MANUALLY -->`
- 正文仅含渲染结果，**不含**任何运行时状态、临时 ID、随机数

## 落档与刷新

- **谁**：CI 构建步骤（`make derive-view` 或等价脚本），**不依赖**本地开发者手动执行
- **何时**：每次合入主分支前（PR gate）、以及真值文件变更的任何提交
- 刷新失败：**必须**非零退出码、且把完整错误写入 `stderr`，**不许**写入部分结果再静默成功
- 真值文件集合由 `sources.yaml` 显式声明（路径列表），缺一不可

## --check 判据

| 场景 | 退出码 | 说明 |
|------|--------|------|
| 渲染结果与落档逐字节一致 | 0 | 绿 |
| 渲染结果与落档不一致 | 1 | 红——视图过期 |
| 渲染器本身失败（读源错、模板错、OOM 等） | 2 | 红——渲染链路故障 |

**防恒真规则**：`source-hash` 与当前真值文件集合的哈希不一致 ⇒ 直接退出码 1，**不再比对正文**

## 假绿

1. 渲染器与 `--check` 共用同一有缺陷的依赖库 ⇒ 双方一起错、哈希看似一致
2. `sources.yaml` 漏列了某真值文件 ⇒ 该文件改动不触发 `source-hash` 变化
3. 生成器把非确定性字段（如进程 PID、内存地址、未固定种子的随机序）写入视图 ⇒ 每次渲染都不同，但 `--check` 若先落档再比对会误判为一致
4. 不确定：文件系统大小写不敏感导致路径规范化差异 ⇒ 可能在 macOS/Windows 上漏报

## 缺料与歧义

- 视图文件是否纳入版本控制（Git LFS？提交体积阈值？）— **不确定**
- 多仓库共享真值时，`source-hash` 计算边界怎么划（跨 repo 相对路径？子模块？）— **不确定**
- `--check` 是否需支持"仅校验 source-hash、跳过正文比对"的快速模式— **不确定**
- 渲染器版本升级导致合法格式变更（如表格对齐方式）如何区分"合理变更"与"漂移"— **不确定**
- 真值文件若为二进制/大文件，哈希计算性能与增量策略— **不确定**

## 要抓什么
命令执行记录（命令+参数+开始/结束时间+退出码） | 还原"做了什么"的因果链
文件系统写入集合（路径+操作类型+字节数+内容哈希） | 交叉锚定工作区改动摘要
环境快照（进程树+环境变量+工作目录） | 排除环境差异导致的不可复现
工具调用链（工具名+输入摘要+输出摘要+耗时） | 覆盖 agent 内部决策路径
产物哈希清单（最终交付物路径+内容哈希） | 与主控侧回收证据交叉验证

## 在哪抓（采集点）
命令执行记录：执行体外壳（内核审计/ebpf）— 内核级不可绕过，零侵入
文件系统写入集合：文件系统层（overlayfs 上层/inotify）— 外部视角，执行体无法篡改
环境快照：执行体启动器（fork 前捕获）— 单次采集，成本极低
工具调用链：执行体内部（框架级埋点）— **必须信任执行体，不可核**
产物哈希清单：主控侧回收时计算— 执行体外生成，可信

## 可核条件
命令执行记录：内核审计日志可由第三方复算，与产物哈希交叉锚定
文件系统写入集合：overlayfs 上层变更可离线复核，与工作区摘要交叉
环境快照：启动器记录可与进程树快照交叉验证
工具调用链：**不可核**（执行体内部产生，执行体可篡改/漏报/伪造）
产物哈希清单：主控侧独立计算，与执行体声称交叉比对

## 假绿
执行体在容器内执行，宿主机审计看不到容器内系统调用
执行体通过 mmap 修改文件，绕过 write 系统调用，文件系统监控漏报
执行体用解释器执行脚本（python -c），命令行只见解释器不见真实逻辑

## 缺料与歧义
命令归一化：argv 如何规范化（展开通配符/别名/环境变量？），无统一标准
二进制/交互式命令：ssh/tmux/vim 等交互式会话的"命令边界"如何切分，不确定
工具调用链的输入/输出摘要粒度：摘要算法未定，可能丢失关键语义
网络调用是否纳入留痕：外部 API 请求对结论的影响未界定
多进程/并发执行时的因果排序：壳层审计日志的时序一致性不确定
