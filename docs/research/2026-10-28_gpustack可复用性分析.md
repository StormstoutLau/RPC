## 2. 可直接复用（口径 / 算法级）

### 2.1 UMA 容量口径

`policies/resource_view.py:117-142`：

```
allocatable.vram[i] = max(total_vram[i] - allocated.vram[i] - system_reserved.vram, 0)
allocatable.ram     = max(total_ram - allocated.ram - system_reserved.ram, 0)
if is_unified_memory:
    allocatable.ram  = max(allocatable.ram - system_reserved.vram - sum(allocated.vram), 0)
    allocatable.vram[0] = min(allocatable.ram, allocatable.vram[0])
```

与本集群同构：AMD 8060S 是 UMA，GTT 就是**同一池**。我们当前 `_guard_capacity` 只用 `estimate_load` 的 `pad_gib=12` 粗判，缺的就是这段「已用 + 预留」的精确对账。

### 2.2 fit 判据（UMA 分支）

`policies/candidate_selectors/gguf_resource_fit_selector.py:734-746`：

```
if is_unified_memory:
    if vram_claim > allocatable_vram:            return None, True    # 这张卡放不下
    if ram_claim  > allocatable_ram - vram_claim: return None, False   # 主机内存放不下
else:
    ...
```

迁移价值：**「同站放第二个模型」必须扣掉第一个的占用**。我们的 `estimate_load` 只回答「这个模型要多少」，没有这条交叉扣减 —— 这正是 P0 补强的落点。

### 2.3 端口预留簿记

`worker/port_reservations.py:56-121`：

- 不是固定端口池，而是**配置段内 bind 探测**（故意不加 `SO_REUSEADDR`）+ 本地内存表 + 持久化占用；
- 并发用单把 `threading.Lock` + `_generation` 计数器：**API 读在锁外**（慢调用不能阻塞清理），回来发现 generation 变了就整体重试；
- 无 TTL 租约，陈旧占用靠「持久化行 + generation」兜底。

迁移价值：我们 P2 的痛点是「`18080` 撞车只能靠 health 超时发现」。这套约 150 行可裁剪，且有 5 个并发测试兜底（`tests/worker/test_port_reservation*.py`）。

## 5. 一个本仓缺失的概念：`system_reserved`

GPUStack 每个 worker 都有 `system_reserved.{ram,vram}` 并参与**每一条**判据。本仓完全没有 —— 这是结构性原因：

- A 站 worker 常态 GTT **110.7 / 125.8G**（余 15.2G）；
- 10-26 两次 `vk::DeviceLostError` 都发生在 GTT 余 ~15–24G 的区间。

⇒ 容量门必须扣一笔预留（本仓定为 `STATION_RESERVED_GIB = 8.0`，见 P0 补强）。

### 8.1 两条可引用的原则

- **「判不了 ≠ 通过，也 ≠ 拒绝」**：`port_capacity` 与 `derive_net_device` 都不把"读不到"当成 0/False，而是留痕后放行或放弃该变量 —— 与本仓 `_guard_port`（ssh 失败留痕放行）、`_guard_capacity`（GTT 读不到回退第 1 道并留痕）同构。
- **「失败时不要编造值」**：`net_device.py` 宁可返回 `None` 让占位符留在命令行上被引擎按名拒绝，也不回退到 `UCX_NET_DEVICES=all` —— 理由是「错的值比干净失败更糟，且故障点远离配置点」。本仓对应纪律：`_uma_fit` 的 `UNKNOWN` 不进放行集；`--keep` 判不出归属只 WARN、不猜。

### 8.2 附带发现（对应 O-181 的遗留项）

`worker/net_device.py` 对「多候选」的处理是**报出候选清单 + 让运维显式指定**，而不是只报一句"不可达"。本仓 `infer-unload` 在 B 站向远端 worker（`10.10.10.1` / `10.10.11.3`）停 `rpc-server@*` 时只打印「不可达」（stderr 被 `2>/dev/null` 吞掉）⇒ 无法区分 host key、地址选错还是链路问题。该缺口已登记为 `O-181` 的遗留项；修法可照此：**保留原始 stderr 并列出候选地址**。
**已修（2026-10-29 23:06）**：根因 = `sudo` 下 `id -un` = root（`~/.ssh` 只有 0 字节 authorized_keys、无 known_hosts），网络本身正常（ping 0.144 ms）。改法 = `RPC_USER` 按「显式 > nodes.env 的 `RPC_USER=` > 首个持钥用户」解析 + 远端 ssh 失败保留 stderr；真站正/负向均验（详见 `O-181`）。

### 8.4 O-181 诊断证据（2026-10-29 23:05 · B 站只读实测）

> 结论：`infer-unload` 的「远端 worker 不可达」**不是网络问题，是身份降级**（`sudo` 下 `id -un` = root，而 root 没有密钥）。

| 检查 | 读数 | 说明 |
|---|---|---|
| `ping 10.10.10.1`（B→A） | **0.144 ms · 0% 丢包** | 链路正常 |
| `sudo -u scott-lau ssh 10.10.10.1 hostname` | `scott-lau-NEX` | 服务用户可达 A |
| `sudo -u scott-lau ssh 10.10.11.3 hostname` | `seaviv` | 服务用户可达 C |
| `sudo ssh 10.10.10.1 hostname` | `Host key verification failed.` | root 无密钥、无 known_hosts |
| `sudo ssh 10.10.11.3 hostname` | 同上 | 同一根因 |
| root `~/.ssh` | 仅 `authorized_keys`（**0 字节**） | 无 `id_*`、无 `known_hosts` |
| `scott-lau` `~/.ssh` | `id_ed25519`（419 B）+ `known_hosts`（22 条） | 唯一可用通道 |
| `/etc/llama-instances/nodes.env` | 只有 `RPC_NODES`，**无 `RPC_USER`** | `id -un` 退化为 root 的直接原因 |

**修法（方案乙）**：`RPC_USER` 解析改为「显式环境变量 > nodes.env 的 `RPC_USER=` > 本机首个持 `id_ed25519`/`id_rsa` 的非系统用户 > 当前用户」；`infer-load` 与 `infer-unload` 同源；远端 ssh 失败时保留并打印 stderr（照 §8.2 的「报清单而不是只报结论」）。

**真站验证**：正向 `sudo infer-unload __o181_probe__` ⇒ `通道用户=scott-lau`、A/C 均执行且无失败告警；负向 `RPC_USER=__no_such_user__` ⇒ 直出 `原始错误: sudo: 未知用户 __no_such_user__`。

**部署纪律（同一坑第 2 次）**：`nodes.env` 由工作区（CRLF）直接 scp ⇒ `source` 报 `$'\r'`，且仓库模板只声明 A 节点，一度覆盖站上双节点 —— 已恢复并同步仓库真值。⇒ 凡部署到站的 `.sh` / `.env`，先 `file` 或 `tr -d '\r'` 核对行尾。
