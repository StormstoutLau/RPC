## 1. 背景与目标

V4-Flash-0731（146G MXFP4）是三站分布式推理的**首个真实负载验证目标**——它必须分布式（单机 124G < 146G），且是引擎归位 `/opt` v0.3.0（含 lightning indexer + transpose + `-sm tensor`）后的首次大模型实测，目的：对比 9/1 双机 RPC 基线（tg ~6.3 t/s）的加速幅度。

执行过程中 B 站**两次 kernel panic 强制重启**。本文档记录完整过程与定案根因。

## 4. 根因分析

### 4.1 直接根因：UMA 架构下 `-ngl 99` 全 offload 146G 权重超池上限

```
llama-cli/llama-server 加载 146G 单文件
      ↓
--load-mode 默认 mmap（按需分页，物理内存不爆——mmap 本身无害）
      ↓
-ngl 99 = 把 1328 个 tensor 全部 offload 到 Vulkan0（GPU）
      ↓
Strix Halo UMA：GPU "显存" = 同一块系统内存池（gttsize=120000 → ~120G）
      ↓
Vulkan 要为全部 146G 权重分配 buffer → 超 120G 池上限
      ↓
Vulkan 分配失败 → 驱动层内存压力 → 内核 OOM/panic → 整机强制重启
```

**146G > 120G（UMA 池上限）** 是最底层算术：任何分片配置下，若 head（B）被要求 `-ngl 99` 全量持有或 mmap 全量 + offload 全量，都会超限。**四次崩溃（三站分片 / `-c 512` 最小 / `-fit on` / `-dio` 分片）全部在加载阶段 panic**，与后续推理无关。

### 4.1b 归因修正：根因 = 单机/本机持有 146G 超限（2026-09-08 用户反例确认）

> **⚠️ 原结论「Vulkan 后端不可行」错误**——由本集群 9/1 成功记录推翻（用户指出）。正确归因如下。

**9/1 成功记录（本集群自证，比外部案例优先）**：

| 模型 | 部署形态 | 引擎 | 结果 |
|---|---|---|---|
| MiniMax-M2.7 Q4_K_S **121G** | **双机 RPC 层分布** | `/opt/llama.cpp-9859`（4fc4ec554, 7/2, RPC v4.0.1） | ✅ tg 19.7 t/s |
| deepseek-v4-flash **145G Q4** | **双机 RPC 层分布** | `/opt/llama.cpp-9859`（同） | ✅ tg ~6.3 t/s |

**引擎版本三方交叉验证（2026-09-08 补充）**：

| 来源 | 记录 |
|---|---|
| 文档 [分布式推理.md L562](file:///d:/RPC/docs/分布式推理.md) | 「llama.cpp 版本: version 9859 (commit 4fc4ec554)，RPC 协议 v4.0.1，2026-07-02 构建」 |

| 用户记忆 | 「/opt 老版本 = 最早版本」 |

**9859 = /opt 最早构建**（7/2）→ v0.2.0（8/28）→ master-d2e206c4（8/31）= 时间线完整。
**⚠️ 现役陷阱**：`/opt/llama.cpp` symlink **当前指向 master-d2e206c4（v0.3.0）而非 9859**——若复现 9/1 时仍走文档 L273/L330 的 symlink 路径，实跑引擎是 master 不是 9859。

**4 次崩溃的共同错误（与成功记录对照）**：

| 尝试 | 形态 | 本机持有量 |
|---|---|---|
| `-sm tensor -ngl 99` | head B 全量持有 + `-ngl 99` | **146G**（超限） |
| `-c 512 -ngl 99` | 单机加载 | **146G**（超限） |
| `-c 512 -fit on` | 单机加载 | **146G**（超限） |
| `-dio` + 分片 | 单机加载 | **146G**（超限） |

**正确根因**：4 次全部是「**单机/本机试图持有 146G > 124G**」——算术必崩，**与 Vulkan 无关、与引擎版本无关**。9/1 成功 = **双机 RPC 层分布，每机仅持 ~73G** << 120G → 不超限。

**两个并存差异（此前混淆）**：
1. **部署形态**：9/1=双机层分布（每机 ~73G）；4 次崩溃=单机/本机全量（146G）→ **这是崩溃的决定性变量**
2. **模型档位**：9/1=Q4 145G（9859 支持）；崩溃尝试=MXFP4 146G → 引擎对 MXFP4 的加载路径差异是**次要因素**（需在正确形态下再验证）

### 4.2 为什么 mmap 不是根因（排除）

| 假设 | 判定 | 依据 |
|---|---|---|
| mmap 导致内存爆 | ❌ 排除 | mmap 按需分页，物理内存只装访问页；146G 文件 mmap 不占 146G 物理内存 |
| 上下文/KV 导致 | ❌ 排除 | `-c 512` 极小仍崩溃 → 与 ctx 无关 |
| RPC 分发导致 | ❌ 排除 | A/C worker 零连接、零推送；B 在本地加载阶段就崩 |
| **MXFP4 格式不被引擎支持** | ✅ **排除（2026-09-08 实证）** | `/opt` v0.3.0 二进制含完整 MXFP4 支持：`libggml-base`（dequantize_row_mxfp4/quantize_mxfp4）、**`libggml-vulkan`（arr_dmmv_mxfp4_* 反量化内核）**、`libggml-cpu`（gemm/gemv_mxfp4）；上游 2026-05 官方公告 gpt-oss 原生 MXFP4 全后端支持——**V4-Flash-0731-MXFP4 的格式完全受支持，非崩溃诱因** |
| **缺 `-dio`** | ✅ **排除（第 4 次崩溃）** | 社区 #19745 workaround 针对 **ROCm/HIP 后端**；本集群 **Vulkan 后端**加 `-dio` 仍崩 |
| **`-fit on` 能规避** | ✅ **排除（第 3 次崩溃）** | 引擎自适应设备内存仍试图装入 146G |
| **UMA 池超限（Vulkan 后端）** | ✅ **主因** | 146G > 120G 池上限 + Vulkan 后端 UMA 分配缺陷（beowulf 实证），四次崩溃全部复现 |

### 4.3 叠加因素

1. **单文件 vs 9/1 分片**：9/1 成功的分片模型可让各站 `-ot` 只持部分层；单文件 146G 无法按站切分，B 必须全量面对
2. **无加载期监控**：未在 A/C/B 侧起 `free`/`vmstat` 轮询，崩溃前兆（free 异常/SSH 超时）无法早期识别
3. **无渐进验证阶梯**：直接从"单机最小加载→双机→三机"跳到最后生产形态（三站全参数），跳过了 `-c 512` 单机先验证格式可 load 的步骤（第二次崩溃正是补做该步骤时发生）

## 7c. FAQ：单文件 vs 分片（2026-09-08 追加）

> 用户提问：「单文件是否也是崩溃原因」「单文件存在意义」「单文件是否提高吞吐」。结论先行：**单文件不是根因（崩溃④用分片仍崩）；单文件对吞吐≈零影响**。

### 7c.1 单文件不是根因——四证据

| 尝试 | 文件形态 | 部署形态 | 结果 |
|---|---|---|---|
| 崩溃① | 单文件 146G | 三站 `-sm tensor` + `-ngl 99` | panic |
| 崩溃② | 单文件 146G | 单机 `-c 512` + `-ngl 99` | panic |
| 崩溃③ | 单文件 146G | 单机 `-fit on` | panic |
| 崩溃④ | **分片 4×45G** + `-dio` | 单机 | **仍 panic** |
| ✅ 成功 | 分片 4×45G | 三站 `-sm layer`，无 `-ngl 99` | 跑通 7.9 t/s |

崩溃④已拆片 + `-dio` + `-fit on` 仍崩 → 决定性变量是**「单机/本机全量持有 146G > 124G UMA 池」**，与文件形态无关。

### 7c.2 单文件存在意义

单文件是**「权威源」而非部署形态**：分发/归档/md5 一致校验简单；兼容需直接 `-m 单路径` 的工具；单机内存充足时最简形态；元数据读取（`llama-gguf r`）一次到位。分片只是派生部署形态。

### 7c.3 单文件加载不会提高吞吐

分片只影响 **I/O 层**（磁盘读取），不影响**计算层**（张量计算）。multi-file 加载按 tensor 顺序拼接，mmap 语义与单文件一致；RPC 层分布时 head 逐 tensor 读出推送，片边界与张量边界对齐与否对总耗时可忽略。

**吞吐决定因素 = 算子与融合，不是文件形态**：

| 因素 | 状态 | 影响 |
|---|---|---|
| lightning indexer / transpose 算子 | ✅ master 已含 | 本次 6.3→7.9 t/s (+26%) 主因 |
| #26578 HC 融合（decode 1.5× / prefill 1.12×） | ⚠️ 未合入 | decode 上限瓶颈（当前 unfused Sinkhorn 慢路径） |
| 层分布策略 `-sm layer` | ✅ 已用 | vs 崩溃形态 `-ngl 99` 全量持有 |
| 后端路线 | ROCm 社区 32t/s 对照 | 架构级差异，见 survey |
| **文件形态单/分片** | — | **≈零影响** |

## 3. 归因分析

### 3.1 无 rpccache：A/C worker 未带 `--cache` 启动

依据（`tmp/rpccache_analysis.sh` / `rpccache_deep.sh`）：

| 检查项 | 结果 |
|---|---|
| master rpc-server 是否支持 cache | `/opt/llama.cpp/ggml-rpc-server -h` 含 cache 选项（v6.0.0） |
| 9859 rpc-server 是否支持 cache | 需比对（`rpccache_deep.sh` §2，待回填） |
| A/C worker 当前进程启动参数 | **未带 `-c/--cache`**（`ps aux` 待回填） |
| 缓存目录 `~/.cache/llama.cpp/rpc/` | 待回填（`rpccache_analysis.sh` §3） |

**结论方向**：llama.cpp 的 RPC 权重缓存在 **worker 侧**——`ggml-rpc-server` 需带 `--cache` 启动才会把收到的权重落盘复用。本次 A/C worker 按旧命令（无 `--cache`）启动 → 每次加载全量推权重，表现为"无 rpccache"。

### 3.2 走 WiFi：环网 ARP 异常 → 10.10 段物理不通

依据（`tmp/rpccache_analysis.sh` §1/§4）：

| 检查项 | 结果 |
|---|---|
| B 环网接口（thunderbolt0/1）ARP 记录 | **A/C 的 10.10.x IP 出现在错误接口 / STALE / FAILED**（跨接口漂移） |
| `ping 10.10.10.1`（A） | **100% 丢包**（此前实测） |
| `ping 10.10.11.3`（C） | **100% 丢包**（此前实测） |
| WiFi 段 ping | 通（因此回退走 WiFi） |

**物理连线已由用户确认未变动**（A↔B、B↔C 环网线仍插在原有口）。故 ARP 异常不是"拔线/换口"导致，方向指向：

1. **接口枚举漂移**：重启后 thunderbolt 网卡接口编号/链路层地址（thunderbolt0/1）与旧配置错位，静态 IP 仍配在旧接口上；
2. **历史 ARP 残留**：ARP 表跨接口残留（A 的 10.10.10.1 被记录在 thunderbolt1，实际在 thunderbolt0），路由/邻居表错乱未刷新；
3. **链路层协议未协商**：雷电/USB4 链路协商失败但物理线正常（对端接口名/驱动加载顺序变化）。

## 5. 环网根治：按 MAC 绑定（2026-09-08 已执行）

### 5.1 根因确认（接口枚举漂移，非物理接线）

用户明确环网物理连线未变动。排查发现 B 站 thunderbolt-net **接口枚举漂移**：thunderbolt0/1 接口名与物理口错位，而 netplan 按接口名（`match: name:` / 危险的 `match: {}`）绑定 IP → A 段 IP 落在连 C 的口、C 段 IP 落在连 A 的口 → 10.10.x 全盲。A-C 直连段（10.10.12.x）此前因 A 站 thunderbolt1 开关未自动开启（用户手动开启）而 down。

### 5.2 物理口锚定（ARP 交叉验证 + 临时 IP 实验）

| 物理口（MAC 锚定） | 对端 | 正确网段 | 证据 |
|---|---|---|---|
| B `02:66:bd:12:dc:35`（现名 thunderbolt1） | A thb0 | 10.10.10.2/24 | 临时加地址 ping A 10.10.10.1 ✅ 0.13ms |
| B `02:00:d2:46:c4:6b`（现名 thunderbolt0） | C thb0 | 10.10.11.1/24 | 临时加地址 ping C 10.10.11.3 ✅ 0.13ms |

MAC 稳定性由历史文档印证：9/1 记录 `10.10.10.2 ⇔ MAC 02:66:bd:12:dc:35`（A站挂死根因分析 L137）与本次一致。

### 5.3 修改内容（B 站 /etc/netplan）

| yaml | 修改前 | 修改后 |
|---|---|---|
| `90-NM-27fcd87a…yaml`（netplan-thunderbolt0） | `match: {}` + 段 id `thunderbolt0` | `match: {macaddress: "02:66:BD:12:DC:35"}` + 段 id `ring-a`（消除 interface-name 约束） |
| `90-NM-73aad587…yaml`（有线连接 4） | `match: {name: "thunderbolt1"}` | `match: {macaddress: "02:00:d2:46:c4:6b"}` |
| 幽灵连接「有线连接 2」（0b59bfcb） | match name thunderbolt0、无地址 | **已删除**（sudo nmcli con delete） |

执行要点：netplan 段 id 若保留 `thunderbolt0` 会被 netplan5 反向导出为 `interface-name` 约束再次失效，故段 id 必须改为非接口名（`ring-a`）。

| 接口名重启后是否漂移 | **是——thunderbolt0/1 名与 MAC 互换**（thunderbolt0 变 02:66:bd:12:dc:35、thunderbolt1 变 02:00:d2:46:c4:6b） |
| IP 是否跟随 MAC 而非接口名 | ✅ 10.10.10.2→thunderbolt0(MAC 02:66=A口)、10.10.11.1→thunderbolt1(MAC 02:00=C口) |
| B→A 环网 | ✅ 0% loss, 0.151ms avg |
| B→C 环网 | ✅ 0% loss, 0.635ms avg |
| 邻居表归属 | ✅ A(10.10.10.1) dev thunderbolt0、C(10.10.11.3) dev thunderbolt1（与接口名一致） |

**结论**：MAC 绑定根治方案经重启验证有效——接口名每次重启都漂移（本次实测互换），但 IP 正确归属物理口，环网稳定连通。**若无 MAC 绑定，重启后环网将再次全盲**。

## 0. ★★ V4 vs V4.1 的关键差异（E3，决定一切）

| 维度 | V4-Flash-0731（现役） | **V4.1-Flash** | 影响 |
|---|---|---|---|
| 总参数 | **284B**（MoE） | **552B**（本轮新架） | **体量翻倍** |
| 激活参数 | ~13B/token | **prefill 8B / decode 16B**（非对称） | ★ 吞吐优势在"读轻" |
| 架构 | 对称 decoder-only，混合注意力（CSA+HCA） | **Causal-Encoder-Decoder（CED，20 enc + 20 dec）+ 1 shared + 384 routed 专家** | ★ **全新架构**，等于又一个"glm5next"级别的新架构 |
| KV Cache | — | **~890 B/token（FP4 为主，E2M1）** ⇒ **1M ctx 仅 ~0.9 GB**，为前代 1/4 | ★ **长上下文内存压力大降** |
| 上下文 | 256k | **1M** | — |
| 原生多模态 | Vision-Exp 分离 | **内置（DeepSeek-ViT，763B 含视觉）** | 权重含视觉编码器需另算 |
| llama.cpp 支持 | ★ 已闭环（算子链全合） | ★ **仅 convert 入口推进中（#28696 转非 draft）**，**编码/架构算子未合** | ★ **现役引擎跑不了 V4.1** |
| 发布 | 2026-03/07 系列 | **2026-09-10**（距今 18 天） | 极早期 |

**一句话**：V4.1 是"**新架构 + 大一倍 + KV 减 3/4**"。长上下文友好是巨大利好，但**体量翻倍 + llama.cpp 未支持**是两条硬墙。

## 1. 可行性算术（E1 口径估算，非实测）

以 552B 总参数计 GGUF 体积（粗略，~0.5 B/param@Q4 / ~0.26 B@Q2）：
- **Q4 级 ≈ 280 GB**（552 × 0.5）—— **远超 A/B/C 任一单机 128 GiB**；
- **Q2 级 ≈ 145 GB** —— 仍**超单机** 128 GiB，但**可贴合双机**（现役 V4 正是 145G 双机口径）；
- 含视觉编码器（DepthSeek-ViT 将 763B）需再加。

**分布式含义**：
- 现役 V4 层分布在 **A+B**（145G → 各 ~72G）；V4.1 Q2（145G）同样 **A+B 双机**可装，但**仅 Q2且无余量**；
- **Q4（280G）需 3 机**（各 ~93G）才勉强 —— 与现状"恢复坡后释放站"的思路冲突。

★★ **对照我们真正的瓶颈**：`O-18` / `O-110` 已证，Strix Halo 上 decode 是 **UMA 带宽受限** ⇒ **对 V4.1 而言，激活只有 16B（decode）/ 8B（prefill），每 token 要搬的"激活权重"远小于 552B 总量** —— 但 **KV 压缩到 1/4** 意味着**长上下文我们一直差的"长 ctx"维度反而被解决**。★ 这正是 V4.1 相对 V4 对本集群真正的增益点：**不是"装下"，而是"长上下文可行"**。

## 2. 三条部署路径对比（含 REAP 剪枝）

### 路径 A：REAP 剪枝至 150–200B（承 O-112）
- **REAP 已查实**（`O-112`）：router-weighted expert activation pruning，一次性免微调，50% 压缩下 code 面近无损（E3，arXiv 2510.13999）。
- ★★ **对 V4.1 的适配是未知的**：REAP 论文验证的是**对称 SMoE**（V4 属此类）；**V4.1 是 CED 非对称 + 1shared+384-routed** ⇒ ★ **剪枝准则（gate×activation norm）作用于 enc/dec 两块、routed/shared 两类专家时如何取舍，无现成验证**。这是**比 V4 更大的一层风险**。
- 剪到 **200B ≈ Q4 ~100G** → **单机可装**（符合用户"单机"目标）；但剪到 **150B ≈ Q4 ~75G**（更安全）。
- 代价（同 O-112）：校准算力（16,384×12,228 ≈ 2×10⁸ tokens 前向）、不可逆、自维护线（**当前引擎连 V4.1 都还不支持 ⇒ 剪枝后更无参考**）、上游不支持。
- ★ **判断：对 V4.1，REAP 比 V4 更不成熟** —— 架构不匹配的风险压过收益。

### 路径 B：分布式推理（llama.cpp 路线，承现役栈）
- 前置：**llama.cpp 需先支持 V4.1 架构**（CED + 新注意力 + 视觉）。现状仅 `#28696`（convert）转非 draft ⇒ **推理算子未合** ⇒ ★ **现役栈当前不能跑 V4.1**。
- 一旦上游合入：Q2 双机 / Q4 三机层分布（`-sm layer`）可直接复用现役 `RPC_MODELS` 编排。
- ★ 与 V4 的差异：V4.1 的 **CED encode/decode 非对称** 可能使 `-sm layer` 切分更复杂（两侧层数 20/20 对称，但激活不对称）。
- 收益：**零新引擎、零新管理面**（符合 ADR-0004）；代价：**等上游**（如同 GLM，可能数月）。

### 路径 C：换引擎（vLLM / ds4 / MLX，承 tracker §1.7 别家栈）
- **vLLM**：官方自述 **2,000 GPU + 存储集群**才做生产自托管（E3）⇒ 与三机 Strix Halo 差 2 个量级；ROCm 侧是否有 gfx1151/V4.1 未证。★ **对本集群而言 inflection 点不现实**。
- **ds4（Dwarf Star 4，antirez 专为 DeepSeek V4 架构做的引擎，AMD 官方 Playbook 已有 Strix Halo + Rocm 教程）**：★ 这是**新线索**，需单列（§3）。它对 V4.1 的支持状态**未核**。
- **MLX**（社区版，Apple Silicon）：与三机 x86 集群无关；但 V4.1 激活稀疏 + 8B/16B 激活 ⇒ **SSD 流式理论上可行**（有 16GB M1 实验跑通 V4.1 的报道，22.8 s/token，属"能跑但不可用"级）⇒ 证明**稀疏流式思路**。
- 收益：绕开 llama.cpp 上游；代价：**新增管理面（撞 ADR-0004 D1/D3）+ EV-4**。

### 7.1 仓库真相：**4 个"档"是玩具，只有 `compressed` 是真货**

### 7.2 ★ 目标架构 = `deepseek41`，**两引擎均不支持**

`compressed-00001-of-00007.gguf` 头实测：

- 该 arch 的 **KV 量级未测**（层结构/KV 参数未全展开；索引器 `top_k=512` ⇒ 稀疏）

### 7.4 顺带发现（改变结论）

README 自述 **`compressed` 保真高于 `balance`**（97.61–99.99% vs 86.32–97.41%）**且小 60 GB** ⇒ **`balance` 未上传并不构成缺口**，`compressed` 本就是更优目标。

### 7.5 方法论副产物：**HTTP Range 读 GGUF 头**

本次对 246 GB 的档只花了几十 KB 就拿到了架构/规模 ⇒ **"支持性判定"不必先下载**。可复用的判据顺序：

```
HEAD 取体积（识破玩具档）→ Range 取前 64 KB 解析 GGUF 头（取 arch/block_count）→ 引擎 strings 精确匹配 arch
```

—— 三次探测（均为秒级/分钟级）即可回答「**这模型我们能不能跑**」，**成本与模型体积无关**。
⚠ 两个已知坑：① `HEAD` 要跟重定向（`curl -L`），否则拿到的是 302 响应体；② 架构匹配必须**整行精确**（见 §7.2 的 `grep -c` 假阳性）。

### 7.6 待办

① 跟踪上游 `deepseek41` 架构支持（进 [upstream-tracker](../../spec/upstream-tracker/TRACKER.md)；届时用 `--engine` **零影响现役**接入）；② 是否预下 246 GB（磁盘可行）**取决于上游时间**；③ 支持后再测其 KV/上下文。

# 第四部 · V4-Flash-0731（现役）· 统一管理入口整合与性能归因

> **来源**：2026-09-29 会话 · **承接** §0 的「V4-Flash 目前**只能走 `/opt` 手工两机形态**」这一判断（该判断**已在本次更正**）

> **证据**：E1 = 本集群实测（含**站上引擎源码**核对）· **状态**：**已闭环**

## 1. 结论速览

| 问题 | 上一轮判断 | 本次结论 |
|---|---|---|
| 统一入口能跑 V4-Flash 双机吗 | ✅ 能（`_load_rpc` 的 backend 漏传已修） | ✅ **能，且性能与手工形态持平** |
| −22% 缺口（10.90 vs 14.06）在哪 | worker 单元缺 `--device Vulkan0` + head 硬编码 `-ngl 999` | ❌ **两条都不是**；真因 = `infer-load` 对 `llama-rpc` **强制 `N_CPU_MOE=8`** |
| worker 缺 `--device Vulkan0` | 疑为性能因素（"CPU 也被暴露给 head"） | ❌ **纯 no-op**（站上源码显式排除 CPU，见 §2） |
| head 硬编码 `-ngl 999` | 疑为性能因素 | ◐ **行为等价**（本引擎 `-ngl` 默认即 `auto`）；仍移除（对齐 9/8 事故口径） |
| 现状 | —— | **`cluster.py load deepseek-v4-flash-0731-b` ⇒ decode 14.06 t/s** |

## 2. 证伪一：worker 缺 `--device Vulkan0` **不是**原因（读源码定案）

上一轮把差异归到「worker 单元的 `ExecStart` 缺 `--device Vulkan0`」，机制假设是
"不限定设备 ⇒ worker 把 **CPU 设备也注册** ⇒ head 的层切分把部分层分到 worker 的 CPU"。

**读站上引擎源码**直接否掉这条 —— `~/src/llama.cpp-master-91f6a6cf/tools/rpc/rpc-server.cpp` 的 `get_devices()`：

```cpp
    // Try non-CPU devices first
    if (devices.empty()) {
        for (size_t i = 0; i < ggml_backend_dev_count(); i++) {
            ggml_backend_dev_t dev = ggml_backend_dev_get(i);
            if (ggml_backend_dev_type(dev) != GGML_BACKEND_DEVICE_TYPE_CPU) {
                devices.push_back(dev);            // ← 只注册**非 CPU** 设备
            }
        }
    }
    // If there are no accelerators, fallback to CPU device
    if (devices.empty()) { ... }
```

⇒ 不给 `-d` 时它**本来就只注册非 CPU 设备**（本机只有 `Vulkan0`），**有加速器就绝不回退 CPU**。
∴ `-d Vulkan0` 在这里是**逐字节等价**的 no-op —— 加与不加都一样。

★ **方法论（比结论值钱）**：这条差一点变成一次「改三站 → 跑一次 → 性能没变 → 再推翻」的弯路
（每次加载 5–9 分钟，且要复现手工形态对照）。**引擎源码就在站上** ⇒
「**先读实现，再改配置**」比「单变量剥离」便宜一个数量级。上一轮的 −22% 归因正是**跳过读源码**
直接靠"参数差异表"推的，于是把一条 no-op 当成了嫌疑。

## 3. 真因：`infer-load` 对 `llama-rpc` **强制 `N_CPU_MOE=8`**

[infer-load](file:///d:/RPC/ops/station-bin/infer-load) 生成 conf 时对 `llama-rpc` 写死 `NCM=8`：

```bash
NCM=0; [ "$BACKEND" = "llama-rpc" ] && NCM=8      # 原实现
```

`--n-cpu-moe N` 的语义 = **把前 N 层的 MoE 专家张量放在 CPU 上算**。
它是**单机**省显存的手段（124 GiB 单站塞 120B 级模型时的腾挪）；但在**双机 RPC** 形态下，
它把前 8 层专家压到 **head 的 CPU** 上算 —— 这部分算力**参与每个 token 的 FFN** ⇒ decode 直接掉 22%。

对照**手工成功形态**（第一部 §7b / `.trae/documents/26578-DSV4-HC融合算子A-B实测计划.md`）：
它的 head 命令里**根本没有 `--n-cpu-moe`**（= 0，引擎缺省）⇒ 这正是 14.06 vs 10.90 的**全部**差额。

**改动**：① [infer-load](file:///d:/RPC/ops/station-bin/infer-load) 的 `NCM` 缺省改 **0**；
② B 站既有 conf 的 `N_CPU_MOE=8` → `0`（该 conf 是 2026-08-30 由**旧规则自动生成**的，属
"按新规则重生成"，非手工调参；备份 `…env.bak-ncm8-20260929`）。

## 4. `-ngl 999` 的处置（与性能无关，但仍要改）

实测 `/opt/llama.cpp/llama-server --help` 原文：`-ngl, --gpu-layers N … (default: auto)`
⇒ **不传参**时引擎按可用设备内存自行放层，与显式 `999` 在本集群**行为等价**（都把放得下的层全放上设备）。
但 `-ngl 999` 恰是第一部 §4.1 那次 9/8 kernel panic 事故里**被点名**的形态 ⇒
[llama-serve-instance](file:///d:/RPC/ops/station-bin/llama-serve-instance) 改为**缺省不传**（回归引擎 `auto`），
需要钉死时在实例 conf 写 `N_GPU_LAYERS=<N>`。
