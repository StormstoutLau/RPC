# 多站接入 IM 桥接：实例隔离问题与备选方案调研

- **日期**: 2026-11-02
- **授权**: 用户 2026-11-02「分析其他备选方案 是否有其他 IM 工具可选 / 飞书长连接对同一个 app 的多条连接没有实例隔离 这个问题调研一下 然后落档」
- **性质**: **只读调研 + 落档**。★ 未改任何站上配置 / 代码 / ADR；A 站**未安装** cc-connect
- **证据级别**: **E1** = 本机/站上只读实测 · **E2** = 外部官方文档 · **E3** = 第三方页面（仅作旁证，不单独采信）
- **射程**: 只回答「同一 IM 应用能否被多站共用」「有哪些备选」「对本仓 A/B 两站意味着什么」；**不**回答「A 站该不该接」「halogen 性能」

---

## 0. 结论前置（五句）

1. ★★ **用户判断被飞书官方原文证实**：长连接事件推送是**集群模式、不支持广播** —— 同一应用部署多个客户端（client）时，**只有随机一个**会收到消息；官方 FAQ 进一步写明「实例随机选择，无环境/机房归属区分，所有权重相同」（E2）。
2. ★★ **「换 IM」本身不解决多实例**：Telegram 同一 bot token 只允许**一个** `getUpdates` 消费者（多实例 ⇒ 409，互相抢队列、回复隔条丢）；Slack Socket Mode 最多 10 条连接、payload **随机投递**且**无重投**；Discord 同一 token 只允许**一个** Gateway 会话。这三家比飞书更严，不是更松。
3. ★★ **可行解只有三类**：(a) **每站独立应用/bot**；(b) **单桥接 + 站间路由**（只让一台持有长连接，另一台作被调方）；(c) **广播型协议**（Matrix 每设备独立 sync）。**不存在「一个 bot 两条连接自动分流」这种选项** —— 这是 IM bot 模型的共性，不是飞书的缺陷。
4. ★★ **cc-connect v1.5.0 不支持 Matrix**：本机 `cc-connect --help` 的平台清单是 `Feishu / TuiTui / Telegram / Slack / DingTalk / Discord / LINE / WeChat Work / Weixin / QQ / QQ Bot`（E1）⇒ 走 (c) 必须换客户端或自研。第三方页面称支持 Matrix，**不采信**。
5. ★★ **对本仓**：(a) 与 (b) 都可行，但各有硬成本 —— (a) 需新建飞书应用且 **open_id 是 app 级**的（换 app 必须重新获取 `allow_from`）；(b) 不新增第二条长连接、最符合 ADR-0004，但**转发逻辑要自研**（cc-connect 无远端路由能力）。

## 1. 飞书长连接的官方事实

| 项 | 官方口径 | 对本仓的含义 |
|---|---|---|
| 连接上限 | 每个应用最多 **50** 条连接（每初始化一个 client = 一条） | 两台远未触顶 ⇒ **不是容量问题** |
| 事件分发 | **集群模式、不支持广播**；多个 client 时**只有随机一个**收到 | 两站共享同一 app ⇒ 消息随机落 A 或 B |
| 实例选择 | 官方 FAQ：**随机选择**，无环境/机房归属区分，**所有 client 权重相同**；「A 环境机器人发的消息，回调节点也可能分配至 B 环境」 | 无任何「就近/粘性」可依赖 |
| 处理时限 | 收到后须 **3 秒内**处理完且不抛异常，否则触发**超时重推** | 3 秒对 agent 任务远远不够 ⇒ 重推可能与首次落到不同实例，进一步放大不确定性 |
| 应用类型 | 长连接**仅支持企业自建应用** | 与 ADR-0015 的「自建应用 + QR onboarding」路径一致 |
| 卡片回传交互（旧） | **不支持**长连接接收，只能走「发送至开发者服务器」 | `card.action.trigger` 的验证仍依赖公网回调，见 ADR-0015 §6 |

★ 结论：**同一飞书应用无法被 A/B 两站共用而不互相扰动**。这不是配置问题，是推送模型的语义。

## 2. 主流 IM 的「同一应用多实例」模型对照

| 平台 | 连接形态 | 多实例行为 | 是否可两站共用 | 证据等级 |
|---|---|---|---|---|
| **飞书 / Lark** | WebSocket 长连接 | 集群消费；随机一个 client 收到，不广播 | ✗ | E2 官方 |
| **钉钉 Stream** | WebSocket 长连接 | 每实例一条连接、应用最多 50 条；官方 FAQ 称「可启动多个监听服务」，**但未明示事件分发策略** | 未定（需实测） | E2 官方，分发未述 |
| **Telegram Bot** | Long Polling / Webhook | 同 token **仅允许一个** `getUpdates` 消费者；第二个实例报 `409 Conflict: terminated by other getUpdates request`，两者互相抢队列 | ✗（比飞书更严） | E2 官方错误码 + E3 多例 |
| **Slack Socket Mode** | WebSocket | 最多 **10** 条连接；payload **可能发到任意一条**，不保证模式；**不是负载均衡也不是队列**，落到重启/卡住实例的 payload 直接丢（无重投） | ✗（官方与第三方分析一致） | E2 官方 + E3 分析 |
| **Discord Gateway** | WebSocket | 同 token **仅允许一个** Gateway 会话；分片（sharding）按 guild 划分，不是为多站设计 | ✗ | E3 库文档 |
| **企业微信 / WeCom** | 回调 URL（Webhook） | 单点回调地址；cc-connect 的 WeCom 模式需公网 URL | ✗（且需公网面） | E3，未核 cc-connect 实现 |
| **Matrix** | 每个设备独立 `sync` | 房间消息**广播给所有成员**，多客户端各自收到 | ✓（但需 homeserver） | E3，**cc-connect 不支持** |

★ 三条推论：

1. **「单 app 多实例」在飞书/Telegram/Slack/Discord 全部不成立**，且后三者比飞书更严格（直接互斥，而非随机）。
2. **钉钉的分发策略官方未写死**，属于「可能可行但未证」；即便可行，也要承担一次实测与长期不确定性。
3. **只有广播型协议（Matrix）天然支持「一个房间、多个 agent」**，但本仓现役客户端不支持，且自建 homeserver 会新增常驻面（与 ADR-0004 冲突）。

## 3. 三类可行解对比

| 方案 | 内容 | 优点 | 成本 / 风险 | 与 ADR 的关系 |
|---|---|---|---|---|
| **(a) 每站独立应用** | A 站新建飞书自建应用（`cc-connect feishu new` 扫码），与 B 站互不共享 app | 语义最干净；两站互不扰动；故障隔离 | 需一次扫码；**open_id 随 app 变化** ⇒ `allow_from` 必须重新获取；ADR-0015 需把「唯一常驻例外」扩展为「两台实例」并写明 | 需改 ADR（例外数量从 1 → 2） |
| **(b) 单桥接 + 站间路由** | 只有 B 站持有长连接；B 收到消息后按前缀（如 `/a`）经 USB4 转发到 A 站执行，结果回传 | **不新增第二条长连接**；不新增飞书应用；A 站无需扫码；符合「仅出站」 | **转发逻辑要自研**（cc-connect 无远端路由）；B 站成单点；需定义前缀协议、幂等与失败回传 | 最符合 ADR-0004；ADR-0015 不变 |
| **(c) 换到广播型协议** | 改用 Matrix 等「多设备各自收」的协议，A/B 各一个 bot 用户加入同一房间，按 @提及 路由 | 一个房间容纳多 agent，语义最自然 | cc-connect **不支持**（E1）；需换客户端或自研；需 homeserver（自建则新增常驻面） | 与 ADR-0004 冲突（新增服务） |
| **复用 B 站 app** | 复制 B 站 app_id/secret 到 A | 零扫码 | **两站长连接抢同一事件流**，消息随机落点；B 站现有桥接不稳定 | ✗ 否决 |

## 4. 对本仓的建议（分阶段，不立即执行）

1. **短期最省 = (b)**：A 站不装 cc-connect，由 B 站桥接按前缀转发。零新增凭证面、零扫码，且不破坏 ADR-0015 的单实例例外。代价是自研一条转发协议（属于新的 spec 工作，不在本轮）。
2. **中期最干净 = (a)**：A 站新建独立应用。需接受「一次扫码 + 重新获取 open_id + ADR 记两台实例」。
3. **(c) 只在未来考虑**：若 cc-connect 增加 Matrix 支持，或本仓另起桥接实现，才谈广播型。
4. **明确不做**：复用 B 站 app（否决）；把钉钉当作既成方案（分发策略未明示，必须先实测）。

★ 三条与方案无关的硬约束（无论选哪条）：

- **open_id 是 app 级标识** —— 换应用必须重新取，不能把 B 站的 `ou_17cc…` 直接抄到 A 站的新 app；
- **`work_dir` 硬边界**必须逐站单独设，不得指向仓库生产目录；
- **`allowed_tools` 与 `permission_mode`** 必须逐站显式写死（B 站的经验：默认值 = 无 `permissions`，容易被误读成「只读」）。
