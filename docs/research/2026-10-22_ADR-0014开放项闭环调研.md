## 2. 逐项分析

### 2.1 #2 digest pin（建议实施，另批）

**为什么值得做**：tag 是可变的（上游可把 `0.18.11` 重推成不同 digest）；本集群三站已在跑同一 digest，但**真值只存在于"三台机器各自的 image store"**，仓库侧无法判"下次 `containers pull` 会拉到什么"。按 digest pin 后，`CONTAINER_MODELS` 自身就能回答"应该跑哪个制品"。

**候选**：

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **甲（推荐）** | `CONTAINER_MODELS.image` 用 `repo:0.18.11@sha256:a579…`（tag + digest 并存） | 一处改动；`docker pull/run` 原生支持（E3-1）；tag 仍可读。**风险**：`containers status` 显示的 image ref 变长（展示层，可截断） |
| 乙 | 新建 `inventory/containers.yaml` 存 digest，`CONTAINER_MODELS` 引用它 | 引入第二份真值/第二解析器 —— 与仓内「单一真值」纪律冲突；收益仅是"非代码文件" |
| 丙 | 只加 `containers status` 的 digest 漂移检查，不改引用 | 能**发现**漂移，但**不能阻止**拉到新制品；治标 |

**建议**：甲 + 一条 drift 检查（`containers status` 或 `rpc_check` 新断言：三站 RepoDigests 与 pin 逐字一致）。pin 更新 = 显式改 digest（E3-1 的"代价"条目，须在 ADR 写明）。
**✅ 已实施（2026-10-22）**：pin 落入 `CONTAINER_MODELS.image`；drift 检查落在 `rpc_check --only engine`（先验红：改假 digest ⇒ 三站 FAIL 并点名；恢复后 PASS）；B 站用 pinned ref 重建容器实测通过。

### 2.2 #6 资源竞争（可关闭，射程写明）

实验直接回答 ADR 点名的对象（A 站 `~/searxng`）：**144 MiB / 0% CPU**，对 halogen 的 8k/32k prefill 无可测影响（−3.8% / +0.3%，均在噪声内）。

**射程（如实）**：
- 已测 = **CPU/内存轻载**（Web 搜索栈级别）。
- 未测 = **第二个 GPU 推理引擎**、VLM、或任何抢 GTT 的负载 —— 这类才是真正会打爆 73 GiB 占用的形态。当前三站策略是"**零自加载/单引擎**"，故不在现网风险面；若将来要同站双引擎，须另做容量实验（可复用 `O-110` 的方法）。

### 2.3 #7 组名口径（关闭，登记项过期）

D4 的正文已经写成数字 GID（2026-10-11 回写），而 #7 仍留着"待用户裁定"——这是**同一事实两处表达、其中一处过期**。按仓内纪律「落档发现的实况与原句不符时，须就地更正原句口径」，本次直接关闭 #7，不再让用户重裁一个已经落过的事。

结论口径：**数字 GID 是唯一可用形态**（E1-6 + E3-3）；组名写法保留为"失败历史"，不恢复。

### 2.4 #9 共享权重目录落物（调研完成，待裁定）

**事实**：每站 1.5 G（+22 M +60 K），root 属主；`down` 后仍在。删除后下次 `up` 需重新取件（E1：B/C 首次 **60–90 s**；ADR §V6.1）。磁盘余量 629 G–1.1 T。

**候选**：

| 方案 | 影响 | 评价 |
|---|---|---|
| **甲（推荐）保留** | 复起快 60–90 s；目录含 root 落物 | 磁盘余量 3 个数量级富余；落物是**引擎自己产生的缓存**，不是模型真值 |
| 乙 每次 `down` 后删除 | 恢复"模型目录只读"；每次 `up` 多 60–90 s + 1.5 G 下载 | 只有"目录必须干净"这一收益；下载依赖 HF 镜像可达性（O-148 同类风险） |
| 丙 移到独立 cache 目录 | 两边都干净 + 复起快 | 需要引擎支持可配置 cache 路径 —— **当前无此 env 证据**（E4：未验证），不提议 |

**建议**：甲；在 ADR 里明确"`UD-IQ4_XS/` 不是纯只读目录，含引擎落物（root）"。若用户坚持只读，再走乙。
