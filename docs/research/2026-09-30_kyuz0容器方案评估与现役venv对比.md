# `kyuz0/vllm-therock-gfx1151` 方案评估 —— 本集群可行性 · 与现役 vLLM 栈对比

> **缘起**：Scott 指令「kyuz0/vllm-therock-gfx1151 分析一下这个方案在本集群可行性 对比原生 vllm」（2026-09-30）。
> **证据等级**：**E1**（站上实测：容器运行时 / 现役栈盘点）+ **E3**（上游仓库与 DeepWiki 文档，未复现）。
> ⚠ **本文件不部署任何东西**：未启容器服务、未拉镜像、未改任何站上配置。
> ★ **本文只回答"这条路线在本集群值不值"，不重复 [RCCL 评估](./2026-09-30_RCCL部署方案与集群必要性评估.md) 与 [AMD395 互连调研](../../spec/rpc-optimization/research/AMD395分布式推理高性能互连方案调研.md) 的正文** —— 相关处只建链接。

## 0. 结论摘要

> ★★ **一句话**：**技术上可行（Docker 已装、磁盘充足），但当前不必要 —— 因为它在本集群的"核心增量"（gfx1151 的 RCCL 与 device 补丁）已经由 AMD 官方渠道具备，且本集群已实测可用。**

| 问 | 判定 |
|---|---|
| **技术可行性** | ✅ **具备** —— 三站已装 Docker CLI（A 站 daemon 在跑）；Ubuntu 24.04 在其支持面内（**需 Distrobox**，三站均无）；磁盘充足（773 G / 790 G / 1.1 T 可用） |
| ★ **必要性** | ❌ **不必要** —— 见 §3 的"增量对账"：kyuz0 的**两项核心补丁价值**在本集群**均已失效或不需要** |
| ★★ **最关键的一条** | **kyuz0 的容器与集群现役 venv 不是"两条路线"，而是【同一条路线（TheRock）的两种封装】** —— 见 §2.3 |
| **前置（若仍要做）** | ① **`ADR-0004`**（引入容器栈 = **新实体**，须立项）② 在 **`ADR-0011`** 的 vLLM 框架内（vLLM 路径当前**暂缓**） |
| **RDMA 集群模式** | ❌ **对本集群封闭** —— 需 Intel E810 + PCIe 槽（迷你主机无槽），与 [AMD395 互连调研](../../spec/rpc-optimization/research/AMD395分布式推理高性能互连方案调研.md) §2.3 同结论 |

## 1. 方案是什么（E3，逐项取证）

**仓库**：`kyuz0/amd-strix-halo-vllm-toolboxes`（镜像 `kyuz0/vllm-therock-gfx1151`）。

| 项 | 实测/取证值 |
|---|---|
| **形态** | **OCI 容器**（Docker/Podman），10 阶段 Dockerfile |
| **宿主主支持** | ★ **Fedora 43 + Fedora Toolbox**（镜像基底即 Fedora 43） |
| ★ **Ubuntu 路径** | ⚠ **需 Distrobox**（原文：Ubuntu 原生 toolbox 有 **GPU 访问问题**） |
| **ROCm 来源** | **TheRock ROCm SDK**（`scripts/install_rocm_sdk.sh`，SDK tarball 安装）；构建参数 `ROCM_MAJOR_VER=7` · `GFX=gfx1151` |
| ★★ **RCCL** | ★ **自建补丁版**：`custom_libs/librccl.so.1.gz`，由独立 CI workflow（`.github/workflows/build-rccl.yml`）产出并**替换**镜像内标准 RCCL |
| ★ **vLLM** | ★ **自编译**（**ROCm Clang**）+ **gfx1151 device detection 补丁** |
| 附带修复 | `tcmalloc`（`libtcmalloc_minimal.so.4`）—— 原文：**防 vLLM shutdown 时的 double-free 崩溃** |
| **两种模式** | **单机** TP=1（`start-vllm` TUI）· **RDMA 集群** TP=2（`start-vllm-cluster` TUI + **Ray** + 补丁 RCCL） |
| 附赠资产 | 策展模型表（`scripts/models.py`）+ benchmark 脚本（`find_max_context.py` / `run_vllm_bench.py` / `vllm_cluster_bench.py`） |
| 构建期要求 | 磁盘 **50 GB+**；RAM 16 GB+ |
| 宿主内核参数主张 | `iommu=pt pci=realloc pcie_aspm=off amdgpu.gttsize=126976 ttm.pages_limit=32505856` |

## 2. 本集群现状（E1 实测）

### 2.1 容器运行时与现役栈盘点

| 站 | OS | 内核 | `docker` CLI | **docker daemon** | `~/vllm-rocm` | 磁盘可用 |
|---|---|---|---|---|---|---|
| **A** | Ubuntu 24.04.4 | 6.17.0-40 | ✅ `/usr/local/bin/docker` | ✅ **active · daemon OK** | 8.0 G | 773 G |
| **B** | Ubuntu 24.04.5 | 6.17.0-23 | ✅ 同 | ❌ **inactive** | 8.0 G | 790 G |
| **C** | Ubuntu 24.04.5 | 6.17.0-23 | ✅ 同 | ❌ **inactive · 且无 unit** | 8.0 G | **1.1 T** |

- **Docker 版本**（A 站实测）：`29.8.1`，Storage Driver `overlayfs`，Root Dir `/var/lib/docker`
- ★ **`podman` / `distrobox` / `toolbox` 三站全无** ⇒ 走 kyuz0 的 Ubuntu 路径**必须先补 Distrobox**
- **现役 vLLM 栈**：三站 **逐字一致** `vllm 0.25.2.dev0+rocm7.15.0a20260724.g752a3a504.d20260724` + `torch 2.12.0+rocm7.15.0a20260724`（与 [ADR-0011](../../adr/ADR-0011-A4-vLLM-TP2-暂缓裁定.md) 记录一致）
- **HF 权重缓存**：仅剩 `MiniMax-M2.7-AWQ-G32-STRIX-2H` 的 **48 KB 元数据**（权重已于 ADR-0011 记的时点删净）⇒ **当前没有可供 vLLM 直接服务的本地权重**

### 2.2 ★ 现役 venv 里装的是什么（这条决定了整个对比）

实测 `~/vllm-rocm/lib/python3.14/site-packages/`：

```
amd_torch_device_gfx1151-2.12.0+rocm7.15.0a20260724.dist-info
amd_torch_device_gfx115x-2.12.0+rocm7.15.0a20260724.dist-info
rocm-7.15.0a20260724.dist-info
rocm_bootstrap / rocm_sdk
_rocm_sdk_libraries/lib/  →  libhipblaslt.so.1 · libhipblas.so.3 · libhipdnn_backend.so
                              libhipfft.so.0 · libhipsolver.so.1 · libhipsparselt.so.0
                              … 以及 librccl.so.1
```

⇒ ★★ **集群现役栈不是"裸 pip 的 vLLM"，而是「ROCm SDK 的 pip 分发形态」**（TheRock 的 wheel 路线）：
**自带宽完整 ROCm 7.15 库栈 + `amd_torch_device_gfx1151` 设备包 + 自带 RCCL**。

### 2.3 ★★★ 关键洞察：两者是**同一条技术路线的两种封装**

| | **kyuz0 镜像** | **集群现役 venv** |
|---|---|---|
| 底层 | **TheRock ROCm SDK**（容器内 tarball 安装） | ★ **TheRock ROCm SDK**（`rocm_sdk` **wheel**） |
| 封装 | OCI 容器 | Python venv（裸机） |
| RCCL | **自建补丁版**（`librccl.so.1.gz`） | venv 自带 `_rocm_sdk_libraries/lib/librccl.so.1`（**实测 2.30.4，跨机已跑通**） |
| vLLM | 自编译（ROCm Clang）+ device 补丁 | AMD/lemonade 渠道（`0.25.2.dev0+rocm7.15.0a…`） |

★★ **结论**：**"kyuz0 vs 原生 vLLM"这个对比的框架需要先纠正** ——
它不是"容器方案 vs 裸机方案"，而是 **"社区策展的补丁容器"** vs **"AMD 官方渠道的 ROCm SDK wheel（本集群已在用、且三站逐字一致）"**。
**两者同源于 TheRock**，差异集中在**封装形态**与**谁打了什么补丁**。

## 3. ★ 增量对账：kyuz0 在本集群**比现役多什么**

| # | kyuz0 的卖点 | 本集群是否已有 | 判定 |
|---|---|---|---|
| **①** | ★★ **补丁 RCCL（让 gfx1151 能做集合通信）** | ★ **已有，且更强** —— 本集群 RCCL **2.30.4** 含**官方 `gfx1151` 目标 + 分架构包 `rccl_lib_gfx1151.kpack`**；**跨机 collective 已实测跑通**（双 rank `ALLREDUCE_OK`、`NET/Socket`、**median 182 µs**） | ❌ **无增量**（详见 [RCCL 评估 §4.2/§4.4](./2026-09-30_RCCL部署方案与集群必要性评估.md)） |
| **②** | **vLLM 的 gfx1151 device detection 补丁** | ◐ **疑似已有等价物** —— venv 内含 AMD 官方 **`amd_torch_device_gfx1151`** device 包；且 ADR-0011 记 **A4 实测已跑通**（pp512 298 t/s / tg128 17.60）⇒ **本集群 vLLM 在 gfx1151 上能起来并被量过** | ❌ **无明确增量**（⚠ 未逐行比对补丁内容，属**推断**） |
| **③** | `tcmalloc` 防 shutdown double-free | ❌ 未见 | ◐ **可能有增量** —— 本仓**无 vLLM 长期驻留/shutdown 崩溃的实测记录**，故**无法判断**该修复对本集群是否必要 |
| **④** | 策展模型表 + benchmark 脚本 | ◐ 本仓有自己的 gold 夹具（`spec/model-eval/`）+ `results-ledger` + 冒烟口径 | ◐ **口径不同，非替代** —— 但**不构成引入理由**（本仓评测面自成体系） |
| **⑤** | 容器化可复现 / 隔离 | ◐ 本仓以 **venv + 三站逐字一致版本 + 门禁断言** 达成可复现 | ❌ **本集群另有纪律**：`ADR-0004` **唯一管理面**；容器栈 = **新实体** |
| **⑥** | RDMA 集群 TP=2 | ❌ **不可用** —— 需 **Intel E810 + PCIe 槽**，迷你主机无槽 | ❌ **封闭**（同 [AMD395 互连调研](../../spec/rpc-optimization/research/AMD395分布式推理高性能互连方案调研.md) §2.3） |

★ **合计**：**6 条里 4 条无增量或封闭、2 条"可能有但未证"** ⇒ **不构成引入理由**。

## 4. 可行性逐层判定

| 层 | 判定 | 依据（E1/E3） |
|---|---|---|
| **宿主 OS** | ◐ **需补一步** | Ubuntu 24.04 在支持面内，但 kyuz0 的 Ubuntu 路径**要求 Distrobox**，三站均无 ⇒ 需新增一层 |
| **容器运行时** | ◐ **半数就绪** | CLI 三站全有；daemon **仅 A 站 active**（B inactive / C 无 unit）⇒ 要用须先起服务，**属"改站上配置"** |
| **磁盘** | ✅ **充足** | 773 G / 790 G / 1.1 T 可用（镜像 + 权重按 kyuz0 建议 100 GB 量级亦宽裕） |
| **GPU 访问** | ✅ **可满足** | 用户已在 `render` 组；容器可 `--device=/dev/kfd /dev/dri`（kyuz0 的 RDMA 路径另需 `/dev/infiniband`，**本集群无该设备**） |
| **内核参数** | ◐ **不一致** | kyuz0 主张 `iommu=pt …`；本集群 **B 缺 `iommu=pt` / C 是 `amd_iommu=off`**。★ 但 [RCCL 评估 §6-③.3](./2026-09-30_RCCL部署方案与集群必要性评估.md) 已实测：**未改该参数也跑通了 socket collective** ⇒ **非阻断项** |
| **RDMA/集群模式** | ❌ **不可用** | 无 RDMA 设备（三站 `/sys/class/infiniband` 空）+ 无 PCIe 槽 |
| **治理** | ❌ **未过闸** | `ADR-0004`（唯一管理面 / **新增引擎栈须立项**）+ `ADR-0011`（vLLM 路径**暂缓**）。★ 且引入后**三站管理面要多管一套容器栈**（版本锁 / 加载 / 卸载 / 台账 / 手册铁律） |
| **网络可达性** | ⚠ **未核** | 站上 `huggingface.co` 直连被重置（本仓已证），**Docker Hub / ghcr 可达性本轮未测** ⇒ 拉镜像能否成功**未验** |

★ **综合**：**技术上可做**（需：起 daemon + 装 Distrobox + 过两道 ADR），**但没有一条增量价值支撑这个成本**。

## 5. 与"原生 vLLM"的对比（本仓口径）

★ 先纠正称谓：本仓真正的两个可比对象是 ——
**(甲) `AMD 官方渠道 vLLM`**（= 集群现役 `~/vllm-rocm`，ROCm SDK wheel 形态）· **(乙) `ROCm 官方 vLLM 容器`**（`rocm/vllm-dev:…`，官方文档载明 **支持 gfx1151/gfx1150**）· **(丙) `kyuz0 补丁容器`**。

| 维度 | **(甲) 集群现役 venv** | **(乙) ROCm 官方容器** | **(丙) kyuz0 补丁容器** |
|---|---|---|---|
| 分发形态 | pip venv（裸机） | OCI 容器 | OCI 容器 |
| 底层 ROCm | TheRock `rocm_sdk` wheel **7.15.0** | ROCm 官方镜像版本 | TheRock SDK **7.x** |
| vLLM | **0.25.2.dev0**（三站逐字一致） | 随镜像（如 0.10.2rc1 档） | **自编译**（ROCm Clang + 补丁） |
| **RCCL** | venv 自带 **2.30.4**（★ **跨机已实测**） | 随官方镜像 | **自建补丁版** |
| gfx1151 适配 | ★ 有 **`amd_torch_device_gfx1151`** 官方 device 包 | **官方声明支持** | 补丁 |
| 三站一致性 | ★ **逐字一致**（已验） | 需自己钉 tag | 需自己钉 tag |
| 宿主依赖 | **无**（venv 自带运行时） | Docker | Docker + **（Ubuntu）Distrobox** |
| 治理成本 | **已在 `ADR-0004`/`0011` 内** | **新实体 ⇒ 须立项** | **新实体 + 需跟第三方 CI 产物 ⇒ 须立项** |
| 供应链 | AMD 官方渠道 | AMD 官方镜像 | ★ **第三方镜像 + 第三方 CI 产出的 RCCL 二进制** |
| 本仓评测面 | 已接（`model-eval` / `results-ledger` / 冒烟） | 需另接 | 需另接 |

★★ **结论（对比的直接回答）**：
1. **与现役栈（甲）比：kyuz0 无必要** —— 它的两个核心补丁（RCCL / device）在本集群**已由官方渠道具备并实测可用**；而它引入的是**容器新实体 + 第三方二进制供应链**。
2. **若真要容器化：`(乙) ROCm 官方容器` 是更该先看的那个** —— 同样容器化收益，但**供应链是 AMD 官方**，且**官方文档明载支持 gfx1151**；kyuz0 的优势面（补丁）**在当前 ROCm 版本下已不再是优势**。
3. ★ **唯一仍需单独评估的 kyuz0 特性**：`tcmalloc` 防 shutdown 崩溃（§3-③）—— 但本仓**没有对应的实测症状**，故**不构成先决理由**。

## 7. 诚实边界（必须与结论同读）

1. ★★ **本文没有跑过 kyuz0 镜像** —— 未拉取、未启动、未跑任何模型。**"可行性"是"前置条件盘点"意义上的可行**，**不是"实测可跑通"**。
2. ★★ **§3-② 是推断**：我**未逐行比对** kyuz0 的 vLLM gfx1151 补丁与 `amd_torch_device_gfx1151` 是否等价 —— 只知后者存在、且 ADR-0011 记 A4 曾跑通。
3. ⚠ **镜像体积未实测**（E3 未取到确切数字）⇒ 磁盘占用只是"按 kyuz0 建议的 100 GB 量级"估算。
4. ⚠ **Docker Hub / ghcr 可达性未测** ⇒ "能不能拉到镜像"**未验**（本仓已证站上 `huggingface.co` 直连被重置，故这条**不能想当然**）。
5. ⚠ **三个对比对象都没在同一任务面上跑过** ⇒ 表里的"优劣"是**结构对比**，**不含任何性能/质量读数**。
6. ⚠ **kyuz0 的信息来自 DeepWiki 索引（2026-02 快照）** —— ★ 其"补丁 RCCL"结论的**时效性**已在 [RCCL 评估 §4.2](./2026-09-30_RCCL部署方案与集群必要性评估.md) 被本集群实测推翻过；**引用前须核当前上游状态**。
7. ⚠ **B/C 站 docker daemon 未运行**（C 无 unit）—— 这**不是**"Docker 不可用"，而是"服务未起"；**不要读成"容器路线不可行"**。
8. ⚠ **本轮未碰站上任何配置**（未起服务、未拉镜像、未装 Distrobox）。
