## 0. 结论前置（先看这三句）

1. ★★ **本仓不是"线性流水线"，而是【半张图】** —— **扇出已经存在且已实测真并行**
   （`split` + `decompose`，跨站 round-robin）；**缺的是另外三样**：**汇聚(join)** · **片间依赖边** · **迭代/搜索**。
   ⇒ 所以问题**不是**"要不要换成图"，而是"**这半张图缺的那半，该不该用框架来补**"。
2. ★★ **对 `Auto_Prover`（数学证明）而言，真需求是【搜索】，不是【图】** —— 图框架提供的是
   **固定控制流拓扑 + 持久化 + 人审**，**它本身不提供任何搜索能力**；证明类任务的价值全在
   **搜索器 + verifier 闭环**（§3.3 有外部实证）。⚠ 且本仓 `Auto_Prover` 至今
   **从未与真实形式化证明输入对接**（`inventory/untested-index.yaml`）⇒ 在**零真实输入**的阶段选编排拓扑
   = 为一条**还不存在的工作流**设计图形状。
3. ★★ **图框架【不创造算力】** —— 本集群的并行上界是 **站池大小 = 3**（`O-18` 跨站各 1，物理上界），
   已由 `split` 的 `SPLIT_INFEASIBLE` 硬编码钉住（>3 片直接 `exit 18`）。⇒ 引入图框架**不会**让并行度变大；
   **多节点 TP / PD 分离**在 10G 互联下**官方与实测都指向不划算**（§4.2）。

**⇒ 一句话**：**升级的实质内容 = 补本仓那三样缺口（尤其"汇聚"），不是换框架**；框架只在补完之后，
且**必须解决"双真相源"**时才值得作为**外层薄壳**考虑。

### 1.2 ★★ 明确**没有**的三样（这才是"升级成图"的实际内容）

1. **汇聚 / join** —— ★★ **最实的缺口**。`split` 明确写着
   `SPLIT_ABORT: decompose only valid for readonly tasks … writable merge not supported [exit 2]`
   （agent-cli.ps1 L3706）⇒ **有扇出、无归并**：多片只在**只读**任务上合法，且**没有任何"归并"语义**
   （谁合并、冲突怎么裁、归并判据是什么 —— 全不存在）。
   ⚠ 缺的是**语义**（判据 + 责任归属），**不是框架能力**：任何图框架都不会替你决定"两个片结论冲突时听谁的"。
2. **片间依赖边** —— `decompose` 是**有序列表**，但实际是**并行派发**（顺序只用于命名/编号）
   ⇒ **没有"A 片输出 = B 片输入"的表达**，也没有前置条件/拓扑排序。
3. **迭代 / 搜索** —— 只有**有界重试**（resume ≤3），**没有**搜索树 / 分支预算 / 状态复用的表达。
   ★ 这一条对 `Auto_Prover` 是**决定性**的（见 §3.3）。

### 1.3 ★ 扇出的上界是**站池大小 3**（不是框架能解决的）

```text
$stationPool = @('A','B','C')
if ($shards.Count -gt $stationPool.Count) { SPLIT_INFEASIBLE … [exit 18] }
```
（agent-cli.ps1 L3733-3737）

⇒ 与 `O-18`「跨站各 1 并发」`O-24④`「**勿在同站内叠开并发**」一致：**并行度是物理量**，
由**站数 × 每站 1** 决定。★ **推论**：任何图框架都**不能**提高这个上界；提高它只能靠
**增加站** 或 **改变单站容量约束**（后者本仓已有实测：同站 2 并发聚合 +32~48%，**不支持**旧"~2.8×"说法）。

## 2. 外部侧：2026 年图编排框架的能力与坑（E3 · 未在本仓复现）

### 2.1 能力对照（★ **全部为官方文档声称，无独立评测**）

| 框架 | 条件边 | 循环 | 扇出 | 持久化续跑 | 人审中断 | 子图 |
|---|---|---|---|---|---|---|
| LangGraph 1.2 | ✓ | ✓ | ✓ | checkpointer（sync/async/exit 三档） | `interrupt` | ✓ |
| CrewAI Flows | ✓（`@router`） | ✓ | ✓ | 部分 | 弱 | crew 嵌套 |
| AutoGen / AG2 | ✓ | ✓（每环须 exit 条件） | ✓ | 弱 | 弱 | ✓ |
| MS Agent Framework 1.0 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Google ADK 2.0 | ✓ | ✓ | ✓（fan-out/join） | ✓ | ✓ | ✓ |

- ★ **生态状态（影响选型）**：**AutoGen 已进入维护模式**，官方导向 **MAF 1.0**（2026-04 GA）；
  ADK 2.0 图引擎 GA（Python，2026-05）。
  - MS Agent Framework 公告：<https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-at-build-2026-announce/>
  - ADK 2.0：<https://adk.dev/2.0/>
  - LangGraph 持久化：<https://docs.langchain.com/oss/python/langgraph/persistence>
  - CrewAI Flows：<https://docs.crewai.com/en/concepts/flows.md>
  - AutoGen 图构建：<https://instagit.com/microsoft/autogen/building-graph-based-agent-workflows-with-digraphbuilder-and-graphflow.md>
- ⚠ **Temporal** 是通用 durable-execution，**非 agent 原生**（无流式/记忆，payload 有上限），常与图框架**叠用**；
  对比文出自 LangChain 自家（**厂商立场**）：<https://www.langchain.com/resources/langgraph-vs-temporal>

### 2.2 已知坑（★ 按证据强度分级 —— 这一节比 2.1 更值钱）

- ★★ **有独立论文实测（最强证据）**：对 5 个框架做机器可检的一致性契约测试 ⇒
  **LangGraph 1.2.9 在真实 `SIGKILL` 后会【重跑已记录的工作】**（崩溃下退化为 **at-least-once**），
  并出现"记录第二个 resume 值却从不读取"；且 CrewAI / LlamaIndex / LangGraph 的 **resume 语义互相矛盾**。
  <https://arxiv.org/html/2608.03836v3>
  ⇒ ★ **对本仓的直接含义**：本仓是**证据链 + 产物 digest** 体系，若外层换成"会重跑已记录工作"的调度器，
  **重复副作用**会直接污染 run 产物与证据链。
- ★★ **另一项研究**：checkpoint/rollback 的五类失效**可致重复副作用（原文以重复付款为例）**。
  <https://arxiv.org/html/2608.29381v1>
- ★ **官方承认**：checkpoint **无界增长需 prune**（同上 LangGraph persistence 文档）。
- ★ **厂商自测**：全量快照为 O(N²)；200 轮 coding 序列化 **5.3 GB → Delta 129 MB**（自家 delta 方案）。
  <https://www.langchain.com/blog/delta-channels-evolving-agent-runtime>
- ★ **本地模型（与我们直接相关）**：`llama-server` 必须带 `--jinja`，否则**静默忽略 tools**；
  未经工具微调的模型只吐散文；**小模型 5+ 工具时误报率 >35%**。
  <https://aitoolsguidebook.com/en/articles/local-llm-tool-calling-format-ignored/>
  ⇒ ★ 图的"**条件边**"**依赖工具调用质量**：条件判错的图 = 静默走错分支（本仓最防的形态）。
- ✗ **不予采信**："循环 $1000+/hr"之类出自**非官方成本博文**，无测试条件 ⇒ **本调研不引用**。

### 2.3 ★★ 数学证明场景：要的是**搜索**，不是**图**

外部实证（E3）：

- **LeanDojo-v2** 明确把 **whole-proof generation** 与 **proof search**（tactic 级、与 Lean 状态交互）
  区分为两种任务 ⇒ 后者才是主流形态。<https://leandojo.org/leandojo>
- **LongCat-Flash-Prover**：**agentic lemma tree search** + 工具集成 RL，MiniF2F 97.1% pass@72，
  并**需要 legality 检测**以抑制 reward hacking。<https://arxiv.org/html/2603.21065v1>
- **Gödel-Code-Prover**：**分层证明搜索**（先分解子目标、再 tactic）。
  <https://arxiv.org/html/2603.19329>

★★ **关键区分（本调研的分析结论）**：

| | **搜索 (search)** | **图 (graph)** |
|---|---|---|
| 解决什么 | **解空间怎么探索**（树/MCTS + 启发式 + **verifier 奖励**） | **固定控制流怎么走**（条件边 + 持久化 + 人审） |
| 数学证明里的地位 | ★ **核心价值所在** | **外层调度薄壳** |
| 缺了的后果 | 证不出来 | 还能手跑 |

⇒ ★★ **用 LangGraph/CrewAI 包一层，不提供任何搜索能力**。若目标真是"自动证明"，
**该投入的是 verifier 闭环与搜索，而不是拓扑框架**。

⚠ **且本仓前置条件尚未满足**：`inventory/untested-index.yaml` 记 `Auto_Prover`
**从未与真实形式化证明输入对接** ⇒ **先补"能跑通一个真实证明"的最小闭环**（并量出卡在哪），
**再谈**编排拓扑。★ 在零真实输入的阶段选框架，等于为**不存在的工作流**设计图形状。

## 3. 本地机群算力：哪些能用 · 哪些**不该动**

### 3.1 已有且已被本仓实测的能力（E1）

| 能力 | 形态 | 判据 |
|---|---|---|
| 跨站扇出并行 | `split` 跨站各 1（≤3 片） | 实测墙钟 < 串行下界（O-67） |
| 串行/并发约束 | slot-gate（`/slots` 探测）+ 工作区 `flock` | `O-18` / `O-24④` / `O-25` |
| 引擎加载/卸载 | `infer-load` / `infer-unload` + `cluster.py flow`（预估→加载→基准→**自动卸载**→落账） | 手册 §3 / §2.4 |
| 消费侧只读视图 | `cluster.py agent {runs\|live\|tail\|chain\|verify\|audit\|audit-judge\|dashboard}` | ★ **全部只读、无派发能力**（L4291-4311） |

⇒ ★ **重要口径**：`cluster.py` 的 `agent` 族**不能派发任务**（派发只在控制台侧的 `agent-cli.ps1`）。
⇒ 图编排若要"跑起来"，落点仍只能是**派发外壳**侧（或新实体，须过 §6 的闸）。

### 3.2 明确**不建议**（带官方/实测依据）

- ✗ **多节点 TP**：**llama.cpp 在以太网下不支持 tensor parallel**（NCCL timeout）；
  ★ 实测参照：双 DGX Spark 用 llama.cpp RPC 跑 426B，**decode ≈10.7 tok/s、prefill ≈590 tok/s，
  瓶颈是双节点 RPC 串行化**。<https://forums.developer.nvidia.com/t/minimax3-on-2-nodes-decode-10-7-tok-s-4bits/373421>
  ⇒ 与本仓现状同向（本仓 `RPC_TARGET` 默认空 = 单机；集群基准才临时多机）。
- ✗ **PD 分离（prefill/decode 拆开）**：**官方明确"不提升吞吐，只解耦 TTFT/ITL"**，且依赖 RDMA/IB。
  <https://docs.sglang.io/docs/advanced_features/pd_disaggregation> ·
  <https://docs.vllm.ai/en/stable/features/disagg_prefill/>
  ⇒ 本集群是 **10G** 互联 ⇒ 跨节点 KV 传输**大概率吃掉收益**。
- ✗ **Ray 大规模控制面**：Ray Serve 在超大集群有 **O(N²) 控制面**问题（256 节点 bring-up ~30 min）。
  <https://arxiv.org/pdf/2609.10812> ⇒ 3 站规模**用不上**，但也**不必承担**它的复杂度。
- ★ **值得留意的替代思路**：**PRIMA.CPP** 专攻**异构 / 低资源 home cluster**（pipelined-ring + 调度），
  与"工作站级大内存单站 + 少量节点"的形态更贴。<https://arxiv.org/pdf/2504.08791>

## 4. 对本仓的裁定建议（分级 P1–P5，按**改动面**而非收益排）

| 级 | 动作 | 为什么 | 前置 |
|---|---|---|---|
| **P1** ★ 零成本 | **补 `split` 的【汇聚】语义** —— 先定义"多片结果怎么归并 / 冲突怎么报 / 谁负责"（**不引框架**） | 这是**半张图的缺口**，且**纯本仓工作**；框架帮不上（§1.2①） | 无 |
| **P2** 低成本 | 把 **`G1` 决策表 + `multi-round.yaml`** 的"条件分支/轮数上限"从**文档表**变成**可机判判据**（同 D7 的纯函数 + 契约做法） | ★ 这等于**用本仓既有方式拿到"图的一部分"**，且**不引入新真相源**；与 `O-134`–`O-136` 同一条路 | 无 |
| **P3** 中 | 给 `Auto_Prover` 做**一个真实证明的最小闭环**（verifier-in-the-loop，先能跑通 1 条） | 真问题是**搜索**（§2.3）；**零真实输入**下谈拓扑是空转 | 需形式化输入样本 |
| **P4** 高 · **须 ADR** | 真要图框架 ⇒ **只作外层薄壳**（图管调度/持久化，**搜索仍在自研侧**） | 且**必须先解决"双真相源"**（本仓头号失败形态）+ **重复副作用**（§2.2 实测） | §5 两道闸 |
| **P5** ✗ 不建议 | 多节点 TP / PD 分离 | 官方与实测均指向不划算（§3.2） | — |

★ **P1/P2 的共同点**：它们**不需要任何新栈**，却覆盖了"图"在本仓**真正缺的那部分**。
★ **P4 的判据（什么时候才值得动）**：当 **P1+P2 做完仍不够用**，且能给出**具体的**"哪条工作流
用现有三样表达不出来"的实例时 —— 而不是"项目变复杂了"这类**不可机判**的理由。
