## 0. 结论前置（先看这三句）

1. ★★ **本仓不是"线性流水线"，而是【半张图】** —— **扇出已经存在且已实测真并行**
   （`split` + `decompose`，跨站 round-robin）；**缺的是另外三样**：**汇聚(join)** · **片间依赖边** · **迭代/搜索**。
   ⇒ 所以问题**不是**"要不要换成图"，而是"**这半张图缺的那半，该不该用框架来补**"。
2. ★★ **对 `Auto_Prover`（数学证明）而言 —— 【证明搜索的形态本身就是一张图】**（2026-10-01 就地更正，
   见 §2.3.1）：HTPS 原文即 "builds a **hypergraph** … **tactics as edges** … **subgoals as nodes**"，
   且子目标 "can be **solved independently**" ⇒ 用户描述的「多状态 + 状态间依赖 + 多路径尝试」
   **正是这个结构**。★ **但要把两层分开**：**图的【领域语义】**（AND-OR 超图）**只能自建**；
   **图的【执行外壳】**（运行期扇出 / 汇聚 reducer / 崩溃恢复 / 人审）★ **框架确实能给** ——
   而**外壳不提供搜索策略**（HTPS 的贡献是**搜索算法 + value function**，不是图）。
   ⚠ 本仓 `Auto_Prover` 至今**从未与真实形式化证明输入对接**（`inventory/untested-index.yaml`）
   ⇒ 这是 **P3 的输入需求**，**不是**"所以不该谈拓扑"的理由。
3. ★★★ **图框架【不创造算力】，但"上界 3"这条【首版说错了 · 已二次更正】** ——
   ★ 用户 2026-10-01 纠错**成立**：**并发 LLM 推理资源【不止 3】**。`O-18` 跨站各 1 与
   `SPLIT_INFEASIBLE`（`exit 18`）约束的**只是【同一套本地引擎上的并发】**（**一个特定资源的读数**），
   **不是【总量上界】** —— ★ 这与 §2.3.1 那次「一个词两个所指」是**同一条教训的第三次复发**。
   ⇒ 正确形态 = **【三个池】**（见 §3.1a）：**① 本地引擎池**（跨站各 1，受 `O-18` 内存带宽约束）·
   **② 出网 API 池**（★★ **最大的一池，与①完全不竞争** —— 三站 **独立 OpenRouter 账户**，
   实测各 **1000 请求/日 · 20 请求/分**；`ADR-0003` + `agent-cli.ps1` L93/L3724）·
   **③ Lean 验证池**（便宜、CPU-bound、三站全核心，与①②互不竞争）。
   ★ 且 **② 有内容闸**：`local-only` 内容**不得**走它（`sensitivity.yaml` 档位同时**选择执行后端**）。
   ⇒ **"大量 agent 并行"的真瓶颈不是槽位数**，而是 **① 的账户级速率（20/分/账户）与 ③ 的验证吞吐**；
   **多节点 TP / PD 分离**在 10G 互联下**官方与实测都指向不划算**（§3.2）。

**⇒ 一句话**：**升级的实质内容 = 补本仓那三样缺口（尤其"汇聚"），并在证明场景里把 AND-OR 超图建起来**
（§2.3.1）；**框架不是必须先换的**，但它是**那套执行外壳**（运行期扇出 / 汇聚 / 恢复 / 人审）的现成来源 ——
⇒ 顺序应是 **先把图语义在自研侧跑通（P1→P3），再决定外壳是否外置（P4）**，
且 P4 **必须解决"双真相源"**（本仓头号失败形态）。

### 1.2 ★★ 明确**没有**的三样（这才是"升级成图"的实际内容）

1. **汇聚 / join** —— ★★ **最实的缺口**。`split` 明确写着
   `SPLIT_ABORT: decompose only valid for readonly tasks … writable merge not supported [exit 2]`
   （agent-cli.ps1 L3706）⇒ **有扇出、无归并**：多片只在**只读**任务上合法，且**没有任何"归并"语义**
   （谁合并、冲突怎么裁、归并判据是什么 —— 全不存在）。
   ⚠ 缺的是**语义**（判据 + 责任归属），**不是框架能力**：任何图框架都不会替你决定"两个片结论冲突时听谁的"。
2. **片间依赖边** —— `decompose` 是**有序列表**，但实际是**并行派发**（顺序只用于命名/编号）
   ⇒ **没有"A 片输出 = B 片输入"的表达**，也没有前置条件/拓扑排序。
3. **迭代 / 搜索** —— 只有**有界重试**（resume ≤3），**没有**搜索树 / 分支预算 / 状态复用的表达。
   ★ 这一条对 `Auto_Prover` 是**决定性**的（见 §3.3）。

### 1.3 ★ 扇出的上界是**站池大小 3**（不是框架能解决的）

```text
$stationPool = @('A','B','C')
if ($shards.Count -gt $stationPool.Count) { SPLIT_INFEASIBLE … [exit 18] }
```
（agent-cli.ps1 L3733-3737）

⇒ 与 `O-18`「跨站各 1 并发」`O-24④`「**勿在同站内叠开并发**」一致：**并行度是物理量**，
由**站数 × 每站 1** 决定。★★ **但这条只管【本地引擎池】（2026-10-01 二次更正）** ——
**它是 `split` 的【派发策略】（一片一站），不是【算力上界】**：若片的执行后端走**出网档**，
则算力来自**各站独立的 OpenRouter 账户**（`ADR-0003`），**"一片一站"在算力上并不必要**
（`agent-cli.ps1` L3729 `SPLIT_WARN` 逐字：「跨站（各站独立 key）= **可并行**【实测 2 片/2 站、3 片/3 站】」）。
⇒ ★ `SPLIT_INFEASIBLE`（`exit 18`）是脚本**当下的分配纪律，不是物理墙**；提高片数上界**不必**加站
（可先评估"同站多片 + 出网后端"，⚠ 但**须实测**：同站多片**共用一站引擎**时仍受 `O-18` 约束）。
★ **图框架不能提高【本地引擎池】的上界**；提高它只能靠**增加站** 或 **改变单站容量约束**
（后者本仓已有实测：同站 2 并发聚合 +32~48%，**不支持**旧"~2.8×"说法）。

### 2.3.1 ★★ 就地更正（2026-10-01 · 用户质疑后重取证据）

> ⚠⚠ **首版本节写的是「数学证明要的是搜索，不是图」—— 那句话是【假二分】，现予撤销。**
> 触发 = 用户追问：「若需**并行启动大量 agent**、**多路径尝试**、**多个状态且状态间有依赖**、
> 且**假设 `Auto_Prover` 正在与形式化证明输入对接** —— 图结构是否必须？」
> 该质疑**成立**，且下面的外部证据**直接证伪了首版那句话**。

**① 证明搜索的【运行形态本身就是一张图】—— 有原文实证**

**HyperTree Proof Search（HTPS）**（Lample et al., Meta AI）逐字：

> "The automated prover builds a **hypergraph** with the theorem to be proved as the **root node**,
> **tactics as edges** and **subgoals as nodes**. The prover recursively expands leaves…"
> "…the formal system returns **two subgoals** … that can be **solved independently**."
> —— <https://arxiv.org/pdf/2205.11491v1.pdf>

⇒ ★★ **goal/subgoal 是节点 · tactic 是边 · 独立子目标 = 天然并行分支**。
用户描述的「多状态 + 状态间依赖 + 多路径尝试」**正是这个结构**，不是另一种东西。

**② 正确的那条边界：图【领域语义】vs 图【执行外壳】**

| | **图的【领域语义】** | **图的【执行外壳】** |
|---|---|---|
| 是什么 | goal/subgoal 超图 · **AND 依赖**（子目标全证才证父）vs **OR 分支**（同一 goal 的多个 tactic = 备选路径） | 调度 · 持久化 · 扇出 · 汇聚 · 人审 |
| 谁提供 | ★ **只能自建**（证明的本体） | ★ **框架确实能给** |
| 缺了的后果 | **证不出来** | 还能手跑，但**长期搜索会崩在工程细节上** |

★ **首版错在哪**：把这两层**混成一件事**说了。「框架不提供搜索」**仍然成立**
（HTPS 的贡献是**搜索算法 + 学到的 value function**，不是图）——
但由此推出「所以不需要图」**是错的**：**框架给不了搜索，却正好给了搜索【跑起来】所需的外壳。**

**③ 框架确实对上了用户描述的四件事（有据）**

- **运行期才知宽度的扇出**：LangGraph `Send` —— "dynamically create worker nodes …
  **the number of branches only emerges at runtime**"（[官方 graph API](https://docs.langchain.com/oss/javascript/langgraph/use-graph-api) ·
  [实践](https://matt-harrison.com/posts/9-5-26-langgraph-part-2/)）⇒ 正对"展开一个 leaf ⇒ N 个子目标"。
- ★★ **汇聚（本仓缺的那一样）**：**reducer** —— "无 reducer 则 **last write wins**；
  有 `operator.add` 则合并"（[map-reduce](https://deepwiki.com/langchain-ai/langchain-academy/7.1-map-reduce-pattern)）
  ⇒ 与 §1.2① 的 `SPLIT_ABORT: writable merge not supported` **正好互补**。
- **递归上限**（约束搜索深度）· **`interrupt` 人审** · **子图**（嵌套证明结构）· **checkpointer**（长搜索崩溃恢复）。
  ⚠ 但 §2.2 那条**独立实测**仍成立：**LangGraph 1.2.9 在 `SIGKILL` 后重跑已记录工作**
  ⇒ 对**长搜索**这是**真代价**（重放 = 重算 LLM 调用），不是理论风险。

**④ 修订后的裁定（分两层）**

1. **作为数据模型 ⇒ 实质必须**（领域原生 AND-OR 超图；HTPS 已证）—— ★ **首版的"不需要"予撤销**。
2. **作为执行框架 ⇒ 不是必须**，但在 **P3 跑通后大概率是划算的外壳**（正对扇出/汇聚/恢复/人审四痛点）；
   而 **搜索策略 + Lean 接口 + 双池调度仍须自研**。

⚠ **前置条件（不变，但理由要看清）**：`inventory/untested-index.yaml` 记 `Auto_Prover`
**从未与真实形式化证明输入对接** ⇒ 先补"能跑通 1 条真实证明"的最小闭环。
★ 但注意：**这条不再是"所以不该谈拓扑"的理由** —— 它是**P3 的输入需求**，
而 **P3 的形态现在已明确（AND-OR 超图），不是"先跑通再说"**。

## 3. 本地机群算力：哪些能用 · 哪些**不该动**

### 3.1 已有且已被本仓实测的能力（E1）

| 能力 | 形态 | 判据 |
|---|---|---|
| 跨站扇出并行 | `split` 跨站各 1（≤3 片） | 实测墙钟 < 串行下界（O-67） |
| 串行/并发约束 | slot-gate（`/slots` 探测）+ 工作区 `flock` | `O-18` / `O-24④` / `O-25` |
| 引擎加载/卸载 | `infer-load` / `infer-unload` + `cluster.py flow`（预估→加载→基准→**自动卸载**→落账） | 手册 §3 / §2.4 |
| 消费侧只读视图 | `cluster.py agent {runs\|live\|tail\|chain\|verify\|audit\|audit-judge\|dashboard}` | ★ **全部只读、无派发能力**（L4291-4311） |

⇒ ★ **重要口径**：`cluster.py` 的 `agent` 族**不能派发任务**（派发只在控制台侧的 `agent-cli.ps1`）。
⇒ 图编排若要"跑起来"，落点仍只能是**派发外壳**侧（或新实体，须过 §6 的闸）。

### 3.1a ★★ 三个资源池：**这才是"大量 agent 并行"该怎么读**（2026-10-01 新增 · **同日二次更正**）

> ⚠⚠ **首版本节写「LLM 推理（极稀缺，≈3）」—— 该口径【已更正】。**
> 触发 = 用户 2026-10-01 纠错：「LLM 推理部分，**单站可以使用 OpenRouter 单日 1000 次免费模型额度**，
> 且**单站可以同时加载 gpt120B / qwen3.8 系列 / minimax m2.7**，
> **实际上并发 LLM 推理资源超过 3**」。
> ★ 该纠错**成立**，且**仓内本来就写着这条纪律**（见下表依据列）—— 首次调研**漏了出网这条腿**。
> ⇒ ★ 根因与前一条同族：**把一个特定资源的读数（同引擎叠并发）普遍化成了总量上界。**

★ 用户场景里"并行启动**大量** agent"这句话，**必须拆成三个池**才可判 ——
否则会得出"上界 3 ⇒ 无法大量并行"这个**错的**结论：

| 资源池 | 谁来用 | 稀缺度 | 并行度 | 依据 |
|---|---|---|---|---|
| **① 本地引擎池** | 生成 tactic / 证明片段（`local-only` 内容**只能**走它） | ★★ 极稀缺 | **跨站各 1**（★ 若走 RPC 切分，一个推理吃掉多站 ⇒ 更低）；★ B 站另有 32837 第二 llama-server（`--parallel 4`） | `O-18` · `SPLIT_INFEASIBLE`（L3733）· 手册 §3.5 / §2.4 · `ports.yaml` 8080/32837 |
| **② 出网 API 池** | 生成 tactic / 证明片段（`public` / `sanitized` 内容） | ★★ **不稀缺 —— 最大的一池** | **≈ 3 账户 ×（20 请求/分 · 1000 请求/日）**；三站 `openrouter.key` **独立账户**，**实测按账户隔离、互不挤占** | `ADR-0003` §免费档每日计数（+2026-09-21 更正块）· `docs/security/2026-09-21_OpenRouter多账户配额分配与调配设计.md` · ★ 仓内纪律 `agent-cli.ps1` L93 / L3724 / L3729 |
| **③ Lean 验证池** | 编译判证：tactic 是否合法、子目标是否闭合 | ★ 便宜 · CPU-bound | **多**（三站全部核心可并行，与 ①②**互不竞争**） | 本仓**未实测**；★ 机制推论（`Lean` 是本地编译器进程，**不占引擎 / 不占出网配额**） |

★★ **推论（本场景最要紧的一条 · 已修订）**：HTPS 式搜索的自然形态是
**少量 LLM 调用（只扩当前 frontier）+ 大量便宜的验证** ——
★ 但"量少"是**相对②的额度**而言（② 给的是**千级/日**，**不是 3**）：
**真瓶颈有两个，且都不是"槽位数"** —— **① 的账户级速率（20/分/账户）** 与 **③ 的验证吞吐**。
⇒ ★ 这才是"**充分使用本地机群算力资源**"的真答案：
**能起多少 agent 由②的配额决定（大）；跑不跑得动由①的速率与③的吞吐决定（未测）。**

⚠ **对②的边界（如实，要紧）**：出网池**只对 `public` / `sanitized` 内容开放** ——
`local-only` 内容**不得**走它（`inventory/sensitivity.yaml` 的**双语义**：档位同时**选择执行后端**）。
⇒ **证明场景能否用满②，取决于待证命题的内容档位**；若命题含未发表内容 ⇒ **退回①**。

★ **正面回答用户第二点（2026-10-01 澄清 · 上一轮我读错了）**：用户本意**不是**"单站同时载入三个大模型"，
而是「**加载本地模型与使用外部 API 不冲突，可以同时**」—— 即**同一站在跑本地引擎的同时，可照常打出网请求**
（这正是上表 **①② 互不竞争**那一格；**不需要任何"单站多模型"前提**）。
⇒ 上一轮把它写成"单站同时加载 gpt120B / qwen3.8 / minimax"再判"未确证" = **误读**，本处更正。

- ★ **由此成立（用户主张本身）**：一站的真实并发容量 = **1 条本地腿（①）+ 出网配额（②）**，两腿**可同时打**；
  跨 3 站 ⇒ 3 条本地腿 + 3 份账户配额。**「并发 > 3」不需要"单站多模型"，也不需要加站。**
- ⚠ **旁支事实（非用户主张 · 仅备查，别再拿它当前提）**：**同一引擎**同一时刻只服务**当前加载的那一个模型**
  （`ports.yaml` L66-67 实测「忽略请求里的 model 字段」）；各站 `conf` 面**是多个**（`models.yaml` L183 记 A 站 4 个）
  ⇒ **不同站可同时服务不同模型**。★ 而"同一站同时刻塞两个大档"受单机容量 **≈119 GiB** 限制
  （`m27-q4ks` ≈108.4GB / `qwen3.8-flash-next` ≈93.7GB / `gpt-oss-120b`(Q4) ≈63GB ⇒ 两大档基本塞不进一站）
  —— **但这条与用户主张无关**。

★★ **★ 修正后前提的真正落点：【并发 >3 物理成立，但本仓派发外壳把它锁死】**（本次澄清后**唯一实质新增**）：

- **物理面**：如上 —— 一站多腿、跨站叠加 ⇒ 可用并发**远大于 3**。
- **实现面（读码，E1）**：`ops/station-bin/agent-cli.ps1` 的 `Invoke-Split` **把上界硬编码成"站数"** ——
  L3733 `$stationPool = @('A','B','C')`；L3734-3737 `$shards.Count -gt $stationPool.Count ⇒ SPLIT_INFEASIBLE [exit 18]`；
  ★ **L3732 注释与 L3735 报错都写着 "physical upper bound 3"** ⇒ **把【派发策略】当【物理边界】写进了代码**
  （正是上一轮那条同族错误的**代码化形态**）。
  另注：一次 `split` 只经**一次** `Resolve-Model`（L3711）⇒ **整个 split 共用一个模型 / 一种后端**，
  **同一 split 内无法"一片本地、一片出网"混腿**。
- ⇒ ★★ **可落地含义（三池调度的第一条实现工作）**：让 agent 真正大量并行，**第一步不是加站，而是改 `$stationPool` 的定义** ——
  从"**站数**"改成"**站 × 腿**"（每站 = 1 本地槽 + 出网配额），或让派发走 `cluster.py` 侧绕开这条硬编码。
  ★ 这是 **P0 之后、P4 之前**一件**具体**工作（不是"项目变复杂了"那类**不可机判**的理由）。

⚠ **未实测（如实）**：① 本项**没有**量过三站的 **Lean 编译吞吐**（单条 theorem 编译耗时 /
并发条数上界 / Mathlib 预载内存占用）；② **也没有**测过**出网池在真实多 agent 下的形态**
（20/分/账户 的**排队与 429 退避**在搜索负载下的实际影响）。
⇒ 表里"多"与"不稀缺"**部分是机制推论、不是读数**（`ADR-0003` 的 20/分 · 1000/日 是**实测**，
但"搜索负载下够不够用"**未测**）。⇒ 若要按此设计调度器，**须先补 P0 实测**。

### 3.2 明确**不建议**（带官方/实测依据）

- ✗ **多节点 TP**：**llama.cpp 在以太网下不支持 tensor parallel**（NCCL timeout）；
  ★ 实测参照：双 DGX Spark 用 llama.cpp RPC 跑 426B，**decode ≈10.7 tok/s、prefill ≈590 tok/s，
  瓶颈是双节点 RPC 串行化**。<https://forums.developer.nvidia.com/t/minimax3-on-2-nodes-decode-10-7-tok-s-4bits/373421>
  ⇒ 与本仓现状同向（本仓 `RPC_TARGET` 默认空 = 单机；集群基准才临时多机）。
- ✗ **PD 分离（prefill/decode 拆开）**：**官方明确"不提升吞吐，只解耦 TTFT/ITL"**，且依赖 RDMA/IB。
  <https://docs.sglang.io/docs/advanced_features/pd_disaggregation> ·
  <https://docs.vllm.ai/en/stable/features/disagg_prefill/>
  ⇒ 本集群是 **10G** 互联 ⇒ 跨节点 KV 传输**大概率吃掉收益**。
- ✗ **Ray 大规模控制面**：Ray Serve 在超大集群有 **O(N²) 控制面**问题（256 节点 bring-up ~30 min）。
  <https://arxiv.org/pdf/2609.10812> ⇒ 3 站规模**用不上**，但也**不必承担**它的复杂度。
- ★ **值得留意的替代思路**：**PRIMA.CPP** 专攻**异构 / 低资源 home cluster**（pipelined-ring + 调度），
  与"工作站级大内存单站 + 少量节点"的形态更贴。<https://arxiv.org/pdf/2504.08791>
