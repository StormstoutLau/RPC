> **触发**：框架管理与调用问题持续积累，文档量增长，需要判断「如何分类归档、便于检索」，以及是否需要引入 RAG / 知识图谱。
> **射程**：本仓 `docs/`、`spec/`、`adr/` 的文档治理与检索；含跨仓（Auto_Prover / Spec_Workflow / Textbook）的 ID 面但不含其内部文档。

## 0. 结论前置（五句）

1. ★★ **本仓当前不需要向量 RAG**：实测 **343 篇 md / 8.8 MB**，社区阈值是「约 100 篇密集页（15–20 万 token）以上、且每日数十次以上查询」才划算；本仓查询频率是**人 + agent 偶发**，维护嵌入流水线的成本远大于收益。
2. ★★ **也不需要知识图谱**：本仓已有的关系是**文件级依赖**（`depends` / `upstream` / `doclinks`），不是「实体—关系」多跳查询；GraphRAG/LightRAG 的优势场景（"这些概念怎么连在一起"）在本仓没有消费方。
3. ★ **本仓其实已经在用「索引 + 元数据」范式**：`docs/research/README.md` 是主题索引，每篇文档的 YAML 头（`id/type/version/status/depends/upstream`）就是元数据，`doclinks` / `md-tables` / `doc-status` 是结构门禁 —— 这套组合正是社区推荐的「小中型知识库首选」。
4. ★ **真正缺的是三件轻量事**：① `docs/` 根目录 61 篇**没有索引**（research 有、根目录没有）；② 元数据**不可按字段检索**（status/type 只能人眼读）；③ 缺「该去哪找」的导航层（官方推荐的**分层 `CLAUDE.md`/目录 README**）。
5. **升级触发条件要写成判据**（§4.3），而不是凭感觉：文档超阈值、查询频次上来、或出现「必须多跳才能回答」的真实问题，再谈 RAG/KG。

## 2. 社区阈值与案例

### 2.1 何时才该上 RAG（四个来源的口径）

| 来源 | 阈值口径 |
|---|---|
| Jon Jones AI | 语料 **< 数十万 token** 且每日查询 **< 数十次** ⇒ 先用长上下文，不必检索；百万级或每日数百问才需要 |
| AI/TLDR | **约 100 篇密集页（15–20 万 token）** 以上，检索才开始在经济上成立 |
| Mansoori | 每次查询相关材料 **> 20–40 页**时 RAG 才赢 |
| AkitaOnRails（2026） | 明确主张「长上下文 + grep 已让向量库在多数场景不再必要」，并逐项对比搭建复杂度 |

⇒ **本仓 343 篇但查询稀疏**，落在「不必检索」区间。

### 2.2 索引文件范式（小中型知识库首选）

| 来源 | 主张 |
|---|---|
| MindStudio | **索引文件 vs 向量检索**对照：索引文件搭建成本低、随文档变更更新索引即可；向量检索需嵌入流水线、分块策略、重嵌；索引文件适合「小到中型、结构良好的知识库」 |
| VectifyAI PageIndex | 「无向量、基于推理」的检索：建**层级目录树**，让 LLM 沿树推理；专治「相似度高但不回答问题」 |
| Tellian | 知识库采用**扁平 wiki + `index.md` 导航**，不用子目录，靠索引文件让 LLM 自己找 |

### 2.3 Claude Code 官方的项目知识管理

| 来源 | 关键做法 |
|---|---|
| Claude Code Docs · memory | `CLAUDE.md` 自动加载；**路径作用域规则**按文件匹配加载；`imports` 可组织长文件但**不降低上下文成本** |
| Anthropic · 大型代码库 | 目录结构不表达语义时，在仓库根放**轻量 markdown 目录表**（每个顶层目录一行说明）；目录数上百时用**分层 CLAUDE.md** |
| Claude Code Docs · best practices | 不再建议在 `CLAUDE.md` 里描述架构与文件结构 —— **Claude 自己会读仓库，只写"仓库里没有的"** |

⇒ 与本仓最契合的是「**根索引 + 分层导航 + 只写非显然信息**」，而不是把文档喂进向量库。

### 2.4 RAG vs 知识图谱 vs 混合

| 维度 | 向量 RAG | 知识图谱 | GraphRAG（混合） |
|---|---|---|---|
| 数据结构 | 文本块 + 嵌入 | 实体与命名关系（节点/边） | 图 + 向量 |
| 检索 | 近似最近邻 | 图遍历（Cypher/SPARQL） | 向量召回 + 图扩展 |
| 擅长 | 单点事实查找 | **多跳关系**（"这些怎么连起来"） | 关系型复杂问 |
| 维护成本 | 需重嵌 | 需建图 + 增量更新 | 最高 |
| 代表实现 | 通用向量库 | Neo4j 等 | GraphRAG / LightRAG（LightRAG 主打增量更新与低查询成本） |

⇒ 本仓的「关系」是**文档之间的 depends/upstream 边**，已在 front-matter 与 `doclinks` 中显式表达，**不需要从文本里抽实体建图**。

## 3. 三种方案对照（针对本仓）

| 方案 | 内容 | 成本 | 收益 | 判定 |
|---|---|---|---|---|
| **甲 索引 + 元数据（推荐）** | 派生 `docs/INDEX.md`（由 front-matter 生成）+ 分层目录 README + 状态筛选脚本 | 低（一次性脚本 + 门禁一条） | 解决 §1.3 三个缺口；与既有 `derived-view` / `doc-status` 同范式 | ★ **先做** |
| **乙 向量 RAG** | 嵌入 + 向量库 + 分块 + 重嵌流水线 | 中高（新增长驻/依赖） | 语义召回；但本仓查询稀疏 | **暂缓**（违 ADR-0004 零常驻倾向） |
| **丙 知识图谱 / GraphRAG** | 实体抽取 + 建图 + 增量更新 | 高 | 多跳问答 | **否决**（无消费方） |

## 4. 建议

### 4.1 甲案的三件具体事（不新增文档种类）

1. **`docs/INDEX.md` 派生视图**：从 front-matter 的 `id/type/status/date` 生成表格，按目录分组；由脚本产出、门禁比对（复用 `derived-view` 的「逐字节比对」范式，禁止手工编辑）。
2. **目录级 README / 分层 `CLAUDE.md`**：`docs/`、`spec/`、`adr/` 各一份 20 行以内的目录表，说明「这里放什么、先读哪篇」；根 `CLAUDE.md` 只写"仓库里读不到的东西"（官方 best-practices 明确要求）。
3. **状态筛选**：`ops/` 加一个只读脚本（`ops/rpc_doc_index.py --type research --status todo`），扫 front-matter 输出清单；作为门禁 `doc-status` 的只读补充，不改真值。

> **执行记录（2026-11-03）**：三件已落地 —— ① `ops/rpc_doc_index.py`（`--write` / `--check` / `--type` / `--status` / `--dir`），登记为第 5 个入口（`inventory/ops.yaml`）；② `docs/INDEX.md` 已生成 **242 篇**（含无 front-matter 的文档，type 按顶层目录推断），`--check` 逐字节一致；③ 目录导航 `docs/README.md` / `spec/README.md` / `adr/README.md` 已落。门禁 `doclinks` 4,555 条失效 0、`md-tables` 新增 0、`scripts` 入口 5 未登记 0。

### 4.2 检索纪律（零成本，先立规矩）

| 场景 | 手段 |
|---|---|
| 找某事实/命令 | `Grep` 全文（8.8 MB 毫秒级） |
| 找某主题的权威文档 | `docs/research/README.md` 主题路由 |
| 找「谁引用了这篇」 | `doclinks` 反向索引（门禁已算出全部链接） |
| 找未决问题 | `OPEN-ISSUES.md` 台账（唯一真值） |
| 找活数据 | `TRACKER.md`（唯一真值） |

### 4.3 升级触发条件（写成判据，避免凭感觉）

满足**任一**再讨论 RAG（乙案）：

| 条件 | 阈值 | 现状 |
|---|---|---|
| 文档规模 | md 总数 > **1,500 篇** 或 体积 > **50 MB** | 343 篇 / 8.8 MB |
| 查询频次 | agent 检索类调用 > **每日 100 次** | 未计量（未做） |
| 跨仓检索 | 需同时检索 ≥ **5 个仓库**的文档 | 现为 10 个 ID 面，但不做文档检索 |
| 语义鸿沟 | 出现「关键词搜不到、但语义相关」的高频真实案例 > **每月 5 次** | 未收集 |

知识图谱（丙案）另加一条硬条件：**出现必须多跳才能回答的真实问题**（如"这次引擎升级影响了哪些 ADR、哪些 spec、哪些台账条目"），且无法用 front-matter 边 + 脚本回答。
