# 控制面 LAN 地址漂移 · 失效归因与判据升级

> **性质**：调研 / 归因（单一主题）· **建立日期**：2026-09-29 · **证据**：E1 = 本集群实测
> **触发**：C 站（seaviv）LAN 地址由 `192.168.1.37` 漂移到 `192.168.1.8`，导致 6 项门禁红灯、
> 明细**一律只报「可达 2/3 站」**（无根因）。
> **升级对象**：[ADR-0006 控制面传输绑定 LAN IPv4](../../adr/ADR-0006-控制面传输绑定LAN_IPv4.md)（本次升级为 v1.1）
> **结论**：**之前有管理方法**（ADR-0006 专门为这个问题设计），但它有**一个结构性射程漏洞**，
> 漏洞恰好落在最脆弱的 C 站上 ⇒ 「既无根治、也无兜底」。

## 2. 之前的管理方法（ADR-0006，2026-09-16）

四件套，**每一件都是为这个问题写的**：

| # | 内容 | 原文 |
|---|---|---|
| 1 | 三站 LAN 地址登记为**真值** | [net.yaml `lan:` 段](../../inventory/net.yaml#L93-L98) |
| 2 | 承认是 DHCP，**建议**路由器按 MAC 做保留 | [net.yaml L99-102](../../inventory/net.yaml#L99-L102)：*"建议在路由器按 MAC 做 DHCP 保留(固定 .32/.33/.37)以进一步稳定; **未做保留时靠上面那条门禁断言兜住漂移**"* |
| 3 | 门禁 `stations` 子项 (h)：`ssh -G <名>` 的 hostname 必须 == 真值 | [rpc_check.py L3982-4002](../../ops/rpc_check.py#L3982-L4002) |
| 4 | 维护约定：改地址同步 `net.yaml` / `~/.ssh/config` / `cluster.STATIONS` | [net.yaml L105](../../inventory/net.yaml#L105) |

**设计意图（写得很明确，且正是本次缺失的东西）**：net.yaml L91-92 ——
*"这是『控制面走哪条路』的唯一可断言点……却能把『DHCP 漂移 ⇒ 走公网 IPv6 + 每次多付 ~16s + 最终连不上』
变成一条明确的 FAIL"*，**「而不是『ssh 连不上』的谜题」**。

## 3. 为什么失效（4 条，逐条有实证）

### 3.1 ★★ 射程与风险错位：判据覆盖「有别名」的站，而漂移风险与「有没有别名」无关

[rpc_check.py L3990-3995](../../ops/rpc_check.py#L3990-L3995) 是要害：

```python
alias, want = ent.get("host"), ent.get("ip")
if not alias or not want:
    continue                    # 仅以 IP 直连的站(如 C) 无别名, 跳过
```

D4 的判据靠 `ssh -G <别名>` 展开。**A/B 有别名**（`scott-lau-NEX.local` / `-GTR-Pro.local`）⇒ 有断言；
**C 登记为 `host: null`**、注「一直以 IPv4 直连, 无名别名」⇒ **代码显式跳过**（注释里就点名了 C）。

⇒ C 是**唯一** `host: null` 的站，也**恰恰是**已漂过两次、且本次真的漂了的站。
**判据的射程恰好漏掉最需要它的那个站** —— 这不是实现 bug，是**设计时对"风险与射程正交性"的误判**。

### 3.2 ★ 失败形态退化成了设计者点名要避免的那个「谜题」

ADR-0006 D4 原文承诺把脆弱性变成 *"可检出的红灯"*、**不是** *"ssh 连不上的谜题"*。
实测结果是 6 项红灯**全部**只报 `可达 2/3 站`，根因要人肉去猜 —— **正是那个谜题本身**。

### 3.3 ★★ 「双覆盖」这个假设不成立（且它**掩盖**了 3.1）

ADR-0006 D4 原文（L80）：*"若站真的漂移，**既有的可达性判定也会同时 FAIL（双覆盖）**"*。
实测：可达性判定**确实** FAIL 了 —— 但它 ① **不提供根因**（只报"可达 2/3"）；
② 更糟的是它**让"第一覆盖对 C 完全失效"这件事看起来像"已经被覆盖了"**。
⇒ 一条**不诊断**的兜底，会掩盖另一条兜底的缺失。

### 3.4 ★★ 把「临时兜底」当成了长期方案，而兜底本身有洞

net.yaml L101-102 自述：*"**建议**在路由器按 MAC 做 DHCP 保留…… **未做保留时靠上面那条门禁断言兜住漂移**"*。
即：**推荐的根治没做，改用断言兜住**；而由 3.1，断言对 C 无效
⇒ **C 等于既无根治、也无兜底**。「建议」以散句形式存在 → 无 owner、无判据 → 自然永远不做。

### 3.5 与 ADR-0006 自设纪律的冲突

ADR-0007 转引 ADR-0006 的纪律（[ADR-0007 L45](../../adr/ADR-0007-证据流阶段推进路线与改动验证闭环.md#L45)）：
「**判据必须自证不静默降级**」。本次正是**静默降级**：
`stations` 断言把 C 记为「未计入判定」并**继续 PASS 其余部分**，全量门禁只以"可达 2/3"体现
⇒ **该判据对这档故障是"看起来在判、其实没判"**。

### 3.6 真值仍有多个定义点，登记不完整

`192.168.1.37` 分散在 `inventory/net.yaml`、`ops/cluster.py`、`ops/cluster_const.py`、
`docs/三机推理集群使用手册.md`（12 处）等；且 C 的 `iface` **至今是 `null`**
（本次实测为 `eno1`）—— 登记留空本身就是"没人真走这套维护流程"的证据。

## 4. 改进建议（根治 + 兜底，两层都要）

### A. 根治：站点侧把 C 钉死（**复议** ADR-0006 原「否决」项）

ADR-0006「考虑的替代方案」表**否决过**「在 station 侧把 LAN 改静态」，理由两条：
**① 远程改网络有失联风险；② 需与路由器 DHCP 池避让，易出地址冲突**。
本次升级的依据是**新证据**（不是重新讨论）：

| 原否决理由 | 新证据下的评估 |
|---|---|
| ① 失联风险 | ★ **已被 §1-#7 消解**：USB4 段提供了**不依赖 LAN** 的操作与恢复通道（本次已在真实故障中用它完成诊断与部署）。改法应是「**先经 USB4 起会话，再改 eno1**」，即可全程有退路 |
| ② 地址冲突 | ★ **理由成立，且 2026-09-29 实测确认为真障碍** ⇒ 见下「前置条件实测」 |

**★★ 前置条件实测：`.37` 在 DHCP 动态池内 ⇒ 「站上钉静态」单独做**不安全**（2026-09-29 判定）**

| 判定 | 证据（E1） |
|---|---|
| **`.37` 是 DHCP 服务器发出来的**（⇒ 在池内） | C 站 NM 日志：`9月 28 22:26:09 dhcp4 (eno1): state changed new lease, address=192.168.1.37`；服务器标识 `dhcp_server_identifier = 192.168.1.1` |
| **`.37` 未被 MAC 保留** | 同一台机器、同一块网卡（`eno1`）本次重租拿到的是 **`.8`**，不是 `.37` ⇒ 路由器没为它保留 |
| `.37` **此刻空闲** | C 侧 ARP `192.168.1.37 FAILED`；主控与 B 均 ping/ssh 不通 |
| 池的**低位区在发** | 同时段在用的低位地址 `.2` / `.5` / `.8`（C 侧 ARP）⇒ 池大概自 `.2` 或 `.10` 起，`.37` 落在里面很自然 |

⇒ **A2（站上 `manual` 静态）单独做会制造真实的冲突窗口**：C 的 `.37` 租约已在 `01:39:12` 被
`canceled` / `no lease` 释放，在路由器看来 `.37` 重新可发；C 若私自钉静态，别的设备随时可能被分到 `.37`
（ND 的 `acd` 只在**冲突已发生**时拒绝，**不能阻止别人先拿到**）。

**决策取向（2026-09-29 修订）**：
- **A1 优先** —— 路由器按 MAC 保留 `.37`（ADR-0006 原文即称"最干净"）；或
- **收缩/排除池**把 `.37` 划出去之后，再做 A2。
- 范围仍是**只动 C**（唯一 `host: null`、已漂 2 次、最脆弱）；A/B 维持 DHCP 不动。
- ⚠ 本节早先把 A2 排在前面，是基于"`.37` 可能不在池内"的**未验证假设** —— 现已被实测推翻，
  这也**反向印证了 ADR-0006 原文第②条否决理由是对的**。

**池的精确起止界仍需路由器凭据才能读出** —— 上述是**间接但决定性**的证据链，不是从路由器配置直接读的
（该局限已登记进 ADR-0006 v1.1 的未实测登记）。

### B. 兜底：把判据从「别名」改成「站上实况 + USB4 降级通道」（**必须做**）—— ✅ **已落体 2026-09-29**

> 落体记录与验收（V8–V13）见 [ADR-0006 §实施记录 v1.2](../../adr/ADR-0006-控制面传输绑定LAN_IPv4.md#L232-L258)。
> ★ 落体时**射程扩到主控自身**：现场实测主控自己整段换网（`.1` → `.10`）⇒ "三站全部不可达"，
> 判据已能报出该根因（见 §1 的补记）。

- **B1 ★★ USB4 漂移探针**：`10.10.x` 是**稳定且在射程内**的通道。经它读目标站的 `ip -4 -o addr`，
  与 net.yaml §lan 真值比对 ⇒ **不依赖 `~/.ssh/config` 别名**、三站全覆盖、
  且**在 LAN 已断的情况下仍能查出根因**（正是本次缺的那一环）。
- **B2 把「谜题」降级成「红灯」**：LAN 不通时先问它"你的 LAN IP 现在是多少"，
  不符就报 `C 站 LAN 已漂移 .37 → .8（DHCP），请更新 net.yaml §lan / cluster.STATIONS / ~/.ssh/config`
  —— 而不是只写 `可达 2/3 站`。
- **B3 补齐登记**：C 的 `iface` 填实测 `eno1`；并补一条「`cluster.STATIONS` == net.yaml §lan」的断言
  （现在只有 `~/.ssh/config` 那半条被覆盖）。

### C. 治理：把「建议」升格为有主的登记项

net.yaml 的 `dhcp:` 段把"路由器 MAC 保留"从散句改为**带 owner 与判据的待办**；
同时收敛真值定义点（由 net.yaml 派生后两个消费者，或断言三者一致）。
