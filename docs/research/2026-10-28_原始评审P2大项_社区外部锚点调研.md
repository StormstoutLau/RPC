## 1. 审查基线（E1 实测）

### 1.1 #5：`set -euo pipefail` 的现状

**原文（E2）**：「部署脚本普遍不开 `set -e`，关键写操作失败后继续」；192 个 `.sh` 仅 15 个启用；站上主执行件 `infer-load` 是 `set -uo pipefail`，`llama-serve-instance`/`rpc-serve-instance`/`cluster-ttl` 是 `set -u`；`sudo tee "$CONF"` 失败仍打印「conf 生成」。

**当前 HEAD 事实**：

| 指标 | 实测 |
|---|---|
| 仓内跟踪 `.sh`（不含 `archive/`） | **195** |
| 其中前 25 行含 `set -e` | **15**（≈7.7%） |
| 站上运行/入口执行面（本项合理射程） | **11 个 shell 执行件 + 2 个被 `source` 的库** |

**站上执行件逐个现状**（`ops/station-bin/` + `ops/rpc-nodes`）：

| 文件 | 现 prologue | 失败容忍构造（个数） | 备注 |
|---|---|---|---|
| `infer-load` | `set -uo pipefail` | `\|\| true` ×19 · `if !` ×1 · `rc=$?` ×1 | 最大件（604 行），含远端 ssh 与 sudo 写 conf |
| `infer-unload` | `set -uo pipefail` | `\|\| true` ×10 | |
| `infer-list` | **无** | `\|\| true` ×1 | 174 行；远端 ssh 扫描 |
| `llama-serve-instance` | `set -u` | `\|\| true` ×1 | systemd 包装器 |
| `rpc-serve-instance` | `set -u` | 0 | systemd 包装器 |
| `load-gate` | **`set +e`（有意）** | 0（但大量"取不到就记 0"的赋值） | 四条规则必须**全部跑完**再给结论 ⇒ 不能 abort |
| `load-mem-gate` | **无** | 0 | 纯算术门 |
| `wait-gtt-release` | **无** | 0 | 轮询等待 |
| `conf-get` | `set -uo pipefail` | `\|\| true` ×1 | 薄壳 CLI |
| `rpc-nodes` | `set -u` | 0 | RPC 节点启停 |
| `cluster-watchdog` | **无** | 0 | root oneshot，`sudo mkdir/chown` |

**两个库**（`model-locate.sh`、`conf-lib.sh`）被 `infer-load` / `infer-list` **source**：二者**没有** `set` 行，且**不应有**——库改调用方 shell 选项属于跨层副作用。

**现有静态网**：

- `rpc_check` 的 `syntax` 对全部 `.sh` 跑 `bash -n`（Git Bash + Linux 靶双判）——**只判语法，不判"失败是否被吞"**。
- CI 的 `shellcheck --severity=error` 只覆盖 12 个活跃件（见 `.github/workflows/ci.yml`），**不含** `cluster-watchdog`；`--severity=error` 也报不出"失败被吞"这类警告级问题。
- **没有**任何断言检查脚本的 prologue 或错误处置方式。

**为什么不能机械插入**（E3 锚点见 §2）：

- `set -e` 在 `if`/`&&`/`||`/`!`/循环条件、**管道非末命令**、**命令替换**里都**不生效**（bash 手册；ShellCheck SC2310/SC2311）。
- `load-gate` 的 `set +e` 是**设计**：它要把"不可达 / 额度不足 / 已占用 / loadavg"四条都读完再给 `[ABORT]`/`[OK]`；开 `-e` 会让第一条失败就直接退出、结论缺失。
- `infer-list` 里 `rssm=$(ps … | grep … | awk …)` 这类形态：`grep` 无命中即 rc=1，`pipefail`+`set -e` 会**中止**，而业务上"没有进程"是正常态 ⇒ 必须逐个改写成 `|| true` / `if !` / `|| echo 0`。
- `infer-load` 已有 19 处 `|| true`，说明作者早就按"失败可容忍"逐条标注过——这既是**迁移线索**，也说明**不能一把梭**。

## 3. 逐项分析

### 3.1 #5：不是"扫荡"，是"默认严格 + 逐条豁免"

**分层**（这是与原文「统一 `set -euo pipefail`」的**唯一分歧**）：

1. **执行件**（11 个）：默认 `set -euo pipefail`；**允许**显式豁免并在文件头写明理由（如 `load-gate` 保留 `set +e`，但必须补"为什么不能 abort"与"失败如何进入结论"）。
2. **被 `source` 的库**（2 个）：**禁止**任何 `set` 行（不得改调用方选项）——现状已正确，本批只需**钉住**。
3. **Python**（`cluster-ttl`）：不在本项射程。

**每条豁免都必须可机判**：新增门禁 `shell-strict`（或扩 `syntax`），断言：

- 11 个执行件的 prologue ∈ {`set -euo pipefail`, 显式豁免枚举}；
- 2 个库**不含** `set -[eux]`；
- 豁免表**防腐化**：某条豁免若已不再需要（例如后来补了 `|| true`），门禁自报「已可移除」（同 `SECRET_ALLOW`/`cluster_lazy_allow` 的既有纪律）。

**为什么先做这一层就够**：原文的实质风险是「关键写操作失败后继续」——落在 `infer-load` 写 conf、`cluster-watchdog` 的 `sudo mkdir/chown` 两处。`-u`/`pipefail` 已在多数件上；补 `-e` 的收益集中在这两个写路径，**不需要**去动 192 个冻结件。

**风险**：`set -e` 会**改变**现有"失败后继续"的行为——凡当前靠"命令失败但脚本继续"工作的路径都会**当场变红**。这正是本项需要**先验红**（在站上或 Git Bash 里跑注入用例）的原因。

### 3.2 #8：三刀，风险递增；顺序由依赖面决定

| 刀 | 对象 | 真实成本 | 建议 |
|---|---|---|---|
| **8A** | `station-bin` 分层：`_*` 173 件 → `probes/`（或 `archive/station-bin-probes/`） | 24 个文件的交叉引用 + `ops.yaml` 192 条登记 + 4 处路径常量 + README/文档链接 | **先做**：纯搬运、可逐文件回滚；且必须先修 `agent-cli.ps1` L473/L517 的 `D:\RPC` 硬编码 |
| **8B** | `rpc_check.py` → `rpc_check_<domain>.py` + 门面 | 50 个 `fn` 对象 + 43 个测试 + 180 个符号 + `scripts`/`deps` 登记 + 6 类"扫文本"门禁的扫描清单 | **次做**：有 62 个测试当安全网；门面重导出后调用方零改动 |
| **8C** | `agent-cli.ps1` → 入口 + `. lib/*.ps1` | 12 个测试 + 24 处 `rpc_check` 引用 + **55 处文档行号** + 两个 AST 夹具（663 条黄金断言） | **最后做或另立**：夹具必须改成"多文件拼接"，否则**静默空转**；这是全批最高风险点 |

**8B 的模块边界（来自 58 个段标记，E4 待 Step 2 定稿）**：纯判据层（U-1/U-4/U-5、D7 三信封与状态机、命名空间/方言）与检查器层（`check_*` + `CHECKS`）分开；`CHECKS` 留在入口，`fn` 从各模块导入。

**8A 的命名与部署语义**：站上只部署 `station_runtime` 27 项里真正被 systemd/入口调起的部分；`probes/` 不出仓、不上站。**不要**把 `_fm_golden_test.ps1` / `_probe_fallback.ps1` / `_runstamp_hammer.ps1` 当作"探针"移走——它们是**在跑的门禁夹具**（`rpc_check` 三项 CHECKS 直接调用），移动会改 4 处常量与 172 处文档引用，收益低。**建议原地保留**，只移"一次性 `_a*`/`_b*`/`_qwen27_*`/`_vllcpp*` 等"。

**拆分后的行数契约（需在 DESIGN 裁定）**：本仓无行数门禁；若设，建议**单文件 ≤2000 行**（不是 800——8B 的单一域仍会超 800，硬套会导致为凑数而切碎人工边界），并把"新增文件必须登记 + 层序"沿用 `cluster_layers` 的既有机制。

## 4. 可迁移 / 不可照搬总表

| 外部做法 | 迁移 | 不照搬的理由 |
|---|---|---|
| 全仓 `set -euo pipefail` | 只对 11 个执行件；库禁止 | 冻结件不在运行路径；库改调用方选项是跨层副作用 |
| `set -e` 当异常模型 | ❌ | 条件/管道/命令替换内失效（SC2310/SC2311） |
| 800 行硬上限 | ⚠️ 改为 2000 行或"按域" | 单一域（D7 判据）天然超 800；硬切会破坏人工段边界 |
| PowerShell `.psm1` 模块 | ⚠️ 用 dot-source | PS 5.1 + 无模块路径依赖；且夹具按文件解析 |
| 物理分层 = 全部 173 件都搬 | ⚠️ 只搬一次性件 | 4 个夹具是门禁在跑的件，搬了要改 4 处常量 + 大量文档 |
| 先测后搬 / 门面代理 / 一刀一提交 | ✅ 全部沿用 | 2026-09-23 已用同一套并抓到两个真缺陷 |

## 5. 结论与优先级

1. **#5 可独立交付**：11 个执行件的 prologue 收敛 + 2 个库钉住 + 一条 `shell-strict` 门禁；改动集中、可用"注入失败"先验红。**建议先做**。
2. **#8 必须分期**：8A（探针分层，机械）→ 8B（`rpc_check` 拆分，有测试网）→ 8C（`agent-cli` 拆分，夹具风险最高，建议单独立项或明确"不做"并记录理由）。
3. **两项都遵守既有纪律**：先补/复用特征测试 → 一刀一提交 → 门面重导出 → **搬家后同步所有"扫文本"门禁的清单**（否则静默降级成假绿）→ 漏导入 AST 检查 + 实跑。
