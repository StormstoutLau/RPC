## 0. 结论前置（先看这五句）

1. ★★ **现状不是「边没排序」，而是「边没有执行语义，且产物没有传输通道」** —— 卡面 `needs=` 已被解析并做完整性校验（悬空 / 歧义 / 自指 / 环），但派发循环**完全不读 `needs`**；`join.json.needs_graph` 逐字标「派生非真值 / 仅观测用」。
2. ★★ **只加「拓扑排序派发」不会让依赖成立**：分片跑在三台互不可见的站上，`split` 的合并产物 `merged-output.txt` 是**各子进程 stdout 的拼接**（不是片产物）；分片卡也**不继承** `evidence-manifest` ⇒ 片的 `out/` 产物**从未被回收**。⇒ 「片 i 的输出作为片 j 的输入」缺的是**搬运**，不是排序。
3. ★★ **「总片数 ≤ 站数」这个准入判据在外部九个系统里没有对应物** —— Airflow pool / Argo `parallelism` / Slurm `%` / GHA `max-parallel` / Make `-j` / Ninja `-j` / Bazel `--jobs` 一律是**闸门 + 排队**，**没有任何系统因「图节点数 > worker 数」拒绝整张图**。⇒ 三层串行链被 `SPLIT_INFEASIBLE` 判死，是**本仓特有**的误判。
4. ★★ **建议顺序 = 先乙（fail-closed 拒执行）、再甲1（拓扑波次 + 层宽判据）、最后甲2（片产物搬运）** —— 乙把「声明了却忽略」变成**响亮拒绝**（零执行风险）；甲1 单独落地只是「顺序剧场」（无产物可传）；甲2 才是让依赖**真正成立**的那一刀。**不得**把甲1 报成「依赖边已可执行」。
5. ★★ **「仅排序」与「数据依赖」在外部是两种一等公民边**（Make `|` / Ninja `||` / Prefect `wait_for` / Argo `dependencies` 均只排序不传数据）——**但本仓只落数据依赖这一半**：全仓仅 1 张真卡使用 `needs=`，其本意就是数据依赖；`after=`（仅排序）本批不做、已登记（§6-7 / §8）。失败传播固定 `all_success` 有十系统锚点（§9）。

## 1. 本仓现状（E1 读码，2026-10-31）

### 1.1 已经有的三件

| 件 | 落点（函数名，不写行号） | 做到什么 | 没做到什么 |
|---|---|---|---|
| 卡面解析 | `Expand-DecomposeSubject`（[agent-cli.ps1](../../ops/station-bin/agent-cli.ps1)） | 剥 `subject=` / `needs=` 前缀（可任意顺序、同键只解析一次）；旧语法逐字不变 | 不推断语义、不做归一 |
| 完整性校验 | `Resolve-SplitNeeds`（同上） | 悬空 / 歧义 / 自指 / 环（Kahn）四类坏声明 ⇒ `SPLIT_NEEDS_FAIL` exit 2，**早于模型解析与任何 `Start-Process`** | **不排波次、不阻断、不传产物**（注释逐字「对执行零影响」） |
| 声明式汇聚 | `Resolve-SplitJoin`（同上） | `subject` 分组 + `undeclared` fail-closed；`join.json` 落盘 | 只到**声明层**；不合并片产物（见 §1.4） |

### 1.2 派发路径：`needs` 完全不参与

`Invoke-SplitTask` 的实际顺序（函数体内即可核对）：

1. 解析 `decompose:` ⇒ `$decls` ⇒ `Resolve-SplitNeeds`（只校验）；
2. `Resolve-Model` / 敏感度闸 / `readonly` 闸；
3. `Get-SplitDispatchPlan -ShardCount <总片数>` ⇒ `$plan.assignments`（round-robin）；
4. `for` 循环**一次性** `Start-Process` 全部子卡 ⇒ `WaitForExit` 全部；
5. 合并段：`merged-output.txt` + `join.json`。

⇒ 第 3、4 步的输入里**没有 `needs`**。`needs` 只活在第 1 步与第 5 步（写进 `join.json.needs_graph`）。

### 1.3 容量判据：判的是总片数

`Get-SplitDispatchPlan` 的 `ok = (ShardCount <= StationPool.Count * LegsPerStation)`；`Invoke-SplitTask` 据此打 `SPLIT_INFEASIBLE` exit 18。
⇒ 一条 `#1 → #2 → #3` 的串行链（层宽 1、共 3 片）与「3 片无依赖」**得到同一个结论**：能否跑取决于总片数，而不是**单层最大宽度**。

### 1.4 产物通道：缺的不是排序，是搬运（本调研的**关键新发现**）

| 事实 | 证据 | 后果 |
|---|---|---|
| 合并件 = 子进程 stdout | `Invoke-SplitTask` 合并段把 `shard$i.log` 全文写进 `merged-output.txt` | 「汇聚」是**日志拼接**，不是片产物归并 |
| 分片卡不继承 `evidence-manifest` | 子卡 front-matter 只复制 `model/sensitivity/readonly/timeout-s/accept/accept-golden/cli/complexity/task-type/isolate-xdg`；`evidence-manifest` 不在其中 | 片的 `out/` 声明件**没有任何回收触发点**（`Invoke-EvmStatePull` 只被单任务 collect 调用） |
| 结论契约 §6.2-2 写「归并对象 = 各片 runDir 的产物 + 结论」 | [D7-PROTOCOL-CONCLUSION-CONTRACT.md §6.2](../../spec/d6-agent-standard/D7-PROTOCOL-CONCLUSION-CONTRACT.md) | **该条尚未落实**：当前没有「各片 runDir 产物」进入合并面 |

⇒ 即使把 `needs` 变成拓扑波次，片 j 也**拿不到**片 i 的输出：两片不在同一台站、不共享工作区，主控也没有回收片的产物。**依赖要成立，必须新增一条「片产物 → 依赖片输入」的搬运链**。

### 1.5 对 `O-184` 三个前提的就地更正

| # | `O-184` 原文 | 读码结论 | 处置 |
|---|---|---|---|
| ① | 甲案「环检测复用 `rpc_check._validate_graph`」 | `_validate_graph` 的输入形状是 `CHECKS` 的 `{id, needs[]}`，校验「未知 id / 成环」；**不能直接喂分片行**（键名与语义不同） | **只复用形态**（纯函数 + 正反注入夹具），**不直接调用** |

| ③ | 台账「汇聚已补」 | 补的是**声明层**汇聚（`subject` 分组 / `undeclared`）；片产物未进合并面 | 措辞收窄为「**声明层汇聚已补**；产物层汇聚未做」 |

## 2. 外部锚点（九个系统，官方文档级）

> **取证口径**：只取官方文档；`Prefect` 的「结果持久化/缓存」语义**未核实**，已在表中标注。

| 系统 | 依赖声明 | 并发上限语义 | 上游失败时下游 | 节点间产物传递 | 恢复 / 幂等 |
|---|---|---|---|---|---|
| **Airflow** | `>>` / `set_upstream`；`trigger_rule` 默认 `all_success` | pool（默认 128 slot）与 `max_active_tasks` **满则排队** | 默认 `upstream_failed` / 跳过；可配 `one_failed` / `all_done` | XCom 仅小元数据；大数据须对象存储 | retries；重试清 XCom 保幂等 |
| **Temporal** | 代码内 Activity / Child Workflow 调用（无声明式图），须确定性 | Task Queue；worker 有空闲才 poll，**不拒绝图** | Activity 按 retry policy；Workflow 错误入事件历史 | 结果进 Event History（小数据）；大文件走外部存储 | Event History **重放恢复**（determinism） |
| **Prefect** | future 作为入参即隐式建边 | `max_workers` / GlobalConcurrencyLimit 限流，超出排队 | 下游不运行；`.result()` 抛出 | future 返回值直接作参数；官方建议大数据传引用 | retries；缓存/持久化语义**未核实** |
| **Dask / distributed** | task graph / `delayed`（HLG） | worker 数只影响并行度，**图无上限** | 依赖链失败，可重算 | **worker 间 TCP 直传** bulk data | 纯函数重算 + 结果缓存 |
| **Argo Workflows** | DAG `dependencies`；`depends` 表达式（`.Succeeded/.Failed`）；`when` | controller/namespace `parallelism` **排队**；模板 semaphore 限流 | 默认 failFast：不调度新任务，DAG failed | `outputs.artifacts` → `inputs.artifacts`（需 artifact repository） | `retryStrategy`（limit/policy/backoff） |
| **GitHub Actions** | `needs` | matrix `max-parallel` 限同时；job 数不限 | fail/skip **沿 `needs` 链全部跳过**（除非 `if: always()`） | upload/download-artifact（同一 run） | 重跑 job/run；artifact 复用 |
| **GNU Make** | prerequisites | `-j N` 限同时；**图 > N 分批，不拒绝** | 默认首错即停 | 同机文件路径/时间戳 | 时间戳 + 重跑（无内建幂等） |
| **Ninja** | build 语句 explicit/implicit deps | `-j N`；pool depth 限流 | 默认 `-k 1` 首错即停 | 同机文件路径 | `.ninja_log` + 命令/时间戳增量 |
| **Bazel** | `BUILD` 的 `srcs/deps` ⇒ action graph | `--jobs` 限同时；**图大不拒绝** | 失败 action ⇒ 构建失败，下游不执行 | action 输出文件 + 内容哈希；sandbox / remote cache | 内容寻址缓存 + 远端执行；hermetic 输入保可复现 |
| **Slurm** | `--dependency=afterok:<jobid>`（默认 `afterany`） | 未满足 ⇒ `PENDING` **排队**；数组作业 `%4` 限同时 | 依赖失败 ⇒ 下游**永不运行**；`--kill-on-invalid-dep=yes` 才取消 | 共享文件系统（官方称除脚本外不搬文件） | requeue / 重提交；幂等靠脚本自身 |

### 2.1 直接回答一个问题

**有没有任何一个系统会因为「链长 N > worker 数」而拒绝整张图？——没有。**

- GHA 官方称 job 数不限（仅受用量限额）；matrix 只限**同时**并发，其余排队。
- Airflow pool 满后 runnable task 变 queued；Argo 在 controller `parallelism` 下工作流**排队**。
- Slurm 依赖未满足保持 `PENDING`；Dask 图随提交持续增长；Temporal worker 只在有空闲容量时 poll。
- Make / Ninja / Bazel：`-j` / `--jobs` 是**同时在飞数**，不是**图规模上限**。

⇒ 外部共识 = **「图形态」与「并发预算」正交**。本仓把两者压进同一个 `ok`，是判据层面的错配。

### 2.2 另一个反面教材（必须记）

GNU Make 对环依赖**不是**硬错误：官方输出 `Circular xxx <- yyy dependency dropped` —— **警告后丢边继续**。本仓已用 Kahn 判环并 exit 2（`Resolve-SplitNeeds`），**这个口径是对的**，不要因为「Make 也这么做」而回退。

## 3. 可迁移 / 不可照搬

### 3.1 可迁移（5 条）

| # | 机制 | 来源 | 本仓落点 |
|---|---|---|---|
| M1 | **依赖即准入**：边不只画出来，必须决定「能不能跑、按什么顺序跑」 | Argo / GHA / Slurm | 乙（拒执行）→ 甲1（波次） |
| M2 | **并发是闸门不是准入**：超预算排队，不因图大拒绝 | Airflow pool / Argo `parallelism` / Slurm `%` | 容量判据从「总片数」改为「**单层最大宽度**」 |
| M3 | **失败传播显式化**：默认 `all_success`，上游失败 ⇒ 下游跳过，不许拿空输入硬跑 | Airflow / GHA / Argo | 甲1 的波次调度：某片非 0 ⇒ 依赖它的片**不派发**，报告 `SPLIT_SKIPPED` |
| M4 | **只传句柄/声明，不传内容**：依赖声明只指「哪一 subject / 哪个件」，大产物落站上或主控目录 | XCom / Argo artifacts / Dask | 甲2 用 `evidence-manifest` 的 `state`/`path` 白名单（既有 `Invoke-EvmStatePull`） |

### 3.2 不可照搬（3 条）

| # | 机制 | 来源 | 为什么不能抄 |
|---|---|---|---|
| N1 | 常驻调度器 + 中心元数据库 | Airflow scheduler / Temporal Service | 直接违反 ADR-0004「零自加载 · 无 daemon」 |

## 6. 未实测登记

1. **跨站产物搬运的真实成本与失败形态未测**：主控 → 站 A 回收 → 站 B 注入，两步 scp 的时延与「站间不可达 / 摘要不符 / 目标目录不可写」的处置尚未有真站读数。
2. **波次调度的墙钟收益未测**：串行链（层宽 1）与无依赖链（层宽 N）的墙钟差、以及波次间主控开销（回收 + 注入 + 再派发）是否会吃掉并行收益，没有实测。
3. **`needs` 的语义边界未裁**：本调研把 `needs` 读作「**数据依赖**」（故乙要拒）；2026-10-16 原方案写的是「声明的血缘/读序，对执行零影响」。两者**互斥**，乙落地即撤销旧语义 —— 该撤销须在 DESIGN 里明写并由用户确认。★ **2026-10-31 已补外部证据与存量用法核查（§8）**：结论支持「`needs=` = 数据依赖」；「仅排序」是外部一等公民，但本仓只落这一半（见 #7）。
4. **失败传播的策略未裁**：外部有 `all_success` / `one_failed` / `all_done` 多档；本仓是否需要可配置，还是固定 `all_success`（固定更简单、但少一种用法），未定。★ **2026-10-31 已补十系统触发规则清单（§9）**：默认压倒性 `all_success`，固定它足够；可配置留给「收尾/汇总片」（本仓无此类型，见 #8）。
5. **层宽判据的上界来源未复核**：容量沿用 `Get-SplitDispatchPlan` 的「站 × 腿」，腿仍为 1；层宽放宽后是否会诱导写出更宽的图（进而挤占出网配额），未测。
6. **`_validate_graph` 的「复用」口径**：本调研只确认它**不能直接喂分片行**；若日后抽公共 DAG 校验，须另立条目，不在本批。
7. **`after=`（仅排序边）未实现**：外部（Make `|` / Ninja `||` / Prefect `wait_for` / Argo `dependencies`）把「仅排序」当一等公民；本仓 `needs=` 只承载**数据依赖** ⇒ 「只想排序、无产物可传」的需求**当前无表达方式**。出现真实用例再单独立项（§8.3）。
8. **失败传播可配置未做**：`all_done` / `afterany` 类策略只对「无论如何都要跑」的**收尾/汇总节点**有意义；本仓 `split` 无该节点类型，故固定 `all_success`。若日后新增汇总片/清理片，须复核（§9.3）。

## 8. 补充调研（S1 · 2026-10-31）：`needs=` 该是「数据依赖」还是「仅排序」？

> **来由**：DESIGN §1.3 的 S1 要把 2026-10-16「零影响」口径撤销。用户要求补调研，以确认这个改判**是否过窄**（外部有没有「仅排序」这种边）。

### 8.1 外部：两种边在多数系统里是**一等公民**

| 系统 | 「仅排序」边 | 「数据」边 | 关键口径（官方原文） |
|---|---|---|---|
| GNU Make | **order-only prerequisites**（`target: normal \| order-only`） | 普通 prerequisite（同时管顺序与重建） | order-only「are never checked when determining if the target is out of date」；同一文件两种声明时**普通优先** |
| Ninja | **order-only（`\|\|`）** | explicit / implicit | 三类「subtly different」：order-only 过期时先建上游，但**上游自身变化不触发下游重建** |
| Prefect | **`wait_for`** | future/result 作参数（隐式数据边） | `wait_for` 用于 "tasks that **do not share data dependencies**" |
| Airflow | **`>>` / `set_upstream`**（任务默认 isolated） | XCom（小数据）/ 外部存储 | 跨任务数据「must be passed via XCom」；XCom "only designed for small amounts of data" |
| Argo | **`dependencies`**（可完全不传 artifacts；diamond 示例即如此） | `inputs/outputs.artifacts`（独立机制） | 两者**正交**，`from: "{{tasks.X.outputs.artifacts.Y}}"` 才传件 |
| Bazel / Dask | **没有**仅排序边 | 唯一形态：action 输入=上游输出 / task 按 key 取上游产出 | Bazel action「has declared inputs and output filenames」；Dask 依赖即数据流边 |
| Slurm | **`afterok`**（只约束状态） | 共享文件系统（非系统搬运） | 官方：除批处理脚本外「Slurm does no movement of user files」 |

⇒ **结论**：外部确实把两类边分开；**没有任何主流系统把「原本零影响的声明」直接改判为数据依赖** —— 它们的做法是**新增边类型/参数**。

### 8.2 但本仓情形与外部**不完全同构**（关键差异）

| 维度 | 外部系统 | 本仓 |
|---|---|---|
| 旧边语义 | Make/Ninja 的普通依赖**本来就排序**；Argo `dependencies` **本来就阻塞** | `needs=` 的旧语义是「**对执行零影响**」= **什么都不做** |
| 「新增一种边」是否可行 | 可行：旧边已提供排序，新边补数据 | 若把 `needs=` 留作「仅排序」，它仍**不排序** ⇒ **假图原样保留**；要让它排序，等于还是要改旧边语义 |
| 存量用法 | 大量真实 `order-only` / `wait_for` 用例 | **全仓仅 1 张真卡**：`spec/d6-agent-standard/dogfood-cards/needs-decl-probe.md`（片2 `needs=路由层`，任务要求「说明缓存层与路由层的关系」）⇒ **其本意就是依赖上游内容**；其余命中都是文档论述，不是卡面使用 |

### 8.3 结论（S1）

1. **采纳「`needs=` = 数据依赖」**（上游必须成功 + 产物可传；回收 0 件 ⇒ 响亮失败）。
2. **不新增 `after=`（仅排序边）**：外部是一等公民，但本仓**无真实用例**；新增关键字会引入双语义夹具与误用面。登记为 §6-7，出现真实卡再立项。
3. **为什么不照搬「保留旧语义 + 加 `needs_data=`」**：旧语义「零影响」正是 `O-184` 要治的病；保留它 = 保留假图。而外部能「加新类型不动旧类型」，前提是旧类型**已有排序语义** —— 本仓旧类型**没有**，不是同一情形（§8.2）。
4. **改判风险的缓解**：① 乙期**先拒执行**（不静默改行为，声明者立刻看到 `SPLIT_NEEDS_UNSUPPORTED`）；② 存量唯一样例本就是数据依赖；③ 卡面文档与日志逐字写「`needs=` = 数据依赖」；④ 若日后出现「只想排序」的真实卡，再按 §8.3-2 立项。

## 9. 补充调研（S2 · 2026-10-31）：失败传播固定 `all_success` 够不够？

### 9.1 十系统默认值与可配置面

| 系统 | 默认（上游失败 ⇒ 下游） | 可配置 / 其它状态 |
|---|---|---|
| Airflow | `trigger_rule=all_success` ⇒ 下游 `upstream_failed`（**独立状态**） | 11 档规则：`all_failed` / `all_done` / `one_success` / `one_failed` / `one_done` / `none_failed` / `none_failed_min_one_success` / `none_skipped` / `always` 等；`skipped` 只用于**主动**跳过 |
| Argo | 默认 `failFast`：不再调度新节点，DAG failed | `failFast:false` 全跑；`depends` 支持 `.Succeeded/.Failed/.Errored/.Skipped/.Omitted/.Daemoned` 与 `&& \|\| !`；`when:false` ⇒ `Skipped`，`depends` 不满足 ⇒ `Omitted`。★ 缺省 depends 约等于 `Succeeded\|\|Skipped\|\|Daemoned` ⇒ **Skipped 上游放行下游**（例外，见 9.2-4） |
| GitHub Actions | `needs` 要求上游成功；失败/跳过 ⇒ 下游**整链跳过** | `if: always()` / `failure()` / `cancelled()` 可放行；skipped job 的 `conclusion=skipped` |
| GNU Make | 首错即停，返回非 0；失败目标的下游不重建 | `-k/--keep-going` 继续**无关分支**，最终仍非 0 |
| Ninja | `-k 1`（首错即停）；失败边下游因缺产物不执行 | `-k N` / `-k 0`（无限）只放行无关分支 |
| Bazel | 遇首错即停；失败 action 的下游不执行 | `--keep-going` **只构建先决条件已成功的目标**，最终仍失败 |
| Temporal | Activity 失败默认冒出 ⇒ 后续 Activity 不执行 | `try/catch` 是一等机制（代码层） |
| Prefect | 任一输入 failed ⇒ 下游 run 不启动 | `allow_failure` 注解显式接收失败输入 |
| Dask | 依赖 erred future ⇒ 下游同样 err | 无图级放行开关 |
| Slurm | `afterok` 要求上游 exit 0 | `afterany`（任意终止即放行）/ `afternotok`（仅失败放行）；永不满足 ⇒ 下游**永久 PENDING**（`DependencyNeverSatisfied`），`--kill-on-invalid-dep=yes` 才转 CANCELLED |

### 9.2 三条硬结论

1. **默认值压倒性 `all_success` / failFast**（Airflow、GHA、Make、Ninja、Bazel、Slurm `afterok`、Temporal、Prefect、Dask）。⇒ 固定 `all_success` 不是「偷懒」，是**与外部主流一致**。
2. **「跳过」与「失败」必须分开表示**：Airflow 用 `upstream_failed`（不是 `skipped`），Argo 分 `Skipped`/`Omitted`，GHA `conclusion=skipped`。混同会污染汇总与通知（本仓已有同族教训：`O-149` 的假绿形态）。
3. **`all_done` / `afterany` 只服务「无论如何都要跑」的节点**（清理、汇总、通知），**不宜作产物依赖的默认** —— 对本仓「下游必须拿到上游产物」的片，固定 `all_success` **足够且安全**。
4. ⚠ **Argo 的 Skipped 放行不适用**：那是「**分支主动跳过**」的语义（`when:false`）；本仓的 `SPLIT_SKIPPED` **只由上游失败引起**，不是分支裁剪 ⇒ **不得**让 skipped 满足下游依赖。

### 9.3 结论（S2）

1. **固定 `all_success`**（上游非 0 ⇒ 下游不派发）。
2. **必须落实**：`SPLIT_SKIPPED` 单独日志行 + `join.json.skipped[]` + 「`join.status` 不因 skip 变 `ok`」+ 整体退出码非 0；**不得**把 skipped 读成「通过」（对应 §9.2-2）。
3. **可配置策略（`all_done` 等）不做**：本仓 `split` 的片全是**只读任务**，没有「收尾/汇总片」类型；登记 §6-8。若日后要做「无论如何都汇总」，正确做法是**新增节点类型**（属 join 语义扩展），而不是给依赖边加策略开关。
