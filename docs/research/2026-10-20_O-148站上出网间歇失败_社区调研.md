## 3. 结论：有没有根治方案？（与本仓既有裁的关系）

**候选四条**，两条**已被本仓否掉**（理由仍成立），两条**活着**：

| 候选 | 判读 |
|---|---|
| ~~改路由器 DNS 上游 / 全局 DoH~~ | ❌ **已否**（台账理由②）：会**破坏 `.local`** 站名解析（`net.yaml` / `ssh` 依赖） |
| ~~站上钉静态 IP（hosts / `--resolve`）~~ | ❌ **已否**（理由③）：**冻结 Cloudflare 地址**、需人工维护，脆弱 |
| **① 站上按域名走加密解析（常驻）** | ✅ **活着的根治候选，且端点已实测可达**（见 §4-B）：`resolvectl` 对 `~openrouter.ai`（及同类出网域）单独指定 **DoT 上游**（`1.1.1.1#cloudflare-dns.com` ⇒ ★ **853 从本 LAN 实测可达**）⇒ **不再依赖 `192.168.10.1` 那一跳的明文答案**；用 **`~` 域名路由** ⇒ **不碰 `.local`**（与 `C2`/`C3` 同向，且**就是已裁策略的同一动作**）。⚠ **另一端实测把收益打了折**（§4-A）：可达的国内 DoH（`doh.pub` / `dns.alidns.com`）给的是**同一组全球答案**，而 Cloudflare 的 **DoH(443) 反而不通** ⇒ **端点是这项取舍的关键**，不是"用加密就一定更好" |
| **② 出网腿改从能出网的主机发（主控/隧道）** | ⚠ **= 台账的"乙"**：撞 `station` 字段"任务目标站"的既有语义 ⇒ **须另裁**（本批不动） |

★★ **关键关系（值得写下来）**：已裁策略（2026-10-10）= 「**发作时**就地修 `resolvectl domain '~openrouter.ai' <可信上游>`」；**候选 ① = 把同一动作从"发作时"改为"预先常驻"** ⇒ ★ **两者不冲突，是升级**（策略仍在：常驻之后若仍坏，走"降级到 B 并留痕"）。

★★ **为什么它不是"修缺陷"**（对用户原问题的正面回答）：`C1` 明说**分流是设计行为**、`E2` 明说**那段是别人家的网** ⇒ **没有"被修的对象"**；能改的只有**"谁替我解析"**这一件事 —— 而那**本来就是本仓可支配的**（站上是我们的）。

★ **「发作时判别法」（写进手册 §8 的正是这一段）**：**同一时刻**在站上并排取三路 ——
① `getent ahostsv4 openrouter.ai`（**明文链路** = 现状那一跳）·
② `dig +short openrouter.ai A @1.1.1.1`（**不经路由器**的独立解析）·
③ 对 ① 给出的 IP `curl -4 --resolve …`（判那个 IP 到底是不是**能用**）。
⇒ ★ 判读：① 给非 Cloudflare 段而 ② 给 Cloudflare 段 ⇒ **根因在"明文解析那一跳"**；① 与 ② **同给坏段** ⇒ 根因在**上游自身**（路由器/ISP）⇒ 此时「就地修」的写法（按域名换上游）才有的放矢。
