# 证据流审计「常跑」调研：触发点 / 成本 / 严重度 三件待定事

> **日期**: 2026-09-18
> **触发**: [ADR-0007](../../adr/ADR-0007-证据流阶段推进路线与改动验证闭环.md) 定了「**先 B 后 A**」——路 B（扩面）已于当日完成（框架件基线合并），路 A 是「让 `agent audit` 常跑」。ADR 原文把路 A 的难点写成"需先定**触发点**与**成本上限**"两句，本轮把它拆成可判定的三件事并逐项实测。
> **证据等级**: **E1** = 本轮实测（附命令与数值）；**E2** = 前轮实测留档（引 ADR/OPEN-ISSUES）；**E3** = 本仓代码事实（附行号）；**E4** = 推断/外推（显式标注）
> **方法**: 全部为**只读测量**（不派发、不写 run、不触站）：① 同进程 / 跨进程分别计时，以分离"审计本体"与"解释器启动"；② 枚举全仓所有可挂载点（grep 调用面）；③ 对 gap 集合做**重复性**与**脆弱性**双向探针；④ 严重度判定不自行发明，而是**回查 ADR-0007 D4 既有纪律**并对齐。
> **结论**: ① **成本上限这件事不需要再议** —— 审计本体 86 run 仅 **0.048 s**，端到端 0.34 s 里 **85%** 是"起进程 + `import cluster`"；挂进**已有门禁进程**的真实增量是 **+0.044 s**，占 18 s 门禁的 **0.24%**。② 推荐挂载点为门禁第 15 项断言 `evidence` **内部**（零派发路径改动、无需夹具 e2e）。③ **增量基线不能用 gap 原字符串** —— 实测同类 gap 的文本会随"归档件在/不在"而变，会假告警；必须先归一为结构化 key。④ **严重度不能升 FAIL**：ADR-0007 **D4 已经定死**"覆盖缺口 ⇒ WARN"，理由原文是"报 FAIL 会让判据因噪声被整体忽略"。⑤ 路 A 有**两个前置缺口**（audit 口径对 71/86 个 run 不可见；`syntax` 断言只保证"在选中解释器上能跑"），不修会让"常跑"跑成一张分母只有 17% 的表。

## 1. 问题定义：路 A 到底要定什么

ADR-0007 把路 A 的难点写成一句话：

> 故必须先定三件事：**触发点**（pre-commit / 派发后 / 紧跟 `chain`）· **成本上限**（全语料 0.37s vs 增量只审新 run）· **严重度**。

本调研逐项给出可判定答案。**先明确路 A 要达成的性质**（这是判据，不是目的）：

| 性质 | 含义 | 为什么重要 |
|---|---|---|
| **被日常撞见** | 不依赖"人想起来跑" | 门禁 `evidence` 断言的既有设计理由原文："证据链的价值在**被日常撞见** —— 只靠'人工想起跑 agent verify'，归档被改动可以长期无人察觉"（[rpc_check.py](../../ops/rpc_check.py#L1631)） |
| **不制造噪声** | 存量缺口不天天刷屏 | D4 原文："报 FAIL 会让判据**因噪声被整体忽略**"；同理由见 `doclinks` 断言"判不准的不进门禁" |
| **不静默降级** | 判据失效必须可见 | 本仓反复踩到的家族（恒真判据 / 静默跳过）；ADR-0007 本轮又新增一例 |
| **不自证** | 审计声明不得由被审方产出 | 上游调研结论：编排管线产出审计声明 = self-attestation |

## 2. 成本实测（E1）

### 2.1 语料现状

| 项 | 数值 |
|---|---|
| run 总数 | **86**（Paper 84 + Cpp_Hub 2；Auto_Prover 无 `agent-out`） |
| runDir 归档件总数 | **398** |
| recipe v2（有 manifest） | **15** |
| recipe v1（零声明） | **71** |
| 覆盖现状（`agent audit` 输出） | 可离线复算 **113/120** 条声明 · `collect` 型 **4** · 设计性临时 **2** · **已归档但未声明 37 件** · **有 manifest 的 run 15/86** · gap 表 **15 条**（零篡改） |

### 2.2 成本分解（要紧：成本的大头不是审计）

| 环节 | 实测 | 说明 |
|---|---|---|
| `_chain_runs`（目录扫描） | **0.0034 s** | 扫三个 projRoot 的 `agent-out/*/` |
| 读全部 `run.json` | **0.0081 s** | 86 个 `.agent-run.json` |
| `_run_digest` 全量（**哈希重头**） | **0.0288 s** | 398 件 → **0.07 ms/件** |
| **`agent_audit` 进程内本体** | **0.0484 s** | **0.56 ms/run** |
| `agent audit` **CLI 端到端** | **0.337–0.378 s** | 3 次取样 |
| `python -c pass`（裸冷启） | **0.050 s** | 解释器启动下限 |
| `import cluster` | **0.197 s** | 拖入 paramiko 等 |

> **读法**：端到端 0.34 s − 本体 0.048 s ≈ **0.29 s 全在"起进程 + import cluster"**，与语料规模**无关**。
> ⇒ 若把 audit 挂进**已经 `import cluster` 的门禁进程**，真实增量是 **0.048 s 级**，不是 0.34 s 级。

### 2.3 随语料规模的增长（E4 外推，基于 E1 的 0.56 ms/run）

| run 数 | 审计本体（估） |
|---|---|
| 86（当前） | 0.048 s |
| 1 000 | **0.56 s** |
| 5 000 | **2.81 s** |
| 20 000 | **11.25 s** |

**增长是线性的**（每 run 常量次文件哈希），且**斜率极小**。按当前派发频率（实测当日 17 个 run 的量级），到达 1000 run 需要相当长的时间。

### 2.4 门禁时长预算（决定"值不值得")

| 项 | 实测 |
|---|---|
| `rpc.ps1 check -Quick` 端到端 | **17.50 / 19.04 s**（2 次） |
| `rpc_check.py --only evidence` | **0.37–0.38 s** |
| — 其中 `import cluster` | 0.197 s |
| — 其中 `agent_chain_verify`（verify 本体） | **0.0618 s** |
| — **追加 `agent_audit`（同进程）** | **0.0439 s** |

⇒ 若挂进 `check_evidence`：门禁 **18 s → 18.04 s**，即 **+0.24%**。

**成本上限这件事到此关闭**：原以为要权衡"要不要为一个表付 0.37 s"，实测是 **+44 ms**。

## 3. 触发点枚举（E1 grep 全仓调用面 + 属性对照）

### 3.1 现状调用面（全仓 grep 实测）

| 命令 | 自动调用点 | 说明 |
|---|---|---|
| `agent chain` | ✅ [`ops/rpc.ps1:89`](../../ops/rpc.ps1#L89) | 钩子生成器内，`\|\| true` best-effort，改的是**生成器**而非钩子文件本身 |
| `agent verify` | ✅ 间接：门禁 `evidence` 断言 | `CHECKS` 表内 `quick: True` ⇒ **骑在 pre-commit 上，每天免费跑** |
| `agent audit` | ❌ **零** | 全仓无任何流程调用它 |
| `agent audit-judge` | ❌ **零** | 且需站上在服务引擎（见 §8） |

### 3.2 候选挂载点对照

| # | 挂载点 | 频率 | 谁在跑 | 增量成本 | 失败后果 | 改派发路径? | 要夹具? |
|---|---|---|---|---|---|---|---|
| **A1** | pre-commit/pre-push 钩子（`chain` 那行旁） | 每次提交 | 本机 git | **+0.34 s**（另起 python） | `\|\| true` 不阻断 | 否（改 `rpc.ps1` 的 `Install-HookEntry`） | 否 |
| **A2** | **`check_evidence` 断言内部**（同进程） | **每次门禁** | 本机 git | **+0.044 s** | 可 WARN / FAIL | **否** | **否** |
| A3 | 派发后（`agent-cli.ps1` collect 之后） | 每次派发 | 主控 | +0.34 s（PS 内需 spawn python） | 派发已结束，只能事后 | **是** | **是** |
| A4 | 主控计划任务（周期调用） | cron | 主控 | 0.34 s | **无人看** ⇒ 需告警通道 | 否 | 否 |
| A5 | 人工按需（**现状**） | "想起来" | 人 | 0.34 s | 无 | —— | —— |

### 3.3 推荐 A2，理由三条（可判定，非偏好）

1. **成本最低**：0.044 s vs 0.34 s（**8 倍差**），且是唯一"不额外起进程"的方案。
2. **零派发路径改动**：不动 `agent-cli.ps1` ⇒ **不需要再过一遍阶段 0.5 夹具 e2e**。路 B 刚证明改派发路径要付"夹具 + 双向自证"的代价（见 ADR-0007 §路B）。
3. **时效性足够**：实际工作流是"派发 → `agent chain` → 提交"，`evidence` 骑在 pre-commit 上 ⇒ 新 run 的 gap 会**在下一次提交**被撞见。

**A3 的独有价值**（承认）：能把 gap **绑到具体那次派发**上（run 级归因，而非"语料级多了一条"）。但要改 `.ps1` + 过夹具，本轮判定**收益不抵风险**。
**A4 的定位**：仅在"长时间不提交"时提供兜底。仓库内**没有任何已配置的计划任务**，但已有成文先例（`reqlog sample` 的注释明确写"要连续采样，用主控站的计划任务周期调用它"，[cluster.py](../../ops/cluster.py#L2285)）。

### 3.4 ⚠ 实现陷阱（实测，落地时必须处理）

**`agent_chain_verify` 与 `agent_audit` 都返回键名 `"gaps"`**，而 `check_evidence` 现在取的是 verify 的那个（`gaps = r.get("gaps")`，r 来自 `cluster.agent_chain_verify()`）：

| 来源 | 行 | `gaps` 语义 |
|---|---|---|
| `agent_chain_verify` | [cluster.py:3660](../../ops/cluster.py#L3660) | 未入链 / 缺锚 / 缺 `.meta`（**覆盖缺口**，现为 WARN） |
| `agent_audit` | [cluster.py:3881](../../ops/cluster.py#L3881) | 可重放性缺口（**覆盖缺口**，现为 advisory） |

⇒ 挂进去必须**显式分名**（如 `verify_gaps` / `audit_gaps`），否则两个来源会串成同一个列表 —— 这与本 ADR 记账的"**同一份报告里两个口径打架**"（汇总表 vs 覆盖率行）是同一类错。

## 4. gap 的「可比较标识」：不能用原字符串（E1）

### 4.1 现状形态（86 run，15 条 gap）

| 形态 | 条数 | 例 |
|---|---|---|
| `已归档但未被任何 subject 覆盖: <件列表>` | **10** | `paper/202609181038486558`（6 件） |
| `subject 'X' 声明了 collect 命令但从未执行（归档件按约定名存在）` | **3** | `workspace-diff` |
| `subject 'X' 声明了 collect 命令但从未执行（且约定名无归档件）` | **1** | `workspace-diff` |
| `subject 'X' 声明的 <path> 不在 runDir` | **1** | `session-meta` |

### 4.2 重复性探针：**通过**

连续两次 `agent_audit(limit=0)`：gap 条数 15 = 15，**原字符串逐条完全相同**，集合相等。
⇒ "当前状态下结果确定"，可比较。

### 4.3 脆弱性探针：**不通过**（这是关键发现）

`collect-not-executed` 这一类的**文本会随"约定名归档件在/不在"而变**（实测同标签两条）：

```
paper/202609181118164876: subject 'workspace-diff' 声明了 collect 命令但从未执行（且约定名 `workspace-diff.txt` 无归档件）
paper/202609181119254134: subject 'workspace-diff' 声明了 collect 命令但从未执行（归档件 `workspace-diff.txt` 按约定名存在 ⇒ 只有产物、无执行记录）
```

**同一个 gap，只因那个件在/不在，文本就不同。**
⇒ 拿原字符串做增量基线：件一旦被补上/删掉，**文本变化就会被读成"新增 gap"** ⇒ 假告警 ⇒ 判据被忽略（回到 D4 警戒的失效模式）。

### 4.4 结构化 key（实测可完全覆盖）

`(kind, label, name | sorted(files))`：

| kind | 取值来源 |
|---|---|
| `undeclared` | `("undeclared", label, tuple(sorted(files)))` |
| `collect-not-executed` | `(…, label, subject_name)` |
| `no-path-no-collect` | `(…, label, subject_name)` |
| `missing-artifact` | `(…, label, subject_name)` |

实测：**15/15 无碰撞**（去重后仍 15），且天然免疫 §4.3 的文本漂移（parenthetical 细节不进 key）。

⇒ **把 gap 归一为结构化 key 是路 A 的实现前置，不是可选优化。**

## 5. 严重度：与 ADR-0007 D4 的冲突检查（E2/E3）

### 5.1 D4 已定死"不能升 FAIL"（原文引用）

[ADR-0007](../../adr/ADR-0007-证据流阶段推进路线与改动验证闭环.md) **D4**：

| 类别 | 例 | 处置 | 理由（原文） |
|---|---|---|---|
| 篡改/损坏证据 | `digest_mismatch` / `chain_break` / `cold_mismatch` / `anchor_mismatch` / `run_dir_missing` | **FAIL** | 有明确对立面（改 vs 未改），可判定 |
| **覆盖缺口** | 有 run 未入链 / 缺锚 / 缺 `.meta`（老 run） | **WARN** | 属"**没验到**"，**不是"验出问题"**；**报 FAIL 会让判据因噪声被整体忽略** |
| 合法演进 | golden 源哈希与当次不同 | **info/gap** | 与篡改在此不可区分 ⇒ 只能报"已漂移，需人判" |

且 D4 附注明确：**"后续新增判据必须**先归入某一类再落地"**。

**套用**：audit 的 15 条 gap **全部是"没验到"**（零篡改、零 digest 不符），与"有 run 未入链"同类。
⇒ **把 audit 升 FAIL 不是"保守 vs 激进"的选择，而是违反本 ADR 自己定的 D4。**

### 5.2 剩余两档

| 方案 | 行为 | 问题 |
|---|---|---|
| **W1 · 纯 WARN** | 每次门禁都报（当前 15 条） | 存量天天出现 ⇒ 正是 D4 警告的"因噪声被整体忽略" |
| **W2 · WARN + 增量水印** | 只报**新增** key；存量仅以**计数行**呈现 | 无噪声、新增必被抓 |

### 5.3 W2 的前提已由路 B 满足（这是"先 B 后 A"的兑现点）

- 路 B 前：新增 run 会带 12 件"未声明" ⇒ 水印基线一开始就是脏的（52 条）
- 路 B 后：**实测两个新 run 的 gap 均为 0**（`202609181934560158` / `202609182312282167` / `202609182314143434`）。
  其中 `echo.md`（**零 manifest 声明**）现在也拿到 10 条基线声明且 gap 为空 ⇒ **新 run 不会再产生 gap**
- ⇒ 水印从建立那天起就是干净的，W2 才能成立

### 5.4 ⚠ 诚实边界：WARN **不阻断**

`rpc.ps1` 明确定义退出码：`0=PASS/WARN 1=有 FAIL(阻断)`（[rpc.ps1](../../ops/rpc.ps1#L61)）。
且本轮已实测吃过一次"**一行 WARN 淹没在 18 s 输出里**"的亏（Python 3.11 语法错那次：`evidence` 只报 WARN，整仓仍 PASS）。

⇒ W2 **必须同时把新增 gap 逐条打出来**（放进该断言的 details），否则等于没有。仅报一个数字 = 复现本轮踩到的坑。

## 6. 水印存哪：三选项对照（E3 先例）

| 选项 | 先例 | 优点 | 代价 |
|---|---|---|---|
| **本地**（`ops/.audit-baseline.json`，`.gitignore`） | [`ops/.egress_daily.json`](../../ops/cluster.py#L1126)（同样是本地计数状态，且 `ops/station-bin/agent-chain.json` 已在 `.gitignore`） | 零噪声、零仓库扰动、零提交摩擦 | 换机器/新克隆首跑会把存量当"新增"报一次（**自愈**）；"基线何时建立"**不可审计** |
| **入仓**（仓库跟踪） | [`archive/evidence-chain/ANCHOR.txt`](../../archive/evidence-chain/ANCHOR.txt)（小指纹，已 push 作跨信任域见证） | 可评审、跨机一致、`git log` 可回答"基线何时建立" | 每次新增 gap 都要提交 ⇒ 与"机器产物不入仓"红线擦边（但锚已开"**小指纹可入仓**"的先例） |
| **人工登记例外** | 门禁 `doclinks` 的"已登记例外 2" | 显式、可审计、逐条有理由 | 当前 52 条要手写；且等于把历史欠账**永久洗白**（写进仓库就更难回头） |

> **对照要点**：前两者是"自动豁免"，第三种是"人工豁免"。D4 的精神是"防噪声"，自动化程度高的方案更符合；但"入仓"多出一个**跨机一致**的好处（多人/多机时基线不漂）。

## 7. 两个前置缺口

### 7.1 P1 · audit 口径：**71/86 run 在报告里完全不可见**

**机制**（E3）：`agent_audit` 刻意只对**有 manifest 的 run** 算 `undeclared`（[cluster.py](../../ops/cluster.py#L3853) 注释："仅对**有 manifest 的 run** 计：v1 run 没有'声明'这回事 ⇒ 全列出来只会淹没 gap 表"），而 v1 run 既无 `subjects` 也不进 `undeclared`。

**后果**（E1）：coverage 只写 `有 manifest 的 run: 15/86`，**不说另外 71 个判不了** ⇒ 读表的人会把 `可离线复算 113/120` 当成语料级结论。这正是本 ADR 已记过的"**报告自身两个口径打架**"同族。

**路 B 之后的变化**：新 run 全为 v2 ⇒ 该比例会**自然改善**（不再恶化）。但**报告在"常跑"之前就该说实话** —— 否则你在门禁里常跑的是一张**分母只有 17%** 的表。

**建议**：coverage 增一行显式的"**零声明（v1）run N 个，不参与可重放性判定**"，并注明这是**历史欠账**（早于阶段 1 的 run 无法回溯，见 ADR-0007 §路B 一②）而非缺陷。

### 7.2 P2 · `syntax` 断言只保证"在**选中**解释器上能跑"

**机制**（E3）：`check_syntax` 用**进程内** `py_compile.compile()`（[rpc_check.py](../../ops/rpc_check.py#L249)），解释器 = `rpc.ps1` 挑的那个（候选里**第一个能 `import paramiko` 的** ⇒ 本机落到 **Python312**，[rpc.ps1](../../ops/rpc.ps1#L45)）。仓库根**没有** `pyproject.toml`，也**没有** `requires-python` 声明。

**已造成的实际后果**（E1，2026-09-18）：`cluster.py` 里一行 f-string 表达式段含反斜杠（PEP 701 才允许）⇒
- 在 PATH 第一个 `python`（**3.11.16**）下：`SyntaxError`，**整个 `cluster.py` 不可用**
- 但门禁跑在 312 ⇒ `syntax` 报 **0 失败**
- 且 `evidence` 的 `import cluster` 被 `except Exception` 兜住 ⇒ 只报 **WARN「证据链断言跳过」**，**整仓仍 PASS**

⇒ **判据静默消失、门禁照绿**（与"恒真判据"同族：那次是"判了但恒过"，这次是"根本没判"）。

**两条路选一**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **α · 声明最低版本** | 引入 `requires-python`（或仓库约定文件），门禁在**低于**该版本的候选上**明确报"不支持"**（不得静默通过） | 放弃"PATH 第一个 python 也能跑"；需人记住用哪个解释器 |
| **β · 保证兼容 + 门禁验最旧** | 代码保持 3.11 兼容；门禁**用最旧可用解释器**批量编译一遍（**一个子进程**，非 43 次 spawn，成本 ~0.3 s） | 引入"多解释器矩阵"的维护面 |

> 现状是**两者都没做** —— 这是 P2 必须收口的原因：路 A 让 `evidence` 更重之后，同类"静默跳过"的代价会更大。

## 8. 明确不在路 A 范围内

**`agent audit-judge`（异基座 judge 层）不能常跑**：

- 需站上**在服务**的跨家族引擎：实测 `_flow_find_engine()` → `(None, None)`（当前 0 站在服务；本轮 e2e 用完已 `unload`）
- 成本是 **LLM 级**（题集 16 条 × 4 轮），不是毫秒级
- 目标是**量化 judge 自身的可靠性**（A/A 底噪 / position bias / 措辞稳健性），属**里程碑校准**而非逐提交判据

⇒ **路 A 只覆盖机器层**；judge 层维持"按需跑 + 校准报告入仓"（现状，ADR-0007 阶段 3-b 已定）。

## 10. 诚实边界与风险

1. **外推是 E4**：0.56 ms/run 的线性外推未在 1000+ run 上实测（当前语料只有 86）。若未来单 run 归档件数显著增长（如引入大体积产物），斜率会变。
2. **WARN 不阻断**：即使 W2 落地，"有人真的读输出"仍是前提（§5.4）。本调研**不**提供"阻断"选项 —— 那是 D4 明确否决的。
3. **水印的单调性取舍**：水印方案（`new = current − baseline`，然后 `baseline ∪= current`）保证"同一 key 只报一次"，代价是**同一处 gap 被修复后再次出现不会二次告警**。若要求"复发也告警"，需改为"快照对比"（但那会让 runDir 被删/恢复造成假告警）。**本轮建议取单调水印**（偏向"防噪声"，符合 D4）。
4. **A2 的时效依赖提交**：若一次派发后长期不提交，gap 不会被撞见（此时 A4 计划任务才算真正必要）。
5. **本调研未验证**"把 audit 挂进 `check_evidence` 后门禁输出是否仍可读"（details 行数会变多）。这属落地时的验收项，不是本调研的结论。

## 11. 决策分析：依赖链 / 影响链 / 成本收益 / 短长期 / 综合矩阵

> §9 只给了"待决策 + 建议默认"。本节把四个决策**拆到可裁定的粒度**：先固定"判据从哪来"（11.1），再逐个决策给**依赖链**（它依赖什么才能成立）、**影响链**（选了它会连带发生什么）、成本/收益、短期/长期，最后合成矩阵（11.6）。

### 11.1 先固定前提：W2 的三条**硬前置**（不是可选优化）

W2（WARN + 增量水印）要成立，必须同时满足三条，缺一条就退化成"噪声判据"或"静默判据"：

| # | 硬前置 | 不满足的后果 | 满足成本 | 依赖 |
|---|---|---|---|---|
| **K1** | gap 归一为**结构化 key** `(kind,label,name\|files)` | 同类 gap 的文本会随"归档件在/不在"而变（§4.3 实测）⇒ **假告警** | 小（一个纯函数 + 现有 4 类全覆盖，实测 15/15 无碰撞） | 无 |
| **K2** | 水印的**读点与写点必须分离** | 见 11.1.1（这是**门禁只读不变量**逼出来的，不是偏好） | 小（读在门禁；写在一条显式命令） | 反过来约束 D-a / D-b |
| **K3** | 新增 gap 必须**逐条打印**进 details，并把"如何接受"写进门禁 `fix` 字段 | 只报一个数字 ⇒ 复现本轮踩过的"**一行 WARN 淹没在 18s 输出里**"（§5.4） | 小（沿用门禁既有 `fix` 约定） | 无 |

#### 11.1.1 K2 的由来（实测事实，非推断）

**`rpc_check.py` 对仓库全程只读** —— 全文件检索写入面，唯一的写动作是 `check_syntax` 的 `tempfile.NamedTemporaryFile` + `os.unlink`（[rpc_check.py L288-296](../../ops/rpc_check.py#L288)）。这是**事实不变量**，不是文字约定：
- 门禁挂在 **pre-commit** 上 ⇒ 若门禁改工作区，每次提交都会把工作区弄脏（或产生未暂存改动）；
- 且 `evidence` 断言的设计描述明确写着"quick、**只读**、按 FAIL/WARN/info 分层"。

⇒ **水印不能在门禁里自动推进。**
⇒ 推论（**这是本节最有价值的一条**）：水印只能由**另一条显式命令**推进 ⇒ **"接受这批新 gap"成为一个人类的显式动作**。
这恰好与本仓"不静默降级"和"登记例外要显式"的纪律**同向**——自动推进反而是"静默洗白"。所以 K2 不是妥协，是**纪律要求落到了架构上**。

### 11.2 D-a 挂载点

**依赖链**
```
A2（门禁内）  ⟵ 依赖 K1 + K2 + K3（全部必须在 A2 落地前就绪）
              ⟵ 依赖 D-b（水印放哪 = A2 要读哪个文件）
              ⟵ 不依赖 D-c 的 P2（解释器）—— 但 P2 不修时 A2 的"判据静默失效"风险更高
A1（钩子另起进程）⟵ 依赖 D-b；不依赖 K2（钩子本就 best-effort 可写）
A3（派发后）  ⟵ 依赖 agent-cli.ps1 改动 ⟹ **依赖阶段 0.5 夹具 e2e**（每条派发路径改动都要付）
              ⟵ 依赖 D-b；K1/K3 同样必需
```

**影响链**

| 选择 | 连带发生 | 二级影响 |
|---|---|---|
| **A2** | 必须新造"水印推进命令"（K2）⇒ 多一条要记的运维命令 | 若忘记推进 ⇒ WARN 反复出现 ⇒ 回到噪声。**缓解**：门禁 `fix` 字段直接写出该命令（本仓既有约定，每个 check 都有 `fix`） |
| **A2** | 门禁时长 +0.24%（已实测）；但**长期线性增长**（§2.3：20000 run ⇒ 11.3s ≈ 门禁的 60%） | 需在将来引入"**按 since 增量扫描**"（水印顺便存 `last_audited_run_ts`）⇒ 建议 **A2 的实现里就带 `since` 参数**（现在做成本≈0） |
| **A1** | 与 `chain` 同一行 ⇒ 每次提交**再起一个 python**（+0.34s） | 无额外命令要记（钩子可自动写水印）⇒ 摩擦更低，但**失去了"显式接受"**这一性质；且钩子 `\|\| true` 失败静默 ⇒ 与"不静默"纪律相抵 |
| **A3** | 必须改 `agent-cli.ps1` ⇒ 每次派发后路径变更都要重跑夹具 | 与 `chain`/`verify` 的"零派发路径改动"优势相消；且 PS 内 spawn python（+0.34s/派发，frequency 高） |
| **A（任一）** | **不改变 verify 的 FAIL 集** | 需说明：`manifest_undeclared` **在 verify 里早已是 FAIL**，但只查 `AGENT_MANIFEST_REQUIRED`（5 个固定件，[cluster.py:3638](../../ops/cluster.py#L3638)）；audit 部分只加 WARN ⇒ 两级并存，不冲突 |

**成本 / 收益**

| 方案 | 一次性成本 | 持续成本 | 收益（覆盖度） | 新增摩擦 |
|---|---|---|---|---|
| **A2** | 中（K1+K2+K3 + 两条命令）| **+0.044s/门禁** | 每次门禁（**实测 24 提交/19 派发·当日** ⇒ 覆盖 ≥ 派发） | 需显式接受新 gap |
| A1 | 小（一行 + 水印命令） | +0.34s/提交 | 同上 | 无（自动接受） |
| A3 | **大**（改 `.ps1` + 夹具双向自证） | +0.34s/派发 | 每次派发（**边际收益小**：提交不比派发稀） | 无 |
| A4 | 小 | 0.34s/次 | 仅在"长期不提交"时兜底 | 需告警通道（无 ⇒ 无效） |

**短期 / 长期**

- **短期**：A2 的成本优势决定性（8×），且**唯一免夹具**。
- **长期**：A2 的线性增长是**唯一真实风险**（A1/A3/A4 同样线性，但 A1/A3 每次都要起进程，更早触顶）。**共同解**：`agent audit` 支持 `since` 增量扫描 —— 该能力**不依赖选哪个挂载点**，故应在实现时就加。
- **长期**：A3 的独有价值（gap 绑定到具体派发）随语料增大而更有用（"哪次派发引入的"比"语料里多了一条"可行动）⇒ 若将来 A2 出现噪声，**A3 是最自然的升级路径**（保留为备选，非废弃）。

### 11.3 D-b 水印存储

**依赖链**
```
D-b ⟵ 依赖 K2（写点在门禁外）
    ⟵ 受"单机 or 多机"决定（实测：仓库**单一贡献者**，主控站单机；三站不提交）
```

**影响链**

| 选择 | 连带发生 | 二级影响 |
|---|---|---|
| **本地 gitignore** | 新克隆/换机**首跑会把存量当"新增"报一次** | 自愈（第二次就干净）；但"基线何时建立"**不可审计** |
| **入仓** | 每次接受新 gap ⇒ **一次提交**；`git log` 可回答"基线何时建立、由谁接受" | 与"机器产物不入仓"红线擦边（但 ANCHOR 已开"小指纹可入仓"先例）；**多人/多机时基线一致**（当前无此需求） |
| **人工登记例外** | 52 条要手写；写进仓库后**更难回头** | 最显式、最可审计；但等于把历史欠账**固化进契约**，且随语料增长需持续维护 |

**关键对照（三选一的真正分界）**：**"接受新 gap"这个动作要不要留下版本历史？**
- 本地 ⇒ 不留（只在自己机器上）
- 入仓 ⇒ 留，且随代码评审走（`git log` 就是接受记录）
- 登记例外 ⇒ 留，且是**逐条带理由**的（最强，也最重）

**成本 / 收益**：本地 = 零摩擦零审计性；入仓 = 低摩擦（稳态下几乎不发生）+ 高审计性；**当前是单机单人 ⇒ 入仓的"跨机一致"收益为零**，只剩"审计性"。

**短期 / 长期**：短期选本地（零摩擦）。**长期若要"债务可视化与清零"**，需要第三条路的能力（逐条理由）—— 但那应当是**另一件事**（见 11.6 的"水印永不收缩"风险），不必现在就上。

### 11.4 D-c 前置范围

**依赖链**（三个前置**互不依赖**，但**与 A 的依赖强度不同**）

| 前置 | 是否为 A 的**硬**前置 | 说明 |
|---|---|---|
| **K1 结构化 key** | ✅ **硬** | 不做则 W2 会假告警 ⇒ **A 不能落地** |
| **K3 逐条打印 + fix 提示** | ✅ **硬** | 不做则 A 落地了也看不见 |
| P1 audit 口径（71/86 不可见） | ✗ 软，但**强相关** | 不做则 A 常跑的表**分母只有 17%**，读表的人会误读为语料级结论 |
| P2 syntax 解释器 | ✗ 软，但**同源** | 与 A 同属"**判据静默失效**"家族；且**本轮已实际造成一次事故**（§7.2）。A 让 `evidence` 更重之后，同类代价更大 |

**影响链**：P1 只管**报告诚实性**（不改判定）；P2 无论选 α/β 都只影响 `syntax` 一项。⇒ **两者都不阻塞 A**，可以并行/延后。

**成本 / 收益**

| 项 | 成本 | 收益 | 短期 | 长期 |
|---|---|---|---|---|
| K1 | 小（纯函数 + 单测） | **A 的前提** | 必做 | 稳定 |
| K3 | 小 | **A 的可见性** | 必做 | 稳定 |
| P1 | **很小**（coverage 加一行） | 报告不再被误读 | 立即可得 | 稳定 |
| P2-α（声明最低版本） | 小（一个声明 + 门禁校验） | 明确"支持什么"，低版本**报错而非静默通过** | 立即可得 | 放弃"PATH 第一个 python 也能跑" |
| P2-β（兼容 + 验最旧） | 中（多解释器矩阵 + 一个子进程 ~0.3s） | 保证最旧可用解释器也能跑 | 立即可得 | 需维护矩阵 |

**推荐：K1 + K3 + P1 + P2 一起做**。理由：K1/K3 是 A 的硬前置（无法省）；P1 成本近乎零且**直接决定 A 的产出是否可读**；P2 与 A 同源，且**留着一个已知的"判据静默失效"通道去加重 `evidence`**，逻辑上不自洽。

### 11.5 D-d judge 层

**依赖链**
```
常跑 judge ⟵ 依赖站上**常驻**跨家族引擎
           ⟵ 与"零自加载方针"冲突（check_engine docstring：全站停机属正常）
           ⟵ 与"内存门禁"抢资源（load-mem-gate 可能拒绝真实派发的加载）
           ⟵ 成本是 **LLM 级**（16 题 × 4 轮），不是毫秒级
```

**影响链（实测口径）**

| 后果 | 实测依据 |
|---|---|
| 常驻引擎**本身不会报错** | `check_engine` 把"引擎在服务"记为 `info`（[rpc_check.py:1868](../../ops/rpc_check.py#L1868)），仅当"端口在听但 RSS<1G"才 WARN、"无端口但有残留"才 FAIL |
| **但会掩盖它要抓的东西** | 该断言的立意是"抓**占着内存却没服务**"（[docstring](../../ops/rpc_check.py#L1850)）；有一个**合法的**常驻引擎后，"残留"与之**不可区分** |
| 吃掉内存门禁余量 | 当前 `gates` 实测"最小余量 106G"；跨家族 judge 量级（如 Qwen3.8-27B）⇒ 该站余量掉数十 G，可能触发 `load-mem-gate` 拒绝真实派发 |
| 与 O-18 铁律耦合 | "跨站各 1 / 勿同站叠" —— 常驻 judge 会永久占住一个站的并发位 |

**成本 / 收益**：常跑 judge 的**边际收益低**（judge 测的是"审计员自身可靠性"，属**里程碑校准**，不是逐提交判据）；成本则是**集群资源 + 方针冲突 + 掩盖残留检测**。

**短期 / 长期**：短期明确**维持按需**（现状即正确）。长期若要做"自动复核"，正确的方向不是"常驻引擎"，而是**按需 load-校准-unload 的批处理**（本仓已有此形态，成本可控、不破方针）。

### 11.6 综合决策矩阵

**评分口径**：成本/风险 = **低**加分；收益/可判定性 = **高**加分。★ = 推荐。

| # | 决策 | 选项 | 成本 | 收益 | 可逆性 | 与既有纪律 | 短期 | 长期 | 裁定 |
|---|---|---|---|---|---|---|---|---|---|
| **D-a** | 挂载点 | **A2 门禁内** | **低**（+0.044s） | 高（覆盖≥派发） | 高（删一行即回退） | 一致（WARN 不动 FAIL 集） | ★ | 需 `since` 防线性增长 | **★ 选 A2** |

### 11.7 推荐组合与**执行序**（含验收判据）

```
K1 结构化 key ─┐
K3 逐条打印+fix ─┤
P1 口径一行     ─┼─→ A2 挂载（读水印 + 只报新增） ─→ 双向自证 ─→ 提交
P2 解释器       ─┤        ↑
D-b 本地水印    ─┘        └── 写水印 = 新命令（K2，门禁只读 ⇒ 写点必须在门禁外）
```

**双向自证（沿用本仓纪律，不得省）**
1. **能 FAIL/告警**：构造一条新 gap（如临时把某卡的某个 subject 路径写成不存在的件）⇒ 门禁 **WARN 且逐条列出**；
2. **存量不告**：gap 数不变时重复跑门禁 ⇒ **无告警**（这是"存量 52 条不刷屏"的直接证据）；
3. **恢复后 PASS**：还原构造 ⇒ 门禁回到无告警态。

**执行序的两点说明**
- **K1 必须最先**：它是唯一"不做则 A 会假告警"的硬前置。
- **P2 可选提前**：它与 A 无依赖，可并行；但**不要留到最后**，否则等于"明知有一条静默失效通道，还先去加重 `evidence`"。

### 11.8 三个必须记账的长期风险

| # | 风险 | 依据 | 处置 |
|---|---|---|---|
| 1 | **A2 成本线性增长**（20000 run ⇒ 11.3s ≈ 门禁 60%） | §2.3（E4 外推） | `agent audit` 加 `since` 增量扫描；水印顺带存 `last_audited_run_ts` |
| 2 | **水印单调 ⇒ 永不收缩** | §10.3 的设计取舍 | 短期无害（存量 just 不再触发）；长期若需"债务清零"可见性，另做"已消失 key 回收"，不混进 A |
| 3 | **"忘记接受新 gap" ⇒ WARN 反复** | K2 的必然代价（门禁只读） | 门禁 `fix` 字段直接给出接受命令（沿用既有约定）；这也是"不静默"的代价，**刻意接受** |

### 12.3 两个"顺手抓到"的实证（都记账）

**① 引号坑在本仓是复发性坑。** 写 P1 的 coverage 行时我又踩了一次：f-string 用 ASCII 双引号定界，里面却嵌了 ASCII 双引号 `（v1 无"声明"这回事…）` ⇒ 字符串提前终止、`SyntaxError`。改用 `「声明」` 后通过。
> 与既有记账同族（"python 语法错误（引号）：中文引号内嵌导致 SyntaxError ⇒ 改用「」"）。**措施不是"下次小心"**：本轮已加 P2 —— 这类错误在**当前解释器**下也会被 syntax 抓到（与版本无关），故它不会静默流出去。
