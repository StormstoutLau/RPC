# O-165 / O-166 调研：备路「执行点 / 判据点 / 注入点」三处 cwd 不一致

> **日期**：2026-10-23 · **承载**：台账 `O-165`（站上 accept 判据面错位）· `O-166`（golden 注入点错位）
> **性质**：**只做调研 + 故障复现 + 外部锚点**；未改任何代码、未裁决方案。
> **证据分级**（沿用本仓约定）：**E1** 本会话实测 · **E2** 前会话实测 · **E3** 外部文档/社区案例 · **E4** 推断（须标注）。

## 0. 结论（先行）

**根因一句话**：claude 备路把「agent 在哪跑」「accept/golden 在哪判」「golden 注入到哪」拆成了**三个互不相同的 cwd**；主路（opencode）三者同根（站上工作区 `$W`），备路没有对齐。

两个实例：

| 实例 | 形状 | 影响面 | 严重度 |
|---|---|---|---|
| **O-165** | **站上** claude：产物在 `$stWorkDir`，accept/golden 却用**主控 `$projRoot`** 判 | 主控有陈旧同名件 ⇒ **假绿**；干净 ⇒ **假红** | **P1**（完成信号面） |
| **O-166** | **全部** claude：golden 注入到 `%TEMP%` scratch，判据 cwd 却是 `$projRoot`（站上变体还**根本没把 golden 送上站**） | 任何 claude + golden 卡 ⇒ **必假红**（`GOLDEN_FAIL rc=127`） | **P1/P2**（能力从未跑通；全仓 0 次 claude+golden run） |

**建议方向（不裁决）**：引入**单一 `$judgeRoot` = 执行点**（本地 = `$projRoot`；站上 = `$stWorkDir`），golden 注入、accept、accept-golden 三处全部对齐；站上支的判据在站上执行并回传输出。详见 §5。

## 1. 事实面：三条路径逐点对照

| 环节 | 主路 opencode（站上） | 备路 claude **本地** | 备路 claude **站上** |
|---|---|---|---|
| agent 执行 cwd | `$W`（站上工作区） | `$projRoot`（[L4884](../../ops/station-bin/agent-cli.ps1#L4882-L4884)） | `$stWorkDir`（[L4882](../../ops/station-bin/agent-cli.ps1#L4882-L4884)） |
| `accept` 执行点 | 站上 body：`( cd "$W" && eval "$c" )`（[L3440](../../ops/station-bin/agent-cli.ps1#L3439-L3443)） | 主控 Git Bash，cwd=`$projRoot`（[L4941](../../ops/station-bin/agent-cli.ps1#L4934-L4942)） | **主控** Git Bash，cwd=`$projRoot`（同上） |
| `accept-golden` 执行点 | 站上 body：`( cd "$W" && eval ... )`（[L3146](../../ops/station-bin/agent-cli.ps1#L3145-L3148)） | 主控，cwd=`$projRoot`（[L4925](../../ops/station-bin/agent-cli.ps1#L4912-L4927)） | **主控**，cwd=`$projRoot`（同上） |
| golden 注入点 | `$W/.golden`（站上，tar 解包；[L3253-3255](../../ops/station-bin/agent-cli.ps1#L3252-L3255)） | `$scratch/.golden`（主控 `%TEMP%`；[L4826-4828](../../ops/station-bin/agent-cli.ps1#L4820-L4829)） | `$scratch/.golden`（主控 `%TEMP%`；**未上站**） |
| 产物拉回 | runDir（scp） | runDir（copy） | runDir（scp） |
| `.run-marker` | `$W` | `$projRoot` | `$stWorkDir` |
| **判据与执行同根？** | **✅** | accept **✅** / golden **❌** | accept **❌** / golden **❌** |

> `$scratch` 的定义见 [L4662](../../ops/station-bin/agent-cli.ps1#L4662-L4663)：`Join-Path $env:TEMP "agent-cli-claude-$ts"` —— 与 `$projRoot` **不同目录**。

**结论**：
- **本地备路**的 accept 是**对的**（与 agent 同根）；错的只有 golden 注入点。
- **站上备路**的 accept 与 golden **两处都错**（判在主控、注入不在站上）。

## 2. 故障复现（E1）

### 2.1 golden 注入错位：离线 A/B（同一命令，只换注入点）

```powershell
# A = 现状（golden 在 scratch，判据 cwd=projRoot）
A: rc=127  bash: .golden/smoke_dispatch_golden.sh: No such file or directory
# B = 主路形状（golden 在 projRoot/.golden，判据 cwd=projRoot）
B: rc=0    SMOKE_GOLDEN_OK pwd=/tmp/o166-repro/projRoot
```

- 夹具脚本 = [ops/station-bin/golden/smoke_dispatch_golden.sh](../../ops/station-bin/golden/smoke_dispatch_golden.sh)，它自己就判「`.golden` 存在 + 脚本在其中 + cwd=工作区根」。
- **唯一变量** = 注入点（scratch vs projRoot）；命令、shell、cwd 全部相同。
- **A 的 rc=127 发生在 bash 打开脚本之前** —— 连 golden 自身的诊断都没机会打印。

### 2.2 站上 accept 判据面错位：真跑证据（run `202610231326454774`）

| 事实 | 读数 |
|---|---|
| 站上产物 | `$stWorkDir/out/glob-probe.txt` mtime **13:27:05** |
| 主控同名件 | `d:\RPC\tmp\dogfood-ws\out\glob-probe.txt` mtime **13:00:15**（上一轮**本地** run 留下） |
| 日志 | `ACCEPT_MODE=bash-local (… cwd=d:\RPC\tmp\dogfood-ws)` · `ACCEPT_OK=1` |
| 结论 | `ACCEPT_OK=1` 判的是**主控旧件**，**不可归因于站上产物**（内容恰同 = `GLOB_PROBE_OK` ⇒ "碰巧绿"） |

> 同一 run 的 `EVM_STATE_GLOB` + `pulled=1` 正常 ⇒ **产物拉回不受影响**；错的只是 **accept 判定面**。
> 对照：本地 run `202610231300033396` 的 accept 判的是**执行点**（`$projRoot`）⇒ 本地支无此问题。

### 2.3 未复现（如实）

- **未**做 claude + golden 的端到端真跑（成本 + 会污染台账）；全仓扫四个项目根 **claude + golden run = 0 条**（E1 扫描）。
- **未**故意造「站上 agent 不写产物 + 主控有陈旧件 ⇒ 假绿」的负向 run（按本仓纪律，不为复现缺陷而伪造样本）；§2.2 是**结构 + mtime**证据，非"已观测到假绿"。

## 3. 故障机理

### 3.1 golden（claude 备路）

1. golden 注入：`$goldenLocal = Join-Path $scratch '.golden'`，`Copy-Item $gSrc $goldenLocal`（[L4826-4828](../../ops/station-bin/agent-cli.ps1#L4820-L4829)）。
2. 跑前防篡改：`Get-FileHash $scratch/.golden/<base>` 与 `$goldenSha` 比对（[L4915-4917](../../ops/station-bin/agent-cli.ps1#L4912-L4927)）⇒ **通过**（校验的是 scratch 那份）。
3. 执行：`Invoke-LocalBashCmd -cmd $g.cmd -cwd $projRoot`（[L4925](../../ops/station-bin/agent-cli.ps1#L4912-L4927)）⇒ `.golden/<base>` 在 `$projRoot` 下**不存在** ⇒ `rc≠0`。
4. 结果：`$acceptGoldenOk=0` ⇒ `$finalCode=1`、`status=failed`。
5. **诊断缺口**：主路会打 `GOLDEN_FAIL rc=`（[L3148](../../ops/station-bin/agent-cli.ps1#L3145-L3148)）；备路只打 `ACCEPT_GOLDEN_OK=0`（[L4928](../../ops/station-bin/agent-cli.ps1#L4928)）⇒ 现场更难看懂。

> 站上变体更重：即使把判据 cwd 改成 `$stWorkDir`，golden 那份**也从未 scp 上站** ⇒ 仍然必失败。

### 3.2 accept（站上备路）

1. `Invoke-LocalBashCmd -cmd $c -cwd $projRoot`（[L4941](../../ops/station-bin/agent-cli.ps1#L4934-L4942)）——**无条件**。
2. 主控树可能：**陈旧**（上一轮本地 run 留下）⇒ 假绿；**干净** ⇒ 假红。
3. 站上产物与判定**无关**；`accept-output.txt` 里也看不出判的是哪棵树（只有 cwd 一行）。

### 3.3 为什么夹具没抓到

- `_fm_golden_test.ps1` 有「`Invoke-ClaudeFly` 两处本地调用点都传 `-cwd $projRoot`」的**结构断言**（[L690](../../ops/station-bin/_fm_golden_test.ps1#L675-L690)）—— 它守的是 **agent cwd**，不是 **judge/注入点**。
- 没有断言把「golden 注入目标 == 判据 cwd == agent cwd」绑在一起；也没有 claude golden 的真跑样本。
- `accept` 的 `-cwd $projRoot` 是 O-15/AUDIT（2026-09-21）为**本地支**修的（当时本地支确实该用 projRoot）；站上支复用了同一行，**没有随 `$useStation` 分叉**。

## 4. 外部锚点（E3）

> **用法**：外部锚点只支持**原则**（"判据应在产出环境里跑"），不证明本仓代码对错；本仓的 E1 证据在 §2。
> 每条都标「支持什么 / 不支持什么」，防把类比当证明。

| # | 来源（E3） | 逐字/要点 | 支持 | 不支持 |
|---|---|---|---|---|
| A1 | [Bazel Test encyclopedia](https://bazel.build/reference/test-encyclopedia)（一手） | "The initial working directory shall be `$TEST_SRCDIR/$TEST_WORKSPACE`." | 测试运行器**把 cwd 设进输入树**（runfiles），不是控制器任意目录 | 不涉及"跨机器" |
| A2 | [Bazel Sandboxing](https://bazel.build/versions/9.2.0/docs/sandboxing)（一手） | 进程"runs in a working directory that only contains known inputs" | 判据所需的输入（golden）必须**在判据工作目录内** | 不涉及"主控 vs 站上" |
| A3 | [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)（一手） | "Actions and shell commands execute in this directory [`GITHUB_WORKSPACE`]." | **判据命令在产出方的工作区里跑** | 不涉及"主控"角色 |
| A4 | [GitHub · Store and share data](https://docs.github.com/en/actions/using-workflows/storing-workflow-data-as-artifacts)（一手） | "You can use the `upload-artifact` and `download-artifact` actions to share data between jobs in a workflow." | **不同机器/作业不共享树**；跨边界要显式搬运 | 不判"搬运后能不能判" |
| A5 | [Jenkins · Controller Isolation](https://www.jenkins.io/doc/book/security/controller-isolation/)（一手） | "It is therefore highly advisable to not run any builds on the built-in node, instead using agents… to run builds." | **控制器上跑构建/判据是反模式**；应在 agent 上跑 | 不涉及"验收" |
| A6 | [GitLab CI · Caching](https://docs.gitlab.com/ci/caching/)（一手） | "Cache is stored where GitLab Runner is installed and uploaded to S3 if distributed cache is enabled." | **缓存/工作区默认在 runner 本地**；跨 runner 共享要显式配置 | 不判"是否必须同机" |
| A7 | [Ansible · Delegation](https://docs.ansible.com/ansible/8/playbook_guide/playbooks_delegation.html)（一手） | "If you want to perform a task on one host with the reference to other hosts, use the `delegate_to` keyword on a task." | **执行位置是显式选择**；默认是目标主机，不是控制器 | 不涉及"判据" |
| A8 | [A Warm Workspace Certified the Previous Commit](https://dev.to/bytepro_1774/postmortem-a-warm-workspace-certified-the-previous-commit-pf7)（社区 postmortem，**非一手**） | "A warm job directory still held the previous commit's bytecode. Pytest imported that leftover bytecode and reported success." | **陈旧工作区导致假绿**（与本仓主控陈旧件同形） | 单一案例；且作者自述"重构时间线 · 非生产遥测"+"厂商 outreach" |
| A9 | [Jenkins Workspace Cleanup](https://plugins.jenkins.io/ws-cleanup/)（一手插件文档） | "This plugin deletes the build workspace."（社区实践：残留件会污染后续构建） | **残留件是已知失效源** | 不涉及"判据面" |

**收敛结论（E3 综合，非单条）**：**五类**独立生态（Bazel / GitHub / GitLab / Jenkins / Ansible）一致地：(i) 判据/测试在**产出环境**里跑；(ii) 判据输入（golden）**显式放入**该环境的输入根；(iii) 跨边界数据**显式搬运**；(iv) 陈旧工作区是**已知假绿/假红源**。**没有**一条支持"在控制器上、对着另一棵树判可变产物"。

**反锚点（E4 推断，防过度归纳）**：对**不可变产物**做判据时，"判一份拷贝"是**正当的** —— 前提是拷贝按**内容寻址/摘要钉住**（验的是身份，不是执行环境）。本仓主控那份既不是产物、也没有摘要钉住 ⇒ **不适用**该例外。

## 5. 方案候选与代价（供设计裁，不在此裁决）

### 甲（推荐方向）：`$judgeRoot` = 执行点

- **本地支**：`$judgeRoot = $projRoot`；golden 注入 `$projRoot/.golden`（先清空）；accept/golden 用本地 Git Bash，cwd=`$judgeRoot`。
- **站上支**：`$judgeRoot = $stWorkDir`；golden 先 scp 到 `$stWorkDir/.golden`；accept/golden 用**站上 bash**，cwd=`$judgeRoot`；输出回传后落 `accept-output.txt` / `accept-golden-output.txt`。
- **增量**：甲-1（accept）→ 甲-2（golden），两次可独立验收。
- **收益**：一处概念、同时消掉 O-165 与 O-166；与 §4 全部锚点同向。
- **代价/风险**：
  - 站上 accept 需要**输出捕获**：`Invoke-RemoteScript` 只返回 rc（[L450-454](../../ops/station-bin/agent-cli.ps1#L450-L454)）⇒ 需一个「站上写 per-run 输出件 + scp 回」的路径，或新增 capture helper；**不能**把 stdout 混进返回值（归零纪律）。
  - **解释器可用性**：`.venv/` 在 `.agentsync` 排除项里；A 站的 `paper` 工作区**有** `.venv`，`dogfood` **没有**（E1 实测）⇒ 依赖 `./.venv/bin/python` 的**示例/夹具** golden 命令在站上可能不可用；须逐项目核（或改用 `python`）。
  - Git Bash（本地）→ Linux bash（站上）语义差：现役卡的 accept 命令是 POSIX（`test`/`grep`/`find`），可迁移；含 Windows 路径的卡不可迁移（须显式拒绝或标注）。
  - golden 卡本就触发**排他租约**（`$leaseX` 含 `$goldenActive`）⇒ 在 `$judgeRoot` 写 `.golden` 无跨 run 竞争。

### 乙：先拉回产物再判

- 不够：**未在 manifest `state` 里声明的产物**不会被拉回 ⇒ accept 仍判不到；且把「判据」耦合到「collect」，golden 仍需单独 staging。

### 丙：显式拒绝「站上 claude + 文件型 accept」

- fail-closed、零假绿，但**能力损失**（所有 local-only 文件型卡不能在站上 claude 跑）；可作为过渡（与 O-42 当年的"先拒绝、后做能力"路径同形）。

### 丁：把站上工作区镜像回主控再判

- 等于"全量 sync 反向" ⇒ 会覆盖主控树、制造**两个真值**；与 ADR-0004/单一真值纪律冲突 ⇒ 不建议。

## 6. 未核 / 边界（如实）

1. **无 claude + golden 端到端真跑**（全仓 0 条）；§2.1 是离线 A/B + 代码路径，**不是**整链实弹。
2. **无"已观测到的假绿"**：§2.2 是结构 + mtime 证据；未造"站上不写、主控有旧件"的负向 run。
3. **站上解释器面未普查**：只核了 A 站 `paper` 有 `.venv`、`dogfood` 无；B/C 站与其它项目未核。
4. **输出捕获机制未定**：`Invoke-RemoteScript` 只回 rc；新 helper 或「站上 per-run 文件 + scp」尚未实现/未验。
5. **`readonly: true` + golden**：现役 claude 支给 writable 卡加 `--permission-mode acceptEdits`；golden 卡若 `readonly: true`，站上 `.golden` 的写入由**框架**做（不是 agent），应不受影响，但**未真跑**。
6. **安全面**：甲不扩大攻击面 —— 主路本来就在站上工作区执行 accept/golden；备路只是与主路同址。
7. **CRLF/引号**：`Invoke-RemoteScript` 做 CRLF→LF 归一；accept 命令若含引号/中文，仍走既有 base64/落盘纪律（主路先例）。
