## 1. 结论（TL;DR）

1. **"开源"确实改变了三件事**：可自建 / 可审计 / **配置里可指任意 OpenAI 兼容端点**（`[model_providers.*]` 的 `base_url`）。
   ⚠ 但**不改变"默认模型面在云端"** ⇒ 默认仍属**出网档**。
2. ★★ **用户的动机（治 opencode「无内置循环检测/打断」）需要收窄**：我**没有**找到 Codex CLI「内置循环检测」的证据。
   拿到的是 **`auto_review` 审查子代理 + approval_policy + sandbox + project trust** —— 那是**「批准面/沙箱」**，不是**「循环检测」**。
   ⇒ **它未必治得了"同一条无害命令重复 273 次"**这一类（那不在风险框架里）。
3. ★★★ **因此"控制点"要重新问一句**：治死循环**更可靠的位置在 wrapper 侧**（本仓已有 `timeout -k 10` 硬顶 + `CONT_ATTEMPT` 续跑上限；
   **真正缺的是"同一步重复 N 次 ⇒ 判为循环并终止"**）—— 那是**可以加一条判据**的事，**成本远低于换一条 CLI 面**。
4. **协议面出现"两处外部文档互相矛盾"**（本仓头号形态）：一说 `wire_api` **只支持 `responses`**、一说 `"chat"` 可用。
   ⇒ **本地面（站上 llama-server 走 chat/completions）能否成立，据此判断倾向"不能"**，但**必须实测**。
5. **接入面 = 8 个**（§6），且**撞两条既有治理**：`ADR-0004`（唯一管理面）+ **`O-10`/HERMES-OPTIM-01「不引入新 CLI」裁定**。

## 2. 动机核：opencode 的死循环问题（**本仓已实测记录**）

**现象（E1，本仓留档）**：同任务跨模型实测中，本地 `qwen3-coder-next` **0%（编译失败）**，
行为 = ★ **死循环（273 次 grep）**；且 **`opencode` 无内置循环检测/打断，需人工监控**。
出处：`docs/research/2026-09-28_Textbook并发与派发机制可借鉴性调研.md` §6.2（它逐字引 `SSH_OPENCODE_SETUP.md:872,901`）。

**旁证（E3）**：弱模型会 **malform `tool_calls` 导致循环**；有记录「**480B 级开源模型在 30K token 后出现工具调用幻觉回退**」（`Agent生态升级…:1068`）。

### 2.1 ★ 控制点对比（**这才是要裁的那件事**）

| 控制点 | 现状 | 治什么 | 成本 |
|---|---|---|---|
| **wrapper 侧（本仓现有）** | `timeout -k 10` 硬顶 · `CONT_ATTEMPT` 续跑上限 3 · 判官 `$try -le 3` | **兜住"永不返回"与"总次数"** | 已有 |
| ★ **wrapper 侧（缺的那条）** | **无**「同一步重复 N 次 ⇒ 判循环」 | **正是"273 次 grep"这一类** | **加一条判据**（低） |
| **换 CLI（Codex）** | 未装 | **批准面/沙箱**能拦"危险"调用；**未必**拦"无害但重复" | 新 CLI 面（§6，高） |

⇒ ★ **建议**：**先补 wrapper 那条循环判据**（低风险、立刻见效），再谈"换 CLI 是否能额外买到什么"。
否则可能出现"**花了 4–8 小时换 CLI，死循环照旧**"。

## 3. Codex CLI 事实面（**全部 E3，未复现**）

| 维度 | 事实 | 与本章相关点 |
|---|---|---|
| 许可/形态 | **开源**：`github.com/openai/codex`（npm `@openai/codex`）；OpenAI 官方工程文《Unrolling the Codex agent loop》 | 可自建/审计 |
| 非交互面 | `codex exec …`（stdin 喂 prompt）· **`codex app-server --listen stdio://`** | ★ **headless 契约存在** ⇒ 与 wrapper 的可编排性**不冲突** |
| 自定义 provider | `~/.codex/config.toml` 的 `[model_providers.<名>]`：`base_url` / **`wire_api`** / `env_key` / `http_headers` / `query_params` / `requires_openai_auth` | ★ **可指本机 OpenAI 兼容端点**（内建 Ollama / LM Studio / OpenRouter …）；`codex --oss` 直接走本地 |
| 推理档 | `model_reasoning_effort` = `low/medium/high/xhigh`（+`minimal`） | 与 `D-16` 复杂度路由**同类** |
| ★ **批准面** | `approval_policy` + **`approvals_reviewer = "auto_review"`**（**独立 LLM 审查子代理**，逐条工具调用按风险框架评估，**只把真正危险的升级给人**）；v0.147.0 起 `--approve-for-me` 单开关 | **缓解**异常调用；⚠ **不是循环检测** |
| 沙箱 / 项目信任 | `[projects."<path>"] trust_level` = `trusted` / `sandboxed` / `untrusted`（untrusted 仓库**阻止凭据使用**）；`read-only` 沙箱（macOS 是 Seatbelt profile） | ★★ **直接命中本仓纪律 7b/8/9/10**（站上射程 / `readonly` 与落文件互斥）⇒ **必须重新实测**。⚠ 第三方记录：`read-only` **denies all local writes and network**，曾**弄坏只读 checker 自己的证据工具**（`$TMPDIR` 的 socket `listen EPERM`），且**会覆盖用户配置** |
| MCP / 插件 / 技能 | **MCP 一等**（`config.mcp_servers`、MCP 2026-07-28 协议、分页工具发现）· **Agent Plugin 搜索**（4 个 catalogue scope）· **Cursor Skills 导入** · 对话回放中**凭据脱敏** | "生态更好"**有实物**，但见 §5.2 |
| 凭据 | `~/.codex/auth.json` / `CODEX_API_KEY`；OpenRouter 需 `auth = {command, args}` 形态（否则拉不到模型目录） | 与 `secrets/` 的"凭据单一真值"要对齐 |

## 4. ⚠ 一处**外部文档互相矛盾**（本仓头号形态，**未核**）

`wire_api` 到底支持什么，**三处说法不一致**：

| 来源（E3） | 说法 |
|---|---|
| Codex 官方配置文档（镜像） | `wire_api` 默认 `"responses"`；**「currently only "responses" is supported」** |
| 某第三方集成文档（Lynkr） | 给出 `wire_api = "chat"` 作为**备选**（"Alternative: Use chat completions API"） |
| `codex-as-mcp`（PyPI，注明 `Requires Codex CLI >= 0.46.0`） | ★ **「current Codex CLI rejects `wire_api = "chat"`」**；纯 chat 的 provider 需要 **Responses 兼容代理** |

⇒ **判断（倾向，非结论）**：**较新**的第三条与官方文档一致 ⇒ **大概率只支持 `responses`**。
⇒ **对本章的直接后果**：站上 `llama-server` 走 **chat/completions** ⇒ **本地面大概率不通**（除非加 Responses 兼容代理，即**多一条自维护面**）。
⚠ **必须实测**（本仓纪律：不许猜）。★ 这也是**"两处外部文档互相矛盾"**的又一条 —— **登记在案，不进任何结论**。

### 5.2 ★ 一条**轴缺口**（上一轮已登记）

那次"不引入"的 7 个维度（本地模型一等公民 / 免费额度 / 确定性编排 / 权限边界 / 生态兼容 / 三站同构 / 集成成本）
——**没有"准确率 / 输出质量"这一维**（见 `HARNESS-SAME-MODEL-BENCH-2026-09.md` §7.6）。
⇒ **若上 Codex 的理由是"质量/闭环能力"，那正是那片空地**；若是"成本/集成"，**旧裁定已覆盖**。
⇒ ★ **且** `HARNESS-SAME-MODEL-BENCH` §1 记的第三方同基座结论是 **opencode 与 claude-code 在最高档、codex 跟随**
⇒ **"生态/插件好于 opencode"目前只是推测**：本仓 opencode 侧**已按体系装备**（ARS 链 4 skills+16 commands+4 agents+1 plugin · 12 定制技能 · DCP · codex-memory），
两边**没有同任务对照** ⇒ **不得把"有 MCP/plugin search"读成"更好"**。

## 7. 未核项（**不许猜**）

1. 三站**是否已装** codex / 版本 / 残留（`command -v` + `--version`，一律 `timeout -k 10` 包住）。
2. **`wire_api` 实际支持面**（§4 的矛盾，**实测优先**）。
3. **站上沙箱射程**：`trust_level` / `read-only` 在三站 Linux 上的**真实语义**（纪律 7b/8/9/10 要重测；⚠ 有"覆盖用户配置"的第三方记录）。
4. **工具面是否真可用**（照 `O-111` 口径：报告工具清单 + **实际调用一次**自证）。
5. `auto_review` 对**无害但重复**的调用**是否**会拦（**这才是"治死循环"的关键问**）。
6. 本仓能否用 **`codex app-server`**（stdio 协议）替代裸 CLI ⇒ 影响 headless 契约形态。
7. 成本**重估**：既有 4–8 小时估算写于 **2026-09-09**，此后 wrapper 已多出 claude 分支 + A1/A2 采集点 ⇒ **只会更高**。

## 8. 建议（下一步，**二选一，不建议同时开**）

- **路径甲（推荐，先做）**：**在 wrapper 侧补"循环检测"判据**（同一步重复 N 次 ⇒ 判循环并终止 / 记档）。
  成本低、立刻覆盖 §2 的实测形态、**不碰任何治理闸**。
- **路径乙**：走 **ADR** 裁"是否引入 Codex CLI"。★ 若走这条，**ADR 里必须回答 §2.1 那一问**
  （"换 CLI 到底买到哪一项**现有手段买不到**的能力"），否则就是**用 8 面的成本**换一个**可能买不到的东西**。
