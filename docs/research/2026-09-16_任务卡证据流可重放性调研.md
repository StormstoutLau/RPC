# 任务卡证据流"可独立重放性"调研：evidence_manifest 字段 与 编排管线审计

> **日期**: 2026-09-16
> **触发**: 用户在单 agent 编排收尾阶段提出——把 Spec_Workflow 的取证矩阵从"文档审查"扩展到"任务卡验收"：① 为任务卡增加 `evidence_manifest` 字段（声明需绑定的产物类型 / 每类产物的可重放命令或提取方式 / 审计 agent 验证时需执行的最小操作集）；② 让一个**异基座** agent 审计**编排流程本身**（不是审计某张卡的产出，而是审计"从派发到验收的整个证据流是否可独立重放"）。
> **证据等级**: E1=本轮实测（含行号与实跑）；E2=前轮实测留档；E3=外部文档/标准；E4=推断
> **方法**: 双线取证 —— ① **本仓证据流清点**（全仓只读检索：wrapper / 门禁 / golden / 评审环 / 台账 / 既有产物样本）；② **社区与标准调研**（联网，2025-2026 优先，逐条附来源）；③ 对三条**承重判据**由作者**二次复核**（不采信单一来源）。
> **结论**: 方向正确且与本框架"验证方法论"内核同源，但**按字面直接实施会踩三个已知坑**（自证 / 字段被静默丢弃 / 把"可重放"误解为"重放生成"）；且**有一个前置条件比 manifest 本身更关键**——当前"判据的原始记录"根本没有被回收，`run.json` 的验收结论**是 wrapper 的转述而非可复核证据**。故建议**把顺序倒过来**：先补证据回收闭环 → 再声明化（manifest）→ 最后异基座管线审计。

## 0. 结论摘要

| # | 命题（用户提议拆解） | 可行性判定 | 关键理由（一句话） |
|---|---|---|---|
| A | 给任务卡加 `evidence_manifest`（产物类型 / 重放命令 / 最小操作集） | **可行，但不是第一步** | 解析器白名单会**静默丢弃**未知键（[Get-FrontMatter](../../ops/station-bin/agent-cli.ps1#L631)），要新增嵌套字段需仿 `accept-golden` 分支；更关键的是**被声明的物现在不在手上**（见 §2.9） |
| B | 由编排管线产出该声明 | **不可行（自证）** | 被审方产出审计声明 = self-attestation；2026-05 Mini Shai-Hulud 事件精确命中本拓扑（**推理站就是我们的 builder**）——证明"格式正确、签名有效、哈希自洽"但 builder 已被污染 |
| C | 异基座 agent 独立重放证据流 | **可行，但"重放"必须限定为"重放验证"** | 生成不可重放（temp=0 跑 1000 次得 80 个不同结果，E3）；可重放的是**能证伪的检查**：产物字节 vs 哈希、判据退出码、diff 路径白名单、输入快照哈希、脚本版本哈希 |
| D | 审计**管线**而非单卡产物 | **可行，且应作为阶段 3 的目标形态** | 与 NIST AI RMF"把建造者与验证者分开是最佳实践"一致（E3）；但审计方必须有**机械可判**的接口，否则退化为意见 |

**三个坑（本提案正踩在上面）**

1. **自证**：被审管线产出自己的审计声明（Mini Shai-Hulud）。
2. **静默丢弃**：字段进 front-matter 但不在白名单 ⇒ 解析器忽略、不报错、不进 prompt（本仓已有实证：`status:` / `note:` 两键，见 [cpphub-001.md](../../spec/d6-agent-standard/test-cards/cpphub-001.md)）。
3. **"重放"语义**：若指"重放生成、逐位一致"，物理上不成立 ⇒ 会造出"因无人能处理的原因而失败的判据"，最终被整体忽略。

**一个前置条件（比 manifest 更重要）**：`agent-out/<ts>/` 只收 4 件产物；承载判据结论的 `.meta`、吞吐 trace `.progress`、以及远端 `out/.prompt.txt` / `.accept-cmds.txt` / `.golden-cmd.txt` **全部未回收**，**golden 当次 checksum 也无任何存档** ⇒ 主控侧只能证明"产物字节没被改过 + JSON 自洽 + 标识字段对得上"，**不能**证明"判据真的跑过、golden 真的通过"。

## 1. 提议原文与拆解

用户原文（要点）：为任务卡增加 `evidence_manifest` 字段，声明 **①需要绑定的产物类型（文件/diff/stdout/哈希/测试结果）②每类产物的可重放命令或提取方式 ③审计 agent 验证该产物时需要执行的最小操作集**；然后让一个**异基座 agent** 对**编排流程本身**做一次审计——审计"任务卡从派发到验收的整个证据流是否可独立重放"。

拆成四个可独立判定的子命题：

| 子命题 | 语义 | 归属阶段（本报告建议） |
|---|---|---|
| **A. 声明化** | 把"这次应该产出什么证据、怎么取、怎么验"写进卡，成为可机读契约 | 阶段 1 |
| **B. 采集** | 证据必须被**回收**到主控侧并归档（否则 A 是空头声明） | **阶段 0（前置）** |
| **C. 复验** | 有一方能**不看站上、不重跑生成**就复验证据 | 阶段 2 |
| **D. 管线审计** | 异基座 agent 审"证据流本身"是否可独立重放 | 阶段 3 |

> 注意：用户把 A 放在最前面，但**证据流的瓶颈在 B**。B 不做，A/D 都会退化成"声明了可重放命令，但被声明的物不在手上"——这正是 in-toto layout 的公开失败形态（E3，见 §5.6）。

### 2.9 现状能力边界总结

**已可独立复核（不依赖模型/远端自述）**
1. 产物字节完整性：`agent-output.txt` → 重算 SHA256 ≡ `content_digest`。
2. 契约自洽：run.json 的 JSON 合法性、键集、`status ↔ exit_code ↔ accept.passed ↔ accept_golden.passed` 推导一致性。
3. 索引一致性：台账 7 列与 run.json 的 `ts/proj/model/sens/exit_code` 可机械对齐。
4. 判据原始输出**可人工判读**：`accept-output.txt` 含 `ACCEPT_CMD[i]/ACCEPT_RC[i]`；golden 输出含 `GOLDEN_FAIL + 原因`。
5. golden **源文件现状**可哈希（但**当次** checksum 无存档）。
6. `review.json` 结构 + judge 元数据（含"judge 与产出模型异源"的配置事实）。

**只有自证（模型或 wrapper 自己说）**
1. `status` / `accept.passed` / `accept_golden.passed` —— 全部由 wrapper 解析远端 `.meta` 后**转述**；`.meta`、`out/.prompt.txt`、`out/.accept-cmds.txt`、`out/.golden-cmd.txt` **均未回收** ⇒ 判据是否真在站上执行、退出码是否真为 0，**事后无法回溯**。
2. `.progress` 吞吐 trace —— 主控只留换算后的两个数。
3. `usage.total_tokens/tool_uses` —— 恒 0。
4. `attach` 只存 basename、**无哈希** ⇒ "附件确实按预期注入"不可核。
5. `prompt_sha256` —— prompt 正文不落主控，只能"有卡才能重算"。
6. `review.json` 的 `score/pass/evidence/conclusion` —— 纯模型语义判断（`temperature=0` 非充分，MoE 批路由下不可 bit-reproducible，设计文档自承）。
7. golden 防篡改 —— 只防"注入后被改"，对"读字面量→改→还原"的协同篡改**明确不设防**。

## 5. 社区与标准调研（联网，2025-2026 优先；逐条附来源）

### 5.1 供应链证明体系：产物 + 可复核证明怎么定义

- **SLSA 的核心数据模型就是"产物 + 声明 + 签名"三层**：`subject`（产物，通常用内容哈希标识）、`predicateType`、`predicate`。SLSA Provenance 的谓词体分 `buildDefinition`（`buildType`/`externalParameters`/`internalParameters`/`resolvedDependencies`）与 `runDetails`（`builder.id`/`metadata.invocationId` 等）。**官方明确区分：`externalParameters` 不可信、必须被下游验证；`internalParameters` 由平台写入、可选**——这正是"任务卡声明 vs 编排站内部配置"的现成切分。→ [SLSA Provenance v1](https://slsa.dev/provenance/v1/)
- **版本现状（别引用过时版本）**：SLSA v1.0 已 Retired，v1.1（2025-04 Approved），**v1.2 于 2025-11-24 发布为当前版本**；Build 轨只有 L1（有 provenance）/L2（托管平台 + 签名 provenance）/L3（加固隔离 builder）。→ [Announcing SLSA v1.2](https://slsa.dev/blog/2025/11/announce-slsa-v1.2)、[SLSA v1.2 spec](https://slsa.dev/spec/v1.2/)
- **SLSA 鼓励"没有合适谓词就自己发明一个"**，推荐套件 = DSSE 信封 + in-toto Statement + 自定义 predicate + JSON Lines bundle；但 `Storage/Lookup`（证明存哪、怎么找到）官方标注 **TBD**——这部分必须自定。→ [SLSA: Software attestations](https://slsa.dev/attestation-model)
- **in-toto 是"流程级"证明**：Layout 声明各步骤 + 授权执行者 + inspections；每步产出 Link 元数据（materials → products）；验证时把 layout 策略套用到 attestation 集合上。SLSA v1 只是 in-toto 的一个"有主见的谓词"。→ [in-toto and SLSA](https://slsa.dev/blog/2023/05/in-toto-and-slsa)、[in-toto/attestation](https://github.com/in-toto/attestation)、[validation model](https://github.com/in-toto/attestation/blob/main/docs/validation.md)
- **Sigstore 的关键贡献是"自包含可离线验证的 bundle"**（tlog 条目含 logIndex/inclusionProof/checkpoint）；**Rekor v2 已于 2025-10 GA**，按年分片 URL，官方要求**不要硬编码 URL**（走 TUF 分发）。→ [Sigstore Bundle Format](https://docs.sigstore.dev/about/bundle/)、[Rekor v2 GA](https://blog.sigstore.dev/rekor-v2-ga/)
- **GitHub Artifact Attestations = 平台代签的最小可用形态**：`id-token: write` + `attestations: write`，`actions/attest@v4`；校验 `gh attestation verify`，可加 `--signer-workflow/--signer-repo` 把"谁签的"变成可校验断言；**支持离线/air-gapped 校验**。→ [GitHub Docs: use artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- **SLSA 的验证流程本身就是"审计 agent 最小操作集"模板**：① 用预置 root-of-trust 把 `builder.id` 映射到信任等级并验签；② 校验期望（`buildType`/`externalParameters` 必须匹配，**任何未识别的 externalParameters 应导致校验失败**）；③ 可选递归校验依赖。→ [SLSA: Verifying artifacts](https://slsa.dev/spec/v1.0/verifying-artifacts)
- **"证明太贵"的标准解药是 VSA**（Verification Summary Attestation）：受信验证者合并多份 attestation 后发布签名摘要，下游只校验一份。官方在攻击复盘中直言"全面验证很贵，很少有组织能独立重验依赖图里的每一条"。→ [VSA](https://slsa.dev/verification_summary/v1)、[Mini Shai-Hulud](https://slsa.dev/blog/2026/05/mini-shai-hulud-what-slsa-can-and-cannot-do)

### 5.2 AI/agent 可观测性与轨迹标准

- **OTel GenAI semconv 当前是 Development（实验性）且刚迁仓**：主 semconv 页标注 "GenAI Attributes (Moved)"，定义在独立仓库，所有 agent/事件字段 Stability 仍 Development，并引入 `OTEL_SEMCONV_STABILITY_OPT_IN` 管理新旧并存。⇒ **它是命名参考，不是稳定契约。** → [OTel Gen AI attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)、[semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)
- **Agent span 原语已足够覆盖"编排管线"**：`create_agent` / `invoke_agent`（client/internal）/ `invoke_workflow` / `plan` / `execute_tool`；关键属性 `gen_ai.operation.name`/`gen_ai.agent.id|name|version`/`gen_ai.conversation.id`。→ [GenAI agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- **输入输出/hash 被拆成两类事件**：`gen_ai.client.inference.operation.details`（Opt-In，可独立于 trace 存储输入输出详情，含 `gen_ai.request.seed`、prompt 版本）与 `gen_ai.evaluation.result`。→ [GenAI events](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)
- **OpenInference 把"可解释 vs 可复现"写进设计动机**：trace 必须携带足够上下文以"**复现——或至少解释**"某次执行；10 类 span kind，其中 `CHAIN` 被定义为"**确定性操作序列（prompt 格式化、编排逻辑）**"——**这正是"可重放部分"与"不可重放部分"的分界线**。→ [OpenInference Spec](https://arize-ai.github.io/openinference/spec/)
- **Langfuse 三层模型 + 字段清单可直接当 manifest 字段参考**：observation（`type`=span/generation/event/tool、`input`/`output`、`metadata`、`model_parameters`、`usage_details`、`tool_calls`）→ trace（`user_id`/`session_id`/`tags`/`release`/`version`）→ session；支持按字段组导出到对象存储（便于裁剪与脱敏）。→ [Langfuse Data Model](https://langfuse.com/docs/observability/data-model)、[Export to blob storage](https://langfuse.com/docs/api-and-data-platform/features/export-to-blob-storage)
- **"只依赖三类 span 就能重放+评分"的工业落地**：Bedrock AgentCore Evaluations 只要求 `invoke_agent`/inference/`execute_tool` 三种 span 角色，其余（retrieval/rerank/guardrail/memory）"只是额外上下文，不读也不影响"。⇒ **"最小操作集"思路的工业体现**。→ [Amazon Bedrock AgentCore Evaluations](https://aws.amazon.com/blogs/machine-learning/evaluate-any-agent-framework-with-amazon-bedrock-agentcore-evaluations/)
- **关键区分：trace ≠ audit trail**：可观测 trace 可被整体重写，不是审计证据；补救方式是 append-only + `prev_hash` 的链路，任何 edit/delete/reorder 都在**第一条**断裂处被定位。→ [How to Detect a Tampered AI Agent Audit Trail](https://docs.promptise.com/blog/detect-a-tampered-agent-audit-trail/)

### 5.3 可复现性与非确定性：社区如何界定"可重放"

- **`temperature=0` 与 `seed` 都不等于确定输出**（官方措辞 "best effort"、"mostly identical"，并要求核对 `system_fingerprint`）。→ [OpenAI Cookbook: Reproducible outputs](https://github.com/openai/openai-cookbook/blob/main/examples/Reproducible_outputs_with_the_seed_parameter.ipynb)
- **根因是"缺少 batch invariance"而非单纯浮点结合律**：Qwen3-235B、temp 0、同 prompt 跑 1000 次 → **80 个不同结果**（前 ~102 token 相同后分叉）；换 batch-invariant kernel 后 1000/1000 逐位一致。→ [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- **量级证据**：仅改变 GPU 数量/型号与 batch size，一个 7B 模型可出现最高 ~9% 准确率波动与 ~9000 token 长度差异；"确定性设置"下 gpt-4o-mini 约 1/4 概率产出不同结果、llama3.1-8b 约 1/10。→ [arXiv 2506.09501](https://arxiv.org/html/2506.09501v2)、[arXiv 2601.19934](https://arxiv.org/pdf/2601.19934)
- **"只重放验证、不重放生成"是主流解法**：
  - `agrepl`（传输层 MITM 拦截 + 零出网隔离重放，replay fidelity F=1.0，单步延迟 -98.3%；提出**噪声感知 diff** 把差异分 signal/noise）→ [arXiv 2607.16200](https://arxiv.org/pdf/2607.16200)
  - `agenthound`（pytest 原生录放，回放零 API 调用；断言分 Schema/Constraints/Trace/Content 四层）→ [agenthound](https://pypi.org/project/agenthound/)
  - `timewarp-llm`（event-sourced + `PlaybackLLM` 注入已记录输出**并对 prompt/args 做校验**；OTel span 用 Span Links 指回原 run；属性含 `tw.hash.output|state|prompt`；提供 **first divergence** 定位）→ [timewarp-llm](https://pypi.org/project/timewarp-llm/)
- **LangGraph 官方把界线写得很清楚**：replay 会**重新执行** checkpoint 之后的节点（"包括 LLM 调用、API 请求——会再次触发且可能返回不同结果"），checkpoint 之前跳过。→ [Use time-travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)
- **"state replay / event-sourced agent"已成独立方向**：
  - `AgentRR`（SJTU）：把 record-and-replay 引入 agent，提出多级 experience 抽象 + **`check function` 机制作为重放期的"信任锚"** —— **"审计时需执行的最小操作集"最贴切的学术对应物**。→ [arXiv 2505.17716](https://arxiv.org/pdf/2505.17716v1)
  - `ESAA`：trace-first，agent 只发结构化意图，确定性 orchestrator 写 append-only `activity.jsonl`，提供 `esaa verify` 做哈希重放校验，强调"完成的任务不可回退"。→ [arXiv 2602.23193](https://arxiv.org/pdf/2602.23193v1)
  - `The Log is the Agent`：append-only 事件日志即事实源，给出 **determinism contract** + 内容寻址缓存使重放"不产生任何新的模型调用"，支持从任意事件 fork。→ [arXiv 2605.21997](https://arxiv.org/pdf/2605.21997.pdf)
  - Temporal `Durable AI Agent Loop`：三原语 = 确定性控制流 + 受管副作用抽象 + event-sourced 状态持久化；"确定性指**编排逻辑**可复现，LLM 推理等非确定性操作须封装为副作用抽象"。→ [Durable Execution for AI Agents](https://agtnyc.com/newsletter/papers/durable-execution-for-ai-agents.pdf)
  - 综述式工程总结：**"traces 说明发生了什么，event-sourced runtime log 定义了什么可以被安全重放"**。→ [Replayable Agent Runtimes](https://zylos.ai/research/2026-04-24-replayable-agent-runtimes-event-sourced-execution/)
- **"离线校验 receipt 而非重跑"已工程化**：receipt 形态（sealed brief + 每条 claim 的 verdict + evidence id + 签名），校验做 parse/schema/invariants/doctrine/signature 五类检查；关键性质是**离线、无账号、不信任发送者**，被篡改的 receipt 只有签名一步失败。→ [Loopeix walkthrough](http://raw.githubusercontent.com/naveix/loopeix/HEAD/docs/tutorial/walkthrough.md)

### 5.4 审计与治理框架：对"证据/日志/可追溯性"的要求

- **EU AI Act Art.12/19 把"可追溯"写成技术能力要求**：高风险系统须"在技术上允许对事件自动记录（logs）贯穿生命周期"；提供者须保留自动生成日志**至少 6 个月**。→ [Art.12](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-12)、[Art.19](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-19)
- **Art.12/19 的记录是"逐次决策级"的**，不能由 GDPR Art.30 的"处理活动级"记录替代。→ [Records of Processing beyond GDPR Art.30](https://www.deepinspect.ai/blog/eu-ai-act-records-of-processing)
- **一个结构性张力**：Art.12 的"全量留痕"与 GDPR 最小化/存储限制冲突，业界主张在**输入层剥离 PII**。（厂商白皮书，观点性来源）→ [The Article 12 Paradox](https://cloakllm.dev/article12-paradox-whitepaper.pdf)
- **NIST AI RMF**：自愿、非认证，但 MEASURE 要求"记录系统功能与可信度的可核查文档"；4 功能 / 19 类 / 72 子类。→ [AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)、[AI RMF 1.0](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf)
- **NIST 隐含地制度化了"异基座审计"**：AI RMF 图 3 说明明确写"**把构建/使用模型的人与验证/确认模型的人分开，是最佳实践**"。→ 同上
- **NIST GenAI Profile（AI 600-1）给的是"每项 action 一个 ID + 一份证据产物"的记账法**，并明确警告"**一份运行时日志无法证明整个框架**"。→ [NIST GenAI Profile: Risks, Actions, and Evidence](https://www.deepinspect.ai/blog/nist-genai-profile)
- **ISO/IEC 42001 是"可认证的管理体系"**：Annex A 共 38 控制 / 9 目标，A.6（生命周期）最多，含 **A.6.2.4 验证与确认、A.6.2.7 技术文档、A.6.2.8 事件日志记录**；标准不规定日志格式，但 Clause 9 要求的是**运行期产生的记录**。→ [ISO/IEC 42001:2023](https://www.iso.org/obp/ui/es/#!iso:std:81230:en)、[Annex A 控制清单](https://riskprofs.com/iso-42001-annex-a-controls-list/)
- **"audit the pipeline, not just the artifact"确有公开提法**：VeriEvol 论文公开 prompt/数据/模型/代码与**每个样本的完整 verifier trace**，理由是让下游"**audit the pipeline rather than only inspect its outputs**"。标准侧最接近的表述是 SLSA 的 "Trust platforms, verify artifacts" 与 in-toto 的 layout（把策略施加在**步骤**上）。→ [VeriEvol (arXiv 2606.23543)](https://arxiv.org/html/2606.23543v1)、[SLSA 设计原则](https://slsa.dev/spec/draft/principles)

### 5.5 多模型交叉审计（异基座评审的依据）

- **自偏好是可测量现象**（"LLM Evaluators Recognize and Favor Their Own Generations"）；2026 年量化研究在 20 个模型上测出"能力更强与低自偏置**不相关甚至负相关**"。→ [arXiv 2604.22891](https://arxiv.org/html/2604.22891v2)
- **但需与方法学混杂区分**：有工作发现"自我偏好式回答"这一混杂因子"仅此一项就可把测量误差降低 89.6%"。→ [arXiv 2601.22548](https://arxiv.org/html/2601.22548v2)
- **区分 legitimate vs harmful self-preference**：在可验证基准上，更强模型出错时表现出**更强**的 harmful 自偏好；**长 CoT 可有效降低**。→ [arXiv 2504.03846](https://arxiv.org/html/2504.03846)
- **偏见是"家族级 + 风格级"**：盲测审计（4 前沿模型 / 2 家族 / 1152 次成对判定）测得 self-preference index 全为正、均值 **+0.14**（GPT-4o +0.21），且**4 个模型里只有 1 个能在高于随机水平认出自己的输出，但 4 个全都自偏好**；同时报告 **position bias（第一个回答胜率 63%）** 与近乎确定的长度偏好（r=0.98）。⇒ **这直接支持"换基座（家族）而非换实例"**。→ [The Judge in the Mirror](https://labs.iovstudio.kr/papers/self-preference.pdf)
- **jury / panel 优于单一 judge**：Cohere PoLL 用三个**不同家族**的小模型组成 panel，在 6 个数据集上优于单个 GPT-4 judge、intra-model bias 更低、成本低 7 倍以上。→ [arXiv 2404.18796](https://arxiv.org/pdf/2404.18796v1)、[Arize: LLM as a Jury](https://arize.com/llm-as-a-jury/)
- **panel 的边际价值可被度量**：把 judge panel 视为 role-conditioned allocation，从标注审计集判定每个候选 judge 是 **copy（无信息增益）/ complement（全局增益）/ specialist（切片增益）**，据此丢弃 copies、按条件路由、增益低于阈值即停止。→ [arXiv 2608.19802](https://arxiv.org/html/2608.19802v1)
- **工程实践侧"异基座审计"已是常见做法**，且给出角色选型与"**unanimity is a low-signal event**"（全员一致反而低信息量）。→ [Cross-Model Adversarial Review](https://codex.danielvaughan.com/2026/03/28/cross-model-adversarial-review/)、[Claude Loops: Verification](https://lucagattoni.github.io/Claude-Loops/04-verification/)、[Refute-or-Promote (arXiv 2604.19049)](https://arxiv.org/html/2604.19049)

### 5.6 落地反面教训（证据清单过重 / 审计被绕过）

- **SLSA 采纳实证研究**：233 仓库 / 1523 条 issue 的主题分析，两大挑战是 **complex implementation** 与 **unclear communication**；"**生成的 attestation 该存哪里**"在标准里仍悬而未决。→ [arXiv 2409.05014](https://arxiv.org/pdf/2409.05014.pdf)
- **in-toto layout 的失败模式（社区自承）**：**非常不灵活**（约束一改就难写）、构建 layout 需"全图视角"导致能写的人很少、**几乎没有生产级参考 layout**；自 attestation 兴起后 layout 被落在后面。⇒ **不要把"每步声明式策略"做成全局 layout**。→ [in-toto-policies: Problems with in-toto layouts](https://pkg.go.dev/github.com/alanssitis/in-toto-policies)
- **"合法 attestation ≠ 可信构建"（审计被绕过的最强案例）**：2026-05 Mini Shai-Hulud 中，84 个 npm 包携带**密码学有效、指向正确仓库与 workflow** 的 provenance，但攻击链是 `pull_request_target` → 缓存投毒 → 从 runner 内存窃取 OIDC token 后签名；结论是"**attestation 只记录构建平台观察到的东西；当攻击者代码在平台内运行时，观测是准确的，但构建已被攻陷**"，而 npm 内置 provenance 只到 Build L2（L2 不要求隔离）。⇒ **精确命中本框架拓扑：推理站就是 builder**。→ [Mini Shai-Hulud: Where SLSA's Boundaries Fall](https://slsa.dev/blog/2026/05/mini-shai-hulud-what-slsa-can-and-cannot-do)
- **"逐条证据"会退化为告警疲劳**：SBOM 漏洞管理实证研究（CODASPY'26）指出不可达/无关告警造成巨大 verification burden ⇒ 用户脱敏并开始忽略告警，反而漏掉真漏洞。→ [arXiv 2511.20313](https://arxiv.org/html/2511.20313v2)
- **"只统计不核查"的量化证据**：NDSS 2025 的 JBomAudit 发现 25,882 份 Java SBOM 中 7,907 份（~30.6%）**漏掉至少一个直接依赖**。→ [CRA SBOM mistakes](https://craevidence.com/cra-compliance/sbom/common-mistakes)
- **"证据链空转"的真实案例**：2026 年初 Delve 事件中，据调查报道其 SOC 2 报告大量雷同（Type II 审计被压缩到数小时），核心教训是**没人读那份 80 页报告**——"下游从不验证"会让整套证据体系失效。→ [The $300 million compliance factory that certified nothing](https://sulat.com/p/delve-fake-compliance-scandal)
- **Goodhart：指标一旦成为目标就被优化**：Leaderboard Illusion（2M battles / 243 models）发现未公开私有测试 + 选择性披露导致"**对分布过拟合而非真实质量**"，极端例子是某厂商发布前测 27 个私有变体只公布最好的一个。→ [arXiv 2504.20879](https://arxiv.org/pdf/2504.20879)、[Simon Willison 评论](https://simonwillison.net/2025/Apr/30/criticism-of-the-chatbot-arena/)

### 7.2 `evidence-manifest` 字段草案（阶段 1 用，需走 ADR/D3 后落地）

```yaml
evidence-manifest:
  version: 1
  # ① 需绑定的产物类型 + 提取方式（对齐 SLSA subject：name + digest）
  subjects:
    - name: agent-output        # 已有
      path: agent-output.txt
      digest: sha256
    - name: accept-stdout       # 已有
      path: accept-output.txt
      digest: sha256
    - name: workspace-diff      # 缺失类：readonly 卡的"未越界"证据载体
      collect: "git -C $W diff --no-color; git -C $W status --porcelain"
      digest: sha256
    - name: judgment-record     # 缺失类：当前只有 wrapper 转述
      path: .meta
      digest: sha256
  # ② 审计方可执行的"最小操作集"（只做能证伪的检查；对齐 AgentRR check function）
  replay-ops:
    - id: digest-match
      op: "重算 subjects 各文件 sha256，与 run.json/manifest 比对"
    - id: verdict-chain
      op: "parse .meta 的 TASK_RC/ACCEPT_OK/ACCEPT_GOLDEN_OK → 与 run.json 的 status/accept.passed/accept_golden.passed 一致性"
    - id: golden-identity
      op: "当次 golden checksum == 当前仓库 golden 源哈希（或与登记的期望哈希一致）"
    - id: diff-scope
      op: "readonly 卡：diff 为空或仅触碰 allow-paths"
  # ③ 明确"本清单不做判据"的范围（防自证扩张 + 防判据过重）
  not-a-judgment:
    - "模型语义结论（review.json 的 score/pass/conclusion）"
    - "逐位可复现（非确定性，物理不成立）"
```

**设计要点（均来自 §5 的可借用项）**
1. **形状借 in-toto Statement**（`subject` + `predicateType` 自定义 URI + `predicate` 三块），**不要**自创一套语义。
2. **语义切成 external / internal 两类**：模型名、超时、验收命令、采样参数（seed/temp）属 **externalParameters**——必须落盘、必须逐项核对、**未识别即失败**；站内配置（线程/NUMA/版本细节）属 internalParameters——记为可选。
3. **记录输入快照比记录输出更有价值**（`resolvedDependencies` 思路）：prompt 全文哈希、附件哈希、模型权重/量化文件哈希、llama.cpp/运行时版本与 commit、golden 脚本哈希、**semconv/契约版本号**（否则半年后证据无法自解释）。
4. **`replay-ops` 只放"能证伪的检查"**：可机判 pass/fail、误报低、失败能给行级定位。做不到的**删掉而不是留着**。
5. **审计输出应是 gap 表**（哪条 replay-op 无法执行、缺哪件证据、哪条声明与实际不符），而不是"评分"——评审环已经承担评分，管线审计应承担**可重放性**。

### 7.3 对既有的复用（避免新造）

## 8. 风险与护栏

| 风险 | 护栏 |
|---|---|
| **自证**（被审管线产出自己的声明） | 声明与采集分离：`evidence-manifest` 由**卡**声明（卡是输入，不是运行产物）；**证据由主控侧采集**；审计方核对"声明 vs 实际"，且 `builder.id`（站 + 模型 + 运行栈）作为一等字段 |
| **审计项过重 ⇒ 没人看** | 每条 replay-op 必须满足三条件（可机判 / 低误报 / 行级定位）；**不满足就删**（SBOM 告警疲劳教训） |
| **清单变 KPI 被优化** | golden 脚本哈希入 manifest；周期性由异基座 agent **反向挑战 golden 本身**；人工 override 留痕并回灌 |
| **"一致性"判定被噪声淹没** | 差异分级（signal/noise）+ first-divergence 定位，而不是"全等/不等" |
| **审计方自身有偏** | 跨**家族**；顺序对调（position bias 63%）；A/A 基线；不把"全员一致"当强信号 |
| **合规映射过度** | EU AI Act Art.12/19 只约束**高风险**系统；ISO 42001 A.6.2.8 是与我们日志设计直接对应的控制项；不要按"合规叙事"设计判据 |
| **解析器被新字段破坏** | 嵌套键必须仿 `accept-golden` 分支；顺带修围栏"遇 `---` 即翻转"的陷阱（见 §2.8） |

## 9. 明确不建议照搬

1. **不要复刻 in-toto layout**（社区自评：不灵活、难写、缺参考样例）⇒ 采用"每张卡自带最小断言"。
2. **不要宣称 SLSA L3**（其语义是"加固隔离 builder"，本拓扑不满足）⇒ 用 L1/L2 语义更诚实。
3. **不要照搬 Sigstore keyless/OIDC + Rekor 运维模型**（本地无 OIDC；Rekor v2 要求不硬编码 URL 且走 TUF）⇒ 本地用长期密钥 + append-only 哈希链，**链头外置**。
4. **不要把 OTel GenAI semconv 当稳定契约**（仍 Development 且刚迁仓）⇒ 借字段命名，但**把所用版本号写进 manifest**。
5. **不要把"重放生成、逐位一致"当验收标准**（物理不成立；且"一个因无人能处理的原因而失败的测试套件最终一定会被忽略"）。
