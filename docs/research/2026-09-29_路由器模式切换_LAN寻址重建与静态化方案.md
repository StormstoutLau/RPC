# 路由器「桥 → 路由」模式切换 · LAN 寻址重建与静态化方案

> **性质**：调研 / 方案（单一主题）· **建立日期**：2026-09-29 · **证据**：E1 = 本集群实测
> **触发**：路由器由**桥模式切到路由模式** ⇒ 整张 LAN 重建（`192.168.1.0/24` → `192.168.10.0/24`），
> 三站与主控**全部换地址**；门禁由「可达 2/3 站」变为「**可达 0/3 站**」。
> **同源前篇**：[控制面 LAN 地址漂移 · 失效归因与判据升级](./2026-09-29_控制面LAN地址漂移_失效归因与判据升级.md)
> （那篇是「**池内漂**」，本篇是「**整段换**」—— 症状同族，**根因不同**）
> **脱敏口径**：本文按 C3 最小化 —— **不含 MAC 地址 / 家用设备名 / 路由器型号**（见 §7）

## 1. 事件与根因（E1）

**根因**：路由器工作模式由 **桥**改为 **路由** ⇒ 它开始**自己发 LAN**（新网段 `192.168.10.0/24`），
原先由上游侧持的 `192.168.1.0/24` 不再承载本网络。⇒ 不是"某台机器的 DHCP 重租"，而是**整网重建**。

| 角色 | 旧地址（真值登记的） | 新地址（实测） | 交叉验证 |
|---|---|---|---|
| 站 A | `192.168.1.33` | **`192.168.10.105`** | 路由器 DHCP 租约表 |
| 站 B | `192.168.1.32` | **`192.168.10.104`** | 租约表；且其 LAN 网卡 MAC 与站上实况一致 |
| 站 C | `192.168.1.37` | **`192.168.10.106`** | 租约表；其 MAC == C 站 `eno1` 的 MAC（本次实测过） |
| 主控 | `192.168.1.36` | **`192.168.10.102`** | 租约表（该机在旧网段曾是 `.104`，见 C 站 ARP 留痕） |
| 上游 AP | — | `192.168.10.101` | 租约表（旧网段在 `.5`） |
| 其它家用设备 | — | 池内 `.100` / `.103` / `.107` 等 | 与本次无关，**不具名**（见 §7） |

**★ 要害三条**（合起来解释"不稳定"）：
1. 三站 + 主控**全都在 DHCP 池内**（`.100–.199`）；
2. **租期仅 120 分钟**；
3. 池有 100 个地址 ⇒ 它们会在整段内**持续漂**。

**USB4 数据面未受影响**：`10.10.x` 是站间点对点、由各站自己配 ⇒ 本次诊断与部署**全程靠它**完成
（`主控 → B(LAN) → C(USB4)`）。这条通道此前已在真实故障中证明可用（见前篇 §1-#7）。

## 3. ★ 解锁：池边界已知 ⇒ ADR-0006 的 **D5 前置条件成立**

D5（C 站 LAN 静态化）此前**阻塞**，理由是"不知道 DHCP 池范围 ⇒ 挑不出**确定安全**的静态地址"
（前篇 §4-A 已实测判定 `.37` 在旧池内）。**本次池边界明确**：

- 池 = **`.100 – .199`**（租期 120 分钟）
- ⇒ **静态安全段 = `.2 – .99`**（★ 本次实测扫描：**整段零 ARP 记录，完全空闲**）与 `.200 – .254`

⇒ 「站上钉静态」由"不安全"变为"**可证安全**"（前提：池**不再被改宽** —— 见 §5 的不变式）。

## 4. 推荐方案：末位八位组不变，只把网段八位组 `1` → `10`，然后**站上钉静态**

| 设备 | 目标静态地址 | 与旧真值的关系 |
|---|---|---|
| 站 A | **`192.168.10.33`** | 末位 `.33` **不变** |
| 站 B | **`192.168.10.32`** | 末位 `.32` **不变** |
| 站 C | **`192.168.10.37`** | 末位 `.37` **不变** |
| 主控 | **`192.168.10.36`** | 末位 `.36` **不变** |

**为什么这样选**：
1. **末位零改动** ⇒ `inventory/net.yaml` / `ops/cluster_const.py` 的 `STATIONS` / 主控 `~/.ssh/config`
   以及手册与调研文档里 20+ 处 `192.168.1.x` **只需把第三段 `1` 改 `10`** —— 人的肌肉记忆与文档可读性都不变；
2. 四个地址都落在 `.2–.99` ⇒ **在池外**，与池内设备**永不相撞**；
3. 不需要再引入一套新命名方案。

**备选**（若你更想要"整齐好记"）：`.10/.11/.12/.13` 之类。缺点 = 文档与文档间引用要成套改，收益有限。

## 5. 为什么用「站上静态」而不是「路由器 MAC 保留」

同型事故已是**第 3 次**（`.24 → .37 → 整段换网`），而**本次的根因恰恰是路由器侧被改配置**。

| | 路由器 MAC 保留 | **站上静态（推荐）** |
|---|---|---|
| 权威在哪 | 路由器 | 各站自己 |
| 本次事故下 | 换模式/重置即**被抹掉** | 不受影响 |
| 前置依赖 | 路由器管理面 | 仅需地址在池外（**已确认**） |
| 失败面 | 单点（改配置/复位） | 分散，且每站可独立回滚 |

⚠ **诚实说明残余耦合（不可消除）**：静态地址仍落在 `192.168.10.0/24` 内 ⇒ 若路由器**LAN 网段**
再改（例如改 `192.168.20.x`），控制面照样断。这层**消除不掉** —— 主控在 WLAN 上，够不到站间的
USB4 点对点段（`10.10.x`）。

★ 但它现在**有判据**：D6 会当场报「master / 某站 LAN 已漂移 + 根因」，而不是"可达 0/3 之谜"。
⇒ 把下面两条登记为**不变式**（写进 `net.yaml §lan`，与既有的"改了网络就改本表"并列）：

- **不变式 1**：路由器 LAN 网段 = `192.168.10.0/24`
- **不变式 2**：DHCP 池 = `.100–.199`（**不得改宽进 `.2–.99`**）

## 6. 操作清单（含退路）

**① 三站** —— ★ **经 USB4 会话操作**（改 LAN 不影响 USB4，全程有退路；C 走 `B → 10.10.11.3`）：

```bash
nmcli -t -f NAME,DEVICE con show          # 先确认连接名（C 是「有线连接 1」，A/B 待实测确认）
sudo nmcli con mod '<连接名>' \
  ipv4.method manual ipv4.addresses 192.168.10.<末位>/24 \
  ipv4.gateway 192.168.10.1 ipv4.dns 192.168.10.1 ipv4.ignore-auto-dns yes
sudo nmcli con up '<连接名>'
# 回滚（一条命令）
sudo nmcli con mod '<连接名>' ipv4.method auto ipv4.ignore-auto-dns no && sudo nmcli con up '<连接名>'
```
⚠ `ipv4.ignore-auto-dns yes` **别漏** —— 否则 DHCP 残留的 DNS 会混进来。

**② 主控（Windows / WLAN）** —— 同样钉 `192.168.10.36`（子网 `255.255.255.0`、网关/DNS `192.168.10.1`）。
★ **建议在你能坐到机器前时再做**：WLAN 改静态写错会掉线、需本地改回。
★ 且主控的 WLAN **是整条控制面最脆的一环**（本次就是它先变、一次带走全部三站）。

**③ 路由器** —— DHCP 池**保持 `.100–.199` 不动**（家用设备继续吃 DHCP）；**不要**把池改宽。

**④ 真值源同步**（D6 判据会当场点名，改完才变绿）：
`inventory/net.yaml`（§lan 的 `stations` / `master` / `dhcp`，并把 `known_drift` 收敛）·
`ops/cluster_const.py` 的 `STATIONS` · 主控 `~/.ssh/config` · 文档里的 `192.168.1.x` 全量替换。

**⑤ 顺带**：池内"网关/DNS = 0.0.0.0"= 由路由器自己充当。若旧上游仍在，当前可能是**双重 NAT** ——
簇内通信不受影响，仅影响出网（将来需要端口映射时再看）。

## 7. ★ 脱敏口径（本节即"要不要 gitignore"的落档）

**结论：不走 gitignore，走本仓既有的档位机制 + 对新增件做"与判据无关的指纹剔除"。**

**为什么不用 gitignore**（三条，可复核）：
1. **挡不住已公开的历史**：本仓远端正 `git@github.com:StormstoutLau/RPC.git`，**visibility = PUBLIC**；
   `inventory/net.yaml` 里 `192.168.1.x` / `10.10.x` / 主机名**早已在公网**
   ⇒ 把新文档排除只**新增不披露**，却要付出下面两条代价。且本仓已有一条**豁免裁定先例**明写同一逻辑：
   *"本仓已公开 ⇒ 降档不新增『披露』，只新增『可送第三方 LLM』这一项"*。
2. **会切断证据链**：ADR-0006 v1.2 的验收 **V13**（现场真实命中）指向的件会离开版本控制；
   而"证据可复核"是本仓命门（ADR-0007 的整条纪律）。
3. **门禁看不见未跟踪件**：本仓已踩过一次 —— *"新写的文档在 `git add` 之前不进判据"*
   ⇒ `doclinks` / `spec-untested` 会对被你忽略的那部分**静默失效**。

**本仓本来就有这一层**：`inventory/sensitivity.yaml`（`default_tier = local-only`）逐条登记
`tier` + `fails` + `why`，判据口径为
**C1** 未发表研究方向 / **C2** 他方项目内部（他方未发表）/ **C3** **基础设施指纹**；
配套 [cluster_egress.py](../../ops/cluster_egress.py) 对 local-only 件出网 `REJECT`。
★ 同类先例：`docs/三机推理集群使用手册.md` 判 `local-only`，理由原文 = *"含站 IP / 主机名 / 端口映射 /
内部流程节点 —— 属**基础设施指纹**"*。

**本次的"脱敏"具体落点 = 剔哪、留哪**：

| 项 | 处置 | 理由 |
|---|---|---|
| 站 / 主控的 **LAN IP**（`192.168.10.32/33/36/37`） | **保留** | 它就是**真值本身**，且与存量（`net.yaml` 已公开）同类 |
| **池边界 `.100–.199`** / 租期 `120 分钟` | **保留** | ★ **D5 的解锁依据** —— 删了这份记录就失去意义；属"基础设施参数"，与已被公开的端口映射同类 |

| **家用设备名 / 上游 AP 型号** | ✂ **剔除** | 与本次技术决策无关；型号属"网络拓扑指纹" ⇒ 正文只写"上游 AP""其它家用设备" |
| **主机名**（`scott-lau-*.local`） | **保留** | 存量已公开，且 `~/.ssh/config` 的绑定关系要靠它表达 |

**档位登记**：本文与同源前篇均含 C3（站 IP / 主机名 / 端口与流程细节）⇒ 登记为 **`local-only`**
