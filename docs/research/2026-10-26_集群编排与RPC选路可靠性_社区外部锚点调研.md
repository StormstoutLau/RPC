| 缺口 | 外部实践 | 代表系统 / 文档 | 可迁移的核心机制 | 不可照搬处 |

| 1 未知态 | 探针三态 + 未就绪不调度 | Kubernetes 探针 / 节点条件 / 熔断器 | **只有显式 Success 才算可用**；Unknown 不触发"当成可用" | K8s 有持续 reconcile 自动恢复；本仓是一次性 CLI，必须靠人重试 |

## 3. 逐项深入

### 3.1 缺口 1：未知态必须与"忙"分离

#### 3.1.1 已复现的事实（E1）

`_probe_worker_busy` 的注释写的是 "SSH 探不了 ⇒ probe-failed（fail-closed）"，
但 `resolve_rpc_worker` 只把它当作一个普通的 busy 字符串。实际调用：

```
输入: conf=A, candidates=[A,C], busy={A:"probe-failed", C:"probe-failed"}
输出: target=C, source=auto
reason: conf A 忙(probe-failed) ⇒ 改用 C；C 也忙(probe-failed) ⇒ 回收它
```

也就是说：**两站状态都未知时，系统不仅继续，还计划回收其中一个**。
"fail-closed" 只停留在返回值命名上，没有贯穿到动作。

#### 3.1.2 社区锚点

**(a) Kubernetes 探针：只有 Success 才算就绪**

Kubernetes 探针结果有三种：`Success`、`Failure`、`Unknown`。
`Unknown` 表示"诊断本身失败"，kubelet 不据此触发动作（例如不重启容器），
但**就绪判定只有 Success 才算通过**——Unknown 的容器不会被标记为 ready。
Pod 的 readiness gate 如果找不到对应 condition，默认按 `False` 处理。

> 这正是本仓缺的那条规则：**"判不了"不是"可用"，也不是"忙"，而是第三种状态**。

**(b) 节点条件：不健康节点被排除在集群活动之外**

Kubernetes 文档对节点的表述是：节点健康（所需服务都在跑）才有资格运行 Pod；
否则**该节点会被忽略，直到恢复健康**。节点控制器还会自动打上
`node.kubernetes.io/not-ready` 污点，使调度器不再向它派发新负载。

> 可迁移点：**未知/不健康节点不接收新工作**，而不是"先派过去再回收"。

**(c) 熔断器：状态机里没有"也许"**

熔断器是三态机：`Closed`（正常）、`Open`（快速失败）、`Half-Open`（限量试探）。
`Open` 的语义是**立即拒绝**，不是"尽力尝试"；`Half-Open` 是一次受控的重新准入。

> 可迁移点：未知态应落在 `Open` 一侧（拒绝破坏性动作），恢复要靠一次显式探测。

**(d) NIST SC-24：Fail in Known State**

NIST SC-24 的要求是：在定义的故障条件下，系统应失败到**已知状态**，
保留状态信息，并**限制后续处理**。它与"fail-open 到匿名访问"是明确对立的。

**(e) 反例：Envoy 恐慌阈值**

Envoy 的 `healthy_panic_threshold` 默认 50%：当健康主机比例低于阈值时，
Envoy 会**把流量打到所有主机，包括已知不健康的那些**。这是为了在"全都不健康"时
避免把剩余节点压垮的**有意 fail-open**。

> **本仓不能模仿这条**。Envoy 的请求是无状态、可重试、失败代价低的；
> 本仓的一次 worker 误用会驱逐别人正在服务的 qwen，代价是**中断一个已承诺的服务**，
> 且没有自动重试。所以本仓的正确选择是 SC-24 式 fail-closed，而不是 Envoy 式 panic。

#### 3.1.3 迁移到本仓的判定契约

把探针从"字符串 busy 原因"改为**显式三态**：

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `free` | 该站无容器、`:8080` 无监听 | 可选中、可回收（幂等空操作） |
| `busy(reason)` | 已知占用（halogen / port8080 / 普通引擎） | 可作为"需回收"候选，但必须先卸载成功 |
| `unknown(reason)` | SSH 失败、超时、输出不可解析 | **不得选中、不得回收**；只能用于"排除" |

选路规则建议（替换现有 `busy` 字典语义）：

1. 显式 `--worker` 仍优先，但必须在**任何回收动作之前**确认目标站可达（unknown ⇒ 中止）。
2. conf 目标 `free` ⇒ 用它。
3. conf 目标 `busy` ⇒ 在**已知 free** 的其他候选中选；若其他候选全部 `busy`，
   仍可按现有语义"改用它并回收"（因为它状态已知，回收是安全的）。
4. 只要出现 `unknown`，该节点**退出候选池**；若排除后无候选 ⇒ 中止，退出码非 0。
5. `source` 增加 `aborted-unknown`，日志明确写出"判不了 ≠ 选默认"。

> 与现有语义的唯一冲突点是"两站都忙 ⇒ 改用 C 并回收 C"。这条本身是**安全**的（状态已知），
> 应保留；要禁止的只是**状态未知时也走同一分支**。

### 3.2 缺口 2：独占资源不允许两个消费者

#### 3.2.1 代码事实（E2）

`_load_rpc` 对 `head + 选中 worker` 都执行 `_reclaim_containers`，
但 `infer-unload` **只在 head（B 站）执行**。下游 `rpc-nodes --start` 只做三件事：
写引擎覆盖层、`systemctl restart rpc-server@<alias>`、等端口。
它**不会**清理该站已有的普通 `llama-server` / unsloth studio。

所以当 worker 的忙因是 `port8080`（普通引擎占用）而不是 halogen 容器时，
回收动作对它是空的；随后 `rpc-server` 照样被拉起，形成叠加。

#### 3.2.2 社区锚点

**(a) Kubernetes device plugin：设备不能在容器间共享**

Kubernetes 官方文档明确：扩展资源**只能以整数申请、不能被超卖**，
并且**设备不能在容器之间共享**。请求 1 个 GPU 的 Pod 获得独占访问。

NVIDIA 的 time-slicing 是**显式开启**的能力，且文档明确它**没有内存与故障隔离**。
换句话说：共享不是默认，是需要人为承担风险的选择。

> 本仓的加速器就是这种独占设备：单站 ~124 GiB 统一内存，一个大模型就吃满。
> "普通引擎 + rpc-server"同站共存，等价于让两个消费者同时持有同一块设备——
> 而这正是 device plugin 在平台层禁止的事。本仓没有平台层，只能由编排层禁止。

**(b) systemd `Conflicts=`：单元级互斥**

systemd 的 `Conflicts=` 是"负向依赖"：启动前者会停止后者，反之亦然。
但文档同时说明它**不隐含顺序**，需要配合 `After=` / `Before=` 才能保证"先停后起"。

> 这是一个**低成本第二道防线**：给 `llama-server@*.service` 与 `rpc-server@*.service`
> 加上 `Conflicts=`，即使上层编排漏了一次卸载，systemd 也会拒绝两单元同时 active。
> 局限：它管不到手工进程（studio 直接拉起的二进制），所以**不能替代**上层卸载。

**(c) Slurm `DRAINING`：先让旧作业跑完，再完全退出**

Slurm 的 `DRAINING` 状态语义是：**允许当前运行的作业跑完，但不再分配新作业**；
作业结束后节点转为 `DOWN`/`POWERING_DOWN`。

> 这是"换手"的正确顺序：**先停止接纳新工作，再等待旧消费者退出，最后才移交**。
> 对 `_load_rpc` 的映射是：先把 worker 站标记为"不再服务普通请求"
> （停 `:8080` 上的普通引擎）→ 等 GTT 释放 → 再起 `rpc-server`。

**(d) 端口互斥是同一个不变式的表现**

Docker 发布端口时，同一宿主端口不能被两个容器同时绑定（`port is already allocated`）。
本仓的 `:8080` 既是 halogen 的发布口，也是普通引擎的 API 口，还是健康检查判据——
**它天然就是那个"独占资源"的可见信号**。所以"忙因含 `port8080`"应被视为
**必须卸载**，而不是"可能需要看一眼"。

#### 3.2.3 迁移到本仓的动作契约

```
reclaim_and_unload(station):
    containers = _reclaim_containers(station)     # 容器 + 等 8080 释放
    engines    = ssh_stream(station, "infer-unload")
    return both_ok
```

调用顺序固定为：

```
for st in {head, worker}:
    reclaim_and_unload(st)  → 任一失败即中止
rpc-nodes --start <alias> <worker>
```

要点：

- 回收集合必须包含 **head 与选中 worker**，不能只含 head。
- `infer-unload` 是幂等的（手册 §3.7 已确认它会停 B 站 llama-server、全部 RPC worker
  以及残留 vLLM），所以对 worker 多跑一次没有副作用。
- 失败必须**中止**，而不是打印警告后继续（见 §3.3）。
- 可选加固：systemd `Conflicts=` + `After=`，作为防漏的第二道闸；但要在 ADR 层登记，
  因为它扩大了写动作面（ADR-0004 的唯一管理面约束）。

### 3.3 缺口 3：部分完成不得报成功

#### 3.3.1 代码事实（E2）

- `_reclaim_containers` 在 `PORT8080_STILL_BUSY` 时**只打印**，返回值不受影响。
- 它返回 `bool`，但 `_load_rpc`、`cmd_load`、`_cmd_load_c`、`_load_container_model`、
  `cmd_unload_on` 等调用点普遍**丢弃返回值**。
- `_load_rpc` 里 head 的 `ssh_stream(station, "infer-unload")` **不检查 rc**。
- `cmd_unload()` 最终返回码只看 `infer-unload`，不看容器回收是否成功。

后果形态：旧服务已被卸载 / 容器已被删，但端口未释放或新进程未起，
命令却可能继续走到"启动"甚至报告 READY；或者相反，用户以为卸载干净，
实际容器还在占着 90 GB GTT。

#### 3.3.2 社区锚点

**(a) `kubectl drain`：成功返回 = 全部安全驱逐完成**

官方文档的表述很直接：`kubectl drain` **成功返回**，表示所有（未被排除的）Pod
都已**安全驱逐**，此时才可以安全关机。也就是说，**"部分完成"不会返回成功**。

**(b) PodDisruptionBudget：宁可拒绝，也不硬来**

受 PDB 保护时，驱逐 API 返回 **429 Too Many Requests**——"当前不允许驱逐"。
调用方必须稍后重试，而不是绕过预算强删。

> 对本仓的映射：当端口释放不满足、或卸载 rc 非 0 时，
> 正确行为是**返回失败并要求人重试**，而不是把警告降级为继续。

**(c) Terraform 中断：状态不一致的恢复成本远高于前置拒绝**

Terraform 在 apply 中断后会留下不一致状态（部分资源已建、部分未建），
恢复需要 `state pull` 备份、`refresh` 对账、必要时 `force-unlock`。
社区经验一致指向同一结论：**这类故障的事后修复成本高，所以要在前置阶段拒绝**。

**(d) 控制器是 level-triggered：失败就重新入队，不标记完成**

Kubernetes 控制器的三条不变式之一是"level-triggered, not edge-triggered"：
每次 reconcile 都从期望态与实际态的差值重新计算，失败会带退避重试，
**不会把一次失败的调和记成已完成**。

> 本仓没有 daemon（ADR-0004），不能实现自动重试；
> 但可以保留它的**判定纪律**：函数返回值必须如实反映"是否真的达到期望态"。

**(e) Docker 的两个坑：`rm -f` 对不存在容器返回 0；端口释放有滞后**

- `docker rm -f` 对不存在的名字也返回 0（本仓注释已记录 C 站实测）。这是"幂等成功"，
  但它**掩盖了"什么都没发生"**——所以必须先 `docker container inspect` 探存在性
  （本仓 `_container_cleanup_cmd` 已经这么做了，✓）。
- `docker stop` / `rm` 之后，宿主端口不一定立即释放：
  社区多起案例指向 `docker-proxy` / 网络命名空间仍持有监听，需要等待或重启 daemon。

> 这两条合起来说明：**"命令返回 0"不等于"资源已释放"**。
> 唯一可靠信号是**实际观测**（`ss -ltn` 无监听），而观测失败必须是失败。

#### 3.3.3 迁移到本仓的返回值契约

| 函数 | 现状 | 建议 |
|---|---|---|
| `_reclaim_containers` | 返回 `bool`，端口未释放仍 `True` | 返回 `(ok, reason)`；`PORT8080_STILL_BUSY` ⇒ `ok=False` |
| `_load_rpc` | 丢弃回收结果；head unload 不查 rc | 两站都检查；任一失败 ⇒ `return 1`，且**早于** `rpc-nodes --start` |
| `cmd_load` | 丢弃回收结果 | 回收失败 ⇒ 中止 |
| `_cmd_load_c` | 丢弃回收结果 | 同上 |
| `_load_container_model` | 回收后不检查返回值 | 同上 |
| `cmd_unload_on` | 只返回 `infer-unload` 的 rc | 容器回收失败也计入 rc |
| `cmd_unload` | 同上（并行版） | 同上；失败站单独报出，不吞掉其他站结论 |

**不要**把所有失败都升级为"全局崩溃"：`cmd_unload()` 的现有设计是
"单站失败只记该站"，这是对的，应保留；要补的是"该站失败要体现在最终 rc / 汇总里"。

### 3.4 缺口 4：先验证，再销毁

#### 3.4.1 代码事实（E2）

`_load_container_model` 的顺序是：

```
[1/4] _reclaim_containers + infer-unload     ← 先破坏旧状态
[2/4] docker image inspect                    ← 才发现镜像不在
[3/4] docker run
[4/4] 轮询 /health
```

checkpoint、ngram、tokenizer 三件套**没有被单独预检**：
它们要么在 `docker run` 时以挂载失败暴露，要么在容器起来后由 halogen 报错。
这意味着"镜像缺失 / 权重缺失 / tokenizer 未挂上"这三类**可静态发现**的问题，
都会先付出"杀掉现有可用服务"的代价。

门禁侧（[rpc_check.py](../../ops/rpc_check.py)）：

- `check_aliases` 只判断"该别名有容器配方"（`container_backed`），**不判断目标站资产**。
- `check_stations` 的权重存在性仍主要围绕 conf 的 `MODEL_PATH`（GGUF 路径）。
- `check_engine` 只在容器**正在运行**时校验镜像 digest；停机时不判（零自加载方针，合理）。

结果是：生产已全切 halogen，但"站上 `.hgn` 三件套是否齐"缺少与 GGUF 等价的活体门禁。

#### 3.4.2 社区锚点

**(a) Terraform：plan / apply 分离，`prevent_destroy`，`create_before_destroy`**

Terraform 的核心安全设计就是**先 plan 再 apply**：变更在执行前以可读形式完整列出。
`prevent_destroy` 让"会删除受保护资源"的 plan 直接失败；`create_before_destroy`
则把默认的"先毁后建"翻转为"先建后毁"，用于零停机替换。

> **重要限定**：本仓**不能照搬 `create_before_destroy`**。
> 单站只有一块加速器和一组端口，新旧实例无法并存。
> 正确类比是 **"validate before destroy"**——把可静态验证的部分全部前置，
> 只把"必须销毁后才能进行"的部分留在销毁之后。

**(b) Kubernetes admission：先校验，再落盘；dryRun 不得有副作用**

准入控制分 mutating 与 validating 两步，validating webhook 的职责就是**拒绝非法请求**；
`dryRun=All` 会跑完准入、默认值与 schema 校验，但**不持久化**。
官方还要求：带副作用的 webhook 在 `dryRun=true` 时必须**抑制副作用**。

> 这给了本仓一个清晰的实现范式：写一个**只读**的 `preflight()`，
> 它绝不产生写动作，可以被"加载前"和"门禁"两处复用。
> 这也是"预检必须不碰站"这条测试断言的来源。

**(c) Docker Compose：`service_healthy` ≠ `service_started`**

Compose 的短语法 `depends_on` **只保证启动顺序，不等待就绪**；
要等真实就绪必须用 `condition: service_healthy`，由 healthcheck 判定。
社区文章反复强调这一点：`depends_on` 不等 ready，只等 running。

> 本仓已有正确实践：`_load_container_model` 轮询 `/health` 直到 `status: ok`，
> `rpc-nodes` 也 `wait_port`。要补的不是"等就绪"，而是**"等资源真的释放"**
> （`ss -ltn`）与**"资产真的存在"**（预检）。

**(d) SLSA / digest pinning：制品身份用 digest，不用 tag**

SLSA 的验证流程要求：先形成对制品的期望（digest、provenance、builder），
再逐项核对。Docker 的供应链最佳实践同样把"按 digest 钉死镜像"列为基础项——
因为 tag 可被重推，digest 才是内容身份。

> 本仓已经在 `CONTAINER_MODELS.image` 里用 `tag@sha256:…` 钉死，✓。
> 缺的是把同一个 digest **在加载前**核对一次（现在只在运行中由 `check_engine` 核对）。

#### 3.4.3 迁移到本仓的预检契约

建议新增一个**纯只读**的 `preflight_container(alias, station)`，返回 `(ok, [problems])`，
检查项按成本从低到高：

| 检查 | 手段 | 成本 | 失败含义 |
|---|---|---|---|
| 镜像存在 | `docker image inspect <image>` | 秒级 | 需后台拉取，**不得先杀旧服务** |
| checkpoint 存在 | 站上 `test -f` + 大小下限 | 毫秒 | 权重未分发 |
| ngram 同目录 | `test -f` + 大小下限 | 毫秒 | halogen 起不来（配方要求同目录） |
| tokenizer 目录 | `test -d` + 非空 | 毫秒 | 启动后 tokenizer 报错 |
| 挂载映射 | 由配方派生，无需 SSH | 零 | 配方写错 |
| 磁盘余量 | `df` 对比 checkpoint 大小 | 毫秒 | docker run 中途失败 |
| 镜像 digest | 仅当容器已在跑时核对 | 秒级 | 制品漂移 |

**刻意的取舍**：日常加载**不做** 110 GiB 全量 `sha256`。
存在性 + 大小 + mtime 足以抓住"文件没到 / 被截断 / 挂错目录"；
全量哈希留在**分发流程**与 **full 门禁**，避免每次加载多花数分钟 IO。

顺序固定为：

```
preflight()  → 失败: 打印 problems, return 1（不调用任何回收）
reclaim+unload (head, worker)
docker run
health poll
```

门禁侧建议：

1. `check_aliases` 增加一条：`inventory.stations` 里有该别名的站，必须有容器配方**或** conf。
2. 新增 `check_halogen_assets`（full 档）：逐站复用 `preflight_container`，只读。
3. `check_engine` 的 digest 判据保持不变（运行中才判），但可复用同一份 `problems` 输出格式。

## 4. 反面清单：这些不要照搬

| 外部机制 | 为什么不能直接照搬 | 本仓应取什么 |
|---|---|---|
| Envoy panic threshold | 全不健康时打到坏主机；本仓误用代价是中断已承诺服务 | **不设 panic**；全 unknown ⇒ 中止 |
| K8s 自动 reconcile 重试 | 需要常驻控制面 / daemon；与 ADR-0004 冲突 | 只取"失败不标记完成"的判定纪律 |
| `create_before_destroy` | 单卡单端口，新旧无法并存 | 改为 **validate before destroy** |
| `kubectl drain` 无限等待 Pod 健康 | 默认 Unhealthy Pod Eviction Policy 是等待健康，可能卡住 | 等待必须有超时，超时即**响亮失败** |
| systemd `Conflicts=` 单独使用 | 不隐含顺序，可能先起后停 | 必须配 `After=`，且只作第二道防线 |
| 全量 sha256 每次加载 | 110 GiB × 3 站，IO 成本远超收益 | 日常只做存在性/大小；全量哈希留在分发与 full |

## 5. 建议的落地设计（契约级，不含代码）

### 5.1 探针契约

```
ProbeResult = {state: "free" | "busy" | "unknown", reason: str}
```

- `unknown` 由 SSH 失败、超时、输出无法解析三种情况产生，**不可被解释为 busy**。
- `resolve_rpc_worker` 的入参从 `busy: dict[str,str]` 改为 `probe: dict[str, ProbeResult]`。
- 决策函数仍保持纯函数（不碰站），这一点不变，是现有测试资产的基础。

### 5.2 回收契约

```
reclaim_and_unload(station) -> {ok, steps: [{step, ok, rc, detail}]}
```

- 步骤固定：`containers` → `infer-unload`。
- 任一步失败 ⇒ `ok=False`，**调用方必须中止**。
- `PORT8080_STILL_BUSY` ⇒ `containers.ok=False`，reason 明确写"端口未释放"。
- 回收范围 = `{head, worker}`，对两站执行同一函数。

### 5.3 预检契约

```
preflight_container(alias, station) -> {ok, problems[]}
```

- **零写动作**（测试断言：调用前后 `_reclaim_containers` 调用次数为 0）。
- 可被 `_load_container_model` 与 `rpc_check --only halogen-assets` 复用。
- 资产清单**从 `CONTAINER_MODELS` 派生**，不新开第二份路径真值。

### 5.4 日志与审计

保留现有 `RPC_AUTO_WORKER source=… target=… station=… :: reason` 一行式，
但在 `unknown` 中止时输出：

```
RPC_AUTO_WORKER source=aborted-unknown :: A=unknown(ssh timeout) C=unknown(ssh timeout) ⇒ 中止，不做回收
```

这样台账/手册里可以直接 grep 出"因判不了而中止"的事件，与"因忙而切换"区分开。

### 5.5 先验红测试矩阵

所有用例都应**先红**（当前代码下失败），再改实现。

| # | 用例 | 注入 | 期望 |
|---|---|---|---|
| T1 | 两站 unknown | `probe={A:unknown,C:unknown}` | `target=None`，**不得出现"回收它"** |
| T2 | conf 忙 + 备选 unknown | `probe={A:busy,C:unknown}` | 中止（unknown 不得作为备选） |
| T3 | conf unknown + 备选 free | `probe={A:unknown,C:free}` | 选 C，且**不回收 A** |
| T4 | 显式 worker 不可达 | `probe={C:unknown}` + `--worker C` | 回收前中止 |
| T5 | worker 忙因为普通引擎 | `probe={C:busy("port8080")}` | B、C 都收到 `infer-unload`，且均早于 `rpc-nodes --start` |
| T6 | head 卸载失败 | `ssh_stream rc!=0`（head） | 中止，未调用 `rpc-nodes --start` |
| T7 | worker 卸载失败 | `ssh_stream rc!=0`（worker） | 中止 |
| T8 | 容器回收失败 | `_reclaim_containers → ok=False` | 中止 |
| T9 | 端口未释放 | 命令输出含 `PORT8080_STILL_BUSY` | 回收判失败，中止 |
| T10 | 缺 checkpoint | preflight 注入缺失 | 中止，且**未调用回收** |
| T11 | 缺 tokenizer / ngram | 同上 | 同上 |
| T12 | 镜像缺失 | 同上 | 中止，且未调用回收；提示后台拉取 |
| T13 | digest 漂移（运行中） | `check_engine` 注入 | 门禁 FAIL |
| T14 | inventory 声明站无资产 | 门禁注入 | 门禁 FAIL |

现有 [test_cluster_pure.py](../../tests/test_cluster_pure.py) 的辅助函数把
`_reclaim_containers` 和 `ssh_stream` 全部 mock 为成功，正好是 T5–T9 的注入点；
建议**只加参数**（`reclaim_ok`、`unload_rc`），不重写测试框架。

1. **O-175 不可改写**：它记录的是"自动避让"的真跑结论，本身成立。

   建议补一张"场景 → 当前行为 → 目标行为"表，覆盖 unknown / port8080 / 回收失败 / 资产缺失。
3. **门禁扩展**：`preflight_container` 复用为 full 档只读检查；不新增 daemon、不新增定时任务。
4. **ADR**：若采纳 systemd `Conflicts=` 作为第二道防线，需要走 ADR-0004 的写动作扩权流程；
   若只改 `cluster.py` 的判定与顺序，属于既有管理面内改动，但仍需先验红 + 双向自证。

## 7. 结论与优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 三态探针（缺口 1） | 唯一已复现；且"未知仍回收"是唯一会**误伤其他服务**的分支 |
| **P0** | worker 卸载补齐（缺口 2） | 直接违反"同站禁止多个大模型"的硬约束，后果是 OOM/GTT 争用 |
| **P1** | 回收失败传播（缺口 3） | 决定故障是"响亮失败"还是"静默半成品" |
| **P1** | 预检前置 + 资产门禁（缺口 4） | 把可静态发现的失败挡在破坏性动作之前 |
| **P2** | 手册行为矩阵 / inventory 漂移 / 台账 CTX 对账 | 治理一致性，不改变运行时行为 |

**不建议做的事**（本轮明确排除）：

- 不引入常驻控制器 / daemon 来"自动 reconcile"——与 ADR-0004 冲突，收益不抵复杂度。
- 不为对齐 Kubernetes 而重写编排层；现有纯函数 + CLI 形态是对的。
- 不在每次加载时对 `.hgn` 做全量哈希。
- 不因本次 review 更换推理框架或引擎版本。

**一句话**：外部系统给出的共同答案是——
**未知不等于可用；独占资源不允许两个消费者；部分完成不算成功；校验先于破坏。**
这四条正好对应四个缺口，且都不需要引入新组件就能落地。
