## 1. P1：`opencode run` "无输出 / 卡死"

### 1.1 前一轮的错误结论

前一轮记档为「`opencode run` 在 B 站 60~180s 无输出，`--pure` 与付费模型同样复现，与本次改造无关，既有缺陷待排查」。

**该表述有两个错误**：① 把采样偏差当成站点特征；② 归因为"opencode 缺陷"，掩盖了真实根因。

### 1.2 实测证据

**（a）三站默认模型直跑**（各站 `opencode.jsonc` 的 `model` 值，`< /dev/null` 关闭 stdin，100s 上限，E1）

| 站 | 默认模型 | 结果 |
|----|---------|------|
| A | `opencode/nemotron-3-ultra-free` | **EXIT=0**，返回 `OK` |
| B | `opencode/nemotron-3.5-lightning-free` | EXIT=124（超时） |
| C | `cluster-litellm/nemotron`（本地 :8080） | EXIT=1，`Cannot connect to API`（引擎未加载） |

**（b）交叉对照：站点 vs 模型**（E1）

| 组合 | 结果 |
|------|------|
| A + `nemotron-3.5-lightning-free` | EXIT=0 ✅ |
| B + `nemotron-3.5-lightning-free` | EXIT=124 ❌ |
| B + `nemotron-3-ultra-free`（A 的模型） | EXIT=0 ✅ |
| **B + `nemotron-3.5-lightning-free`（复测）** | **EXIT=0 ✅** |

同一站、同一模型，前后两次结论相反 → **排除模型级与站点级归因**。两个模型在 `opencode models` 目录中**都存在**（E1），排除"模型 ID 失效"。

**（c）重复采样定量**（同一模型各站 5 轮，45s 上限，E1）

| 站 | run1 | run2 | run3 | run4 | run5 | 成功率 |
|----|------|------|------|------|------|--------|
| B | 0 | 0 | 124 | 124 | 124 | **2/5** |
| A | 124 | 124 | 124 | 0 | 0 | **2/5** |

两站成功率相同 → **与站点无关**。

**（d）失败不是"无响应"，而是"极慢"**（关键）

失败样本的 `bytes` 并不总是接近 0：

| 样本 | EXIT | 输出字节 |
|------|------|---------|
| B run3 | 124 | **11431** |
| A run4 | 0 | 9246 |
| B run4/run5 | 124 | 386 / 292 |

B run3 输出了 11KB 仍未在 45s 内结束 → **模型一直在流式生成，只是吞吐不足**。这与"进程挂死"是可区分的两类现象。

**（e）调用形式对照：手册铁律 2 未能复现**（E1）

手册 `§2a.4` 铁律 2（2026-09-02 定版）记：「opencode 必须 stdin 管道形式；**位置参数形式在 1.18.25 会挂死**（init 后无任何 LLM 调用，日志实证）」。以同一模型各跑 4 次复测：

| 形式 | 结果 | 成功 |
|------|------|------|
| 位置参数 `opencode run -m M "prompt" < /dev/null` | 0/0/0/0 | **4/4** |
| stdin 管道 `echo "prompt" \| opencode run -m M` | 0/0/124/124 | **2/4** |

**未能复现该铁律**——两种形式都呈间歇性慢，形式不是决定性变量。该铁律在 2026-09-02 成立、当前不成立，可能因版本/网络/模型侧变化，待独立复核后再改手册。

### 1.3 根因（第三次修正后的结论）

**穷尽三次归因的过程本身是结论的一部分**：

| 轮次 | 归因 | 判定 |
|------|------|------|
| 第 1 轮（落地期记档 F10） | 「opencode 既有缺陷」 | ❌ 错：非缺陷 |
| 第 2 轮（本调研初稿） | 「默认模型免费档低吞吐」 | ◐ 方向对但表述过强 |
| 第 3 轮（形式对照 + 手册交叉） | **`opencode/*` 免费档呈间歇性慢；与调用形式无关；该现象手册两月前已记档，但当时归因到调用形式** | ✅ 当前最一致解释 |

合并四轮采样（5+5 位置参数、4+4 管道）：

| 形式 | 成功/总 | 成功率 |
|------|---------|--------|
| 位置参数 | 6/9 | 67% |
| stdin 管道 | 4/8 | 50% |
| **合计** | **10/17** | **≈59%** |

失败形态恒为 **rc=124（超时）且输出字节 >0**（曾见 11431B）→ **在生成，只是慢**，不是挂死。

**结构性成因**：`opencode/*` provider 是 opencode 官方 zen 免费档（E1：二进制含 `https://api.opencode.ai` + `zen/v1`），属**外部出站且无 SLA**；而 `opencode run` **无默认总超时** → "慢"无法被上层判定，只能表现为无反馈等待。

### 1.4 与方法论教训

本项暴露的最大问题不是 opencode，而是**调研流程**：

> **① 调研前未检索既有记档。** 手册 `§2a.4` 早已把该现象列为"铁律"（含日志实证），`ops/station-bin/agent-cli-smoke.sh` 也是现成的冒烟工具——我全部漏读，把已记档问题"重新发现"了一遍。
> **② 单次采样不足以定性。** 第 1 轮把 5 次里 3 次失败当作站点特征，直接写下"B 站既有缺陷"，造成错误记档。
>
> **改进（已落到本报告与 CHECKLIST）**：诊断类任务的第一步固定为「检索手册 / spec / ADR / 既有 smoke 脚本」；任何"某站坏了"的结论须≥5 次重复采样方可下笔。

### 1.5 与本次明文改造的关系

**无关**，已双向验证：`{file:}` 引用解析由 `opencode debug config` 独立验证通过（三站 EXIT=0、无残留 `{file:`、apiKey 为真实值）；卡死现象在改造前即存在（首轮探测 B 站 `openrouter/*` 同样超时）。

## 2. P2：三站默认模型漂移

### 2.1 现状（E1）

| 站 | 默认模型 | 端点性质 |
|----|---------|---------|
| A | `opencode/nemotron-3-ultra-free` | **外部**（opencode zen 免费档） |
| B | `opencode/nemotron-3.5-lightning-free` | **外部**（同上） |
| C | `cluster-litellm/nemotron` | **本地** `127.0.0.1:8080` |

另有一处同级漂移：A 站 `disabled_providers: ["lm-studio-local"]`，B 站 `disabled_providers: null`。
B 站 `opencode.jsonc` 还有一个**非法根级键** `cluster-local`（应与 `provider` 同级错误放置，重复定义；A/C 站无此问题）。

### 2.2 成因（修正：不是残留，是既定策略）

**本项在初稿中被我误判为「逐站手工设置的历史残留」。实际是 2026-09-02 有意设定并写入手册的策略**：

> 手册 `§2a.4` 铁律 3：「**默认模型 = 免费档 `opencode/nemotron-3.5-lightning-free`（两站 2026-09-02 定）** — 轻任务不吃本地算力；**敏感内容（未发表论文/因子代码/密钥）必须显式 `-m cluster-litellm/nemotron` 或 `cluster-local/gpt-oss` 走本地**（免费模型数据用于改进训练，官方 Privacy 节明文）；wrapper/脚本调用仍永远显式 `-m`」

同节还附「免费模型速查」表（含两站实测延迟与地区封锁记录），证明这是**经过实测的受管策略**，只是未落进任何自动化配置源。

C 站默认走本地属站点特例（C 站 2026-09-09 接入时随其本地引擎复制配置）。

### 2.3 影响（重估）

1. **P1 的"默认路径六成失败"不再是"配置错误"，而是"既定策略的代价"**——策略选择了省本地算力，代价是免费档的可用性波动。这改变了处置优先级：不该简单推倒策略，而应**在策略内补可用性保障**（即 §4.1 的兜底层）。
2. **C 站默认依赖副作用**：指向本地引擎，须先 `cluster.py load` 才能用；未加载时快速失败（形态优于超时）。
3. **合规约束靠"人工规范"，无技术门禁**：手册铁律 3 要求敏感内容显式 `-m` 走本地，但 opencode 侧**无强制门禁**——`agent-cli` 的 `Invoke-Router rule B`（`local-only + egress → exit 4`）**不覆盖 opencode 自身发起的请求**。即：默认配置下，一个本应 local-only 的任务会被送到境外免费档，系统不拦。与 [ADR-0003 D4](../../adr/ADR-0003-OpenRouter密钥与egress路由管理.md)「egress 仅 public/sanitized」的一致性**依赖使用者自觉**，非机制保证。另注：免费档官方 Privacy 明文说明数据用于改进训练，风险高于普通付费 egress。

### 2.4 处置方向（修正）

原建议「统一改为本地优先」**与该既定策略冲突**，不应单方面推翻。正确方向是**不动默认策略，补齐其缺失的可用性保障**：
- 保留「默认免费档 + 敏感显式本地」的既定分工（这条分工本身是合理的：轻任务省算力、敏感不出站）；
- 用 §4.1 的 `oCrun` 兜底层承接"免费档波动"——失败自动切 OpenRouter（自持 key，实测 7/8 可用），再退本地；
- 若要强化合规，正确做法是**加技术门禁**（按任务标签强制 `-m` 本地），而非改默认值。

### 3.2 关键发现：DeepSeek key 无单一真值（已解 → 两把均为死凭据）

A 站同时存在**两把不同的 DeepSeek key**（哈希不同），分别散在 1 处和 2 处 → 表面是"轮换时无从判断哪把在用"。

**取证结论（E1，2026-09-14）**：两把 key **都已失效**。以 `GET https://api.deepseek.com/user/balance` 实测：

| 来源 | hash | 官方判定 |
|------|------|---------|
| `~/.hermes/auth.json` + `~/.hermes/.env` | `1b179602ec` | `Authentication Fails, Your api key: ****d5ec is invalid` |
| `~/.claude/cc-haha/providers.json` | `0404235950` | `Authentication Fails, Your api key: ****0ecf is invalid` |

对照组（无 key 打同一端点）同为 401，且两条报错均指明 "is invalid" → 请求格式无误，**是 key 本身失效**。

**影响重估**：不存在"哪把在用"的问题；**两把都是死凭据**。轮换阻塞项消失，本项降级为**清理明文死凭据**（卫生债，非活跃风险）。另注：hermes `auth.json` 的 `deepseek` 条目中 `Key 1`（id `029e40`）`access_token` 为空、`request_count: 0`，实际承载者是 `source: env:DEEPSEEK_API_KEY` 那条 —— 即 **hermes 侧已有 env 引用机制**，纳管路径清晰。

### 4.1 分层设计（"既定默认"与"自动兜底"如何共存）

opencode 的 `model` 是**单值、无 fallback 链**（已确认），故把两件事拆到两层：

| 层 | 载体 | 取值 | 服务谁 |
|----|------|------|--------|
| **默认（既定策略层）** | `opencode.jsonc` → `model` | **保持不变**（A/B `opencode/nemotron-3.5-lightning-free`；C 本地） | 交互使用——沿用 2026-09-02 既定分工（轻任务走免费档省本地算力，敏感内容人为显式 `-m` 本地） |
| **兜底（可用性层）** | `oCrun` 的 `OCRUN_CHAIN` | **免费档 → OpenRouter（自持 key）→ 本地** | 脚本/自动化——免费档波动时自动切档，不再"无反馈等待" |

**为什么不动默认值**：默认值不是残留，而是手册 `§2a.4` 铁律 3 的既定策略（见 §2.2）。本轮用户答复"本地优先"与"先使用免费模型、不成功则切 OpenRouter、本地兜底"两句存在张力；后一句与手册既定策略一致，故**取其一致解**：默认策略不动，缺的可用性保障由 `oCrun` 补上。若确需改成默认本地，属**策略变更**，应同时改手册铁律 3（每站 1 行 `model` 即可，`oCrun` 不受影响）。

**`oCrun` 的实现要点**
- **入口双形式**：管道（`echo "..." | oCrun`，与手册约定一致，且各档复用同一次 stdin 读取）与位置参数均可；
- **每次尝试独立超时**（默认 120s，`-t` 可调）→ 把"慢"转成可判定的 `rc=124`，再由链逻辑落档；
- **必须先取 `rc=$?` 再判**——`if ...; then` 无 `else` 时语句自身返回 0，会覆盖 `$?`（实测踩过，报告 §4 首行曾输出"rc=0 却落档"）；
- 部署：三站 `/usr/local/bin/ocrun`（755，passwordless sudo 安装），非交互 ssh PATH 直接可达；源文件 `ops/station-bin/ocrun` 入库。

## 9. 调研：A/B/C agent 配置能否「完全统一」

### 9.1 结论

**可以完全统一，而且比预期容易得多——统一后三份配置可以做到字节级相同。**

原本的判断是"本地模型名三站不同 ⇒ `modelOverrides` 无法字面统一"，这是**错的**：决定性实验（§9.3）证明**本地引擎完全忽略请求里的 `model` 字段**，服务的是"当时加载的那个模型"。因此**所有模型标识类字段都可以统一成一个常量**，配置与"运行时加载了什么模型"彻底解耦。

统一后剩余的差异**只剩运行时状态**（各站当前加载的模型），不再有任何配置差异。

### 9.2 有利条件（E1 实测）

| 条件 | 实测结果 | 对统一的意义 |
|------|---------|-------------|
| 用户名 / 家目录同构 | 三站均 `scott-lau` / `/home/scott-lau` | **路径类字段可字面统一**（`apiKeyHelper` 等） |
| CLI 版本一致 | 三站 `opencode 1.18.25` / `claude 2.1.258` | 配置 schema 无版本差异，同一份配置三站通用 |
| **本地引擎忽略 `model` 字段** | `:8080`(unsloth studio) 与 `:32837`(llama-server) 用 bogus 模型名**均 200** | **模型标识类字段可字面统一**（决定性） |
| 本地端点同构 | 三站本地引擎均监听 `127.0.0.1:8080` | `baseURL` 可统一 |
| OpenRouter 侧已统一 | 6 档模型清单三站一致（§7 已落） | 无需再动 |

### 9.3 决定性实验：引擎是否校验 `model` 字段

| 目标 | 引擎 | 请求 model | 结果 |
|------|------|-----------|------|
| B `:8080` | unsloth studio（需 auth） | 真实值 `gpt-oss-20b-MXFP4` | 200，回填真实模型名 |
| B `:8080` | 同上 | **`__bogus_nonexistent__`** | **200**，响应体仍回填 `"model":"gpt-oss-20b-MXFP4"` |
| B `:32837` | llama-server（`--alias gpt-oss-20b-MXFP4`） | `gpt-oss-20b-MXFP4` / `gpt-oss-20b` / `__bogus__` | **三者均 200** |

**判读**：`model` 字段是**纯装饰**，引擎按"已加载模型"服务，不校验也不报错。故 opencode 的 `models` 键、claude 的 `modelOverrides` 值均可取任意常量。

### 11.2 关键方法修正：**"扫全仓库"不可行，改为对账**

我原先提的方案是"扫描仓库里出现的端口/别名，未登记即 FAIL"。**实测推翻了它**：

| 断言 | 实测噪声 |
|------|---------|
| 端口 | 51 个"端口"里 **19 个不是端口**：`9859`(llama.cpp 提交号)、`16384/4096/1024/8192/20000`(ctx/buffer 参数值)、`127/808`(截断匹配) |

根因：**文本里的数字与标识没有唯一语义**。这条路必然噪声爆炸，跑不了两天就会被 `--no-verify` 绕过。

## 12. cluster.py 别名匹配缺陷修复 + 回归护栏（2026-09-14 完成）

§11.3 只改了**数据**（ROUTE 键），**匹配逻辑的结构缺陷没动** —— 同类缺陷会随新键重演。本节是逻辑修复。

### 12.1 原实现的三个缺陷

```python
def resolve_alias(alias):                     # 原实现
    low = alias.lower()
    for full in ROUTE:
        if full.startswith(low): return ...   # ← 只做单向: 键必须以输入开头
    for m in RPC_MODELS:
        if m.startswith(low): return ...
    return DEFAULT_STATION, alias, ...        # ← 未匹配时静默兜底
```

| # | 缺陷 | 后果 |
|---|------|------|
| 1 | **单向前缀匹配** | 键若是缩写，用户输入完整别名必失败 |
| 2 | **多候选静默取首个** | 按 dict 插入顺序取首次（常量层注释"应置于尾部以保前缀匹配序"已是承认脆弱） |
| 3 | **未匹配无区分标识** | 打印 `路由: X -> B 站`，与正常路由外观一致 → 无法察觉"这是没匹配上" |

### 12.2 修复

- **`resolve_alias` 返回 `how`**（`exact` / `prefix` / `rpc` / `default`），`cmd_load` 据此在路由行上标注 —— `default` 会显式打印`[★未在路由表中 → 落默认站; 若站上无此别名, infer-load 会失败]`。
- **精确匹配优先**；**多候选抛 `AliasError`**，`cmd_load` 捕获后 exit 2 并列出全部可用别名。
- **兜底前的安全网**：若输入是某个 ROUTE 键的**更长版本**（如输入 `qwen3.8-27b-mtp`、键为缩写 `qwen3.8-27b`），**直接报错**而不是静默送默认站 —— 这是把本次 bug 类彻底堵死的那一处。
- **刻意不做双向匹配**：否则 `ROUTE["gpt-oss-120b"]` 会吞掉更具体的 `gpt-oss-120b-fable-5-distilled`（后者属 RPC 双机类，必须走 RPC 分支）。单向恰好让"更具体的别名"不撞"更短的别名"。

### 12.3 回归护栏：新增 `aliases` 断言（第 4 条）

从 cluster 常量**派生**用例（不硬编码 ROUTE 内容，自更新），共 **16 例**：

| 组 | 断言 |
|----|------|
| (1) | 每个 ROUTE 键精确命中自己 |
| (2) | 每个 RPC_MODELS 条目走 rpc 分支 |
| (3) | **双向不变式**：ROUTE 键的**前缀**与其**更长变体**都不得静默落默认站 |
| (4) | 未知别名必须显式标 `default` |
| (5) | 多候选必须抛 `AliasError`（打桩 ROUTE，事后还原） |
| (6) | `inventory/models.yaml` 里声明 `route:` 的别名必须真的路由到该站 |

### 12.4 关键过程：第一版护栏**测错了方向**（被实测打回）

第一版 (3) 只测「ROUTE 键的**前缀**」。做注入复验时 —— 把 `ROUTE` 改回旧 bug 值 —— **护栏仍然 PASS**。

原因：真实 bug 的方向恰好相反。bug 是「**输入比键更长**」（输入 `qwen3.8-27b-mtp`，键是缩写 `qwen3.8-27b`），而我测的是「输入比键更短」（`qwen3.8-27`）——后者从来不是问题。

修正两处后复验通过：

| 步骤 | 结果 |
|------|------|
| A) 当前（已修） | `[PASS]` 16 例，exit 0 |
| **B) 注入旧 bug 值** | **`[FAIL]` + exit 1**，明细：`inventory 声明 'qwen3.8-27b-mtp' -> C 站, 但解析报错: …比路由键 qwen3.8-27b 更具体…说明该路由键已过期` |

（这条经验值得记住：**护栏必须用"注入历史 bug"来验证，否则很容易写出测不到目标缺陷的护栏**。第一版就是"看起来对、实际测不到"。）

### 13.2 设计依据（两条都来自实测）

1. **模型侧只查 conf + 点名几个路由键，不做全量比对** —— `conf` 是**人工维护的命名集合**（稳定，可双向严格比对）；`infer-list` 反映磁盘模型库（下载即变，全量比对必然天天误报）。判定"别名在该站是否可用"本就该看 conf：`infer-load` 读的正是 `/etc/llama-instances/<alias>.env`。
2. **刻意不取 `infer-list`** —— 除上述语义理由外还有性能实据：带上它全量耗时从 **31s 涨到 60s**（它自身 10s+/站）；改为只用 conf 后回到 **29.1s**。

### 13.3 首轮就暴露的实现 bug（自省）

第一版把"三站一致"的**信息行也 append 进了 `detail`**，而 `detail` 非空即判 FAIL —— 断言**永远红**（实测 59.7s 后报 FAIL，明细则只有两条"三站一致"和一条 WARN，看不出哪项失败）。

修法：分离 `detail`（判定失败项）与 `info`（仅上下文，只在失败/告警时附带打印）。

> 再次印证：**断言必须既看"通过"输出也看"失败"输出**。这次是"通过"路径被信息行污染；上次（§12.4）是"失败"路径没被测到。只验证一种输出必然漏。
