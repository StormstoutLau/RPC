## 1. 结论速览（E1 · Flash）

## 4. 引擎引入（E1）—— 为什么不能走 `UPGRADE_SOP`

`glm5next` 支持来自 **PR #27754**（unsloth `glm5next/upstream` 分支，**至今未合主线**；状态见 tracker §1.1）。因此：

| 做法 | 判定 |
|---|---|
| 走 `UPGRADE_SOP`（构建 → `/opt/llama.cpp-<ver>` → **原子切 symlink**）| ❌ **不可**：SOP 是**主线升级**语义。特性分支若切 symlink 会**替换现役引擎**，把未合分支的风险扩散到**全部模型** |
| **并存版本目录（本次采用）** | ✅ `/opt/llama.cpp-glm5next-20260928` + MANIFEST + `patchelf $ORIGIN`，**不动 `/opt/llama.cpp`**（仍指 `master-91f6a6cf`）⇒ **现役引擎零影响，可随时 `rm -rf` 回退** |

- 取源：`codeload.github.com/unslothai/llama.cpp/tar.gz/refs/heads/glm5next%2Fupstream`（**注意分支名含 `/` 需 `%2F` 转义**）
- 构建：`cmake -DGGML_VULKAN=1 -DGGML_RPC=ON -DLLAMA_CURL=OFF Release`
- 版本：`0.4.1-dev (build 0, commit unknown)`（tarball 无 `.git`）
- **RPC 要求两端同版** ⇒ 同目录已分发到 **A 与 C**（`tar` + `scp`，`ARCH_GLM5NEXT=1` 校验）

## 5. 统一管理入口（E1）

★ **不新增 backend 轴** —— "引擎变体"与现有 backend 的"拓扑"轴**不正交**（`glm5next` 变体**既能单机也能 RPC**），加成 backend 会组合爆炸。故表达为**实例 conf 的一个值**：

```
# 已存在的钩子（ops/llama-serve-instance L31，无需改 wrapper）
exec "${LLAMA_SERVER_BIN:-/opt/llama.cpp/llama-server}" -m "$MODEL_PATH" $RPC_ARGS …
```

用法：

```bash
python ops/cluster.py load <别名> --backend llama-rpc --engine glm5next-20260928
#   --engine <名>          → /opt/llama.cpp-<名>/llama-server
#   --engine /abs/path     → 原样使用
```

实现要点（**踩过的坑**）：
1. `--engine` 解析后**校验可执行**，不存在则列出现有变体并 `exit 1`；
2. ★ **必须落 conf**（`/etc/llama-instances/<alias>.env` 的 `LLAMA_SERVER_BIN=`）—— 因为 llama-rpc/llama-single 实际由 **systemd 单元**驱动，单元会**重新 source 同一 conf**，只 export 本进程环境**对单元无效**；
3. ★ `cluster.py` 侧加**白名单字符校验**（仅 `字母/数字/./_/-`）—— engine 来自命令行且会拼进**远端 ssh 命令**，不校验等于开放注入面；
4. ds4 走独立命名空间（`/etc/ds4-instances`），不写 llama 系键。

## 7. 实测吞吐（E1，全部同机同档同 prompt）

> 测量口径：**prompt 1513 token**、`max_tokens=64`、`temperature=0`，读 `/v1/chat/completions` 的 `timings`。

### 7.1 双机（B + A · 2×32768 ctx 基线）

| 配置 | prompt t/s | decode t/s |
|---|---|---|
| 首跑（`-c 4096 -b 512`，20-token prompt） | 15.32 ⚠️ | 11.78 |
| `-c 32768 -b 512 -ub 512` | 126.58 | 11.85 |
| **`-c 32768 -b 4096 -ub 2048 -fa on`** | **138.90** | **11.94** |
| 同上 + `--tensor-split 1,1` | 140.79 | 11.62 |

⚠️ **首跑那 15.32 t/s 是"20 token 的极小 prompt"**（被固定开销主导），**不可外推** —— 这是本项工作里最容易犯的量级错误。

### 7.2 ★ 三节点（B + A + C）—— **不提速，但解内存**

| 配置 | B 站 GTT | prompt t/s | **decode t/s** | B 内存余量 |
|---|---|---|---|---|
| 双机 | 72.2 GiB | 138.90 | **11.94** | 49 G |
| **三机** | **52.5 GiB** | 136.54 | **11.22（−6%）** | **72 G（+23 G）** |

⇒ **加节点分摊权重、但不增加带宽**，且多一段跨站流水线 ⇒ **decode 略降、prefill 持平**。
★ **三节点的真实价值在内存**：1M ctx 时双机 B 站只剩 **25 G**（紧），三机降到 ~49 GiB 模型份额 ⇒ 配 24 GiB KV 后仍余 ~45 G。

### 7.3 读数（机制）

- **`-ub` 放大只给 prefill +10%**；**decode 完全不动（11.6–11.9）** ⇒ ★ **decode 是内存带宽墙**，配置调不动。
- `--tensor-split 1,1` ≈ 持平 ⇒ 默认已均衡。
- 分位数/长跑稳定性**未测**（单次 64 token 采样）。

### 7.4 与其它路线的对照

| 路线 | decode | 倍率 |
|---|---|---|
| **本路径（llama.cpp glm5next + RPC）** | **11.9 t/s** | 1× |
| ds4 单机 `--ssd-streaming` | 0.41–0.44 t/s | **1/27** |
| ds4 双机 PP | ❌ 两端夹死（见 ds4 文档 §16.9） | — |
| ds4 ROCm TP | ❌ 源码门禁（见 ds4 文档 §18.1） | — |

## 8. 上下文容量（E1 实测 + 定标）

### 8.1 1M 可起（实测）

`-c 1048576` ⇒ `n_ctx_slot = 1048576` → `model loaded` → `/v1/models` **200** ✅

| ctx | B 站 GTT | ΔKV |
|---|---|---|
| 8,192 | 72.2 GiB | — |
| 262,144 | 78.2 GiB | +6.0 GiB |
| **1,048,576** | **95.9 GiB** | **+23.7 GiB** |

### 8.2 KV = **24,576 B/token**（理论 ↔ 实测精确吻合）

来源（GGUF 真值）：
- `head_count_kv` = `[0,0,0,1, 0,0,0,1, …]` ⇒ ★ **46 层中仅 12 层是注意力层**（3,7,…,43,45），**其余 34 层为线性/循环（KDA）⇒ 常数状态、不随 ctx 增长**
- 注意力层 `kv heads = 1` + `kv_lora_rank = 512` + `rope.dimension_count = 0` ⇒ **MLA 压缩**，每 token 仅存 512 维潜变量（nope-only）
- 索引器 `kpool 4 × key_length 128 = 512` ⇒ 每 token 再加 512 维
- ⇒ 12 × (512+512) × 2 B = **24,576 B/token** ✓

### 8.3 稀疏注意力已启用

`indexer_scoring = (n_ctx > glm5next_n_select())`，`n_select = top_k + kpool − 1 = 2048+4−1 = **2051**` ⇒ **ctx > 2051 即启用 top-k(2048) 稀疏**。

### 8.4 prefill 与质量边界

- **prefill ≈138.9 t/s ⇒ 灌满 1M ≈ 2.1 小时**（★ 注意：不是 19 小时 —— 那是小 prompt 外推的错误，见 §7.1）
- ⚠ Unsloth 卡面：**"1M positions in config; evaluated to 300K"** ⇒ **>300K 质量无官方背书**
- ⚠ 索引器每 token 对**全部历史 key** 打分（O(ctx) 额外算力）⇒ 越长越慢（**衰减曲线未测**，需数小时 prefill）

⇒ **实用甜点区 = 128k–256k**（在 300K 评估范围内、双机余量也够）。

### A.1 替代路径调研：GLM-5.3-Flash 还能用什么跑（原 §17 · E3 为主）

**缘起**：ADR-0010 v1.1 冻结 ds4 双机后，需回答「当前是否有别的方法 PP/TP 跑 GLM-5.3-Flash」与「AMD 官方对这类模型分布式推理的支持到哪一步」。

**AMD 官方进展（E3）**

| 维度 | 事实 |
|---|---|
| 引擎 | ROCm 10（8/27）宣称经 **vLLM v1 / llm-d / SGLang** 提供 "robust distributed inference … multi-GPU and **multi-node**"；集合通信 **NCCL/RCCL**，由新 **NIXL** 层抽象 |
| 并行方式 | ROCm 官方文档《vLLM V1 performance optimization》专节 **Parallelism strategies**：**TP / PP / DP / EP** 四类**全部文档化** ⇒ **PP 是 AMD 官方路径，不只 TP** |
| ★ GLM 系 | 同文档点名 **"DSA models (DeepSeek-V3.2, GLM-5)：`ROCM_AITER_MLA_SPARSE`（自动选择）… `VLLM_ROCM_USE_AITER=1`，由 config `index_topk` 自动识别，需 `--block-size 1`"** ⇒ **AMD 为 GLM-5 系稀疏注意力写了官方 ROCm kernel 路径** |
| 规模案例 | 官方博客：《Scaling **GLM-5.1**-FP8 to 64× MI300X》·《DP Attention and TBO for **DeepSeek-V4** on MI355X》·《**DeepSeek-V4-Flash** 训练 on MI355X with Primus》 |
| 量化工具 | **AMD Quark** 开箱架构含 **DeepSeek-V4-Pro/Flash、GLM-5 / 5.1 / 5.2**（★ **不含 GLM-5.3-Flash**）|
| ★ 我方 GPU | vLLM ROCm 官方支持列表**含 `gfx1151/1150`（Ryzen AI MAX）**，要求 ROCm ≥ 7.0.2 |

⇒ **解读**：AMD 把"分布式"做成**框架层能力**（vLLM/SGLang 的 TP/PP/DP/EP），官方投入集中在 **Instinct 数据中心卡**；`gfx1151` 只列"能跑"。**GLM-5.3-Flash 不在 Quark 官方量化清单** ⇒ 属"新架构 + nightly 级"。

**可选替代路径（按可行性）**

| # | 路径 | 关键事实 | 判定 |
|---|---|---|---|
| ① | **llama.cpp `glm5next` PR 分支 + RPC 层切分** | Flash（`glm5next`）**未进主线**，但 Unsloth 提供可直接构建的分支；构建后可用**我方已在运维的** RPC **`-sm layer`** 做多机层切分（= PP 语义），模型用**已有 Unsloth GGUF** | ★ **最贴近现状**（同栈、免新引擎）⇒ **本文正文即此路线的落地**。风险：跟随 PR 分支；该 GGUF **丢弃 MTP head** ⇒ 无投机解码（§9-1） |
| ② | **vLLM / SGLang on ROCm** | 官方路线；vLLM 支持 gfx1151、TP/PP/DP/EP 有文档；但 **Flash 需 nightly + 专用镜像**。**塞得下是硬问题**：官方 FP8 = **321 GB**、NVFP4 = **229 GB（Blackwell 专用）** ⇒ 2×~124 GiB 装不下；4-bit HF ~160–190 GB 仍偏大 ⇒ 需 **2-bit 级 HF 量化（~90–110 GB）** 才可能 TP=2 | **引擎与并行方式都有官方支撑，卡点在量化格式与权重可得性** |
| ③ | **ds4 的 ROCm TP** | 源码门禁 `"tensor parallelism requires the Metal backend"` | ❌ **已被否证**：读源码后确认**双门禁**（编译期 `DS4_HAS_DEEPSEEK41_GPU` 在 ROCm 构建下被显式排除 + 运行期要求 Metal 或 CUDA∧family=DEEPSEEK41）⇒ **GLM 系不在其中**，且**不是"开个构建宏就行"**（见 ds4 文档 §18.1） |
| ④ | **GLM-5.3 旗舰（753B）on stock llama.cpp** | 旗舰架构 = **`glm-dsa`**，llama.cpp **自 GLM-5.2 起已支持** ⇒ ★ **反直觉：不支持的是"更小的 Flash"，旗舰反而支持**（详见 A.2）| 可做，但需多机 + 大磁盘 |
| ⑤ | ds4 Metal TP | 需 Mac | 不适用 |
| ⑥ | ds4 单机 `--ssd-streaming` | 已实测跑通 | **但仅 0.41–0.44 t/s**（§7.4）⇒ 不构成可用路径 |

**处置倾向**：① 立即动手 = **已执行**（本文）；② 留作"拿到 2-bit HF 量化权重后"再评估；③ 关闭（已否证）。渠道纪律：落地**必须走统一管理入口**（ADR-0004），llama.cpp 新变体须并入既有的**引擎升级/多版本管理**机制。

### A.3 `glm5next` 分支引入方案（原 §18.3 · E1/E3）

**侦察（E1/E3）**
- PR **#27754**（`glm5next/upstream`，unsloth）**仍 OPEN、非 Draft、未合并**；#27752 亦 OPEN ⇒ **只能从分支构建**（状态见 [tracker §1.1](../../spec/upstream-tracker/TRACKER.md)）。
- **codeload 可达**：`https://codeload.github.com/unslothai/llama.cpp/tar.gz/refs/heads/glm5next/upstream` → **HTTP/2 200** ✓（B 站 git 协议不可达，走 tarball，与 ds4 源码同法）。
- 引擎布局（`cluster.py versions` 的射程）：**RPC/分布式 = `/opt/llama.cpp`（symlink → `/opt/llama.cpp-master-<commit>`）**；单机 = `~/.unsloth/llama.cpp`（studio, HIP）；另有 `/opt/llama.cpp-9859`。

**为什么不能照搬 `UPGRADE_SOP`**：SOP 是**主线版本升级**（构建 → `/opt/llama.cpp-<ver>` → **原子切换 symlink** → 三站同步冒烟）。而 `glm5next` 是**特性分支**，若切换全局 symlink 会**替换现役引擎**（违反 ADR-0010「不自动升级」与"不换主栈"原则，也会把未合分支的风险扩散到全部模型）。

**方案（并存变体 + 入口化，零散落脚本）**

| 步 | 动作 | 与既有机制的关系 |
|---|---|---|
| 1 | B 单点：`curl codeload` 取 `glm5next/upstream` tarball 到 `~/src/llama.cpp-glm5next-<sha>/` | 复用 SOP 第 2 步的"B 单点构建"形态 |
| 2 | 构建（`-DGGML_VULKAN=1 -DGGML_RPC=ON -DCMAKE_BUILD_TYPE=Release`），记录 commit 短哈希 | 同上 |
| 3 | 安装为**并存版本目录** `/opt/llama.cpp-glm5next-<sha>/` + **MANIFEST**（沿用现役格式，含 `patchelf $ORIGIN`）| ★ **不切 symlink** ⇒ 现役引擎零影响 |
| 4 | 需要双机时，同版分发到配对站（RPC 要求**两端同版**）| 复用 SOP 第 3 步（tar + md5 校验）|
| 5 | ★ **入口化**：**不写新脚本** —— 让入口选用该版本目录；并让 `cluster.py versions` 的矩阵**能看到该变体** | 承 ADR-0004「新增管理能力加枚举/子命令，不新增并列入口」|
| 6 | 模型侧：Flash 用**已有 Unsloth GGUF** | 走 `lm-download@` + `inventory/models.yaml` 登记 |

★ **实际落地与上表的偏差（本文正文）**：第 5 步**没有**新增 backend 轴，而是落成实例 conf 的 `LLAMA_SERVER_BIN`（`--engine`）—— 理由见 §5；第 1–4、6 步按上表执行（结果见 §4/§7）。

**已知代价（须先声明）**：① 跟随**未合并分支**（非主线，随时可能变）；② 该 GGUF 转换**丢弃 MTP head** ⇒ **无投机解码**；③ `-sm layer` 在 USB4 下的收益需实测（前例：DeepSeek 走 RPC 可用但非免费）。

### A.4 ds4 那份 Q2 档为何**只能**给 ds4 用（原 §19.3 · E1）

`GLM-5.3-Flash-Q2.gguf`（96,505,816,384 B）实读元数据：`architecture = **glm5-next**`（带连字符；llama.cpp 为 `glm5next`）、block_count 46、tensors 1412、量化类**全是标准 llama.cpp 类型**（F32/Q8_0/BF16/IQ2_XXS/Q4_K/Q2_K）⇒ 量化层**不**构成障碍。用变体引擎实加载报 **`unknown model architecture: 'glm5-next'`**。

进一步查**张量命名体系**（决定性，非推测）：

| 张量族 | ds4 转换器 | llama.cpp `glm5next.cpp`/`llama-arch.cpp` | 判定 |
|---|---|---|---|
| 超连接 | `hc_attn_fn/base/scale`、`hc_ffn_*` | `blk.%d.hc_attn_fn/…` | ✅ 一致 |
| 线性注意力 | `kda_q/k/v`、`kda_q_conv`、`kda_f_a`、`kda_a_log`、`kda_beta`、`kda_o_norm`、`kda_output` | `attn_q/k/v`、`ssm_conv1d_q`、`ssm_f_a`、`ssm_a`、`ssm_beta`、`ssm_o_norm` | ❌ **不一致** |

⇒ **即使改架构串也会在张量绑定处失败** ⇒ 该档**只有 ds4 能读**。**已按裁决删除**（+ 清 `lm-download` 任务定义）⇒ 磁盘回收 **101→758 G 空闲**。**教训：架构串只是第一道门，转换器命名体系才是真门槛。**
（同一判据用于那份 190 GB 的 `Q4_K`：`kda_like = 510` · `ssm_like = 0` ⇒ 同样只有 ds4 可读；其存废见 ds4 文档 §21.2/§21.3。）

### A.5 运维事实（原 §19.6 · E1）

- ★ **GitHub(codeload) 从 B 站极慢：~40 KB/s**（37.5 MB 走了 ~15 min）；而 `hf-mirror` 为 **56 MB/s**、LAN/TB 链路 ~106 MB/s。⇒ 将来拉整仓源码应**改本地中继**（这侧取好再推）。
- 站址真值：A = `192.168.1.33`（LAN）+ **`thunderbolt0 = 10.10.10.1`**（B↔A 直连，RPC 走这条）；USB4 `10.10.11.x` 仅 B↔C。
- RPC 首跑期间 `infer-load`/systemd 均未介入（手动起停），符合**零自加载纪律**（本文 §6 即按此写成）。

## 13. GLM-5.3 **旗舰**（`glm-dsa`）三机 RPC 可行性分析（2026-09-28，E1 取证 / 判断已标注）

> **触发**：Scott 给出具体来源 —— **AesSedai 的 GGUF `IQ4_XS`**，问「GLM 5.3 在本机群部署可行性 · **三机 RPC**」。
> **方法**：**零下载**（hf-mirror 元数据 + Range 读 GGUF 头 + 引擎 `strings`），全部为 E1 本仓实测；记忆体估算标注为**估算**。

### 13.0 先说一个坑：AesSedai 有两个"GLM 5.3"仓库，**架构完全不同**

| 仓库 | `general.architecture` | 张量体系（实测） | llama.cpp 能否读 |
|---|---|---|---|
| **`AesSedai/GLM-5.3-GGUF`**（**旗舰**） | **`glm-dsa`**（无连字符 = llama.cpp 命名） | `blk.N.indexer.attn_k` · `ffn_*_shexp` · `attn_kv_a_mqa` | ✅ **能**（与主线张量表逐一命中） |
| `AesSedai/GLM-5.3-Flash-GGUF` | **`glm5-next`**（**带连字符 = ds4 命名**） | `ssm_conv1d_*` · `ssm_a` · `attn_q.weight` ⇒ **实为 llama.cpp 体系**（无 `kda_*`） | ❌ **拒载**（架构串不认，同附录 A.4 的 `glm5-next` 坑） |

⇒ ★ **两个都要看名字而不是"都是 GLM 5.3"**：旗舰档是 llama.cpp 路线；**Flash 档的架构串被写成 ds4 的带连字符形**，现役变体引擎会因 `unknown model architecture: 'glm5-next'` 拒载（张量名虽一致，但改元数据前缀属**自维护补丁** ⇒ 不建议，因为 **Unsloth 的等价档已在用**）。
⇒ 以下只分析**旗舰**（用户问的"GLM 5.3"，且 Flash 我们已在跑）。

### 13.1 旗舰档的真实参数（E1，Range 读头，零下载）

| 项 | 值 |
|---|---|
| 架构 | **`glm-dsa`**（`general.name = 'GLM 5.3'`） |
| `block_count` | **79** = **78 主层 + 1 MTP 层**（`blk.78.nextn.*`） |
| 上下文 | **1,048,576**（1M） |
| 注意力 | **MLA**：`head_count 64` / `head_count_kv 1` / `key_length_mla 256 + value_length_mla 256`；`rope.dimension_count 64` |
| 稀疏 | **DSA indexer**：`head_count 32` · `key_length 128` · **`top_k 2048`** |
| MoE | `expert_count 256` · `expert_used_count **8**` · `expert_shared_count 1` · `expert_feed_forward_length 2048` · `leading_dense_block_count 3` |
| embedding | 6144 |
| ★ **MTP** | **`nextn_predict_layers = 1`，且末分片实含 `blk.78.nextn.{eh_proj,shared_head_norm,enorm,hnorm}`** ⇒ **带 1 层 MTP**（★ 与 Flash 档不同 —— Flash 的 Unsloth 档**丢失 MTP**，故旗舰在"可能有投机解码"上反而更好） |

### 13.2 引擎与前置（E1）—— ★ **零新引擎工作**

| 项 | 实测 | 结论 |
|---|---|---|
| 主线 `/opt/llama.cpp` = `master-91f6a6cf` | `strings libllama.so \| grep -x glm-dsa` ⇒ **命中** | ✅ 架构层支持 |
| 张量表逐一对上 | 引擎含 `blk.%d.indexer.attn_k` · `blk.%d.ffn_gate_shexp` / `ffn_down_shexp` / `ffn_up_shexp` / `ffn_gate_inp_shexp` · `blk.%d.attn_kv_a_mqa` | ✅ **本档所需张量全部在现役引擎里** |
| MTP 路径 | 引擎有 `GLM_DSA MTP: missing both nextn.shared_head_norm and output_norm` 等串 ⇒ 该档**两者都有** | ◐ **具备条件**，是否生效**需实测** |
| **#28047**（GLM-5.3 **多 worker RPC 确定性 crash**） | 已由 **#26500**（merged 8/30）修复，TRACKER §1.2 记「**现役已含**」 | ✅ **分布式禁用前置已解除**（仍按"实测确认"） |

⇒ ★★ **与 Flash 的最大区别**：旗舰**不需要 `UPGRADE_SOP`、不需要特性分支、不需要并存变体** —— 现役主线引擎直接可用（同版分发到三站即可，两站本来就同版）。

### 13.3 容量账（用本集群**实测锚**，不是纸面 spec）

- 每站总 RAM **124.9 GiB**；**实测单机 GTT 上界 ≈ 119.4 GiB**（59.03 GiB 权重撑出 61.84 GiB GTT、余 57.55 GiB —— 见 [O-110/O-112 实测文档](./2026-09-28_O-110同站并发实测与O-112单机容量核验.md) §6.2）
- ⇒ 可给权重的预算 ≈ **115 GiB/站**（留 ~4 GiB 给 KV + compute）

| 档 | 双机 /站 | 三机 /站 | 双机 | 三机 |
|---|---|---|---|---|
| IQ2_S 241.33 | 120.7 | **80.4** | ❌ >119.4 | ✅ 余 ~39 |
| IQ3_S 265.94 | 133.0 | **88.6** | ❌ | ✅ 余 ~31 |
| **IQ4_XS 342.02** | 171.0 | **114.0** | ❌ | **◐ 贴顶：仅余 ~5.4 GiB/站** |
| Q4_K_M 436.95 | 218.5 | 145.7 | ❌ | ❌ |
| Q5_K_M 523.08 | 261.5 | 174.4 | ❌ | ❌ |

★ **双机连最低档都装不下**（IQ2_S 也要 120.7 GiB/站 > 119.4） ⇒ **旗舰必须三机**。

### 13.4 KV / 上下文（**估算，必须实机定标**）

- **MLA-only 下界**：78 主层 × (256+256) 维 × 2 B = **79,872 B/token ≈ 78 KiB/token**（全模型）；按层分到每站 ~26 层 ⇒ **~26 KiB/token/站**
- ⚠ **DSA indexer 的 KV 项未定**：本档是 `indexer.head_count 32 × key_length 128`，与 Flash 档的 `kpool 4 × 128 = 512` **结构不同** ⇒ **不能沿用 Flash 的 24 KiB/token**
- 按 MLA-only 下界推算（**未含 indexer**）：

| ctx | 全集群 KV | 每站 | IQ4_XS 三机（余 5.4 GiB/站）判定 |
|---|---|---|---|
| 32k | ~2.6 GiB | ~0.87 GiB | ◐ 可行（紧） |
| 128k | ~10.5 GiB | ~3.5 GiB | ◐ 边缘（剩 ~1.9 GiB 给 compute/OS） |
| 1M | ~82 GiB | ~27 GiB | ❌ **不可行** |

⇒ **1M 是纸面能力，不是三机 IQ4_XS 的现实能力**；**默认按 32k 设计**，长 ctx 需换更小档。

### 13.5 结论

| 问 | 答 |
|---|---|
| **能部署吗** | ✅ **三机可行**（引擎侧零新工作；这与 Flash 需自建分支形成对比） |
| **推荐哪个档** | ★ **IQ3_S（88.6/站）或 IQ2_S（80.4/站）** —— 才有 KV/上下文余量；**IQ4_XS 贴顶（114.0/119.4）**，只适合 32k 级短 ctx |
| 双机行不行 | ❌ **不行**（最低档 120.7 GiB/站 > 119.4） |
| 磁盘够吗 | ✅ B 站余 **612 G**，够放 342 GiB（IQ4_XS 需 9 片同盘） |
