## 一、问题1：需求方 ↔ 受理方 双向协商 / 验收协议

### 1.1 结论先行

> **部分考虑，未成标准。** `inbox/` 状态机覆盖了**受理→执行→结案**这条单向往链路；
> 但用户点名的**协商回环**（初步方案→对方复核→修改）与**验收签收**（结果审核 vs 结案）**没有显式建模**。
> 应建立一条薄薄的"协商与验收协议"叠在 inbox 状态机之上，且与社区做法强对齐。

### 1.2 现状 vs 用户点名的链路

| 用户点名环节 | inbox 现状 | 覆盖? |
|---|---|---|
| 提出需求 | `00_handoff/`（转运包冻结原件） | ✅ |
| 受理 | `open → triage`，`10_admin/裁决报告` | ✅ |
| 初步方案 | `20_plan/`（**仅管理员写**） | ⚠️ 单向 |
| **对方复核** | 无；无"意见已交回"状态 | ❌ |
| **修改** | 无；`20_plan` 可被管理员隐式重写，无版本/回流痕迹 | ❌ |
| 执行 | `running`，`agent-cli task` 派发 | ✅ |
| **结果审核** | `done`（**运维自判**"回收完成"） | ❌ 被折叠 |
| **验收** | 无独立终态；`done` 即结案 | ❌ 被折叠 |

两处核心落差:
1. **协商回环不存在**：`20_plan` 是管理员单向产物。没有"提交方案→需求方复核→退回修订→再审"的循环，
   也没有一个状态表"正在等需求方回复/管理员正在修订"（上一份 community review 的 `waiting` 建议②
   只解决了"卡住"，没定义回环协议本身）。
2. **验收被折叠进 `done`**：`done` 是"运维确认完成"，而非"需求方签收"。二者语义必须分开——
   否则"做完"与"对方认账"混淆，正是 RFP/变更管理文献反复强调要拆的。

### 1.3 社区对这条单向→双向链路的成熟做法（这次新增调研）

| 社区来源 | 与协商/验收最相关的模式 |
|---|---|
| **RFC 生命周期**（thunderbird/engineering）| `proposed→accepted→rejected→obsolete`；"**在同一个 PR 里按 review 意见修订**，与审阅人共同做决定" → 协商回环内嵌在同一载体，不另开新文档 |
| **ServiceNow IT 变更管理（RFC）** | `Authorize` 态：审批人初审，**approve 或 reject-with-reasoning**（Notes 写明"**需改哪里才能重新提交**"）→ 正是"对方复核-修改-再提交" |
| **RFP 流程**（Vendorful）| draft→issue→**vendor 澄清答疑（Q&A round）**→score→shortlist→select；买-卖双方靠**澄清轮**做双向沟通 |
| **IETF 标准流程** | 显式 **review→revise→advance/retire** + 冲突申诉；标准推进是循环不是线 |

共同点：**协商 = 在同一请求载体上的多轮 adjudge→revise 回环**，且**终态"验收/签收"独立于"实现完成"**。

### 1.4 建议的标准形态（薄协议，待裁定）

> 不做成新机制，只给现有 inbox 状态机**补两个显式环节 + 一个签名产物**：

- **补状态**：在 `accepted` 与 `running` 之间、`running` 与 `done` 之间各加一个"回环"标记位
  （或复用 ① `waiting`），例如：
  - `plan-review`（方案已交需求方复核，等回复）
  - `plan-revise`（收到意见，管理员修订 `20_plan` 更新到 `10_admin/`）
  - `release`（执行完毕，交付证据束，**等需求方验收**）
  - `accepted-by-requester` / `rejected-by-requester`（验收签收终态）
- **补产物**：每轮复核意见落 `10_admin/`（如 `复核意见-1.md`、`复核意见-2.md`），
  `20_plan` 每次修订留版本——协商过程可审计、可回滚，与 `STATE` LOG/结构化建议（community review ①）
  同一纪律。
- **验收语义**：`done`（运维结案）与**验收签收**（需求方认账）解耦；`done` 后若需求方提交新证据/新需求 →
  开新 `open`，不重写旧 `40_state/STATE`。

## 二、问题2：项目产出交付物是否应包含"证据重放"机制 + 是否建标准

### 2.1 结论先行

> **机制已实现（且相当强）；缺的是把它提为"交付物层面"的标准。**
> 你的直觉成立：`open issue`/证据流里确实已做证据重放/复验，但那在 **run/卡 级**；
> **inbox 的"项目交付"还没有强制绑定"可重放验证证据束"**。应建标准，且本仓先例（ADR-0005/0007 + 调研文档）
> 已经为它铺好了路——只需把链死动作落实。

### 2.2 本仓已有证据重放机制清点（E1，本仓实现，非新建）

| 能力 | 位置 | 状态 |
|---|---|---|
| 证据回收闭环 | [ADR-0005](../adr/ADR-0005-任务卡证据回收闭环.md)（collect） | 阶段 0 已落地 |
| 证据流阶段路线 | [ADR-0007](../adr/ADR-0007-证据流阶段推进路线与改动验证闭环.md)（0 采集/1 声明/2 复验/3 管线审计） | Phase 1 落地 |
| `evidence-manifest` 声明契约 + `evidence_manifest` 落 run.json | agent-cli.ps1 L670/692-707、L2038/L2749 | 已实现 |
| 复验判官 `agent verify` / `cluster.py agent_audit`（undeclared vs artifact-ephemeral-by-design 分列） | agent-cli.ps1 L821-838 | 已实现 |
| 判官可复现（temp=0 + seed 落档，arXiv 2606.26185）+ anchor/evidence 记录 | agent-cli.ps1 L3366-3405 | 已实现 |
| 单 run 回收证据束（`.meta`/`.prompt.txt`/`.progress`/`.accept-cmds.txt`/`.golden-cmd.txt`/`.workspace-diff.txt`/`.attach-manifest.txt`/`.session-meta.txt`） | agent-cli.ps1 L1777 | 已实现 |
| 进度采样 + 陈旧判据（`.progress`，O-25/O-22，`EVIDENCE_STALE`） | agent-cli.ps1 L1610-1855 | 已实现 |
| "重放=重放验证、非重放生成"语义 + 社区映射（SLSA/attestation/VSA、OpenInference CHAIN span、NIST AI RMF 建造者/验证者分离、agrepl、LangGraph） | [调研文档 2026-09-16](research/2026-09-16_任务卡证据流可重放性调研.md) | 已定义 |

### 2.3 缺的是什么：交付物绑定

机制层面**不缺**；缺的是**"一次项目交付必须含可重放验证证据束"这条硬约束**：

- inbox ADR-0008 的 `30_evidence` 目前只是"回收指针"，回收 hash 链死只是 **P2 建议（①⑥）**；
- 没有东西要求"结案时把 `agent-out/<ts>/` 的证据束 + `evidence_manifest` + run.json 哈希**钉进** `30_evidence`"。

### 2.4 社区对"交付物可重放性"的做法（这次新增调研）

| 社区来源 | 与交付物标准最相关 |
|---|---|
| **六阶段可复现审计**（[arXiv 2608.26236](https://arxiv.org/html/2608.26236v1)）| 实证提交需过**自动 artifact audit**：六项必备 = 全源码 / 不可变数据集 / checkpoint / 可执行评估脚本 / **机器可读环境描述** / 够用的文档 |
| **ACM/NISO 可复现徽章**（SC26 [AD/AE](https://sc26.supercomputing.org/program/papers/reproducibility-appendices-badges/)）| 两级：**Artifacts Evaluated-Functional** vs **Results Replicated**；且**artifact freeze + DOI**=结案后不可再改 |
| **发表后代码核验**（[arXiv 2601.07189](https://arxiv.org/html/2601.07189v1)）| 拆 `Reproduced`（用作者 artifact）vs `Replicated`（独立、少依赖作者 artifact）——正是"重放验证"分层 |
| **Croissant Tasks**（[arXiv 2605.29786](https://arxiv.org/html/2605.29786)）| **机器可读元数据**、把 task problem 与 solution **解耦**，供 agent 独立重生成复现 |
| **溯源/封装标准** | W3C PROV-DM、RO-Crate、ReproZip、DVC、MLflow、in-toto/SLSA attestation |

共同点：**交付物 = 源码 + 不可变数据 + 环境描述 + 可执行脚本 + 验收判据，结案时冻结 + 哈希/DOI 钉死**。

### 2.5 建议的标准形态（薄标准，待裁定）

> 把本仓已有的 run/卡级证据束，**在 inbox 结案点钉成交付物标准**，借社区五要点 + 本仓先例：

1. **交付物含"可重放验证证据束"**（升格：把 community review 建议 ⑥ 从 P2 → P0/P1）：
   结案时把 `agent-out/<ts>/` 的 `run.json`（含 `evidence_manifest`）+ 单 run 证据束 + 哈希，
   **链死到 `inbox/<proj>/30_evidence/`**。未附证据束不 `done`。
2. **声明"重放=重放验证、非重放生成"**（沿用 ADR-0007/调研文档定义）为验收判据：
   拒把"逐位一致再生成"当要求——那会造出没人能处理的判据。
3. **区分 `Reproduced vs Replicated` 两级**：内部同基座复验（Phase 2）vs 异基座独立审计（Phase 3 / cold mirror）；
   交付物标注它达到了哪一级。
4. **环境快照进证据束** = 社区"机器可读环境描述"之一：引擎/uv/模型哈希/`--kv-cache` 参数随 run 落档
   （三站引擎版本矩阵已可采，`cluster.py versions`）。
5. **结案 artifact freeze**：`00_handoff` 已做 MANIFEST.sha256；`30_evidence` 同样补 hash 钉死，
   `done` 后不动。
