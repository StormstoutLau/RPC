## 二、重大反证(影响决策方向的两项)

### 反证 1: DSpark 在 Vulkan 主线实测无加速 — 推翻 DSpark 报告核心预期

- **原断言**: "B 单机 Vulkan IQ2 + DSpark → 预期 25~35 t/s"(DSpark 报告 5.3; 依据 = LocalMaxxing 榜单 15.6~18.99 × Unsloth 1.5~1.9x)
- **反证来源**: [sypherin/strix-halo-setup docs/deepseek-v4-flash-284b.md](https://github.com/sypherin/strix-halo-setup/blob/master/docs/deepseek-v4-flash-284b.md) — **同款硬件**(395 + 8060S + 128GB)、同后端(Vulkan/RADV 主线 build 69bf643, 2026-08-08 实测):

| 配置 | draft 接受率 | tg t/s |
|:---|:---|:---|
| 裸 AR (IQ2_XXS) | — | ~9.5 |
| + DSpark, n-max=3 | 61.8% (2.85 tok/draft) | **9.5** |
| + DSpark, n-max=5 | 46.3% (3.31 tok/draft) | **9.6** |

- **机制**: DSpark 草稿是**完整 ~10.1 GiB 模型**(vs MTP 头≈一层), 其自身前向成本在带宽受限 iGPU 上 ≈ 接受收益; Unsloth 的 1.5~1.9x 来自 CUDA(B200/DGX, 优化过的投机 kernel + tensor core 使草稿和批量验证近零成本)
- **交叉印证**: #26578 PR 的基线数据(IQ3_XXS 裸 AR tg = 11.16)与 sypherin(IQ2_XXS tg32 = 12.24)同量级 — **Vulkan 主线 DS4-Flash 真实基线 ~10~12 t/s**; 榜单 18.99 是 HipFire MQ2+**MTP**(含投机), 非裸基线
- **决策改判**: 换 DS4-Flash 单机 Vulkan **不升反降**(10-12 vs 现 MiniMax 双机 18.2); 提速正道 = #26578 融合算子(+50% → ~17 t/s)或 Lucebox ROCm 路线(32 t/s)
- **附带收获**(sypherin 文档的工程陷阱, 已补入 DSpark 报告 2.4): 草稿必须同源同 quant 家族配对(antirez 重量化草稿接受率仅 **0.15%**); `--spec-type` 误写 `draft-dflash` 会**静默失效**; 大模型需 `GGML_VK_PREFER_HOST_MEMORY=ON`

### 反证 2: "108GiB GTT 墙"无来源支持 — 内存预算判定失真

- **原断言**: "Strix Halo 128GB (Linux 可见 124GiB) 中 iGPU 经 GTT 仅能寻址 ~108GiB (社区刻意 cap)... 103GB 档 + 草稿溢出 → 单机只能 IQ1/IQ2 档"(DSpark 报告摘要 4 / 3.2 / 5.1, 引注 sypherin/strix-halo-setup)
- **核验结果**: 该仓库及其已读文档中**找不到 108GiB/124GiB 任何字样** — 属合成幻觉。各来源实测值互相独立且不一致:

| 来源 | GTT/内存上限值 |
|:---|:---|
| llama.cpp #21948 构建行 (RADV) | **120 GiB** |
| tinycomputers.io (HIP+VMM 路径) | **96 GB** |
| sypherin 实跑 (Vulkan, host memory 偏好) | IQ2_XXS+131k ctx+草稿 = **97G used / 26G free** |
| Unsloth 官方 | IQ3_XXS (103GB) **"可在 110GB RAM 设备上运行"**, 推荐 128GB 机器 IQ3_XXS+Q8_0 草稿 |

- **决策改判**: Q3+草稿单机从 "✗ 溢出" 改判 "⚠ 边缘但官方推荐组合, 以实测为准"; IQ2 档从 "~80GB" 修正为 84.6GiB(IQ2_XXS)且**有同硬件 131k 上下文实跑实证**

## 六、逻辑链与决策依据评估

**RPC 报告(最强)**: "物理层(pm_qos)→传输层(RDMA)→协议层(#26610)"三层因果链完整且每层有同硬件实测支撑; v1.1 盲区扫描已自我修正过传输层收益预期(decode 个位数)。本次审计再砍一刀: 加载并行(#26291)从"已合入"回归"未来项" — 该报告的行动清单现在**全部基于已验证能力**。决策建议排序(pm_qos/MTU/-c/绑定面 → 软RoCE → #26610)经修正后依然成立。

**DSpark 报告(最弱, 修正后可用)**: 原逻辑链 "DSpark 可用 × 1.9x 倍数 × 榜单基线 → 25~35 t/s" 的三环中, 后两环分别被适用域(CUDA-only)和基线污染(含 MTP)打断, 第三环(GTT 墙)本身是幻觉 — 但第一环(DSpark 已进主线、v0.2.0 已含)完全成立。修正后的决策逻辑: **DS4-Flash 的价值 = 质量 + 1M 上下文 + 容量拆分, 不是速度**; 速度诉求 → #26578(等合并)或 Lucebox(脱离主线)。行动路径(阶段 0-3)结构保留, 预期全部改写。
- 结构性教训: 调研时把"框架可用性"与"框架在本硬件的收益"混为一谈; 榜单成绩未区分"裸 AR/含投机"口径 — 这正是用户研究方法论中"表演性自信内容"的典型形态。

**AMD 报告(数据最硬)**: 五个 issue/PR 的算子数据全部逐字复验通过, "单机 Vulkan 日常 + 双机 RPC 容量"的核心结论有两独立同构集群(visorcraft + strix-halo-guide #12)交叉支撑。修正点(PR 状态×2、单位算术)不伤结论; "27 倍"修正为 218 倍反而强化"单机碾压"。遗留: §2.5 后端横评表有一处二手来源内部矛盾(ignasivt vs visorcraft pp 结论), 已加注采信实测数据带。

## 七、审计方法注记(本审计自身的局限)

1. GitHub API 状态为 2026-08-28 快照, Open PR 的后续合并/关闭不再追踪
2. 博客类来源只核验"存在 + 已读段落数字"; 未读段落(如 Lucebox ROCmFPX 细节)标记为未核验而非错误
3. 二手转述引语(引号内英文)无法区分"原文"与"转述者的转写", 一律按未核验处理
4. llama.cpp PR review 讨论线(#26610 的 6.0.0 评论等)未逐条拉取 — 这类断言在报告中的表述已加"(review 语境)"限定
5. 数值断言的独立复算仅限算术类(27→218 倍、MTU 8972=9000-20-28 ✓、内存预算加法); 他人实测数据(如 15.35 t/s)只做来源比对不做复现
