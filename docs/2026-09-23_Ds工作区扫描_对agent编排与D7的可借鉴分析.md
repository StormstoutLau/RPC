## 0. 结论先行

> **`D:\ds` 与本机群是"同一问题族的两次独立求解"，且在多个关键处独立收敛到同一结论。**
> 对本机群最有价值的三条：
>
> 1. **D7 的关键机制不在协议里**（E1）：A2A **零 server→client 回调**（7 方法全 client→server，v1.0.0 的 11 个 rpc 同）⇒
>    「对等互审」**必须双侧同构部署**（每站同时挂「被审」与「去审」两半），且**主动回推首期不可用**。
>    这条直接决定 D7 的架构形态，且**恰好解释了本机群 O-16 为何把 `--peer` 定性为"独立协议层"**。
> 2. **D7 缺的那一格已被 ds 明确命名**（E1）：ds 把
>    **"RULE-5 异构复审编排（subagent-a2a 基建已就绪，缺编排层）"** 登记为悬挂项 ——
>    与本机群 D7 的缺口**同名同形**（协议/基建都有，缺"谁审谁、几轮、结论怎么收束记账"）。
> 3. **ds 的「审阅方法论」比协议层更可直接搬**（E2）：RULE-5/RULE-6 + ADD Iron Law + trust-registry 的
>    「AI 初审 → 人工终裁 → 留痕机器强制」是一套**可执行的审阅质量规范**，与 D7 目标直接对接。

**不建议照搬的**：cordis 插件内核、HMR 进程内重载、168 个 invariant companion、40+ 门禁——那是
Node/TS monorepo + 团队规模的回本结构；本机群是三机 SSH + PowerShell + 单人，照搬会变成新债务。

这不是"谁抄谁"，而是**同一问题族的收敛解**，故可信度较高：

| 结论 | `D:\ds` 的形态 | 本机群对应 |
|---|---|---|
| **证据分级** | E1-E5（E5 禁入结论） | ADR-0004 证据等级约定（E1-E4）**已同构** |

## 3. 对 agent 编排（D6 框架）可吸收的

按"对本机群的可迁移性"排序。

### 3.1 【P0 最有价值】门禁调度器的数据结构

`scripts/run-gates.ts` 的 `Gate` 定义可直接移植到 `rpc_check.py`：

- **`needs` vs `after` 的语义区分**（源码注释明确）：
  `needs` = 必须 **passed** 才启动；`after` = 只需 **settle**（passed/failed/skipped 均可）。
  本机群现在的"先验红"纪律靠人记，用这个 struct 可**机械表达**。
- **启动期图校验**：空图 / **重复 gate id** / 引用未知 id / **依赖环**（DFS 报出 `a -> b -> a` 路径）——
  在跑之前就 fail，而不是跑到一半。
- **有界并发 + 代价感知**：本地模式上限 4，源码给出理由——
  "several doc gates each build a full ts.Program, so an uncapped default on a large host trades wall clock for memory blowups"。
- **`allowFailure`**：保持失败**可见**但不计入 aggregate 失败 ⇒ 本机群"黄灯"概念的现成实现。
- **失败级联为 `skipped`**，且**被跳过的门禁默认也算失败**（避免"跳过 = 通过"的隐性绿灯）。
- 失败输出把 error / exit code / signal **三条事实分别列出**（"without allowing one to hide another"）。

### 3.2 【P0】生成物 freshness 门 + "生成器先行"

- ds 的规则：生成物类文件**禁止手工编辑**，一律"采用上游生成物/生成器 → 重跑 → 跑 `--check`"；
  且**显式声明 `typecheck` 链不含任何生成器** ⇒ **编译通过 ≠ 接线完整**。
- 对本机群的含义：凡"由某处推导出来的清单"（`inventory/ops.yaml` 的登记表、手册的端口/模型表、
  `MODELS`/`ROUTES` 之类），都应视作**生成物**，改源头 + 重跑 + `--check`，而不是手改产物。
- **这正是本会话踩过的坑的正面解法**：常量层搬走后门禁扫描清单未同步 ⇒ 报数静默掉到 0 仍 PASS。

### 3.3 【P1】HMR 的"依赖传播"算法（与 cluster.py 模块化直接相关）

`vendor/hmr/src/index.ts` 的 `analyzeChanges` / `partialReload`：

- **变更分类**：直接变更或"有 accepted 依赖者" ⇒ accepted；"所有依赖者都 declined 或是 external" ⇒ declined；
  反复迭代传播直到稳定，剩下一律 declined。
- **双缓存清理**：同时清 ESM `loadCache` 与 CJS `require.cache`（否则清了假的一半）。
- **失败 rollback**：重导入失败 ⇒ 恢复两份缓存 + 重新注册旧插件。
- 触发全量重启的判据：变更落在 `externals`（框架级依赖）⇒ `loader.exit()`。

> 移植价值（E4）：本机群不需要 HMR，但"**改了 A 要重跑哪些检查/重建哪些产物**"是同一类问题。
> 与其每次靠人判断，可给 `inventory/impact.yaml` 加一张 consumer 反向传播表。

### 3.4 【P1】cordis 的依赖注入语义 = "高内聚低耦合"的机械实现

- **按 key 查服务**（`ctx.tools` / `ctx.llm`）而非 import 具体实现 —— 跨模块耦合的唯一通道。
- **声明式依赖（`inject`）表达加载顺序**，不手写 boot 排序；**服务被替换 ⇒ 依赖者自动卸载并按需重载**
  （`Fiber` 的 epoch 机制：`_refresh` 拼 `':' + impl.fiber.uid`，epoch 变化即 reload）。
- **注册即可逆 effect**：每个注册产出 disposer，卸载时**逆序**执行 —— 解"插件化后关不干净"。
- **误配置大声失败**；**显式 `resolve(request): Spec` 优先于 `run()` 里隐藏的 `?? default`**。

这正是本会话 `cluster.py` 模块化想要的**终态**：现在已做到"门面重导出"，但依赖方向仍靠人维持。

### 3.5 【P1】依赖治理三层（全部可执行）

| 层 | 机制 | 本机群对应 |
|---|---|---|
| 包级 | `module-graph` 由 `peerDependencies` 生成，**拓扑排序在生成阶段就拒绝成环** | `cluster_*.py` 之间是否成环？**当前无检查** |
| 目录级 | `verify-client-domain-graph`：`contract → domain → assembly` 分层，**domain 之间禁止互相 import** | `ops/` 下模块边界无检查 |
| 部署级 | `verify-runtime-closure`：preset 引用的每个包 + 每个非 optional peer 都必须在运行时清单里 | 站上运行时件 vs repo 的一致性（`scripts` 断言的 `station_runtime`） |

### 3.6 【P1】逐包 invariant companion

每个包一个 `src/invariant.ts`（ds 有 **168 个**），Vitest 全局拦截 `RegistryService.prototype.plugin`
让测试挂上当前包的不变式；并有拓扑测试挂载**全部** companion 保证覆盖。
硬规则：**"Runtime invariants assert owned relationships"，而非服务/方法是否存在**。

> 对本机群：`tests/test_cluster_pure.py` 是"特征测试"，等价物是"改完后**关系**仍成立"的断言
> （例：门面重导出的 46 个符号仍在、`ROUTE_TABLE` 与 `inventory` 声明源仍一致）。

### 3.7 【P2】Agent Note 制度（决策记录的强制形态）

- **路径即元数据**：`{lifecycle}/{class}/yyyy-mm-dd-topic.md`，`class` 为**封闭集合**
  （feature/bug-fix/simplification/architecture/process/testing）由脚本拥有，分类门禁拒绝其他目录。
- **非平凡改动必须在同一 PR 新增或更新至少一个 Note**；"非平凡"被逐项列出。
- **`## Alternatives considered` 是强制 section** —— ds 的理由值得引用：
  **"A decision recorded without what it beat invites re-litigation."**
- 格式门禁机械校验；`implemented/` **禁 spec-speak**；归档后**永久冻结、不得作为当前权威**。

> 本机群 ADR 已有"替代方案"节（ADR-0008 有），但缺少**格式门禁**与**归档冻结**的机械保证。

## 4. 对未来 D7（`--peer` 站间互审）可吸收的

### 4.1 【硬事实，决定架构】A2A 没有 server→client 回调

**E1 抽验原文**（`spec/wp07b-a2a-client/RESEARCH.md` §2 表格"权限回调"行）：

> **协议无此面**（v1.2 审计补强：规范 7 方法 const 全表 :400~:1906——tasks/cancel、
> pushNotificationConfig/get、tasks/get、message/send、message/stream、pushNotificationConfig/set、
> tasks/resubscribe——**全部 client→server 方向，零 server→client 回调方法**；server 侧 D-4 同结论方向反转）

三条推论：

1. **"对等互审"不是协议给的**。A2A 提供的只是"每个节点**能**扮演 server（被调用）与 client（调用别人）"
   的**对称能力面**。⇒ D7 若走 A2A，**每站必须同时挂两半**：`a2a-server`（我被审）+ `a2a-client/subagent`（我去审）。
   ⇒ **这与本机群 O-16 的定性完全吻合**——OPEN-ISSUES 原文：
   "站间互审属**独立协议层**，明确**递延 D7**"。
2. **主动回推首期不可用**：唯一 server→client 通道 `pushNotificationConfig/set|get` 首期恒返
   `-32003 PushNotificationNotSupported`（诚实降级，不假装支持）。⇒ **审阅结论只能**：
   (a) SSE 流同步收束（`message/stream` → `status-update(final=true)`），或 (b) client 侧轮询 `tasks/get`。
3. **诚实降级优于伪造能力**：ds 的 `-32003` / `-32005 ContentTypeNotSupported` 是同一条纪律的两次落地。
   ⇒ 本机群 O-16 的"未实现子项显式挂起 + 关闭判据"是同一风格。

### 4.2 【P0】D7 缺的那一格，ds 已明确命名

**E1 抽验原文**（`spec/wp04-spec-workflow/DESIGN.md` 悬挂项，第 175 行）：

> - **RULE-5 异构复审编排(subagent-a2a 基建已就绪,缺编排层);**

**E1 抽验原文**（本机群 `spec/d6-agent-standard/OPEN-ISSUES.md` O-16）：

> **--peer 站间互审（2026-09-14 复核确认）**: `agent-cli` 侧 `--peer` 无任何实现（grep 仅命中注释处）；
> 站间互审属**独立协议层**，明确**递延 D7**…D6 一期 review ring（五源异基座 judge：egress/local/http/http-local）
> 已覆盖单机闭环；站间互审（peer station 互审）待 D7 立项。

以及 O-24 断点① 的定性（同一文件）：

> **① review --peer 缺** | D7+ 站间互审协议未做；"复审"靠人工切会话 | 任务完成≠质量闭环；
> 单机无第二站互审 → 产出→ledger 后**无机器复核门**

> **判断（E4）**：ds 的悬挂项与本机群 D7 是**同一个缺口的两种叫法**——
> 双方都已有"通道/基座/协议"，缺的都是**编排层**（谁审谁、审几轮、结论怎么收束并记账）。
> 差别在于：ds 的编排层是**纯新增**（它自己的基建已就绪）；本机群的编排层要**跨三站 + 跨 CLI**。

### 4.3 【P0】审阅方法论本体（比协议更可直接搬）

ds 的 RULE 家族是"站间互审"的**规范定义**，来自 `wp04-spec-workflow/RESEARCH.md` §1.1：

| 规则 | 内容 | 对 D7 的直接用途 |
|---|---|---|
| **RULE-5 异质性** | ① reviewer ≠ implementer **基座**（异构模型家族）② **reviewer 只标记、永不改写**（单向权限，防 answer corruption） | **D7 的权限模型**：审方只产"标记/意见"，**不得直接改写被审产物** |
| RULE-5 文献依据 | MAD（arXiv:2502.08788）：**同质辩论胜率 <20% 且耗 3–5x token** | 为"为何要跨站跨模型"提供外部依据（本机群 O-16 五源异基座可引用） |
| **RULE-6 证据绑定** | (a) E5 推测**禁入**结论 (b) 审计项↔证据**双向映射** (c) **诚实结果列**："发现 N 项"合法、**零发现触发降级重扫** (d) **最高等级绑定**（E1/E2 可得却只绑 E4 = 静默降级） | **审阅意见质量的验收标准** |
| **RULE-4 自查声明** | 既写又审必须标 `自查(单视角)`；文献：同上下文反思纠错率 <2%、自我纠错盲区 64.5% | 本机群同一 Agent 既写又审的场景需要此声明 |
| **RULE-1 时序独立** | Review 勾选须在完稿后的**独立 pass**，禁与正文同次 Write | ds 因"基座无文档编辑事件面"**登记悬挂**；**本机群有 git ⇒ 反而更容易做**（E4） |
| **ADD Iron Law** | **测试通过 ≠ 设计落地**；四阶段审计：完整性 / 忠实度 / 必要性 / **语义**（意图层） | 互审要分"有没有 / 对不对 / 该不该 / 是不是这个意思"四层，混审会互相掩盖 |

### 4.4 【P0】裁决机制：AI 初审 → 人工终裁 → 留痕机器强制

`trust-registry/` 的 `adjudicate.py` 是本机群**最有直接参照价值**的一块：

- **AI 初审 ≠ 终裁**（代码抬头明写"RULE-4：初审不构成终裁"）：`pre_review()` 只给
  `expected-by-design` / `needs-review` **建议**。
- **终裁必须显式回写**：`--apply <id> --verdict <v>`；**flagged 条目无自动批准路径**（不变式 I-F5）。
- **裁量必须留痕，且机器强制**：走 flagged 路径批 `approved-personal` 时 `adjudicated_reason` **非空是硬约束**
  （SCHEMA 约束 4 + `_legal()` 双重校验）；`rejected` 必须给 `--reason`。
  > **实测**：`registry.jsonl` 有 **20 条** `adjudicated_reason`，恰好等于 flagged/failed 的 20 条
  > ⇒ **约束真的在执行**（不是纸面规则）。
- **裁决界面按人工成本分层**：flagged 逐件给 `file:line` + 代码上下文 + 初审 + **该条目的终裁命令模板**；
  passed 只给汇总表 + 批量入口；failed 单列。**LOW 命中不入队列只入报告**，理由明写"队列保持人工可过目规模"。
- **验证器自带对抗负例**：`validate_registry.py --selftest` 内建 **8 条坏条目**，要求"漏检 0/8"
  —— 把"验证器本身可信度"也纳入度量。

> **对 D7 的映射（E4）**：站间互审的结论回写，应照此形状——
> **审方给"建议 + 证据 + file:line"，终裁由被审方/管理员显式回写，且回写必须带理由、
> 无理由的批准路径不存在**。这与本机群 ADR-0005/0007 的证据链是同族。

### 4.5 【P1】任务状态机与跨域映射

- **九态 TaskState**：`submitted / working / input-required / completed / canceled / failed / rejected /
  auth-required / unknown`；终态 = completed/canceled/failed/rejected。
- **身份映射三态**：`contextId ↔ Session`（一对一）、`taskId ↔ context 内一次任务`（可多轮续聊）；
  创建语义三分支（新 taskId / 续 taskId / 带 contextId 无 taskId）。
  ⇒ **互审映射**：一次"审阅委托" = 一个 task；同一被审对象的多轮往返 = **同 task 续聊**。
- **跨域映射 + 裁量登记**：`TurnEndReason(6 值) → TaskState` 逐分支穷举，**无对应态的 4 处显式登记为 M-1~M-4**
  （例：`max-tokens` → `completed` + status.message 说明）。
  ⇒ **站间状态词汇必然不匹配**，"逐分支穷举 + 每处不对应登记裁量号"是可复制的工程范式。
- **双向对称性检验（防死锁）**：ds 明写 server 侧"approval 挂起不桥接 `input-required`"与 client 侧
  "`input-required` → error + diagnostic + best-effort cancel"是**方向反转对称**，
  **两端都不把 input-required 当可完成态**。
  ⇒ **D7 必须对"需要补充信息"这类中断态双方同时声明口径**，否则会出现一端等待、一端失败的死锁。
- **`rejected` 映射到 `refusal` 而非 `error`**：保留"这是**拒绝**而非**故障**"的语义
  （否则模型无法区分"远端不想做"与"远端坏了"）。**对互审结论的"驳回"语义直接适用。**

### 4.6 【P1】能力发现 = 机器可读的"我能审什么"

`GET /.well-known/agent.json` → AgentCard：必填 8 字段（capabilities / defaultInputModes /
defaultOutputModes / description / name / **skills** / url / version），`AgentSkill` 必填四字段
（description / id / name / tags），`capabilities` 三布尔（streaming / pushNotifications /
stateTransitionHistory），可选 `extensions: AgentExtension[]`（uri + required + params）。

> **对 D7**：`skills[]` 就是"**这个站能审什么**"的公开声明面；`extensions[]` 是挂私有审阅语义
> （如"审阅协议版本 / 判官能力"）的**官方扩展点**。本机群已有 `JUDGE_TABLE`，可考虑对外暴露同形声明。

### 4.7 【P1】自环验证的复利 + **必须登记盲区**

- **复利**：wp07b 用 wp07 已交付的真 `a2a-server` + MockAdapter 作对端，
  **同一仓库内起真 server、真 SSE、真任务状态机**，"零新 mock 基建"。
- **盲区（ds 自己登记的原文）**：
  "dsh↔dsh 自环永远走我方两端的善意实现；**异构第三方 A2A server 的真实差异未测**"。

> **对本机群（重要）**：三站自环互审**也有同一个盲区**——
> A↔B 互审走的是**我方同一套 agent-cli + 同一批模型族**，
> 无法证明"对**异构**审方有效"。ds 的做法是**显式登记**；本机群应照做
> （O-16 的"五源异基座"正是缓解手段，但**跨站**维度仍属自环）。

### 4.8 【P1】离线/运行时分层 + "未测量"纪律

ds 的交付状态词表：`accepted-offline`（wp06）、"有条件通过（条件 = daemon 启动后闭合）"（wp06）、
"单题通过 ≠ 全量可用"（wp02 Iron Law）、"E2 前不宣称可用"（wp01 不变式 I-E）。

> **对 D7**：跨站必然大量处于"未测量"（对端站可能关机、引擎可能未加载、零自加载铁律）。
> 这套状态词表能**防止把"没测过"混进"已验证"**——与本机群门禁 `quick`/`full` 分层同源。

### 4.9 【P2】协议版本选型方法论（v0.2.2 vs v1.0.0）

ds 选 **v0.2.2** 弃 v1.0.0，四条理由：栈契合（TS monorepo 无 protobuf 工具链）/ 生态现实 /
核心模型连续 / **范围纪律**（多租户、签名 Card、mTLS 属企业特性）。
并明确 **"v1.0.0 不实现、不预留钩子"**（不留半成品钩子）。

其差异表中**对"审计签名的审阅意见"最有价值的两项**（E2）：
- v1.0.0 新增 **签名 Agent Card**（`AgentCardSignature`）与 **mTLS**；
- v1.0.0 新增 `AgentInterface{url, protocol_binding, protocol_version, tenant}`
  （一个 agent 可在多协议绑定下暴露同一功能）。

> **若 D7 要求"审阅意见可验证签名"**，则 v1.0.0 的签名 Card 是比 v0.2.2 更合适的起点（E4）。
