## 3. 对 agent 编排（D6 框架）可吸收的

### 3.1 【P0】门禁调度器的数据结构

**出处（E2）**：`deepseek-harness/scripts/run-gates.ts`。

- **`needs` vs `after` 语义区分**（源码注释明确）：`needs` = 必须 **passed** 才启动
  （`predecessorsReady` 要求 `states.get(id) === 'passed'`）；`after` = 只需 **settle**
  （`gateSettled` = passed | failed | skipped）。
- **启动期图校验** `validateGateGraph()`：空图 / **重复 gate id** / 引用**未知 id** / **依赖环**
  （`findDependencyCycle` 用 active/complete 双集合 + path 栈 DFS，报出 `a -> b -> a`）。
- **有界并发 + 代价感知**：本地模式上限 4，源码理由 ——
  "several doc gates each build a full ts.Program, so an uncapped default on a large host
  trades wall clock for memory blowups"。`DSH_GATE_CONCURRENCY` 可覆盖。
- **`allowFailure: true`** = "**保持失败可见，但不算 aggregate 失败**"（退出码计算显式排除）。
  ⇒ 本机群"黄灯"（`rpc_check` 现报 `绿灯 11 · 黄灯 0 · 红灯 0`）的现成实现。
- **失败级联为 `skipped`**，且**被跳过的门禁默认也算失败**（`main()` 的退出码条件含 `status === 'skipped'`）。
- **失败输出把三事实分列**：`formatGateResultReason` 把 error / exit code / signal
  全部独立拼出，"without allowing one to hide another"。

### 3.2 【P0】生成物 freshness 门 + "生成器先行"

**出处（E2）**：`UPSTREAM_DRIFT_RESEARCH.md` §4.6 / §8 建议 2 / §9 坑 4；
`DSH_UPGRADE_PLAN.md` §13.5 第 9 条。

- 生成物类文件**禁止手工编辑**，一律"采用上游生成物 / 生成器 → 重跑 → 跑 `--check`"。
- **显式声明 `typecheck` 链不含任何生成器** ⇒ **编译通过 ≠ 接线完整**。
- 活案例（E2，`UPSTREAM_DRIFT_RESEARCH.md` §4.6.1）：手写 alias 会漏掉 invariant 变体
  （alias 数量是包数的 2 倍）；正确的检查项是"迁移后跑 `verify-tsconfig-paths`"。
- **对本机群**（E4）：凡"由某处推导出来的清单"（`inventory/ops.yaml` 登记表、手册端口/模型表、
  `ROUTE_TABLE`/`MODELS`）都应视作**生成物**：改源头 + 重跑 + `--check`，不手改产物。
  **这是本会话那个假绿的正面解法。**

### 3.3 【P1】HMR 的"依赖传播"算法

**出处（E2）**：`deepseek-harness/vendor/hmr/src/index.ts`（`analyzeChanges` / `partialReload`）；
`vendor/hmr/README.md`。

- **变更分类**：直接变更或在 `stashed` 中 ⇒ accepted；"有 accepted 的 dependent" ⇒ accepted；
  "所有 dependent 都 declined 或是 external" ⇒ declined；迭代传播至稳定，剩下归 declined。
- **双缓存清理**：同时清 ESM `loadCache` 与 CJS `require.cache`
  （源码注释："In Node 24, both CJS and ESM modules imported via import() end up in loadCache"；
  且 `LoadCache.delete()` 只把 type 槽置 undefined，不真正移除）。
- **失败 rollback**：重导入失败 ⇒ `handleError` + `rollback()` 恢复两份缓存并重新注册旧插件。
- 触发全量重启的判据：变更落在 `externals`（框架级依赖）⇒ `loader.exit()`。
- **"Plugin entry files are treated as atomic reload units."**

> 移植价值（E4）：本机群不需要 HMR，但"**改了 A 要重跑哪些检查 / 重建哪些产物**"是同一类问题。
> 可给 `inventory/impact.yaml`（现有 8 模型 / 5 端口 / 4 配置 / 28 条 consumer 校验）加反向传播表。

### 3.4 【P1】cordis 的依赖注入语义 = "高内聚低耦合"的机械实现

**出处（E2）**：`vendor/cordis/src/{context,service,fiber,registry,events}.ts`；
`docs/cordis-primer.md`。

- **按 key 查服务**（`ctx.tools` / `ctx.llm`）：`Context` 构造器返回
  `new Proxy(this, ReflectService.handler)` ⇒ **普通属性读取走服务解析器**，不是字段读取
  （`vendor/cordis/src/context.ts`）。
- **声明式依赖（`inject`）表达加载顺序**，不手写 boot 排序；**服务被替换 ⇒ 依赖者自动卸载并按需重载**：
  `Fiber._refresh()` 遍历 `inject` 各服务，任一缺失则 epoch = `INACTIVE`，否则拼 `':' + impl.fiber.uid`；
  epoch 变为有效 ⇒ `_reload()`，有效值变化 ⇒ `_unload()` 后 `_reload()`（`fiber.ts`）。
- **注册即可逆 effect**：`ctx.effect(execute, label?)` 收集 disposer，卸载时**逆序**执行
  （`docs/cordis-primer.md` Practical Rules："If teardown order matters, keep the related work in one effect"）。
- **误配置大声失败** + **显式 `resolve(request): Spec` 优先于 `run()` 里隐藏的 `?? default`**
  （`AGENTS.md` Conventions："Explicit > implicit at package boundaries"，`dsh-shell` 为模板）。
- **三种插件形态正交**：`Plugin.Function` / `Plugin.Constructor` / `Plugin.Object{apply}`
  （`vendor/cordis/src/registry.ts`）。

### 3.7 【P2】Agent Note 制度（决策记录的强制形态）

**出处（E2）**：`.agents/notes/README.md`、`AGENTS.md`、`scripts/run-gates.ts`（docSyncLeafGates 三项）。

### 3.8 【P0】门禁拓扑：单一 required check 的 fan-in（本轮新增，E2）

**出处（E2）**：`codex-main/.github/workflows/blocking-ci.yml`、`.github/scripts/check_ci_results.py`、
`.github/workflows/README.md`、`bazel.yml`、`rust-ci.yml`。

- **单一 required check**：`blocking-ci.yml` 把 7 个子工作流（bazel / blob-size-policy / cargo-deny /
  codespell / repo-checks / rust-ci / sdk）扇入**一个** `CI required` job；
  分支保护只需维护一个状态（注释原文："The `required` job below is the version-controlled list
  that the main-branch ruleset should require."）。
- **⚠ `if: always()` 是必需的**（注释解释）：不加它，依赖失败时 required check 反而会显示**成功**。
- **判定策略集中在唯一脚本**（`check_ci_results.py`，注释："Keep result policy in one script so
  blocking-ci and postmerge-ci cannot drift"），且 **skipped 与 cancelled 一律按失败处理**，
  只认显式 success。
- **变更检测驱动提速**：`rust-ci.yml` 用手写 `git diff --name-only` 判定 4 个路径开关
  （不用外部 action，`persist-credentials: false`）；`results` job 在"无相关改动"时直接成功。
- **PR 门禁与 post-merge 全量分离**，且有书面 rule of thumb（`README.md`）：
  "能写成 Bazel 的检查，PR 版本就放 `bazel.yml`"；全量 nextest 矩阵 / release 构建 /
  ARM64 交叉+回放放 `rust-ci-full.yml`，只在 main / `**full-ci` / dispatch 跑。
- **"保留 required check 名字"的占位 job**：`test-windows` 是纯 fan-in 占位，注释明写
  "Preserve the existing required-check surface while the real work happens in the sharded
  Windows jobs above" —— **避免改分支保护规则**。
- **分片用确定性哈希而非随机**：`cksum % 4` 分桶；空分片直接 `exit 1`（防空转）。
- **没有把任何实质检查设成 allow-failure**；文件里的 `continue-on-error: true` 只作用于
  非门禁副作用（上传日志、存 cache）。

### 3.9 【P0】"一份事实源 + 一处镜像 + 一个脚本保证同步"（本轮新增，E2）

**出处（E2）**：`codex-rs/Cargo.toml`（`[workspace.lints.clippy]`）、`codex-rs/.bazelrc`（`--config=clippy`）、

### 3.12 【P1】网络隔离的**双层 default-deny**（本轮新增，E2）

**出处（E2）**：`codex-rs/network-proxy/`（含 `README.md`、`config.rs`、`network_policy.rs`）、
`.devcontainer/init-firewall.sh`、`.devcontainer/Dockerfile.secure`。

- **第一层（应用层代理）**：白名单未配置 ⇒ **一律阻断**；通配三态
  （精确 / `*.sub` / `**.apex`，**全局 `*` 默认拒绝**）。
  **`deny` 始终覆盖 `allow`，且用枚举序编码优先级** `None < Allow < Deny`
  （注释原文："so deny wins over allow when entries conflict"）⇒ **靠类型系统而非散落的 if**。
- **本地/私网保护**：即使白名单里写了 localhost，**解析到私网 IP 的域名仍被阻断**。
- **覆盖仅限"未命中"**：策略钩子只能覆盖 `NotAllowed`，**不能覆盖显式 deny / local 阻断**。
- **审计刻意不含完整 URL**（只记 host/port/method/decision/source/reason），
  被阻断返回 403 + `x-proxy-error`（可归因到 `blocked-by-allowlist`/`-denylist`/`-method-policy`）。
- **第二层（OS 层防火墙）**：`iptables`/`ip6tables` 三链 **DROP**；域名 `dig +short A` 解析为
  IPv4 后进 `ipset` 白名单；末尾用 **`REJECT --reject-with icmp-admin-prohibited` 而非静默丢弃**
  （注释："让策略失败可见"）；**IPv6 独立默认拒绝**。
- **★ 脚本末尾自验证**：`init-firewall.sh` 结束时断言"`example.com` 不可达、`api.openai.com` 可达、
  `example.com` 的 IPv6 不可达"，**任一不符即 `exit 1`** —— 这是"策略生效"的**正向+反向**证明，
  与本机群"先验红"同源（E4）。
- **已知局限（作者自述）**：不 pin 解析 IP 就无法彻底防 DNS rebinding，建议在更低层（防火墙/VPC）也做出口管控。

### 4.1 【硬事实，决定架构】A2A 没有 server→client 回调

**E1 抽验原文**（`spec/wp07b-a2a-client/RESEARCH.md` §2 表格"权限回调"行）：

> server 侧 D-4 同结论方向反转）

**版本面复核（E2）**：`spec/wp07-a2a/a2a-v1.0.0.proto` 的 `service A2AService` **11 个 rpc 亦全为单向**。

**三条推论**：

1. **"对等互审"不是协议给的**。A2A 只提供"每个节点**能**扮演 server（被调用）与 client（调用别人）"
   的**对称能力面** ⇒ D7 若走 A2A，**每站必须同时挂两半**：`a2a-server`（我被审）+
   `subagent-a2a`（我去审），二者共享同一份 `a2a-protocol` 纯函数库。
   ⇒ **与本机群 O-16 定性吻合**（E1，`OPEN-ISSUES.md` O-16 原文）：
   "站间互审属**独立协议层**，明确**递延 D7**…D6 一期 review ring（五源异基座 judge：
   egress/local/http/http-local）已覆盖单机闭环；站间互审（peer station 互审）待 D7 立项。"
2. **主动回推首期不可用**（E2）：唯一 server→client 通道 `pushNotificationConfig/set|get`
   首期恒返 `-32003 PushNotificationNotSupported`（`wp07-a2a/DESIGN.md` §1 R-3 + §7 D-2）
   ⇒ 审阅结论只能 (a) SSE 流同步收束（`message/stream` → `status-update(final=true)`）
   或 (b) client 侧轮询 `tasks/get`（`wp07b/DESIGN` D-3 已 deferred）。
3. **诚实降级优于伪造能力**（E2）：`-32003` / `-32005 ContentTypeNotSupported` 是同一纪律两次落地
   ⇒ 与本机群"未实现子项显式挂起 + 关闭判据"同风格。

### 4.4 【P0】裁决机制：AI 初审 → 人工终裁 → 留痕机器强制

**出处（E2）**：`trust-registry/adjudicate.py`、`trust-registry/SCHEMA.md` §3、`registry.jsonl`。

- **AI 初审 ≠ 终裁**（`adjudicate.py` 抬头注释明写"RULE-4：初审不构成终裁"）：
  `pre_review()` 只给 `expected-by-design` / `needs-review` **建议**。
- **终裁必须显式回写**：`--apply <id> --verdict <v>`；**flagged 条目无自动批准路径**（不变式 I-F5）。
- **裁量留痕是机器强制的**：`approved-personal` 走 flagged 路径时 `adjudicated_reason` **非空为硬约束**
  （SCHEMA §3 约束 4 + `_legal()` 双重校验）；`rejected` 必须给 `--reason`。
  > **实测（E2）**：`registry.jsonl` 有 **20 条** `adjudicated_reason`，
  > **恰好等于** `scan_status ∈ {flagged, failed}` 的 20 条 ⇒ **约束真的在执行，不是纸面规则**。
  > 示例（第 34 行）：`plg-claude-skills-cc-haha-enhanced-5db3`（T0-exec, flagged, approved-personal）
  > → `adjudicated_reason: "MED=测试文件 spawn node 起本地服务,功能本体"`。
- **裁决界面按人工成本分层**（`build_queue()`）：flagged 逐件给 `file:line` + 代码上下文（命中行前 1 行 + 命中行）
  + AI 初审 + **该条目的终裁命令模板**；passed 只给汇总表 + 批量入口；failed 单列。
  **LOW 命中不入队列只入报告**，理由明写"队列保持人工可过目规模"。
- **验证器自带对抗负例**：`validate_registry.py --selftest` 内建 **8 条坏条目**
  （模板 4 + 全量 4：path 不存在 / 非法跃迁 / 计数不符 / T0 获 reference 批准 / approved-personal 缺约束 /
  flagged 无留痕自动批准 / parent 不存在 / 许可 pass 冒用 approved-personal），要求"漏检 0/8"
  ⇒ **把"验证器本身可信度"也纳入度量**。

> **对 D7 的映射（E4）**：站间互审的结论回写应照此形状 ——
> **审方给"建议 + 证据 + file:line"，终裁由被审方 / 管理员显式回写，回写必须带理由，
> 且"无理由的批准路径"不存在**。与本机群 `ADR-0005`/`ADR-0007` 的证据链同族。

### 4.5 【P1】任务状态机与跨域映射

**出处（E2）**：`spec/wp07-a2a/DESIGN.md` §3、`spec/wp07b-a2a-client/DESIGN.md` §4、
`spec/wp07-a2a/a2a-v0.2.2.json`。

- **TaskState 九态**：`submitted / working / input-required / completed / canceled / failed /
  rejected / auth-required / unknown`；终态 = completed/canceled/failed/rejected。
- **身份映射三态**（`wp07 DESIGN` §3.1）：`contextId ↔ harness Session`（一对一）、
  `taskId ↔ context 内一次任务`（可多轮续聊）；创建语义三分支（无 taskId ⇒ 新建 session + 新 task；
  带既有 taskId ⇒ 同 task 续聊 `agent.followup`；带 contextId 无 taskId ⇒ 同 session 新 task = **M-6 裁量**）。
  ⇒ **互审映射**：一次"审阅委托" = 一个 task；同一被审对象的多轮往返 = **同 task 续聊**。
- **跨域映射 + 裁量登记**：`TurnEndReason(6 值) → TaskState` 逐分支穷举，
  **无对应态的 4 处显式登记为 M-1~M-4**（`max-tokens` → `completed` + status.message 说明；
  `blocked` → `completed`；`aborted` → `canceled`；`interrupted` → `failed`）。
  ⇒ **站间状态词汇必然不匹配**，"逐分支穷举 + 每处不对应登记裁量号"是可复制的工程范式。
- **双向对称性检验（防死锁）**（E2，`wp07b RESEARCH` §10 R-5）：ds 明写 server 侧
  "approval 挂起**不桥接** `input-required`"与 client 侧"`input-required` → error + 固定 diagnostic
  + best-effort `tasks/cancel`"是**方向反转对称 —— 两端都不把 input-required 当可完成态**。
  ⇒ **D7 必须对"需要补充信息"这类中断态双方同时声明口径**，否则一端等待、一端失败的死锁。
- **`rejected` → `refusal` 而非 `error`**（E2，`wp07b DESIGN` §1 R-4）：保留"这是**拒绝**而非**故障**"
  的语义（映射 error 会让模型无法区分"远端不想做"与"远端坏了"）。**对互审结论的"驳回"语义直接适用。**
- **client 侧九态→五值完整映射表**（E2，`wp07b DESIGN` §4）：completed→completed / canceled→aborted /
  failed→error+diagnostic / **rejected→refusal** / auth-required→error+diagnostic /
  unknown→error+diagnostic（**不作 completed：未知即失败**）/ input-required→error+diagnostic+best-effort cancel。

### 4.9 【P2】协议版本选型方法论（v0.2.2 vs v1.0.0）

**出处（E2）**：`spec/wp07-a2a/RESEARCH.md` §2.1（差异表）、`wp07-a2a/DESIGN.md` §1 R-1。

选 **v0.2.2** 弃 v1.0.0，四条理由：**栈契合**（TS monorepo 无 protobuf 工具链，JSON-RPC 零摩擦）/
**生态现实** / **核心模型连续** / **范围纪律**（多租户、签名 Card、mTLS 属企业特性）。
DESIGN R-1 明确 **"v1.0.0 不实现、不预留钩子"**（不留半成品钩子）。

**差异表要点（E2）**：

| 维度 | v0.2.2（选定） | v1.0.0 |
|---|---|---|
| 序列化/传输 | **JSON-RPC 2.0 over HTTP + SSE** | protobuf/gRPC 优先 + REST 绑定 |
| RPC 方法 | **7 个** | **11 个**（新增 `ListTasks` + push-config CRUD 5 个 + `GetExtendedAgentCard`） |
| TaskState | 小写连字符九态 | `SCREAMING_SNAKE_CASE`（含 `TASK_STATE_UNSPECIFIED`） |
| 多租户 | 无 | 路径参数 `/{tenant}/…` |
| 安全 | securitySchemes 五型 | + **签名 Agent Card**（`AgentCardSignature`）、**OAuth2 Device Code**、**mTLS** |
| **破坏性变更** | — | **移除 `kind` 判别器**；`TaskStatusUpdateEvent` **移除 `final` boolean** |

另（E2）：v1.0.0 用 `AgentInterface{supported_interfaces[]}`（`url` + `protocol_binding` + `tenant`
+ `protocol_version`）**取代单一 `url` 字段**；`Part` 改为 `oneof content{text|raw|url|data}`。

> **若 D7 要求"审阅意见可验证签名"**，则 v1.0.0 的签名 Card 是比 v0.2.2 更合适的起点（E4）。

### 4.10 【P0】Codex 自己就实现了"评审" —— `core/src/tasks/review.rs`（本轮新增，E2）

**出处（E2）**：`codex-rs/core/src/tasks/review.rs`、`codex-rs/protocol/src/protocol.rs`、
`codex-rs/prompts/src/review_request.rs` + `prompts/templates/review/rubric.md`、`codex-rs/core/src/tasks/mod.rs`。

> **这一节是本次补调研最重要的发现**：Codex 内建了一个完整的"代码评审"任务实现，
> 与 D7 要做的"站间互审"是**同一个问题的另一种解法**，可直接对表。

**① 评审对象（`ReviewTarget`，`protocol.rs`）四类**：
`UncommittedChanges`（工作区 staged+unstaged+untracked）/ `BaseBranch{branch}`（分支 diff）/
`Commit{sha,title}` / `Custom{instructions}`。⇒ **评审对象 = 代码改动，最终以 diff/patch 形式进入评审**。

**② 结论契约（`ReviewOutputEvent`）**：

```
ReviewOutputEvent {
  findings: Vec<ReviewFinding>,
  overall_correctness: String,      // "patch is correct" | "patch is incorrect"
  overall_explanation: String,
  overall_confidence_score: f32,
}
ReviewFinding { title, body, confidence_score: f32, priority: i32, code_location }
ReviewCodeLocation { absolute_file_path: PathBuf, line_range: { start, end } }
```

- **没有 `approve`/`reject` 枚举** —— verdict 用**受限字符串**表达，
  severity 用 **`priority: i32`（0=P0 blocking release … 3=P3 nice-to-have）**，
  另有 `confidence_score: f32`。
  ⇒ **可借鉴**（E4）：D7 的审阅结论若也用"整数优先级 + 浮点置信度 + 受限字符串判定"，
  比定义一套自造枚举更易阈值化与排序。
- **每条 finding 必须带 `code_location{path, line_range}`** ⇒ 意见**必须可定位到行**。

**③ 评审者 = 独立子会话 + 能力削减**（关键设计）：
另起 `run_codex_thread_one_shot(..., SubAgentSource::Review, ...)`，并**强制裁剪配置**：
- `web_search_mode = Disabled`
- **禁用 `Feature::Collab` / `Feature::MultiAgentV2`**
  （注释原文："Carry over review-only feature restrictions so the **delegate cannot re-enable
  blocked tools**（web search, collab tools, view image）"）
- **`approval_policy = Constrained::allow_only(AskForApproval::Never)`** ⇒ 评审者**永不触发审批**
- `base_instructions = Some(REVIEW_PROMPT)`（rubric 独立成文件，`include_str!` 嵌入）
- 模型：`config.review_model` 优先，否则退回当前模型

⇒ **可借鉴**：**评审者的能力必须被裁剪，且要防它"自己把工具开回来"**；
`approval = Never` 保证评审过程零交互。**这与 RULE-5「reviewer 只标记、永不改写」是同一条原则的两种落地。**

**④ rubric 是纯提示词，且明确"只管本次引入的问题"**（`rubric.md`）：
- 8 条"算不算 bug"的判据，**第 4 条：只管本次 commit 引入的问题，不报既存 bug**
- **评论风格约束**：最多 1 段、代码片段 ≤ 3 行、语气平实
- **仓库规则归因优先级**：`AGENTS.override.md` → `AGENTS.md` → 回退名，且需给出**最小支持行范围**
- 结尾 **"Do not generate a PR fix."**（评审者不产出修复）

⇒ **可借鉴**（E4）：**"不报既存问题"是防噪音的关键规则**——否则评审意见会被历史债务淹没；
"评审者不产修复"与 RULE-5 单向权限一致。

**⑤ ⚠ 只有单轮，没有复核循环**：一次 `run` = 一次子会话 = 一次 `TurnComplete`；
**无循环、无二次校验、无 reviewer↔被评者往返**。
⇒ **与 ds 的 A2A 侧结论呼应**（见 §5"不一致处"）：**"多轮续聊"在这两处都是缺的**
⇒ D7 若需要"审→改→再审"，**必须自建多轮编排**（这是本轮补调研给出的**第二个独立佐证**）。

**⑥ 结论回写是双通道**：① 写一条 user message + 一条 assistant message 到会话历史；
② 发射结构化协议 item **`TurnItem::ExitedReviewMode { id, review_output }`**（started+completed）。
另有工程细节：**评审可在任何常规 user turn 之前发生，因此**显式物化 rollout
（注释："Review turns can run before any regular user turn, so explicitly materialize rollout persistence."）。

**⑦ 解析三级容错**（`parse_review_output_event`）：直接 `serde_json` 解析 →
截取首个 `{` 到末个 `}` 再解析 → 全失败则把**原始文本塞进 `overall_explanation`** 兜底。
⇒ **可借鉴**：**结构化契约 + 漂移容错**，避免"模型输出偏一点就整轮失败"。

**⑧ 屏蔽 legacy 通道**：丢弃 `ItemCompleted(TurnItem::AgentMessage)` 与 `AgentMessageContentDelta`，
注释理由："forwarding it would trigger legacy AgentMessage via `as_legacy_events()`,
which this review flow **intentionally hides in favor of structured output**."
⇒ **单一结构化输出源**，避免协议歧义。

### 4.11 【P0】`guardian`：准入闸门 + fail-closed + 熔断器（本轮新增，E2）

**出处（E2）**：`codex-rs/core/src/guardian/{mod,review,review_session,prompt}.rs`。

**① 它是"闸门"不是"监控"**（模块注释原文）：
"Guardian review decides whether an `on-request` approval should be granted
**automatically instead of shown to the user**." 四步：
重建紧凑 transcript → 专用 guardian 会话评估**确切计划动作**并返回严格 JSON →
**Fail closed（超时/失败/格式错一律阻断）** → 应用明确 allow/deny。
路由条件：`(approval_policy == OnRequest || Granular) && approvals_reviewer == AutoReview`。

**② 输出契约**：`{risk_level: low|medium|high|critical, user_authorization: unknown|low|medium|high,
outcome: allow|deny, rationale}`；`risk_level` 缺失时**allow→Low / deny→High**（保守默认）。

**③ ★ 熔断器（这是 D7 最该抄的一条）**：
- 常量：`MAX_CONSECUTIVE_GUARDIAN_DENIALS_PER_TURN = 3`；Cyber 变体 = **1**；
  近期窗口 `AUTO_REVIEW_DENIAL_WINDOW_SIZE = 50`，窗口内阈 `MAX_RECENT_..._DENIALS_PER_TURN = 10`（Cyber 1）；
  超时 `GUARDIAN_REVIEW_TIMEOUT = 90s`；`MAX_ATTEMPTS = 3`。
- 动作：超阈 ⇒ 发 `GuardianWarning` 并 **`abort_turn_if_active(turn_id, Interrupted)`**
  —— **中断整个 turn，而不是只拒这一次动作**。
- **熔断器状态与 turn 生命周期严格对齐**：turn start / finish / abort **三处都清**
  （防跨 turn 污染）。
⇒ **可借鉴**（E4）：**"反复请求 → 反复被拒"是自动审批的死循环，必须用熔断打断**；
且**熔断要打断整个 turn**（否则模型会换个形式继续试）。

**④ 拒绝指令不可绕过**（`GUARDIAN_REJECTION_INSTRUCTIONS` 原文要点）：
"must not attempt to achieve the same outcome via **workaround, indirect execution, or policy
circumvention** … Otherwise, stop and request user input."
⇒ **可借鉴**：拒绝必须**显式禁止变相绕过**，否则模型会绕。

**⑤ ★ 会话复用 + Full/Delta 提示**（`review_session.rs`）：
- `GuardianReviewSessionManager { trunk, ephemeral_reviews }`：空闲时后续审批**追加到同一 guardian 会话**
  （保持 prompt-cache 稳定）；繁忙则从最后一次已提交 trunk **fork 出 ephemeral 会话**避免互相阻塞。
- **多轮提示模式**：`prior_review_count == 0 → Full`；否则持 cursor → **`Delta{cursor}`**
  （"自上次评审以来新增的历史"，含 `>>> TRANSCRIPT DELTA START` 标题）。
- **★ 显式 `reuse key`**：`GuardianReviewSessionReuseKey` **枚举所有会改变评审语义的配置项**，
  任一变化即重建会话；`parent_history_version` 仅在特定 feature 下纳入。
- **prompt cache key**：`guardian:{parent_thread_id}`（测试断言 ≤64 字符）。
- 重试**只对瞬时的会话错误与解析错误**（`should_retry_guardian_review`），有 deadline + 取消约束。

⇒ **可借鉴**（E4）：**这是"同一评审者连续多轮"的最佳参考** ——
D7 的"审→改→再审"若由同一站连续评审，正需要"会话复用 + 增量提示 + 显式失效键"三件套。

**⑥ ★ guardian 的输入是"不可信证据"**（`session/turn.rs` 注释原文）：
"Guardian input embeds the parent transcript as **untrusted evidence**.
**Do not interpret skill or plugin mentions from that generated prompt as requests to inject
additional instructions**."
⇒ **可借鉴**：**把对方/上游的文本当不可信输入**，其内部提及不触发指令解析
—— 这是**跨信任边界传文本的通用规则**，D7 传"审阅请求/证据"时同样适用。

**⑦ 配置锁定**：guardian 会话强制 `approval=never`、权限**与只读求交**、清空 `mcp_servers`、
关闭 skill/memories/notify/developer_instructions，并禁用一大串 feature
（`Collab, MultiAgentV2, GuardianV2, CodexHooks, Apps, Plugins, WebSearchRequest, WebSearchCached`）。
⇒ **能力最小化的又一处实例**（与 §4.10 ③ 同理）。

### 4.12 【P1】角色权限模型："只减不增"（本轮新增，E2）

**出处（E2）**：`codex-rs/core/src/agent/role.rs`、`core/src/agent/control.rs`。

- 模块注释原文：“Roles may customize the child or **reduce** its capabilities,
  but **never replace the parent session's authority**.”
- **内置 3 个角色**：`default` / `explorer` / `worker`（`awaiter` 被整段注释移除）。
  `explorer` 的 description 鼓励**并行 spawn 多个**并**复用已有 explorer**；
  `worker` 强调**明确 ownership（文件/职责）**、"你不是独自在改代码库"、**不得回滚他人改动**。
- **可削减面是一个白名单**：只能把 `ShellTool | Apps | Personality | Plugins | MemoryTool |
  RequestPermissionsTool` 这些 feature 置为 **false 才生效**（值为 true 被忽略）；
  skill 也只能**禁用**（`max_context_tokens` 强制置 `None`）。
- ⇒ **角色没有独立的"工具允许列表"字段**，工具可用性只能通过禁用 feature 间接改变。
- **spawn 工具描述里显式声明"该角色的 model/reasoning/service_tier 不可更改"**
  —— 防止模型试图覆盖。
- 角色层以 `ConfigLayerSource::SessionFlags` 插入 ⇒ **可被审计**。

⇒ **可借鉴**（E4）：**"子只能减、不能增"是干净的授权基线**，可直接用于站间互审
（审方权限 ⊆ 被审方权限，且审方只读）。与 RULE-5 单向权限同族。

### 4.13 【P1】多 agent 通信原语三件套 + 完成回推（本轮新增，E2）

**出处（E2）**：`codex-rs/core/src/agent/control.rs`、`core/src/session/multi_agents.rs`、
`tui/src/multi_agents.rs`、`core/src/state/turn.rs`。

- **⚠ 一处必须纠正的误解**：`tui/src/multi_agents.rs` **只是展示层**
  （文件头注释："This module owns the shared **presentation contracts** … Higher-level coordination …
  stays in `crate::app::App`."）。**真正的编排在 `core/src/agent/control.rs`**。
- **三件套（语义极清晰）**：
  | 原语 | 语义 |
  |---|---|
  | `spawn_agent` | 起新 agent（可带 `agent_role`；fork mode = `FullHistory` / `LastNTurns(n)`） |
  | `followup_task` | 给已有 agent 派新任务**并唤醒**（`trigger_turn=true`） |
  | `send_message` | 只留言**不唤醒**（`trigger_turn=false`） |
- ⇒ **可借鉴**（E4）：**用一个布尔区分"唤醒"与"留言"**，比定义两套通道更干净。
  本机群的 `agent-cli task/review` 若要加"异步留言"，可直接套这个语义。
- **完成回推 = 订阅状态直到终态再通知父 agent**（`maybe_start_completion_watcher`），**而非轮询**。
- **并发与深度显式建模**：`max_concurrent_threads_per_session`、`AgentExecutionLimiter`、
  `exceeds_thread_spawn_depth_limit`；且**把并发数写进 usage hint**（"There are {N} available
  concurrency slots…"）。
- **★ `MailboxDeliveryPhase` 显式状态机（`CurrentTurn ↔ NextTurn`）** —— 这个细节很值得抄：
  - turn 始于 `CurrentTurn`，子 agent 邮件可并入下一次模型请求；
  - **一旦记录用户可见终态输出 ⇒ 切到 `NextTurn`**，把后到的邮件留到下一 turn，
    **避免"答案已展示又被追加"**；
  - 若同一 task 又有同 turn 的工作（steered prompt）⇒ **重新打开 `CurrentTurn`**。
  ⇒ **可借鉴**（E4）：本机群的 agent 流若要支持"边跑边追加"，这是防"输出后又变"的正确姿势。
- **通信消息格式**（V2 usage hints）：`Message Type: NEW_TASK | MESSAGE | FINAL_ANSWER` +
  `Task name` / `Sender` / `Payload`；root 自称 `/root`，**"所有 agent 同等智能、工具集相同"**。
- **`AgentStatus`** 七态：`PendingInit / Running / Interrupted / Completed / Errored / Shutdown / NotFound`。
- **★ spawn 图落库为有向边表**（`state/migrations/0021_thread_spawn_edges.sql`）：
  `thread_spawn_edges(parent_thread_id, child_thread_id PRIMARY KEY, status{Open|Closed})`
  + 索引 `(parent_thread_id, status)`；`ON CONFLICT(child_thread_id)` 保证**一个子只有一个父边**；
  查后代用**递归 CTE**，注释约定 **BFS + 按深度再按 id 稳定排序**。
  ⇒ **可借鉴**（E4）：**agent 派生关系是"图"而非"树字段"**，落成边表后
  "查某任务的全部后代/直属子"就成为一次 SQL（本机群已有 DuckDB，成本极低）。

### 4.14 【P1】hooks：只有**同步** hook 有控制权（本轮新增，E2）

**出处（E2）**：`codex-rs/hooks/src/`（`lib.rs`、`engine/mod.rs`、`events/stop.rs`、`schema.rs`、`registry.rs`）。

- **触发点 11 个**：`PreToolUse / PermissionRequest / PostToolUse / PreCompact / PostCompact /
  SessionStart / SessionEnd / UserPromptSubmit / SubagentStart / SubagentStop / Stop`；
  其中 **9 个带 matcher**（除 `UserPromptSubmit`、`Stop`）。
- **★ 控制权只给同步 hook**：`can_apply_control_effects()` 只在 **Sync** 为真
  （ExecutorScoped 或 `async:true` 的命令 hook ⇒ Async ⇒ **输出被忽略**）。
  ⇒ **可借鉴**（E4）：异步钩子只作**旁路观测**，不参与决策 —— 避免"决策依赖未完成的副作用"。
- **★ stop hook 的 block 语义："一物两用"**：
  `{"decision":"block","reason":"…"}` 中 **`reason` 既是"阻止理由"也是"续写提示"**
  （直接作为 `continuation_prompt` 回灌）。
- **优先级明确**：`continue:false` **覆盖** block（有专门测试 `continue_false_overrides_block_decision`）。
- **`exit 2` + stderr 非空 = block**（stderr 作续写提示）；`exit 2` 但 stderr 空 = Failed 不 block。
- **schema 用 `deny_unknown_fields`，且语义规则在解析层强制**（如 "block 必须带 reason"，
  注释明说"we enforce that semantic rule during output parsing rather than in the JSON schema"）。
- **reserved 字段 fail-closed**：`PermissionRequestDecisionWire` 的
  `updated_input`/`updated_permissions`/`interrupt` 标 "reserved for future"，
  **当前出现即 fail closed**（而非忽略）。
- **hook 状态键 = `{key_source}:{event_label}:{group}:{handler}`**（持久化可精确定位）。
- **hook 契约里加了 `turn_id` 扩展字段**（注释反复标 "**Codex extension**"），
  让 hook 能按 turn 定位上下文，**并有测试固化该扩展**。

⇒ **可借鉴**（E4）：本机群 `agent-cli` 的 review 环若要加钩子，
应照此：**同步 hook 才有决策权；block 的 reason 直接复用作续写提示；reserved 字段出现即拒**。

# 附录 C — trust-registry 与 swebench-smoke 详细调研

## C.1 `trust-registry/`（内容信任治理与裁决系统）

### C.1.1 定位

**WP-05 产物**，四件套：**内容信任登记表 + 静态风险扫描 + 人工裁决队列 + 一致性验证器**。
为铁律 3「**内容吸收晚于信任治理**」提供执行载体。**不是运行时组件**，是**供应链/许可/安全的前置治理管线**。
关键立场（`SCHEMA.md` 第 3 行、`validate_registry.py` 第 1 行注释）：**"登记 ≠ 可信"**，
故必须有独立验证器（E1 断言重放）来**证伪登记表自身**。

### C.1.2 登记对象：七类 kind + 两级粒度

`kind ∈ {repo-snapshot, plugin-bundle, skill-ecosystem, methodology, profile-assets, skill, source-file}`。
**源级 `src-*`**（如 `src-dsh-base` / `src-codex` / `src-haha` / `src-spec-workflow` / `src-crucix` /
`src-trae-plugins` / `src-claude-skills` / `src-dsh-profiles`）与
**插件级 `plg-*`**（`SCHEMA.md` §6："插件级条目逐件登记，`parent_entry` 指向源级"）。
粒度规则（`enumerate.py:132-140`、`DESIGN §4.1`）：技能生态按"**每个 `SKILL.md` 所在目录**"一条；
Crucix 固定拆 2 条（`plg-crucix-own` 排除 `node_modules` / `plg-crucix-vendor` 即 `node_modules` 子树）。

### C.1.4 信任分级 T0-T3（`SCHEMA.md` §2）

T0-exec（含可执行内容或可执行包）⇒ 静态扫描 + 版本锁 + 许可门；
T1-content（纯提示词/配置）⇒ 许可门 + 提示注入审查；
T2-reference（只读参考）⇒ 许可门；T3-cleanroom（版权第三方，haha 专用）⇒ ADR-002 只读理解零复制。
**判定规则**：目录类按**递归可执行文件枚举**判定（`exec_count > 0 → T0`），
**"降级须扫描证实后改登记（禁人工径改）"、"内容检测决定，人工不可越级下调"**。
依据：`.claude/skills` 实测内嵌 **321 个可执行文件** ⇒ 结论"**内容型生态在信任维度不成立**"。

### C.1.5 verdict 六态状态机 + 七条一致性约束（A5 强制）

```
pending ──scan──> passed ──人工批准+许可pass──> approved-exec
   │                ├──人工批准+许可flag──> approved-personal
   │                └──(T2 参考)──────────> approved-reference
   ├──scan──> flagged(HIGH/MED 命中)──人工裁决+留痕──> approved-personal | rejected
   └──scan──> failed(扫描器异常)────────────────> rejected(或修复后 reset 重扫)
T3-cleanroom 恒为 cleanroom-only
```
约束（`SCHEMA.md` §3 / `validate_registry.py:139-190`）：
① `approved-exec` ⟹ T0 ∧ scan ∈ {passed, not-required} ∧ 许可门 pass；
② `approved-reference` ⟹ tier ∈ {T2,T3} ∧ scan ∈ {passed, not-required}；
③ `cleanroom-only` ⟹ T3；
④ `approved-personal` ⟹ tier ∈ {T0,T1} ∧ scan ∈ {passed, flagged} ∧ 许可 flag 态 ∧
`use_constraint=personal-only-no-redistribute` ∧ (**scan=flagged ⟹ `adjudicated_reason` 非空**)；
⑤ **`pending` ⟹ scan ∈ {pending, passed, flagged, failed}`（全量期"扫描完成待终裁"为合法未终态）**；
⑥ **T0 ∧ scan ∉ {passed, not-required} ⟹ verdict 不得为任何 approved 态**（唯一豁免 = 约束 4 的 flagged 路径）；
⑦ T0 不得 `approved-reference`；plg 条目 `parent_entry` 须指向存在的 `src-*`。
**许可门三态（§5）**：MIT/Apache-2.0/BSD/self = pass；`AGPL-3.0-only` = flag（强 copyleft）；
absent/unknown/proprietary = flag（自用不二次分发）。

### C.1.6 四脚本与流水线顺序（`IMPLEMENTATION §6` 官方运行手册）

| 脚本 | 职责 | 输入 → 输出 |
|---|---|---|
| `enumerate.py` | 枚举器：源级 → 插件级逐件登记 + 结构指纹 | `--src <src-id>` → `registry.jsonl` + `manifests/<entry_id>.txt` |
| `scan.py` | 静态扫描器（三级正则），回写 `scan_status` | 扫 `scan_status=pending` 且 `entry_id` 以 `plg-` 开头 → 追加 `scan_report.jsonl` + 回写 |
| `adjudicate.py` | 裁决队列生成 + AI 初审 + 用户终裁回写 | → `adjudicate_queue.md`；`--apply` / `--approve-all-passed` 回写 |
| `validate_registry.py` | E1 验证器（A1-A6 断言 + 8 条对抗负例自检） | 逐条 PASS/FAIL + 汇总 |

顺序（逐字）：`enumerate --src …`（×3）→ `scan.py` → `adjudicate.py`（生成队列）→
`adjudicate.py --apply …`（终裁）→ `validate_registry.py`。
**以 `registry.jsonl` 单文件为交接介质（磁盘状态机），任何一步可中断续跑。**
实现细节：`enumerate.py` **幂等**（同 `entry_id` 重跑只刷新结构字段，**保留人工终态**，除非 `--reset`，
`:143-165`）；`scan.py` **只扫 `plg-` 前缀**（`:104`）；`scan_report.jsonl` **追加式**（`:129-132`
"保留历史轮次"）。

**扫描模式集（`scan.py:20-38`）**：HIGH 4 项（`download-exec` `curl…|sh`/`wget…|sh`/`iwr…|iex`；
`dynamic-exec` `eval(`/`new Function(`；`ssh-key-read`（负向前瞻排除 `.pub`）；`b64-exec-chain`）；
MED 4 项（`child-process` / `env-exfil` / `cred-file-write` / `b64-blob` ≥1024 连续 base64）；
LOW 3 项（`net-call` / `env-read` / `fs-write`）。
**判定 `classify()`：任何 HIGH/MED → flagged；仅 LOW/零命中 → passed**；
文件读取异常记 `scan-error` 行且 `scan_status=failed`（**扫描器自身异常入队列人工处理**）。

### C.1.7 裁决机制细节

- **谁判**：**AI 初审 = 建议，非终裁**（`adjudicate.py` 抬头 "RULE-4:初审不构成终裁"）。
  `pre_review()` 规则：`LOW` → `expected-by-design`；`parent_entry == "src-crucix"` 且
  pattern ∈ {`net-call`,`env-read`} → `expected-by-design`（OSINT 工具网络调用是功能本体）；
  其余 → `needs-review`。**终裁 = 用户**，必须经 `--apply` 显式回写（I-F5"flagged 条目无自动批准路径"）。
- **判据 `_legal()`（`:94-113`）**：`approved-personal` 须 tier T0/T1、scan passed 或 flagged **且必须给 `--reason`**、
  scan=failed 不可批准；`approved-exec` 须 tier T0、scan passed/not-required、
  `license ∈ LICENSE_PASS = {mit, apache-2.0, bsd-2-clause, bsd-3-clause, self, bsd}`；
  `rejected` **必须给 `--reason`**。回写副作用：`approved-personal` 自动补 `use_constraint`；有 reason 则写 `adjudicated_reason`。
- **`adjudicate_queue.md` 三节（`build_queue()`）**：A. flagged（逐件过目：逐命中 `[severity] pattern @ file:line`
  + 代码上下文 + **AI 初审列** + 该条目的**终裁命令行模板**）；B. passed（汇总表 + 批量批准提示）；
  C. failed（待人工检查后 reset 重扫或 rejected）。

### C.2.1 测什么

### C.2.3 `orchestrate.py` 编排逻辑

1. **串行，不并发**：`pairs = [(iid, side) for iid in sorted(iids) for side in sides]`，`run_units()` 逐个 for 循环；
   `AB_REPORT` §5 亦写明"LM Studio 单实例串行服务（电池串行执行，无并发争用）"。
2. **分批能力**：`--iids`（逗号分隔子集）与 `--sides`（默认 `dsh,claude`）。
3. **四阶段状态机 + 断点续跑（I6，`run_units()`:70-113）**：
   `eval_result.json` 存在 ⇒ **直接读盘跳过整个单元，零 API 调用**（`test_t10_resume` 断言 `calls == []`）；
   `workspace` 不存在 → `prep_workspace.py`；`<side>.out` 不存在 → `run_agent`；
   `<side>.agent.patch` 不存在 → `eval_prep.py`（既有 patch 视为已注入，幂等）；最后 `evaluate()`。
4. **重试策略**：`timeout` → **不重试**（成本控制）；其余 `failed` → **重试恰好 1 次**，重试前
   `prep_workspace.py` **重置 workspace**。**patch 产出优先于退出码**：`patch_bytes > 0` 即判 `ok`，
   即使 `exit_code=1`（注释原文："claude.exe 在沙箱下因 home 目录写入被拦 exit 1, 但 workspace 产出完好"）。
   单次子进程统一 `timeout=600`。
5. **失败分层统计（I5，`summarize()`）**：分母 = `resolved + not_resolved + failed`，

6. **产出**：`results.json`，含 `summary{..., per_side{...}, total_units, wall_s}` 与 `units[]` 全量记录。

## D.1 整体架构

- **内核定位（`docs/architecture.md` 开篇）**：**Cordis 是 dsh 之下的框架；插件向共享 context 贡献
  service、typed event 与可逆 effect。产品中每一部分都是插件** —— 模型适配器、工具注册表、会话日志、
  **甚至 agent loop 本身**。"**There is no privileged core to patch.**"
- **组合模型 = profile + bundle + patch**（`docs/architecture.md`、`apps/cli/README.md`）：
  一个运行中的 dsh 是**启动时按有序层组合出来的插件树**；
  **层序**：profile 的 `dsh.profile.bundles`（按序）→ profile 的 `cordis.patch.yml` →
  home 级 `$DSH_HOME/cordis.patch.yml` → `--patch` overlay。
  **patch 按 id 命中一行并整体替换其 config**，或插入新行。
- **入口链路**：`apps/cli/src/bin.ts` → `parseDshArgs` → 按 mode 动态 import
  （`profile` → `profile-boot.ts#runProfile`；`plugin`；`dump-config`）；`bin.ts` 用 `switch + assertNever`。
- **`dsh plugin` 的运行时对账（`apps/cli/src/plugin.ts` `reconcilePlugins()`）**：
  **按"安装后的实际状态"而非依赖 diff** 重建 `dsh.profile.bundles` 列表 ——
  一个依赖若解析到的包声明了 `dsh.bundle.patch` 就加入层栈，否则移出。
- **Turn / step 循环（`docs/architecture.md`）**：见 §A.3 §2.7；**step = 一次模型请求 + 其调用的工具；
  turn = 0 个或多个 step**；`agent/turn-stopping` 是 **serial 且没有 `next()`**。
- **Session log 是唯一真源**：`deriveMessages()` 从 log 投影模型历史；核心不变式
  **`Model-visible means logged`** 有 runtime invariant 断言；
  **新增一个模型可见输入必须新增一个 session event**（扩展 `SessionEventMap`）。
- **Capability seam 三角色（`docs/architecture.md`、`docs/glossary.md`）**：
  Service Definition（**抽象类或具体注册表，绝不是 TS `interface`**）+ 若干 Service Provider + 若干 Consumer；
  **三者共同构成 seam，单独一个角色不是 seam**。规范例：`packages/shell` 的
  `dsh-shell`（定义）/ `dsh-bash-local`·`dsh-bash-sandbox`（提供者）/ `dsh-tool-bash`（消费者）。
  **flavor 的意义**：filesystem 与 subprocess provider 共享一个执行世界 ⇒ 指向远端 sandbox 就同时移动
  Bash/PTY/LSP。
- **核心包与 ctx key（`docs/architecture.md`）**：`core/session`→`ctx.sessions`；
  `core/system-prompt`→`ctx.systemPrompt`；`core/tools`→`ctx.tools`；`core/agent`→`ctx.agents`；
  `core/agent-loop`→`ctx.agentLoop`；`core/scope`（library, no key）；`llm/llm`→`ctx.llm`。
- **"新行为放哪里"索引表（`docs/architecture.md` 末尾）**：加模型 provider → `ctx.llm`；
  加模型可见能力 → `ctx.tools`；加 shell 执行 → `ctx.shell` 后端；加人类命令 → `ctx.commands`；
  加后台工作 → `ctx.jobs`；限制派生进程 → `ctx.sandbox`；拦截请求/工具/turn → 对应 `agent/*` / `tools/*` 事件；
  加模型可见上下文 → `agent.inject()`；加 durable session 状态 → 扩展 `SessionEventMap`。
- **API Gateway / Typert（`docs/api-gateway.md`）**：`@Remote`/`@RemoteScope` 装饰器标记暴露方法；
  构建期 `dsh-typert-generator` 从 Host `ts.Program` **严格分析** Remote 签名
  （必须 public / 非 static / 实例方法 / 非泛型 / 参数必填且为简单标识符，不能解构/默认值/rest/可选）；

## D.2 插件 / 扩展机制

- **Cordis 五想法（`docs/cordis-primer.md`）**：① 插件是实现 Service 的对象；② **context 是 service 的仓库**
  （按 key 找服务，不 import 具体实现）；③ **用 `inject` 声明服务依赖** ⇒ **加载顺序由服务需求表达，
  而不是手工 boot 排序**；④ 用 Typed Events 通信，按监听器语义选 dispatch mode；
  ⑤ **注册是可逆 effect**。
- **Context 实现（`vendor/cordis/src/context.ts`）**：构造器返回 `new Proxy(this, ReflectService.handler)`
  ⇒ 普通属性读取走**服务解析器**；三个派生原语 `extend(meta)`（原型继承，**父不被修改**）/
  `isolate(name, label?)`（**传同一 label 两次会合并 scope**）/ `intercept(name, config)`。
- **插件三形态 + 元数据（`vendor/cordis/src/registry.ts`）**：`Plugin.Function` / `Plugin.Constructor` /
  `Plugin.Object{apply}`；`Plugin.Base` 字段 `name` / `Config`（standard-schema 校验器）/
  `inject` / `provide` / `intercept`。`Inject` 两种写法（数组 / 对象映射）；
  `@Inject()` 装饰器可作用于**类方法**（延迟调用直到所需服务可用）。
- **Fiber 状态机**：`PENDING → LOADING → ACTIVE → FAILED → UNLOADING → DISPOSED`（不可重启）；
  emit `internal/status`。**epoch 机制**：`_refresh()` 遍历 `inject`，任一缺失 ⇒ `INACTIVE`，
  否则拼 `':' + impl.fiber.uid`；变为有效 ⇒ `_reload()`；有效值变化（依赖被替换）⇒ `_unload()` 后 `_reload()`；
  变为 `INACTIVE` ⇒ `_unload()`。**这就是"依赖注入 + 自动热重挂"的机械实现。**
- **`ctx.effect()`**：立即执行 `execute`，收集 disposer，在"disposer 被调用"或"fiber 卸载"时**逆序**执行；
  `Disposable<T>` 可为同步函数 / 返回 Promise 的函数 / **异步生成器**（每 yield 一个 disposer 登记一个）。
  **对上游的加固定制（`vendor/README.md` 本地修改第 6 条）**：owner-list wrapper 先于 setup body 注册；
  同步 setup 失败会移除 wrapper 并回滚；异步清理直到静止前保持 owner 可见；
  `UNLOADING` 期间创建 effect 被拒绝（`CordisError('INACTIVE_EFFECT')`）。
- **Service 基类（`vendor/cordis/src/service.ts`）**：`super(ctx, name)` 即 `ctx.reflect.provide(...)`
  ⇒ **服务随 owning fiber 卸载自动注销**；`Service.init`（symbol，返回值当 effect）/`Service.check`
  （可用性谓词，供 `Fiber._checkImpl`）/`Service.invoke`/`Service.resolveConfig`
  （祖先 intercept 与 base/head 合并，**就近优先**）。
- **五种派发模式（`docs/cordis-primer.md` + `events.ts` 的 `DispatchMode`）**：
  `emit`（不 await，无返回）/ `waterfall`（不 await，有返回，around-middleware）/
  `parallel`（await，并行）/ `serial`（await，顺序，有返回）/ `bail`（同步，遇真值即停）。
  **派发模式是事件的公开契约**，新事件必须用 `@mode` JSDoc 记录以便 catalog 核对。
  **waterfall 语义**：监听器收到 `(...args, next)`；**调用 `next()` 委派，不调用就短路整条链**。
- **监听器归 fiber 所有 ⇒ fiber 卸载自动移除**（`EventsService.register` 内部即 `ctx.fiber.effect(...)`）。
- **内建事件**：`internal/plugin` / `internal/status` / `internal/config`(waterfall) / `internal/service` /
  `internal/update`(waterfall，跳过 `next()` 可否决配置更新) / `internal/get`·`internal/set`(waterfall) /
  `internal/listener`(bail) / **`internal/dispatch`（派发任何非 `internal/` 事件前 emit 它 ⇒ 事件总线的可观测点）**。
- **Loader（`vendor/loader/README.md` + `src/index.ts`）**：
  entry 字段 `id`/`name`/`config`/`group`/`disabled`/`inject`；
  API `create`/`update`/`remove`/`resolve`（含嵌套 `a:b` id）/`resolveGroup`/`await`/`locate`/`exit`；
  `unwrapExports()` 归一化 ESM/CJS/default 导出形状（含 esbuild `__esModule` interop）。
  **`!!js` 插值只在 entry 根做**（`internal/config` 监听器 + `EntryGroup.key` 判断）——
  **Group/Include 等树载体的 config 保持字面量**，因为其中承载的是别人的 config。
  **self-dispose 侦测**（`:117-157` 的 `internal/plugin` 监听器）区分**七种情形**，
  只在"注册表仍持有该 callback、树没在卸载、不是 Loader 自己在替换/移除、entry 未 disabled"时
  判定插件自行 `dispose()` 并把 `entry.options.disabled = true` **写回配置文件**。
- **Include**：YAML/JSON 配置文件 include + **patch overlay**；把私有 `applyPatches` 抽成导出纯函数
  `applyEntryPatches(data, patches, warn)`，**动机："配置工具（如 `dsh --dump-config`）绝不能重新实现
  补丁算法而与其漂移"**；`insert` 进去的 entry **立即索引**（同列表内后续 patch 可配置/禁用它）。
  每次子树变更走 **per-Include 队列串行化**；HMR 主 watcher 加 `ignoreInitial: true` 以避免
  **重放启动刚消费过的文件触发死锁回滚（exit 13 无诊断）**；
  debounced 写做了**串行化 + 有界 EACCES/EBUSY/EPERM rename 重试 + teardown 时 drain**（Windows 句柄）。
- **Group / Timer**：`group: true` 的 entry 其 config 是子 entry 列表；
  **禁用 group entry 会阻止其子 entry 运行**；嵌套 id 用 `:` 分隔。
  Timer 是 **disposal-aware**：`ctx.timeout`/`ctx.interval`/`ctx.throttle`/`ctx.debounce`，
  **timer handle 注册在当前 fiber 上 ⇒ 插件被 dispose 时自动清除**。
- **HMR（`vendor/hmr/README.md` + `src/index.ts`）**：前置要求 loader + timer + **暴露 Node 内部 module loader
  的 runtime**（否则 `throw new Error('--expose-internals is required for HMR service')`）；
  Config `base`/`root`/`ignored`（默认 `['**/node_modules','**/.*','cache','data']`）/`debounce`（默认 100ms）。
  **启动**先算 externals（递归收集 main module 的模块图，跳过 `node:` 与 `/node_modules/`）再开 watcher；
  `onChange` 分三类：配置重载（是某 entry 的 `Include.filename`）/ 全量重载（URL 在 `externals` ⇒ `loader.exit()`）/
  局部重载。**`partialReload()`**：`analyzeChanges()` 分 accepted/declined（迭代双向传播）；
  按 `entry.parent.tree.ctx.baseUrl` 构建 `nameMap`；**"Plugin entry files are treated as atomic reload units."**；
  **双缓存清理**（ESM `loadCache` + CJS `require.cache`，注释："In Node 24, both CJS and ESM modules
  imported via import() end up in loadCache"；`LoadCache.delete()` 只置 undefined 不真正移除 ⇒
  用 `Map.prototype.get/delete` 直接操作）；**重导入 + rollback**（任一失败 ⇒ 恢复两份缓存 + 重新注册旧插件）；
  成功 emit `hmr/reload`。
  事件：`hmr/change` / `hmr/reload` / `hmr/config-update-failed`（本地新增，`@mode parallel`）。
  **`registerConfig(filename, refresh)`**：在配置模块根之外监视**一个绝对配置文件路径**
  （含父目录不存在的情形：`findWatchRoot` 上溯到最深已存在祖先并 **realpath**，再补回缺失后缀）——
  **realpath 的必要性：避免 Windows 8.3 短名别名与 libuv 长格式事件路径冲突**。
- **动态插件（self-modification）**：`docs/tool-catalog.md` 的 `dsh-tool-cordis` 提供
  `cordis_define`/`cordis_inspect_*`/`cordis_run`/`cordis_stop`/`cordis_undefine`；
  **一个运行中的包可以注册额外的模型可见工具**直到 stop/undefine；
  它是**刻意的 opt-in**（不在任何随发行树中）。

## D.3 门禁体系（`scripts/run-gates.ts`）

- **定位（头部注释）**："**Package scripts own public aggregate names; this runner owns their validated
  dependency graphs, scheduler environment, and process diagnostics.**"
- **15 个 `Mode`**：`ci-primary | ci-linux-primary | ci-static | ci-lint-contracts-ready | ci-coverage |
  ci-snapshot | ci-artifacts | ci-consumers | ci-windows-blocking | ci-windows-complete |
  ci-windows-observational | node-compat | check-all | hygiene | doc-sync`。**未知 mode 抛错（不静默）。**
- **`Gate` 字段**：`id` / `label` / `displayCommand` / `command` / `args` / `needs?` / `after?` / `env?` /
  `allowFailure?` / `streamOutput?`。**`needs` vs `after` 的区别见 §3.1。**
- **`validateGateGraph()` 抛错三类**：空图；**重复 gate id**；`needs`/`after` 引用**未知 id**；

- **失败传播**：构造 `status:'skipped'` 结果（`error: 'dependency failed or skipped: <ids>'`）并级联；
  若没有任何 gate 的 needs 失败却仍卡住 ⇒ `throw new Error('run-gates: validated graph stalled
  without a failed dependency.')`。
- **退出码**：`results.some(r => r.gate.allowFailure !== true && (r.status === 'failed' ||
  r.status === 'skipped')) ? 1 : 0` ⇒ **被跳过的门禁默认也算失败**。
- **输出**：每个门禁打印 `PASS <label> (Ns)`；失败向 stderr 打印 `== <STATUS> <label> ==` + `command:`

### E.7.1 Ink 渲染引擎（`ink.tsx` / `root.ts` / `frame.ts` / `dom.ts` / `focus.ts`）

- **渲染模型 = "提交驱动 + 16ms 节流"，不是固定帧率循环**（E2）：
  `constants.ts` 定义 `FRAME_INTERVAL_MS = 16`（注释："~60fps"）；
  `ink.tsx` 用 `scheduleRender = throttle(() => queueMicrotask(this.onRender), 16, {leading, trailing})`；
  节流入口挂在 reconciler 的 `resetAfterCommit`。
  **★ 用 `queueMicrotask` 而非同步渲染的理由（代码注释原文要点）**：
  `resetAfterCommit` 跑在 React layout 阶段（ref attach / `useLayoutEffect`）**之前**，
  同步渲染会让 `useDeclaredCursor` 这类 layout effect 状态**落后一帧**；
  改用微任务延后到 layout effect 提交之后，**同一事件循环 tick，吞吐不变**。
  **无 `requestAnimationFrame`、无常驻 `setInterval` 渲染循环**；
  唯一定时器是滚动 drain：`setTimeout(..., FRAME_INTERVAL_MS >> 2)`（**4ms**，注释："~250fps、
  setTimeout 实际下限"），并明确说明此处**不能**再调 `scheduleRender()`（throttle 的 leadingEdge
  会立刻重入 ⇒ 双渲染）。
- **`onRender()` 一帧的阶段**（E2，代码逐段带注释且阶段名即上报指标）：
  清 drainTimer → `flushInteractionTime()`（合并交互时间戳为每帧一次 `Date.now()`）→
  `renderer(...)` 产出 `frame` → sticky/follow 滚动时平移选择锚点 →
  alt-screen 专属 overlay（选择反色 / 全量搜索高亮 / 当前位置高亮）→
  **全量 damage 兜底**（`didLayoutShift() || selActive || hlActive || prevFrameContaminated`
  ⇒ `screen.damage` 设为整屏）→ `log.render(prevFrame, frame, altScreen, SYNC_OUTPUT_SUPPORTED)` →
  **交换缓冲**（`backFrame = frontFrame; frontFrame = frame`）→
  **每 5 分钟 `resetPools()` 防 ID 池无界增长**（池是迁移而非重建）→ `optimize(diff)` →
  光标停靠记账 → `writeDiffToTerminal` → 标记 `prevFrameContaminated` → drain 续帧 → `onFrame(...)`。
- **`FlickerReason = 'resize' | 'offscreen' | 'clear'`** + `shouldClearScreen` 三规则（E2）：
  viewport 尺寸变了 ⇒ `resize`；本帧或上帧 `screen.height >= viewport.height` ⇒ `offscreen`；
  否则不清屏。`flickers` 从 `patch.type === 'clearTerminal'` 统计；
  开 `CLAUDE_CODE_DEBUG_REPAINTS` 时会用 `dom.findOwnerChainAtRow(rootNode, patch.debug.triggerY)`
  **打出"是哪个 React 组件导致整屏重绘"**。
- **root 与 reconciler 的关系（E2）**：`root.ts` **不是 DOM 根**，而是入口 API 层
  （`renderSync` / `wrappedRender` / `createRoot`）。
  真正的根 = `Ink.rootNode`（`nodeName === 'ink-root'` 的 DOMElement）
  **被交给** `reconciler.createContainer(this.rootNode, ConcurrentRoot, ...)`。
  实例按 stdout 复用（`instances.ts` 是 `Map<WriteStream, Ink>`）。
  **★ `wrappedRender`/`createRoot` 都先 `await Promise.resolve()`**（注释：**保留原先 `await loadYoga()`
  提供的微任务边界**——否则首帧会在异步启动工作 settle 之前同步触发，
  **后续 `Static` 写入会覆盖 scrollback 而不是追加**）。这是"Yoga 从 WASM 换成 TS 同步实现"后
  **刻意保留的时序约束**。
- **`Frame` 内容（E2）**：`{screen, viewport, cursor{x,y,visible}, scrollHint?, scrollDrainPending?}`。
  - `screen`（`screen.ts`）：`cells: Int32Array` + `cells64: BigInt64Array`
    （**每 cell 2 个 Int32：`[charId, packed(styleId|hyperlinkId|width)]`**）+ 共享三池
    （char/style/hyperlink）+ `damage`（只记"写过而非 blit 过"的包围盒）+
    `noSelect`（逐 cell "不可选中"位图，给行号/gutter）+ `softWrap`（逐行软换行标记，
    注释详述 `shiftRows` 时语义如何保持）。
  - `scrollHint = {top, bottom, delta}`：唯一用途是 **DECSTBM 滚动优化，仅 alt-screen**。
  - 输出契约 `Patch` 联合：`stdout`/`clear(count)`/`clearTerminal(reason,debug)`/`cursor*`/
    `hyperlink(uri)`/`styleStr`（由 `StylePool.transition()` 缓存 `(fromId,toId)`，warmup 后零分配）。
  - `FrameEvent.phases` 是**显式性能契约**，含 `yogaVisited/yogaMeasured/yogaCacheHits/yogaLive`
    （注释："total yoga Node instances alive… **Growth = leak**"）。
- **`dom.ts` 的双树结构（E2）**：UI 树（7 种 `ink-*` 元素 + `#text`）+ Yoga 树，增删时手工对齐，
  且**存在"无 Yoga 节点的 DOM 子节点"这一不对称**（`ink-virtual-text`/`ink-link`/`ink-progress`
  不创建 Yoga 节点 ⇒ **DOM index ≠ yoga index**，`insertBeforeNode` 有详细注释解释必须在改

  - **★ 所有写入都必须 value-compare**：`setAttribute` 跳过未变值；`setStyle`/`setTextStyles`
    用浅比较，**注释直说理由："React creates new style objects on every render even when unchanged"**。
  - **★ 事件处理器不放在 `attributes` 里**（放 `_eventHandlers`），
    理由：处理器身份变化若进 attributes 会 markDirty，**破坏 blit 优化**。
  - **移除子树时按需"全局禁用 blit"**：若被删节点或祖先 `position: 'absolute'`
    ⇒ 升级为禁用 blit（注释：绝对定位的像素可能与非兄弟重叠）。
  - **★ `scheduleRenderFrom(node)`：给 DOM 级变更（如 `scrollTop`）留一条不经过 React 的重绘通道**，
    注释要求与 `markDirty()` 配对。
  - `ink-raw-ansi` 节点**不做 stringWidth、不换行、不展开 tab**（生产者已按目标宽度排好）。
- **`focus.ts`（E2）**：**纯状态 FocusManager，不持有树引用**
  （注释："Has no reference to the tree; callers pass the root when tree walks are needed"）；

  **★ Tab 顺序每次按键用 DFS 现算** `collectTabbable`（`tabIndex >= 0`）后取模环形
  （注释：代价 O(节点数)/按键，收益**永不与树不同步**）；
  **★ 节点被卸载时"焦点栈回退"而非"找下一个候选"**：过滤掉不在树中的栈项 ⇒ blur ⇒
  **从栈顶往下找到第一个仍在树中的元素恢复焦点**。

### E.7.3 `Ansi.tsx` / `bidi.ts` / `warn.ts`（E2）

- **`Ansi.tsx` = "逃生舱"**：把外部工具（注释点名 cli-highlight）产出的**已带 ANSI 转义**的字符串
  解析成 Ink 的 `Text`/`Link` 组件树；**颜色被规约为 Ink 的颜色 DSL**
  （`named → 'ansi:xxx'` / `indexed → 'ansi256(N)'` / `rgb → 'rgb(r,g,b)'` / `default → undefined`）
  而非透传 SGR 字节 ⇒ 外部高亮结果能进入 Ink 的 `StylePool` 复用与 diff 体系；
  **dim 优先于 bold**（注释："terminals treat them as mutually exclusive"）；
  相邻同 props 的 span 合并；**只有 1 个 span 且无样式 ⇒ 直接 `<Text>` 不发组件**（热路径优化）；
  文件是 **React Compiler 产物**（`import { c as _c } from "react/compiler-runtime"` + memo 槽位）。
  **与 `RawAnsi`/`ink-raw-ansi` 是两条不同路线**：前者"解析成组件"（参与布局/换行），
  后者"整块预渲染像素"。
- **`bidi.ts`**：仅在平台不支持时启用（`win32` / `WT_SESSION`（覆盖 WSL）/ `TERM_PROGRAM === 'vscode'`），
  结果缓存；复用 `bidi-js` 取 `getEmbeddingLevels`；
  **★ 把 level 映射回 `ClusteredChar` 索引**（`offset += characters[i].value.length`
  —— 因为 value 可能是多 code unit 的代理对/组合序列）；
  经典 UBA **L2 实现**（从 maxLevel 逐层反转连续 run）；
  **纯 LTR 快路径**（一个正则覆盖希伯来/阿拉伯/Thaana/Syriac 区间）；
  **调用点在 `output.ts` 的 `writeLineToScreen`，且带每行 `charCache`** ⇒ 同一行重排帧间只算一次；
  **顺序 = tokenize → grapheme 聚类 → 算宽度 → bidi 重排 → 按列落 cell**
  ⇒ 之后一切（宽度、截断、选区）都按**视觉序**工作。
- **`warn.ts` 只是一个 helper**（`ifNotInteger` 写 `logForDebugging(level:'warn')`），

  （注释：容器/远端上 `process.platform` 报的是容器 OS）。
- **`cwd.ts`**：`AsyncLocalStorage<string>` + `runWithCwdOverride` + `pwd()`；

- **`git.ts`**：`findGitRoot` 向上找 `.git`（**目录或文件都算**，覆盖 worktree/submodule），
  **`memoizeWithLRU(..., 50)`**（注释：`gitDiff` 会按 `dirname(file)` 调用，**不封顶会无限增长**）；
  用 `Symbol('git-root-not-found')` 区分"没找到"与"缓存 miss"；
  `findCanonicalGitRoot` 沿 `.git` 文件 → `gitdir:` → `commondir` 链解析到主仓库；
  `gitExe = memoize(() => whichSync('git') || 'git')`（注释："避免每次 spawn 都查路径"）。
- **`ide.ts`**：锁文件 `LockfileJsonContent{workspaceFolders, pid, ideName, transport: 'ws'|'sse',
  runningInWindows, authToken}`；`getSortedIdeLockfiles()` **按 mtime 倒序**（"最新活跃的 IDE 优先"）；
  探测手段含 `process.kill(pid, 0)` 判活 + **祖先 PID 链匹配**
  （注释提醒 **PID 会回收，故只在单次探测内缓存**）；WSL 特殊处理；
  **`ideOnboardingDialog` 用 `require()` 懒加载**（注释："pull React/ink，only needed in
  interactive onboarding path"）⇒ **避免非交互路径背上 UI 依赖**。
- **`log.ts`**：`logError` **多目的地** —— ① `feature('HARD_FAIL')` 且 `--hard-fail` ⇒
  `console.error` + `process.exit(1)`；② Bedrock/Vertex/Foundry 或 `DISABLE_ERROR_REPORTING` ⇒ 直接 return；
  ③ 写内存环形缓冲（上限 100）；④ **sink 未 attach 时入队 `errorQueue`，attach 后立即排空**；
  ⑤ 否则走 `errorLogSink`。整体 try/catch 静默。
- **`pdf.ts`**：**校验 `%PDF-` 魔数**，否则判 `corrupted`
  —— 注释解释：**一旦非法 PDF block 进入消息历史，后续每次请求都 400，会话不可恢复**；
  `PDFError.reason` 枚举统一返回 `PDFResult<T>` 而非 throw。
- **`xdg.ts`**：`XDG_STATE_HOME ?? ~/.local/state` / `XDG_CACHE_HOME ?? ~/.cache` /
  `XDG_DATA_HOME ?? ~/.local/share` / `getUserBinDir = ~/.local/bin`（注释："not technically XDG
  but follows the convention"）；**可注入 `env`/`homedir` 便于测试**。
- **`xml.ts` 揭示了这套 harness 的模型侧协议是"XML 标签化"的**：
  只有 `escapeXml`（`& < >`）与 `escapeXmlAttr`（再转义 `" '`）两个函数，
  用途注释：**当不可信字符串（进程 stdout、用户输入、外部数据）要插进 `<tag>${here}</tag>` 时使用**。
  实际用法：`<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>`、`<LOCAL_COMMAND_STDOUT_TAG>`、
  `<SUMMARY_TAG>`、channel 标签、SVG `tspan`
  ⇒ **"转义"是防提示注入的一环**。

### E.7.5 CLI 层与入口（E2）

- **`cli/exit.ts`**（文件头注释：把散在 ~60 处 `claude mcp *` / `claude plugin *` handler 里的
  "打印 + 抑制 lint + exit"四行模板**收敛成一个出口**）：
  `cliError(msg?): never`（`console.error` + `process.exit(1)`）/
  `cliOk(msg?): never`（`process.stdout.write` + `process.exit(0)`）。
  **退出码语义：0 成功 / 1 失败**；返回 `never` 让调用点写 `return cliError(...)` 即可让 TS 收窄控制流。
  两个刻意的实现细节（注释）：① 用 `return undefined as never` 而非"exit 后 throw"
  —— **因为测试会 spy `process.exit` 并让它返回**；② `cliOk` 走 `process.stdout.write`
  —— **因为测试分别 spy 这两个，而 Bun 的 `console.log` 不经过被 spy 的 `process.stdout.write`**。
- **`cli/print.ts`（`--print` 无头模式，约 5500 行）**：
  `runHeadless(...)` → `runHeadlessStreaming(...): AsyncIterable<StdoutMessage>`（真正的执行循环）。
  要点：
  ① **没有 React 树** ⇒ `useSettingsChange` 等 hook 不运行，改为直接订阅

  ⑤ **退出码 = `result.is_error ? 1 : 0`**；
  ⑥ `setInterval(Bun.gc, 1000).unref()`；`registerProcessOutputErrorHandlers()` 处理 broken pipe。
  配套 `cli/structuredIO.ts`（NDJSON 输出通道）与
  **`cli/ndjsonSafeStringify.ts`：转义 `U+2028`/`U+2029`**

  **`process.env.CLAUDE_CODE_LOCAL_SKIP_REMOTE_PREFETCH ??= '1'`（用 `??=` 保证不覆盖既有值）**、
  `Object.assign(globalThis, { MACRO: {...} })` 补齐编译期宏。
  **⚠ 当前 `preload.ts` 不设置任何 `LOCAL_RECOVERY`**；`README.md:200` 的修复表明确记录
  "setup 被跳过 | `preload.ts` 自动设置 `LOCAL_RECOVERY=1` 跳过全部初始化 | 移除默认设置"。
  grep 全仓库，`CLAUDE_CODE_LOCAL_RECOVERY` 只剩**两处显式读取**
