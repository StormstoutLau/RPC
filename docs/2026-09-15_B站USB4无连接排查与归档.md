# B站 USB4 无连接排查与归因归档 (2026-09-15)

> **日期**: 2026-09-15
> **问题**: B 站 USB4 端口插拔 A/C 线均无连接显示，A 站曾显示"3台设备连接"但 B 站无任何反应
> **结论**: 根因为 **BIOS 修改 USB4 Security 为 mode 0 (None) 后必须彻底断电冷启动才能真正生效**；热重启不清 USB4 控制器遗留状态
> **状态**: 已解决，三站环网恢复

---

## 1. 问题现象

- B 站 USB4 端口插 A 线、插 C 线均"无内核级反应"：
  - `/sys/bus/thunderbolt/devices/` 下无对端 `0-2`（只有域头 `0-0`/`1-0`）
  - 无 `thunderbolt_net` 网卡，驱动 `thunderbolt` ref=0
  - `dmesg` 无任何 `new host found` / `new retimer found`
- A/C 站均显示"2台设备连接"，正常

## 2. 排查过程（按时间线）

### 2.1 排除"BIOS 控制器被禁"
- 读取 B 站 BIOS，`USB/Thunderbolt Configurations` 页：
  - `PD USB4 Control Enable/Disable = Enabled` ✓ 未禁用
  - `PD Thunderbolt3 Alt Mode = Enabled`
  - 该页无 Security Level 项
- 初步结论：控制器未被 UEFI/DBX 更新禁用

### 2.2 发现 Security 模式卡点
- B 站 `USB Type-C Security = auto`（可选 mode 0/1/2）
- 判读：`auto` 可能解析为 User → 对端未授权 → 拒绝连接
- 操作：B 站改为 **mode 0 (None)**，重启

### 2.3 热重启后仍无效
- 改为 mode 0 后（11:12 重启进系统），B 站仍无 `0-2`、无 authorized 节点、无 thunderbolt_net
- `dmesg` 只有 `ACPI: USB4 _OSC: OS supports/controls USB3+DP+PCIe+XDomain+` 和 `bus type thunderbolt registered`，**没有任何对端事件**
- 判定：改模式后热重启**不足以**让 USB4 控制器重置

### 2.4 冷启动解决
- 关机→**拔电源→等 30s 以上**→重新上电
- 开机后（11:45 boot）B 站两臂全部枚举成功：
  ```
  thunderbolt 0-0:2.1: new retimer found            (domain0 → A)
  thunderbolt 1-0:2.1 / 1-0:2.2: new retimer found   (domain1 → C)
  thunderbolt 0-2: new host found = scott-lau-NEX (A)  → B-A 通
  thunderbolt 1-2: new host found = seaviv (C)        → B-C 通
  ```

## 3. 归因（Root Cause）

**B 站 USB4 无连接的真正根因**：

1. **直接原因**：BIOS 修改 USB4 Security（或相关控制器配置）后，**热重启不会释放 USB4 控制器/HW 路由器的残留状态**，必须 **彻底断电冷启动** 才生效。这是 AMI/Strix Halo 平台 USB4 配置变更的已知特性。
2. **深层**：`auto` Security 对 XDomain 对端授权语义不确定；固定为 mode 0 (None) 消除授权歧义。
3. 历史 A/C 站"idle 振荡"（见 [USB4-40G链路能力评估.md](../spec/rpc-optimization/USB4-40G链路能力评估.md) §4.2）同属此类 Strix Halo USB4 电源/重置敏感问题。

## 4. 验证结果（链路级，非 UI 假象）

| 对端 | A 看到 | C 看到 | B 看到 |
|---|---|---|---|
| B (GTR-Pro) | ✅ `1-2` | ✅ `1-2` | — |
| A (NEX) | — | ✅ `0-2` | ✅ `0-2` |
| C (seaviv) | ✅ `0-2` | — | ✅ `1-2` |

- 每个 USB4 域 `thunderbolt0/thunderbolt1` 均 UP
- 三站成环互通（A-B-C 三角环）

## 5. 经验教训

### 5.1 USB4/Thunderbolt 运维（Hard Rule，记入全局）

1. **改 USB4 Security/Controller 后必须冷启动（拔电源 ≥30s 再上电）**，热重启无效。这是本类主板换 USB4 配置的第一步，不是最后一步。
2. **判断"USB4 通了"必须看内核链路级证据**，不是看系统托盘"N台设备连接"：
   - `ls /sys/bus/thunderbolt/devices/`（有无 `0-2` 对端）
   - `dmesg | grep -E 'new host|new retimer'`（有无热插拔事件）
   - `ip -br link | grep thunderbolt`（有无 UP 的 thunderboltX）
   - 三者齐备才算通。
3. **三站识别对端用 `device_name` / `unique_id`**，不要靠 IP 猜测：`/sys/bus/thunderbolt/devices/0-2/device_name` 直接给 host 名。
4. 断电排障优先于软件重试：连续"成功修改却不生效"时，先怀疑电源/重启层级，再改参数。

### 5.2 排查方法论（与项目既有教训一致）

- 复用了既有规则："连续失败后必须停止换参数 → 查成功记录 → 用差异对比定位真正变量"，这里的"差异"是 **hot reboot vs cold boot**。

环网三站物理链路全通后，整理出**确定性的三层 IP 规划**。各段独占一个 /24，消除路由歧义；MTU 统一 9000。

### 6.1 物理拓扑（`/sys/bus/thunderbolt/devices/*-2/device_name` 确认，非猜测）

| A ⇄ B | A.tb1 ↔ B.tb0 | A domain1=GTR-Pro(B)，B domain0=scott-lau-NEX(A) |
| B ⇄ C | B.tb1 ↔ C.tb1 | B domain1=seaviv(C)，C domain1=GTR-Pro(B) |

### 6.2 三层 IP 规划（最终定档）

| 段 | 网段 | IP 对 |
|---|---|---|
| A–B | **10.10.10**/24 | A.tb0=10.10.10.1 ↔ B.tb0=10.10.10.2 |
| A–C | **10.10.12**/24 | A.tb1=10.10.12.1 ↔ C.tb0=10.10.12.3 |
| B–C | 10.10.11/24 | B.tb1=10.10.11.1 ↔ C.tb1=10.10.11.3 |

> 📌 **段位沿用历史约定**（A–B=10.10.10、A–C=10.10.12、B–C=10.10.11）。原因是既有配置全部以 `10.10.10.x = A–B 段` 为前提：RPC（A `ggml-rpc-server -H 10.10.10.1` + B `--rpc 10.10.10.1:50052`）、B 站 `nodes.env`/`wait_rpc.sh`、netconsole（10.10.10.1↔.2）、Beszel agent（hub `10.10.10.2:8090`）。曾短暂试过 A–B=10.10.12/A–C=10.10.10 的反向分配，实测导致 B→10.10.10.1 走默认网关 100% 丢包（**RPC 断裂**），已回退。

> ⚠️ **接口编号 ≠ 物理对端顺序（2026-09-15 A 站重启后暴露）**：`A.tb0` 实连 **B**、`A.tb1` 实连 **C**（用 `readlink /sys/class/net/thunderboltX/device` 看所属 domain + `device_name` 反查确定）。曾按"tb0 对第一台"臆测，把 A–C 段地址配到 A.tb0、A–B 段配到 A.tb1，导致**同一物理段两端 IP 落在不同网段** → A 重启后 A–C/A–B 全断。**铁律：同一物理段两端必须同网段；配地址前先反查对端**。
> ⚠️ **B 站命名陷阱**：B 的 NM 连接名 `netplan-thunderbolt0` 实际绑定的是 **thunderbolt1**（con 名 ≠ 接口名）。改配置必须以**接口名**为准，不能以 con 名判断。

### 6.5 固化要点

- **先确认接口→物理对端映射，再配 IP（教训：A 站接口错位）**。A 站 thunderbolt0 实连 B、thunderbolt1 实连 C，误配反了导致重启后 A 侧全断。判定方法：`readlink -f /sys/class/net/thunderboltX/device` 看它落在哪个 domain，再 `cat /sys/bus/thunderbolt/devices/<N-2>/device_name` 反查对端 host。**不要想当然"thunderbolt0 对第一台对端"**。
- **`netplan apply` 会增删 `90-NM-*.yaml`，且 NM 活动连接缓存旧地址**。改 netplan 后需 flush 接口、必要时删 NM 连接再 apply 重建，否则旧 IP 残留（曾出现 `netplan-thunderbolt0` NM 连接缓存 `10.10.10.1,10.10.12.1` 双地址污染）。
- **改 netplan 用精确 sed**：yaml 行是 `- "10.10.11.1/24"`（`- ` 后有空格）。首次 sed 用 `-\"...\"` 未匹配空格导致**静默失败**——必须 `- "..."`（含空格）才改到。
- **B 站 `netplan apply`/`generate` 报 `systemd-networkd is not running` 是误报**：renderer=NetworkManager 时由 NM 重载，非 networkd。
- **netplan yaml 权限须 600**（`too open` 警告），改写后 `chmod 600`。

### 6.6 主备冗余路由（A 站，DEPLOYMENT D-5）

环网三段各有直连，但**跨段访问**需显式路由。设计见 [station-c/DEPLOYMENT.md](../spec/station-c/DEPLOYMENT.md) D-5：

| 目标 | 主路由 | 备路由 |
|---|---|---|
| A → 10.10.11/24（B-C 段） | via C `10.10.12.3` m102 | via B `10.10.10.2` m200 |
| C → 10.10.10/24（A-B 段） | via A `10.10.12.1` m102 | via B `10.10.11.1` m200 |

- 前提：三站 `ip_forward=1`（B 站实测 =1），实现跨段转发。
- **2026-09-15 踩坑**：修复 A 站接口错位时，把上述 A 站主备路由**误判为"残留坏路由"删除** → 形成**不对称路由**：C→A 去程经 B 可达，但 **A 无 10.10.11/24 回程路由** → 回包走 `default via 192.168.1.1` → 丢包（表现为 `C→10.10.10.1` 100% 丢包）。已按 D-5 在 netplan `routes:` 段恢复。
- 恢复后实测：`A→10.10.11.3` 0% 丢包（主路由经 C）、`C→10.10.10.1` 0% 丢包。
- **C 站主路由同步补齐（2026-09-15）**：C 原先只有备份路由，已在 tb0（A-C 段）加 `10.10.10.0/24 via 10.10.12.1 m102`，与 A 站结构对称。
- **实测性能差（iperf3，2026-09-15）**：`C→10.10.10.1` 走主路由（直连）**9.46 Gb/s** vs 走备路由（经 B）**35.3 Mb/s** —— **268×**，与 D-5 记载「9.2Gbps vs 31Mbps」吻合。**结论：缺主路由 = 跨段流量被降级到 ~35Mbps，主备两条缺一不可**。
- ⚠️ **教训**：删除"看起来多余"的路由/配置前，**必须先查设计文档**（此处 D-5 明确写了主备两条），否则会打断精心设计的冗余。

> ⚠️ **对 thunderbolt 接口执行 `ip addr flush` + `nmcli con down/up` 会触发 retimer 振荡**：A 站 13:19\~13:24 观察到 `0-0:2.1/2.2 retimer disconnected ↔ new retimer found` 循环、`thunderbolt1` netdev 一度消失，约 5 分钟后自愈并重新枚举对端（`0-2: new host found = seaviv`）。操作后应**等待并复验**，勿误判为链路损坏。根因见 [USB4-40G链路能力评估.md](../spec/rpc-optimization/USB4-40G链路能力评估.md) §4.2。
