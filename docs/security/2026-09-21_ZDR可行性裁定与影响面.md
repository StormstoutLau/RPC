# ZDR 可行性裁定与影响面清单（P5，2026-09-21）

> **状态：裁定完成 —— ⛔ 不做 P5（不给 `public`/`sanitized` 开 ZDR）。**
> 但**理由不是"懒得开"，而是"在现有三档语义下不存在需要 ZDR 的流量"**；并且本次裁定**顺带发现一个真正的风险点**（§6），它比 ZDR 本身要紧。
>
> **裁定要点**
> 1. **ZDR 是"按 model group 分作用域"的**（Anthropic / OpenAI / Google / SpaceXAI / **All other models**），不是全开关 ⇒ 我此前"账户级 ZDR 会把免费档一锅端"的说法**只对最后一个作用域成立**，已更正。
> 2. **我们现用的 OpenRouter 型号全部落在 "All other models"**（都是 `:free`，非 Anthropic/OpenAI/Google/SpaceXAI 系）⇒ **给该作用域开 ZDR = 那 5 类消费者全灭**（§5 影响面）。
> 3. **`local-only` 已经强于 ZDR**：它**根本不出网**（P3 站上本地引擎），而 ZDR 明确**不改变"数据到达 provider 并被模型处理"** ⇒ 对 `local-only` 而言 ZDR 是**降级**而非升级。
> 4. **`sanitized` 抹完 = `public`**（档位定义）⇒ 与 `public` 同级 ⇒ **没有一类流量落在"允许出网、但不允许 provider 留存"这个格子里**（除非新增档位）。
> 5. ⇒ 结论：**P5 不做**；将来若出现"不得留存"的要求，正确动作是**换付费型号**（§6 已给出实测可用的型号），**不是开 ZDR**（免费档开不了）。

## 1. ZDR 的机制（官方，2026-09-21 核）

来源：[OpenRouter ZDR 文档](https://openrouter.ai/docs/guides/features/zdr) + [Guardrails](https://openrouter.ai/docs/guides/features/guardrails) + [ZDR 博客](https://openrouter.ai/blog/insights/zero-data-retention/)。

| 维度 | 事实 |
|---|---|
| **四种施加层级** | ① **账户级**（`/settings/privacy`）② **guardrail 级**（按 API key / 成员分派）③ **per-request**（`provider.zdr: true`）④ 组织级 |
| **五个作用域** | **Anthropic / OpenAI / Google / SpaceXAI / All other models** —— 每个**独立开关**。例：给 Anthropic 开 ⇒ 只移除 Anthropic 一方端点（Bedrock/Vertex 仍在），**不影响** other models |
| **ZDR 保证什么** | provider **不留存** prompt/completion |
| **ZDR 不保证什么** | ❌ **不改变"数据到达 provider 并被模型处理"**；❌ **不管处理地**（那是 in-region routing，需 Business/Enterprise）；❌ 不管 OpenRouter 自己的日志（那是 `input/output logging`，默认关，见 P1）；❌ 不管 plugins / tools |
| **保守判定** | 若 OpenRouter **无法确认**某端点的策略 ⇒ **假定它既留存又训练**（⇒ "不可用 ZDR"往往意味着"策略未知"，不一定等于"该 provider 会留存"） |
| **与 training 的关系** | **不留存 ⇒ 无法训练**（间接）；但**"不训练" ≠ ZDR**（provider 可能为滥用扫描/法律原因**短暂留存**，却不训练） |

⇒ **强度谱（本项目语境）**：`ZDR`（不留存）**>** `data_collection:deny`（不训练，但可能留存）**>** 无约束（免费档：**既训练又能留存**）。

## 4. 裁定：**不做 P5**

**判据不是"ZDR 好不好"，而是"有没有流量需要它"**。逐档过一遍：

| 档位 | 后端现状 | 需要 ZDR 吗 |
|---|---|---|
| `local-only` | **站上本地引擎，物理不出网**（P3 已实施；实测 `P3-LOCAL-OK`） | **不需要，且 ZDR 是降级** —— ZDR 只管"provider 不留存"，**不改变"数据到达 provider"**；而 `local-only` 要的是**不到达**。⇒ 给 `local-only` 开 ZDR 等于"允许它出网但要求不留存"，**直接违反不变式②** |
| `sanitized` | 允许出网 | **不需要** —— 档位定义是"含**可机判**敏感项 ⇒ 先机械 scrub 才可进远端"⇒ **抹完的残留等级 = `public`** |
| `public` | 允许出网 | **不需要**（定义上无约束） |

⇒ **"允许出网、但不允许 provider 留存"这个格子是空的** —— 没有任何一档落在里面。**ZDR 在当前档位体系里无处可用。**

**为什么这不等于"推迟"**：若将来真要 ZDR，**当前后端做不到**（免费档 404），必须**换付费型号**（§3 已实测可用两个）。⇒ 所以"开 ZDR"从来不是可执行动作，**它是"换后端"的同义语** —— 与本项目 2026-09-21 早已裁定的"关那个训练开关 ≡ 放弃免费档"是**同一件事的两副面孔**。

## 6. ⚠ 本次裁定**顺带发现的真正风险点**（比 ZDR 要紧）

第 4 节的裁定**有一条前提**：「`sanitized` 抹完 = `public`」。这条是**从档位定义的推论**，**从未被验证**。

⇒ 如果 scrubber **漏了**东西（bug / 未覆盖的敏感形态），那么 `sanitized` 流量**实际不是 public**，而它**走的是云端免费档**（可能被训练）⇒ **那才是真正需要更强后端的情形**（或更准确说：需要**修 scrubber**）。

⇒ **正确的防线不是开 ZDR，而是让 scrubber 不漏**。而这件事**是可测的**（scrubber 有确定性输入输出 ⇒ 可做真值表夹具）。

**登记为新的可做项**：`sanitized` 档 scrubber 的**覆盖率判据**（哪些敏感形态被认、哪些没被认、有没有"认了但没抹干净"）。**这是 P5 的真正替代品。**

### 6.1 已执行（2026-09-21）：判据建成 + 跑出一个**真 bug**

**夹具**：`ops/station-bin/_scrubber_coverage_test.ps1`（AST 提取 `Invoke-Scrubber`，不执行主入口）。**结果 `pass=14 fail=0`**。

它按**三态**设计，且第三态正是为"认了但残留"设的 —— 结果**第三态直接命中一个真 bug**：

| 态 | 内容 | 结果 |
|---|---|---|
| ① 该认的 | 6 例（key / email / win 路径）⇒ 必须替换**且原文片段不残留** | 6/6 PASS |
| ② 不该认的 | 4 例 ⇒ 不得替换（误伤 = 静默破坏任务输入） | 4/4 PASS |
| ③ **认了但残留** | `C:\Program Files\Git\bin\bash.exe` | **FAIL ⇒ 真 bug** |

**Bug 根因**：`win-path` 规则是 `(?i)\b[A-Z]:\\\S+` —— **`\S` 遇空格即断** ⇒ 只吃掉 `C:\Program`，**留下** `Files\Git\bin\bash.exe`。
**为什么这条最危险**：输出里**出现了 `[REDACTED-PATH]`**，看起来"已经处理过"；而路径尾还在。且 `C:\Program Files\...` 在本机（Git Bash / 大量工具链）**是高频形态**，不是理论边角。

**修法**（含一次**必须二选一**的取舍）：
- ❌ "段内一律允许空格"（`(?:\\[^\\]+)+`）⇒ 贪心会把**路径后面的普通词一起吃**：`C:\RPC\out.txt done` 整段变 `[REDACTED-PATH]`。本机 prompt 里句中路径极常见 ⇒ 这是**误伤任务输入**（同族于静默降级）。
- ✅ 采用：**只有当段后还有 `\`（即能证明它仍是路径）时才允许段内含空格**；末段遇空格即停。
  `(?i)\b[A-Z]:\\(?:[^\\/:*?"<>|\r\n\t]+\\+)*[^\\/:*?"<>|\r\n\t\s]*`
- ⇒ 「末段含空格」与「路径后跟普通词」**字面上不可机械区分**，只能二选一；选了**优先不误伤输入**，代价是前者**残留**（下方 §6.2 已知缺口）。夹具为此**新增 §2b 过度消费守门**（3 例）—— 这条守门当轮就抓到了我第一版改法的过度消费。

### 6.2 判据的两类**诚实输出**（都不是 FAIL，但必须可见）

| 类 | 定义 | 数量 | 内容 |
|---|---|---|---|
| **[4] 未覆盖形态** | 这类东西**根本没规则管** | **14 / 14 探测形态一个都没覆盖** | GitHub PAT · AWS AKIA · Slack `xoxb-` · JWT · Bearer · OpenSSH 私钥块 · **Linux 绝对路径** · **UNC 路径** · **内网 IP** · 主机名 `.local` · **用户名** · 手机号 · 身份证 · 银行卡 |
| **[4b] 已知残留缺口** | 规则**碰了**但没吃干净（§6.1 取舍的直接代价） | **2 / 2** | `C:\Users\John Doe` ⇒ 残留 `Doe`；`"C:\Program Files\my file.txt"` ⇒ 残留 `file.txt` |

> ⚠ **[4] 这一列把 §4 的裁定基础说清楚了**：现有 scrubber 只有 **3 条规则**（`sk-` / email / win-path），它的设计注释自明 `no whitelist in MVP`。**"抹完"离"干净"很远** —— 尤其 **内网 IP / 用户名 / `.local` 主机名 / Linux 绝对路径**都**原样出网**。
> **是否加规则 = 决策**（加规则有误伤风险，见 §6.1 那次取舍）。已登记到 `OPEN-ISSUES`。

**⇒ 对 §4 与 §7-1 的影响**：§4 的结论**仍成立但有条件** —— `sanitized` 流量里的**敏感形态若属 [4]/[4b] 两类，就会原样进云端免费档**。所以 **`sanitized` 的实际档位介于 `sanitized` 与 `public` 之间**，这正是"要更强后端"的真实触发条件；而在**换后端之前**，正确的动作是**修 scrubber**（可测、低成本）。
