>
> ① **`claude.key` 已退役**：claude 的 `apiKeyHelper` 改为直接输出引擎 key（`cat $HOME/.config/rpc/unsloth.key`），不再另存一份拷贝 —— 该拷贝**没有任何写入方**，必然陈旧（B/C 两站门禁黄灯即由此而来：C 是 09-14 脱敏遗留的占位串，B 是"加载后 `unsloth.key` 变新、`claude.key` 仍旧"）。三站与主控正本均已删除 `claude.key`。
> ② **`unsloth.key` 不适用上表流程**：它是 unsloth studio **每次加载重铸**的站内产物，唯一写入方是 `infer-load`，不存在"控制台吊销 + 下发轮换"的语义。正本保留它只为兜底 ⇒ **站上每次加载后正本即陈旧，`secrets push` 会用旧 key 覆盖站上真 key，打断该站 opencode/claude**。**故顺序必须是先回写正本、再下发**（回写已是一等入口动作，不再手工 scp）：
> ```bash
> python ops/cluster.py secrets pull <站>   # 先回写正本 (取代手工 scp)
> python ops/cluster.py secrets push        # 再下发 (此时幂等)
> ```
> **2026-09-16 强化（危险动作已设机制闸门）**：`push` 对"站内产物"型凭据（`STATION_MINTED`，当前 = `unsloth.key`）**默认拒绝覆盖** —— 站上已有且与正本不同则**跳过并给出两条出路**（`secrets pull <站>` / `secrets push --force`）；`secrets status` 增"站内产物"行（只打归一化指纹）显示站上 vs 正本是否一致。
> 详见 DEVELOPMENT-LOG 2026-09-16 ⑨、ADR-0003《凭据单一真值修正》。
>
> ③ **`~/.unsloth/run-*.log` 是引擎 key 的第三个明文落点（2026-09-16 已纳管）**：studio **每次加载把 key 写进该日志 4 处**，而 `infer-load` 正是**从该日志 grep 取 key** ⇒ 含 key 消除不掉。此前该面**完全不在审计视野内**（`secrets scan` 只探 `~/.config/rpc` + 两份配置及备份），实测三站曾累积 **21 份日志 / 68 处明文 / 16 个历史 key 值**，权限为 **775 目录 / 664 日志**（组与其他用户可读）。**已处置**：`infer-load` 每次加载强制 `chmod 700 ~/.unsloth` + `chmod 600 run-*.log`；存量 21 份就地脱敏（`sk-<prefix>-****`）；`stations` 门禁新增 `unslothlog` 探针（判**权限**而非"含不含 key"，含负向自证）。
> ⇒ **运维要求**：新增/复现生成的 studio 日志不应放宽权限（`chmod 600`），且不要为"备份现场"而 `cp` 出一份可读副本（那会重建泄露面）。

**巡检命令**：`cluster.py secrets scan`（明文命中门禁，PASS/FAIL）、`cluster.py secrets status`（落点/引用/权限）、`cluster.py providers`（凭据引用形态 + 漂移）。
