## 1. 社区成熟方案谱系（这次新增调研）

### 1.1 商业 SaaS（Asana / Monday / ClickUp / Jira / Wrike / Smartsheet / Nifty / ONES / Sigmaviu）

| 模式 | 代表做法 | 对本仓最相关的点 |
|---|---|---|
| **自动进度计算** | Nifty：从任务数据自动算完成率，无人手填百分比 | "进度 = 推导值，不是汇报值" |
| **实时自动聚合** | Asana portfolio "real-time updates"；Monday "board updates automatically as project data changes，无需手动刷新/重建报告" | dashboard 是**派生视图**，非人工维护 |
| **跨项目 portfolio** | Monday All Projects Dashboard / 健康快照（完成率、计划 vs 实际） | 单一 pane-of-glass 看全部项目 |
| **异常优先** | 风险旗标/阻塞/延期高亮；Sigmaviu "Open actions" | **认知过载解法**：只看需要动作的 |

### 1.2 开源 / 自托管（贴合本机群本地偏好）

| 工具 | 定位 | 对本仓的适用性 |
|---|---|---|
| Planka / WeKan / Focalboard / Vikunja / Taiga / OpenProject | 完整自托管看板（需 DB+服务常驻） | ❌ 重量级：新增常驻服务违背零自加载哲学，与既有 ADR-0004 单入口纪律重叠 |
| **Upptime 模式** | 仓库当数据库 + cron 探针 + 静态站 + Issues 当事件簿 | ✅ **借鉴其心智**：声明式配置 + cron 自动生成 + 静态产出，零常驻服务 |
| **AI 生成 HTML 提交进仓库**（McGarrah 模式） | 单文件 HTML（内联 CSS/JS）commit 进仓库 + 静态托管 + 稳定 URL | ✅ **dashboard-as-code**：产物 = git 工件，可 diff/回滚/留档 |
| **Observable Framework** | 静态站生成器 + 构建时 data loader（Python） | ⚠️ 有用但引入 Node/构建链，对本仓偏重 |
| 状态页工具（Uptime Kuma / OpenStatus / gatus） | 健康监控状态页 | 心智可借（组件级状态 + 历史），但面向服务可用性非任务进度 |

### 1.3 三句提炼（社区共识）

1. **进度看板必须是派生视图**：从底层状态数据自动推导，无人手维护 —— 手填的 dashboard 一周后就骗人。
2. **查看成本趋零**：要么实时读（打开即最新），要么定时生成静态物（稳定 URL / 可 git diff）。
3. **过载解法 = 异常优先**：高亮"需要动作"（blocked / 等回复 / 等验收），终态与无事件折叠。

## 3. 方案建议（分层，由 Scott 裁定）

### A（推荐，成本最低）— `cluster_web.py` 加「受理区」卡片
- **做法**：复用既有 web 管理页架构：后端加 `/inbox` 端点（读 inbox/*/STATE.json），
  PAGE_HTML 加一个 `<details>` 卡片 + `loadInbox()`（并入既有 15s 自动刷新循环 `refreshAll()`）。
- **符合**：ADR-0004（管理走入口）、零常驻（web 本就随用随起）、查看成本趋零（打开即最新）、
  **自动更新零手动**（15s 轮询机制已存在）。
- **过载缓解**：卡片按"需要动作"分组 ——
  `waiting`/`plan-review`/`release`（等需求方 / 等验收）→ 黄色高亮；`running` → 蓝色；
  `done`/`accepted-by-requester`/`rejected*` → 折叠到"已关闭"；顶部一行健康快照
  （活跃 N · 待动作 M · 最近变更）。

### B（离线/留档）— `cluster.py inbox --board` 生成静态看板（dashboard-as-code）
- **做法**：`cluster.py inbox --board` 读 STATE.json 生成**单文件 HTML**（内联 CSS/JS，
  与 A 同布局）→ 写 `inbox/board.html`（git 版本化，可 diff/回滚，Upptime/McGarrah 模式）。
- **自动更新**：Windows 计划任务（schtasks，本机定时 `python cluster.py inbox --board`）——
  不需要用户手动跑/给提示词；或 git 提交后 hook。
- **定位**：A 的离线孪生；适合"不开 web 也能看"与留档。

### C（可选演进）— 待办聚合 / 通知
- 看板按需列出每笔"当前待办"（如 paper 裁决报告），从 `40_state/评估摘要.md` 或 `LOG.md` 提取；
- 若需要"被动作唤醒"而非"主动查看"：可选 cron 生成日报 markdown（异常优先）或现有 web 的轮询即为答案。

**约束核对**：全部方案为**主控本地**新增能力，无站上部署、无新常驻服务、无一次性脚本
（`--board` 是 `cluster.py inbox` 子命令的扩展，符合 ADR-0004 入口纪律；web 卡片进 `cluster_web.py`）。

### A + C 实施记录（2026-09-23）

- **后端**：`cluster_web.py` 新增 `_collect_inbox()` + `/api/inbox` 端点（复用既有 `_auth_ok` 鉴权）；
  `_INBOX_NEXT` 状态→下一动作映射 = **待办聚合的单一真值**（与 inbox/README §3 状态机对齐）。

  分组 `action`（waiting/plan-review/release，黄底高亮）/ `active` / `closed`（折叠）；
  顶部健康快照行（共 N 笔 · 需动作 M · 进行中 K）。
- **自证（E1，真机）**：
  1. HTTP 端到端：带 token `/api/inbox` → 200 + 正确 JSON；无 token → **401**（与既有端点同鉴权纪律）。
  2. 多项目聚合：临时注入第二笔（`plan-review`）→ 看板 2 行、`action=2`；改 `running` →
     `action=1 active=1`（**分组分离成立**）；改 `done` → 落 `closed` 组。
  3. **门禁交叉验证**：探针 `done` 缺 `30_evidence`/受理决定 → `rpc_check --only inbox`
     **FAIL 并点名探针** —— 证明**看板分组与门禁对状态语义的判断一致**（非两套口径）。
  4. 清理探针后：`rpc_check --quick` **11 绿 0 红**。
