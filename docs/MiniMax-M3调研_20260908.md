### 3.2 关键工程事实

- **Q4_K_M = 256.2G 权重**；**全 1M ctx 增加 ~96.5G KV** → 共 **353G**
- **MSA 尚未在 GGUF 运行时实现**：llama.cpp / ds4 / Ollama（包装 llama.cpp）均**回退 dense attention** → 1M context 的稀疏加速优势主要属于 vLLM/SGLang 官方栈；本地 GGUF 跑 M3 长上下文仍线性吃内存（部分中文社区实测 13B 档 KV 增长近线性，但 428B 档无此验证）
- **llama.cpp 主线支持状态**：M3 架构已合（含 MSA prefill 优化 PR #26297 **merged 7/30**，vision merged 7/27）；但社区普遍用专用 `minimax-m3` 分支；**MSA 稀疏 attention 计算仍缺**（ik_llama.cpp #2046 讨论中，Q4 graft 在 ctx≤2048 与 dense 无差、2560 时 +0.16% → **短上下文下 dense 回退是忠实替代**）

| 路线 | 可行性 | 说明 |
|---|---|---|
| **llama.cpp RPC 三站分摊 Q4_K_M**（256.7G 权重） | ⚠️ **工程可行，质量必须过门** | A+B+C=384G；层分布 `-sm layer`；协议 v6.0.0 + -dio；**M2.7 工程先例成立，但同套件 2/5 零产出被删 → M3 需过 quality gate 再部署**（§5.1/5.2） |
| 三站 RPC + 全 1M ctx（+96.5G KV=353G） | ⚠️ 需严格规划 | 384G 池勉强覆盖，KV 峰值下余量低，风险高 |

### 5.1 同族工程先例 + 质量失败记录（关键双面证据）

> **工程面**：MiniMax 家族 MoE（M2.7: 230B/10B 激活）曾在集群 **llama.cpp Vulkan RPC 双机层分布**上实测跑通（[分布式推理.md §7.3](分布式推理.md)）：

| 指标 | M2.7 Q4_K_S 双机 RPC 实测 |
|---|---|
| 引擎 | llama.cpp 9859（commit 4fc4ec554，RPC v4.0.1，2026-07-02） |
| 加载 | ~4.4 min |
| 生成 / prompt | **17.7 t/s / 22.7 t/s** |
| 并发 | 4 slots × 32K ctx |
| 配置要点 | `--n-cpu-moe 8~16`（MoE 专家 offload CPU），TEMPERATURE 0.3 |

> **质量面（决定性 — 该模型最终因此被删）**：[results-ledger.md §冒烟对比 m27-q4ks](results-ledger.md)（2026-09-01，用户数理金融/编程测试题，双机 RPC 部署下实测）：

| 题号 | 型 | m27 结果 | 判定 |
|---|---|---|---|
| dmx-b2 | 数值 | 通过（-0.1575, 19.3s） | ✅ |
| dmx-a1 | rubric | 良好（构造规范） | ✅ |
| dmx-g1 | rubric | 通过（逊于 qwen SDF 深度） | ⚠️ |
| dmx-a3 | 数值 | **6 次尝试零产出**（think 2048/16384 timeout、nothink 2048/16384 length） | ❌ 不可测 |
| dmx-c2 | 代码 | **nothink 6144/12288/16384 均零产出**（最长 763s） | ❌ 不可测 |

**判定: 冒烟 3/5 有效, 2 题不可测 → 越狱版行为不合格 → 模型删除**（rpccache 两代 169G 随删）。

### 5.2 对本调研的修正性结论（关键）

1. **工程链路可行 ≠ 可用**：M2.7 证明 "MiniMax MoE + 双机 RPC 层分布" 能跑通并达 17.7 t/s，但**用户测试题暴露 2/5 零产出**（数理金融 a3 + 编程 c2），root cause = **MiniMax 家用无 reasoning 分离（思考/正文混杂）→ 禁思考只改输出形态、预算失控 → 长题/代码题输出前置失控**。
2. **M3 同族风险必须预设**：M3 同为 MiniMax MoE（428B/23B 激活），**thinking 分离架构问题大概率继承**（除非官方 M3 新增 reasoning_content 通道——需核实）。
3. **"按 M2.7 同法放大"应改为"工程可行，但质量门必须重测"**：M3 上集群前，**必须以 results-ledger 同套件（dmx-a3/dmx-c2 等）过质量门**，否则复现 2/5 不可测风险高。
4. **qwen3.8-flash-next 是已实证的优质替代**：同套件 5/5 有效（thinking 独立通道、禁思考真禁、预算可控），吞吐 15.7 t/s 与 m27（19.7）差距<25% → **若需求"数理金融/编程可靠输出"，qwen 系优先级高于 MiniMax 系**。

**推荐初判（更新）**：
1. **不预设 M3 可直接替换 M2.7 用**：先核实 M3 是否具备 reasoning 分离；若无 → 仅用于无严格输出约束场景
2. **上 M3 前必经质量门**：results-ledger 同套件跑通（包含用户数理金融/编程测试题）→ 通过才部署
3. **三站 RPC Q4_K_M 仍为技术形态**，但**模型选型层面 M3 相对 qwen3.8-flash-next 无明确优势**（后者 5/5 可用且单站即可）
4. **若目标=编码/长上下文**：Qwen3.8-Flash-Next（262K ctx 本机实证）优先；M3 的 1M ctx 因 MSA 未实现而优势旁落

### 5.3 unsloth 官方信息补充（unsloth.ai MiniMax-M3 文档，2026-09-09 抓取）

> unsloth（GGUF 量化方 + 运行时官方）对 M3 的本地运行定位，**多处与此前社区/llmrun 结论一致，并新增工程细节**：

#### 5.3.1 官方确认的关键限制
- **当前 M3 GGUF = 仅文本**（原生多模态，但实验性 GGUF 未含视觉）
- **MSA 不支持** → 推理**回退稠密注意力**；官方明确建议 **`--ctx-size` 保持适度**（"非常长的上下文中稠密注意力会消耗大量内存"）→ **1M ctx 在 GGUF 路线不可行，此前提最终确认**
- llama.cpp 运行需**专用 PR 分支 #24523（minimax-m3）**，非主线

#### 5.3.2 与集群相关的工程细节
| 项 | unsloth 官方值 | 备注 |
|---|---|---|
| 推理硬件表 | 1-bit 133G / 2-bit 148G / 3-bit 164-200G / **4-bit 213-270G** / 5-bit 325G / 8-bit 460-470G | Q4 档 213-270G（含 KV/上下文余量口径）|
| 推荐最小/最佳 | `UD-IQ1_M` 128G / **`UD-IQ3_XXS` 159G 最佳** | ≥133G RAM 运行 IQ1 |
| 推荐参数 | `--temp 1.0 --top-p 0.95 --top-k 40` | MiniMax 官方建议（注意 temp=1.0 非 0.3）|
| 构建 | `git fetch origin pull/24523/head:minimax-m3` + `cmake -DGGML_CUDA=ON` | 集群 ROCm 需 `-DGGML_HIP` 变体，未验证 |
| 多模态 | GGUF 仅文本；视觉走原生 safetensor（Unsloth Studio）| 集群 RPC 路线=文本 only |

#### 5.3.3 对集群结论的增量修正
1. **PR #24523 是运行前提**：此前调研待验证项"llama.cpp minimax-m3 分支可用性"→ 官方指向 **PR #24523**；集群若要跑 M3 需基于此分支构建（非普通 master；注意与现役 /opt master v6.0.0 的 MANIFEST/协议版本关系）
2. **温控参数**：temp=1.0 为官方推荐（此前 M2.7 经验 TEMPERATURE 0.3 是 minmax 系旧建议；M3 官方档=1.0）→ 质量门测试须用官方参数否则口径偏
3. **Q4 档位口径核对**：llmrun 记 Q4_K_M=256.7G 权重；unsloth 硬件表 4-bit="213-270G（总内存 RAM+VRAM）"——两口径一致（权重 256G + 上下文余量），**单站 128G 无解，三站 RPC Q4_K_M 是唯一路径**（除非只跑 159G 3-bit 单站）
4. **候选对比降级**：unsloth 未提 reasoning 分离 → M2.7 的 output 失控风险在 M3 GGUF 侧仍无解除证据（保持 §5.2 预设）
