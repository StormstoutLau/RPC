## 2. 取证：两个计数器各是谁、覆盖什么（E1）

### 2.1 旧件 `ops/.egress_daily.json`（主控侧 · **设计过写入手、从未接线**）

| 项 | 事实（E1） |
|---|---|
| 形状 | `{"date","count"}` —— **不分站 / 不分账户**（`cluster_egress.py` L88-97） |
| 写手（设计） | `_egress_bump()`（L100-105）—— `ADR-0003` L221 逐字「**由真正发 OpenRouter 免费请求的调用方（`opencode -m openrouter/...` / review 免费源）在发请求前自增**」 |
| 写手（**实际**） | ★★ **零调用点** —— 全仓仅 L100（定义）与 `cluster.py` L545（重导出）两处命中；`ops/` 下无任何 `.py/.sh/.ps1/.js/.ts` 调它 |

| **日界** | ★★ `datetime.date.today()` = **本地日**；而注释（L89）与 `ADR-0003` L220 都写「**UTC 日**滚动归零」⇒ **代码与文档不符** |
| 设计覆盖面 | `ADR-0003` L223 逐字（诚实边界）：「本地计数覆盖"**主控侧入口能感知**"的请求（wrapper / egress / review），**人手动 TUI 直调不在此计数**」 |
| **实际覆盖面** | **空**（零写手） |

### 2.2 新件 `ops/.egress_station.json`（派发侧 · 活）

| 项 | 事实（E1/E2） |
|---|---|
| 形状 | `{date, by_station:{A,B,C}, last_used}`（**缺键补 0**；跨 UTC 日归零）—— L5107-5154 |
| 写手 | `Write-EgressStationPick` —— **唯一生产调用点** = `Invoke-Task` 的 egress 块 **L2513**（**每派发一次 +1**）；★ 另有两处**夹具测试**调用（写系统 TEMP、**不触真件**） |
| 读者 | `Read-EgressStationState` → `Get-EgressStationCandidates`（L2503-2506）⇒ **派发前实时选站依据** |
| 盘上状态 | ★ **E2 实测**：`{"date":"2026-10-20","by_station":{"C":0,"B":1,"A":1},"last_used":"B"}` |
| **覆盖面** | ★★ **仅"默认出网档的 `task` 派发"**（`$Script:EGRESS_MULTI_ALIASES` ∈ `{ultra, free-1m, lightning}`）⇒ **不含**：per-station 别名（`ultra-a/-b/-c` **不进候选 ⇒ 不 bump**）· `review` 判官出网（`Invoke-JudgeHttp` 那条路）· 人手动 TUI 直调 |

### 2.3 ★ 精确结论（比"同一事实两处表达"更准的定性）

两个计数器**不是同一个集合的两处计数**，而是**两个不同集合**：

- 旧件（**设计**）= 集合 **S₁**「主控侧入口能感知的 EGRESS 请求」（⊇ 含 review 判官那一路）；
- 新件（**实际**）= 集合 **S₂**「默认出网档的 task 派发」（**严格的子集**）。

⇒ ★★ 真正的风险**不是"同一个数被算了两遍"**，而是 **① 名词冲突**（两件都叫"**本地计数**"，而它们的**定义域与用途都不同** ⇒ 下一个人极易把其中一个读成另一个）· **② 名义覆盖 ≠ 实际覆盖**（旧件**声明**覆盖 S₁，**实际**覆盖 ∅ ⇒ **假防线**）· **③ 日界口径不一**（本地日 vs UTC 日 ⇒ **对账窗口不重合**：UTC+8 机器的"本地日"在 UTC 16:00 翻转，而服务端在 UTC 00:00 重置）。

| R2 | **统一入口增强 + 写入手 + 诚实边界** | 「统一入口 `egress` 增强：… 显示**主控本地每日计数**（`.egress_daily.json`，UTC 日滚动归零）+ 达 80% 预警」· 「**写入手 `_egress_bump()`**：由真正发 OpenRouter 免费请求的调用方…在发请求前自增」· 「**诚实披露边界**：本地计数覆盖"主控侧入口能感知"的请求…**人手动 TUI 直调不在此计数**」 | `ADR-0003` **L219-223** |
| R3 | **本地计数器降级为旁证** | 「**本地计数器 `.egress_daily.json` 的去留**：**降级为旁证**（服务端是快照、本地是流；两者可交叉验证"是否有未记录的调用方"），**不再作为唯一依据**；`_egress_bump()` **保留但不再是权威**」 | [多账户设计](security/2026-09-21_OpenRouter多账户配额分配与调配设计.md) **§5.2 第 2 条** |
| R4 | **限速只在 wrapper 出口** | 「**RPM 20 硬限速 + 429 指数退避**…**只在"经过 wrapper 的出口"限速**，opencode 内部 HTTP 拦不到」 | `ADR-0003` **L227-229** |

★★ **两条结论**：
1. **既有裁定链把本地计数器定义为「旁证 / 实时近似 → 交叉验证」**，**从未**把它定义为「**派发决策依据**」⇒ 本批的用法是**角色升格**（比"形状变更"更重的一个变更）。
2. **既有裁定链通篇未提"按站"这一维**（`ADR-0003` 的免费档计数讲的是**账户**；多账户设计的 §4/§5 讲的是**借用/指派**，不是"按站分片计数"）⇒ ★ **"按站"是本批新引入的一维**，须在裁中**定性**（写进 `ADR-0003` 或明确登记为"派发侧专用、与旁证件不同域"）。

## 5. 外部社区对照（E3 · 全部为外部来源，**未在本仓复现**）

> 说明：**OpenRouter 官方没有"按站分片"这种概念** —— "station" 是本仓自己的调度面概念。⇒ 外部只引**计数器职责分离**与**权威-近似**的更一般形态，**不**杜撰厂商建议。

### 5.1 「本地近似层 vs 全局权威层」是**规范形态**，且**越界被明确接受**

- **Envoy（官方）**：两层**同用**是设计意图，越界由本地桶吸收 ——「Local rate limiting can be used in conjunction with global rate limiting … a local token bucket rate limit can absorb very large bursts … Thus, the rate limit is applied in **two stages**.」（[global_rate_limiting](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/other_features/global_rate_limiting)）
- **Envoy 本地过滤器（官方）**：本地桶**天然 ≠ 全局** ——「the token bucket is either shared across all workers or on a per connection basis … the local rate limits being applied either per Envoy process or per downstream connection.」（[local_rate_limit_filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/local_rate_limit_filter)）
- **nginx（官方）**：`limit_req` 的 zone 是**节点内共享内存**；跨节点同步属商业版 ——「Sets parameters for a shared memory zone that will keep states for various keys.」/「The `sync` parameter … enables synchronization of the shared memory zone.」（[ngx_http_limit_req_module](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)）
- **APISIX（官方 cookbook）**：跨节点共享配额才上 Redis 全局计数，并**直说本地近似会越界** ——「A request can therefore take usage past the limit before the next request is rejected.」（[redis-shared-token-quota](https://apisix.apache.org/cookbooks/redis-shared-token-quota/)）
  ⇒ ★ **对本仓的直接含义**：**不要把"本地数 == 服务端数"当判据** —— 本地层（派发侧选站）与权威层（服务端 `remaining`）**本就允许不等**；能被判的是**差值有解释**。

### 5.2 「权威但滞后」的计数**不能当预检门**，且应**对账**

- **APISIX（官方）**：权威计数**在回程**写入 + 要求对账 ——「APISIX reads the current counter before proxying a request and records the provider-reported usage **after** the response」（同 5.1 URL）
- **AWS EventBridge Scheduler（官方）**：CloudWatch 指标是 **best-effort**、「The completeness and timeliness of metrics are **not guaranteed**. … They are **not meant to be a complete accounting** of all operations.」（[monitoring-cloudwatch](https://docs.aws.amazon.com/scheduler/latest/UserGuide/monitoring-cloudwatch.html)）
- **AWS AgentCore（官方）**：「Resource usage data **may be delayed by up to 60 minutes**」（[observability-runtime-metrics](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-runtime-metrics.html)）
- **Stripe（官方）**：用量事件**异步**处理 ——「Because Stripe processes meter events **asynchronously**, upcoming invoices might not immediately reflect recently received meter events.」（[usage-based-v1](https://docs.stripe.com/billing/subscriptions/usage-based-v1/use-cases/flat-fee-and-overages)）
  ⇒ ★ **与本仓 `ADR-0003` 点 2**（"不能当调用前实时闸门，只适合巡检/预警/事后对账"）**逐字同向** —— 本仓的裁定在这一点上**与社区一致**。

### 5.3 「分片」的规范形态 = **一个逻辑计数器，聚合=求和**（而**不是**第二个平行计数器）

- **CRDT 权威论文（Shapiro 等）**：「A trivial example of a CRDT is a replicated counter, which converges because the increment and decrement operations **commute**」；G-Counter 形状 = 每个节点只更新自己的下标、**总系统值 = 各下标之和**（[crdt-tr2011.pdf](https://dsf.berkeley.edu/cs286/papers/crdt-tr2011.pdf)）
- **Firestore（官方）**：分片计数器的定义 ——「the value of the counter **is the sum of the value of the shards**. Write throughput increases linearly with the number of shards.」（[solutions/counters](https://firebase.google.com/docs/firestore/solutions/counters)）
- **单写者原则（社区）**：「for any item of data, or resource, that item of data should be owned by a **single execution context** for all mutations.」（[single-writer-principle](https://www.javacodegeeks.com/2012/08/single-writer-principle.html)）
- **DynamoDB（官方）**：单聚合原子计数"**非幂等**"的代价（重放会多计）——「a numeric attribute that is incremented, unconditionally … the updates are **not idempotent**.」（[WorkingWithItems](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html)）
- **Prometheus（官方）**：`counter` 是**累积量**、只能增或重启归零（[metric_types](https://prometheus.io/docs/concepts/metric_types/)）
  ⇒ ★★ **对本仓的直接含义**：**"按站分片"的正统形态就是"一个计数器 + 一个求和"**（Firestore/CRDT 都如此）⇒ 它**支持甲/丙（单件 + 按站形状）**，而**不支持"两个平行业绩账"**。乙若选，必须靠**"两件不同域"**这条论证站住（即 §2.3 那条：它们覆盖**两个不同集合**）。

### 10.5 核查三（**一条口径边界 · 建议登记、不实测**）：「exempt ⇒ `remaining` 不是强制上限」

- **对本仓的含义**：三账户 `is_free_tier=false`（**曾充值**）⇒ **是否属"exempt"未核**。若属，则 `remaining` 在它们身上是**档位政策值**、**不是硬闸** ⇒ ★ 影响的是 `O-147` 里「服务端 = **权威**」这一层的**语义**：它仍可作**巡检 / 对账**，但「**打满即被拒**」这一预期**可能不成立**。
- **建议**：**只登记为口径边界**（写进 `ADR-0003` 的更正段），**不为此专门实测**（它**不改变**"按站计数选站"的算法）。

### 10.6 核查四（**建议做一次"引用清扫" · 零行为变化**）：**「20 请求/分」的归属 + 它的引用面**

- **E1 事实（本轮回扫，`grep` 命中 ≈30 处）**：仓内**多处**把"20 请求/分"当**既定事实**引用，且**多数还加了「/账户」这个限定词** —— `agent-cli.ps1` **L3903 / L4134 / L5636-5637**（RPM20 令牌桶）· `cluster_egress.py` **L80 / L240 / L261 / L452** · `ADR-0003` **L188 / L193 / L227 / L235** · `security/2026-09-21_多账户…设计.md` L104-105 · `research/2026-10-01_图结构…调研.md` L47 / L243 / L285 / L355 / L393 等。
