## 1. 背景与问题定义

主控站多个任务项目（RPC/Paper/Spec_Workflow/Auto_Prover/Cpp_Hub）通过 wrapper 调用三站 **6 个 agent CLI**（opencode + claude code × A/B/C，每站各 2 个）。现役选型依据（2026-06 定）：**opencode 因免费额度**（原 sst 系，无硬 API key 依赖）+ **claude code 因生态与标准**（Anthropic 官方 CLI 事实标准）。

本调研回答：社区当前流行的 **Pi agent**、**Hermes agent** 及其他 agent，相对现役有/无替代价值？结合本集群使用场景回溯验证现役选型是否仍然成立。

**非目标**：不重新调研 claude code / opencode 的全部生态细节（D5 调研已覆盖，附录 A 含 opencode 生态全文）；不评估 MCP/skills 插件层（PLUGIN-LEDGER.md 已维护）。

## 2. 使用场景约束（选型判据来源）

从集群实际运行提炼的硬约束：

1. **本地模型一等公民**：所有 agent 直连本地 llama-server/Unsloth 端点（127.0.0.1:8080 / A/B:8080），敏感内容 local-only 三档硬路由（任务卡 sensitivity 字段，wrapper 层拒绝远端）——**CLI 必须对 OpenAI 兼容本地端点第一优先支持**
2. **免费额度 / 无 key 硬依赖**：选型动机之一是没有云端 API key 时仍可工作（离线/断网场景）
3. **spec_workflow + strong-accept 降幻觉**：任务卡状态机、主控站权威 golden 测试、（未来）mutation 加固——要求 wrapper 对 CLI 有**确定性编排能力**（headless 模式、stdin 管道、退出码契约、并发锁）
4. **三站同构、锁版本**：任何新 CLI = 重做 ROUTE 映射 + 重验调用铁律 + 重跑 6 CLI 冒烟 + 回归 A1-A16（集成成本量化见 D6）
5. **长任务上下文管理**：单会话长任务（论文、大代码库）受本地模型窗口限制，已落地 DCP（会话内压缩）+ codex-memory（跨会话记忆）+ CLAUDE.md 三层方案——**生态必须可被现有三层方案覆盖**

## 3. 候选方案基本事实（核实后）

### 3.1 opencode（现役）· E2

| 项 | 事实 |
|---|---|
| 仓库 | `anomalyco/opencode`（原 sst/opencode，2025-06-19 发布，2026 团队改名 Anomaly）|
| 形态 | 支持 75+ LLM 供应商（models.dev），TUI / Desktop / Web / SDK |
| 本地模型 | 一等公民（provider 直连本地端点，E1 本集群双 provider PONG 实证，D6 wrapper 硬编码 stdin 管道形态 L1 实证）|
| 免费额度 | 保留云端免费档路由（E1 实测可出站免费档）|
| 生态 | opencode 原生 plugin API（codex-memory / DCP 均原生）、直接读 `.claude/skills/` |
| 已知坑 | plugin API 多次 patch 版内静默破坏（`api.command.*` 移除 / V2 hook 失效）；需锁版本 + 预装系统 ripgrep（D5 §8.6 实证）|

### 3.2 Claude Code（现役）· E2

| 项 | 事实 |
|---|---|
| 仓库 | `anthropics/claude-code`（官方）|
| 形态 | Anthropic 官方 CLI，事实标准（生态/教程/技能最全）|
| 本地模型 | 需 ANTHROPIC_BASE_URL 转换层（LiteLLM anthropic 协议，tool-use PASS 实证），非官方推荐路径 |
| 收费 | 云端按 token 计费；PRO/MAX 订阅 |
| 生态 | CLI 侧机制（skills/hooks/MCP/subagents）与后端无关，已全套可用 |
| 已知坑 | hooks 上游零认领（#31250/#34573/#31777/#24115 closed as not planned）；marketplace 自动更新静默清空插件 → 锁版本（D5 §8.6/§8.9 实证）|

### 3.3 Pi（`@earendil-works/pi-coding-agent`）· E2/E3

| 项 | 事实 |
|---|---|
| 仓库/官网 | `earendil-works/pi` · pi.dev · MIT · TypeScript/Bun |
| 作者 | Mario Zechner（libGDX）+ Armin Ronacher（Flask/Jinja），Earendil Works 维护 |
| 热度 | ~80K stars；周下载 ~130 万 npm（E3 社区 2026-08 报道）|
| 定位 | **极简 harness**：默认仅 4 工具（read/write/edit/bash），无内置 sub-agents / plan mode / MCP / 权限系统 / 安全沙箱 |
| 模型支持 | 30+ providers：Anthropic/OpenAI/Google/DeepSeek/Groq/Cerebras/xAI/OpenRouter/Ollama/llama.cpp 本地等 |
| 四种模式 | interactive TUI / print/JSON headless / RPC（stdin/stdout JSON 协议）/ SDK |
| 上下文管理 | AGENTS.md + SYSTEM.md + 可定制 compaction 扩展 + skills 按需加载（progressive disclosure）|
| 安全 | **明确无内置权限边界（community 评价 safety defaults 5/10）**，需自己沙箱 |
| 会话 | session tree 分支/回退（/tree /fork /clone）|
| 与集群的相关点 | 有 RPC 模式 + `models.json` 自定义 provider（可指本地端点）；但**无内置 subagent/plan mode** = 与我们"任务卡前置、strong-accept 权威验收"的编排模式不匹配（需全部自建扩展）|

> **注记（初版口头分析纠错）**：本调研初版曾误述 Pi 为"轻量单文件 CLI"，实为 4 工具极简 harness + TypeScript 扩展体系；非 Rust 实现。以本表为准。

## 5. 深度分析

### 5.1 Pi：理念值得跟踪，但"零内建"与本集群纪律冲突

Pi 的极简哲学（默认 4 工具 + 扩展自行构建）与"确定性编排优先"的集群纪律**方向相反**——集群在 agent 之上已经建了 wrapper 确定性层（任务卡/并发锁/strong-accept），需要的是 CLI 提供**稳定可控的 headless 契约 + 内建安全边界**，而不是一个"每次都要自建 subagent/plan mode/权限门"的裸 harness。

价值点：
- RPC 模式（stdin/stdout JSON）与 D6 wrapper 的跨进程调用形态同构，若未来 wrapper 需要第三 CLI 面，Pi 的 RPC 契约可借鉴
- session tree 分支/回溯 → 可观察性设计可学（对应集群 .agent-run.json 契约的增强方向）
- skills 注入方式（index+contents inline）与现有 12 定制技能设计同思路

跟踪项（不落地）：Pi 扩展生态成熟度、权限体系是否收敛（community 持续评 5/10 无沙箱）。

### 5.2 Hermes：存量不弃、不复用

本机已有 Hermes Agent 源码，D5 §9 已实读其编排机制（进程内真并行/落盘恢复/batch checkpoint 是**业界范式佐证**，佐证 D6 任务卡方向）。但：
- 官方能力边界（委托≠多智能体）→ 无法替代 D6 wrapper
- 性能裁定 HERMES-OPTIM-01 明确"不引入现役替换"
- 上下文管理生态空白 → 无法进入 DCP/codex-memory 三层方案

**定位**：研究资产（编排范式参考），非运行资产。

### 5.3 现役选型回溯：2026-09 时点仍然成立

当初两个选型点（免费额度 / 生态标准）在现役上均未失效：
- opencode 离线可跑 + 本地端点直连（免费额度动机的延伸：无云端依赖）
- claude code 生态与标准：CLI 侧机制全部可用 + 双 CLI 共用 `.claude/skills/` + 三层上下文方案已覆盖长任务短板

**附加说明**：现役组合已承担了"后训生态"的扩展（unsloth/llama.cpp 引擎层由独立链路管理），CLI 层无需再引入新面。

### 5.4 集成成本量化（按 6 CLI 重估，2026-09-09）

任何新增/替换 CLI 的集成成本 =

```
[固定成本]
1.  ROUTE_TABLE 新增 cli 列：每站新增 2 条路由记录 → 6 个路由映射 = 重写 + 全链路冒烟 → 1 轮
2.  调用铁律（stdin 管道 / < /dev/null 重定向 / headless 契约）全链路验证：每站 2 轮 → 6 轮 × (10-30) 分钟 = 1-3 小时
[可变成本]
3.  冒烟脚本 `ops/station-bin/agent-cli-smoke.sh` 全 6 CLI 跑通：D6 实测 4 CLI = 约 1 小时 → 6 CLI 预计 1.5-2 小时
4.  A1-A16 回归测试（wrapper 全流程验证，每 CLI × 16 条）：已测 4 CLI → 新增 2 CLI 需要回归
5.  PLUGIN-LEDGER.md 台账更新：每 CLI 补记录测试状态、社区反馈
6.  三站插件同构：codex-memory + DCP + 12 定制技能 + superpowers + ARS + CLAUDE.md → 每站迁移验证
```

**总成本估算（净新增一个 CLI）**：
- 固定 + 冒烟 + 回归 + 插件 → **约 4-8 小时人工验证时间**（分布式串行）
- 若**替换现役两个 CLI 为新 CLI**（即全栈迁移）→ 总成本约 **8-16 小时**（插件全迁移 + 原有路由完全废弃 + 三站配置全重构）

**结论**：任何新 CLI 的集成成本（人工时间 > 4 小时，分布式串行耗时 > 1 天）均显著大于边际收益（Pi/Hermes 仅理念增量，无功能增量满足场景约束）。**HERMES-OPTIM-01 原裁定"边际收益 < 集成成本"在 6 CLI 框架下依然成立**，不改变结论。

## 6. 结论与既有决策一致性

| 事项 | 裁定 |
|---|---|
| 主路径 | **维持 opencode + Claude Code 双 CLI**，不做替换、不做新增第三 CLI |
| Pi | **不落地**（零内建安全/生态空白）；理念观察项（RPC 契约、session tree 可观察性、skills inline 注入）|
| Hermes | **不移除、不复用**（存量研究资产）；编排范式继续作为 D6 V2 参考（§9.4 已摘要）|
| Gemini/Codex CLI | **不引入**（云端绑定与 local-only 硬路由冲突；新增维护面）|
| 一致性 | 与 HERMES-OPTIM-01（O-10 覆盖）"不引入新 CLI"裁定一致；本档为选型面完整证据，不新增未决项 |

**后续若需重新评估的触发器**（本档不设哨兵任务，记录失效条件）：
1. Pi 生态出现"subagent/plan mode 内建化 + 权限体系收敛"的官方转向，且社区实测本地模型正反馈 → 复核 §5.1
2. claude code hooks 上游出现认领/修复（当前 #31250 等全部 closed as not planned）→ 复核 §3.2 坑清单
3. 集群出现第三个"CLI 面"强需求（如站间互审 D7+ 需要三方互写）→ 复核 §5.1 RPC 借鉴
