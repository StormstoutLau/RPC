**核心结论：C 站是唯一「ODM 公板 + UMA carveout 1G」的平台，且与 A/B 的差异只剩硬件层（子系统 ID 与 BIOS UMA 档位）。**

## 3. 决定性佐证 — 同公板社区案例

- **日本 EVO-X2（同 `2014:801d` 子系统，同 Strix Halo 平台）**：用户安装 Ubuntu + ROCm 后，最终在 ollama 中设置 **`OLLAMA_VULKAN=1` 使用 Vulkan 后端**（而非 HIP），才稳定运行 —— 与该公板 HIP 路径易出问题的结论一致。
- ROCm issue #6139 / #6269：gfx1151 上 `GCVM_L2_PROTECTION_FAULT_STATUS:0x00800932` + CPF 故障签名与 C 站完全一致；其中 #6269 同现 `amdxdna SVA bind failed -95`（三站共有的平台噪音，非本案根因）。
- AMD 官方 Ryzen AI 安装指南：**"AMD recommends setting the minimum dedicated VRAM in the BIOS (0.5GB)"** — C 站 BIOS 竟无 0.5G 档位（最小 1G），即出厂违反官方建议。

## 5. 定案

> ⚠️ **已修正（2026-09-08 晚）**：本条早期结论"HIP 不可用=硬件限制"被 **UMA=4G 档实测推翻**。C 站 HIP **完全可用**（gpt-oss-120b: 23s 加载 / decode 48.8 t/s）。定案更新如下，早期过程保留以备审计。

1. **✅ 最终成功形态（现行）**：C 站 BIOS **UMA Frame Buffer = 4G** + 引擎 b10715 HIP `--device ROCm0 -ngl -1 --fit off` → gpt-oss-120b 全链路打通，与 A/B 站同构。根因 = **carveout 档位**：1G 档 → SVM page fault；Auto(64G) 档 → HIP 池仅 61G 装不下 60G；4G 档两者兼优。
2. **早期失败归因（保留存证）**：1G 档下穷尽软件变体（qwen 停用/ROCm 屏蔽/aqlprofile 隔离/hipBLASLt=0/XNACK/CPU-only/amd_iommu=off+pages_limit=32M）均无法规避 page fault — 因 **1G carveout 是硬件档位缺陷**，非软件可修；B 站同参 54s 成功即因 B 站 carveout=0.5G 处于安全区间。
3. **Auto=64G 已确认是 ODM BIOS 最劣配置**（carveout 划走 62G，系统仅剩 62G，GTT 可借上限被压缩）— 与社区 jstormes/StrixHalo "大 carveout 浪费内存" 结论一致。
4. **Vulkan 兜底不再必要**（HIP 已通），仍保留为多后端选项。`amd_iommu=off + ttm.pages_limit=32000000` 现行生效，无碍。

## 6. 社区调研 — 同类问题/ODM 公板案例（2026-09-08 追加）

> 结论先行：**C 站并非孤例**。gfx1151 + UMA carveout 异常 + HIP/SVM 卡死的社区案例不止一起，且「单站用 Vulkan 收敛」是社区共同落点。

### 6.1 决定性社群案例一览

| 来源 | 硬件 | 问题与结论 |
|---|---|---|
| **GH jstormes/StrixHalo**（llama.cpp + ROCm 6.4.1 + Docker） | AI Max+ 395, 128G | **UMA Frame Buffer 建议 `Auto / 512 MB`**（"most important setting"，carveout 大则浪费内存）；推荐 `ttm.pages_limit=32000000`（~122G GTT）、**IOMMU off** → HIP 全 offload 跑 Qwen3 稳定成功 |
| **EVO-X2 部署记录**（mrz-net.org，同 `2014:801d` 公板） | 同型 ODM 小板 | 安装 ROCm 后最终 **`OLLAMA_VULKAN=1`** 用 Vulkan 收敛（不是 HIP）→ 同公板 HIP 可靠性差的直接旁证 |
| **ROCm #6582**（open, 2w 前） | BOSGAME BeyondMax, AXB35-02 公板, 128G, 96G carveout | llama.cpp mmap 大模型上传**卡死 + 用户态 spin + amdgpu SVM mapping failed / exceeds resident system memory limit**；进程 `kfd_process_wq_release` hog CPU → 与 C 站「加载死循环 + CPU 100%」同族故障 |
| **ROCm #6146** | Strix Halo gfx1151 | **ROCm 7.2.1 上 hipMemcpy() 直接 page fault，官方 samples 都失败**（C 站系统 ROCm 恰为 7.2.1） |
| **Otama 博客「Strix Halo 炼狱 3 天」** | 96G UMA | 排查路径：先疑 ROCm（7.2.1→7.2.3 无效）→ 真因 **MES SCH firmware 0x83 bug**，linux-firmware 已 revert commit `3d5c8135`（"Revert amdgpu: update GC 11.5.0 firmware"）→ 换固件后修复。**MES bug 直接导致 gfx1151 ROCm 计算故障** |
| **Frame.work 社区** | Strix Halo | vLLM 编译后运行遇 `Memory access fault by GPU node-1 / Page not present`，靠驱动 reset 恢复；最终 16 t/s 可用 |

### 6.2 C/B 与现代固件核验

- **MES/GC 固件 md5 全一致**（C=B：`gc_11_0_0_{mes,mes1,mes_2,pfp,me,mec,imu}.bin.zst` 各 7 项全同）→ 排除 MES 0x83 类固件差异（该 revert 早已入库，当前固件已含修复）。
- **内核 amdgpu 模块 srcversion 一致**、`mes_v11_0` ip block 一致 → 驱动层无差。
- 因此 C 站问题**仍归因 UMA carveout 1G（BIOS 最小档）+ ODM 公板**，社区所有「UMA=512M/成功」「UMA 异常→卡死/转 Vulkan」案例相互印证。

### 6.3 软件层最后一招 — 实测结果（2026-09-08 晚）

参考 jstormes 配置，C 站 GRUB 追加 **`amd_iommu=off`** 并上调 **`ttm.pages_limit=32000000`**（备份 `/etc/default/grub.bak-before-iommu-20260908`）→ 重启生效（iommu_groups=0、pages_limit=32000000、GTT 125GB、ROCm0 125000 MiB 可用）→ **复测 gpt-oss-120b HIP 仍 100% gfxhub page fault（ring:153, CPF），加载死循环**。

**结论：软件层全招穷尽，HIP 在 C 站定案不可用 → Vulkan 兜底。**
> ⚠️ **本条已纠正 (2026-09-08 晚)**: §5 头部定案已推翻本结论 — C 站 BIOS UMA 设 **4G** 后 HIP 全通 (gpt-oss-120b 23s 加载 / decode 48.8 t/s)。根因 = **UMA carveout 档位**（1G 档 SVM page fault, Auto 64G 压缩 HIP 池, 4G 档最优），非硬件不可用。本节保留为早期失败归因存证，不作为现行结论。
