# 统一管理入口 · 调研与优化方案（v1 ⚠️ 已废）

> ⚠️ **本版方向错误，请读 [v2 · 深入分析与优化方案](./2026-09-15_统一管理入口_深入分析与优化方案_v2.md)**
> v1 的关键错误：建议「复用三站已装的 LM Studio `lms` 作第二引擎通道」。但**复用其运行时是净性能下降** —— 引擎版本落后于现役构建（现役受 `vulkan-version-control` MANIFEST + UPGRADE_SOP 管控）、`-fa`/`--cache-type-k|v`/`--n-cpu-moe`/`--fit` 等调优参数在其路径上无法表达、独立 server(:1234)+GUI 会与现役引擎争 GTT（违反 load-gate 单实例硬规则）。
> 正确姿势（v2）：**只学其「产品化功能与编排设计」，引擎与参数体系自建**；方案锚定既有 ADR + spec 域 + 台账 + 硬规则 + 契约。
> 另：v1 未回溯既有管理框架（ADR-0001 边界、params-ledger 台账、rpc-nodes 声明式底座等），故盘点偏浅。

## 1. 现状盘点（七项管理覆盖度）

| # | 管理面 | 现状 | 载体 | 缺口 |
|---|---|---|---|---|
| 1 | **工作站负载监控** | ❌ 基本没有 | 外部 Beszel（三站 agent→B hub `10.10.10.2:8090`） | 无进程级/引擎级视角；无 GPU 遥测（利用率/VRAM/温度/功耗）；无推理指标（prefill/decode tps、KV 占用）；无统一面板 |
| 2 | **推理框架管理** | ⚠️ 只读 | `cluster.py frames`（llama/unsloth/vllm/litellm/opencode/claude 六框架状态） | 无启停、无版本管理、无 runtime 切换（LM Studio 的 `lms runtime` 式能力） |
| 3 | **模型数据管理** | ⚠️ 清单新加 | `GET /api/models`（三站库扫描）、`b5k_sync.sh --verify`（双端 sha256） | 无下载/导入/删除/冷移、无跨站去重、无磁盘配额告警联动、无模型元数据（ctx 上限/量化/来源） |
| 4 | **模型加载管理** | ✅ 较完整 | `cmd_load`/`cmd_load_on`/`cmd_unload_on` + 站上 `infer-load`/`infer-unload` + load-gate 内存门禁 | 无"加载参数"下发（ctx/threads/GPU offload/port）；无加载前**内存预估**（对标 `lms load --estimate-only`）；无 TTL/自动驱逐 |
| 5 | **RPC 分布式加载** | ⚠️ 弱（半手动） | `cmd_load` 对 RPC 类**只打印手动步骤并 exit 2**；`nodes.env` 手改；`rpc-nodes` 起停 | 未编排成一条命令：A 起 rpc-server → B 起 llama-server → 健康等待 → 收尾；无 RPC 拓扑可视化；无跨站层分布（`-sm layer`）参数管理 |
| 6 | **agent 端口管理** | ⚠️ 只读 | `cluster.py providers`、`inventory/ports.yaml` | 无端口分配/占用冲突检测/建议；agent 端点（8080/18080/4000/50052/8090/1234）无统一登记与巡检 |
| 7 | **插件管理** | ❌ 无 | — | LM Studio extensions/hub、opencode 插件、MCP servers（`~/.lmstudio/mcp.json`、`opencode.jsonc`）均无入口 |
| 8 | **工作流管理** | ❌ 无 | 仅脚本散落（`b5_bench_cluster.sh` 起 RPC→bench→收尾） | 无任务编排/定时/依赖/产物归档；无"加载→压测→报告"一键链 |

**已有入口（不统一）**：`ops/rpc.ps1`（check/install-hooks）、`ops/cluster.py`（status/load/frames/unload/e2e/secrets/providers/egress/web）、`ops/cluster_web.py`（Web UI）、`ops/rpc_check.py`（6 项断言）、`inventory/*.yaml`（真值表）、站上 `infer-*`/`rpc-nodes`/`load-gate`。

## 2. 社区案例调研

### 2.1 LM Studio（本地模型平台，`lms` CLI + REST API）
- **CLI**：`lms ls`（磁盘模型）/`ps`（已加载）/`load`/`unload`/`import`/`get`（下载）/`server start|stop`/`runtime`（推理运行时管理）/`daemon`（无头守护 `llmster`）/`log`（请求日志）
- **加载参数**：`--gpu=max|auto|0.0-1.0`、`--context-length`、`--identifier`；**`--estimate-only` 先估内存不加载**
- **REST API v1**：`GET /api/v1/models`、`POST /api/v1/models/load|unload|download`、`/download/status`；另有 OpenAI 兼容与 Anthropic 兼容端点
- **其他**：Idle TTL / Auto-Evict（空闲自动卸载）、MCP via API、有状态会话
- → **可复用点**：模型生命周期语义（含内存预估、TTL）、"加载参数"模型

### 2.2 GPUStack（开源 GPU 集群管理器）
- 多集群/多节点纳管（裸金属、K8s、云），**可插拔推理引擎**（vLLM/SGLang/TensorRT-LLM/自定义），Day-0 新模型上线
- 企业级运维：**自动故障恢复、负载均衡、Grafana+Prometheus 监控、用户认证、Token 计量**；还能按需开 GPU 实例
- → **可复用点**：多节点纳管模型、引擎可插拔、故障恢复与计量思路

### 2.3 Ollama Herd（把多设备变成一个本地集群）
- mDNS **零配置发现** + **智能评分路由**（温度/内存适配/队列深度/延迟/亲和性/上下文适配）+ 容量学习（设备可用性行为模型）
- **Live Dashboard**：fleet 概览、趋势、模型洞察、基准、**健康引擎（18 项自动检查）**、推荐、健康/设置
- 支持多模态路由与 **model fallbacks**
- → **可复用点**：健康引擎清单、评分/路由、Dashboard 信息架构

### 2.4 vLLM Cluster Manager
- Host（Postgres + Consul 服务发现 + FastAPI + React）+ Client（节点 agent）
- 能力：注册管理 GPU 节点、**模型配置管理**、按节点启动、节点健康与模型状态、**实时日志流**
- → **可复用点**：节点注册/心跳、模型配置与节点绑定、实时日志

### 2.5 llm-serve-dashboard（MIT，零依赖）
- 单 `index.html` + 单 Python 标准库脚本（`fleet-metrics.py`，:8092 JSON 端点）
- **GPU 遥测**：利用率/VRAM/功耗/温度/时钟；**推理指标**：decode/prefill tps、请求数、**KV cache 填充**、LoRA 状态；多服务器；reasoning tap
- → **可复用点**：与我们"零外部框架依赖"的技术路线完全一致，指标项可直接照搬

### 2.6 小结（共性能力清单）
| 能力 | 代表 | 我们是否需要 |
|---|---|---|
| 模型生命周期（list/load/unload/import/download + 内存预估） | LM Studio | ✅ 急需 |
| 加载参数（gpu/ctx/identifier/TTL） | LM Studio | ✅ 需要 |
| 多节点纳管 + 引擎可插拔 | GPUStack | ✅ 有限需要（固定 3 站） |
| 健康检查引擎（成体系的自检项） | Ollama Herd | ✅ 已有雏形（`rpc_check.py` 6 项） |
| GPU/推理遥测面板 | llm-serve-dashboard | ✅ 急需（当前空白） |
| 节点注册 + 实时日志流 | vLLM CM | ✅ 需要（日志流） |
| 智能路由/负载均衡 | Ollama Herd / GPUStack | ❌ 暂不需要（3 站静态路由已够） |

## 3. 本地 LM Studio 实测（关键发现）

三站**已装全套 LM Studio，但从未用起来**：

| 项 | 实测 |
|---|---|
| `lms` CLI | ✅ 三站均有 `/home/scott-lau/.lmstudio/bin/lms`（109MB 可执行）——**但不在 PATH**（`which lms` 失败） |
| GUI/主程序 | ✅ `/opt/LM-Studio/lm-studio`（`/usr/bin/lm-studio` 软链） |
| 配置/资产 | ✅ `~/.lmstudio/{models,credentials,extensions,hub,mcp.json,settings.json,server-logs,conversations}` 完整 |
| 推理后端 | ✅ `~/.lmstudio/extensions/backends/llama.cpp-linux-x86_64-{vulkan,rocm,cuda,avx2}-*`（多版本多后端） |
| LM Studio server(1234) | ❌ 未监听（未启动） |
| headless `llmster` | ❌ 未安装 |

**含义**：
1. 我们有**两套推理栈并存**——自建 `infer-load`（unsloth studio / systemd llama-server，走 `/data/models/gguf` 聚合视图）与 LM Studio 栈（走 `~/.lmstudio/models` 物理库 + 自带多后端 llama.cpp）。
2. **模型库的"物理库"其实是 LM Studio 的**（`/data/models/gguf` 只是软链聚合视图，这也是 MiniMax 漏显示的原因）。
3. `lms` 可直接补上**模型下载/导入/内存预估/TTL**等我们缺的能力，无需自研。

## 4. 差距分析（按优先级）

| 差距 | 影响 | 优先级 |
|---|---|---|
| 无负载/GPU/推理指标可视 | 加载决策靠猜；`-ngl`/`--n-cpu-moe` 调参无数据；事故无法回溯 | **P0** |
| RPC 分布式加载半手动（exit 2） | 每次 RPC 加载需 3 步手工；易漏收尾 | **P0** |
| 无加载参数与内存预估 | 只能改站上 conf；加载前不知会不会 OOM | **P1** |
| 模型生命周期不全（下载/删除/导入/去重） | 新模型要手工 rsync + 手工软链（MiniMax 的坑） | **P1** |
| 端口无统一登记与冲突检测 | agent/引擎端口散落，冲突靠人发现 | **P1** |
| 插件/MCP 无入口 | opencode 插件、LM Studio extensions、MCP servers 不可见 | **P2** |
| 工作流无编排 | 加载→压测→报告 靠记忆拼命令 | **P2** |
| 入口分散（CLI/Web/脚本/站上工具） | "改了这个忘了哪个" | **P0**（收敛） |

## 5. 优化方案

### 5.1 总体架构：一个门面 + 一个控制台 + 三层能力

```
                 ┌──────────── 统一入口 ────────────┐
                 │  CLI: ops/rpc.ps1 / cluster.py    │   ← 唯一命令行门面
                 │  GUI: cluster_web.py (Web 控制台)  │   ← 唯一图形入口
                 └──────────────┬───────────────────┘
        ┌───────────────────────┼───────────────────────┐
   L1 数据层               L2 编排层                L3 可观测层
   · inventory 真值表      · 模型加载/卸载(按站)      · 负载/GPU 遥测
   · 模型库统一视图        · RPC 分布式编排           · 推理指标(tps/KV)
   · 端口登记表            · 框架生命周期             · 健康引擎(自检项)
   · 凭据/Provider/出站    · 端口分配与冲突检测        · 日志流
   · 插件/MCP 清单         · 工作流(任务编排)          · 告警
```

**收敛原则**：任何管理动作**只允许**通过 `cluster.py` 子命令或 Web 控制台执行；站上 `infer-*`/`rpc-nodes` 降级为"被调用方"，不再直接使用。

### 5.2 P0（体验与正确性，本轮即可做）

| 项 | 动作 |
|---|---|
| **token 体验** | ✅ 已做：启动打印「免输链接 `/?token=…`」，前端从 URL 自动登录（手输入口保留为兜底） |
| **模型移动端可见** | ✅ 已做：`/api/models` 直扫站上模型库；MiniMax 软链已补（**规则化**：新模型入站必须同步补聚合软链，纳入 `rpc_check.py` 断言） |
| **负载与 GPU 遥测** | 新增 `GET /api/metrics` + Web 卡片：每站 `CPU/内存/swap/磁盘` + `GPU 利用率/VRAM/温度/功耗`（`/sys/class/drm/card*/device/`、`rocm-smi`）+ 引擎 `prefill/decode tps`（llama.cpp `/metrics` 或 `/slots`） |
| **RPC 分布式加载编排** | `cluster.py load <rpc模型>` 从"打印步骤 exit 2"升级为**真编排**：起 A `rpc-server` → 起 B `llama-server --rpc` → 轮询就绪 → 记录拓扑；`unload` 自动收尾两端 |
| **入口收敛** | 文档 + `cluster.py --help` 明确：**CLI/Web 是唯一入口**；旧脚本标注"内部/被调用" |

### 5.3 P1（补齐管理面）

| 项 | 动作 |
|---|---|
| **加载参数** | `/api/load` 增 `ctx`/`threads`/`ngl`/`n_cpu_moe`/`port`；对应站上 `infer-load --ctx …`（已支持这些 flag）；Web 弹"高级参数"面板 |
| **内存预估** | 对标 `lms load --estimate-only`：加载前按 `模型大小 + KV(ctx) + 余量` 预估并与 `load-gate` 规则联算，不达标**拒绝加载并给替代建议**（如降 ctx / 加 `--n-cpu-moe`） |
| **模型生命周期** | 新 `cluster.py models {list,sync,verify,import,rm,link}`：`sync` 即 `b5k_sync.sh`；`link` 自动补 `/data/models/gguf` 软链（根治 MiniMax 类问题）；`rm` 带二次确认与磁盘回收报告 |
| **端口管理** | 扩 `inventory/ports.yaml` 为"分配表"（owner/purpose/bind/占用者）；`rpc_check.py` 增端口断言（声明 vs 实况）；Web 显示端口矩阵与冲突告警 |
| **复用 LM Studio `lms`** | 把 `~/.lmstudio/bin/lms` 加进 PATH（三站）；用 `lms ls/ps/load/unload/server` 作为**第二引擎通道**（`--backend lmstudio`），并在 Web 显示其 `runtime` 版本矩阵 |

### 5.4 P2（可观测与编排）

| 项 | 动作 |
|---|---|
| **插件/MCP 管理** | 新增 `/api/plugins`：汇总 `~/.lmstudio/{extensions,mcp.json,hub}`、`opencode.jsonc` 插件、claude settings，做**三站一致性对账**（沿用既有"sha256 一致"思路） |
| **工作流编排** | `cluster.py flow run <name>`：内置 `bench`（起 RPC→bench→收尾→归档 metrics-log）、`verify`（三站校验）、`rotate`（凭据轮换）；Web 提供一键触发 + 产物归档 |
| **健康引擎** | 借鉴 Ollama Herd 思路，把 `rpc_check.py` 从 6 项扩到成体系（网络/USB4 链路/内存门禁/引擎/端口/凭据/配置一致性/模型库完整性），Web 显示红黄绿 + 修复建议 |
| **日志流** | 对标 vLLM CM：`/api/logs?station=X&unit=Y`（SSE/轮询），Web 内嵌实时日志窗（含 infer-load 与引擎日志） |

## 7. 与既有资产的关系

- **不推翻**：现有 `cluster.py` 四平面、`inventory/` 真值表、`rpc_check.py` 断言、`infer-*` 站上工具全部保留 —— 本方案是在其上加"面"（监控/生命周期/编排），并把入口收敛。
- **复用 LM Studio**：三站已装，仅需 `PATH` 与按需 `lms server start`；它补的是**模型生命周期**，不是替代我们的多站编排。
- **技术路线一致**：仍坚持"零外部框架依赖"（stdlib + paramiko），与 llm-serve-dashboard 同思路，避免引入 Postgres/Consul/K8s 这类重量依赖。
