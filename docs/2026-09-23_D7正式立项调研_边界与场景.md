## 1. 厘清 D6 / D7 边界（本次核心）

### 1.1 一句话判据

| | D6 | D7 |
|---|---|---|
| **一句话** | **单次派发的闭环** | **跨主体的复核闭环** |
| 链路 | 需求 → 受理 → **一次执行** → 证据回收 → 抽检 | **审 → 改 → 再审**（多轮）→ 结论收束 → 留痕 |
| 主体数 | **1 个执行主体**（可跨站选站，但仍是"派一次"） | **≥2 个主体**（产出方 + 复核方） |
| 终止判据 | 证据入链 + 门禁绿 | **复核方签收**（≠ 产出方自认完成） |

### 1.2 三条可机械判定的分界判据（建议写入 ADR）

| # | 判据 | 归 |
|---|---|---|
| **B-1** | **是否需要一个"非产出方"的主体来给结论？** | 是 ⇒ **D7** |
| **B-2** | **是否在同一产物上需要多轮往返（改完再审）？** | 是 ⇒ **D7** |
| **B-3** | **是否只是"这一次派发内部"的质量门（判官抽检、accept 判据）？** | 是 ⇒ **D6** |

> 用 B-1/B-2/B-3 复核 D6 期间"归给 D7"的 14 项，**结论全部一致**（无一项应退回 D6）：
> 它们要么需要第二个主体（权限/结论/裁决），要么需要多轮（续聊/编排），要么是跨站形态（架构/自环盲区）。

### 1.3 边界上的灰色地带（必须显式裁定，否则会被两边都漏掉）

| 灰色项 | 现状归属 | 本次建议 |

## 3. D7 的现成母版（E2，不必另造）

### 3.1 母版一：Spec_Workflow 的六相协议草案

**出处（E2）**：`F:\Spec_Workflow\spec\distributed-agent\DISTRIBUTED_AGENT_RESEARCH.md` v1.3（status: in-review）。

**它已经回答的问题**：三机（AMD Strix Halo 异构集群）能否承载本仓 10 步工作流，以及三个子命题
**P-a**（每步由站上 agent CLI 执行）/ **P-b**（每 agent 嵌套微工作流）/ **P-c**（主控派发 + 审核）。

**结论（文档明确写的）**：

| 命题 | 结论 |
|---|---|
| **最高价值落点** | **"异构验证的物理化"**（RULE-5 从"同机换模型"升级为"跨站跨家族"），**不是算力分摊** |
| **P-a** | **可行**（复用 `D:\RPC` 的 agent-cli 三件套 + accept 判据），但必须接受两条：并行只能由**编排层**发起（agent 内自扇出已被实证否证）、gate 必须留在**编排层** |
| **P-b** | **本仓判负**（收益"上下文隔离"在本仓不成立；代价"复利误差 p^N + MAST FC1 41.77%+FC3 21.30% + 四重硬约束 + 递归退化"全数命中） |
| **P-c** | **可行且优先级最高**（与本仓 + 集群既有机制最同构：集群已有可执行判据 + `.agent-run.json` + 独立 golden checksum） |

**★ 六相状态机协议草案（这是 D7 的骨架，可直接用）**：

```
P0 立契 → P1 领取 → P2 执行 → P3 回收 → P4a 机械验证 → P4b 语义复核 → P5 裁决登记
```

**★ 三种信封**：`TaskContract` / `RunReport` / `Verdict` —— 其中
**`RunReport` 刻意不含 verdict 字段**（产出方**不得自评**）。

**★ 三条设计红线（逐字）**：
1. **完成信号权只在主控站**；
2. **L1 机械门先于 L2 语义门，且 L2 无权改写**；
3. **判据与 golden 哈希在 P0 固化**（即"判据不能事后改"）。

⇒ **与 RULE-5「reviewer 只标记、永不改写」、与本机群"模型不自我盖章"（`accept` 由主控独立断言）
是同一条原则的三处独立表述** —— 可信度因此很高。

### 3.2 母版二：Auto_Prover 的 mission 三角色（权限模型范本）

**出处（E2）**：`F:\Auto_Prover\download\prove2me_workspace-main\references\mission_{captain,solver,auditor}.md`。

- **Captain**：起草 mission、与人类迭代、投递后 curation；**captain-only** 权限（里程碑增删改、
  `theorem_id` 链接、mission 元数据编辑）；**"You cannot self-audit or launch — those are human-only"**。
- **Solver**：默认角色，"pick open theorems, prove or disprove them (or reduce them)"。
- **Auditor**：**只做 read-back**（"a natural-language rendering of what a Lean 4 declaration *literally
  asserts* — the artifact's own testimony"），**"is not a summary and not an explanation"**。

**★ auditor 不能改写 solver 产物的三条理由（文档明确写的）**：

| # | 理由 | 原文 |
|---|---|---|
| 1 | 角色契约本身是"只陈述、不判断" | "Translate the code, not the intent"；**"No judgment, no advocacy."** |
| 2 | **它拿不到可改写的上下文** | "Never give the auditor the informal statement, the source material, the mission pitch, or your own intent." |
| 3 | 平台层禁止就地修改 | 草稿 Submit 时编译成**不可变** published theorem；改动是**重写 + 重审**，而非审计者直接改 |

**★ 为什么必须"盲写"**（原文）："**Faithfulness is also why read-backs exist: your own review is not
independent — you know what the code is *supposed* to say.** Delegate the read-back to a blind auditor
sub-agent … let your human compare its testimony against the source."

⇒ **与 Cpp_Hub 的"双盲重推导"完全同源**（E2）："**双盲是硬条件: Phase 2 的 auditor 不得接触原推理文本
— 否则锚定效应会把跳步复制一遍**"。

### 3.3 母版三：Open_Data 的审计规则集（可机判部分）

- **单人工作流特义**：**"实施者与验收者是同一人时，P2 是唯一防线——程序化地不信任自己的记忆。"**
- **证据档位 L1/L2/L3** + **"不标注档位 = 默认不可信"** + **"混档是最常见的幻觉形态"**。
- **M1–M5 教训（含审计方自身）**：M2 **审计结论也要标注取证强度**；M5 **审计 subagent 的误判也须入档**。

### 4.2 代码评审的工业标准（一手）

**Google eng-practices（官方）**：

- **"A code review is a process where someone other than the author(s) of a piece of code examines that code."**
  ⇒ **作者不得自审**（定义层面）。
- 评审应看 **8 个维度**：Design / Functionality / Complexity / Tests / Naming / Comments / Style / Documentation。
- **标准（senior principle）**："favor approving a CL once it is in a state where it **definitely improves the
  overall code health**, even if the CL isn't perfect"；**"there is no such thing as 'perfect' code—there is only
  *better* code"**；非必须项加 **`Nit:`** 前缀。
- **"Technical facts and data overrule opinions and personal preferences."**
- **★ "Tests do not test themselves, and we rarely write tests for our tests—a human must ensure that tests are valid."**
- **Reviewers should be especially vigilant about over-engineering.**
- 来源：[eng-practices: The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html) ·
  [What to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html) ·
  [Introduction](https://google.github.io/eng-practices/review/)

**Gerrit / Go / AOSP 的**提交要求**（一手，机制级）**：

| 要求 | 原文要点 |
|---|---|
| **Code-Review** | 每个 CL 须至少一个 **Code-Review+2**；**"The CL owner cannot approve their own CL."** 理由：**"Requiring multiple people ensures that code cannot be submitted unilaterally from a single compromised account."** |
| **No-Unresolved-Comments** | **"CLs must not have any unresolved code review comments."** ⇒ **未解决的意见阻断提交** |
| Review-Enforcement | 须**至少两名 Google 员工**用 Google 安全设备参与（owner 或 +1 投票者） |
| 投票刻度 | `-2`（不应提交）/ `-1`（有问题需修）/ `0` / `+1`（看起来不错，需他人批准）/ `+2`（正确且适合提交）；**`Hold+1` 可在评审继续的同时阻断提交** |
| 意见锚定 | 评审意见**锚定到被高亮的代码行**（line-level） |
| 来源 | [Go Wiki: Gerrit Access](https://go.dev/wiki/GerritAccess) · [AOSP: 对更改进行审核](https://source.android.google.cn/docs/setup/contribute/view-patches?hl=zh-cn) |

⇒ **对 D7 的直接含义**：**"作者不得自审" + "未解决意见阻断" + "意见锚定到行" + "事实优于偏好"
是四条可直接落成机器判据的工业标准**（其中"意见锚定到行"与 Codex `ReviewFinding.code_location` 必填**互相印证**）。

### 4.3 ITIL 4「变更使能」的分阶段权限（E3，多来源一致）

- **ITIL 4 已把 "change management" 改名为 "change enablement"**（重点从"管控"转为"**以风险为基础的快速放行**"）；
  **目标是把不需要的重流程拿掉**（"If your CAB still reviews password policy updates and DNS changes the same way
  it reviews a core database migration, you're running ITIL v3 thinking"）。
- **三类变更 + 风险分级路由**（与 D7 的"分级复核"直接对应）：

| 类型 | 是否逐次批准 | 路由 |
|---|---|---|
| **Standard（标准变更）** | **不**（预授权，一次性批准流程） | 走**标准变更目录**，直接排期 |
| **Normal（常规变更）** | 是（需风险评估 + 批准） | **按风险分级**：低 → 同级评审/组长（**异步，不开会**）；中 → 指定变更授权人/小组；高 → **CAB** |
| **Emergency** | 走**加速路径**但仍有文档与**事后复核** | ECAB / 值班批准人（含 SLA，如 1 小时） |

- **六阶段流程**：`RFC 提交 → 评估（影响/风险/紧迫性）→ 授权 → 排期（变更日历、冲突检查）→ 实施（含 backout plan）→ 复核与关闭（确认达成预期 + 记录教训）`
  ⇒ **"复核与关闭"是独立阶段**，与"实施完成"分开。
- **角色**：change initiator / change manager / **change authority** / change owner。
- **★ 两条最值得抄的**：
  1. **"Write the Change Policy Before You Write the Workflow"** —— 政策 2–4 页，须定义：
     变更范围（什么算/不算）、三类变更如何分类、**角色**、**权威等级（谁能批哪个风险级别）**、争议升级路径、
     **事后复核触发条件**。
  2. **标准变更目录（Standard Change Catalog）** —— **"Every time the CAB approves the same type of change twice,
     someone should ask: 'Should this be a standard change?'"**；中型团队目标 **40–60% 的变更量走标准变更**；
     低于 20% ⇒ "your CAB is doing busy work"。
- 指标：**紧急变更占比 > 10–15% 通常说明是计划问题而非真紧急**。
- 来源：[Motadata: ITIL Change Management Best Practices 2026](https://www.motadata.com/blog/itil-change-management-best-practices) ·
  [opservices: Change Management com ITIL](https://www.opservices.com.br/change-management/) ·
  [ServiceNow Community: ITIL change management](https://www.servicenow.com/community/incident-management-forum/itil-management-in-that-change-management-in-detail-and-their/td-p/3568586)（**二手：厂商/博客，非 ITIL 官方规范**）

⇒ **对 D7 的直接含义**：**"标准变更目录"是缓解 D7 过载的关键机制** —— 否则每一次小复核都走全套 CAB 会
把 D7 变成瓶颈。**D7 应允许"预授权的复核类型"**（如"只读 lint 类复核"免终裁）。

### 4.4 异构多智能体辩论（E3，一手 arXiv/厂商报告）—— **本轮最重要的外部依据**

| 结论 | 出处 |
|---|---|
| **同质 agent 无法稳定优于多数投票**；"Controlled evidence indicates that **homogeneous agents cannot reliably improve over majority voting** (Zhu et al., 2026). We therefore introduce **model heterogeneity**" | [Courtroom-Style MAD (arXiv 2603.28488)](https://arxiv.org/html/2603.28488) |
| **固定轮次辩论会浪费算力，并"amplify correlated errors among similar agents"**；须 **genuine model heterogeneity + agreement-based control** 两者兼备 → 三组件 **PAR（Pre-debate Agreement Routing）/ EASE（Early Agreement Stopping）/ SOD（Semantic Outlier Detection）** | [ARMOR-MAD (arXiv 2606.13197)](https://arxiv.org/html/2606.13197v1) |
| **用"来自不同 provider 的异构模型"而非同模型多实例**（"maximizing cognitive diversity"）；三阶段 **Triage → Parallel Expert Generation → Consensus Synthesis**；**综合阶段显式分类 consensus / disagreement / unique findings，而非简单多数投票**；HaluEval 幻觉率相对降 **35.9%**，TruthfulQA **+7.8 分** | [Council Mode (arXiv 2604.02923v2)](https://arxiv.org/html/2604.02923v2) |
| **角色化为三层：Solvers（产出）/ Reflectors（评估+给权重）/ Orchestrator（统合出指令）**；用 **WISE–Dawid–Skene 无监督概率聚合**按可靠性加权 | [WISE (MERL TR2026-083)](https://www.merl.com/publications/docs/TR2026-083.pdf) |

**★ 对 D7 最硬的一条含义（E4）**：
**本机群三站是同构硬件 + 同批模型族** ⇒ 按上表，三站互审**在"模型家族"维度上是同质的**。
所以：
- **不能把 D7 宣传成"异构互审"** —— 那是自我误认；
- 若真要高价值异构，需**跨模型族**（本地 Qwen / 站上 nemotron / 出站 openrouter 三者跨族）
  —— 这正是 `O-16` 五源异基座**已经在做的**（单机内）；
- **D7 的正确定位 = "独立执行主体 + 能力最小化 + 可审计收束"**，而异构性应由"判官家族路由"补，不由"站点"补。

**另两条直接可用的**：
- **"显式分类 consensus / disagreement / unique findings"**（Council Mode）——
  比"多数投票出一个结论"信息量大得多，**建议直接作为 D7 结论契约的形态**。
- **"Early Agreement Stopping"（EASE）** —— 一致即早停，**直接解决 D7 的"几轮"问题**（不必硬性 N 轮）。
