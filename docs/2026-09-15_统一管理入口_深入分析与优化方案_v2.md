## 1. 回溯：既有管理框架全景

> 这是本方案的立足点。七项管理**不是空白**，而是"**资产齐、入口散、联动缺**"。

### 1.1 治理层（ADR）

| ADR | 决策要点 | 对本方案的硬约束 |
|---|---|---|
| **ADR-0001**（运维框架四改进） | 四缺口=hang 模态检测/网关容灾/参数台账/集群聚合；决策顺序 收尾→重构→聚合→加固 | ⚠️ **"不做第四个面板"**（Cockpit + 静态页够用）；⚠️ **替代方案 A「上报盘式集群平台（Open WebUI/OneAPI）」已被否决** —— 理由"引入新常驻服务与新依赖链，违背**三机预算上限 + 最小运维面**"；⚠️ D2 哲学 = **纯客户端聚合器 + 站内自足** |
| ADR-0002 | 网关 401 根因 → 决策 C「绕网关，fan-out 直连各站引擎」 | LiteLLM 已退役；**无统一入口网关**（有意为之） |
| ADR-0003 | OpenRouter 密钥与 egress 路由管理 | 出站平面已有治理 |

**ADR-0001 §3.4 的边界演进**（2026-09-13 落地）：`cluster.py web`（纯 stdlib + paramiko 自建轻量 UI）**被允许**——因为它是"零外部依赖的自建聚合器"，不是"引入外部平台"。**这条线就是本方案的可行边界**。

### 1.4 硬规则与契约

- **`load-gate`**（内存门禁硬规则）：`used+need+12G≤total`、`avail≥need+12G`、已有 llama RSS 防叠加、loadavg 检查；ABORT 即不可加载
- **哨兵语义**：`RPC_TARGET=auto`（运行时展开 rpc-nodes）；`空值 = 单机`（**语义不可动** — 审计修正 #1）
- **`infer-list` 输出契约**：`ALIAS | 位置 | 大小 | 建议后端 | CONF`
- **`.agent-run.json`**：D6 agent 任务契约
- **口径冻结**：bench `-ngl 999 -t 16 -b 512 --n-cpu-moe 8 -fa on -p 512 -n 128 -r 2`（跨版本可比）
- **证据等级**：E1 本会话实测 / E2 前会话留档 / E3 外部 web / E4 推断

## 3. LM Studio 的可学点（并明确为何不引入其引擎）

### 3.1 为什么不能复用其运行时（性能下降的具体机制）

| 维度 | LM Studio 自带 | 我们现役 | 后果 |
|---|---|---|---|
| 引擎版本 | 打包的 llama.cpp（`~/.lmstudio/extensions/backends/llama.cpp-linux-x86_64-{vulkan,rocm,cuda}-*`，版本随其发行节奏） | `~/llama.cpp/build`（ggml 0.13，HEAD 0d18aaa）/ `/opt/llama.cpp` v0.3.0 —— 由 `vulkan-version-control` + MANIFEST 管控，可按 gfx1151 优化 PR 自行升级 | 版本不可控、与 UPGRADE_SOP 体系冲突 |
| 参数暴露 | GPU offload / ctx / identifier 等有限项 | `-fa on`、`--cache-type-k/v q8_0`、`--n-cpu-moe`、`--fit off`、`-ot` 张量放置等 | **调优参数在 LM Studio 路径上无法表达**（params-ledger 的结论无法复现） |
| 资源 | 独立 server（:1234）+ GUI 进程 + 自身 backend 缓存 | 站内 systemd/infer-load 单实例互斥 + GTT 门禁 | **双栈并存 → GTT 争用**，违反 `load-gate` 单实例硬规则 |
| 与既有编排 | 无 | `infer-load` 互斥 / `wait-gtt-release` / rpccache / RPC 哨兵 | 破坏编排一致性 |

**结论**：接入 LM Studio 运行时 = 用**更差的引擎 + 更少的参数 + 更高的资源争用**，换取一个更漂亮的 UI。**不划算，撤销**。

### 3.2 值得学的：功能与编排设计（可映射到既有体系）

| LM Studio 的设计 | 本质 | 我们的对应物 | 差什么 |
|---|---|---|---|
| 模型库 `lms ls` + **模型详情**（量化/大小/ctx 上限/来源） | 模型"可读的档案" | `infer-list` + `/api/models` + `results-ledger` + `params-ledger` | **档案没在一个界面里汇总** |
| `lms ps` 已加载视图 | 运行态可见 | `probe_station.loaded` | ✅ 已有 |
| **加载即配置**（`--gpu/--context-length/--identifier`） | 实例 = 权重+后端+参数+标识 的不可变描述 | conf（`/etc/llama-instances/<alias>.env`） | **UI 不能改 conf/下发参数** |
| **`--estimate-only` 预估** | 先算再点，失败前置 | `load-gate`（有，但**站内事后**） | **未前置到操作前** |
| **`lms runtime`** 运行时管理 | 多引擎/多后端版本共存与切换 | `vulkan-version-control`（MANIFEST/UPGRADE_SOP）+ HIP/Vulkan 实测结论 | **版本矩阵与切换入口缺** |
| **Idle TTL / auto-evict** | 空闲自动释放 | ❌ 无（"零自加载"是既定方针） | 可选补 |
| 请求日志 `lms log` | 请求级可观测 | ❌（网关退役后无统一请求日志） | 缺 |
| **加载状态机**（未加载→加载中→就绪→服务中→卸载） | 编排的状态语义 | `infer-load`/`unload`/`wait-gtt-release` 已有过程 | **状态未显式化/可视化** |

## 4. 结合当下场景的深入分析

### 4.1 资源与拓扑的硬约束（决定了"什么能做、什么不能做"）

- 三站 **Strix Halo / UMA 128G**，Linux GTT 顶 ~120G → **`load-gate` 的 12G 垫是刚需**（事故换来的）
- USB4 三角环（A-B `10.10.10/24`、B-C `10.10.11/24`、A-C `10.10.12/24`，MTU 9000），**Gen2 20G 实测 9 Gb/s**（A-C 直连 9.46 vs 经 B 35.3 Mb/s，D-5 主备路由不可删）
- **RPC 串行跨链是结构性瓶颈**：单机 decode ≈ 2× 双机 RPC（nemotron 双机 -17.3% = 反例 X2）；tg 20 t/s 的天花板在协议不在算子

### 4.2 双路径战略对管理面的要求（来自 operator-optimization）

| 路径 | 定位 | 管理面要求 |
|---|---|---|
| **容量路径**（双机 RPC，Q4_K_S 121G，tg 20） | Q8 无损 / 397B / 128k 长上下文 | RPC 编排**必须一键化**（当前 exit 2 是断点）；rpccache 热度可视化 |
| **速度路径**（单机 UD-Q3_K_XL 101.8G，预期 29-33） | 交互优先、免疫链路振荡 | 单机加载参数面板 + 快速切换 |
| **决策门**（C3 tg 阈值 28/24） | 决定默认路径 | 需要"路径对比"视图（同一模型两形态的实测对照） |

**推论**：管理入口必须能表达"**同一模型的多种部署形态**"（单机/双机/不同量化），而不只是"一个模型一个按钮"。

### 4.3 加载编排的真实状态机（既有实现映射）

```
[未加载] --infer-load--> [门禁校验 load-gate] --ABORT--> [未加载]（含替代建议）
                              |
                              v 通过
                        [停旧实例+等 wait-gtt-release]
                              |
                              v
                        [起引擎 unsloth/systemd/vLLM] --超时--> [失败+journal 提示]
                              |
                              v
        [就绪 /health or 进程抓名 / READY] --> [服务中] --infer-unload--> [等 GTT 释放] --> [未加载]
```
**关键**：这条链**已完整存在**，缺的是①RPC 形态的接入（第 3 步需先起对端 rpc-server）②状态对用户可见③门禁的"事前预估"。

### 4.4 RPC 编排为何是当前最大缺口（且最容易补）

`cluster-bench` 已把**最难的声明式底座**做好了（`nodes.env` 单一事实源 + `rpc-nodes` 探测/起停 + `b5_bench_cluster` 起→收尾范式）。而 `cmd_load` 的 RPC 分支仍是：
```
[cluster] '{matched}' 为 llama-rpc 双机类模型, 超出单命令边界 (exit 2)。
  手动步骤: 1) A 站 systemctl start rpc-server  2) B 站 infer-load  3) 用毕 infer-unload
```
**这是"零件齐了没装机"** —— 只要把这三步按 `b5_bench_cluster` 的模式串起来即可。

## 5. 优化方案

### 5.1 设计原则（继承 ADR，不越界）

1. **最小运维面**：不新增常驻服务、不引外部平台（Open WebUI/GPUStack/Portainer 一律不引）
2. **纯客户端聚合器 + 站内自足**：主控只做聚合/编排/呈现，**能力长在站上**（`infer-*`/`rpc-nodes`/`load-gate`）
3. **零外部框架依赖**：`cluster_web.py` 继续纯 stdlib + paramiko
4. **台账即真源**：任何界面/命令的展示**必须能回溯到台账**（params-ledger / results-ledger / metrics-log / PLUGIN-LEDGER / TRACKER），不允许 UI 自创数据
5. **学形不学体**：学 LM Studio 的**功能与编排语义**，引擎与参数体系**保持自建**

### 5.2 目标形态

```
                      ┌─────────── 统一门面（唯一入口）───────────┐
                      │  CLI : ops/cluster.py  (+ rpc.ps1 check)   │
                      │  GUI : ops/cluster_web.py（自建，零依赖）   │
                      └──────────────────┬────────────────────────┘
                                         │  共享同一批站上能力
        ┌────────────────────────────────┼────────────────────────────────┐
   ① 可观测面                      ② 编排面                          ③ 数据面
   负载/GPU/引擎指标             加载·卸载·RPC·框架版本            模型库·端口·插件·台账
   → 自动追加 metrics-log        → 复用 infer-load/rpc-nodes        → 复用 lm-download/b5k_sync
   → d1 看门狗联动               → load-gate 前置预估               → 台账单一真源
```

### A.1.1 llama.cpp 原生监控端点 —— **这是我们缺的"可观测面"的现成答案**

**实测（2026-09-15，E1）**：

| 路径 | `/health` | `/metrics` | `/slots` |
|---|---|---|---|
| **A 站 unsloth**（studio 代理后内层 `:53873`） | ✅ `{"status":"ok"}` | ✅ **全套 Prometheus** | ✅ 4 slots，`n_ctx=131072` |
| **B 站 systemd**（`:18080`） | ✅ `{"status":"ok"}` | ⚠️ `501 This server does not support metrics endpoint. Start it with --metrics` | ✅ **开箱可用**（无需参数） |
| A 站 **8080 代理层**（studio） | ❌ `{"detail":"API endpoint not found"}` | ❌ 同上 | ❌ 同上 |

**关键结论**：
1. **`/slots` 零成本可用**（systemd 路径开箱即有）—— 返回 `id / n_ctx / speculative / is_processing`，可做"槽位占用与并发"视图
2. **`/metrics` 只需一个词**：systemd 路径在 conf `EXTRA_FLAGS` 加 `--metrics` 即可；**unsloth 路径 studio 已自动加** `--metrics --slots`，只是代理层不透传 → **直连内层端口**即可
3. **内层端口可运行时抓取**：`ps -eo args | grep 'unsloth/llama.cpp/llama-server' | grep -oE '\-\-port [0-9]+'`
4. **这同时确认了 §4.3 的一个架构事实**：unsloth studio 是**代理层**（这解释了 `/health` 为何 404 —— 不是引擎问题，是 studio 未实现该端点）

**可用指标**（Prometheus exposition）：

| 指标 | 类型 | 用途 |
|---|---|---|
| `llamacpp:tokens_predicted_total` / `prompt_tokens_total` | Counter | 累计 token |
| `llamacpp:prompt_tokens_seconds` / `predicted_tokens_seconds` | **Gauge** | **实时 prefill / decode 吞吐（t/s）** |
| `llamacpp:requests_processing` / `requests_deferred` | Gauge | 并发与排队（背压信号） |
| `llamacpp:n_busy_slots_per_decode` | Counter | 批处理效率 |

→ **P0-4（指标采集）的实现方式就此确定**：不加依赖、不引 exporter，**站内 curl 内层 `/metrics` + `/slots`，主控解析后呈现并追加 `metrics-log`**。

### A.2.1 llama-swap（MIT，单二进制 Go，零运行时依赖）—— **设计参考的最佳样本**

它解决的问题与我们高度同构：**把多个模型暴露在一个 API 后面，按需加载、空闲卸载**。可借鉴点：

| llama-swap 设计 | 语义 | 对我们的映射 |
|---|---|---|
| `cmd` / `cmdStop` | 启动/优雅停止命令 | 与我们 `infer-load` / `infer-unload`（systemctl stop + 等 GTT）同构 ✅ 已是我们的做法 |
| `${PORT}` 宏自动端口分配 | 免手工配端口 | 可补进 `infer-load`（当前 conf 里 PORT 手写，B 站 qwen 用 18080 与 8080 并存易混） |
| **`matrix` + `evict_costs`** | **并发矩阵**（哪些模型可同时跑）+ **驱逐成本**（大模型加载慢→优先保留） | ⚠️ **我们完全缺**。当前是"全局单实例互斥"；若未来要"多 agent 并发用不同模型"，这是现成范式 |
| `ttl` / `globalTTL` | 空闲 N 秒自动卸载 | 可选补（与"零自加载"方针并存，默认关） |
| `metadata`（context_size / quantization） | 模型元数据随 `/v1/models` 暴露 | ✅ 直接补进我们的 `/api/models`（数据已在 GGUF metadata + params-ledger 里） |

| `filters.stripParams` / `setParams` | 服务端强制/剥离采样参数 | 可选（我们目前靠 conf + CLI 纪律） |
| `concurrencyLimit` | 单模型并发上限 | 可选（与 `-np` 联动） |
| `hooks.on_startup.preload` | 启动预加载 | 我们坚持"零自加载"，但可用于"warm"场景 |
| web UI `/ui` + `/logs/stream` + `/metrics` + `POST /api/models/unload` | 一体化运维面 | 我们的 `cluster_web.py` 目标形态（但因 ADR 边界，**不引它的二进制**） |

**⚠️ 为什么不用它的二进制**：
1. ADR-0002 已决策「**绕网关、直连各站引擎**」—— 再引一层代理是**回退**
2. 我们的场景是「**人工按需加载**」（零自加载方针），**不是**「服务端按请求名自动切换」—— 代理层无收益
3. 多一个常驻进程 = 多一个故障点，违背「**最小运维面**」

**保留意见**：若未来出现「**多 agent 并发消费不同模型、要求自动切换**」的场景，llama-swap 是**首选**（优于自研代理）。

## A.3 GGUF 精确内存预估 —— **直接升级 `load-gate`** 🎯

社区已有成熟做法（`gguf_vram_calc.py` 等）：**读 GGUF 架构元数据**，逐项算：

| 组件 | 算法 |
|---|---|
| 模型权重 | 磁盘文件实际大小（对 UD/混合量化最准） |
| **KV cache** | `batch × ctx × 2 × layers × kv_heads × head_dim × bytes_per_value` |
| **SSM recurrent state** | Mamba2 固定状态（**与 ctx 无关**） |
| Vision projector | `--mmproj` 文件大小 |
| Draft/MTP 模型 | `--draft-model` 文件大小 |
| 运行时开销 | 约 0.5–1.5 GB（`-fa` 可减半） |

**输出三态**：`[FITS]` / `[FITS WITH SPILLAGE]`（并算最优 `-ngl`）/ `[DOES NOT FIT]`。

**对我们两个具体价值**：
1. **`load-gate` 升级**：从"文件大小 + 12G 垫"的**粗判**，升级为**基于 GGUF metadata 的精确预估**（含 KV dtype `q8_0`、`-c`、`-np` 的联合影响）→ 支撑 P1-1 的"**事前**预估"
2. **理论补强既有台账**：`params-ledger` §1.1 记录 nemotron「**KV 仅 1G @128k**」但未解释原因 —— 现得到架构解释：**nemotron 是 hybrid SSM/attention（mamba+MoE）**，其 **SSM recurrent state 是固定大小、与上下文长度无关**，所以长 ctx 极廉。这也是它能上 1M ctx 而 KV 不爆的机理。
   → **推论**：对这类模型，"按 KV 线性增长外推"会**严重高估**内存；粗判 gate 可能误拒。

1. **对齐站上 `load-gate` 口径**：`used = total - avail`（**不是** free 的 `total-free-buffers-cached`）

3. 内存读取改用 `/proc/meminfo`（`free` 输出**随 locale 变化** —— 中文表头是「内存：」，曾致结论恒为 UNKNOWN）

|---|---|
| `gpt-oss-120b @ A`（clean） | 权重 59.0 + KV 4.78 + 开销 0.5 = **64.3G**，avail_eff 122.0 → **FITS** |
| `qwen3.8-27b-mtp @ C` | **全注意力层 17 层**（65 ÷ interval 4）→ KV 仅 0.28G，合计 **29.5G** → **FITS** |
| `gpt-oss --ctx 1000000` | KV 4.78 → **36.48G**，合计 96.0G → **TIGHT** |

**踩坑记录（重要）**：首版把 `used` 写成 free 口径、且**漏了 rss 维度**，导致 A 站被误报 `NO_FIT` —— 而当用户指出"负载低不可能"后排查发现：A 站当时有我**测试残留**的 gpt-oss（RSS 62.6G），且 UMA 架构下模型权重表现为 `Cached`。
两条教训：①**预估判据必须与站上硬规则逐条对齐**（不能凭直觉重写）；②**测试后必须清理现场**（残留引擎会污染后续所有判定）。

**对账规则（本次定档，写进 ports.yaml 头部注释）**：
- 无 `scope` = 三站通用；`proto` 缺省 = 两侧都算，`tcp+udp` 表示双栈
- **≥ 32768（`ip_local_port_range` 下界，三站实测一致）的未登记端口一律豁免** —— 该段是内核临时端口，服务每次启动换号
- 方向一（FAIL）：站上在听、端口 < 32768、分配表没有 → 漏登记
- 方向二（WARN）：分配表声明在用却未监听；带 `status` 或 `mode: on_demand` 的豁免

**关键设计判断：为什么"端口号不是真值"**
2026-09-14 把 NFS 的 `mountd/statd` **当次**端口（52591/53517/55723）登记进 `unmanaged`；2026-09-15 复核发现**已全部变化**（本轮 mountd → 33179/43589/…）。故新开 `dynamic` 段，只记 **owner + 段位**，把端口级豁免交给上述段位规则。

**对账首次跑出的真实错误（本项的直接产出）**：

| # | 发现 | 处置 |
|---|---|---|
| 1 | **8090 登记错**：写成 "Beszel agent, scope [A, B]"，实际监听方是 **B 站 `beszel-hub.service`**；A 站的 `beszel-agent` 是**出站**客户端，从不监听 | scope 收敛 `[B]`，owner 改 hub |
| 2 | **137/138/546/5353/3702/6665/724 七类长期监听端口从未登记** | 全部补登（并注明归属进程：nmbd / NetworkManager / avahi / wsdd / netconsole / rpc.statd） |
| 3 | **mihomo 7890/1053 实为 TCP+UDP 双栈**，表里各只登记了单侧 | 改 `proto: tcp+udp`（故为此新增该枚举值） |
| 4 | 52591/53517/55723 已失效 | 移入 `dynamic` 段并记录原由 |

**踩坑记录（我引入的 bug，被自己的门禁抓到）**
1. **YAML 值未加引号**：`note: 2026-09-15 对账修正: 原登记 proto: http …` 含 `: ` → `ScannerError: mapping values are not allowed here`。
2. **更严重的是被掩盖**：初版 `_port_entries()` 把解析异常 `except: return {}` 吞掉 → 整张表变空 → `stations` 随即报出 **40+ 条"端口未登记"的假象**，真正的错因（第 142 行）完全看不到。
   **修复**：`_port_entries()` 改为**解析失败即抛异常**，`check_ports` 直接 FAIL 并显示错误行；`check_stations` 捕获后**跳整段对账**并报真因（绝不用"表读不出"伪造成"一切都没登记"）。
   教训：**降级要显式，不能把"输入坏了"表现成"业务全错"** —— 后者会把排查引向完全错误的方向。
