## 1. 回溯：既有管理框架全景

> 这是本方案的立足点。七项管理**不是空白**，而是"**资产齐、入口散、联动缺**"。

### 1.1 治理层（ADR）

| ADR | 决策要点 | 对本方案的硬约束 |
|---|---|---|
| **ADR-0001**（运维框架四改进） | 四缺口=hang 模态检测/网关容灾/参数台账/集群聚合；决策顺序 收尾→重构→聚合→加固 | ⚠️ **"不做第四个面板"**（Cockpit + 静态页够用）；⚠️ **替代方案 A「上报盘式集群平台（Open WebUI/OneAPI）」已被否决** —— 理由"引入新常驻服务与新依赖链，违背**三机预算上限 + 最小运维面**"；⚠️ D2 哲学 = **纯客户端聚合器 + 站内自足** |
| ADR-0002 | 网关 401 根因 → 决策 C「绕网关，fan-out 直连各站引擎」 | LiteLLM 已退役；**无统一入口网关**（有意为之） |
| ADR-0003 | OpenRouter 密钥与 egress 路由管理 | 出站平面已有治理 |

**ADR-0001 §3.4 的边界演进**（2026-09-13 落地）：`cluster.py web`（纯 stdlib + paramiko 自建轻量 UI）**被允许**——因为它是"零外部依赖的自建聚合器"，不是"引入外部平台"。**这条线就是本方案的可行边界**。

### 1.4 硬规则与契约

- **`load-gate`**（内存门禁硬规则）：`used+need+12G≤total`、`avail≥need+12G`、已有 llama RSS 防叠加、loadavg 检查；ABORT 即不可加载
- **哨兵语义**：`RPC_TARGET=auto`（运行时展开 rpc-nodes）；`空值 = 单机`（**语义不可动** — 审计修正 #1）
- **`infer-list` 输出契约**：`ALIAS | 位置 | 大小 | 建议后端 | CONF`
- **`.agent-run.json`**：D6 agent 任务契约
- **口径冻结**：bench `-ngl 999 -t 16 -b 512 --n-cpu-moe 8 -fa on -p 512 -n 128 -r 2`（跨版本可比）
- **证据等级**：E1 本会话实测 / E2 前会话留档 / E3 外部 web / E4 推断

## 3. LM Studio 的可学点（并明确为何不引入其引擎）

### 3.1 为什么不能复用其运行时（性能下降的具体机制）

| 维度 | LM Studio 自带 | 我们现役 | 后果 |
|---|---|---|---|
| 引擎版本 | 打包的 llama.cpp（`~/.lmstudio/extensions/backends/llama.cpp-linux-x86_64-{vulkan,rocm,cuda}-*`，版本随其发行节奏） | `~/llama.cpp/build`（ggml 0.13，HEAD 0d18aaa）/ `/opt/llama.cpp` v0.3.0 —— 由 `vulkan-version-control` + MANIFEST 管控，可按 gfx1151 优化 PR 自行升级 | 版本不可控、与 UPGRADE_SOP 体系冲突 |
| 参数暴露 | GPU offload / ctx / identifier 等有限项 | `-fa on`、`--cache-type-k/v q8_0`、`--n-cpu-moe`、`--fit off`、`-ot` 张量放置等 | **调优参数在 LM Studio 路径上无法表达**（params-ledger 的结论无法复现） |
| 资源 | 独立 server（:1234）+ GUI 进程 + 自身 backend 缓存 | 站内 systemd/infer-load 单实例互斥 + GTT 门禁 | **双栈并存 → GTT 争用**，违反 `load-gate` 单实例硬规则 |
| 与既有编排 | 无 | `infer-load` 互斥 / `wait-gtt-release` / rpccache / RPC 哨兵 | 破坏编排一致性 |

**结论**：接入 LM Studio 运行时 = 用**更差的引擎 + 更少的参数 + 更高的资源争用**，换取一个更漂亮的 UI。**不划算，撤销**。

### 3.2 值得学的：功能与编排设计（可映射到既有体系）

| LM Studio 的设计 | 本质 | 我们的对应物 | 差什么 |
|---|---|---|---|
| 模型库 `lms ls` + **模型详情**（量化/大小/ctx 上限/来源） | 模型"可读的档案" | `infer-list` + `/api/models` + `results-ledger` + `params-ledger` | **档案没在一个界面里汇总** |
| `lms ps` 已加载视图 | 运行态可见 | `probe_station.loaded` | ✅ 已有 |
| **加载即配置**（`--gpu/--context-length/--identifier`） | 实例 = 权重+后端+参数+标识 的不可变描述 | conf（`/etc/llama-instances/<alias>.env`） | **UI 不能改 conf/下发参数** |
| **`--estimate-only` 预估** | 先算再点，失败前置 | `load-gate`（有，但**站内事后**） | **未前置到操作前** |
| **`lms runtime`** 运行时管理 | 多引擎/多后端版本共存与切换 | `vulkan-version-control`（MANIFEST/UPGRADE_SOP）+ HIP/Vulkan 实测结论 | **版本矩阵与切换入口缺** |
| **Idle TTL / auto-evict** | 空闲自动释放 | ❌ 无（"零自加载"是既定方针） | 可选补 |
| 请求日志 `lms log` | 请求级可观测 | ❌（网关退役后无统一请求日志） | 缺 |
| **加载状态机**（未加载→加载中→就绪→服务中→卸载） | 编排的状态语义 | `infer-load`/`unload`/`wait-gtt-release` 已有过程 | **状态未显式化/可视化** |

## 4. 结合当下场景的深入分析

### 4.1 资源与拓扑的硬约束（决定了"什么能做、什么不能做"）

- 三站 **Strix Halo / UMA 128G**，Linux GTT 顶 ~120G → **`load-gate` 的 12G 垫是刚需**（事故换来的）
- USB4 三角环（A-B `10.10.10/24`、B-C `10.10.11/24`、A-C `10.10.12/24`，MTU 9000），**Gen2 20G 实测 9 Gb/s**（A-C 直连 9.46 vs 经 B 35.3 Mb/s，D-5 主备路由不可删）
- **RPC 串行跨链是结构性瓶颈**：单机 decode ≈ 2× 双机 RPC（nemotron 双机 -17.3% = 反例 X2）；tg 20 t/s 的天花板在协议不在算子

### 4.2 双路径战略对管理面的要求（来自 operator-optimization）

| 路径 | 定位 | 管理面要求 |
|---|---|---|
| **容量路径**（双机 RPC，Q4_K_S 121G，tg 20） | Q8 无损 / 397B / 128k 长上下文 | RPC 编排**必须一键化**（当前 exit 2 是断点）；rpccache 热度可视化 |
| **速度路径**（单机 UD-Q3_K_XL 101.8G，预期 29-33） | 交互优先、免疫链路振荡 | 单机加载参数面板 + 快速切换 |
| **决策门**（C3 tg 阈值 28/24） | 决定默认路径 | 需要"路径对比"视图（同一模型两形态的实测对照） |

**推论**：管理入口必须能表达"**同一模型的多种部署形态**"（单机/双机/不同量化），而不只是"一个模型一个按钮"。

### 4.3 加载编排的真实状态机（既有实现映射）

```
[未加载] --infer-load--> [门禁校验 load-gate] --ABORT--> [未加载]（含替代建议）
                              |
                              v 通过
                        [停旧实例+等 wait-gtt-release]
                              |
                              v
                        [起引擎 unsloth/systemd/vLLM] --超时--> [失败+journal 提示]
                              |
                              v
        [就绪 /health or 进程抓名 / READY] --> [服务中] --infer-unload--> [等 GTT 释放] --> [未加载]
```
**关键**：这条链**已完整存在**，缺的是①RPC 形态的接入（第 3 步需先起对端 rpc-server）②状态对用户可见③门禁的"事前预估"。

### 4.4 RPC 编排为何是当前最大缺口（且最容易补）

`cluster-bench` 已把**最难的声明式底座**做好了（`nodes.env` 单一事实源 + `rpc-nodes` 探测/起停 + `b5_bench_cluster` 起→收尾范式）。而 `cmd_load` 的 RPC 分支仍是：
```
[cluster] '{matched}' 为 llama-rpc 双机类模型, 超出单命令边界 (exit 2)。
  手动步骤: 1) A 站 systemctl start rpc-server  2) B 站 infer-load  3) 用毕 infer-unload
```
**这是"零件齐了没装机"** —— 只要把这三步按 `b5_bench_cluster` 的模式串起来即可。

## 5. 优化方案

### 5.1 设计原则（继承 ADR，不越界）

1. **最小运维面**：不新增常驻服务、不引外部平台（Open WebUI/GPUStack/Portainer 一律不引）
2. **纯客户端聚合器 + 站内自足**：主控只做聚合/编排/呈现，**能力长在站上**（`infer-*`/`rpc-nodes`/`load-gate`）
3. **零外部框架依赖**：`cluster_web.py` 继续纯 stdlib + paramiko
4. **台账即真源**：任何界面/命令的展示**必须能回溯到台账**（params-ledger / results-ledger / metrics-log / PLUGIN-LEDGER / TRACKER），不允许 UI 自创数据
5. **学形不学体**：学 LM Studio 的**功能与编排语义**，引擎与参数体系**保持自建**

### 5.2 目标形态

```
                      ┌─────────── 统一门面（唯一入口）───────────┐
                      │  CLI : ops/cluster.py  (+ rpc.ps1 check)   │
                      │  GUI : ops/cluster_web.py（自建，零依赖）   │
                      └──────────────────┬────────────────────────┘
                                         │  共享同一批站上能力
        ┌────────────────────────────────┼────────────────────────────────┐
   ① 可观测面                      ② 编排面                          ③ 数据面
   负载/GPU/引擎指标             加载·卸载·RPC·框架版本            模型库·端口·插件·台账
   → 自动追加 metrics-log        → 复用 infer-load/rpc-nodes        → 复用 lm-download/b5k_sync
   → d1 看门狗联动               → load-gate 前置预估               → 台账单一真源
```

### 5.3 分期项（每项都标注"学自何处"与"复用何资产"）

#### P0（体验与正确性）

| 项 | 内容 | 学自 | 复用 |

### A.1.1 llama.cpp 原生监控端点 —— **这是我们缺的"可观测面"的现成答案**

**实测（2026-09-15，E1）**：

| 路径 | `/health` | `/metrics` | `/slots` |
|---|---|---|---|
| **A 站 unsloth**（studio 代理后内层 `:53873`） | ✅ `{"status":"ok"}` | ✅ **全套 Prometheus** | ✅ 4 slots，`n_ctx=131072` |
| **B 站 systemd**（`:18080`） | ✅ `{"status":"ok"}` | ⚠️ `501 This server does not support metrics endpoint. Start it with --metrics` | ✅ **开箱可用**（无需参数） |
| A 站 **8080 代理层**（studio） | ❌ `{"detail":"API endpoint not found"}` | ❌ 同上 | ❌ 同上 |

**关键结论**：
1. **`/slots` 零成本可用**（systemd 路径开箱即有）—— 返回 `id / n_ctx / speculative / is_processing`，可做"槽位占用与并发"视图
2. **`/metrics` 只需一个词**：systemd 路径在 conf `EXTRA_FLAGS` 加 `--metrics` 即可；**unsloth 路径 studio 已自动加** `--metrics --slots`，只是代理层不透传 → **直连内层端口**即可
3. **内层端口可运行时抓取**：`ps -eo args | grep 'unsloth/llama.cpp/llama-server' | grep -oE '\-\-port [0-9]+'`
4. **这同时确认了 §4.3 的一个架构事实**：unsloth studio 是**代理层**（这解释了 `/health` 为何 404 —— 不是引擎问题，是 studio 未实现该端点）

**可用指标**（Prometheus exposition）：

| 指标 | 类型 | 用途 |
|---|---|---|
| `llamacpp:tokens_predicted_total` / `prompt_tokens_total` | Counter | 累计 token |
| `llamacpp:prompt_tokens_seconds` / `predicted_tokens_seconds` | **Gauge** | **实时 prefill / decode 吞吐（t/s）** |
| `llamacpp:requests_processing` / `requests_deferred` | Gauge | 并发与排队（背压信号） |
| `llamacpp:n_busy_slots_per_decode` | Counter | 批处理效率 |

→ **P0-4（指标采集）的实现方式就此确定**：不加依赖、不引 exporter，**站内 curl 内层 `/metrics` + `/slots`，主控解析后呈现并追加 `metrics-log`**。

### A.2.1 llama-swap（MIT，单二进制 Go，零运行时依赖）—— **设计参考的最佳样本**

它解决的问题与我们高度同构：**把多个模型暴露在一个 API 后面，按需加载、空闲卸载**。可借鉴点：

| llama-swap 设计 | 语义 | 对我们的映射 |
|---|---|---|
| `cmd` / `cmdStop` | 启动/优雅停止命令 | 与我们 `infer-load` / `infer-unload`（systemctl stop + 等 GTT）同构 ✅ 已是我们的做法 |

| `filters.stripParams` / `setParams` | 服务端强制/剥离采样参数 | 可选（我们目前靠 conf + CLI 纪律） |
| `concurrencyLimit` | 单模型并发上限 | 可选（与 `-np` 联动） |
| `hooks.on_startup.preload` | 启动预加载 | 我们坚持"零自加载"，但可用于"warm"场景 |
| web UI `/ui` + `/logs/stream` + `/metrics` + `POST /api/models/unload` | 一体化运维面 | 我们的 `cluster_web.py` 目标形态（但因 ADR 边界，**不引它的二进制**） |

**⚠️ 为什么不用它的二进制**：
1. ADR-0002 已决策「**绕网关、直连各站引擎**」—— 再引一层代理是**回退**

**保留意见**：若未来出现「**多 agent 并发消费不同模型、要求自动切换**」的场景，llama-swap 是**首选**（优于自研代理）。

## A.3 GGUF 精确内存预估 —— **直接升级 `load-gate`** 🎯

社区已有成熟做法（`gguf_vram_calc.py` 等）：**读 GGUF 架构元数据**，逐项算：

| 组件 | 算法 |
|---|---|
| 模型权重 | 磁盘文件实际大小（对 UD/混合量化最准） |
| **KV cache** | `batch × ctx × 2 × layers × kv_heads × head_dim × bytes_per_value` |
| **SSM recurrent state** | Mamba2 固定状态（**与 ctx 无关**） |
| Vision projector | `--mmproj` 文件大小 |
| Draft/MTP 模型 | `--draft-model` 文件大小 |
| 运行时开销 | 约 0.5–1.5 GB（`-fa` 可减半） |

**输出三态**：`[FITS]` / `[FITS WITH SPILLAGE]`（并算最优 `-ngl`）/ `[DOES NOT FIT]`。

**对我们两个具体价值**：
1. **`load-gate` 升级**：从"文件大小 + 12G 垫"的**粗判**，升级为**基于 GGUF metadata 的精确预估**（含 KV dtype `q8_0`、`-c`、`-np` 的联合影响）→ 支撑 P1-1 的"**事前**预估"
2. **理论补强既有台账**：`params-ledger` §1.1 记录 nemotron「**KV 仅 1G @128k**」但未解释原因 —— 现得到架构解释：**nemotron 是 hybrid SSM/attention（mamba+MoE）**，其 **SSM recurrent state 是固定大小、与上下文长度无关**，所以长 ctx 极廉。这也是它能上 1M ctx 而 KV 不爆的机理。
   → **推论**：对这类模型，"按 KV 线性增长外推"会**严重高估**内存；粗判 gate 可能误拒。

### P1-6 收尾：`infer-list` 重写 —— ✅ 已落地并验证

`infer-list` 是站上最常用的模型清单工具（手册把它当作标准入口），但上面两条让它在三站场景下不可信。重写要点：

| 问题 | 旧实现 | 新实现 |
|---|---|---|
| 落点形态 | `find -mindepth 2 -maxdepth 2 -type d` 找**模型目录** → 漏掉 `gguf/<repo>/<file>.gguf` | 改从 **gguf 文件**分组（`NF==2 → 模型=repo`），与主控侧 `cluster.group_by_model` **同一规则** |
| 本站判定 | 写死"本站 = B" | 由 `hostname -s` 判定（`scott-lau-NEX`→A / `scott-lau-GTR-Pro`→B / `seaviv`→C） |
| 对端寻址 | `ssh scott-lau@scott-lau-NEX.local`（`.local`） | **管理网 IP**（`.local` 实测站间解析不可靠；首次连接还会因 host key 未收录直接失败） |
| 对端口径 | 内联一份**手抄的** find（正是它漏形态的原因） | 把 `scan()` 的定义用 `declare -f` **原样送过去执行**，两端口径不可能漂移 |
| 取不到对端 | 静默返回空 → 表现为"该站没有这些模型" | **显式告警**（表末列出未取到的站 + 排查命令），位置列不含它 |
| 指定对端 | 无此能力 | `infer-list [A\|B\|C ...]`；**自动剔除本站**（ssh 自己会因 host key 未收录而报假失败） |
| 位置语义 | `AB` / `A-only` / `B`（两段逻辑拼出） | 拥有该别名的**站代号串**（`ABC` / `AB` / `BC` / `A` / `C`），单循环产出 |
| 大小 | 一律 `sz/1024` → 24MB 的 embedding 显示成 `0G` | `<1024MB` 显示 MB |

**踩坑（我引入的，写完自查发现）**：对端扫描最初写成
`ssh host bash -s <<EOF … $(declare -f scan) … EOF` —— **非引用型 heredoc 会在本地展开函数体里的 `$d`/`$full`/`$(…)`**，送过去就成了坏函数。改为先把 payload 存进变量再 `printf | ssh host bash -s`。

**补做：站间免密与寻址（2026-09-15 同日收口）**

`infer-list` 要跨站取数，就必须先让"站间 ssh"本身成立。核对后发现两件事：

| 项 | 实测结论 | 处置 |
|---|---|---|
| **A→C 免密** | A 的公钥**从未下发**到 C（C 的 `authorized_keys` 只有 github 与 B 站两把 key）→ `Permission denied (publickey,password)`。C 的 sshd 侧无需改动（`pubkeyauthentication yes` / `authorizedkeysfile .ssh/authorized_keys` 已就绪） | 主控站对 C 已有免密，**经主控站直接下发** A 的 `id_rsa.pub`（带 `authorized_keys.bak-20260915` 备份 + `grep -qF` 幂等 + 700/600 权限）。**未使用** `tmp/deploy_key.py` 的 pexpect 方案——那条路要处理 C 站的明文密码 |

### P2-1 `flow` 通用化 —— ✅ 已落地并验证（**端到端真跑过一次真实基准**）

**定位**：把"一次操作要走的一串步骤"从散落的一次性脚本收敛成**声明式表** —— 每个 flow 声明「**步骤 → 判据 → 台账落点**」，一次跑完并留下记录。范式取自 `b5_bench_cluster.sh` 的五段式（读声明 → 起依赖 → 执行 → **无条件收尾** → 落账）。

| 内置 flow | 步骤 | 判据 | 默认 |
|---|---|---|---|
| `verify` | 健康引擎 9 项断言 | 全 PASS | **执行**（只读） |
| `bench` | 定位在服务的引擎 → 确保就绪 → 标准请求取 timings | 有引擎端口 / 预估非 NO_FIT / HTTP 200 且含 timings | 计划（`--go` 执行） |
| `swap` | 事前预估 → 按站加载 → 就绪复核 | FITS·TIGHT / `cmd_load_on` rc=0 / `llama=READY` 且有端口 | 计划 |
| `rotate` | 凭据巡检 → 明文门禁 → 下发正本 | 三站 verdict OK / 命中 0 / push rc=0 | 计划 |

**三条设计约定（都对齐既有纪律）**
1. **只读 flow 默认执行；会改站上状态的一律默认只出计划，`--go` 才动手**（沿用 `models link|prune` 的 dry-run 约定）
2. 判据既写进 `run()` 也用 `criteria` 字符串**声明出来** —— `flow list` / `flow <name> --plan` 会把"步骤→判据"整表打印，跑之前就知道要满足什么
3. 任一步不达标 **fail-fast**（中止后续步骤），flow 若加载过则执行已登记的 **teardown**

**台账写入器（净新增件）**：查证过三份台账，**在此之前没有任何脚本写它们** —— `b5_bench_cluster.sh` 只 `echo` 到 stdout（其 DESIGN 声称"自动追加 metrics-log"从未落地），手册也写了"结果自动追加到 metrics-log"，属**空头承诺**。本次补上：`_ledger_append()` 只增不改、缺节则补节与表头、每条必带 **日期 / 判据(口径) / 证据** 三要素（metrics-log 既有教训）。
**刻意只挂 metrics-log**：params-ledger 的表是「参数变更」、results-ledger 是「模型评测」（按模型分节 + 题号表），各有专属 schema —— 由脚本往别人的表里塞异构行会写坏它。另两份台账保持人工维护（不假装支持）。

### P2-3 引擎请求/token 统计 —— ✅ 已落地并验证（**口径错误被实测抓出并修正**）

**形态**：站上采样 + 主控聚合。站上 `reqlog sample` 读 llama.cpp 原生 `/metrics` + `/slots`，与上一条样本**差分**，追加一行 JSONL 到 `~/.local/share/rpc/reqlog.jsonl`；主控（CLI + Web）读回原文聚合。

**也不伪造"请求数"**：实测 `/metrics` **没有 requests 计数器**（只有 `requests_processing` / `requests_deferred` 两个 gauge）→ 汇总里显式说明并留空，不拿 `n_decode_total` 冒名顶替。

`prompt_tokens_total` / `prompt_tokens_cached_total` / `prompt_seconds_total` / `tokens_predicted_total` / `tokens_predicted_seconds_total` / `n_decode_total` / `n_tokens_max` / `spec_decode_num_{draft,accepted,drafts}_tokens_total` / `prompt_tokens_seconds` / `predicted_tokens_seconds` / `requests_processing` / `requests_deferred` / `n_busy_slots_per_decode`

**⚠ 口径错误（本项最大产出，实测抓出）**
首版用 `Δtoken / Δ采样间隔` 当吞吐 → 实测得 **tg 32.0 t/s**，而同一请求的 API `timings` 是 **67.6 t/s**，**差 2 倍**。根因：墙钟间隔里含引擎空闲（那 4 秒只有 ~1.9 秒在真正生成）。
修正：站上其实有 `prompt_seconds_total` / `tokens_predicted_seconds_total`（**引擎自报的计算耗时**）→ 正确口径是 **`ΣΔtoken / ΣΔ引擎耗时`**。修正后：

| 口径 | pp t/s | tg t/s | 与 API timings 对比 |
|---|---|---|---|
| API 响应 `timings`（基准） | 990.6 | 67.6 | — |
| **引擎耗时口径（主）** | **992.0** | **68.1** | **差 <1%** ✅ |
| 墙钟口径（辅，含空闲） | 117.0 | 32.0（忙占比 0.47） | 被空闲稀释 —— 只作辅助 |

两个口径**并列暴露**（不是二选一），并用 `*_busy = Δ引擎耗时/Δ采样间隔` 解释差异。聚合一律**加权**（ΣΔtoken / ΣΔ耗时），不逐条平均比值（短样本会把比值带偏）。

### P2-4 路径对比视图（单机 vs 双机，决策门）—— 已落地；双机 RPC 回退已修，对照首次有效

**交付**：新增 `flow paths <alias> [--go]` —— 同一模型在两条路径上各做一次实测基准，输出对照表 + 推荐 + 落账。步骤：`单机事前预估 → 单机实测 → 双机 RPC 实测 → 对照与推荐`。

**两处框架扩展（都是被这次实测逼出来的）**
1. **`continue_on_fail`**：对比类 flow **刻意不 fail-fast** —— 某条路径跑不通本身就是决策所需的信息。中间步骤失败记 `PARTIAL`（跑完了、有结论），**最后一步（对照/报告）失败才算 `FAIL`**。
2. **双机侧不给"事前预估"**：`estimate_load` 的口径是"整个模型落在一站"，而 RPC 会把层拆到两站 —— 拿单站口径套双机会得出错误结论。与其编一个看似精确的粗判数字，不如只给单机的精确预估 + 双机的**实测**。

**⚠ 三个真实发现（本项最大产出）**

| # | 发现 | 证据 | 处置 |
|---|---|---|---|
| 1 | **`infer-load` 的 `--backend` 不彻底**：只切 `BACKEND`，**不清 conf 的 `RPC_TARGET`** → `--backend llama-single` 仍会拉起 A 站 rpc-server 并带 `--rpc`，**名义"单机"实际"双机"** | 单机路径加载日志出现 `A 站起 rpc-server@...` | **已修**：显式 `--backend` 现在同时决定 RPC 与否（`llama-rpc` → `RPC_TARGET` 置 auto；其他 → 清空并打印"真正走单机"）。用 11MB 的 `rpc=auto` 模型三向验证：单机不含 `--rpc` ✓ / `llama-rpc` 含 ✓ / 缺省按 conf 走 ✓ |
| 2 | **判据不能只看"以为选了什么"** | 上一条正是被判据缺失放过的 | **已加后端生效性判据**：读 `/proc/<pid>/cmdline` **全文**判断有没有 `--rpc`，不符即判"该路径未按请求生效，**数据不可用于对照**"，不再进台账 |
| 3 | **内存代价测法错误（连错两次）**：① `MemAvailable` 差值 → 77G 模型显示"+0.1G"；② 改进程 RSS → 仍只 0.2G | UMA (AMD 8060S) 下权重驻留 **GTT**，**不进进程 RSS** —— 77G 模型实测 `ps` RSS 仅 **217MB** 而 GTT **54.6GB** | **已改用 GTT**（新增 `_station_gtt_gib`，与站上 `load-gate` 门禁同口径）；对照表内存列 = **GTT 增量**（单机 +77.2G / 双机 +41.7G） |

**判据自身的两个坑（都实测踩到）**
- `pgrep -af 'llama-server'` 会**匹配到执行它的 `bash -c` 包装进程本身** → `head -1` 拿到的是 bash 的命令行，判据直接失效。改用 `pgrep -x`（按进程名精确匹配）→ 不对自匹配。
- **不能截断命令行**：`--rpc` 出现在很长的命令行靠后位置，截前 120 字符会漏判（我第一版测试脚本就因此误报）→ 必须读 `/proc/<pid>/cmdline` 全文。

**⚠ 双机 RPC "静默回退"的三个真因（已全部定位并修复）**

表象：双机路径"加载看起来成功"，实际是 master 单机在跑（命令行里没有 `--rpc`），而 `/health` 照样通过。
三个真因**都在"静默回退"这条链上，缺一即可复现**：

| # | 真因 | 决定性证据 | 修法 |
|---|---|---|---|
| ① | **身份错**：`infer-load` 由 `sudo` 拉起 ⇒ 以 **root** 执行 ssh，而 root 的 `~/.ssh` 无节点密钥；脚本是 `set -uo pipefail`（**没有 `-e`**）⇒ 失败**不中断也不报错** | 同一命令：root 身份 ssh → `Host key verification failed.`；服务用户身份 ssh → `rc=0` | `sudo -u <服务用户> rpc-nodes --start <alias>`；**拿不到节点 `exit 7`**（拒静默回退） |
| ② | **没等端口**：`RPC_TARGET=auto` 的展开原为**单次探测、无重试** | 端口未监听时 `/dev/tcp` 连接被**立即拒绝**（不是等 2s 超时）；实测节点 bind 仅 **1.06s**、`rpc-nodes` 探测 0.2s ⇒ 窗口窄但非零 | 改用自带 `wait_port`(15×2s) 且按 `nodes.env` 启动**全部**节点的 `rpc-nodes --start` |
| ③ | **systemd 单元重新读 conf**：单机路径起的是**单元** `llama-server@<alias>`，单元里的 `llama-serve-instance` 会**重新 source conf** ⇒ `infer-load` 清掉自己 shell 的 `RPC_TARGET` **对单元无效**，conf 的 `RPC_TARGET=auto` 照样让单元带上 `--rpc` | `flow paths` 的后端生效性判据直接抓到：`✕ 单机: 后端未生效 —— 请求 llama-single, 但进程含 --rpc`。此前"单机无 --rpc"的验证是**假通过**（当时节点恰好没起，单元静默回退成单机） | **运行时覆盖层**：`infer-load` 显式指定后端时写 `/run/llama-instances/<alias>.env`（tmpfs，重启自清），`llama-serve-instance` 在 `source "$CONF"` **之后**再 source 一次；未显式指定后端则删除该文件，回归 conf 语义 |

⚠ **真因③ 的教训（比 bug 本身更重要）**：**"改了某个 shell 的变量" ≠ "改了最终进程的参数"** ——
中间隔着一层 systemd 单元 + 重新 source 的 conf。判据必须看**最终进程的命令行**，
而不是看"我以为传下去的那个值"（这正是本轮给 `flow paths` 加后端生效性判据的价值）。

**验证（两层，都做完）**
- **wrapper 级 4/4**（秒级，不起真模型）：无覆盖时 `auto` 仍照常展开（防改坏原语义）/ 覆盖为空 ⇒ 不含 `--rpc` / 覆盖 `auto` ⇒ 照常展开 / 覆盖内容有显式日志可观测。
- **端到端**（`flow paths gpt-oss-120b-fable-5-distilled --go`，两次）：

| 路径 | 后端生效 | pp / tg | 加载 | GTT 增量 |
|---|---|---|---|---|
| 单机 | `rpc=否` ✓ | 244.2 t/s / **36.7 t/s** | 108.6s | +77.2G |
| 双机 RPC | `rpc=是(10.10.10.1:50052,10.10.11.3:50052)` ✓ | 218.1 t/s / 27.1 t/s | 121.4s | +41.7G |

⇒ 该模型**推荐单机**（双机 decode 仅 27.1，且加载更慢）；双机的价值在**省单站内存**（+41.7G vs +77.2G），
不在提速。台账见 `spec/rpc-optimization/metrics-log.md` Phase 7 的 19:56 行与其后「更正说明二」。

**顺带修掉的两处缺陷（都是"这次真跑了双机"才暴露的）**
1. **`_flow_path_measure` 的返回串引用改名前的键** `mem_used_gib`（RSS→GTT 改名时漏改）→ 每次实测
   都以 `KeyError` 收尾、步骤被记成失败（19:51 那行 `PARTIAL` 即此）。**数值本身是有效的** ——
   这只是记账错误，但足以让"数据可信"的流程输出假 FAIL。
2. **`infer-unload` 只停 A 站的 rpc-server**（硬编码 `AWORK`）：C 站 2026-09-15 起也是 worker
   （`nodes.env` 的 `RPC_NODES` 声明 A + C）⇒ 每轮双机加载都会在 C 留下**常驻** `rpc-server@<alias>`，
   让集群门禁 `engine` 项长期黄灯（实测 "C 站引擎在服务: 端口 50052 / 有端口在听但 RSS 仅 121M"）。
   修法：① **本站就地停**（不经 ssh —— 自 ssh 到本机 USB4 IP 会 host key 失败，A/C 实测都踩到）；
   ② **master 侧按 `nodes.env` 停远端全部 worker**（清单来自 `rpc-nodes --all`，不在脚本里再抄一份 IP）；
   非 master 站没有 `nodes.env` 属正常，**静默跳过而不报 WARN**（否则常规 unload 看起来像出错）。
   验：起 A+C 节点（2 个 active）→ 只跑 B 站 unload → A=0 / C=0；三站全量 unload → A=0 / C=0，
   门禁 `engine` 由黄转绿（11 绿 / 1 黄 / 0 红）。

**台账纪律的一处修补**：验证过程中负向测试跑出的 `FAIL` 行落进了 metrics-log（17:47）。已给 flow 加 **`--no-ledger`**（跑了但不落账，供负向测试/试跑用）。原行按"只增不改"保留，并在表下追加**更正说明**（同时标注 18:14 的 paths 行数据无效、不可用于决策）。

**收尾核验**：三站 `0` 引擎端口 / `0` RSS / rpc-server 全 `inactive`（无残留）。

### P2-5 空闲 TTL 自动卸载 —— ✅ 已落地并端到端验证（**默认关**）

**定位**：引擎加载后长期没人用 → 一直占着 GTT。本项给一个**可选的**空闲释放机制，与"**零自加载**"方针并存：
TTL 只**释放**已加载的资源，**从不**加载任何模型。语义对齐 llama-swap 的 `ttl`（空闲 N 秒即卸载）。

**交付物（三处，各管一层）**

| 层 | 件 | 职责 |
|---|---|---|
| 站上 | `ops/station-bin/cluster-ttl`（+ `/etc/llama-instances/ttl.env`） | 判定 + 执行 + 留证；`--status` 只读、`--dry-run` 强制演练、`--set KEY=VAL` 改 conf |
| 站上 | `ops/cluster-ttl.service` + `cluster-ttl.timer`（60s oneshot，复用 `d1` timer 框架） | 周期触发；**部署即 disabled**，显式 `enable --now` 才生效 |
| 主控 | `cluster.py ttl {status\|check\|enable\|disable}` | 三站聚合视图 / 立刻判一次 / 写 conf + 开关 timer |
| 主控 | `cluster_web.py` 的 `GET /api/ttl` + `POST /api/ttl-toggle` + 页面卡片 | 一屏看状态、一键开关（含二次确认） |

**七个设计决策（每条都在防一类具体的错）**

| # | 决策 | 不这样做会怎样 |
|---|---|---|
| 1 | **空闲判据 = 累计计数器差分**（`prompt_tokens_total` / `tokens_predicted_total` / `*_cached_total`） | llama.cpp `/metrics` **没有**"最后请求时间"这种东西（P2-3 已核实）；拿 `/slots` 或连接数当活跃信号都是猜 |
| 2 | **判据缺失就不动作**：`/metrics` 无输出或计数器缺失 ⇒ 打印"无法判定空闲"并退出 | 否则会用别的信号冒名顶替 —— 那是"静默换判据"，比不动作危险 |
| 3 | **绝不打断在途请求**：`requests_processing>0` 或 `/slots` 有 busy 槽位 ⇒ 视为活跃 | 空闲阈值到点正好撞上长生成 → 把正在跑的推理砍了 |
| 4 | **实例身份（pid）变了 / 计数器下降 ⇒ 空闲时钟重新起算** | 把上一个实例的时钟套到新实例上 → 刚加载完就被判"空闲 6 小时"立刻卸掉 |
| 5 | **卸载走 `infer-unload`**（不是自己 `systemctl stop`） | 它是本集群唯一的正规卸载路径，会一并停掉 RPC worker；自己 stop 会在 worker 上留残留（P2-4 刚修过） |
| 6 | **默认关**；关闭时**降级为"演练"**（照常判定并打印结论，但绝不卸载）；另有 `TTL_DRY_RUN=1` 与 `check --go` 两级闸门 | "默认开"会与"零自加载"方针下的使用习惯冲突；而没有演练档，上线前无法观察它到底会不会误判 |
| 7 | **动作必须留证**：每次判定打印 `pid / 在途 / Δtok / idle / 阈值`，卸载前后各留一行，并写进 `state.json` 的 `last_action`（+ journald） | 自动卸载一旦发生，"谁在什么时候被卸了、依据是什么"必须能直接回答 —— 否则就是个不可审计的暗杀器 |

**验证证据（E12，2026-09-15 20:56-20:59，B 站 `gpt-oss-20b` @ `llama-single` :8080）**

| # | 用例 | 结果 |
|---|---|---|
| 1 | **负向**: 总开关关（默认）+ 阈值 3s，idle 已 5s ⇒ 只演练 | ✓ `TTL 到期 —— [演练] 本应执行 infer-unload`，引擎 pid 不变，`last_action.result=dry-run` |
| 2 | **负向**: 在途请求（`max_tokens=400`）时判定 | ✓ `在途=1 busy槽=1 Δtok=78.0 → 活跃`，**未卸载**；请求跑完引擎仍在 |
| 3 | **正演**: 真开 + 阈值 3s，由 **timer** 自动卸载 | ✓ 开启后 **62s** 自动卸载：`idle 60s ≥ 3s → 执行 infer-unload` → `rc=0 · 卸载后引擎=已停 · GTT 12.5G → 0.3G` |
| 4 | 证据链 | ✓ `state.json.last_action = {idle_s:60, ttl_s:3, delta_tokens:0.0, result:"unloaded", unload_rc:0}`；journald 有判定行 + 卸载行 + `infer-unload` 的收尾行（含两个 RPC worker） |

**⚠ 一条测试自身的教训（代码是对的，错的是测试）**

起因：想给站上那批**无扩展名**脚本（`infer-load` / `infer-unload` / `cluster-ttl` / `reqlog` …）
补语法覆盖 —— 它们一个都不在 `.py/.ps1/.sh/.json` 之内，即**从不过门禁**。
补完做负向验证（往已跟踪脚本注入语法错）时，门禁**仍然报 PASS**。追查如下：

| 事实 | 证据 |
|---|---|
| PATH 上的 `bash` 是 **WSL**（`C:\Windows\system32\bash.EXE`） | `test -f "D:\RPC\...\infer-load"` → `INVISIBLE` |
| 该 bash 读不到仓库路径 ⇒ `bash -n` 对它等于"文件不存在" | `ls` → `No such file or directory` |
| 在这种 bash 下注入语法错**不会被报出** | 往 tracked `.sh` 与 tracked 无扩展名脚本各注入一次 → `.sh:447文件/0失败` 不变 |
| `C:\Program Files\Git\bin\bash.exe`（5.2.37）能读到两种路径形式 | `test -f` → `WIN_OK` / `POSIX_OK` |

**修法（四处，缺一仍会静默出错）**
1. **显式选 bash 并实测它读得到仓库**：候选 = PATH 上的 + Git for Windows 三个常见落点，
   用**真实仓库 .sh** 逐个探 `test -f`；都不行 ⇒ 该栏直接判 **FAIL("不可信")** 而不是 PASS。
2. **统一传 POSIX 路径**（`/d/RPC/...`），任何一种 MSYS/Git Bash 都能读。
3. **stdin 必须走字节模式**：Windows 上 `text=True` 会把喂给子壳的 `\n` 翻成 `\r\n`，
   `while IFS= read -r` 吃掉 `\n` 后路径尾巴留 `\r` ⇒ **每个路径都变成不存在的文件**
   （实测表现是"447/447 全失败"，极易误判成仓库全坏了）。另需**补尾换行**，否则
   `read` 对没有换行结尾的最后一行不执行循环体 —— 少查一个文件却毫无提示。
4. **自证 + 覆盖度断言**：先拿"好样本必须不报错 / 坏样本必须报**语法错**"双向对照，
   再校验"喂入 N 个文件必须读到 N 个"；任何一条不满足 ⇒ 整栏 FAIL。

**⚠ 自证自身也踩过一次坑（值得记住）**：我第一版的自证只断言"出现了 FAIL"，于是在"所有路径都因
CRLF 变成不存在"时**自证依然通过**（它测的其实是个不存在的文件）。**"能报错"不等于"报的是那个错"** ——
判据必须校验**报错内容**（这里要求 stderr 含 `syntax error`），并配一个正向对照样本。

**结果与验证（20/20）**：`.sh:447文件/0失败 · 无扩展名:13文件/0失败`，且是**真检查**（自证与覆盖度均通过）。
负向：注入 `.sh` → FAIL 并点名；注入无扩展名 bash 脚本（`infer-load`）→ FAIL 并点名；注入无扩展名
python 脚本（`reqlog`）→ FAIL 并点名；模拟"bash 不可用"/"bash 空转"/"覆盖不全"三种退化 →
整栏分别以「不可信 / 自证失败 / 覆盖不全」判 FAIL，**均不报绿**；注入后 md5 还原一致。
脚本：`tmp/_verify_syntax_gate_fix.py`。全量门禁 12 项仍 11 绿 / 1 黄 / 0 红。

**边界（沿用 §5.4）**：不做常驻服务（复用 `d1` timer）；不做"按需自动加载"（那是 llama-swap 的另一半，
与"零自加载"方针直接冲突）；不引入新的时序库。
