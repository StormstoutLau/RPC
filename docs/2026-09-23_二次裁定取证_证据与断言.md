## ① D6 是否从 P0 开始？（依赖关系取证）

**裁定问题**：P0 是否真是 P1 的前置？

**证据（E1，实测读码）**：

- `ops/rpc_check.py` 的 `CHECKS` 是**平表**，字段仅 `id / title / fn / quick / fix`
  （实测读第 2483–2544 行，17 条）。**无 `needs` / `after` / 依赖图 / 并发 / `streamOutput`**。
- 执行体是**扁平串行 for 循环**：

  ```
  2569  results, failures = [], 0
  2570  for c in selected:
  2571      try:
  2572          status, note, detail = c["fn"] (以空参调用)
  ...
  2576      if status == "FAIL":
  2577          failures += 1
  ```

- **判据**：`failures` 只累加 `status == "FAIL"`；`WARN` 不计入 ⇒ **黄灯（≈ ds 的 `allowFailure`）已具备**。
- **P0 与 P1 的硬依赖（E1 可证）**：P1 的三项都要"重算 → 比对 → 不一致即 FAIL"，
  而**"比对结果如何影响最终退出码"**正是 `failures` 的语义。
  P0 要改的正是这条通路（加 `needs`/级联 skip 算失败/`allowFailure` 显式化）。
  ⇒ **不先动 P0，P1 的 `--check` 只能各自手写退出码**，会出现多套口径（正是 ds 要避免的
  "blocking-ci 与 postmerge-ci 不能漂移"）。

**断言（若采纳 P0-1）**：

| 断言 | 判据 | 先验红方式 |
|---|---|---|
| 图无重复 id | `len(ids) == len(set(ids))` | 复制 `CHECKS` 里一条 id ⇒ FAIL 点名 |
| 图无未知引用 | 每个 `needs`/`after` ∈ 已知 id 集 | 写一个不存在的 id ⇒ FAIL 点名 |
| 图无环 | DFS 检测，报出 `a -> b -> a` | 造 `A needs B` + `B needs A` ⇒ FAIL 报环路径 |
| 级联 skip 算失败 | `needs` 失败 ⇒ 后继记 `skipped` 且**计入失败** | 注入一个必失败的 `needs` ⇒ 后继 `skipped` 且退出码非零 |
| 模式性省略**不算**失败 | `--quick` 下未选中的项**不进失败集** | 跑 `--quick` ⇒ 6 项省略但退出码 0（现状必须保持） |

**结论**：**从 P0 开始成立**，且依赖是代码级的（同一条 `failures` 通路），不是流程约定。

## ⑥ 原 20（`MailboxDeliveryPhase`）确认"条件触发、暂不做"？

**裁定问题**：本机群是否真有"边跑边追加"的场景？

**证据（E1，实测 grep `agent-cli.ps1`）**：

- 命中 `--continue` 的**唯一语义是"失败后续接"**，不是"追加新输入"：
  - 第 1605 行注释：`# Use opencode native --session/--continue to resume partial session (NOT restart/re-read),`
  - 第 1644 行：`# O-24 P0-① resume loop: on failure retry <=2 via `--continue`（opencode isolates sessions`
  - 第 2331 行：`# 调用形式: 首跑 `claude -p "" --model <id>`(stdin 喂 prompt), 失败续接 `claude --continue -p "" --model <id>``
- **无** `followup` / `inject` / `MailboxDelivery` 相关实现（grep 命中均为注释里的"inject"指**注入文件/配置**，
  如第 246 行 `STATION_NOT_READY: inject failed`、第 1498 行 golden "injected BEFORE dispatch"）。

**⇒ 语义确认**：本机群是**一次性 headless 执行**（`opencode run` / `claude -p`），
**不存在"输出已展示后又有新消息送入同一 turn"** 的形态。
`MailboxDeliveryPhase`（`CurrentTurn ↔ NextTurn`）解决的正是那个问题 ⇒ **本机群无对应场景**。

**结论**：**"条件触发、暂不做"成立**。触发条件可写死为：
"若将来引入交互式会话或 agent 间通信（如 D7 的站间互审多轮），再评估"。

**裁定问题**：本机群是否有多 agent 派生场景？

## ⑧ D7 是否等 D6-P0 完成后再开？

**裁定问题**：D7 的哪些部分真依赖 D6-P0？

**证据与推理**：

- **强依赖（真依赖 P0 的 `needs`/退出码通路）**：
  - D7-D「结论回写：**留痕机器强制**」⇒ 需要"缺留痕即 FAIL"的断言能力 ⇒ **依赖 P0-1**。
  - D7-D「**熔断器**」⇒ 需要"某条件不满足即中断"的判据 ⇒ 同源。
- **弱依赖（只需 P1 的 `--check` 思路）**：
  - D7-C 结论契约、D7-H rubric/盲区登记 ⇒ 属"新写机制"，不依赖门禁改造。
- **无依赖**：
  - D7-A 架构形态定案（纯决策）、D7-B 权限模型（纯设计）。

⇒ **不需要"全部 D7 等 P0"**，只需 **D7-D 批等 P0**。
**更精确的表述**：可先做 **D7-A/B（定案与设计）**，把它当"设计期"与 D6-P0 并行；
**D7-D 必须等 P0**。

**结论**：**修正为"不做全局阻塞"**——
原方案写"D6-P0 完成后再开 D7"**过严**；应为
"**D7-A/B/C/H 可与 D6 并行（设计期）；D7-D/E 依赖 P0 与 P1**"。
