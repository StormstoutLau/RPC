## 0. 结论先行（三稿结论合并去重）

> **① D7 该立项；定位 = "独立执行主体 + 能力最小化 + 可审计收束"，且"跨族异构"应作为一条可机判判据。**
> **⚠ 2026-09-23 更正（Scott 指出，已 E1 复核）**：本节原写"本机群三站是**同构硬件 + 同批模型族** ⇒
> 三站互审**在模型家族维度上仍是同质的**" —— **该断言不成立，已撤回**（详见 §4.4 更正块）。
> 实测：**三站均可走 openrouter 出站**（`agent-cli.ps1:54` 三站 opencode.jsonc 实况=仅 `local`+`openrouter`；
> `:70` 站上 openrouter provider 已有 key 且实测可用），且**三站可加载不同模型**；本地至少 **4 族**
> （gpt-oss / nemotron / MiniMax-M2.7 / Qwen3.8-flash-next），出站再加族。
> **⇒ 但"跨站"本身不等于"跨族"**：它取决于**派发时选了哪个模型**。
> **⇒ 且它的上位目标是"九项目的统一基座"**（Scott 二轮定位，§11/§12）。
>
> **② 最大的缺口不是"缺协议"，而是三件本机群与九项目都缺的东西**：
> **统一证据强度字典** · **机读产物身份与依赖边** · **失效传播**。
> 其中后两项在九项目里的实测结果是 **0/9**（§10.3），且**三个项目已各自把它命名成待建占位**。
>
> **③ Q4「信息修改回写传递」有一个成熟答案，而且不是"某种状态机"那么含糊。**
> 它是**增量计算 / 失效传播**问题，社区已有**规范级硬规则**（Ontoly RFC-0002 的 H-1~H-4，§8.2）。
> 本机群既有资产（`MANIFEST.sha256` 内容寻址 · `LOG.md` append-only · 证据链 `prev_hash` + 外部锚）
> **已经具备这套形态的三分之二**，缺的是**依赖边**与**失效降级规则**。
>
> **④ 防污染的关键不是"审得更准"，是"结构 contain"。**
> arXiv 2609.17648 实测 **JBR(Judgment Bypass Rate) 100% 但 Unsafe Action Rate 0%** ——
> **"structural authorization can contain compromised agent behavior even when upstream LLM judgment fails"**（§8.1）。
> ⇒ 本机群两位开发者**各自独立得出了同一结论**并把不信任写成程序（§11.7）。
>
> **⑤ ⚠ 硬件现实检查推翻了"多站=更快"的直觉**（§5.1）：
> 跨站串行 RPC **损失 47%**、同站叠并发恶化 **~2.8×**、跨站并行**物理上界 = 3**。
> ⇒ **D7 的收益必须来自结构性（独立主体/可审计/可重算），不是吞吐**。
>
> **⑥ 建议批次 D7-A~F 之外，新增前置批次 D7-G（统一基座）**，因为 D7-B（机械门先行）

# 第一编 · 立项与边界

## 1. 厘清 D6 / D7 边界

### 1.1 一句话判据

| | D6 | D7 |
|---|---|---|
| **一句话** | **单次派发的闭环** | **跨主体的复核闭环** |
| 链路 | 需求 → 受理 → **一次执行** → 证据回收 → 抽检 | **审 → 改 → 再审**（多轮）→ 结论收束 → 留痕 |
| 主体数 | **1 个执行主体**（可跨站选站，但仍是"派一次"） | **≥2 个主体**（产出方 + 复核方） |
| 终止判据 | 证据入链 + 门禁绿 | **复核方签收**（≠ 产出方自认完成） |

### 1.2 三条可机械判定的分界判据（建议写入 ADR）

| # | 判据 | 归 |
|---|---|---|
| **B-1** | **是否需要一个"非产出方"的主体来给结论？** | 是 ⇒ **D7** |
| **B-2** | **是否在同一产物上需要多轮往返（改完再审）？** | 是 ⇒ **D7** |
| **B-3** | **是否只是"这一次派发内部"的质量门（判官抽检、accept 判据）？** | 是 ⇒ **D6** |

> 用 B-1/B-2/B-3 复核 D6 期间"归给 D7"的 14 项，**结论全部一致**（无一项应退回 D6）：
> 它们要么需要第二个主体（权限/结论/裁决），要么需要多轮（续聊/编排），要么是跨站形态（架构/自环盲区）。

### 1.3 边界上的灰色地带（必须显式裁定，否则会被两边都漏掉）

| 灰色项 | 现状归属 | 本次建议 |
|---|---|---|
| **判官抽检（`evidence` 断言里的 A1/A2/A3 + judge 校准）** | D6 | **留 D6** —— 它是"单次派发内的质量门"，判官是**同侧**的（B-3）。**不得**因它"像评审"就并进 D7 |
| **`inbox` 的 `plan-review ⇄ plan-revise` 协商回环** | D6（已实现） | **留 D6** —— 协商发生在**管理员 ↔ 需求方**之间，是**受理阶段**的事，与"产出复核"不同层 |
| **`accepted-by-requester` 验收签收** | D6（已实现） | **留 D6，但它是 D7 的接入点**：D7 的"复核方签收"应复用同一状态语义，**不新造** |
| **跨站派发（`--RemoteHost`）** | D6 | **留 D6** —— 跨站只是"派到哪个站"，主体仍只有 1 个 |
| **`--peer` 站间互审** | **D7** | 确认 D7（B-1 + B-2 同时命中） |
| **`RULE-5` 异构复审编排** | **D7** | 确认 D7（缺的正是"编排层"） |
| **多轮续聊（审→改→再审）** | **D7** | 确认 D7（B-2） |
| **agent 派生边表 / 多 agent 树** | **D7** | 确认 D7 —— **但见 §2.1 的反证：九项目中无一提出此需求** |

**⇒ 关键裁定**：**D7 ≠ "把 D6 没做完的补完"**。D6 的剩余项全部是事件驱动（等 429 / 等升级窗口 / 等试点），
**没有一个因为"做不动"而被推给 D7**。D7 是**新能力**，不是 D6 的尾巴。

### 4.3 ITIL 4「变更使能」的分阶段权限（E3，多来源一致）

- **ITIL 4 已把 "change management" 改名为 "change enablement"**（重点从"管控"转为"**以风险为基础的快速放行**"）；
  **目标是把不需要的重流程拿掉**（"If your CAB still reviews password policy updates and DNS changes the same way
  it reviews a core database migration, you're running ITIL v3 thinking"）。
- **三类变更 + 风险分级路由**（与 D7 的"分级复核"直接对应）：

| 类型 | 是否逐次批准 | 路由 |
|---|---|---|
| **Standard（标准变更）** | **不**（预授权，一次性批准流程） | 走**标准变更目录**，直接排期 |
| **Normal（常规变更）** | 是（需风险评估 + 批准） | **按风险分级**：低 → 同级评审/组长（**异步，不开会**）；中 → 指定变更授权人/小组；高 → **CAB** |
| **Emergency** | 走**加速路径**但仍有文档与**事后复核** | ECAB / 值班批准人（含 SLA，如 1 小时） |

- **六阶段流程**：`RFC 提交 → 评估（影响/风险/紧迫性）→ 授权 → 排期（变更日历、冲突检查）→ 实施（含 backout plan）→ 复核与关闭（确认达成预期 + 记录教训）`
  ⇒ **"复核与关闭"是独立阶段**，与"实施完成"分开。
- **角色**：change initiator / change manager / **change authority** / change owner。
- **★ 两条最值得抄的**：
  1. **"Write the Change Policy Before You Write the Workflow"** —— 政策 2–4 页，须定义：
     变更范围（什么算/不算）、三类变更如何分类、**角色**、**权威等级（谁能批哪个风险级别）**、争议升级路径、
     **事后复核触发条件**。
  2. **标准变更目录（Standard Change Catalog）** —— **"Every time the CAB approves the same type of change twice,
     someone should ask: 'Should this be a standard change?'"**；中型团队目标 **40–60% 的变更量走标准变更**；
     低于 20% ⇒ "your CAB is doing busy work"。
- 指标：**紧急变更占比 > 10–15% 通常说明是计划问题而非真紧急**。
- 来源：[Motadata: ITIL Change Management Best Practices 2026](https://www.motadata.com/blog/itil-change-management-best-practices) ·
  [opservices: Change Management com ITIL](https://www.opservices.com.br/change-management/) ·
  [ServiceNow Community: ITIL change management](https://www.servicenow.com/community/incident-management-forum/itil-management-in-that-change-management-in-detail-and-their/td-p/3568586)
  （**二手：厂商/博客，非 ITIL 官方规范**）

⇒ **对 D7 的直接含义**：**"标准变更目录"是缓解 D7 过载的关键机制** —— 否则每一次小复核都走全套 CAB 会
把 D7 变成瓶颈。**D7 应允许"预授权的复核类型"**（如"只读 lint 类复核"免终裁）。

### 4.4 异构多智能体辩论（E3，一手 arXiv/厂商报告）—— **最重要的外部依据**

| 结论 | 出处 |
|---|---|
| **同质 agent 无法稳定优于多数投票**；"Controlled evidence indicates that **homogeneous agents cannot reliably improve over majority voting** (Zhu et al., 2026). We therefore introduce **model heterogeneity**" | [Courtroom-Style MAD (arXiv 2603.28488)](https://arxiv.org/html/2603.28488) |
| **固定轮次辩论会浪费算力，并"amplify correlated errors among similar agents"**；须 **genuine model heterogeneity + agreement-based control** 两者兼备 → 三组件 **PAR / EASE（Early Agreement Stopping）/ SOD（Semantic Outlier Detection）** | [ARMOR-MAD (arXiv 2606.13197)](https://arxiv.org/html/2606.13197v1) |
| **用"来自不同 provider 的异构模型"而非同模型多实例**（"maximizing cognitive diversity"）；三阶段 **Triage → Parallel Expert Generation → Consensus Synthesis**；**综合阶段显式分类 consensus / disagreement / unique findings，而非简单多数投票**；HaluEval 幻觉率相对降 **35.9%**，TruthfulQA **+7.8 分** | [Council Mode (arXiv 2604.02923v2)](https://arxiv.org/html/2604.02923v2) |
| **角色化为三层：Solvers（产出）/ Reflectors（评估+给权重）/ Orchestrator（统合出指令）**；用 **WISE–Dawid–Skene 无监督概率聚合**按可靠性加权 | [WISE (MERL TR2026-083)](https://www.merl.com/publications/docs/TR2026-083.pdf) |

>   三站 `opencode.jsonc` 的 `local.models` 亦为三站同改的同一清单（`ADR-0004:415`）。

>
> 1. **异构是"派发选择"的结果，不是"跨站"的属性** —— 三站若都加载 nemotron，则仍是**同质复核**。
>    所以 D7 **必须**把 **`judge.family ≠ producer.family`** 写成**可机判判据**，
>    而不是假定"跨站 = 异构"。这与 `RULE-5` 的原话一致：它要的一直是
>    **reviewer ≠ implementer 的"基座（异构模型家族）"**，**不是"换一个站"**。
>    > **★ v2 补充（来自一次真实跨仓复核的实测，见** [基准调研 §8.3](2026-09-23_Spec_Workflow能否作为D6-D7工作流基准_调研.md)**）**：
>    > **"家族异构"与"信息独立"是两个正交维度**。实测中两个**同族** agent（都是 LLM），
>    > 因**各自只读自己的仓库**，仍产生了**对等反证**（它找到了我方引文的自相矛盾）。
>    > ⇒ **判据应同时写两条**：`judge.family ≠ producer.family`（家族）
>    > **与** `judge.input ≠ producer.input`（**信息独立** = "**盲写**"的机器化表述，
>    > 与 §3.2 的"不给审方非正式陈述/源材料/意图"同源）。
> 2. **异构有三个来源，按可用性排序取用**：① **站内跨族**（`O-16` 五源异基座，**已实现**）
>    → ② **跨站跨族**（如 A 的 gpt-oss 审 B 的 nemotron）→ ③ **出站跨族**（openrouter）。
>    ③ **受合规闸限制**：`local-only` × 会出网 ⇒ `REJECT exit 4`（**无覆写通道**，owner-policy）
>    ⇒ **未发表语料只能走 ①/②**。
> 3. **两条会"静默失败"的坑必须先堵**（E1）：
>    - **本地引擎忽略请求里的 `model` 字段** —— `docs/research/2026-09-14_暴露问题调研.md:414`：
>      **"本地引擎完全忽略请求里的 `model` 字段，服务的是『当时加载的那个模型』"**
>      ⇒ **"站 ↔ 已加载模型"必须显式登记**，否则会**"以为跨族、实际同族"**；
>    - **Zen（`opencode/*`）当前 0 credentials，只静默挂死**（`agent-cli.ps1:63-68` 实测 360s 无产出）。
>
> **⇒ D7 的正确定位** = **独立执行主体 + 能力最小化 + 可审计收束**，
> **并且把"跨族"做成一条可机判的派发判据**（不是宣传语，是判据）。

**另两条直接可用的**：
- **"显式分类 consensus / disagreement / unique findings"**（Council Mode）—— 比"多数投票出一个结论"信息量大得多，**建议直接作为 D7 结论契约的形态**。

## 7. Q1：agent 间通信的机读机制（避免人为干预）

### 7.1 协议层：已有的一手事实（E3）

| 层 | 定位（官方口径） | 现状 |
|---|---|---|
| **MCP** | **agent ↔ tool** | 本机群已用（opencode MCP 接入） |
| **A2A** | **agent ↔ agent** | **v1.0.0 为当前发布版**；Linux Foundation；`a2a.proto` 为规范源；**TaskState 八态**；**AgentCard 路径 `/.well-known/agent-card.json`** |
| **两者关系** | **官方明示"互补而非竞争"** | — |

**⚠ 但协议本身不解决 D7 的核心问题**（E2/E3）：
- **A2A 无 server→client 反向调用**（7 方法 / v1.0 方法表均 client→server 形态）；
- **无任何协议原生提供"评审/仲裁语义"**；
- 真正缺的仍是 **"谁审谁 / 几轮 / 结论如何收束记账"**（编排层）。

### 7.2 ★ 学界的主流解法：**不是加协议，是把「产物」变成可机读的一等公民**

四条**独立**的长时 agent 科研系统（2026）**在这一点上高度收敛**：

| 系统 | 核心机制 | 关键引文/证据 |
|---|---|---|
| **ScienceClaw / Infinite**（MIT，arXiv 2603.14312） | **plannerless 三原语**：① **typed artifacts** ② **global index（agent 广播"未满足的需求"）** ③ **pressure-based scoring** | **"Every computation produces an immutable, content-hashed artifact with explicit parent lineage, accumulating in a directed acyclic graph"**；peer agents **"pick those needs up via schema-overlap matching"**；**无中央 planner** |
| **AutoScientists**（arXiv 2605.28655） | **shared experimental state** + **Heartbeat Protocol** + **Queue and Claim Protocol** + **Noise-Aware Champion Validation** | agent **"self-organize into teams around promising hypotheses, critique proposals before using experimental compute, and share successes and failures to reduce redundant exploration"** |
| **CORAL**（arXiv 2604.01658v2） | **shared persistent memory**（symlink 架构 + 并发模型）+ **异步执行** + **heartbeat 干预** + **isolated workspaces + evaluator separation** | **"replaces rigid control with long-running agents that explore, reflect, and collaborate through shared persistent memory"** |
| **MCP-native AI scientist**（IBM Research/RPI，Frontiers 2026） | 主张**层级化 + 共享产物**（借 Simon 组织理论） | **两个瓶颈：lack of interoperability；"unstructured communication and memory become brittle as the number of agents grows"** |

**⇒ Q1 的答案**：**机读机制的关键不是"消息格式"，而是"产物格式"**。
四套系统都把**产物**做成：**不可变 + 内容寻址 + 显式父系血缘 + 类型化（schema）**，
然后让 agent 之间**通过产物寻址与 schema 匹配来协作**，而不是通过自由文本对话。
⇒ **这同时解决了"避免人为干预"**（无需人来搬运/转述）**与"可审计"**（每个产物可追父系）。

**对本机群的含义（E4）**：
- **已有**：`agent-out/<ts>/` 证据束 + `run.json` + `MANIFEST.sha256` + 证据链（`prev_hash` + 锚）
  ⇒ **"不可变 + 内容寻址"这一半已经具备**；
- **缺**：**显式父系血缘（依赖边）** 与 **schema-overlap 路由** ⇒ 这正是 §11/§12 要补的。
- **且九项目里已有 3 种机读信封**（`Cpp_Hub` 的 `.agent-run.json` · `Spec_Workflow` 的三信封 · `Paper` 的任务卡 YAML）
  ⇒ **不缺格式，缺统一**。

### 7.3 「避免人为干预」的现实边界（诚实标注）

- 本机群**当前所有派发都是人工发起**（E2：Fin_Agent 任务卡写明"运行动作（供管理员参考）"；
  手册 §2a.5 `agent-cli task` 是控制台命令）；
- 唯一自动化触发点是 **git 钩子**（对证据链 `agent chain`，非派发）；
- ⇒ **"避免人为干预"是 D7 要从零建的能力**，不是调参。且必须配套 `O-25` 的**排队/拒绝**语义。

## 8. Q2：抑制模型幻觉

### 8.1 已被实证有效的手段（E3，按证据强度排）

| 手段 | 证据 | 效果 |
|---|---|---|
| **异构（跨 provider/家族）** | Courtroom-MAD：**"homogeneous agents cannot reliably improve over majority voting"**；ARMOR-MAD：固定轮次会 **"amplify correlated errors among similar agents"** | 同质辩论**收益低** |
| **结构化综合（非多数投票）** | Council Mode：**显式分类 consensus / disagreement / unique findings** | HaluEval 幻觉率**相对降 35.9%**；TruthfulQA **+7.8** |
| **一致即早停（EASE）+ 离群降权（SOD）** | ARMOR-MAD 三组件 | 提精度 + 省算力 |
| **角色化 + 可靠性加权聚合** | WISE：Solvers / Reflectors / Orchestrator + **Dawid–Skene 无监督概率聚合** | — |
| **形式化验证** | Erdős 案例中 Gowers 的"毫不犹豫接收" | **最高强度**（本机群有 Lean4 线：`F:\Auto_Prover`、`D:\Textbook`、`F:\Cpp_Hub`） |

### 8.2 ★ 一条被忽视的关键：**评分器自己也会错**（E2，CORAL 的实测）

CORAL 论文**专设一节 `Evaluator Corrections`**，记录他们在 **4 个任务上发现评分器本身有缺陷**：

- `PRISM`：**"failed placements silently skipped"**（失败的摆放被静默跳过 ⇒ 计分虚高）
- `Transaction Scheduling`：**"invalid schedules scored above zero"**（非法调度得分大于零）
- `EPLB`：**"dropped experts and redundant averaging"**
- `LLM-SQL`：**"type handling"**

**⇒ 这与本机群 ADR-0007 反复记录的同一条教训完全同源**（E1）：
**"判据通过了，是因为它什么都没判"**（`TASK_ID != label` 恒真 / audit 首版自比恒真 /
`Keys.Count` 恒为 18 / 校准指纹恒假），且本机群已给出对策：
**"判据的『通过』与『没判』必须可区分，覆盖率是唯一手段"**。

⇒ **Q2 的关键增量**：**幻觉抑制不能只审"产出"，还必须审"判据"**。
D7 必须把"**判据自身的有效性**"作为一等公民（覆盖率 + 正反用例 + 恒真检测）。
> **本机群已有的正例**（E2）：`Cpp_Hub` 的 `AUDIT_CHECKLIST` 记录了**测试曾真为红**的实例
> （"原 JumpRejected 测试…z=1.855 < 1.96…测试**实际失败**"）并自纠过一次**计数幻觉**
> （"原审计声称 15/15 + 1283/1283 为**计数幻觉**, 已修正"）；
> `factor_pipeline` 专列**"5 项断言恒真式修复"**（把 `abs() ≥ 0` 类恒真断言改写为可证伪断言）。
> ⇒ **这两条可直接作为 D7 "审判据"批次的验收用例。**

### 8.3 「新颖性检查」作为幻觉检测的一个独立维度（来自 §6.2 的 T-2）

Erdős 虚报事件的形式是"**重新发现已发表结果**"，任何只检查"推理是否自洽、结论是否成立"的
机制都**检测不出**它。⇒ D7 的语义复核**必须包含一条**：
**"这个结论/构造是否为已知？"**（对账文献库 / 知识库 / 既有证据链）。

## 9. Q3 + Q4 合并回答：共享记忆、污染、与「回写传递」的硬机制

> Scott 把 Q3（共享记忆污染）与 Q4（回写传递麻烦）连在一起问，**这是对的** ——
> 学术界把两者交叉处称为 **"memory poisoning propagation"**（记忆污染**传播**），
> 而 Q4 的"回写传递"在计算机科学里是**独立的成熟领域**：**增量计算 / 失效传播**。

### 9.1 Q3 的现状：记忆污染已是成熟研究领域（E3）

| 论文 | 核心发现 | 对 D7 的用途 |
|---|---|---|
| **MAPLE-Guard**（arXiv 2608.00426，2026-08） | **"a poisoned memory can be written once, continuously retrieved in later tasks, promoted into shared memory, and reused by other agents. A single poisoned write can therefore steer many later decisions and contaminate agents that never saw the original attack, all while no malicious message crosses a visible communication edge at the moment of harm."** | **★ 直接解释 Scott 的担忧**；并给出**四道门**：**write / retrieval / promotion / cross-agent reuse**；ASR **38.2%→0.9%**（LongMemEval）、**34.7%→0.2%**（AppWorld） |
| **Trust propagation & structural containment**（arXiv 2609.17648，2026-09） | 四 agent 管道（Supervisor/Researcher/Validator/Executor）实测 **"memory poisoning reaches execution in every undefended trial"**；**加授权层后：JBR(Judgment Bypass Rate) 100% 但 Unsafe Action Rate 0%** | **★ 最重要的一条**：**"structural authorization can contain compromised agent behavior even when upstream LLM judgment fails"**；且 Observer 层把劫持误报率 **49%→7%** |
| **MemPoison**（arXiv 2605.29960） | 通过**正常对话**注入可检索后门，ASR 高达 **0.95**；利用 embedding 空间各向异性 | 证明"**黑盒对话接口**就足以投毒" |
| **MemIncept**（ICML 2026） | **合作式隐蔽注入**："有效注入往往明显恶意易被检测，而隐蔽良性的注入效果差" ⇒ 用 meet-in-the-middle 同时满足 | 证明"**看起来良性**"是最危险的形态 |
| **Memory Poisoning Propagation and Repair**（ACM 2026-01） | **"constructs an evidence graph based on memory source credibility and content consistency to validate newly added memories"** | **★ 正是"修复传播"的机制**：**按来源可信度 + 内容一致性建证据图** |

**⇒ Q3 的答案（三层）**：

1. **共享记忆应该做，但"共享"必须是有门的**：
   **私有 → 共享的"晋升（promotion）"是攻击面的关键一跳**（MAPLE-Guard 明确指出），
   **D7 必须在 write / retrieval / promotion / reuse 四个点各设一道门**。
2. **记忆条目必须带"来源可信度 + 证据"**（ACM 2026-01 的做法），
   且"来源可信度"要能被机读 —— 这与缺失的**证据强度字典**是同一件事（§11.1）。
3. **★ 不要指望"审得更准"，要靠"结构 contain"**（arXiv 2609.17648）：
   即便审核者的判断**被污染**（JBR 100%），**只要授权边界在**，
   **危险动作率仍可为 0%** ⇒ **D7 的授权/权限边界比"评审智能"更重要**。

> **★ 本机群已独立发明了"晋升门"三次**（E2，§11.5）：
> `Textbook` 的 `FixMemory`（只记成功 + LRU 50 + `min_success_for_inject`）·
> `Spec_Workflow` 的 `discoveries` 门槛（**"单发事件不登记，仅跨 feature/跨仓库复发的系统性模式入册"**）·
> `Fin_Agent`（**仅 `verified=True` 落库**）。
> ⇒ **上一版只有 arXiv 依据，现在有三处实现**；但**三处判据各不相同**，应当**统一为一个 schema 的不同字段**。

### 9.2 ★ Q4 的成熟答案：这就是「增量计算 / 失效传播」

Scott 的原话："**这种复杂网络的信息修改回写传递非常麻烦，是否应存在某种状态机或者硬机制？**"

**⇒ 答案：有，而且已有规范级的硬规则**（E3）。这不是要发明的东西，是**可以照抄的工程纪律**。

#### 9.2.1 基本模型（E3）

- **依赖图是 DAG**；**边的语义 = "若 A 的输出改变，B 的有效性即被摧毁"**。
- 变更时做 **Topological Invalidation（拓扑失效）**：从变更节点出发，把所有可达节点标为 **Dirty**。
- **必须用内容寻址（content hash），不能用时间戳** ——
  **"file timestamps … are unreliable across machines and builds"**。
- **"Header Contamination" 问题**：改一处被广泛依赖的东西 ⇒ 触发全量重算
  ⇒ 用 **Fingerprinting（内容指纹）** 缓解：**内容没变就不必失效**。
- **Turbopack 的 value cell 机制**（2026-01，借鉴 Salsa / rustc query system / Adapton）：
  **"When reading a cell, it records the currently executing function and all of its cells as dependent
  on that cell"**；变更时 **"marks all functions that read the file's value cell as dirty and queues them
  for re-computation"**；**"Cell updates are skipped if the cell contents are equal"**；
  且**自动追踪依赖而非手工声明**，理由：
  **"manually declaring and adding dependencies to a graph is prone to human errors"**。

#### 9.2.2 ★★ 四条可直接落成判据的硬规则（E3，规范级）

来源：Ontoly **RFC-0002（Compiler Pipeline）**，用 **RFC 2119 的 MUST/MUST NOT** 写就：

| # | 规则（原文） | 为什么这正是 Scott 要的"硬机制" |
|---|---|---|
| **H-1** | **"Incremental builds MUST be clean-build equivalent."**（另有 invariant：**"A successful incremental build MUST be semantically equivalent to a successful clean build."**） | 增量结果**不许**与全量结果不一致 ⇒ **传播不能"猜"** |
| **H-2** | **"Dependency invalidation MUST be conservative."** | 宁可多失效，不可漏失效 |
| **H-3** | **★ "If affected regions cannot be determined safely, the compiler MUST broaden invalidation or fall back to a clean build."** | **★ 这一条就是答案**：**无法安全判定影响面 ⇒ 强制降级为全量重算**。不允许"我觉得应该没影响" |
| **H-4** | **"A failed build MUST NOT partially overwrite the last valid canonical graph artifact."** | **失败不得部分覆盖** ⇒ 与 append-only + 原子提交同源 |

**另两条同源 invariant（同样适用于 agent 记忆）**：

- **"Edges SHOULD contain provenance. Edges without provenance are invalid."**
  ⇒ **依赖边必须带来源，无来源的边无效**。
- **"No AI in graph construction. Compiler graph facts MUST NOT depend on probabilistic model output."**
  ⇒ **★ 结构性事实不得依赖概率模型输出** —— 即：**LLM 可以产生"内容"，但不得产生"拓扑/结构事实"**。
  这条对 D7 极其重要：**依赖边应由确定性机制（内容哈希/文件读写追踪）产生，而不由 LLM 判断产生**。

#### 9.2.3 与 Scott 的担忧逐条对上

| Scott 的担忧 | 成熟机制 |
|---|---|
| "信息修改回写传递非常麻烦" | **不用"回写"，用"失效 + 重算"**：改源 → 标脏 → 按 DAG 传播 → 只重算脏点 |
| "复杂网络" | 依赖图 = **DAG**，天然表达复杂网络；环在构造期即拒绝 |
| "是否应存在某种状态机" | 状态机不够 —— 需要的是 **内容寻址的 DAG + 失效规则**（状态机只能表达"当前状态"，不能表达"谁依赖谁"） |
| "硬机制" | **H-1~H-4 四条 MUST 级规则**（尤其 **H-3 的强制降级**） |
| 怕"污染扩散" | **provenance 必填 + 无 provenance 的边无效 + 结构事实不由 LLM 产生** |

### 11.6 发现六：**ID 算法有 6 种，且截断长度不统一**（U-1 的直接输入）

**⇒ 三个问题**：① **算法不统一**（md5/sha1/sha256）；② **截断长度不统一**（`[:8]`/`[:12]`/`[:16]`/`[:32]`/全）；

> "`raster_id` … 是**维度哈希**，与 md5 **同长度不同语义** … **「同长度/同形态」不构成「同语义」**"

⇒ **U-1 必须同时规定：算法 + 截断长度 + 取值维度 + 算法标识前缀**（否则跨项目必然撞车或误比）。

| 批 | 项目 | 理由（E2） |
|---|---|---|

### 13.2 建议的**非范围**（明确不做，防膨胀）

| 不做 | 理由 |
|---|---|
| **引入 LangGraph/CrewAI/AutoGen 等编排框架** | 全部材料一致：跨机器归**协议层**，框架归"单进程内改 agent-loop"；本机群纪律是**不动派发关键路径** |
| **给 D7 建"多 agent 树 / 派生边表"** | **九项目中无一提出此需求**（E2）；原 21 项归 D7 的前提**未获使用场景支持** ⇒ 建议**降为"条件触发"** |
| **把"跨站"本身当作"异构"来讲** | **⚠ 口径修正（§4.4 更正块）**：跨站**不自动**带来异构；**只有当判据强制 `judge.family ≠ producer.family` 时**，才可称"跨族复核"。不得用"跨站"替代"跨族"作为宣传 |
| **替换现有判官/证据链** | D7 是**叠在** ADR-0005/0007 之上，不另造第二套证据机制 |
| **把 `Auto_Prover` 的"定理级依赖图"并入 U-3** | 它管的是**证明的引理依赖**（业务），U-3 管的是**产物级消费关系**（基座）。**两者不是一回事，不要合并** |

### 13.3 与 D6 计划的接口

- **D7-B（机械门）应复用 D6-P0 的门禁调度器**（`needs` / 级联 skip 算失败 / `allowFailure`）——
  **这是 D7 对 D6 的硬依赖**。
- **D7-D（"不得自审"）与 D7-E（标准复核目录）应复用 D6-P2 的决策记录门禁**（ADR 格式断言）。
- **D7 的结论留痕应复用 `inbox` 的 `40_state/LOG.md` 追加式纪律**，**不新造账本**。
