**站间 (station↔station) 寻址补充 (2026-09-15 实测)**: 站间 ssh 用**管理网 IP 优先, `.local` 名兜底** ——
  实测差异: 站间 mDNS 解析需 6~10s (慢), 且各站 `known_hosts` 原先只按 **IP** 收录,
  直接用 `.local` 会 `Host key verification failed`; 而 IP 六向全通。
  2026-09-15 已为三站的 `.local` 名补齐 known_hosts (由已信任的 IP 密钥派生 `ssh-keyscan | sed`),
  故**兜底路径是真的可用** —— 已实测: 把首选 IP 指成不可达地址后, `infer-list` 仍靠 `.local`
  取到完整三站数据 (DHCP 真漂移时不会失明)。
  站间免密同日补齐 **A→C** (此前 A 的公钥未下发到 C, 表现为 `Permission denied (publickey,password)`);
  现 A/B/C 三向全通。新站入网时须把本站公钥下发到其余两站的 `~/.ssh/authorized_keys`。

### 1.4 生成物纪律（2026-09-24，D6-P1-1）

> **为什么需要它**：本仓有一批"**权威源在别处**"的文件（推导出来的清单/水印/证据链）。它们此前**没有"生成物"这个概念**，
> 于是同时存在两种病：**手工改了会被下次重跑覆盖（白改）** · **改了源头忘了重跑（记录与实效脱节）**。

**清单（单一真值）**：[`inventory/artifacts.yaml`](../inventory/artifacts.yaml) —— 逐条声明
`path`（生成物）· `authority`（权威源）· `check`（**判它的真实断言 id**）或 `exempt`（豁免理由）。

**纪律（硬性）**：

1. **生成物禁止手工编辑** —— 一律 **"改源头 → 重跑 → 跑 `--check`"**。
2. 清单每条**必须**给 `check`（且该 id 必须在 `rpc_check.py` 的 `CHECKS` 里**真实存在**）或 `exempt`（写明理由）；
   **两者都缺 = 静默缺口 ⇒ 门禁 `artifacts` FAIL**（"没人判、也没说明为什么不判"是最贵的一类错）。
3. **"语法/编译通过" ≠ "接线完整"** —— `syntax` 绿**不代表**生成物与源头一致；一致性由 `check` 指定的断言负责，
   而"到底有没有人真的在判它"由 `artifacts` 断言负责（它**报覆盖率**：`生成物 N 条 · 有断言覆盖 M · 显式豁免 K`）。

**机判入口**：`ops/rpc.ps1 check`（含 `artifacts` 项）· 护栏 `tests/test_rpc_check_artifacts.py` ·
跨文件验证（改一处生成物 ⇒ 应红）`spec/d6-agent-standard/fixtures/negtest_artifacts.py`（**手工运行**）。

### 2.2 模型名路由语义 (LiteLLM, 2026-09-01 20:30 双端点换防后已验证; C 站 2026-09-09 接入)

> ⚠️ **本表是 LiteLLM 时代的语义 —— LiteLLM 网关已依 ADR-0002 于 2026-09-13 退役，
> 表里的「模型名」在现行 `ops/cluster.py` 下多数已不成立**（2026-09-14 由 `rpc check` 复核后加注）：
>
> | 表里的名字 | 现行 CLI 下的实际行为 |
> |-----------|---------------------|
> | `nemotron` | 落默认站 B，而 B 站无 `nemotron` 这个 conf（真名是 `nvidia-nemotron-3-super-120b-a12b`）⇒ **`load` 必失败** |
> | `nemotron-c` / `gpt-oss-c` | 同上 ⇒ **必失败**（cluster.py 无此路由键） |
> | `gpt-oss` | 前缀匹配到 ROUTE 键 `gpt-oss-120b` ⇒ **凑巧可用**（实际加载 gpt-oss-120b） |
>
> **现行用法**：`python ops/cluster.py load <站上真实别名>`。
> 别名真值见 [inventory/models.yaml](../inventory/models.yaml)；路由表见 `ops/cluster.py` 的
> `ROUTE` / `RPC_MODELS`。本表的「实际路径」列（哪个站、哪个端口）**信息仍然有效**，退役的只是
> 「模型名」这一列的网关别名语义。
>
> **现行替代（要指定"从哪个站加载"时用）**：**按站路由名** = `<站上真实别名>-<A|B|C>`，例如
>
> | 按站路由名 | 含义 |
> |-----------|------|
> | `gpt-oss-120b-a` / `gpt-oss-120b-b` / `gpt-oss-120b-c` | 同一模型在三个站都有 conf，用它指定来源站 |
> | `nvidia-nemotron-3-super-120b-a12b-b` / `...-c` | 同上（B / C 站） |
> | `qwen3.8-27b-mtp-b` / `...-c` | 同上 |
>
> 即本表 `gpt-oss-c` / `nemotron-c` 的**现行替代品**（那两个是 LiteLLM 网关别名，已失效）。
> 全部可用名见 `ops/cluster.py` 的 `STATION_ROUTES`；`load` 传入无法解析的名字时也会列出。
> 命名用「完整别名 + 站后缀」而非短名：短名无法从真值表派生，会再引入一套要人工同步的命名。


| 模型名        | 实际路径                                     | 何时用                                                                                                        |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------- |

### 2a.5 `oCrun` — headless 调用的可控包装（2026-09-14 新增）

**为什么存在**：`opencode run` **无默认总超时**。免费档间歇性慢时（实测合并成功率 ≈59%，失败恒为 rc=124 且已有输出），上层脚本既拿不到错误也等不到结果，表现为"无反馈挂起"。

**它做什么**：给每一次尝试套独立超时，失败自动落下一档；把"慢"转成可判定的 `rc=124`。

| 项 | 值 |
|----|----|
| 位置 | 三站 `/usr/local/bin/ocrun`（755，非交互 ssh PATH 可达）；源 `ops/station-bin/ocrun` |
| 默认链 | `opencode/nemotron-3.5-lightning-free` → OpenRouter 5 档（用户指定序，见下）→ `cluster-local/gpt-oss` |
| OpenRouter 档序 | `thinkingmachines/inkling:free` → `nvidia/nemotron-3-ultra-550b-a55b:free` → `thinkingmachines/inkling-small:free` → `nvidia/nemotron-3-super-120b-a12b:free` → `poolside/laguna-s-2.1:free`（权威清单在 `secrets/openrouter.conf` 的 `harness_priority`） |
| 覆盖链 | `OCRUN_CHAIN="模型A 模型B" oCrun ...` |
| 默认超时 | 120s（`-t 秒` 可调） |
| 退出码 | 0=某档成功 / 1=全链失败 / 2=用法错误 |
| 设计记档 | [2026-09-14_暴露问题调研.md](research/2026-09-14_暴露问题调研.md) §1/§4.1 |

**与铁律 3 的关系**：`oCrun` **不改**默认模型策略（轻任务走免费档省本地算力），只在该策略之外补一层可用性兜底；敏感内容仍须由使用者显式指定 `-m` 走本地。

**headless 调用铁律 (2026-09-02 实测定版,** **`ops/station-bin/agent-cli-smoke.sh`** **4/4 PASS)**:

1. **claude 必须** **`< /dev/null`** — 不关 stdin 时可能长时间等待输入
2. **opencode 必须 stdin 管道形式** `echo "<prompt>" | opencode run -m <model>` — 位置参数形式 (`opencode run -m x "prompt"`) 在 1.18.25 会挂死 (init 后无任何 LLM 调用, 日志实证)
3. **默认模型 = 免费档** **`opencode/nemotron-3.5-lightning-free`** (两站 2026-09-02 定) — 轻任务不吃本地算力; **敏感内容 (未发表论文/因子代码/密钥) 必须显式** **`-m cluster-litellm/nemotron`** **或** **`cluster-local/gpt-oss`** **走本地** (免费模型数据用于改进训练, 官方 Privacy 节明文); wrapper/脚本调用仍永远显式 `-m`
4. **B-claude 冷启动慢 (估计 \~20min, 非精确测量)** — 33k 系统提示在 nemotron (8 专家 CPU 卸载) 上首次预填充极慢 (观察事实: 首次调用 >25min 未完成被中断, 20min 系算术估计且 stdin 等待因素未隔离); 热缓存后 30-120s (实测)。首次使用先发轻量 PING 预热
5. **A-claude 是纯文本模式** (`CLAUDE_CODE_DISABLE_TOOLS=1`) — 3s 快速响应, 但无工具调用能力; 文件级 agent 任务走 opencode

> **⚠ 铁律 2 复核（2026-09-14，未复现）**: 以同一模型各跑 4 次对照 —— **位置参数形式 4/4 成功、stdin 管道形式 2/4 成功**，两种形式都呈间歇性慢，**形式不是决定性变量**。该铁律在 2026-09-02 成立、当前不成立，待独立复核后再定修订。证据见 [2026-09-14_暴露问题调研.md](research/2026-09-14_暴露问题调研.md) §1.2(e)。

### 3.4 长上下文扩展 (YaRN → 1M, 仅需长文时启用)

**背景**: `qwen3.8-flash-next` 原生上下文 **256K (262,144)**（架构 `qwen4exp`, 36 GDN + 12 QSA 稀疏注意力）；Qwen 官方支持 YaRN 扩展至 **1M**。**静态 YaRN 会损害短文本生成质量, 只在真需要 >256K 时开**, 日常 32K 一律用默认 conf。

```bash
# 调参 (B 站, 改 conf 的 EXTRA_FLAGS 后 restart):
sudo vi /etc/llama-instances/qwen3.8-flash-next.env
# EXTRA_FLAGS 追加 (对比默认只加长文相关项):
EXTRA_FLAGS="-fa on --ctx-size 1048576 --rope-scaling yarn --yarn-orig-ctx 262144 --rope-scale 4.0 -ctk q8_0 -ctv q8_0"
sudo systemctl restart llama-server@qwen3.8-flash-next
```

- 参数来源 (排幻觉审计修正 2026-08-31): `factor=4.0, original_max_position_embeddings=262144` 来自 **Qwen3.8-Flash-Next-FP8 的 vLLM recipe** (社区全攻略引 vLLM recipe); **Qwen 官方未直接给 qwen4exp 的 llama.cpp YaRN config**, llama.cpp 路径 `--rope-scale 4.0` = 目标/原始 (1M/256K) 为推断, 需实测换算 — 若典型负载 \~512K 用 `2.0`

- **KV 内存纠正**: QSA 是**稀疏有界缓存** (`indexer_top_k=2048` + compress ratio, ll.cpp#27742 "optional third cache in llama\_memory\_hybrid"), **KV 不随 ctx 全量线性增长** (这正是 Qwen4 稀疏注意力的卖点); 12 层全量 \~24G\@1M 只是**最坏上界非真实分配**, 实际看引擎 memory\_hybrid 实现 — 须 `-c 1M` 启动日志实测

- 内存: N-gram 表 \~97.7G 走 host mmap (不占 GTT); QSA 稀疏缓存 + 36 GDN 固定态 → KV 非全量; 权重 103G 经 RPC 分载 A/B — **双机 128G 可行性高于初判, 以启动日志 KV 分配为准**

> **⚠ 结论 (2026-08-31 实测裁决, 取代原"待验证")**: ① **YaRN 对 qwen4exp 不生效** — qwen4exp 走 `ggml_rope_multi IMRoPE` 专用路径, `--yarn-*` 未被消费, 任意 `-c > 262144` 被 llama.cpp 强制 cap 回 `n_ctx_train` (实测 journal: `slot context exceeds training context - capping`). **当前 llama.cpp 构建无法对 qwen4exp 扩展超 256K**; ② 原生 262144 已验证可用, KV 增量小 (QSA 稀疏, 无全量线性增长); ③ ll.cpp #28012: decode 随 ctx 线性退化 (176K 约 122ms/token). **1M 唯一可达路径 = vLLM (Flash-Next FP8 recipe factor=4.0), 或等 llama.cpp 接入 qwen4exp IMRoPE yarn.**

**若引擎修复后复测**: `-c 262144` 原生基线 → `-c 524288` 看 KV/内存 → `-c 1048576` 确认装下 + needle 长文对答 → 失败回退默认 conf。

**结论 (ROCm vs Vulkan, 2026-09-03)**:

1. **算子完备性: ROCm 完胜**——Lightning Indexer/HC 融合/top-k 三项 Vulkan 等待中的问题在 HIP 侧全部已有; DeepSeek 慢因 (HC 非融合 32%) 在 ROCm 下大概率直接消失
2. **但切换成本被三重锁定**: ① 内核纪律 (6.17 锁定 vs 社区要求 ≥6.18.4); ② 全集群基线重测 (nemotron 锚点/bench/质量门全链); ③ Strix Halo 最优 ROCm 优化包 #27233 本身未合入主线 (拆分中)
3. **定案**: 维持 Vulkan 现役 + 小升级窗口 (收 #27453+#28032) 路线不变; **ROCm 列为 D7+ 大窗口候选**——若升级到 #26610 协议时同步评估切 ROCm (一次性重测成本与两后端长期收益摊平); #27233 拆分 PR 进每周跟踪清单

### 10.1a 内核 6.18.4 升级评估 (2026-09-03, 社区调研 + B 站实测)

> 问题: AMD 官方称 Strix Halo 要求 ≥6.18.4 (KFD 修复), 社区 (kyuz0) 称 <6.18.4 有稳定性 bug——本集群 6.17 是否应该升级?

**证据面 (E1 直抓 + E2 社区)**:

| 证据源                                                                                                                | 内容                                                                                              | 对本集群的适用性                                                              |
| ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| [AMD 官方 ROCm 7.2 Strix Halo 文档](https://rocm.docs.amd.com/en/docs-7.2.0/how-to/system-optimization/strixhalo.html) | "必需修复已合入 **6.18.4+**"——具体是 **KFD 驱动内部限制** (队列创建/内存可用性检查), 无此修复"GPU 计算负载可能初始化失败或行为不可预测"          | **面向 ROCm/HSA 路径**; 本集群 Vulkan+llama.cpp RPC 不经 KFD 用户态——修复对现役路径收益未证实 |
| kyuz0 toolboxes                                                                                                    | 最稳配置 Fedora 6.18.6 + firmware 20260110; "<6.18.4 有 bug 应避免"; **firmware 20251125 有毒 (ROCm 崩溃)** | 其场景=ROCm 容器跑 llama.cpp; Vulkan-RADV 容器在其清单标"最稳"但宿主也是 6.18             |

**B 站实测 (2026-09-03)**: 当前 6.17.0-23 · `linux-image-generic-hwe-24.04` 候选=**7.0.0-30** (noble HWE 轨道 6.17→7.0 直跳, **无 6.18.x 官方包**) · `linux-firmware` 已装=候选=20240318 (noble 停更; 社区稳定线 20260110 需手动装) · 无 DKMS 模块 (amdgpu 内建, 升内核不涉重建)。

**结论**:

1. **"≥6.18.4 稳定性"的社区主张成立但场景错位**——AMD 官方要求的修复 (KFD 队列/内存检查) 服务 ROCm/HSA 路径; kyuz0 的稳定性结论来自 ROCm 容器; 本集群 Vulkan+RPC 路径在 6.17 上 D1-D5 全程稳定, 且唯一挂死族已 E1 关案于 cron 干扰 (非内核)。**升级对现役路径收益: 未证实**
2. **6.18.x 在 noble 无官方通道**——HWE 轨道直接跳 7.0; 装 6.18.4 只能 mainline PPA (不受 Canonical 支持, 缺 Ubuntu 补丁) + 手动装 firmware 20260110 + 过 modules-extra 完整性坑 (§10.1 已录)——**成本高且脱离支持轨道**
3. **6.19/7.0 均有实锤回归** (gfx1151 误识别/ring timeout), 不是升级目标
4. **定案**: **维持 6.17 锁定**; 内核升级动机与 ROCm 大窗口 (§10.0a 定案 D7+) **绑定**——届时一次性评估 6.18.x mainline + ROCm 7.2 + #26610 协议三联升, 单独立 spec 过 ADD; 期间每周跟踪 kyuz0 对 6.18.x 的持续反馈与 mainline-6.18 在 noble 的兼容性报告。**Vulkan 现役稳定性无需内核动作**: D1-D5 实证 + 挂死根因已闭环, 社区 Vulkan 风险报告均发生在 ROCm/其他内核线
