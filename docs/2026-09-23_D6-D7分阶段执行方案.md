#### P0-1 门禁调度器 struct

- **现状（E1 实证）**：`rpc_check.py` 用的是**扁平 `for c in selected` 串行循环**
  （`main()` 第 2570-2577 行），`CHECKS` 是平表，字段只有 `id/title/fn/quick/fix`。
  **没有** `needs` / `after` / 依赖图校验 / 有界并发 / `streamOutput`。
- **做什么**（按 ds `run-gates.ts` 的可映射部分裁剪）：
  1. **`needs`（必须 passed 才启动）与 `after`（只需 settle）两个新字段** —— 目前无依赖关系可表达。
  2. **启动期图校验**：空图 / **重复断言 id** / 引用**未知 id** / **依赖环**（DFS 报出 `a -> b -> a`）。
     ⇒ 在跑之前 fail，而不是跑到一半。
  3. **依赖级联的 `skipped` 必须算失败**（ds 原文规则）。
     ⚠ **必须区分两种 skipped**：**模式性省略**（`--quick` 下不跑全量项 → **合法，不算失败**）
     vs **依赖失败导致的跳过**（→ **算失败**）。当前只有前者，加了 `needs` 后必须有后者。
  4. **有界并发**：`--jobs N`（默认 1 保持现状；可设 4）。理由沿用 ds：
     多个断言各自建大对象时，无上限并发在大机器上是"拿墙钟换内存爆炸"。
  5. **`streamOutput`**：长断言实时透传而非完成后缓冲（本次 `_bash_lint_parallel` 已是并行，
     可接此标志）。
- **不做（明确标注 N/A）**：ds 的 GitHub 专属部分 —— **required-check fan-in 与 `if: always()`**
  在本机群**无对应物**（本机群无 CI 分支保护；已有唯一入口 `rpc.ps1 check`）。
  ⇒ **原编号 22 的可映射部分以上 3/4/5 三条已覆盖，其余记 N/A，不假装做**。
- **落点**：`ops/rpc_check.py`（调度器 + `CHECKS` 字段）+ `tests/`（新增调度器单测）
- **验证**：
  - 单测：重复 id / 未知 id / 依赖环 / 级联 skip 四类**各注入一次看变红**
  - `rpc_check --quick` 仍 **11 绿**；报数**逐项与改造前一致**
- **风险**：低（纯新增字段 + 校验）。**回滚**：还原 `rpc_check.py` + 删新测试。

#### P1-1 定义"生成物"清单 + `--check` 模式

- **现状（E1）**：本仓有一批"**由某处推导出来的清单**"，但目前**没有"生成物"这个概念**：
  - `inventory/ops.yaml`（脚本登记表，由 `ops/` 目录扫描推导 → 门禁 `scripts` 报"扫描 217 个脚本 · 未登记 0"）

  - `inventory/models.yaml` / `ports.yaml` / `plugins.yaml`（真值表）
- **做什么**：
  1. 显式列出**生成物清单**（哪些文件的权威源在别处）。
  2. 给每类加 **`--check` 等价物**：**重算 → 与磁盘比对 → 不一致即 FAIL**（而非靠人记得重跑）。
  3. **纪律入册**：生成物类文件**禁止手工编辑**，一律"改源头 → 重跑 → 跑 `--check`"。
  4. **★ 明确写出"编译/语法通过 ≠ 接线完整"**（ds 原文：`typecheck` 链不含任何生成器）——
     这正是本会话 `inventory` 报数掉到 0 仍 PASS 的同类问题的正面表述。
- **落点**：`inventory/`（新增生成物清单）+ `ops/rpc_check.py`（各 `--check`）+ 手册 §1.3
- **验证**：**先验红** —— 手工改一处生成物（如 `ops.yaml` 某计数）⇒ `--check` 应 FAIL；重跑生成 ⇒ PASS。
- **风险**：中（要先把"权威源在哪"逐项定清，定错会把好数据判成坏）。
  **回滚**：`--check` 默认关闭或降为 WARN。
