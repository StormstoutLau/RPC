#### P0-1 门禁调度器 struct

- **现状（E1 实证）**：`rpc_check.py` 用的是**扁平 `for c in selected` 串行循环**
  （`main()` 第 2570-2577 行），`CHECKS` 是平表，字段只有 `id/title/fn/quick/fix`。
  **没有** `needs` / `after` / 依赖图校验 / 有界并发 / `streamOutput`。
- **做什么**（按 ds `run-gates.ts` 的可映射部分裁剪）：
  1. **`needs`（必须 passed 才启动）与 `after`（只需 settle）两个新字段** —— 目前无依赖关系可表达。
  2. **启动期图校验**：空图 / **重复断言 id** / 引用**未知 id** / **依赖环**（DFS 报出 `a -> b -> a`）。
     ⇒ 在跑之前 fail，而不是跑到一半。
  3. **依赖级联的 `skipped` 必须算失败**（ds 原文规则）。
     ⚠ **必须区分两种 skipped**：**模式性省略**（`--quick` 下不跑全量项 → **合法，不算失败**）
     vs **依赖失败导致的跳过**（→ **算失败**）。当前只有前者，加了 `needs` 后必须有后者。
  4. **有界并发**：`--jobs N`（默认 1 保持现状；可设 4）。理由沿用 ds：
     多个断言各自建大对象时，无上限并发在大机器上是"拿墙钟换内存爆炸"。
  5. **`streamOutput`**：长断言实时透传而非完成后缓冲（本次 `_bash_lint_parallel` 已是并行，
     可接此标志）。
- **不做（明确标注 N/A）**：ds 的 GitHub 专属部分 —— **required-check fan-in 与 `if: always()`**
  在本机群**无对应物**（本机群无 CI 分支保护；已有唯一入口 `rpc.ps1 check`）。
  ⇒ **原编号 22 的可映射部分以上 3/4/5 三条已覆盖，其余记 N/A，不假装做**。
- **落点**：`ops/rpc_check.py`（调度器 + `CHECKS` 字段）+ `tests/`（新增调度器单测）
- **验证**：
  - 单测：重复 id / 未知 id / 依赖环 / 级联 skip 四类**各注入一次看变红**
  - `rpc_check --quick` 仍 **11 绿**；报数**逐项与改造前一致**
- **风险**：低（纯新增字段 + 校验）。**回滚**：还原 `rpc_check.py` + 删新测试。

#### P0-2 豁免白名单"未命中自报"（防腐化）

- **现状（E1）**：`doclinks` 已有 **"已登记例外 2"**（`DOCLINK_ALLOW`），
  **但豁免项失效后不会被告知** ⇒ 清单会长期腐化（豁免留着、实际已不需要）。
- **做什么**：豁免项**未被命中时自报 WARN**（不是 FAIL），提示"该豁免已可移除"。
  ds 的做法（`--exemptions` + **未命中自报 P2**）与本仓"**登记这个动作本身要在 review 里可见**"
  （ADR-0004 D2 的既有纪律）同源。
- **⚠ 合并说明**：原编号 **4 与 25 是同一件事**（都指"未命中自报"）⇒ **合并为一批**，
  只做一次。
- **落点**：`ops/rpc_check.py`（各 `*_ALLOW` 的命中统计）
- **验证**：**先验红** —— 临时移除一个真实命中、留一个假豁免 ⇒ 应报"未命中"WARN；还原 ⇒ 0。
- **风险**：低。**回滚**：还原判据。

#### P1-1 定义"生成物"清单 + `--check` 模式

- **现状（E1）**：本仓有一批"**由某处推导出来的清单**"，但目前**没有"生成物"这个概念**：
  - `inventory/ops.yaml`（脚本登记表，由 `ops/` 目录扫描推导 → 门禁 `scripts` 报"扫描 217 个脚本 · 未登记 0"）
  - 手册 §2.2 的模型/路由表（由 `agent-cli.ps1` 的 `ROUTE_TABLE`/`MODELS` 推导）
  - `inventory/models.yaml` / `ports.yaml` / `plugins.yaml`（真值表）
- **做什么**：
  1. 显式列出**生成物清单**（哪些文件的权威源在别处）。
  2. 给每类加 **`--check` 等价物**：**重算 → 与磁盘比对 → 不一致即 FAIL**（而非靠人记得重跑）。
  3. **纪律入册**：生成物类文件**禁止手工编辑**，一律"改源头 → 重跑 → 跑 `--check`"。
  4. **★ 明确写出"编译/语法通过 ≠ 接线完整"**（ds 原文：`typecheck` 链不含任何生成器）——
     这正是本会话 `inventory` 报数掉到 0 仍 PASS 的同类问题的正面表述。
- **落点**：`inventory/`（新增生成物清单）+ `ops/rpc_check.py`（各 `--check`）+ 手册 §1.3
- **验证**：**先验红** —— 手工改一处生成物（如 `ops.yaml` 某计数）⇒ `--check` 应 FAIL；重跑生成 ⇒ PASS。
- **风险**：中（要先把"权威源在哪"逐项定清，定错会把好数据判成坏）。
  **回滚**：`--check` 默认关闭或降为 WARN。

#### P1-2 事实源 ↔ 镜像 一致性检查

- **现状（E1）**：`inventory` 断言已在做**对账**（"声明源 6 端口 / 3 模型标识 · 真值表 30 端口 / 26 模型键 · 未登记 0/0"）

  - `JUDGE_TABLE`（`agent-cli.ps1`）↔ 手册 §1.3 的判官行
- **落点**：`ops/rpc_check.py`（新增"一致性"类断言，或并入 `inventory`）
- **验证**：**先验红** —— 改手册某一格数字 ⇒ 断言 FAIL 并点名；还原 ⇒ PASS。
- **风险**：中（若把"历史记档"当"镜像"会误报 ⇒ **必须先区分"指向未来的指令"与"记录当时事实"**，

### D6-P3 输出层与隔离

#### P3-1 中文对齐（**已实测出真 bug**）

- **现状（E1 实证，本轮新发现）**：
  - `ops/cluster.py` 的 `inbox` 输出用 `f"  {name:<30} {st:<26} {ts}"`（第 4489-4491 行）
  - `ops/rpc_check.py` 的输出用 `{cid:10s} {title:16s}`（第 2580 行）
  - **Python 的 `ljust`/格式宽度数的是「码点」而非「显示列」** ⇒ 含中文时**必然错位**
    （例：`明文扫描` 4 码点 = 8 显示列，`{title:16s}` 会多补 12 空格而非 8）。
- **做什么**（取 ds 三条硬规则中**适用的两条半**）：
  1. **定"歧义宽度按 1 还是 2"并全局统一**（ds 取 `ambiguousIsNarrow: true` = 按 1 列）。
  2. **宽字符截断/填充处理"边界放不下一个双宽字符"**（对填充即"不能补半个字"）。
  3. **零宽组合标记跟随前字符**（本项目中文为主，此项优先级最低）。
  - **⚠ 适用范围**：本机群**没有 TUI**，唯一相关的是**控制台表格对齐**（`rpc_check` / `cluster.py inbox`）。
    看板是 HTML/CSS ⇒ **浏览器负责宽度，不受此影响** ⇒ **原编号 27 的适用范围要收窄**。
- **落点**：新增共用工具（如 `ops/_console.py` 的 `pad_display()`）+ 上述两处改用它
- **验证**：**先验红** —— 写一条含中文/emoji 的用例，旧 `ljust` 的对齐断言**必须失败**，新函数通过。
- **风险**：低。**回滚**：还原两处格式化。
- **⚠ 需裁定**：是否值得为此加一个共用工具（还是**直接改这两处、不留抽象**）——
  本仓纪律「不要创建只被引用一次的小 helper」（ds `AGENTS.md`），但这里**有两处引用** ⇒ 建工具是合理的。

#### P3-2 出站 / 隔离加固（**先评估适用性，再决定做不做**）

- **现状（E1）**：本仓出站由 **`egress` 平面**管（门禁 `impact` 有 4 配置 / 28 consumer；
  `local-only` 硬门 `egress → REJECT exit 4`）。**没有**网络代理或防火墙层。
- **ds 的三条可借鉴**：
  1. **`deny` 优先用枚举序编码**（`None < Allow < Deny`，靠类型而非散落 if）
  2. **阻断用 `REJECT` 而非静默丢弃**（"让策略失败可见"）
  3. **策略脚本末尾正反用例自验证**（断言"该通的通、该断的断"，**任一不符即非零退出**）
- **⚠ 适用性评估（必须先做，不可直接照搬）**：
  - 本机群**没有** ds 那种"容器内不可信代码"场景（三站是裸机 SSH + 受控 CLI），
    **上代理/防火墙层可能是过度设计**。
  - 真正可映射的是 **③ 的正反用例自验证** —— 这**正是本仓"先验红"的同一条**，
    可直接用来加强 `egress` 断言本身（例如：断言"未发表语料出站必被拒"）。
- **建议**：**只做 ③**（给现有 `egress` 断言补正反用例）；① ② 记 N/A 并说明理由。
- **验证**：**先验红** —— 构造一个"应当被拒但被放行"的出站样本 ⇒ 断言必须 FAIL。
- **风险**：低（只加测试）。**回滚**：删测试。
