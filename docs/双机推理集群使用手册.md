## 2. 快速开始 (主控站日常使用)

### 2.1 统一入口 (推荐)

```powershell
# ── 主力: nemotron (经 LiteLLM 网关, 2026-09-01 双端点架构) ──
# 1. 取 key (只在本机读, 别写进脚本硬编码)
$key = (Get-Content d:\RPC\secrets\litellm_master.key -Raw).Trim()

# 2. 确认模型已加载 (B 站)
ssh scott-lau@scott-lau-GTR-Pro.local "infer-list"

# 3. 若未加载, 加载 (B 站单机 ~2min; conf RPC_TARGET 已置空, 不再走双机 RPC)
ssh scott-lau@scott-lau-GTR-Pro.local "infer-load nvidia-nemotron-3-super"

# 3b. 速度档 gpt-oss (A 站独立端点, 与 nemotron 可同时服务):
ssh scott-lau@scott-lau-NEX.local "infer-load gpt-oss-120b"

# 4. 调用 (与 OpenAI API 完全兼容; model 名 = 路由名)
$r = Invoke-RestMethod -Uri "http://scott-lau-GTR-Pro.local:4000/v1/chat/completions" `
  -Headers @{ Authorization = "Bearer $key" } `
  -ContentType 'application/json' `
  -Body '{"model":"nemotron","messages":[{"role":"user","content":"你好"}],"max_tokens":256}'
$r.choices[0].message.content

# 直连备选 (无需 key): http://scott-lau-GTR-Pro.local:8080/v1/chat/completions
#   model 名填实际加载的别名 (llama.cpp 不校验 model 名)
```

### 2.2 模型名路由语义 (LiteLLM, 2026-09-01 20:30 双端点换防后已验证)

| 模型名        | 实际路径                                     | 何时用                                                                                                        |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `nemotron` | B 站 llama.cpp :8080 (回环)                 | **主力** — nvidia-nemotron-3-super-120b-a12b (1M ctx, 96.5k needle 5/5, prefill 158 t/s, 单机 decode 20.9 t/s) |
| `gpt-oss`  | **A 站** llama.cpp 10.10.10.1:8080 (USB4) | **速度档** — gpt-oss-120b MXFP4 (A 站单机, decode 58-64 t/s 冠军)                                                  |

**双端点说明**: 两路由指向不同物理站, **可同时服务** (各站内仍 GTT 互斥)。模型名=实际模型, 无需换档切换。切 deepseek 145G 等超 65G 单机墙模型时才回 RPC 模式 (改 conf `RPC_TARGET=auto` + A 站起 rpc-server, \~5min)。**E2E 已验证** (两路由并行调用均正确生成; claudecode/opencode 双 agent CLI 也已接通)。

**网关容错 (D1, 2026-09-02 起)**: config.yaml 已配 `fallbacks` 双向互备 (nemotron↔gpt-oss) + `rpm: 30` 限流 + `routing_strategy: usage-based-routing-v2` (rpm 拦截的前提, 见 [参数台账 §1.7](../spec/infer-load/params-ledger.md))。实际行为:

- 主模型连接失败/超时/5xx → 自动 fallback 到对端路由 (A4 实测: kill 主力进程后 1 次重试内降级成功)

- rpm 超限请求**不返回 429**, 而是被网关按 `retry-after: 60s` 延迟重试背压 (新分钟窗口计数归零后 200) — 客户端表现为请求变慢而非报错 (A6 实测两轮复现)

- **已知边界**: nemotron (ctx 128k) → gpt-oss (ctx 32k) 降级时, 超 32k 的长上下文请求会**报错非截断** — 长上下文任务勿依赖 fallback, 需直连主力端点

> 旧路由 `minimax-m2` / `minimax-m2-long` 已删 (模型全删); config 备份 `/home/scott-lau/litellm/config.yaml.bak.minimax-20260901`。vLLM :8081 路径已退役。
>
> 注: 空/错 key 请求会返回 500 (而非干净 401) — litellm auth 错误处理器引用未安装的 prisma 模块 (无 DB 部署的装饰性旧问题, 不影响正确 key 路径)。

## 3. 模型加载层 (infer-\* CLI, 两站均有)

### 3.1 三条命令

```bash
# B 站执行 (ssh scott-lau@scott-lau-GTR-Pro.local)
# A 站执行 (ssh scott-lau@scott-lau-NEX.local)  — 2026-09-01 起框架已双站部署

infer-list                    # 扫描本站全部模型: alias/位置/大小/建议后端/conf 状态
                              #  "位置"列: AB=两站均有 A-only=仅A站 B=仅B站

infer-load <前缀>             # 加载 (前缀唯一匹配即可)
  # 例: B 站 infer-load nvidia-nemotron-3-super  → B 站单机 (conf RPC_TARGET 已置空)
  #     A 站 infer-load gpt-oss-120b             → A 站单机端点 :8080
  # 歧义时用 $ 锚定: infer-load "gpt-oss-120b$"   (grep 正则匹配)

infer-unload                  # 卸载当前实例 (两站 llama + vLLM), 等 GTT 回收后完成
                              # (B 站执行会同时停 A 站 rpc-server)
```

**加载的模型路径**（`infer-load` 实际读取的权重文件）：

| 层              | 路径                                                | 说明                                                                                   |
| -------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **conf**       | `/etc/llama-instances/<alias>.env`                | 首次 `infer-load` 自动生成; 含 `MODEL_PATH`/`PORT`/`CTX`/`RPC_TARGET`/`EXTRA_FLAGS`         |
| **权重文件**       | `MODEL_PATH` 指向 `/data/models/.../*.gguf`（B 站）等实体 | `llama-serve-instance` wrapper 读 conf 拼 args 后 `exec /opt/llama.cpp/llama-server`    |
| **A 站 RPC 缓存** | 由 conf 的 alias 自动同步, 缓存于 `/data/rpccache/<alias>` | 张量 blob, 非 GGUF; 作用是下次加载跳过网络推送                                                       |
| **引擎**         | `/opt/llama.cpp/llama-server`                     | symlink → 当前版本 (master 0.3.0-dev); 回滚 `sudo ln -sfn llama.cpp-v0.2.0 /opt/llama.cpp` |

### 3.4 长上下文扩展 (YaRN → 1M, 仅需长文时启用)

**背景**: `qwen3.8-flash-next` 原生上下文 **256K (262,144)**（架构 `qwen4exp`, 36 GDN + 12 QSA 稀疏注意力）；Qwen 官方支持 YaRN 扩展至 **1M**。**静态 YaRN 会损害短文本生成质量, 只在真需要 >256K 时开**, 日常 32K 一律用默认 conf。

```bash
# 调参 (B 站, 改 conf 的 EXTRA_FLAGS 后 restart):
sudo vi /etc/llama-instances/qwen3.8-flash-next.env
# EXTRA_FLAGS 追加 (对比默认只加长文相关项):
EXTRA_FLAGS="-fa on --ctx-size 1048576 --rope-scaling yarn --yarn-orig-ctx 262144 --rope-scale 4.0 -ctk q8_0 -ctv q8_0"
sudo systemctl restart llama-server@qwen3.8-flash-next
```

- 参数来源 (排幻觉审计修正 2026-08-31): `factor=4.0, original_max_position_embeddings=262144` 来自 **Qwen3.8-Flash-Next-FP8 的 vLLM recipe** (社区全攻略引 vLLM recipe); **Qwen 官方未直接给 qwen4exp 的 llama.cpp YaRN config**, llama.cpp 路径 `--rope-scale 4.0` = 目标/原始 (1M/256K) 为推断, 需实测换算 — 若典型负载 \~512K 用 `2.0`

- **KV 内存纠正**: QSA 是**稀疏有界缓存** (`indexer_top_k=2048` + compress ratio, ll.cpp#27742 "optional third cache in llama\_memory\_hybrid"), **KV 不随 ctx 全量线性增长** (这正是 Qwen4 稀疏注意力的卖点); 12 层全量 \~24G\@1M 只是**最坏上界非真实分配**, 实际看引擎 memory\_hybrid 实现 — 须 `-c 1M` 启动日志实测

- 内存: N-gram 表 \~97.7G 走 host mmap (不占 GTT); QSA 稀疏缓存 + 36 GDN 固定态 → KV 非全量; 权重 103G 经 RPC 分载 A/B — **双机 128G 可行性高于初判, 以启动日志 KV 分配为准**

> **⚠ 结论 (2026-08-31 实测裁决, 取代原"待验证")**: ① **YaRN 对 qwen4exp 不生效** — qwen4exp 走 `ggml_rope_multi IMRoPE` 专用路径, `--yarn-*` 未被消费, 任意 `-c > 262144` 被 llama.cpp 强制 cap 回 `n_ctx_train` (实测 journal: `slot context exceeds training context - capping`). **当前 llama.cpp 构建无法对 qwen4exp 扩展超 256K**; ② 原生 262144 已验证可用, KV 增量小 (QSA 稀疏, 无全量线性增长); ③ ll.cpp #28012: decode 随 ctx 线性退化 (176K 约 122ms/token). **1M 唯一可达路径 = vLLM (Flash-Next FP8 recipe factor=4.0), 或等 llama.cpp 接入 qwen4exp IMRoPE yarn.**

**若引擎修复后复测**: `-c 262144` 原生基线 → `-c 524288` 看 KV/内存 → `-c 1048576` 确认装下 + needle 长文对答 → 失败回退默认 conf。

| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |

**结论 (ROCm vs Vulkan, 2026-09-03)**:

1. **算子完备性: ROCm 完胜**——Lightning Indexer/HC 融合/top-k 三项 Vulkan 等待中的问题在 HIP 侧全部已有; DeepSeek 慢因 (HC 非融合 32%) 在 ROCm 下大概率直接消失
2. **但切换成本被三重锁定**: ① 内核纪律 (6.17 锁定 vs 社区要求 ≥6.18.4); ② 全集群基线重测 (nemotron 锚点/bench/质量门全链); ③ Strix Halo 最优 ROCm 优化包 #27233 本身未合入主线 (拆分中)
3. **定案**: 维持 Vulkan 现役 + 小升级窗口 (收 #27453+#28032) 路线不变; **ROCm 列为 D7+ 大窗口候选**——若升级到 #26610 协议时同步评估切 ROCm (一次性重测成本与两后端长期收益摊平); #27233 拆分 PR 进每周跟踪清单
