## CR-2（P1）抽检判官资源与落点（避免与蒸馏泳道争用）

| 项 | 内容 |
|---|---|
| **诉求** | 确认 `agent-cli review --peer` 的**执行体落在哪一档资源**，以及是否与蒸馏泳道争用同一引擎 |
| **证据** | ① `JUDGE_TABLE` 中 `main`（`type='local'`）与 `m27`/`rpc-v4flash`（`type='http-local'`，C 站）**均需落到某站引擎**<br>② 手册实测约束：「**勿在同站内叠开并发任务**——统一内存带宽顶起，单请求恶化 ~2.8×（BS-2 L1 实测 1.7→4.8s）」<br>③ 我的 3 泳道已占满 A/B/C 三站，**无空闲站** |
| **影响** | 判官启动会拖慢同站蒸馏泳道 → 全量墙钟上升；若不加协调，抽检与蒸馏会互相干扰 |
| **期望** | ① 明确 `review --peer` 的判官可用档与落点；<br>② 若无独立资源，给出推荐做法（例如"判官串行于泳道空闲窗口"或"固定用主控侧判官与三泳道解耦"） |
| **验收判据** | 抽检期间蒸馏泳道单篇耗时劣化 **<20%** |
| **备注** | 抽样量约 5% + 全部 SUSPECT（估 200–400 次评审），分摊到 20 天，密度不高，**串行窗口是可行的** |

| **证据 / 我的关切** | ① 我全程需**一站一档常驻**（`nemotron` 或 `gpt-oss`，CTX 131072），且手册方针为「**零自加载**」——即引擎不会自启，**每次断掉都需人工 `infer-load`**<br>② 站上 `cluster-ttl` 空闲自动卸载**默认关闭**（三层闸门），若被开启会在我队列间隙误卸 → 我需要确认它保持关闭<br>③ C 站**不纳入看门狗**（硬规则），其引擎为**手动进程** → 异常挂掉不会被自动拉起<br>④ A 站有历史挂死族（已定案为 bjork cron 干扰，已删）；2468 篇 × 20 天对稳定性是新压力 |

| **验收判据** | 连续运行期间，泳道因引擎原因的中断次数与恢复时延有明确记录；中断可被我在台账中识别（而非静默超时） |
| **备注** | 我会用 `cluster.py agent live` / `reqlog` 观测新鲜度，并在连续 N 次超时时**主动上报**而非盲目重试 |
